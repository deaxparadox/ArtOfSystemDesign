## 1. What Is It? (Theory)

### Plain English

Database replication is the practice of keeping **multiple synchronized copies of the same data on different machines** so that if one machine dies, another can take over — and so that multiple machines can serve reads simultaneously.

Without replication you have a single database node. That is fine until:
- The machine crashes and your entire service is down while you restore from a backup (can be hours)
- Your read load exceeds what one machine can handle
- Your users in Tokyo are hitting a database in Virginia with 150 ms of latency on every query
- A planned maintenance window requires downtime

Replication solves all four problems simultaneously. The cost is complexity — you now have multiple copies of data that must stay in sync, and anything that touches network synchronization eventually has to answer the question: *what happens when two nodes disagree?*

### The Core Problem: Replication Lag

Every replication system must answer: **after a write lands on one node, how quickly does it appear on all other nodes?** The time between "write committed on primary" and "write visible on replica" is called **replication lag**. Under moderate load in the same data center, PostgreSQL streaming replication lag is typically **5–50 ms**. Under heavy write load or across regions it can be **seconds to minutes**.

### Real-World Analogy

Think of a Google Doc shared between three people. When you type a character, Google's servers decide: do they hold your keypress until all three synced copies confirm they have it (synchronous — zero data loss, slower)? Or do they confirm your keypress immediately and sync the other copies in the background (asynchronous — faster, but if Google's servers die in the next 50 ms, those other copies might miss the keystroke)?

That is, precisely, the leader-follower vs. synchronous-vs-asynchronous replication decision.

### Why Three Models Exist

The three replication topologies emerged because no single model is optimal for all workloads:

| Driver | Forces You Toward |
|---|---|
| Need simple strong consistency | Leader-Follower (single leader) |
| Need writes to be fast/local in multiple DCs | Multi-Leader |
| Need maximum availability, no single point of failure | Leaderless |

### Concrete Numbers to Ground the Discussion

A single PostgreSQL primary on a `db.r6g.2xlarge` (AWS RDS) can handle roughly **5,000–8,000 write TPS** and **15,000–25,000 read TPS**. Once you add 2-3 read replicas, your effective read capacity scales to **45,000–75,000 read TPS** — a 3x improvement for reads with no change to write capacity. Stripe reported 5 million database queries/second across their DocDB cluster, which is a MongoDB replica-set topology (leader-follower per shard) with thousands of shards.

## 2. How It Actually Works (Deep Mechanics)

### 2.1 Leader-Follower (Single-Leader) Replication

**Step-by-step mechanics:**

1. Client sends a `WRITE` (INSERT/UPDATE/DELETE) to the **leader** (also called primary or master).
2. Leader executes the write and appends it to its **Write-Ahead Log (WAL)** or **binary log (binlog)**.
3. Leader streams the log entry to each follower (replica/standby) over a persistent TCP connection.
4. Follower applies the log entry to its own local copy.
5. Client sends `READ` queries to any node — either the leader or any follower.

```
                        WRITES ONLY
                            │
                            ▼
                     ┌─────────────┐
                     │   LEADER    │  ── WAL / binlog ──►
                     │  (primary)  │
                     └──────┬──────┘
                            │ WAL stream
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
       ┌──────────┐  ┌──────────┐  ┌──────────┐
       │FOLLOWER 1│  │FOLLOWER 2│  │FOLLOWER 3│
       │(replica) │  │(replica) │  │(replica) │
       └──────────┘  └──────────┘  └──────────┘
              ▲             ▲             ▲
              └─────────────┴─────────────┘
                        READS
```

**Synchronous vs. Asynchronous replication:**

- **Asynchronous (default):** Leader confirms the write to the client before followers acknowledge. RPO = seconds to minutes in worst case. Write latency impact = ~0 ms added. **Most common in production.**
- **Synchronous:** Leader waits for at least one follower to confirm before returning to client. RPO = 0 (zero data loss). Write latency impact = +1–5 ms same-DC, +50–150 ms cross-region. **Use for financial data only.**
- **Semi-synchronous (MySQL term):** Leader waits for exactly one follower, then proceeds. A middle ground.

**PostgreSQL WAL shipping specifics:**

PostgreSQL sends WAL segments (default 16 MB each) or streams changes in real-time via the `walsender` process. The follower's `walreceiver` process writes incoming WAL and the `startup` process replays it. `synchronous_commit` has five levels:

| Level | What It Waits For | Durability | Latency Added |
|---|---|---|---|
| `off` | Nothing — fire and forget | Low | 0 ms |
| `local` | Local disk write | Medium | 0 ms (async) |
| `remote_write` | WAL written to standby memory | High | +RTT/2 |
| `on` (default) | WAL flushed to standby disk | Very high | +RTT |
| `remote_apply` | WAL replayed on standby | Maximum | +RTT + replay time |

**MySQL binlog replication specifics:**

MySQL uses a separate binary log (binlog) in one of three formats:
- **Statement-based (SBR):** Logs the SQL statement. Compact but non-deterministic functions like `NOW()` can cause divergence.
- **Row-based (RBR):** Logs the actual row change. Larger log size but deterministic. Default in MySQL 8.0.
- **Mixed:** Switches between the two based on statement type.

### 2.2 Multi-Leader Replication

Multi-leader (also: multi-master, active-active) allows writes on more than one node. Changes are asynchronously replicated between leaders.

**Step-by-step mechanics:**

1. Client sends a `WRITE` to **any leader** (typically the geographically nearest one).
2. That leader executes locally and queues the change for replication to all other leaders.
3. Each receiving leader applies the change — but must handle **conflicts** if two leaders modified the same row concurrently.
4. Conflict resolution runs (see below) and the winning value is applied everywhere.

```
        DC-US-EAST                     DC-EU-WEST
       ┌──────────┐                   ┌──────────┐
  ──►  │ LEADER A │ ◄── async sync ──► │ LEADER B │  ◄──
       └────┬─────┘                   └─────┬────┘
            │ WAL                           │ WAL
      ┌─────┴──────┐                  ┌─────┴──────┐
      │  Replica   │                  │  Replica   │
      └────────────┘                  └────────────┘

  User in NYC writes user.name = "Alice"
  User in London writes user.name = "Bob"
  at the same time → CONFLICT
```

**Conflict resolution strategies:**

- **Last-Write-Wins (LWW):** Attach a timestamp to each write. Higher timestamp wins. Problem: clock skew between servers means this can silently drop data. Used by Cassandra by default.
- **First-Write-Wins:** Keep the first version, reject later conflicting writes. Lower data loss risk but can frustrate users.
- **Custom application logic:** Expose the conflict to the application layer to resolve. Most correct but expensive to implement.
- **CRDT (Conflict-Free Replicated Data Types):** Data structures (counters, sets, maps) that have mathematically defined merge functions. No conflict possible by definition. Used in Riak, Redis cluster. Works only for specific data types.
- **Operational transformation / Version vectors:** Track causal history so the merge algorithm knows which values are truly concurrent vs. causally ordered. Used in collaborative editing systems.

---

### 2.3 Leaderless Replication (Dynamo-style)

Pioneered by Amazon Dynamo (2007), leaderless replication removes the concept of a primary entirely. Any node can accept reads and writes.

**Step-by-step mechanics:**

1. Client sends a `WRITE` to **W nodes** simultaneously (out of N total replicas).
2. Once W nodes acknowledge, the write is considered successful.
3. Client sends a `READ` to **R nodes** simultaneously.
4. Client takes the most recent value (by timestamp or version vector) from the R responses.
5. **Read repair:** If R nodes return different values, the node with the stale value is updated in the background.
6. **Hinted handoff:** If a target node is temporarily down during a write, another node stores the write temporarily and forwards it when the target recovers.

```
     Client
       │
  ┌────┴─────────┐
  ▼     ▼        ▼
Node1  Node2   Node3   (N=3 total replicas)
  ▼     ▼
  ACK   ACK            (W=2 writes, success)

  Read: ask Node1, Node2, Node3 (R=3)
  Node1: version 5
  Node2: version 5
  Node3: version 4  ← stale → read repair triggered
```

**Quorum math:** For consistency, you need `W + R > N`.

| N | W | R | Guarantee |
|---|---|---|---|
| 3 | 2 | 2 | Strong consistency (quorum overlap guaranteed) |
| 3 | 1 | 3 | Fast writes, reads always consistent |
| 3 | 3 | 1 | Fast reads, writes are slower |
| 3 | 1 | 1 | Maximum availability, eventual consistency only |
| 5 | 3 | 3 | Tolerates 2 node failures on either side |

**Sloppy quorum:** Instead of strictly requiring W of the N designated nodes to be up, allow any W nodes in the cluster to accept the write (with a "hint" to forward when the target recovers). Increases availability at the cost of even weaker consistency guarantees.

---

### 2.4 Key Misconceptions

**❌ Misconception:** Replicas are always consistent with the leader — reads are always fresh.
**✅ Reality:** In asynchronous replication (the default), replicas can lag by milliseconds to minutes. A read from a replica can return data that was already overwritten on the leader. This is called **stale reads** or **read-your-own-writes violation**.

**❌ Misconception:** Synchronous replication makes the system safe because you always have two copies.
**✅ Reality:** With only one synchronous follower and the follower goes down, the leader must either block all writes (if configured strictly) or fall back to async — giving you no protection at the worst possible time.

**❌ Misconception:** Leaderless replication with W+R>N guarantees linearizability.
**✅ Reality:** It does not. Clock skew, concurrent writes to different node sets, and the mechanics of how "latest" is determined (LWW by timestamp) can all produce non-linearizable results. This is a well-known limitation of the Dynamo paper.

**❌ Misconception:** Multi-leader replication is just leader-follower with two leaders.
**✅ Reality:** It's fundamentally different because you must solve write conflicts, which leader-follower avoids entirely by routing all writes through one node. The conflict-resolution logic is non-trivial and buggy implementations regularly cause silent data loss.

## 3. Real-World Architecture Examples

### 3.1 Discord — Cassandra (Leaderless) to ScyllaDB Migration

**Context:** Discord stores trillions of messages. In 2017 they migrated from MongoDB to Apache Cassandra because they needed a write-scalable, fault-tolerant store. Cassandra's leaderless, ring-based replication looked ideal.

**What they got wrong first:**
- Cassandra compactions (merging SSTables to reclaim space) were falling behind under load. When compactions lag, read amplification increases dramatically — reads had to scan multiple overlapping SSTables.
- JVM garbage collection pauses (50–200 ms GC stop-the-world events) caused latency spikes that propagated to user-visible errors.
- The "gossip dance" — taking nodes out of the ring one at a time to force compactions — required manual weekend operations work just to keep up.

**Scale that triggered the decision:**
- ~100 nodes in the Cassandra cluster, multiple data centers
- Billions of messages per day at peak

**What they actually did:**
- Migrated to ScyllaDB — a Cassandra-compatible database written in C++ rather than Java. Same Cassandra Query Language (CQL), same token-ring leaderless replication model, but:
  - No JVM, so no GC pauses
  - Per-core shard architecture (each CPU core owns its own data and I/O) → better workload isolation
  - Faster compactions built into the storage engine

**Result:** Discord reduced their node count by approximately 75% for equivalent workload after migrating, with significantly lower tail latency p99.

**Reference:** [Discord Blog — How Discord Stores Trillions of Messages](https://discord.com/blog/how-discord-stores-trillions-of-messages)

---

### 3.2 Stripe — DocDB Leader-Follower Sharded Architecture

**Context:** Stripe processes over $1 trillion in annual payment volume and requires five-nines (99.999%) availability. They built DocDB, an internal database-as-a-service (DBaaS) on top of MongoDB's community edition.

**Architecture decisions:**
- Each DocDB shard is a MongoDB **replica set** — one primary (leader), multiple secondaries (followers) across availability zones and regions. Classic leader-follower per shard.
- Shards are distributed across DCs so that writes to any given customer's data go to a geographically appropriate shard.
- **Change Data Capture (CDC) via Oplog:** Each shard's MongoDB Oplog (the WAL equivalent) is streamed into Kafka, then a replication service consumes those events for cross-shard and cross-region data movement.

**What they got wrong first:**
- Early on, under-provisioned shards caused replication lag during peak traffic. A lagging secondary that got promoted to primary (after a failover) was not fully caught up, causing brief periods of stale reads post-failover.
- Managing thousands of shards individually was unscalable — they built a DBaaS platform so developers don't touch individual shard topology.

**Scale numbers:**
- 5 million database queries per second
- 1.5 petabytes migrated across shards in 2023 using their Data Movement Platform
- Cluster consolidation reduced total shard count by ~75% in 2023 while increasing utilization

**Reference:** [Stripe Dev Blog — Zero-Downtime Data Migrations](https://stripe.dev/blog/how-stripes-document-databases-supported-99.999-uptime-with-zero-downtime-data-migrations)

---

### 3.3 Netflix — Cassandra Multi-Region Active-Active (Leaderless)

**Context:** Netflix runs in 4 AWS regions simultaneously. Every user's viewing history, recommendations, and preferences must be readable from any region with low latency and survive a full regional outage.

**Architecture decisions:**
- Apache Cassandra with RF=3 per region, replicated to all 4 regions asynchronously → effective RF=12 globally.
- Leaderless model means any region can accept both reads and writes — Netflix enforces **strict region autonomy** (no synchronous cross-region calls at the application layer).
- Consistency level: `LOCAL_QUORUM` for both reads and writes — quorum is met within the local region, not globally. This means reads are fast (single-digit millisecond in-region) but cross-region consistency is eventual.

**Validation experiment Netflix ran:**
They wrote 1 million records in one region, then read 500 ms later from another region under production-level load. All records were successfully readable. This gave them confidence in Cassandra's replication speed for their specific use case.

**What they got wrong first (and fixed):**
- Memcached (EvCache) doesn't support multi-master replication natively. Netflix solved this by adding cross-region cache invalidation: writes in one region send SQS messages to other regions to invalidate cache entries, forcing those regions to re-read from Cassandra on the next request.
- Cross-region writes via Cassandra's built-in async replication occasionally caused a user in Europe to see an older playlist version for 200–500 ms after a US write. Acceptable for Netflix's use case.

**Reference:** [Netflix TechBlog — Active-Active for Multi-Regional Resiliency](https://medium.com/netflix-techblog/active-active-for-multi-regional-resiliency-c47719f6685b)

---

### 3.4 Uber — Schemaless Multi-DC Replication (Custom Leader-Follower on MySQL)

**Context:** Uber needed a globally distributed trip datastore that could write in each city's local DC and replicate to all other DCs. They built "Schemaless" on top of MySQL, then added "Herb" for multi-DC replication.

**Architecture:**
- Data is divided into 4096 fixed shards. Each shard is a MySQL replica set (1 master + 2 minions/followers), distributed across data centers.
- Herb is an async CDC-based replication engine that reads MySQL binlog from the shard master in one DC and replays it in other DCs.
- To handle MySQL async replication's data-loss window, Uber uses **buffered writes**: writes go to multiple clusters before being confirmed, minimizing the window of potential loss during failover.

**What they switched away from (and why):**
Uber famously published a blog post explaining why they migrated from PostgreSQL to MySQL. Key reasons relevant to replication:
- PostgreSQL's WAL-based replica promotion was more complex when they needed to rewind a diverged replica (they had to rebuild from scratch).
- MySQL's binlog-based replication provided better tooling (Orchestrator, pt-online-schema-change) for their at-scale operations.

**Reference:** [Uber Engineering — Herb: Multi-DC Replication Engine](https://eng.uber.com/herb-datacenter-replication/)

### 4.2 Design Questions to Ask Before Starting

1. **What is the acceptable RPO (Recovery Point Objective)?** — "How many seconds of data loss can you tolerate?" If the answer is zero, you need synchronous replication to at least one follower.
2. **What is the acceptable RTO (Recovery Time Objective)?** — "How fast must the database be back up?" This determines how many replicas you need and how automated your failover must be.
3. **What is the read:write ratio?** — High read ratio → many read replicas. High write ratio → replication won't help; consider sharding instead.
4. **Are any reads read-your-own-writes?** — "Does the user who just submitted a post need to immediately see it in their feed?" If yes, you must route those reads to the primary or implement sticky sessions.
5. **Do you need multi-DC or multi-region?** — Same-DC replication is simple. Cross-region adds 30–150 ms cross-region RTT to synchronous replication latency.
6. **Who handles failover?** — Manual (minutes of downtime), automated (seconds), or transparent (milliseconds with shared storage like Aurora)?

### 4.3 Scale Evolution

**1K users / ~10 writes/sec:**
- Single PostgreSQL instance. No replication needed. Backups to S3. Focus on getting the schema right.

**100K users / ~500 writes/sec:**
- Add one async read replica. Route analytics and reporting queries to it.
- RPO of a few seconds is acceptable.
- Use `pg_stat_replication` to monitor lag. Alert if lag > 30 seconds.

**1M users / ~5,000 writes/sec:**
- 2–3 read replicas. Connection pooling with PgBouncer (max 100–200 connections per Postgres node; PgBouncer multiplexes thousands of app connections into that).
- Add one **synchronous replica** in a separate AZ for RPO=0 on critical tables (user accounts, financial records).
- Implement read-your-own-writes logic: after a write, cache the written key for 5 seconds and route reads for that key to primary.
- Automated failover with Patroni or AWS RDS Multi-AZ.

**100M+ users / ~50,000+ writes/sec:**
- The write bottleneck is now real. Vertical scaling maxes out around 8,000–12,000 writes/sec on most hardware configurations.
- You **must** shard (partition) data (see Section 3.4). Each shard is independently replicated.
- Consider multi-region active-active (multi-leader or leaderless) for write distribution across regions.
- Replication monitoring becomes a first-class SRE concern: dashboards, alerting, runbooks for lag spikes.
- Netflix/Discord scale: Cassandra or ScyllaDB with leaderless replication, `LOCAL_QUORUM` consistency, 3–5 replicas per DC.

## 5. Code / Implementation Perspective

### 5.1 Python: Simulating Read-Your-Own-Writes with Connection Routing

```python
import time
import threading
from dataclasses import dataclass, field
from typing import Optional
import psycopg2
from psycopg2 import pool

@dataclass
class ReplicationRouter:
    """
    Routes DB reads to primary or replica based on replication-aware logic.
    Implements read-your-own-writes by tracking recent writes per user.
    """
    primary_dsn: str
    replica_dsns: list[str]
    replication_lag_buffer_sec: float = 2.0  # conservative lag buffer

    _primary_pool: pool.ThreadedConnectionPool = field(init=False)
    _replica_pools: list[pool.ThreadedConnectionPool] = field(init=False)
    _recent_writes: dict[str, float] = field(default_factory=dict)  # user_id -> write_timestamp
    _lock: threading.Lock = field(default_factory=threading.Lock)
    _replica_index: int = 0  # round-robin counter

    def __post_init__(self):
        self._primary_pool = pool.ThreadedConnectionPool(
            minconn=2, maxconn=20, dsn=self.primary_dsn
        )
        self._replica_pools = [
            pool.ThreadedConnectionPool(minconn=2, maxconn=20, dsn=dsn)
            for dsn in self.replica_dsns
        ]

    def record_write(self, user_id: str) -> None:
        """Call this immediately after any write for this user."""
        with self._lock:
            self._recent_writes[user_id] = time.monotonic()

    def _wrote_recently(self, user_id: str) -> bool:
        with self._lock:
            last_write = self._recent_writes.get(user_id)
            if last_write is None:
                return False
            elapsed = time.monotonic() - last_write
            if elapsed > self.replication_lag_buffer_sec:
                del self._recent_writes[user_id]  # cleanup
                return False
            return True

    def get_connection(self, user_id: Optional[str] = None, write: bool = False):
        """
        Return a connection from the appropriate pool.
        - Writes always go to primary.
        - Reads go to replica UNLESS the user wrote recently (read-your-own-writes).
        """
        if write or (user_id and self._wrote_recently(user_id)):
            return self._primary_pool.getconn(), "primary"

        # Round-robin across replicas
        with self._lock:
            idx = self._replica_index % len(self._replica_pools)
            self._replica_index += 1
        return self._replica_pools[idx].getconn(), f"replica-{idx}"

    def execute_write(self, user_id: str, query: str, params=()) -> None:
        conn, source = self.get_connection(user_id=user_id, write=True)
        try:
            with conn.cursor() as cur:
                cur.execute(query, params)
                conn.commit()
            self.record_write(user_id)
        finally:
            self._primary_pool.putconn(conn)

    def execute_read(self, user_id: str, query: str, params=()) -> list:
        conn, source = self.get_connection(user_id=user_id, write=False)
        pool_to_return = (
            self._primary_pool if source == "primary"
            else self._replica_pools[int(source.split("-")[1])]
        )
        try:
            with conn.cursor() as cur:
                cur.execute(query, params)
                return cur.fetchall()
        finally:
            pool_to_return.putconn(conn)
```

### 5.2 PostgreSQL Replication Configuration

```sql
-- On primary: postgresql.conf
-- wal_level must be 'replica' or 'logical' for streaming replication
wal_level = replica
max_wal_senders = 10           -- max concurrent WAL streaming connections
wal_keep_size = 1024           -- keep 1GB of WAL for replicas to catch up
synchronous_standby_names = 'FIRST 1 (replica1)'  -- require 1 sync replica

-- On primary: pg_hba.conf
-- Allow replica to connect for replication
host replication replicator 10.0.1.0/24 scram-sha-256

-- Create replication user
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'secure_password';

-- On replica: recovery.conf (Postgres < 12) or postgresql.conf (Postgres >= 12)
primary_conninfo = 'host=10.0.1.10 port=5432 user=replicator password=secure_password'
primary_slot_name = 'replica1_slot'  -- replication slot prevents WAL deletion

-- Create replication slot on primary (prevents lag-driven WAL cleanup)
SELECT pg_create_physical_replication_slot('replica1_slot');

-- Monitor replication lag on primary
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    (sent_lsn - replay_lsn) AS replication_lag_bytes,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication;
```

### 5.3 Cassandra Keyspace with Replication Config (YAML/CQL)

```sql
-- Leaderless replication configuration in Cassandra
-- NetworkTopologyStrategy for multi-DC deployments

CREATE KEYSPACE social_media
WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'us-east-1': 3,    -- 3 replicas in US East
    'eu-west-1': 3,    -- 3 replicas in EU West
    'ap-southeast-1': 2  -- 2 replicas in Asia Pacific
}
AND durable_writes = true;

-- Query with LOCAL_QUORUM: fastest consistency (2 of 3 in local DC)
-- Use for most application reads/writes
CONSISTENCY LOCAL_QUORUM;
SELECT * FROM social_media.posts WHERE user_id = ? AND created_at > ?;

-- Query with QUORUM: requires majority globally — only for critical data
CONSISTENCY QUORUM;
INSERT INTO social_media.payments (id, amount, status) VALUES (?, ?, ?);
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Leader-Follower (Async)** | General purpose, read-heavy workloads, most web apps | RPO = seconds; stale reads on replicas; write bottleneck at leader | PostgreSQL users everywhere; MySQL; MongoDB |
| **Leader-Follower (Sync, 1 replica)** | Financial data, zero-data-loss requirement | Write latency +1–5 ms same DC, +50–150 ms cross-region; blocks if replica is down | Banking systems, payment processors |
| **Multi-Leader (2 DC active-active)** | Multi-region write performance, offline-capable apps | Conflict resolution complexity; potential silent data loss; very hard to debug | CouchDB, Google Docs, some gaming backends |
| **Leaderless (Cassandra/Dynamo)** | High write throughput, maximum availability, multi-DC active-active | Eventual consistency by default; complex to achieve strong consistency; no foreign keys | Netflix, Discord, Instagram (Cassandra), DynamoDB users |
| **Shared-Storage (Aurora)** | AWS-locked workloads needing fast failover and many read replicas | Vendor lock-in; single-region primary still; cost premium | Dropbox, Samsung, Dow Jones |
| **Distributed SQL (Spanner, CockroachDB)** | Global strong consistency, multi-region reads AND writes | High latency for cross-region writes (~100–200ms); significant cost premium | Mercado Libre (CockroachDB), Google internal (Spanner) |

### Opinionated Recommendation

**Start with Leader-Follower async.** It is what PostgreSQL, MySQL, and MongoDB do by default, it handles 95% of use cases, and the operational complexity is manageable. Add a synchronous replica only for tables that absolutely cannot tolerate data loss (think: financial ledger, user authentication tokens). Do not add multi-leader until you have a concrete write-scalability or multi-region latency problem that you have verified cannot be solved by sharding. Do not reach for leaderless until you need Cassandra/ScyllaDB scale (billions of writes per day) or true active-active multi-region writes. The conflict resolution complexity of multi-leader and the consistency caveats of leaderless are serious costs — do not pay them unless you have to.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Read scaling:** Add 2 replicas → ~2–3x read throughput. At 3 async replicas, a PostgreSQL cluster can handle 45,000–60,000 read QPS on a `db.r6g.2xlarge`, up from ~15,000 single-node.
- **High availability:** Leader-follower with automated failover achieves RTO of 30–60 seconds (RDS Multi-AZ). Aurora Global achieves RTO of ~1 minute for cross-region failover.
- **Geographic distribution:** Replicas in multiple regions put data physically closer to users. Cross-region latency drops from 100–200 ms (round-trip to a single region) to 1–5 ms (local replica read).
- **Operational safety:** A replica can be promoted for blue-green upgrades, schema migrations tested on the replica first, and analytics workloads isolated without impacting the primary.
- **RPO control:** With synchronous replication, RPO = 0. With async, RPO = seconds. You choose the tradeoff per-table.

### Costs & Limitations

- **Write bottleneck:** Replication does not help write throughput. All writes still go to one primary (in leader-follower). A heavily loaded primary at 8,000 writes/sec stays at 8,000 writes/sec no matter how many replicas you add.
- **Replication lag:** Under heavy write load, async replicas routinely fall 5–60 seconds behind. This is not hypothetical — at production scale, AWS RDS PostgreSQL replication lag regularly hits 30–60 seconds during write peaks. Aurora's shared storage reduces this to <100 ms.
- **Storage cost:** N replicas = N times the storage cost. At 10 TB of data, 3 replicas = 30 TB.
- **Failover risk:** Automated failover is not instantaneous. During the 30–60 second failover window, writes may fail or be queued. Applications must handle `Connection refused` gracefully with retries and exponential backoff.
- **Conflict complexity (multi-leader only):** Implementing correct conflict resolution is one of the hardest problems in distributed systems. Last-write-wins silently drops data. Custom resolution requires significant application code. CRDTs only work for specific data structures.
- **Consistency surprises (leaderless):** W+R>N does not give you linearizability. Concurrent writes to the same key handled by different node sets can result in non-intuitive orderings that cause subtle data corruption bugs that are very hard to reproduce.

### Core Tension

**Durability vs. Latency vs. Availability.** These three cannot all be maximized simultaneously. Synchronous replication maximizes durability but increases write latency and reduces availability (the leader blocks if the sync replica is down). Async maximizes performance and availability but risks data loss on failover. Every replication configuration is a point in this three-way trade-off space.

### My Recommendation

**For most production systems:** Leader-follower async replication with 2–3 read replicas. Use synchronous commit for your financial/critical tables only. Run Patroni (PostgreSQL) or Orchestrator (MySQL) for automated failover. Set `wal_keep_size = 1GB` to prevent replicas that fall behind from needing a full rebuild. Alert on replication lag > 30 seconds.

**For multi-region active-active:** Do not attempt multi-leader with a relational database unless you have a team of experienced distributed systems engineers. Instead, use Cassandra/ScyllaDB with `LOCAL_QUORUM`, accept eventual consistency, and design your application around idempotent operations and tombstone-based conflict resolution.

## 9. Failure Modes — What Goes Wrong

### 9.1 Replication Slot Bloat / WAL Accumulation

**Trigger:** A replica falls behind (due to hardware issues, a slow query, network partition) and cannot consume WAL fast enough. A replication slot holds a reference to the position in the WAL the replica last confirmed. The primary cannot delete WAL segments older than the slot's confirmed position.

**Symptoms:** Primary disk fills up with WAL files (`pg_wal/` directory grows rapidly, can consume hundreds of GB). Primary runs out of disk space and crashes. This takes down the entire primary — not just the replica.

**Detection:**
```sql
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;
-- Alert if lag > 5 GB
```

**Recovery:**
1. If the replica can catch up quickly, wait it out.
2. If not, drop the replication slot: `SELECT pg_drop_replication_slot('slot_name');`
3. The replica will need a full rebuild (pg_basebackup) once it reconnects.

**Real Example:** A 2024 post-mortem from a PostgreSQL SaaS company described a scenario where a replica running a long analytical query held back WAL consumption for 6 hours. By the time ops noticed, the primary had consumed all available disk space and crashed. The actual outage was caused by disk space exhaustion on the primary, not the replica issue.

---

### 9.2 Split-Brain After Failover

**Trigger:** The primary goes down. Automated failover promotes a replica to primary. The original primary recovers (it was actually just partitioned from the monitoring network, not crashed) and continues accepting writes. Now two nodes both believe they are the primary and are accepting writes independently.

**Symptoms:** Two divergent versions of the data exist. Applications connected to different endpoints are reading/writing different data. Clients may not notice immediately — both nodes respond normally.

**Detection:** Monitoring shows two nodes both reporting as primary. Replication lag on the "old primary" shows infinite or no connection to the new primary.

**Recovery:**
1. **STONITH (Shoot The Other Node In The Head):** The failover automation must fence the old primary immediately — either by shutting it down, revoking its network access, or forcing a reboot. This is why Patroni uses distributed lock mechanisms (etcd, Consul, ZooKeeper) — to prevent two nodes from simultaneously holding the primary lock.
2. If writes occurred on the old primary during the split-brain window, use `pg_rewind` (PostgreSQL) or `gh-mysql-rewind` (GitHub's open-source tool for MySQL) to identify and rewind the divergent writes.
3. Perform a full audit of transactions that occurred during the split-brain window. Depending on RPO requirements, some writes may need to be manually reconciled or discarded.

**Real Example:** GitHub documented exactly this scenario. A data center network isolation caused their monitoring to fail over MySQL to a second DC. The isolated DC's master kept accepting writes. When the partition healed, they had a split-brain with diverged writes in both DCs. GitHub open-sourced `gh-mysql-rewind` specifically to handle this recovery.

---

### 9.3 Replication Conflicts on Logical Replicas (PostgreSQL)

**Trigger:** In PostgreSQL logical replication, a conflict occurs when an incoming row from the publisher violates a constraint on the subscriber (primary key conflict, foreign key violation, NOT NULL violation). The logical replication worker enters an infinite retry loop by default.

**Symptoms:** The logical replication subscription stops applying changes. The `pg_stat_subscription_stats` shows increasing `skip_count` or errors. Applications reading from the subscriber return increasingly stale data.

**Detection:**
```sql
SELECT subname, received_lsn, latest_end_lsn, last_msg_receipt_time
FROM pg_stat_subscription;
-- If received_lsn is not advancing, there is a conflict
```

**Recovery:**
1. Identify the conflicting transaction: `SELECT * FROM pg_replication_origin_status;`
2. Manually skip the problematic transaction: `SELECT pg_replication_origin_advance('pg_16392', '<lsn>');`
3. PostgreSQL 15+ added `disable_on_error` subscription option to automatically pause (rather than infinite retry) on error, making detection and recovery more tractable.
4. In PostgreSQL 16+, you can configure the subscription to skip conflicting transactions automatically: `ALTER SUBSCRIPTION mysub SET (conflict_action = skip);`

**Real Example:** A PostgREST GitHub issue (2024) documented an infinite retry loop on a replica where a SQL statement kept hitting a conflict, accumulating replication lag over hours until the replica was effectively useless.

---

### 9.4 Phantom Reads and Stale Read Bugs

**Trigger:** Application reads from a replica immediately after a write on the primary. The replica has not yet applied the write (replication lag of 50–500 ms). The application shows the user the old data — for example, a newly created user account appears to not exist.

**Symptoms:** Intermittent "user not found" errors after registration. Shopping cart items disappear after being added. Idempotency checks fail because the previous write isn't visible yet.

**Detection:** These bugs are insidious because they are timing-dependent. They appear under load (when replica lag increases) and disappear in low-load testing. Monitor replica lag continuously. Add application-level assertions on critical read-after-write paths.

**Recovery / Mitigation:**
1. Implement read-your-own-writes: after any write, route reads for that entity to the primary for a configurable window (typically 2–5 seconds).
2. Use `synchronous_commit = remote_apply` for specific transactions that require immediate visibility on replicas.
3. Pass a causal token (the LSN of the last write) to the replica and have it wait until its `pg_last_wal_replay_lsn()` advances past that value before executing the read.

**Real Example:** A common pattern in high-traffic e-commerce: a user completes checkout, the order write lands on primary, the user is redirected to the order confirmation page which reads from a replica — and sees "order not found." This is a classic stale-read bug.

## 10. When To Use vs. When To Avoid

### Use Replication When:

**Read-heavy workload with a high read:write ratio.** If your application has a 10:1 or higher read:write ratio (e.g., a news site, product catalog, social media feed), read replicas provide near-linear read scaling. Adding 3 replicas to a system that's 90% reads gives you roughly 3x read capacity improvement.

**High availability and disaster recovery are required.** Any production service that cannot tolerate hours of downtime during a database failure needs at least one replica in a separate availability zone. Leader-follower with automated failover achieves RTO of 30–60 seconds vs. hours to restore from backup.

**Geographically distributed users with latency requirements.** If you have users in Europe reading data that is only stored in a US data center, they experience 100–200 ms added round-trip latency on every read. A read replica in a European region brings this down to single-digit milliseconds.

**Offloading analytics and reporting queries.** Long-running analytical queries (seconds to minutes) should never run on the primary. Route them to a dedicated replica to prevent OLAP queries from starving OLTP traffic.

### Do NOT Use Replication When:

**You have a write-bottleneck, not a read-bottleneck.** Replication does not increase write throughput. If your primary is saturated at 8,000 writes/sec and you add 5 replicas, you still max out at 8,000 writes/sec. The solution to write-bottleneck is sharding (Section 3.4), not replication.

**Your application cannot tolerate any eventual consistency.** If every read must see the latest write (e.g., financial ledger queries, inventory management where a -1 quantity would be catastrophic), async replicas will cause correctness bugs. Either use synchronous replication (accepting the latency cost) or always read from the primary.

**You have a tiny dataset and no meaningful traffic.** A 10 GB database serving 100 users does not need replication infrastructure. The operational overhead of maintaining replicas, monitoring lag, managing failover runbooks, and training on-call engineers far exceeds the value. Use backups + point-in-time recovery instead.

### The #1 Mistake Engineers Make:

**Reading from replicas without accounting for replication lag.** Engineers add read replicas to reduce load on the primary — correctly! — but then route ALL reads to replicas, including reads that immediately follow writes. The result is intermittent, hard-to-reproduce bugs where users see stale data after mutations. This manifests as: "user updates their profile but sees the old profile for a few seconds," "item added to cart disappears," "just-registered user can't log in." Fix it by implementing read-your-own-writes: track recent writes per user and route those reads to the primary for a configurable staleness window (2–5 seconds covers 99%+ of real-world replication lag).

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a system that needs to handle 100,000 reads/second and 5,000 writes/second for a user profile service."
- "You're designing Twitter. How would you handle database replication for the follow graph?"
- "How would you design a global e-commerce platform that needs low-latency reads in Europe and Asia while maintaining write consistency?"
- "Walk me through what happens when a database primary goes down and a replica gets promoted. What can go wrong?"
- "We're seeing that users sometimes see stale data after updating their profile. The app uses a replica for reads. How would you debug and fix this?"
- "Compare leader-follower vs. leaderless replication. When would you choose each?"

### What the Interviewer Is Evaluating

1. **Can you frame the problem correctly?** Most replication discussions should start with "what's the read:write ratio?" and "what's the RPO/RTO requirement?" before jumping to a solution.
2. **Do you understand the failure modes?** Mentioning replication lag, split-brain, read-your-own-writes violations signals senior-level thinking.
3. **Do you know actual numbers?** "Aurora has <100 ms replica lag" vs. "RDS PostgreSQL can lag by minutes under heavy load" — specific, differentiated knowledge.
4. **Can you evolve the design?** Starting with single-leader and explaining when/why you'd layer in read replicas, then when you'd consider multi-region or leaderless.
5. **Do you understand the trade-offs honestly?** Not "replication makes everything better" but "replication solves read scaling and HA but does not help writes and introduces lag-related consistency bugs."

### Questions YOU Ask the Interviewer Before Answering

1. "What's the read:write ratio?"
2. "What's the acceptable RPO and RTO? Is any data loss tolerable?"
3. "Is this single-region or multi-region?"
4. "Does the application ever need to read its own writes immediately after writing?"
5. "What consistency level do you need — strong, eventual, or something in between?"

### Junior (L3-L4) Answer Example

"I'd add read replicas to the database to handle the read load. The primary handles writes and the replicas handle reads. If the primary goes down, we fail over to a replica."

This answer is directionally correct but missing: quorum of replicas needed, replication lag handling, specific tooling, how failover actually works, RPO/RTO numbers, read-your-own-writes consideration.

### Senior (L5) Answer Example

"First, let me understand the workload. At 100K reads/sec and 5K writes/sec, that's a 20:1 read:write ratio, which is well-suited for read replicas. I'd start with a primary PostgreSQL instance and 3 async read replicas. That handles the read scaling. For HA, I'd add a synchronous replica in a separate AZ — this guarantees RPO=0 and gives us RTO of about 30 seconds with Patroni for automated failover. The critical design decision is read-your-own-writes: we need to track per-user write timestamps and route reads to the primary for ~2 seconds after any write to prevent stale-read bugs. If this is multi-region, I'd add async cross-region replicas for disaster recovery, but writes still go to one primary region — that keeps us out of the complexity swamp of multi-leader conflict resolution."

### Staff (L6+) Answer Example

The L5 answer, plus: discussion of the trade-off between synchronous_commit levels for different tables (not all tables need RPO=0 — be surgical about which ones do), replication slot monitoring to prevent WAL accumulation, the specific PostgreSQL `pg_stat_replication` query they'd put in an SLO dashboard, when they would abandon leader-follower entirely in favor of a Spanner-style distributed SQL database (when multi-region writes are the bottleneck, not reads), and the organizational/operational cost of running a Cassandra cluster (JVM tuning, compaction management, team knowledge requirements) vs. the managed alternative (ScyllaDB Cloud, DynamoDB).

The L6 engineer also asks: "Is this a new system or are we migrating an existing one? If migrating, how do we do a zero-downtime cutover with live replication traffic?" — because operational complexity at scale is as important as the architectural decision itself.
