## 1. What Is It? (Theory)

### Plain English

A **read replica** is a copy of your primary database that receives a continuous stream of changes from the primary and can answer read queries. Writes still go to one place — the primary — while reads can be distributed across many replicas.

**Write amplification** is the multiplier effect where a single logical write from an application causes significantly more physical bytes to be written to storage. It emerges from database internals (journaling, B-tree page splits, compaction) and replication mechanics (sending changes to multiple replicas). Understanding both concepts together is essential because scaling reads with replicas *also* amplifies writes on the primary.

### The Problem At Scale

A single PostgreSQL instance on modern hardware (32-core, NVMe SSD) can handle approximately:
- **~50,000–100,000 reads/sec** for simple queries
- **~5,000–20,000 writes/sec** for OLTP workloads

Most applications are read-heavy. A social feed, product catalog, analytics dashboard, or user profile page typically shows a **read:write ratio of 80:20 to 99:1**. When you hit 10M+ users, reads become the bottleneck first.

Without read replicas, your options are:
1. Scale up vertically (expensive, has hard limits, single point of failure)
2. Cache everything (complex invalidation, not suitable for all query patterns)
3. Accept degraded performance (not an option in production)

### Why It Was Invented

Early web applications in the 2000s (think early MySpace, early Twitter) found that their primary databases were melting under read load. The pattern emerged naturally: MySQL's binary log already tracked all changes in order. Why not ship that log to another server and let it replay the same writes? The replica ends up with identical data and can serve reads.

Write amplification was later formalized as a metric when SSDs became mainstream. NAND flash has limited write endurance (program/erase cycles), so measuring how many actual bytes your software writes per logical user write became critical for predicting hardware lifetime and cost.

### Real-World Analogy

Think of a **library system**:
- The **primary database** is the master catalog maintained by the head librarian. Every new book, every check-out, every return gets recorded here first.
- **Read replicas** are photocopied catalogs distributed to branch libraries. Patrons at any branch can look up books, but new acquisitions are only processed at headquarters and then propagated to branches. A branch catalog might be 5 minutes behind — that is your replication lag.
- **Write amplification** is the head librarian having to write in the master catalog, update the digital index, update the physical card catalog, and log the change in an audit ledger — four physical writes for one logical "add new book" operation.

### Concrete Example: E-Commerce at Scale

Shopify runs thousands of MySQL instances. A merchant's storefront serves product listings (reads) far more than it processes orders (writes). At peak (e.g., Black Friday), a single storefront might receive:
- **200,000 product page views/minute** → read-heavy
- **2,000 orders/minute** → write-moderate

Without read replicas, the primary MySQL instance is crushed by reads. With 3 replicas, each instance handles ~50,000 reads/minute — well within its capacity. The primary focuses exclusively on writes.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step: Streaming Replication (PostgreSQL WAL)

PostgreSQL uses **Write-Ahead Logging (WAL)** — every change is written to the WAL before being applied to data files. This is also what replicas consume.

```
Step 1: Application sends INSERT/UPDATE/DELETE to primary
Step 2: Primary writes WAL record (binary format, ~100-500 bytes/row change)
Step 3: Primary applies change to its own buffer pool (in-memory)
Step 4: WAL sender process streams WAL records to replica(s) via TCP
Step 5: Replica receives WAL records via WAL receiver process
Step 6: Replica replays WAL records — applies changes to its own buffer pool
Step 7: Application reads from replica — sees committed data (with lag)
```

**Synchronous vs. Asynchronous Replication:**
- **Async (default):** Primary commits as soon as WAL is written locally. Replica applies independently. Lag: 10ms–several seconds depending on write volume.
- **Sync (`synchronous_commit = on`):** Primary waits for replica to acknowledge WAL receipt before confirming commit to application. Adds ~1–5ms latency per write. Zero data loss on failover.

### Write Amplification: The Full Stack

When you issue a single `UPDATE users SET last_seen = NOW() WHERE id = 42`:

**Layer 1: B-Tree Storage Engine (PostgreSQL heap + B-tree index)**
```
Logical write:    1 row = ~200 bytes
Physical writes:
  - WAL record:                    ~300 bytes  (write-ahead log)
  - Heap page (8KB page, 1 row):   8,192 bytes (full page written on first modify)
  - Index page (user_id index):    8,192 bytes (B-tree leaf page)
  - Double-write buffer (MySQL):   8,192 bytes (crash safety)
  - OS page cache flush:           4,096 bytes (kernel page)
  ──────────────────────────────────────────────────────────
  Total physical writes:           ~28,000 bytes for 200 bytes of user data

  Write Amplification Factor:      ~140x at storage level
```

**Layer 2: LSM-Tree Storage Engine (RocksDB, Cassandra, ScyllaDB)**
```
Logical write:    1 row = ~200 bytes
Physical writes:
  - Append to MemTable (in-memory):    ~200 bytes  (near zero I/O)
  - WAL/commit log:                    ~250 bytes  (durability)
  - L0 SSTable flush (4MB file):       4MB / (rows in batch)
  - Compaction L0→L1:                  read + rewrite each file
  - Compaction L1→L2:                  read + rewrite again
  ──────────────────────────────────────────────────────────
  Write Amplification Factor:          10x–30x (leveled) or 5x–10x (tiered)
  Read Amplification Factor:           5x–10x (must check multiple SSTables)
  Space Amplification Factor:          1.1x–1.5x (leveled) or 2x–10x (tiered)
```

**The Amplification Trilemma (RUM Conjecture):**
You cannot simultaneously minimize all three. You must pick two:
```
        Read Amplification
              │
              │  B-tree: Low R, High W
              │  LSM:    High R, Low W
              │
Write ────────┼──────── Space
Amplification │         Amplification
              │
     Every storage engine lives somewhere on this triangle
```

### Misconceptions

**❌ Misconception: Read replicas are perfectly consistent copies of the primary.**
**✅ Reality:** Replicas are *eventually consistent* by default. Under heavy write load, replicas can lag by seconds or minutes. A user who just saved their profile might read stale data from a replica 500ms later. This is a hard distributed systems constraint, not a bug.

**❌ Misconception: Adding more read replicas linearly scales write capacity.**
**✅ Reality:** Each replica *receives every write* from the primary. With 5 replicas, the primary must send the full WAL stream to 5 destinations. This increases network I/O and CPU on the primary. At extreme replica counts, the primary's WAL sender processes become a bottleneck.

**❌ Misconception: LSM trees have lower write amplification than B-trees.**
**✅ Reality:** LSM trees have lower *initial* write amplification (appends are cheap), but compaction adds amplification over time. At steady state, LSM WAF is 10–30x for leveled compaction. B-trees have 10–100x. The difference is that LSM's amplification is *sequential* (compaction), while B-tree's is *random* (page updates). On modern SSDs, sequential writes are 2–5x faster than random writes, making LSM's WAF more practical.

**❌ Misconception: Synchronous replication eliminates all data loss risk.**
**✅ Reality:** Synchronous replication to a single replica eliminates data loss *if the replica is available*. If the network partition prevents the replica from acknowledging, PostgreSQL will either block writes (if `synchronous_commit = remote_apply`) or fall back to async (if `synchronous_standby_names` allows degradation).

## 3. Real-World Architecture Examples

### Shopify — Solving Stale Reads at Scale

**Scale:** Hundreds of thousands of merchant storefronts, millions of requests/second, each merchant on a dedicated MySQL shard.

**The Problem:** Shopify routes reads to replicas aggressively to reduce load on primaries. This caused a class of bugs: a merchant updates a product price, immediately views their storefront, and sees the old price. The merchant files a support ticket. This is the classic **read-your-writes** consistency violation.

**What They Got Wrong First:** They tried a simple rule — "after a write, read from the primary for 5 seconds." This worked but was wasteful (unnecessary primary load) and fragile (what is the right window?).

**The Solution:** Shopify forked ProxySQL and introduced **session consistency tokens** (UUIDs). When a write completes, the application receives a consistency token. Subsequent reads within the same user session pass this token. ProxySQL routes the read to a replica that has already applied WAL beyond that token's LSN (Log Sequence Number). Reads that don't carry a token are freely routed to any replica.

**Result:** Eliminated stale read user complaints. Primary load reduced by ~60%. Documented in their engineering blog: [Read Consistency with Database Replicas](https://shopify.engineering/read-consistency-database-replicas).

### GitHub — freno: Throttling Replication-Aware Writes

**Scale:** Hundreds of MySQL instances, petabytes of data, billions of rows.

**The Problem:** Background jobs (migrations, data backups, bulk updates) hammer the primary, producing a surge of WAL/binlog. Replicas fall seconds to minutes behind. Meanwhile, the application is serving reads from lagging replicas — users see inconsistent data. Worse, during replica lag, GitHub removed lagging replicas from the read pool, forcing *all* reads back to the primary, which amplified the problem.

**What They Got Wrong First:** Individual services had their own throttling logic. They were inconsistent, didn't account for cluster-wide replica health, and were hard to reason about.

**The Solution:** GitHub built [freno](https://github.blog/engineering/infrastructure/mitigating-replication-lag-and-reducing-read-load-with-freno/), a centralized HTTP throttler. Before executing a write-heavy batch operation, services ask freno: "Is it safe to write right now?" freno checks real-time replica lag across the cluster. If any replica exceeds the threshold (e.g., 1 second lag), freno returns HTTP 429 and the job waits.

**Result:** Eliminated replica lag spikes from background jobs. Reduced write-induced lag by >90% during maintenance windows. freno is open source.

### Netflix — Aurora for Reduced Write Amplification

**Scale:** Hundreds of millions of subscribers, dozens of microservices, each with its own relational database.

**The Problem:** Netflix ran RDS for MySQL/PostgreSQL for years. Classic streaming replication meant each replica received the full WAL stream, including full page images. Adding replicas added CPU and network overhead to the primary. Write amplification from double-write buffers (MySQL InnoDB) wasted ~50% of write IOPS.

**What They Got Wrong First:** Vertical scaling was the first response — keep upgrading to larger instance types. This delayed but did not solve the problem.

**The Solution:** Netflix consolidated to [Amazon Aurora](https://aws.amazon.com/blogs/database/netflix-consolidates-relational-database-infrastructure-on-amazon-aurora-achieving-up-to-75-improved-performance/), which uses a fundamentally different architecture: **shared distributed storage**. The primary writes only redo log records (not full pages) to 6 storage nodes across 3 AZs. Replicas read from the *same storage layer* — there is no physical data copy per replica. Replication lag for Aurora replicas is typically <100ms because replicas only receive the log stream, not data pages.

**Result:** Up to 75% improved performance compared to vanilla RDS MySQL/PostgreSQL. Write amplification reduced because Aurora eliminates the double-write buffer entirely. Up to 15 replicas vs. 5 for RDS. Netflix uses Aurora Global Database for cross-region replication with <1 second lag.

### Design Questions To Ask Before Starting

1. **What is the read:write ratio?** If it is 50:50 or higher writes, read replicas solve the wrong problem.
2. **What is the acceptable replication lag?** Financial transactions? Zero lag required. Social feeds? 5 seconds is fine.
3. **Do any queries require read-your-writes consistency?** If yes, you need session pinning or primary reads for those queries.
4. **How large is the write throughput?** >10,000 writes/sec means your WAL stream is large. Can your network handle shipping it to 5 replicas?
5. **Are background jobs (migrations, analytics) hitting the same DB?** These should be offloaded to a dedicated replica.
6. **What is the failure mode if the primary dies?** You need a promotion strategy — automatic (Patroni, RDS Multi-AZ) or manual?
7. **Is the data model write-heavy with compaction pressure?** Consider LSM-based stores (Cassandra, ScyllaDB) if write throughput dominates.

#### 100K–1M DAU
```
Setup: Primary + 3 read replicas + read-routing middleware
Specs: db.r5.xlarge (4 vCPU, 32GB), io1 SSD (3,000 IOPS)
Read capacity: ~40,000 queries/sec (10K each)
Write capacity: ~3,000 writes/sec
Replication lag: 100ms–2s under peak writes
Cost: ~$2,000/month

```

#### 1M–100M+ DAU
```
Setup: Aurora cluster (1 writer, 5-15 readers) per shard
       OR Vitess (MySQL sharding) with replicas per shard
Specs: db.r6g.4xlarge (16 vCPU, 128GB)
Read capacity: ~200,000 queries/sec (Aurora shared storage, replica overhead minimal)
Write capacity: ~20,000 writes/sec per shard
Replication lag: <100ms (Aurora), up to 5s (standard MySQL at high write rate)
Cost: ~$10,000–$50,000/month depending on shard count
Action: Auto-scaling read replicas based on CPU/lag metrics.
        Aurora Global Database for cross-region reads (<1s lag).
        Separate OLTP and OLAP into different databases entirely.
        Consider read-through cache (Amazon ElastiCache) for hot paths.
        freno-style write throttling for background jobs.
        Proactive compaction scheduling for LSM-based auxiliary stores.
```

## 5. Code / Implementation Perspective

### Python: Read/Write Splitting with Lag-Awareness

```python
import time
import random
import psycopg2
from dataclasses import dataclass, field
from typing import Optional
from contextlib import contextmanager

@dataclass
class ReplicaNode:
    host: str
    port: int = 5432
    lag_seconds: float = 0.0
    healthy: bool = True
    conn: Optional[psycopg2.extensions.connection] = field(default=None, repr=False)

class ReadWriteRouter:
    """
    Routes queries to primary (writes) or replicas (reads).
    Tracks replica lag and avoids stale replicas for lag-sensitive reads.
    """

    MAX_ACCEPTABLE_LAG = 5.0  # seconds

    def __init__(self, primary_host: str, replica_hosts: list[str]):
        self.primary = psycopg2.connect(host=primary_host, dbname="app", user="app")
        self.replicas = [ReplicaNode(host=h) for h in replica_hosts]
        self._connect_replicas()
        self._last_write_lsn: Optional[str] = None

    def _connect_replicas(self):
        for r in self.replicas:
            try:
                r.conn = psycopg2.connect(host=r.host, dbname="app", user="app_readonly")
                r.healthy = True
            except Exception:
                r.healthy = False

    def _refresh_replica_lag(self):
        """Poll pg_stat_replication lag from primary view."""
        with self.primary.cursor() as cur:
            cur.execute("""
                SELECT client_addr,
                       EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))
                FROM pg_stat_replication
            """)
            lag_map = {row[0]: row[1] for row in cur.fetchall()}
        for r in self.replicas:
            r.lag_seconds = lag_map.get(r.host, 999.0)

    def _pick_replica(self, max_lag: float = MAX_ACCEPTABLE_LAG) -> Optional[ReplicaNode]:
        """Select a healthy replica below the lag threshold."""
        candidates = [
            r for r in self.replicas
            if r.healthy and r.lag_seconds <= max_lag
        ]
        return random.choice(candidates) if candidates else None

    @contextmanager
    def write_connection(self):
        """Always use primary for writes. Capture LSN after commit."""
        yield self.primary
        with self.primary.cursor() as cur:
            cur.execute("SELECT pg_current_wal_lsn()")
            self._last_write_lsn = cur.fetchone()[0]

    @contextmanager
    def read_connection(self, require_fresh: bool = False):
        """
        Return replica connection. Falls back to primary if:
        - No healthy replica with acceptable lag
        - require_fresh=True (read-your-writes semantics needed)
        """
        if require_fresh and self._last_write_lsn:
            # Ensure replica has applied past our last write
            replica = self._find_caught_up_replica(self._last_write_lsn)
            if replica:
                yield replica.conn
                return
            # Fall back to primary for strict consistency
            yield self.primary
            return

        self._refresh_replica_lag()
        replica = self._pick_replica()
        if replica:
            yield replica.conn
        else:
            # All replicas lagging or unhealthy — fall back to primary
            yield self.primary

    def _find_caught_up_replica(self, target_lsn: str) -> Optional[ReplicaNode]:
        for r in self.replicas:
            if not r.healthy:
                continue
            with r.conn.cursor() as cur:
                cur.execute("SELECT pg_last_wal_replay_lsn() >= %s::pg_lsn", (target_lsn,))
                if cur.fetchone()[0]:
                    return r
        return None


# Usage
router = ReadWriteRouter(
    primary_host="db-primary.internal",
    replica_hosts=["db-replica-1.internal", "db-replica-2.internal"]
)

# Write path
with router.write_connection() as conn:
    with conn.cursor() as cur:
        cur.execute("UPDATE users SET last_seen = NOW() WHERE id = %s", (user_id,))
    conn.commit()

# Read path (strict: read-your-writes after the write above)
with router.read_connection(require_fresh=True) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT last_seen FROM users WHERE id = %s", (user_id,))
        result = cur.fetchone()
```

### Infrastructure Config: PostgreSQL Streaming Replication (postgresql.conf)

    variable_name,
    variable_value
FROM information_schema.global_status
WHERE variable_name IN (
    'Innodb_data_written',         -- Total bytes written to InnoDB data files

| **Neon** | Serverless Postgres | Branching DBs, dev/test environments | Per-branch replicas | Yes | Compute seconds + storage | Copy-on-write storage; instant branching; cold-start latency |
| **RocksDB (embedded)** | LSM-tree KV store | Write-heavy, embedded in app layer | N/A (embedded) | No | Free (Meta open source) | WAF: 10–30x leveled; used by MyRocks, TiKV, CockroachDB |
| **Cassandra / ScyllaDB** | LSM-tree wide-column | Time-series, IoT, write-heavy analytics | N-way replication (3x typical) | No (Cassandra) / Yes (Scylla Cloud) | Per node or instance-hour | RF=3 means 3x write amplification at cluster level; ScyllaDB is C++ rewrite of Cassandra, 10x faster |
| **CockroachDB** | Distributed SQL | Multi-region OLTP, geo-partitioning | Built-in via Raft | Yes (CockroachCloud) | Per vCPU-hour | Raft replication = synchronous to quorum; higher write latency than single-region Postgres |

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Read Replicas** | Read:write ratio >4:1; acceptable eventual consistency; geographic distribution | Replication lag; stale reads; primary still bottlenecked at extreme write rates | Shopify, GitHub, Netflix, Instagram |
| **Read-through Cache (Redis/Memcached)** | Hot read patterns; latency <1ms required; data fits in memory | Cache invalidation complexity; stale data risk; doesn't help non-cacheable queries | Twitter (timeline cache), Discord (message cache) |
| **Vertical Scaling** | Write-heavy workload; simplicity required; budget allows | Hard limit on single machine size (largest AWS RDS: db.r6g.16xlarge = 512GB RAM); SPOF; expensive | Early-stage startups |
| **CQRS (Command Query Responsibility Segregation)** | Complex read models; event-sourced systems; read model schema differs from write model | Architectural complexity; eventual consistency between command and query stores; operational overhead | Axon, event-sourced systems at Zalando, Microsoft |
| **Database Sharding** | Write throughput exceeds single primary capacity; dataset >multi-TB | Cross-shard transactions; rebalancing complexity; operational burden | Vitess/YouTube, Shopify (per-merchant shards), Pinterest |
| **Multi-primary replication (Galera, CockroachDB)** | Multi-region writes required; write-heavy with geo-distribution | Write conflicts; higher per-write latency (synchronous to quorum); complex conflict resolution | PlanetScale (Vitess), Cloudflare (CockroachDB for DNS) |
| **Time-series databases (InfluxDB, TimescaleDB)** | Metrics/events; append-only; time-partitioned access patterns | Not for general OLTP; limited JOIN support | Datadog (metrics), InfluxData |

### My Recommendation

**Start with read replicas and a cache layer.** This is the right answer for 95% of scaling problems. The cache (Redis) handles hot, idempotent reads with <1ms latency. The read replica handles complex queries, reports, and anything not worth caching. Together they remove >80% of primary load with manageable operational complexity.

**Do not reach for sharding before exhausting replicas + caching.** Sharding multiplies operational complexity by 10x. A well-tuned Aurora cluster with 5 read replicas and Redis L1 cache can handle 500K+ requests/second for typical web workloads. Shopify ran millions of storefronts on per-merchant MySQL shards each with replicas — they didn't need distributed multi-primary SQL.

**The one exception:** if your write volume exceeds ~20,000 writes/second on a single primary, replicas do not help — they hurt (WAL sender overhead). At that point, shard the write path or move to a write-optimized store like ScyllaDB or Cassandra.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Linear read scaling:** Each replica adds ~10,000–50,000 additional read QPS. Aurora's shared storage makes replica overhead nearly zero; adding replica #14 costs roughly $0 in primary CPU.
- **Geographic read locality:** A replica in eu-west-1 serves European users with 10ms latency vs. 90ms cross-Atlantic to us-east-1. AWS Aurora Global Database achieves <1 second cross-region replication lag.
- **Workload isolation:** Analytics queries (long-running, table scans, high CPU) on a dedicated replica do not disrupt OLTP performance on the primary. This is one of the most underrated benefits — it eliminates "the report query that took down production."
- **Zero-downtime failover (with Multi-AZ):** RDS Multi-AZ keeps a synchronous standby. On primary failure, DNS is updated and the standby is promoted in 20–60 seconds. Aurora PITR (Point-In-Time Recovery) to 5-minute granularity further protects against logical errors.
- **Reduced write amplification (Aurora-specific):** By eliminating the double-write buffer and sending only redo logs to shared storage, Aurora reduces write I/O by approximately 50% compared to standard MySQL InnoDB on the same hardware.

### Costs and Limitations

- **Replication lag is unavoidable (async mode):** Under a sustained 10,000 writes/sec workload with complex transactions, replicas routinely fall 1–30 seconds behind. Building your application to handle this gracefully is mandatory work, not optional.
- **Primary CPU overhead from WAL sending:** With 5 traditional streaming replicas, expect 10–20% additional CPU overhead on the primary just for WAL sender processes. This overhead compounds with write throughput.
- **Cost doubles per replica:** Each replica is a full database instance. 1 primary + 3 replicas = 4x the compute cost. Aurora's per-ACU pricing and shared storage make this cheaper, but not free.
- **No horizontal write scaling:** Read replicas solve the read problem. They do nothing for write throughput. If your bottleneck is writes, you need sharding, a write-optimized store, or both.
- **Connection management complexity:** Each replica needs its own connection pool. Your application layer needs logic to route writes to primary and reads to replicas. Libraries like SQLAlchemy support this, but it is non-trivial configuration.
- **Cascading failure risk:** If replication lag causes replicas to be removed from the read pool (GitHub's behavior), all reads hit the primary, which is now overloaded, which slows writes, which increases lag — a death spiral. This is not theoretical; it has taken down production systems.

### Core Tension

**Consistency vs. Throughput.** Asynchronous replication gives you maximum throughput (no added write latency) but sacrifices consistency (stale reads). Synchronous replication gives you consistency (no stale reads) but adds 1–5ms latency to every write and reduces availability if the replica is unreachable. You cannot have both at the extremes. Every system design decision about replication mode is a position on this spectrum.

### My Recommendation

Use **async replication with application-level session consistency** as the default. This is what Shopify, GitHub, and most mature OLTP systems do. Accept that most reads can be slightly stale (social feeds, product listings, dashboards). Implement read-your-writes consistency only for user-facing operations where stale data would be obviously wrong (profile updates, order confirmations, settings changes). Pin those specific reads to the primary or to a replica verified to have applied past the user's last write LSN.

Use **sync replication only** for financial transactions, audit trails, and any data where loss is more costly than latency. Accept the 1–5ms write overhead and build your SLAs accordingly.

## 9. Failure Modes — What Goes Wrong

### Replication Lag Cascade (Death Spiral)

**Trigger:** A large batch operation (migration, bulk insert, analytical export) generates a sustained surge of WAL/binlog, typically 100–500 MB/sec. Replicas cannot apply changes fast enough — especially with single-threaded MySQL replication. Replica lag climbs to 30+ seconds.

**Symptoms:** Read replica monitoring shows `ReplicaLag` > alerting threshold. Application routes reads to primary as replicas are removed from the pool. Primary CPU spikes (now handling read + write load). Response times degrade across the board. The batch job slows due to primary pressure, which prolongs the lag. System enters a self-reinforcing degraded state.

**Detection:**
- CloudWatch metric: `ReplicaLag > 5s` for >2 minutes
- Custom query on replica: `SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())) AS lag_sec;`
- PagerDuty alert on primary CPU > 85%

**Recovery:**
1. Immediately throttle or kill the triggering batch job.
2. Enable MySQL parallel replication: `SET GLOBAL slave_parallel_workers = 8;`
3. Allow replicas to catch up before re-adding to pool.
4. Post-incident: implement freno-style throttling for all batch jobs.

**Real Example:** GitHub documented this pattern in their freno blog post. Large schema migrations on MySQL primaries caused replica lag spikes that removed replicas from the serving pool, routing traffic to the primary, which further slowed the migration. freno was built specifically to prevent this.

---

### Split-Brain on Failover

**Trigger:** Primary becomes unreachable (hardware failure, network partition). Automatic failover promotes a replica to primary. The original primary recovers 60 seconds later and believes it is still primary. Both nodes accept writes. Now two nodes have diverged state.

**Symptoms:** Application writes to both "primaries." Data integrity violations. Duplicate records. Lost updates. Customers see inconsistent data. Merging the two diverged states may be impossible without data loss.

**Detection:**
- Two nodes both report `pg_is_in_recovery() = false` simultaneously
- Fencing token / STONITH (Shoot The Other Node In The Head) alerts
- Patroni cluster health endpoint returns unexpected topology

**Recovery:**
1. **Prevention is the only reliable fix.** Use Patroni with etcd/Consul for leader election. Use STONITH to forcibly shut down the old primary before promotion. AWS RDS/Aurora handle this via DNS CNAME switching with a brief unavailability window.
2. If split-brain occurred: stop all writes to both nodes. Compare WAL/binlog positions. Identify which node has newer, correct data. Discard the other's diverged writes (data loss is likely). Restore from backup if divergence is unresolvable.

**Real Example:** A common incident in self-managed PostgreSQL clusters with Pacemaker before etcd-based tools (Patroni, repmgr) became standard. AWS RDS Multi-AZ prevents this via its own fencing, but documentation warns: never change CNAME manually during automated failover.

---

### Write Amplification Causing SSD Wear-Out

**Trigger:** A write-heavy LSM workload (e.g., Cassandra ingesting IoT events at 100,000 writes/sec) with a poorly tuned compaction strategy. Write amplification factor of 25x means the SSDs are writing 2.5 GB/s for every 100 MB/s of user data.

**Symptoms:** SSD write endurance warnings (SMART data showing high percentage of drive life consumed). Compaction failing to keep up with write rate — L0 SSTable count grows, query latency spikes. In extreme cases, SSDs fail prematurely, causing data loss.

**Detection:**
- `nodetool compactionstats` in Cassandra shows pending compactions > 100
- RocksDB `rocksdb.estimate-pending-compaction-bytes` metric > 10GB
- SMART data: `Percentage_Used` > 80% on SSDs younger than 2 years

**Recovery:**
1. Switch from leveled to tiered compaction to reduce immediate WAF at the cost of read amplification.
2. Throttle ingestion rate to allow compaction to catch up.
3. Increase compaction thread count: `concurrent_compactors = 4` in cassandra.yaml.
4. Long-term: provision SSDs with higher TBW (terabytes written) rating — enterprise NVMe rated 3–10 DWPD vs. consumer SSDs at 0.3 DWPD.

**Real Example:** Several early Cassandra deployments (pre-2016) on AWS with magnetic HDDs experienced this. The solution was moving to SSD instances (i2.xlarge, then i3.xlarge) and tuning compaction. Meta's engineering blog documented similar challenges with RocksDB write amplification in MyRocks before universal compaction was introduced.

---

### Stale Read Causing Data Corruption (Silent Bug)

**Trigger:** Application reads a value from a lagging replica, performs a calculation, and writes the result back to the primary. The calculation was based on stale data. Classic example: inventory decrement. Two requests read stock=5 from a replica (1 second stale). Both proceed to "buy the last item." Both write stock=4 to the primary. Stock should be 3 but is now 4.

**Symptoms:** Data inconsistencies that are hard to reproduce (only happen under concurrent load with replica lag). Inventory discrepancies, double-booking, incorrect totals. No exceptions in application logs — the queries succeeded, the data is just wrong.

**Detection:**
- Periodic reconciliation jobs comparing expected vs. actual aggregate values
- Business metric anomalies: negative inventory, revenue not matching order totals
- Synthetic read-after-write consistency checks in integration tests

**Recovery:**
1. **Prevention only:** Read-modify-write operations must always read from the primary, not replicas. Use `SELECT ... FOR UPDATE` on the primary.
2. If corruption occurred: audit affected rows via event log or transaction history. Restore from backup point before corruption began. Apply missed events.

**Real Example:** E-commerce flash sale incidents where inventory "oversold." The application was routing product stock reads to a replica. Under load, replication lagged, allowing concurrent buyers to all see available inventory that had already been sold. The fix: inventory reads for purchase flow always go to primary with `SELECT stock FOR UPDATE`.

## 10. When To Use vs. When To Avoid

### Use When

- **Read:write ratio is at least 4:1.** If your workload is 80% reads, read replicas directly address the bottleneck. Below that ratio, cache or vertical scaling is likely more cost-effective.
- **Queries have latency tolerance for eventual consistency.** Product listings, social feeds, analytics dashboards, search result counts, public profiles — none of these require the absolute latest write. 100–500ms of replica lag is invisible to users.
- **Geographic distribution is required.** Serving users in Asia-Pacific from a us-east-1 primary means 150–300ms base latency. A replica in ap-southeast-1 reduces that to 10–20ms. This alone often justifies the infrastructure cost for global products.
- **Workload isolation is needed.** Running analytics, ML feature extraction, or reporting queries on the production primary is an operational risk. A dedicated analytics replica quarantines these queries.
- **You need resilience against primary failure.** Even if you do not need read scaling, a replica with automatic failover provides 99.95%+ availability vs. single-instance 99.5%.

### Do NOT Use When

- **Write throughput is the bottleneck.** Read replicas receive every write and add overhead to the primary's WAL sender. Adding replicas to a write-bottlenecked system makes things worse. Shard the write path instead.
- **Your application requires strict linearizability for all reads.** Financial systems, distributed locks, ticketing systems — if every read must see the latest committed write, async replicas will cause correctness bugs. Use synchronous replication (higher latency) or single-node reads from the primary.
- **Your working set doesn't fit in memory.** If replica buffer pools are too small to cache hot pages, reads hit disk on both primary and replicas. Adding replicas does not help; your limiting factor is I/O bandwidth, not CPU. Increase RAM or use a cache layer.
- **You have not fixed your query patterns first.** Adding replicas to a system with missing indexes or N+1 query problems is papering over the real issue. A query doing a full table scan takes 10 seconds on a replica just as it does on the primary. Fix indexes first, then scale.

### The #1 Mistake Engineers Make

**Sending all reads to replicas without handling read-your-writes consistency.**

It is the first thing teams do when setting up read replicas: change the DB connection string to point reads at a replica pool. Within 24 hours, users file bugs: "I just updated my profile picture and it's showing the old one." "I just placed an order but my order history is empty." These are classic stale read bugs caused by replication lag.

The mistake is treating the replica as a drop-in replacement for the primary for all reads. It is not. The replica is eventually consistent. Any read that must see a user's own recent write — authentication, profile display, order confirmation, settings — must either go to the primary or use a consistency token mechanism. Plan for this from day one.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a system for a read-heavy social media feed that scales to 100M users."
- "How would you scale a PostgreSQL database that's hitting 80% CPU?"
- "Our database is struggling with a 90:10 read:write ratio. What would you do?"
- "Design the data layer for a global e-commerce platform."
- "What is write amplification and why does it matter?"
- "Our RDS instance is overwhelmed during peak traffic. Walk me through your approach."
- "When would you choose Aurora over RDS PostgreSQL?"

### What The Interviewer Evaluates

1. **Can you identify the actual bottleneck?** Read-heavy? Write-heavy? Network? Storage I/O? The solution differs.
2. **Do you understand eventual consistency implications?** Will you proactively bring up stale reads, or do you need prompting?
3. **Do you know the numbers?** Can you estimate QPS per replica, replication lag thresholds, cost implications?
4. **Can you describe the failure modes?** Death spiral, split-brain, stale reads causing data corruption.
5. **Do you know when NOT to use it?** Recommending replicas for a write-bottlenecked system fails the interview.

### Questions YOU Should Ask Before Answering

1. "What is the current read:write ratio?"
2. "What consistency guarantees does the product require? Is stale data acceptable for any reads?"
3. "What is the target latency — single region or global?"
4. "Is the bottleneck reads, writes, or storage I/O? Do you have monitoring data?"
5. "What is the team's operational maturity — managed cloud services or self-hosted?"

### Junior (L3–L4) Expected Answer

"I would add read replicas to distribute read traffic away from the primary. Writes go to the primary, reads go to replicas. This scales read capacity linearly. Potential issue is replication lag — the replica might be a few seconds behind. I'd monitor this with CloudWatch's ReplicaLag metric and alert if it exceeds a threshold."

*Good: covers the basics, mentions lag. Missing: stale read handling, failure modes, when not to use it.*

### Senior (L5) Expected Answer

"Before jumping to replicas, I'd confirm the bottleneck is reads, not writes — replicas don't help write-bound systems. Assuming read-heavy: I'd add Aurora replicas (shared storage means near-zero overhead per replica, <100ms lag typical) and implement read-your-writes consistency at the application layer — any read following a write in the same user session either hits the primary or uses LSN-based replica selection. I'd separate analytics queries to a dedicated replica to isolate OLTP from scan-heavy workloads. I'd set alerts on ReplicaLag > 5s and implement freno-style throttling for batch jobs to prevent the lag cascade failure mode. If write volume is growing, I'd track it — once writes exceed ~10,000/sec on a single primary, I'd start planning sharding."

*Good: bottleneck validation, consistency handling, failure modes, operational practices.*

### Staff (L6+) Expected Answer

"Let me scope this first: what's the read:write ratio, what consistency does the product require, what's the geographic distribution of users, and are we write-bound or read-bound? [After clarification.]

For a read-heavy globally distributed system: I'd use Aurora Global Database — one writer region, up to 5 secondary regions each with up to 16 read-only replicas. Aurora's shared storage architecture eliminates per-replica WAL overhead and keeps lag <100ms in-region, <1s cross-region. Write amplification on Aurora is ~50% lower than standard MySQL because there is no double-write buffer.

Application layer: route reads to the nearest regional replica by default. Implement session consistency tokens (LSN pinning) for read-your-writes operations — Shopify's ProxySQL fork is the reference implementation. Mark specific operations (order confirmation, profile update, payment) as requiring fresh reads and pin those to the writer for 30 seconds post-write.

Operational concerns: I'd instrument ReplicaLag as a P0 metric with a 5-second SLA. Any background migration uses freno to throttle based on real-time replica health. Schema changes use pt-online-schema-change (MySQL) or pg_reorg (Postgres) to avoid table locks that would spike lag.

At 100M+ users, if write throughput exceeds single-Aurora-writer capacity (~20,000 TPS), I'd consider Vitess for horizontal write sharding while keeping per-shard Aurora replica clusters for reads.

The failure mode I'd design around most carefully: stale reads for read-modify-write operations (inventory, balances). Those must read from the writer with `SELECT ... FOR UPDATE`, not from replicas. This is the silent data corruption bug that has caused overselling incidents at multiple e-commerce companies."

*Full answer: scoping, numbers, architecture, consistency model, failure modes, scale evolution.*
