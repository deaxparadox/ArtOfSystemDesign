## 1. What Is It? (Theory)

### Plain English

Sharding is splitting your database — not just the rows, but the entire server — across multiple independent machines. Each machine (shard) owns a slice of the data, answers queries about only its slice, and knows nothing about the rest.

Partitioning is the broader term: dividing data into logical or physical segments. Sharding is a specific type of **horizontal partitioning** where those partitions live on **separate servers**.

Think of it this way: if your database is a library, vertical scaling is getting taller bookshelves — you hit a ceiling eventually. Partitioning is dividing the library into sections (fiction, non-fiction). Sharding is opening ten branch libraries, each holding a portion of the full catalog.

### The Problem It Solves

A single PostgreSQL node — even on the largest available EC2 instance (r6g.metal, 512 GiB RAM, 128 vCPUs) — tops out around:
- **~50,000–100,000 queries/second** for simple read workloads
- **~10,000–20,000 writes/second** under heavy contention
- **~10–20 TB** of data before query performance degrades noticeably on cold pages

When your application crosses these thresholds, no amount of replication or caching alone can fix the write bottleneck. Replication gives you more read capacity; sharding gives you more **write capacity** and **storage capacity**.

### Why It Was Invented

Before sharding, engineers added replicas for reads and hoped writes stayed manageable. Twitter in 2009, Facebook in 2008, and Digg in 2010 all hit the same wall: their monolithic MySQL cluster could not absorb their write volume. The solution — borrowed from data warehousing where range partitioning had existed for years — was to split the write path itself.

### Real-World Analogy

A bank with one teller handles 50 customers/hour. Adding 10 tellers in the same branch scales to 500/hour — but they share the same vault (I/O bottleneck) and lobby (connection limit). Sharding is opening 10 branch banks. Each branch has its own tellers **and** its own vault. A routing system (shard router) decides which branch a customer goes to based on their account number.

### Concrete Numbers

| Scenario | Single DB | Sharded (8 shards) |
|---|---|---|
| Write throughput | 15,000 writes/s | 120,000 writes/s |
| Storage capacity | 8 TB practical | 64 TB practical |
| P99 write latency | 8 ms (at load) | 8 ms (each shard at 1/8 load) |
| Cross-shard join | N/A | 50–200 ms (fan-out query) |

## 2. How It Actually Works (Deep Mechanics)

### Core Sharding Strategies

#### Strategy 1: Range-Based Sharding

Data is divided by contiguous ranges of the shard key.

```
Shard Key: user_id (integer)

Shard 0: user_id  0 –  24,999,999
Shard 1: user_id 25,000,000 – 49,999,999
Shard 2: user_id 50,000,000 – 74,999,999
Shard 3: user_id 75,000,000 – 99,999,999
```

**How routing works:**
1. Client sends `SELECT * FROM users WHERE user_id = 62,000,000`
2. Shard router checks range table: `62M` falls in shard 2 range
3. Query routed to shard 2 exclusively
4. Result returned to client

**ASCII Flow:**

```
Client Request
     |
     v
 [Shard Router / Proxy]
  ┌─────────────────────────────┐
  │  range_map:                 │
  │  [0, 25M)     → shard-0     │
  │  [25M, 50M)   → shard-1     │
  │  [50M, 75M)   → shard-2     │
  │  [75M, 100M)  → shard-3     │
  └────────────┬────────────────┘
               │ user_id=62M → shard-2
               v
          [shard-2 DB]
          Returns result
               │
               v
           Client
```

**Trade-off:** Range queries are fast (sequential scan on one shard). Risk: uneven distribution if recent IDs are all new users — shard 3 takes all new signups while shards 0-2 are idle. This is the **hot shard** / **write hotspot** problem.

#### Strategy 2: Hash-Based Sharding

Apply a hash function to the shard key; use modulo to select a shard.

```python
shard_id = hash(user_id) % num_shards
# user_id = 62,000,000
# hash(62000000) = 3,847,293,847 (example)
# 3,847,293,847 % 4 = 3  → shard-3
```

**Distribution:** Uniform random. 4 shards → each gets ~25% of data assuming good hash function (MurmurHash3, xxHash are common).

**Trade-off:** Eliminates hotspots for uniform access patterns. Destroys range locality — `WHERE user_id BETWEEN 1000 AND 2000` requires querying ALL shards. Resharding (changing `num_shards`) remaps all existing keys — expensive.

#### Strategy 3: Directory-Based (Lookup) Sharding

A separate lookup table stores the mapping from entity to shard.

```
Lookup Service (shard_directory table):
┌────────────────┬──────────┐
│ tenant_id      │ shard_id │
├────────────────┼──────────┤
│ acme-corp      │ shard-4  │
│ globex-inc     │ shard-7  │
│ initech        │ shard-2  │
│ umbrella-corp  │ shard-4  │
└────────────────┴──────────┘
```

The directory service is itself a strongly-consistent, replicated store (often Redis Cluster or etcd). Every query makes a lookup-then-route hop.

**Trade-off:** Maximum flexibility — move tenants between shards without data migration. The directory itself becomes a critical bottleneck and must be highly available. Adds ~1–3 ms latency per query for the lookup round-trip.

#### Strategy 4: Geo/Zone-Based Sharding

Data is pinned to geographic regions, often combining hash sharding within a region.

```
┌─────────────────────────────────────────┐
│              Geo Router                  │
│   user IP / user.region attribute        │
└──────┬──────────┬──────────┬────────────┘
       │          │          │
    EU-West    US-East    AP-SE
    [shard-0]  [shard-1]  [shard-2]
    [shard-1]  [shard-2]  [shard-3]
```

Used heavily for GDPR compliance (EU data must stay in EU), latency reduction (serve users from nearby shards), and regulatory requirements.

### Step-by-Step Write Path Mechanics

```
1. Application writes:  INSERT INTO orders (user_id=42, amount=99.99)

2. Shard router intercepts (library, proxy, or app-layer logic):
   shard = hash(42) % 8  →  shard-6

3. Connection pool selects a connection to shard-6's PRIMARY node

4. Write executes on shard-6 primary:  WAL appended, index updated

5. shard-6 replication to shard-6 replicas (async, ~1–5 ms lag)

6. ACK returned to application (~1–3 ms for local DC write)

Total wall time: 2–5 ms (vs same without sharding at idle: 1–2 ms)
```

### Key Algorithms & Data Structures

| Component | Implementation | Why |
|---|---|---|
| Shard key hash | MurmurHash3 (128-bit, then mod) | Non-cryptographic, ~2 billion keys/sec, uniform |
| Range index | B-tree or sorted array | O(log n) range lookup |
| Directory store | etcd / Redis Cluster | CP system, strong consistency for routing |
| Connection pool | PgBouncer / ProxySQL | 100s of app threads → tens of DB connections |
| Rebalancing | Virtual nodes (vnodes) | Move vnodes not physical shards on resize |

### Misconceptions

❌ **Misconception:** Sharding fixes read performance automatically.
✅ **Reality:** Sharding primarily fixes **write** and **storage** bottlenecks. For reads, you still need replicas on each shard. Sharding also helps reads if your read queries can be routed to a single shard (shard key in WHERE clause).

❌ **Misconception:** You can always add shards without data migration.
✅ **Reality:** With naive hash sharding (`user_id % N`), changing N from 4 to 5 remaps ~80% of data. This requires a full data migration. Consistent hashing reduces this to ~20% of data moving, but it's never zero.

❌ **Misconception:** More shards = always better performance.
✅ **Reality:** Each shard adds operational overhead. With 100 shards, a fan-out query (no shard key in WHERE) hits all 100 shards, aggregates 100 result sets, and often performs **worse** than the original single-DB query. There is an optimal shard count for a given workload.

❌ **Misconception:** Sharding and partitioning are the same thing.
✅ **Reality:** Partitioning (e.g., PostgreSQL `PARTITION BY RANGE`) divides a table on a single server. Sharding distributes partitions across multiple servers. All sharding involves partitioning; not all partitioning involves sharding.

## 3. Real-World Architecture Examples

### Instagram — PostgreSQL Sharding with Logical Shards

**Scale trigger:** 25+ million photos/day, hundreds of millions of likes. Single PostgreSQL instance maxing out on write I/O around 2012.

**What they decided:**
Instagram chose to shard PostgreSQL rather than adopt NoSQL (they evaluated Cassandra and rejected it for operational complexity). They created **thousands of logical shards** mapped to a smaller number of physical PostgreSQL servers.

- **Logical shards:** 2,000 Postgres schemas, each a "shard"
- **Physical servers:** Started with ~10 physical DB servers, each hosting ~200 logical shards
- **Shard key:** User ID embedded in the globally unique ID (Instagram's Snowflake-inspired 64-bit ID)

The 64-bit ID structure:
```
Bit layout: [41 bits: millisecond timestamp] [13 bits: shard_id] [10 bits: sequence]
```

This meant every ID **carried its own routing information** — no directory lookup needed. The shard router extracts bits 10–22 to get the logical shard ID, then consults a config map to find the physical server.

**What they got wrong first:**
They initially considered Twitter's Snowflake service for ID generation but found the additional network hop and operational complexity unacceptable. Their solution: delegate ID generation to each PostgreSQL table using `PL/pgSQL` functions and sequences — IDs generated inside the DB, no extra service.

**Moving logical shards:** When a physical server got too hot, they moved logical shards from it to a new physical server. Because each logical shard was a Postgres schema, migration was: dump schema + data, restore to new server, update config map, no shard key changes required.

**Source:** [Sharding & IDs at Instagram](https://instagram-engineering.com/sharding-ids-at-instagram-1cf5a71e5a5c)

---

### Notion — 480 Logical Shards on 32 Physical PostgreSQL Servers

**Scale trigger:** Mid-2020. Notion's user base exploded during COVID remote work adoption. A single PostgreSQL monolith was running hot; vacuum, index maintenance, and DDL migrations were becoming impossible without user-visible slowdowns.

**What they decided:**
- **480 logical shards** across **32 physical PostgreSQL instances**
- Each physical DB holds 15 logical shards
- **Shard key:** `workspace_id` (their core tenant identifier)
- Routing: application-level, each workspace maps to a shard via `workspace_id % 480`

Why 480? It factors into many numbers: 480 = 2⁵ × 3 × 5. This gives flexibility: 32, 48, 60, 80, 96, 120, 160, 240 physical DBs all divide evenly into 480, so doubling physical capacity never requires remapping logical shards.

**Migration strategy:**
1. Dual-write: new writes go to both monolith and new sharded DB via audit log replay
2. Backfill: migrate historical data in background
3. Traffic cutover per workspace: flip workspace X from monolith to shard, validate, proceed
4. ~18 months total migration timeline

**What they got wrong first:**
Initial design used `page_id` as shard key. This caused cross-shard joins constantly because a single workspace's pages span multiple shards. Rekey to `workspace_id` fixed this — all data for a workspace lives in one shard, so most queries hit a single server.

**Result:** Eliminated 90%+ of cross-shard queries, DDL migrations went from "multi-hour outage window" to "online, rolling, minutes per shard."

**Source:** [Herding elephants: lessons learned from sharding Postgres at Notion](https://www.notion.com/blog/sharding-postgres-at-notion)

### Shopify — Pod Architecture with MySQL Shards

**Scale trigger:** By 2019, Shopify's platform handled millions of shops, billions of orders. A shared MySQL cluster was a single point of contention for all shops.

**What they decided:**
Shopify's "pod" architecture: each pod is an **isolated, self-contained unit** containing:
- One MySQL shard (primary + replicas)
- Redis for caching
- Memcached
- Application servers routed to that pod

Every shop is assigned to exactly one pod. The routing layer (`ShopId → pod_id`) is a lookup-based directory in a fast in-memory store.

**Shard key:** `shop_id`. All tables have `shop_id` as part of their primary key. Queries without `shop_id` are not allowed by application convention (enforced via code review and linting).

**Shard balancing — the hard part:**
As Shopify grew, some pods held "heavy" shops (Black Friday power sellers) that drove CPU/IO spikes. Shopify built **Ghostferry** — a Go tool that:
1. Batch-copies rows from source shard to destination shard
2. Tails MySQL binlog to capture changes during copy
3. Applies binlog deltas to destination
4. Validates row counts and checksums
5. Executes a sub-second cutover with a write lock

Result: terabyte-scale migrations with **< 1 second of shop downtime**. They run shard rebalancing continuously as a background operation.

**What they got wrong first:**
Early versions of their shard balancing required taking the shop offline for minutes. At their scale (millions of merchants), even a 30-second window per shop was unacceptable. It took 18 months of engineering to achieve the sub-second cutover with Ghostferry + binlog tailing.

**Source:** [Shard Balancing: Moving Shops Confidently with Zero-Downtime](https://shopify.engineering/mysql-database-shard-balancing-terabyte-scale)

---

### Stripe — DocDB: Sharding on Top of MongoDB

**Scale trigger:** Stripe processes trillions of dollars in payments. Their original MongoDB setup had no structured sharding. Data movement between nodes required downtime and was operationally fragile.

**What they decided:**
Built **DocDB** — an internal platform layer on top of MongoDB that provides:
- **Chunk-based sharding:** Data divided into ~1 GB chunks, each chunk assigned to a shard
- **Chunk metadata service:** Consistent store of chunk → shard mappings
- **Database Proxy:** Intercepts all reads/writes, looks up chunk location, routes to correct shard
- **Zero-downtime chunk migration:** Dual-write during migration, consistent cutover using MongoDB change streams

**Key insight:** Stripe separated the chunk metadata (where is data?) from the actual data nodes (the MongoDB shards). This lets them move chunks between shards for load balancing without any application changes.

**Cross-shard transactions:** Stripe handles financial consistency with a two-phase commit protocol at the chunk level. They accept some latency cost (~5–10 ms extra for transactions spanning shards) to maintain correctness for payment data.

**Source:** [Stripe's Docdb: How Zero-Downtime Data Movement Powers Trillion-Dollar Payment Processing](https://www.infoq.com/presentations/docdb-online-database/)

### Design Questions to Ask Before Starting

Before choosing a sharding strategy, answer these in a design review:

1. **What is your shard key?** What field will you use to route queries? Is it present in 95%+ of your queries?
2. **What is your data access pattern?** Key-value lookups (hash works), time-series (range works), tenant-isolated (directory works)?
3. **What are your hotspot risks?** Are some entities orders of magnitude more active than others (celebrity users, Shopify's big merchants)?
4. **Do you need cross-shard queries?** If yes, at what frequency? Infrequent background jobs are acceptable. OLTP paths needing cross-shard joins are a red flag.
5. **What is your resharding story?** You will outgrow your initial shard count. How painful is adding shards?
6. **Do you need cross-shard transactions?** If yes, understand that you're accepting either 2PC overhead or eventual consistency.
7. **What is the team's operational maturity?** Sharding multiplies operational complexity by your shard count.

### Scale Evolution: What Changes at Each Level

**1K–10K users (early stage):**
Single PostgreSQL on a large instance. No sharding. Add a read replica for reporting queries. Focus on correct indexes and query optimization. Sharding here is engineering malpractice.

**100K–1M users:**
Single primary + 2–3 read replicas. Add PgBouncer connection pooling. Separate write-heavy tables (events, logs) to a different DB. Still no sharding. Vertical scaling: move to db.r6g.8xlarge (256 GB RAM). This takes you surprisingly far.

**1M–10M users:**
You're feeling write latency spikes at peak. Before sharding, exhaust:
- Async writes where possible (Kafka → consumer → DB)
- Batched inserts instead of row-by-row
- Partition large tables by date on the same server (dramatically speeds up VACUUM, DROP PARTITION for archival)
- Caching hot read paths with Redis

If writes are still the bottleneck, introduce **application-level sharding with 2–4 shards**. Start with a shard count you can multiply (choose 4, plan for 8, 16, 32).

**10M–100M users:**
16–32 shards across dedicated physical servers. Add shard-level connection pooling (PgBouncer per shard). Introduce a shard proxy layer to hide routing from application code. At this scale, begin investing in sharding-aware tooling: automated shard health monitoring, shard rebalancing automation.

**100M+ users:**
100+ shards, multiple availability zones per shard, auto-scaling replicas per shard. Consider whether a NewSQL database (CockroachDB, Google Spanner) now makes more operational sense than managing hundreds of shards. The cross-over point where auto-sharding DBs become cost-competitive with manual sharding is typically 50–100 shards.

## 5. Code / Implementation Perspective

### Python: Shard Router Implementation

```python
import hashlib
import threading
from dataclasses import dataclass
from typing import Optional
import psycopg2
from psycopg2 import pool

@dataclass
class ShardConfig:
    shard_id: int
    host: str
    port: int
    dbname: str
    user: str
    password: str

class ShardRouter:
    """
    Application-level shard router for hash-based sharding.
    
    Usage:
        router = ShardRouter(shard_configs)
        conn = router.get_connection(user_id=12345)
        cursor = conn.cursor()
        cursor.execute("SELECT * FROM users WHERE id = %s", (12345,))
    """
    
    def __init__(self, shard_configs: list[ShardConfig], pool_size: int = 10):
        self.num_shards = len(shard_configs)
        self._pools: dict[int, pool.ThreadedConnectionPool] = {}
        self._lock = threading.Lock()
        
        for config in shard_configs:
            self._pools[config.shard_id] = pool.ThreadedConnectionPool(
                minconn=2,
                maxconn=pool_size,
                host=config.host,
                port=config.port,
                dbname=config.dbname,
                user=config.user,
                password=config.password,
            )
    
    def _get_shard_id(self, shard_key: int | str) -> int:
        """Deterministic shard selection via MurmurHash-style hash."""
        # Use SHA-256 for portability; swap for mmh3 in production
        key_bytes = str(shard_key).encode("utf-8")
        hash_int = int(hashlib.sha256(key_bytes).hexdigest(), 16)
        return hash_int % self.num_shards
    
    def get_connection(self, shard_key: int | str):
        """Returns a DB connection for the shard owning shard_key."""
        shard_id = self._get_shard_id(shard_key)
        return self._pools[shard_id].getconn()
    
    def release_connection(self, shard_key: int | str, conn):
        shard_id = self._get_shard_id(shard_key)
        self._pools[shard_id].putconn(conn)
    
    def scatter_gather(self, query: str, params: tuple = ()) -> list[dict]:
        """
        Fan-out query to ALL shards, merge results.
        Use sparingly — O(num_shards) connections and queries.
        """
        import concurrent.futures
        
        def query_shard(shard_id: int) -> list:
            conn = self._pools[shard_id].getconn()
            try:
                with conn.cursor() as cur:
                    cur.execute(query, params)
                    cols = [desc[0] for desc in cur.description]
                    return [dict(zip(cols, row)) for row in cur.fetchall()]
            finally:
                self._pools[shard_id].putconn(conn)
        
        with concurrent.futures.ThreadPoolExecutor(max_workers=self.num_shards) as ex:
            futures = {ex.submit(query_shard, sid): sid for sid in self._pools}
            results = []
            for fut in concurrent.futures.as_completed(futures):
                results.extend(fut.result())
        return results


# Usage example
if __name__ == "__main__":
    configs = [
        ShardConfig(0, "db-shard-0.internal", 5432, "app", "app_user", "secret"),
        ShardConfig(1, "db-shard-1.internal", 5432, "app", "app_user", "secret"),
        ShardConfig(2, "db-shard-2.internal", 5432, "app", "app_user", "secret"),
        ShardConfig(3, "db-shard-3.internal", 5432, "app", "app_user", "secret"),
    ]
    router = ShardRouter(configs, pool_size=20)
    
    # Single-shard routed query (fast path: ~2 ms)
    user_id = 42
    conn = router.get_connection(shard_key=user_id)
    # ... execute query ...
    router.release_connection(user_id, conn)
    
    # Cross-shard fan-out (slow path: ~20-50 ms)
    all_recent = router.scatter_gather(
        "SELECT id, email FROM users WHERE created_at > NOW() - INTERVAL '1 hour'"
    )
```

### PostgreSQL Table Partitioning (Single-Server Partitioning, Pre-Sharding Step)

```sql
-- Range partition by date: orders table split by month
-- Each partition is a separate heap file, enabling fast DROP old partitions

CREATE TABLE orders (
    id          BIGSERIAL,
    user_id     BIGINT       NOT NULL,
    amount      NUMERIC(12,2) NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    status      TEXT         NOT NULL
) PARTITION BY RANGE (created_at);

-- Create monthly partitions
CREATE TABLE orders_2024_01 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE orders_2024_02 PARTITION OF orders
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ... continue ...

-- Local index per partition (much faster than global index at scale)
CREATE INDEX idx_orders_2024_01_user ON orders_2024_01 (user_id, created_at);

-- Archival: drop partitions older than 2 years (instant, no vacuum needed)
DROP TABLE orders_2022_01;  -- drops in milliseconds regardless of row count
```

```json
}
```

This VSchema tells Vitess to shard `users` and `orders` by `user_id` with a hash function, and to maintain a secondary lookup index so queries by `order_id` alone can still find the right shard (at the cost of one extra lookup hop).

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Manual sharding (app-layer)** | Full control needed; existing SQL DB; team has DB expertise | Maximum flexibility but maximum operational burden; resharding is painful | Instagram, Shopify, Notion, early Twitter |
| **Auto-sharding (NewSQL)** | Greenfield; want SQL semantics without ops; can afford higher $/query | Simplicity and consistency guarantees; less cost control; vendor lock-in | Banks on Spanner, Cockroach-based fintechs |
| **Vertical scaling (scale-up)** | Dataset fits on largest available instance (<20 TB, <100K WPS) | Simpler operations; single point of failure; limited ceiling | Most startups up to $50M ARR |
| **Read replicas only** | Read:Write ratio > 10:1; writes are not the bottleneck | Solves read scale; does nothing for write throughput | Most web apps where reads dominate |
| **Caching layer (Redis)** | Hot read data fits in memory; can tolerate eventual consistency for reads | Dramatically reduces DB read load; adds cache invalidation complexity | Virtually every company at scale |
| **CQRS + event sourcing** | Complex domain; reads and writes have fundamentally different shapes | Decouples read/write scaling; significantly higher code complexity | Fintech, event-driven microservices |
| **Partitioning (same server)** | Large tables; time-series archival; query pruning by partition key | No write bottleneck relief; great for maintenance and query performance on large tables | Analytics workloads, time-series data |

### My Recommendation

Do not shard until you have exhausted the following in order:

1. Query optimization (indexes, EXPLAIN ANALYZE — this fixes 80% of "slow DB" problems)
2. Connection pooling (PgBouncer, ProxySQL — this fixes many "DB overload" problems)
3. Read replicas (for read-heavy workloads)
4. Async processing via queues (Kafka, SQS — offload write spikes from synchronous path)
5. Table partitioning on a single server (for large tables, especially time-series)
6. Vertical scaling to a larger instance

If you have genuinely exhausted all of the above and writes are still the bottleneck, shard. Start with **4 shards** and design for doubling to 8. Use **application-level hash sharding** unless you have a SaaS tenant model (use directory-based) or strong geo requirements (use zone-based). If you're starting fresh and can afford it, use **CockroachDB or Google Spanner** instead — the operational savings from auto-sharding outweigh the cost premium at most scales.

## 8. Trade-offs (Be Opinionated)

### Benefits (with numbers)

- **Write throughput scales linearly:** 4 shards → 4x write throughput ceiling; 8 shards → 8x. Each shard's primary can sustain ~10,000–20,000 writes/second, so 8 shards → 80,000–160,000 writes/second.
- **Storage capacity scales linearly:** 32 shards with 8 TB each → 256 TB total practical capacity.
- **Query isolation:** A slow query on shard-3 does not block queries on shard-0. Noisy neighbor problems are contained to a single shard.
- **Smaller indexes per shard:** An index on 1/8th of the data fits in memory far more easily. A 10 TB table's B-tree index may be 500 GB — won't fit in RAM. Sharded to 8 × 1.25 TB, each shard's index is ~62 GB — much more cache-friendly.
- **Faster DDL and maintenance:** VACUUM, REINDEX, schema changes affect 1/N of the dataset at a time.

### Costs & Limitations (honest, with numbers)

- **Cross-shard queries become expensive:** A scatter-gather query across 32 shards has 32x the I/O and network cost. With 5 ms per shard (in parallel), you're looking at 5 ms + fan-out overhead + merge time = 20–50 ms minimum for any unrouted query.
- **Cross-shard transactions require 2PC:** Two-phase commit adds at least one extra network round-trip (~1–5 ms per hop), and introduces coordinator failure scenarios that can leave transactions in-doubt.
- **Resharding is painful and expensive:** With hash sharding, changing N from 4 to 5 means migrating ~80% of your data. Even with good tooling (Ghostferry, Vitess online DDL), a 10 TB migration at 500 MB/s takes ~6 hours and generates significant replication lag.
- **Operational complexity multiplies by shard count:** With 32 shards, you have 32 primaries, 64+ replicas, 32 backup streams, 32 monitoring streams. Operational burden is genuinely N times a single-DB setup.
- **Application code carries routing logic:** Every ORM query, migration script, and analytics query must be shard-aware. This constraint percolates through your entire codebase. Schema migrations need to run N times.
- **Hot shards are not solved by adding more shards:** If user ID 1 (a celebrity) generates 1,000x normal traffic, they saturate their shard regardless of how many total shards you have. Hot spots require separate mitigation (sharding that specific entity's data, caching, rate limiting).

### Core Tension

**Scalability vs. Operational Simplicity.**

Sharding is a bet that the write throughput and storage gains are worth the permanent increase in operational and application complexity. This bet pays off at large scale. It almost never pays off at small scale.

### My Recommendation

**Shard only when you have clear write saturation evidence** — P99 write latency degrading under load, primary CPU above 70% at peak, or I/O wait consistently above 20%. Instrument first. Most teams shard too early based on fear, not data.

When you do shard: **choose your shard key with extreme care**. The shard key is nearly impossible to change later. A bad shard key (one that creates hot shards or requires frequent cross-shard joins) is worse than no sharding — it gives you the operational complexity without the performance benefits.

## 9. Failure Modes — What Goes Wrong

### Hot Shard (Write Hotspot)

**Trigger:** Shard key has low cardinality, non-uniform access, or is correlated with time (e.g., auto-increment ID with sequential writes always hitting the latest shard). Celebrity users/items generate disproportionate traffic to a single shard.

**Symptoms:** One shard shows 10x–100x the CPU/IO of others in monitoring. Writes to that shard start experiencing timeouts or queue buildup. Read latency spikes on the hot shard's replicas.

**Detection:** Shard-level CPU, I/O, and QPS dashboards (Prometheus + Grafana per shard). Alert when any single shard exceeds 2x the average. DynamoDB exposes this via per-partition consumed capacity metrics.

**Recovery:**
1. Immediate: increase read replica count on hot shard, enable connection pooling throttle to shed read load
2. Tactical: cache the hot entity (Redis TTL cache for the celebrity user's profile)
3. Strategic: re-shard with a composite key that distributes the hot entity's data across multiple shards (e.g., `user_id || bucket` where `bucket = random 0–9`)

**Real Example:** A fintech startup using range-based sharding on `transaction_id` (auto-increment) had Black Friday send 80% of writes to the newest shard (highest range). The shard failed under load. Post-mortem: switched to hash sharding on `account_id`.

---

### Resharding Downtime / Data Inconsistency

**Trigger:** Shard count needs to change (growing beyond capacity, or rebalancing). Hash-based sharding with modulo: changing `N` from 8 to 16 moves ~50% of all data. During migration, the old and new routing tables diverge.

**Symptoms:** Queries return missing data (routed to new location, data not yet migrated). Duplicate writes (double-write period). Replication lag spikes during bulk data copy. Application errors due to split-brain routing.

**Detection:** Consistency validation jobs comparing row counts between old and new locations. Application-level error rate spike. Replication lag monitoring.

**Recovery:**
1. Use a dual-write + backfill + validation + atomic cutover strategy (never flip routing before data is fully validated)
2. Use virtual nodes / consistent hashing to minimize data movement: adding 1 server to a 10-node consistent hash ring moves only ~10% of data
3. Tools: Vitess horizontal resharding, Ghostferry (Shopify), AWS DMS, custom dual-write + binlog tail

**Real Example:** GitHub's migration from a manual MySQL sharding scheme to Vitess required months of careful dual-write periods and validation before each shard cutover to avoid any data loss.

---

### Cross-Shard Query Latency Blowup

**Trigger:** Application adds a feature requiring a query without the shard key in the WHERE clause. This query becomes a scatter-gather hitting all N shards in parallel, collecting results, and merging. At N=100 shards, this is now 100 parallel queries.

**Symptoms:** Specific query types suddenly show P99 latency of 500 ms–2 s. DB connection counts spike (100 connections opened simultaneously). Application threads block waiting for all shards to respond; slowest shard determines total latency.

**Detection:** Slow query log showing queries with full-scan patterns on shard proxy. Tracing (Jaeger/Zipkin) showing fan-out to all shards. Connection pool exhaustion alerts.

**Recovery:**
1. Identify the offending query pattern; determine if shard key can be added (often it can if you restructure the query or denormalize)
2. For analytics/reporting queries: redirect to a dedicated analytics replica or data warehouse (BigQuery, Redshift, Snowflake) that aggregates across all shards
3. Add a secondary index table in a non-sharded store (Elasticsearch for full-text, separate PostgreSQL for cross-shard lookups)
4. Rate-limit the scatter-gather endpoint to prevent connection pool exhaustion

**Real Example:** Notion's initial `page_id` shard key caused every workspace-level query to scatter across all shards. Fixing it required re-keying the entire sharding scheme to `workspace_id`, an 18-month migration effort.

---

### Shard Metadata Service Outage (Directory-Based Sharding)

**Trigger:** The lookup/directory service (etcd, Redis, custom shard map service) that maps keys to shards becomes unavailable or returns stale data.

**Symptoms:** All database queries fail — the router cannot determine which shard to contact. Error rate spikes to 100%. Application treats it as total DB outage even though all data shards are healthy.

**Detection:** Health check on directory service endpoint. Circuit breaker trips when directory service response time > 50 ms.

**Recovery:**
1. Cache the shard map aggressively in application memory (TTL: 30–60 seconds). Stale routing is usually preferable to no routing.
2. Design directory service as highly available (3-node etcd cluster, automatic leader election)
3. For non-directory sharding (hash, range): the router is stateless — no directory outage possible. Directory-based sharding accepts this availability risk as a trade-off for flexibility.

**Real Example:** A large multi-tenant SaaS lost all database access for 12 minutes when their Redis-based shard directory hit an OOM event during a memory spike. Fix: moved shard map to etcd with persistent storage and added local in-process cache with 60s TTL.

## 10. When To Use vs. When To Avoid

### Use When:

✅ **Write throughput exceeds a single primary's capacity:** P99 write latency is degrading under peak load and you've already tuned queries, added connection pooling, and explored async write paths. Rule of thumb: consider sharding above ~15,000 sustained writes/second on PostgreSQL or MySQL.

✅ **Dataset size prevents effective indexing:** Total dataset > 10–20 TB and your working set (hot data) no longer fits in the largest available server's RAM (512 GB on db.r6g.metal). Index pages being evicted from cache cause 10–100x latency spikes on cache misses.

✅ **Tenant isolation is a hard requirement:** Multi-tenant SaaS where compliance, security, or SLA requirements mandate that tenant A's queries cannot be impacted by tenant B. A pod or directory-based sharding model gives hard isolation boundaries.

✅ **Geographic data locality is required:** GDPR requires EU user data to remain in EU data centers, or you need to minimize cross-region latency for global users. Geo/zone sharding achieves this cleanly.

### Do NOT Use When:

❌ **You haven't saturated a single node:** If your primary DB CPU is under 50% at peak and your write P99 is under 10 ms, you don't need sharding. Premature sharding adds enormous complexity with zero benefit.

❌ **Your workload is read-dominated:** If reads:writes > 10:1, read replicas solve your problem at a fraction of the operational cost. Sharding write capacity you don't need is waste.

❌ **Your queries frequently require cross-shard joins:** If your most common queries join entities that would land on different shards, you have not found a valid shard key. No shard key = forced scatter-gather on every query = worse performance than a single DB. Go back and redesign the data model before sharding.

❌ **Your team lacks database operational experience:** Sharding doubles or triples the operational burden of running your database fleet. If you don't have engineers who can confidently perform a zero-downtime shard migration, debug replication lag under load, and operate N independent DB primaries, the risk of data loss or extended outage is high.

❌ **Your data model requires frequent global aggregations:** OLAP workloads that routinely `COUNT(*)`, `SUM()`, or `GROUP BY` across the entire dataset will be miserable on a sharded OLTP database. Use a dedicated analytics system (data warehouse + ETL) instead.

### The #1 Mistake Engineers Make

⚠️ **Choosing the wrong shard key — specifically, using an auto-incrementing ID or timestamp as the shard key in a hash-sharded system, or using it as-is in a range-sharded system.**

- Auto-increment + range sharding: all new writes go to the latest shard. 95% of your shards are cold, 1 shard is on fire.
- Auto-increment + hash sharding: works for even distribution but completely destroys any time-range query performance (range scans must fan out to all shards).
- The right key is the one that appears in the WHERE clause of your most frequent, most latency-sensitive queries, and distributes writes evenly.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a URL shortener that needs to handle 100 billion URLs. How would you store and look up URLs?"
- "Twitter needs to store 500 million tweets per day. How would you design the tweet storage layer?"
- "Design a multi-tenant SaaS application where you must guarantee tenant data isolation."
- "How would you scale Instagram's database to handle 1 billion users?"
- "Walk me through the trade-offs between hash sharding and range sharding. When would you use each?"
- "Your database is experiencing write bottlenecks at 50,000 writes/second. What do you do?"
- "How would you re-shard a database that's already in production without downtime?"

### What the Interviewer Is Evaluating

1. **Scale instinct:** Do you know when sharding is and isn't needed? Do you exhaust simpler options first?
2. **Shard key reasoning:** Can you identify a good shard key for a given data model and access pattern?
3. **Hot spot awareness:** Do you proactively identify celebrity/hotspot problems and propose mitigations?
4. **Operational reality:** Do you address resharding, monitoring, cross-shard queries — or do you just draw a box labeled "shard"?
5. **Trade-off articulation:** Can you clearly state what you're giving up (cross-shard query performance, operational complexity) to gain write scale?

### Questions YOU Ask Before Answering

- "What is the primary access pattern? Are we doing key-value lookups, time-range queries, or full scans?"
- "What is the expected read:write ratio?"
- "Are there any hot entities — celebrities, viral posts, high-volume merchants — that might dominate traffic?"
- "Do we have multi-tenancy requirements? Does data isolation matter per tenant?"
- "What are the geographic requirements — single region, multi-region, data residency?"
- "Are there any cross-entity queries that must be low-latency?"

### Junior (L3–L4) Answer

Knows that sharding splits data across multiple servers. Can describe hash vs. range sharding at a conceptual level. Identifies that you need a shard key. May not proactively address hot spots, resharding, or cross-shard query problems unless asked.

**Expected to say:** "We shard by user_id using consistent hashing. Each shard is a separate MySQL instance."

**Not expected to know:** Dual-write migration strategies, vnode-based consistent hashing, how to handle cross-shard transactions.

### Senior (L5) Answer

Drives through the full design: shard key selection with justification, routing mechanism, hot spot identification and mitigation, cross-shard query strategy, and a concrete resharding plan. Identifies the operational cost explicitly.

**Expected to cover:**
- Why a specific shard key is chosen over alternatives
- Hot spot risk for specific entities (celebrity problem)
- Cross-shard queries: which are acceptable (background jobs), which are not (OLTP paths)
- Resharding: logical shards allow physical re-mapping without key changes (Instagram/Notion approach)
- Connection pooling per shard

**Key numbers to know:** single MySQL/PG primary caps around 10,000–20,000 writes/second; a 4-shard cluster → ~4x; hash(key) % N is the simplest router; consistent hashing moves O(1/N) data on resize.

### Staff (L6+) Answer

Connects sharding to the broader system design. Challenges the requirement — is sharding actually necessary, or does async processing / caching solve the problem? Discusses organizational impact: schema migrations, on-call burden, engineer velocity.

**Expected to cover:**
- Exhaustion of pre-sharding options before recommending sharding
- Build vs. buy: evaluate Vitess / CockroachDB / Spanner vs. hand-rolled application sharding
- Migration strategy in detail: dual-write + backfill + validation + cutover, with concrete tooling
- Monitoring and alerting design for a sharded fleet
- Long-term resharding story: why 480 (Notion) or 2000 (Instagram) logical shards is better than 4 physical shards as the initial setup
- Cross-team impact: how sharding constraints (shard key in every query) affect product engineering velocity

### Key Facts and Numbers to Memorize

| Fact | Number |
|---|---|
| PostgreSQL single primary write ceiling | ~15,000–20,000 writes/second |
| MySQL single primary write ceiling | ~10,000–15,000 writes/second |
| Hash reshard data movement (modulo) | ~(N-1)/N × 100% — changing 4→5 moves ~80% |
| Consistent hashing data movement on resize | ~1/N × 100% — adding 1 to 10 nodes moves ~10% |
| Notion logical shards | 480 logical / 32 physical |
| Instagram logical shards (early) | 2,000 logical schemas in PostgreSQL |
| Directory lookup overhead | 1–3 ms per query (Redis round-trip) |
| Cassandra max partition size | < 100 MB ideal, < 10 MB recommended |
| DynamoDB per-partition limits | 3,000 RCU / 1,000 WCU per partition |
| Cross-shard scatter-gather (32 shards) | 20–100 ms typical (vs 2–5 ms single-shard) |
