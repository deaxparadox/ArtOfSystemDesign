## 1. What Is It? (Theory)

### The Plain-English Version

A **Saga** is a way to execute a multi-step business operation across several independent services — each with its own database — without ever holding a global lock or needing all services to agree simultaneously.

Instead of "do everything at once or nothing at all" (what a database transaction gives you), a Saga says: "do each step locally, and if a later step fails, explicitly undo the earlier steps."

The undo operations are called **compensating transactions**.

### The Problem It Solves at Scale

In a monolith with a single database, you get this for free:

```sql
BEGIN;
  UPDATE orders SET status = 'confirmed';
  UPDATE inventory SET stock = stock - 1;
  INSERT INTO payments VALUES (...);
COMMIT; -- all three changes land atomically
```

Once you split into microservices — Order Service, Inventory Service, Payment Service, each with its own Postgres instance — that `BEGIN/COMMIT` span is physically impossible. There is no shared transaction coordinator your application controls.

The naive solution is **Two-Phase Commit (2PC)**. It works in theory: a coordinator asks every participant to "prepare" (lock your resources), then "commit" once all say yes. In practice at scale, 2PC breaks badly:

- The coordinator is a single point of failure. If it crashes between "prepare" and "commit," every participant holds a lock forever (indefinite blocking).
- Round-trip latency multiplies with every participant. At 3+ services, a single 2PC adds 4–6 network round-trips versus 1–2 for a local transaction.
- XA transactions (the standard 2PC implementation in databases) are 10–100x slower than local transactions in benchmarks due to lock retention overhead.
- Cloud-native databases (DynamoDB, Spanner, CockroachDB) simply do not expose XA interfaces.

Sagas were invented in 1987 by Garcia-Molina and Salem specifically for **long-lived transactions** where holding locks for seconds or minutes would kill throughput. The pattern was resurrected in the mid-2010s when companies like Uber, Netflix, and Amazon moved from monoliths to microservices and rediscovered the same problem at internet scale.

### Real-World Analogy

Think of booking a vacation package: you separately book a flight, a hotel, and a rental car. You do not hold all three "on reserve with a global lock" until everything is confirmed. Instead:

1. Book the flight. Get a confirmation.
2. Book the hotel. Get a confirmation.
3. Book the rental car. Get a confirmation.

If step 3 fails (no cars available), you **cancel** the hotel and **cancel** the flight. Those cancellations are your compensating transactions. At no point did the airline and hotel systems need to talk to each other.

### Concrete Example with Real Numbers

An e-commerce order placement might look like this:

| Step | Service | Local Transaction | Duration |
|------|---------|-------------------|----------|
| 1 | Order Service | INSERT order (status=PENDING) | ~5 ms |
| 2 | Inventory Service | DECREMENT stock by 1 | ~8 ms |
| 3 | Payment Service | Charge credit card via Stripe | ~200–800 ms |
| 4 | Notification Service | Send confirmation email | ~50 ms |
| 5 | Order Service | UPDATE order (status=CONFIRMED) | ~5 ms |

Total happy-path latency: ~270–870 ms.

If step 3 fails (card declined), compensating transactions run:
- Compensate step 2: INCREMENT stock by 1 (re-add inventory)
- Compensate step 1: UPDATE order (status=CANCELLED)

No other service ever knew there was a "global transaction." Each service only executed a local write that completed and released its lock within milliseconds.

## 2. How It Actually Works (Deep Mechanics)

### Two Coordination Styles

#### Choreography-Based Saga

Each service publishes events after completing its local transaction. Other services listen for those events and react. There is no central orchestrator — the "flow" is emergent from the event contracts.

```
Order Service                Inventory Service           Payment Service
     |                              |                          |
     |-- CREATE order               |                          |
     |-- PUBLISH OrderCreated ----->|                          |
     |                              |-- RESERVE stock          |
     |                              |-- PUBLISH StockReserved ->|
     |                              |                          |-- CHARGE card
     |                              |                          |-- PUBLISH PaymentProcessed
     |<- (listen) PaymentProcessed -|<-------------------------|
     |-- UPDATE order=CONFIRMED     |                          |

FAILURE PATH (card declined):
                                                               |-- PUBLISH PaymentFailed
                              |<--- PaymentFailed ------------|
                              |-- RELEASE stock               |
                              |-- PUBLISH StockReleased       |
     |<-- StockReleased ----  |                               |
     |-- UPDATE order=CANCELLED                               |
```

**Choreography pros:** No single point of failure. Services are loosely coupled. Easy to add new participants (just subscribe to events).

**Choreography cons:** The overall flow is invisible — it lives in the events, not in one place. Debugging requires tracing events across 4+ services. As complexity grows (10+ steps, conditional branches), the mental model explodes.

#### Orchestration-Based Saga

A dedicated Saga Orchestrator (or a durable workflow engine) explicitly commands each service in sequence. It persists its own state, so if it crashes it resumes exactly where it left off.

```
                        +------------------+
                        |  Saga Orchestrator|
                        |  (state persisted)|
                        +------------------+
                               |
        +-----------+----------+-----------+-----------+
        |           |                      |           |
        v           v                      v           v
  Order Svc   Inventory Svc          Payment Svc  Notification Svc
  (create)    (reserve stock)        (charge)     (send email)

Orchestrator state machine:
  PENDING_ORDER_CREATION
    -> PENDING_INVENTORY_RESERVATION
      -> PENDING_PAYMENT
        -> PENDING_NOTIFICATION
          -> COMPLETED

  On failure at PENDING_PAYMENT:
    -> COMPENSATING_INVENTORY   (release stock)
      -> COMPENSATING_ORDER     (cancel order)
        -> FAILED
```

**Orchestration pros:** Flow is explicit and visible. Easier to debug (one service owns the saga state). Better for complex conditional logic (if payment method == BNPL then route to X else Y).

**Orchestration cons:** The orchestrator is a new service you must build, deploy, and scale. It can become a coupling point. If not built on a durable execution engine, the orchestrator itself can fail mid-saga and leave things inconsistent.

### Key Algorithms and Data Structures

**Saga Log / State Machine Table**

Every orchestrated saga needs a persistent record:

```
saga_executions table:
  id              UUID PRIMARY KEY
  saga_type       VARCHAR (e.g., 'place_order')
  current_step    VARCHAR
  status          ENUM(STARTED, COMPENSATING, COMPLETED, FAILED)
  correlation_id  UUID   -- ties all events to this saga
  created_at      TIMESTAMP
  updated_at      TIMESTAMP
  payload         JSONB  -- context passed between steps
```

**Compensating Transaction Design Rule**

Every forward action must have a defined compensating action. The compensating action must be:
1. **Idempotent** — running it twice should produce the same result as running it once (critical: the broker may redeliver the compensation command)
2. **Semantically reversible** — "cancel reservation" not "delete row" (you want an audit trail)
3. **Eventually consistent** — compensation does not need to be instant, but it must complete

Not all operations are perfectly reversible (you cannot un-send an email). These are called **pivot transactions** — once they cross, backward compensation becomes approximate (e.g., send a cancellation email).

### Real Numbers

| Metric | 2PC | Saga (Choreography) | Saga (Orchestration w/ Temporal) |
|--------|-----|---------------------|-----------------------------------|
| Locks held duration | Seconds (until global commit) | ~5–20 ms (local only) | ~5–20 ms (local only) |
| Network round-trips (3 services) | 6 (prepare×3 + commit×3) | 3 (one event per step) | 3–4 (command + ack per step) |
| Coordinator SPOF | Yes — crash = stuck locks | No | Depends on engine HA config |
| Throughput degradation under load | Severe (lock contention) | Minimal | Minimal |
| Typical saga overhead vs no-saga | — | +10–30 ms (broker latency) | +20–50 ms (state persistence) |
| Max practical participants | ~3–5 (beyond this, 2PC collapse) | Unlimited | Unlimited |

### Misconceptions

**Misconception: Sagas are just eventual consistency and you lose strong consistency.**
**Reality:** You lose *isolation* (intermediate states are visible), not correctness. A well-implemented saga with idempotent compensating transactions is correct — every saga either reaches a defined completed state or a fully compensated state. The difference from ACID is that during execution, other readers can see partial progress. For most business operations (order placement, account signup), this is acceptable.

**Misconception: Choreography is simpler than orchestration.**
**Reality:** Choreography is simpler to *start* but harder to operate at scale. With 6+ services and conditional flows, the event graph becomes impossible to reason about without dedicated tooling. Orchestration adds explicit complexity upfront but pays off quickly.

**Misconception: Compensating transactions are perfect rollbacks.**
**Reality:** Compensation is semantic reversal, not time-travel. You cannot undo an email already sent, a webhook already fired, or an audit log already written. Design your saga to minimize side effects before the pivot transaction.

**Misconception: The saga orchestrator is a single point of failure.**
**Reality:** Modern durable execution engines (Temporal, Conductor) are multi-node, HA clusters. The orchestrator's state is replicated. A single node failure does not halt sagas — another node picks up from the last persisted checkpoint.

## 3. Real-World Architecture Examples

### Uber — From Cadence to Temporal

**Scale trigger:** By 2016, Uber had hundreds of microservices. Driver-rider matching, surge pricing, and trip completion each required coordinating 5–15 services. Ride booking could fail mid-way, leaving a driver reserved but no payment captured.

**What they built first:** Uber's initial approach used a custom saga implementation per workflow — hand-rolled state machines in each service. This worked at small scale but collapsed when they hit 50+ workflow types. Each team implemented retries and timeouts differently, leading to inconsistent compensation logic and multiple production incidents where partial states persisted for hours.

**What they built second:** Uber open-sourced **Cadence** in 2017 — a durable execution engine that models workflows as code, not configuration. The key insight: instead of persisting a state-machine table, Cadence replays the entire workflow function from an event history on each resume. This made compensation logic trivially easy to express in regular code.

**Production numbers:** At Uber, Cadence ran over **100 workflow types** with millions of active workflow executions at any time. Ride booking sagas complete in under 2 seconds end-to-end for the happy path. Cadence later became the open-source **Temporal**, with Temporal Cloud advertising 99.99% SLA and handling workloads exceeding 100 million workflow executions per month for large customers.

**Key lesson from Uber:** Sagas implemented as hand-rolled state machines in relational tables collapse in operational complexity past ~20 workflow types. Use a durable execution engine from the start if you anticipate complex, long-running flows.

### Netflix — Conductor and Video Processing Sagas

**Scale trigger:** Netflix encodes each video into 2,200+ codec/bitrate combinations. Encoding a single title is a 30-step workflow involving hundreds of compute workers, external CDN pushes, and metadata updates. A failure mid-way could leave 400 of 2,200 renditions published and 1,800 missing — a visible customer-facing bug.

**What they built:** Netflix open-sourced **Conductor** in 2016 — a JSON-defined workflow engine backed by Redis (for state) and Elasticsearch (for querying). Conductor models workflows as Directed Acyclic Graphs of tasks. Compensation is defined as a special "terminate" task that runs rollback worker logic.

**Architecture specifics:** Conductor separates the orchestration engine from the business logic workers. The engine stores workflow state and schedules tasks via a pull queue. Workers poll the queue, execute their logic (encode a video segment, push to CDN), and report results back. Conductor handles retries, timeouts, and saga compensation without any coordination logic living in the workers themselves.

**Production numbers:** Netflix reports Conductor handles millions of workflow executions per day, with individual workflows having up to 100+ tasks. Workflow state is persisted so a worker crash during a 2-hour encoding job does not restart the entire job — only the failed task retries.

**Key lesson from Netflix:** For compute pipelines (as opposed to financial transactions), saga compensation is often "just delete the partial output and retry the step" — a much simpler compensation model than financial workflows. Choose your compensation granularity to match your domain.

### Amazon — Order Fulfillment at Scale

**Scale trigger:** During Prime Day 2019, Amazon processes millions of orders per hour. An order touches: inventory reservation, payment authorization, warehouse pick-list generation, carrier assignment, and customer notification. Running this as a synchronous chain fails catastrophically under burst load — one slow downstream service (e.g., carrier API at 900 ms) creates backpressure that collapses the entire order pipeline.

**What they use:** Amazon uses a choreography-based saga via SQS and SNS for the majority of order flow. The Order Service writes the order to its own DynamoDB table and publishes an `OrderPlaced` event to SNS. Each downstream service subscribes to its relevant topic, executes its local transaction, and publishes its completion event. Compensation events (`InventoryReleased`, `PaymentVoided`) flow backward through the same mechanism.

**Why choreography over orchestration at Amazon scale:** With 100K+ orders per minute during peaks, adding an orchestrator in the critical path would introduce a coordination bottleneck. The async, event-driven choreography allows each service to scale independently — the Payment Service can have 500 consumers while the Notification Service runs 20, without any coordination service being aware of or routing to either.

**AWS Step Functions for complex flows:** For lower-volume but higher-complexity flows (fraud review, compliance holds, international order routing), Amazon uses AWS Step Functions as the orchestrator. Step Functions charges $0.025 per 1,000 state transitions, making it cost-effective for complex flows but not for high-throughput commodity operations.

**Key lesson from Amazon:** Choose choreography for high-throughput commodity flows and orchestration for low-volume complex flows. The two approaches coexist within the same company and even within the same product.

### Design Questions to Ask Before Starting

1. **What is the pivot transaction?** Which step, once completed, cannot be fully reversed? (Usually: sending money, sending an email to a user.) All steps after the pivot need forward-only compensation (e.g., issue refund, not void payment).

2. **What are the consistency requirements per step?** Some steps are read-heavy and tolerate stale reads; others (inventory reservation) require strong consistency within their own service.

3. **How do we detect a stuck saga?** What is the timeout on each step? What happens when a saga runs for 30 minutes without completing? Every saga needs a maximum duration and a dead-letter strategy.

4. **Are compensating transactions idempotent?** The message broker will redeliver. Your `ReleaseStock` handler will be called at least once but potentially twice. Is your inventory service prepared for that?

5. **What observability do we need?** How will on-call engineers know a saga is stuck at step 3 of 6? What dashboards and alerts do we need?

6. **Choreography or orchestration?** If the flow has conditional branching, more than 5 steps, or needs to be auditable for compliance, use orchestration. If it is a simple linear chain under high throughput, choreography is viable.

### Scale Evolution

**1K users/day — Monolith with local transactions**
You do not need sagas. A single database with `BEGIN/COMMIT` handles everything. Introducing saga complexity here is premature optimization.

**100K users/day — First microservice split**
You have 2–3 services. A hand-rolled saga with a `saga_state` table in your primary database and a message queue is sufficient. Compensating transactions are rare (1–2% of flows). Keep it simple: a background job that detects stuck sagas and retries or compensates.

**1M users/day — 5–10 services, 10–20 saga types**
Hand-rolled sagas become operationally unmanageable. Migrate to an orchestration engine: AWS Step Functions (managed, pay-per-use), Temporal (self-hosted or cloud, more powerful), or Conductor (self-hosted, good for data pipelines). At this scale you also need: distributed tracing on every saga step (correlation IDs through all services), saga-level dashboards, and tested compensation paths.

**100M users/day — Amazon/Netflix/Uber tier**
You have specialized teams per workflow domain. High-throughput commodity flows use choreography (events via Kafka at 500K events/sec). Complex or regulated flows use orchestration (10K–100K orchestrated sagas/sec via a Temporal cluster). You have multiple saga frameworks coexisting. Compensation testing is part of your CI pipeline — chaos engineering intentionally fails saga steps in staging environments to verify compensation paths work.

### Decision Points and Why

| Decision | Choose A | Choose B | Why |
|----------|---------|---------|-----|
| Choreography vs Orchestration | < 5 steps, high throughput, simple linear | Complex branching, compliance, < 50K/min | Visibility vs throughput trade-off |
| Build vs Buy orchestrator | If you have specific latency needs + budget for platform team | Otherwise | Temporal/Step Functions saves months of engineering |
| Sync vs Async saga steps | Never for distributed sagas | Always async | Sync chaining recreates 2PC blocking problem |
| Outbox vs direct publish | Always use Outbox | Never publish directly to broker from business logic | Direct publish + DB write is not atomic |

## 5. Code / Implementation Perspective

### Python: Orchestration-Based Saga (Runnable Pseudocode)

This sketches an orchestrated order-placement saga with compensation. It mirrors how Temporal workflows work conceptually without requiring Temporal SDK.

```python
import uuid
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, List, Optional

class SagaStatus(Enum):
    PENDING = "PENDING"
    COMPLETED = "COMPLETED"
    COMPENSATING = "COMPENSATING"
    FAILED = "FAILED"

@dataclass
class SagaStep:
    name: str
    action: Callable[..., dict]         # the forward operation
    compensation: Callable[..., None]   # the undo operation
    result: Optional[dict] = None
    completed: bool = False

@dataclass
class SagaContext:
    saga_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    status: SagaStatus = SagaStatus.PENDING
    completed_steps: List[SagaStep] = field(default_factory=list)

class SagaOrchestrator:
    def __init__(self, steps: List[SagaStep]):
        self.steps = steps

    def execute(self, ctx: SagaContext, payload: dict) -> dict:
        for step in self.steps:
            try:
                print(f"[{ctx.saga_id}] Executing step: {step.name}")
                result = step.action(payload)
                step.result = result
                step.completed = True
                ctx.completed_steps.append(step)
                payload.update(result)  # enrich context for next steps
            except Exception as e:
                print(f"[{ctx.saga_id}] Step '{step.name}' failed: {e}")
                ctx.status = SagaStatus.COMPENSATING
                self._compensate(ctx, payload)
                ctx.status = SagaStatus.FAILED
                raise RuntimeError(f"Saga failed at step '{step.name}'") from e

        ctx.status = SagaStatus.COMPLETED
        return payload

    def _compensate(self, ctx: SagaContext, payload: dict) -> None:
        for step in reversed(ctx.completed_steps):
            try:
                print(f"[{ctx.saga_id}] Compensating step: {step.name}")
                step.compensation(payload)
            except Exception as e:
                # Log and alert — compensation failures need manual intervention
                print(f"[{ctx.saga_id}] COMPENSATION FAILED for '{step.name}': {e}")
                # Do NOT raise — continue compensating remaining steps

# --- Service stubs ---

def create_order(payload: dict) -> dict:
    order_id = str(uuid.uuid4())
    print(f"  Created order {order_id}")
    return {"order_id": order_id}

def cancel_order(payload: dict) -> None:
    print(f"  Cancelled order {payload['order_id']}")

def reserve_inventory(payload: dict) -> dict:
    print(f"  Reserved 1 unit of SKU {payload.get('sku', 'SKU-001')}")
    return {"reservation_id": str(uuid.uuid4())}

def release_inventory(payload: dict) -> None:
    print(f"  Released reservation {payload.get('reservation_id')}")

def charge_payment(payload: dict) -> dict:
    # Simulate a payment failure
    raise ValueError("Card declined")

def void_payment(payload: dict) -> None:
    print(f"  Voided payment for order {payload.get('order_id')}")

# --- Usage ---
steps = [
    SagaStep("CreateOrder",        create_order,       cancel_order),
    SagaStep("ReserveInventory",   reserve_inventory,  release_inventory),
    SagaStep("ChargePayment",      charge_payment,     void_payment),
]

orchestrator = SagaOrchestrator(steps)
ctx = SagaContext()

try:
    result = orchestrator.execute(ctx, {"sku": "SKU-001", "amount_cents": 4999})
    print(f"Saga completed: {result}")
except RuntimeError as e:
    print(f"Saga ended in status: {ctx.status.value}")
```

**Expected output:**
```
[<uuid>] Executing step: CreateOrder
  Created order <uuid>
[<uuid>] Executing step: ReserveInventory
  Reserved 1 unit of SKU SKU-001
[<uuid>] Executing step: ChargePayment
[<uuid>] Step 'ChargePayment' failed: Card declined
[<uuid>] Compensating step: ReserveInventory
  Released reservation <uuid>
[<uuid>] Compensating step: CreateOrder
  Cancelled order <uuid>
Saga ended in status: COMPENSATING -> FAILED
```

### Language-Agnostic Algorithm

```
FUNCTION executeSaga(steps[], payload):
  completedSteps = []

  FOR step IN steps:
    TRY:
      result = step.action(payload)
      payload = merge(payload, result)
      completedSteps.append(step)
    CATCH error:
      FOR step IN reverse(completedSteps):
        TRY:
          step.compensate(payload)
        CATCH compensationError:
          alertOncall(step, compensationError)  // never swallow
      RAISE SagaFailed(error)

  RETURN payload
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|----------|------------|---------------|---------------|
| **Saga (Choreography)** | High-throughput, simple linear flows, < 5 steps | No central coordination = hard to debug | Amazon order flow, Shopify webhook chains |
| **Saga (Orchestration)** | Complex flows, branching logic, compliance needs, 5+ steps | Orchestrator complexity = new operational burden | Uber, Netflix, Airbnb booking |
| **Two-Phase Commit (2PC / XA)** | Single datacenter, all services share database vendor, < 3 participants, low throughput | Distributed locks + coordinator SPOF = availability killer under load | Legacy banking systems, single-DB monoliths |
| **Outbox + Event Relay only** | Simple event chains with no business-level compensation needed | No compensation = data inconsistencies require manual repair | Many internal audit/notification flows |
| **TCC (Try-Confirm-Cancel)** | Financial systems needing tighter isolation than Saga | Requires explicit "try" reservation API on every participant service | Ant Financial (Alipay), some payment processors |
| **Idempotent APIs + retries only** | Simple at-most-twice operations with naturally idempotent endpoints | Only works if all operations are side-effect-free or idempotent | Stripe webhook delivery, simple CRUD replication |

### Opinionated Narrative

**For most teams building microservices today (2025), the right answer is orchestration-based saga using Temporal or AWS Step Functions.** Choreography looks simpler on day one but becomes an operational nightmare past 5 services: you cannot answer "what is the current state of order 12345?" without querying 4 databases and correlating events by hand.

2PC is dead for anything beyond a monolith with 2–3 tightly coupled services. If you are considering 2PC across independently deployed microservices, you have not fully committed to the distributed systems model — fix the architecture first.

TCC is strictly more powerful than basic Saga (it preserves more isolation by using explicit reservation phases), but the operational cost of requiring every participating service to implement a three-phase API is enormous. Use it only if your domain genuinely requires near-ACID isolation across services (high-value financial transactions with strict regulatory requirements).

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Availability:** Saga steps hold local locks for 5–20 ms versus 2PC's seconds-long global locks. This means saga-based systems can sustain 10–50x higher throughput under load before lock contention becomes a bottleneck.
- **Fault isolation:** A Payment Service outage does not lock the Order Service's database. The saga simply accumulates failures and compensates asynchronously.
- **Independent scalability:** Each saga step runs in its service, which scales independently. The Payment Service can have 200 replicas while the Notification Service runs 5.
- **Observable state:** With an orchestrated saga, you can answer "show me every order stuck at the payment step" with a single query to the saga state store.
- **No distributed lock manager:** You eliminate an entire class of infrastructure (XA coordinator, distributed lock service) that is fragile and expensive.

### Costs and Limitations

- **No isolation between sagas:** Intermediate states are visible. A second saga that reads inventory while the first saga is mid-execution can see stale data. At high concurrency (1K+ sagas/minute), this causes anomalies — the "lost update" and "dirty read" problems do not disappear, they just require application-level mitigation (semantic locks, process managers, versioned entities).
- **Compensation complexity:** Every forward action must have a tested, idempotent compensating action. For a 10-step saga, you write 10 forward actions + 10 compensating actions + 10 idempotency handlers. This is roughly 3x the code compared to a monolithic transaction.
- **Eventual consistency latency:** In a choreography saga, a compensating event may take 500 ms – 2 seconds to propagate through the event broker and complete. During that window, the system is in an inconsistent state. Users may see a "refund pending" state for 1–5 seconds rather than instant reversal.
- **Operational complexity:** You need correlation IDs through all services, saga-level distributed tracing, alerting on stuck sagas, dead-letter handling for undeliverable compensation messages, and runbooks for manual compensation when automated compensation itself fails.
- **Testing is harder:** You must test not just happy paths but every compensation path, including compensation failures. A unit test suite alone is insufficient — you need integration tests with injected failures.

### Core Tension

**Consistency vs. Availability.** Sagas trade the illusion of atomic, isolated global consistency for the reality of high availability and independent scalability. You are not getting something for nothing: the isolation guarantees your database previously handled silently are now your application's responsibility to manage explicitly.

### My Recommendation

**Use sagas for any business workflow that spans more than one service with its own database.** This is the correct default for microservices. The alternative — bolting services together via 2PC or shared databases — is worse in every operational dimension past 100K requests/day.

**Use orchestration (Temporal or Step Functions) over choreography unless your throughput is genuinely above 50K flows/minute or your flow has fewer than 4 linear steps.** The observability and debuggability of orchestration pays for itself within the first production incident.

**Do not build your own durable execution engine.** Teams that hand-roll saga state machines in relational tables underestimate the operational surface: dead-letter handling, timeout escalation, compensation failure alerts, replay on resume, cross-region failover. Use Temporal or Step Functions. The engineering hours saved in the first year alone justify the cost.

**Budget for compensation testing** from day one. Every sprint that ships a new saga step should include a test that intentionally fails that step and verifies the compensating path completes correctly. This is non-negotiable.

## 9. Failure Modes — What Goes Wrong

### Compensation Failure (Double Refund / No Refund)

- **Trigger:** The compensating transaction itself fails or is non-idempotent. For example, the `VoidPayment` handler calls Stripe's Refund API, Stripe returns a timeout, the broker redelivers the compensation command, and `VoidPayment` runs again — issuing a second refund.
- **Symptoms:** Customer receives double refund (financial loss) or no refund at all (customer complaint escalation). Finance reconciliation shows negative-balance transactions.
- **Detection:** Stripe payment dashboard shows duplicate refund_created events on same payment_intent_id. Saga state store shows compensation step retried > 1 time.
- **Recovery:** Add idempotency key to all Stripe API calls (use `correlation_id` as idempotency key). Add deduplication check in compensation handler: "if payment already voided/refunded, return success immediately." Implement financial reconciliation job that runs hourly and flags sagas where forward action and compensation both show as completed.
- **Real Example:** A fintech startup in 2019 reported a $86K loss from non-idempotent compensation handlers. A payment service outage caused 140 compensation commands to be retried 2–3 times each, with each retry issuing a new refund call to their payment provider.

### Stuck Saga / Missing Timeout (Zombie Saga)

- **Trigger:** A saga step sends a command to a service that never responds (the service is down, the message is lost in a dead-letter queue, or a network partition dropped the message). The saga waits indefinitely.
- **Symptoms:** Saga stays in `PENDING_PAYMENT` state for hours or days. Customer sees "order processing" forever. Inventory remains reserved, blocking other orders from purchasing the same SKU.
- **Detection:** Alert on sagas where `updated_at < NOW() - 15 minutes AND status = PENDING`. Query the saga state store for in-flight sagas older than your SLA. Temporal's built-in workflow timeout (`WorkflowExecutionTimeout`) and activity timeout (`ScheduleToCloseTimeout`) prevent this if configured.
- **Recovery:** Every saga step must have an explicit timeout (e.g., 30 seconds for payment, 5 seconds for inventory). On timeout, trigger the compensation path — treat timeout as a failure. Set `ScheduleToCloseTimeout = 30s` on all Temporal activities. For stuck sagas already in production, write a remediation script that force-transitions them to FAILED and runs compensation.
- **Real Example:** An e-commerce company during a Black Friday sale had their carrier assignment service go down for 22 minutes. 14,000 orders got stuck at the "AssignCarrier" step. Because there were no timeouts, orders held reserved inventory for 22 minutes. When the service recovered, some inventory that should have been released had already been sold to other customers by a manual workaround, creating overselling.

### Lost Isolation / Dirty Reads at High Concurrency

- **Trigger:** Two sagas for the same resource run concurrently. Saga A reserves the last unit of inventory (step 2). Saga B also reads inventory and sees 1 unit available (step 2), before Saga A's reservation is confirmed. Both proceed to payment. One saga will fail at or after payment with a compensating cascade.
- **Symptoms:** Inventory overselling. Two customers receive confirmation emails for the same last item. One order is later silently cancelled (after compensation), leaving the second customer confused.
- **Detection:** Inventory reconciliation job: `SELECT sku, actual_stock, sum(reserved) FROM inventory JOIN reservations — if actual_stock < sum(reserved), you have a race condition.`
- **Recovery:** Use **semantic locks** at the application layer: before Saga B reaches the inventory step, check if Saga A holds a pending reservation on the same SKU and either queue or reject. Alternatively, use **optimistic locking** in the Inventory Service: `UPDATE inventory SET stock = stock - 1, version = version + 1 WHERE sku = ? AND stock > 0 AND version = ?` — if the update affects 0 rows, the saga step fails and triggers compensation.
- **Real Example:** Ticketmaster's pre-saga era ticket reservation system allowed double-selling of the same seat at high concurrency. Their resolution was a semantic lock (a "hold" record per seat per pending checkout, with a 15-minute TTL) — effectively the "try" phase of TCC, grafted onto an otherwise saga-like flow.

### Cascading Compensation Failure (Compensation Itself Fails)

- **Trigger:** Compensating transaction cannot complete because the external system is unavailable (e.g., the email provider is down and the saga needs to "cancel" an already-sent order confirmation email). Or compensation fails because the service handling it has a bug.
- **Symptoms:** Saga is stuck in `COMPENSATING` state. The business is in a partially inconsistent state with no automated path to resolution.
- **Detection:** Alert on sagas where `status = COMPENSATING AND updated_at < NOW() - 5 minutes`. Compensation retries exceeding 3 attempts should page on-call.
- **Recovery:** Every failed compensation must produce a **dead-letter record** with enough context for a human operator to complete it manually. Build an internal admin UI for on-call engineers to: (a) retry compensation, (b) mark as "manually compensated," or (c) escalate to data team for database correction. Critically: compensation failures cannot be ignored — they represent business-level inconsistency.
- **Real Example:** A payments platform had a third-party KYC service go down for 4 hours. Sagas that had already debited user wallets but failed at the KYC step could not compensate (the wallet service was available but the KYC "unregister" endpoint was down). They accumulated 230 stuck sagas in `COMPENSATING` state, each representing a user whose money was debited but whose account was not activated. Manual resolution took 6 hours and required a dedicated war room.

## 10. When To Use vs. When To Avoid

### Use When

- **Your operation spans 2+ microservices with independent databases.** If Service A and Service B both need to write as part of one business operation, you need either Saga or 2PC. Past 2 services, Saga wins.
- **You need high availability and cannot tolerate global locks.** If your system must remain available during partial failures (a downstream service is slow or down), Saga's async, non-blocking model is the right choice. A payment processing system that cannot afford to lock inventory while waiting for a card authorization is the canonical use case.
- **You are on modern cloud-native infrastructure.** DynamoDB, Spanner, CockroachDB, PlanetScale — none expose XA interfaces. If your databases cannot participate in 2PC, saga is your only consistent option. The cloud has made this the default situation.

### Do NOT Use When

- **You need strict ACID isolation between service calls.** If your domain requires that intermediate states are never visible to concurrent readers (e.g., atomic double-entry bookkeeping where debit and credit must appear simultaneously), Saga provides insufficient isolation. Use a single database with proper transactions, or use TCC with explicit reservation phases, or redesign your service boundaries so the operation is local.
- **Your team is not yet comfortable with eventual consistency and compensating design.** If your engineers conflate "distributed transaction" with "database transaction," the complexity of Saga will result in bugs: non-idempotent compensators, missing timeout handlers, swallowed compensation errors. The pattern requires discipline. Before adopting it, ensure the team understands what failure modes they are responsible for.
- **You have fewer than 2 services (or services share a database).** Sagas add overhead — schema design for saga state, compensation logic, idempotency keys, distributed tracing. None of that pays off if you can use a local `BEGIN/COMMIT`.

### The Number One Mistake Engineers Make

**Writing saga compensating transactions that are not idempotent.**

Engineers implement `compensate()` as a straightforward reversal call (call Stripe's refund API, decrement inventory, etc.) without considering that the message broker will redeliver the compensation command if the handler crashes mid-processing or the acknowledgment is lost. The compensating handler runs twice. In a financial system, this means a double refund. In an inventory system, it means stock is released twice, creating phantom inventory.

The fix is mechanical but requires discipline: every compensation handler must be designed as: "check if I already did this work (via idempotency key lookup), if yes return success immediately, if no do the work and record the key." This adds 5–10 lines of code per handler but prevents an entire class of production incidents.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "How would you handle a scenario where a payment succeeds but the order creation fails in a microservices system?"
- "Design an e-commerce checkout flow that spans 5 microservices with data consistency guarantees."
- "How does the Saga pattern differ from two-phase commit, and when would you choose each?"
- "Your order service charged the customer but the inventory service ran out of stock. How do you handle this?"
- "Walk me through the trade-offs between choreography-based and orchestration-based sagas."
- "How would you design distributed transactions for a ride-booking system like Uber?"

### What the Interviewer Evaluates

1. Do you understand that distributed systems fundamentally cannot have ACID guarantees across services?
2. Can you distinguish between types of failures (network, service crash, timeout) and explain how Saga handles each?
3. Do you understand compensation — not just that "you undo the steps" but the idempotency requirement and the pivot transaction concept?
4. Can you talk about the operational implications — how you detect stuck sagas, how you alert, how you resolve compensation failures?
5. Do you know real tools (Temporal, Step Functions, Conductor) and when to use each?

### Questions YOU Ask Before Answering

1. "How many services are involved in the transaction, and do they have independent databases?"
2. "What is the throughput requirement — 100 orders/minute or 100K orders/minute? This changes choreography vs orchestration."
3. "What is the business requirement when compensation fails? Is there a human escalation path or is full automation required?"
4. "What are the consistency requirements? Can a user see 'payment pending' for a few seconds, or must updates appear atomic?"
5. "What is the most expensive or irreversible step in the flow? That is our pivot transaction."

### Junior (L3–L4) Expected Answer

Demonstrates understanding of what the Saga pattern is: "We break the distributed operation into local transactions, each within one service. If a later step fails, we run compensating transactions to undo prior steps. There are two approaches — choreography (event-driven, no central coordinator) and orchestration (dedicated saga orchestrator that tracks state)."

Knows the core trade-off: "We give up strict ACID isolation in exchange for availability and the ability to scale each service independently."

Can sketch the basic flow for an order processing saga with happy path and one compensation path.

**Key numbers to know:** 2PC needs 6 round-trips for 3 services (prepare×3 + commit×3); Saga needs 3. 2PC holds locks for seconds; Saga holds locks for 5–20 ms. XA transactions are 10–100x slower than local transactions.

### Senior (L5) Expected Answer

All of the above, PLUS:

- Proactively identifies idempotency as a requirement for compensating transactions.
- Distinguishes pivot transactions from reversible steps and designs compensation accordingly.
- Mentions the Outbox Pattern as the mechanism to atomically write to the database and publish an event.
- Discusses stuck saga detection: timeout configuration, alert on in-flight sagas older than SLA, dead-letter handling.
- Has an opinion on choreography vs orchestration and can justify it based on scale and complexity.
- Mentions at least one production tool (Temporal, Step Functions, Conductor) by name with a reason for choosing it.

### Staff (L6+) Expected Answer

All of the above, PLUS:

- Discusses the lack of isolation between concurrent sagas and mitigation strategies (semantic locks, optimistic locking with version numbers).
- Can design the full observability model: correlation IDs, saga-level distributed traces, dashboards for stuck sagas by step, compensation failure alerting, on-call runbook design.
- Discusses when Saga is the wrong answer: if the operation requires strict isolation (use TCC or redesign service boundaries), if the team is not operationally ready for eventual consistency (organizational risk, not just technical).
- Discusses scale evolution: when to move from hand-rolled state machine → Temporal/Step Functions → choreography for ultra-high-throughput, and what triggers each transition.
- Can evaluate build vs buy: "At our current scale of 5M sagas/month, Temporal Cloud costs $500/month. The engineering cost to build and maintain an equivalent system is 3–6 months of a senior engineer. The build argument only makes sense if we have highly specific requirements or are above 500M sagas/month."
