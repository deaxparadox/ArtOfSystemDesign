# 6.8 — Fan-out on Write vs Fan-out on Read

> 📍 Phase 6 — Scalability Patterns | Section 6.8

**Prerequisites:**
- Familiarity with key-value stores and cache eviction policies (LRU, LFU)
- Basic understanding of message queues / pub-sub (Kafka, Redis Pub/Sub)

- Basic graph theory: directed graphs, in-degree / out-degree of nodes

## 1. What Is It? (Theory)

### Plain English

Every social product — Twitter/X, Instagram, LinkedIn, TikTok — has to answer the same question when a user publishes a post:

> **"When should I do the work of computing each follower's feed — now (at write time) or later (at read time)?"**

That is the entire fan-out problem. "Fan-out" simply means taking one event (a new post) and fanning it out to N recipients (the author's followers).

- **Fan-out on Write (push model):** When Alice posts, immediately write Alice's post ID into the timeline cache of every one of her 3,000 followers. Reads are instant. Writes are expensive and proportional to follower count.
- **Fan-out on Read (pull model):** When Alice posts, write nothing to follower caches. When Bob opens his feed, fetch the recent posts from everyone Bob follows, merge and rank them on the fly. Reads are expensive. Writes are cheap.

### The Problem It Solves

Without a deliberate choice here, social feed reads degrade at scale. If you do everything at read time on a platform with 100 million users, fetching a feed requires scatter-gathering posts from potentially hundreds of accounts, sorting and ranking them, and returning a ranked list — all inside a 100–200 ms budget. You cannot brute-force your way through that.

If you do everything at write time, a celebrity with 50 million followers posting a single tweet generates 50 million Redis writes. At 1 MB/s per Redis instance, that single tweet saturates your write path for minutes.

### Why It Was Invented

Twitter's original architecture (2006–2010) was pure fan-out on read. Every timeline request ran a scatter-gather query across all followed accounts. At ~50 million active users and modest follower counts, this was acceptable. When celebrities joined the platform — Barack Obama's account reached 50 million followers by 2012 — the read path collapsed. A single Obama tweet caused 50 million concurrent timeline refreshes each triggering the same scatter-gather.

Twitter rebuilt around fan-out on write between 2009 and 2012, using a Redis-backed "home timeline" cache. That fixed the read problem but created the write amplification problem (covered in detail in Section 9).

### Real-World Analogy

Think of a newspaper:
- **Fan-out on write** = the newspaper prints 500,000 physical copies and delivers one to every subscriber's doorstep before 7 AM. Reading is instant. Printing and delivery are expensive regardless of how many people actually read that day.
- **Fan-out on read** = a central archive exists. When you want to "read the paper," you drive to the archive and pull today's edition. No printing cost. But every reader pays the retrieval cost, and if 500,000 people arrive at 7 AM simultaneously, the archive melts.

### Concrete Example With Real Numbers

Assume a mid-size social platform:
- 10 million daily active users (DAU)
- Average follower count: 300
- Peak post rate: 5,000 posts/second
- Peak read (feed open) rate: 50,000 requests/second
- Target read latency: < 100 ms p99

**Fan-out on write:**
- 5,000 posts/sec × 300 followers = 1,500,000 Redis writes/second sustained
- A single Redis node handles ~100,000–200,000 ZADD operations/second
- You need at minimum 8–15 Redis write shards just for fan-out

**Fan-out on read:**
- 50,000 feed reads/sec, each requiring a scatter-gather across 300 followed accounts
- 50,000 × 300 = 15,000,000 DB/cache reads/second for the post index
- Plus merge/rank computation per request

Neither pure approach works cleanly. The hybrid is mandatory above roughly 100K DAU.

## 2. How It Actually Works (Deep Mechanics)

### Fan-out on Write — Step by Step

```
1. User (Alice, 3,000 followers) submits POST /tweets  {"text": "Hello world"}
2. API server validates, assigns tweet_id, writes to persistent store (MySQL/Cassandra)
3. API server publishes {tweet_id, author_id, timestamp} to Kafka topic "new-tweets"
4. Fanout workers (consumer group, N instances) consume from Kafka
5. Each worker:
   a. Looks up Alice's follower list from FollowerDB (sharded by author_id)
   b. For each follower_id:
      ZADD timeline:{follower_id}  {unix_timestamp}  {tweet_id}
      ZREMRANGEBYRANK timeline:{follower_id}  0  -1001   # keep newest 1000
   c. Acknowledges Kafka offset
6. Feed read:
   ZREVRANGE timeline:{user_id}  0  49  -- returns 50 tweet_ids, newest first
   MGET tweet:{id} for each tweet_id     -- hydrate from tweet cache
```

```

  Alice POSTs tweet
        |
        v

  | API Layer|------>| Kafka |------>| Fanout    |

        |             +-------+       |  group)  |

  | (Cassandra/ |            ZADD timeline:{fid}
```

### Fan-out on Read — Step by Step

```
1. User (Alice) submits POST /tweets {"text": "Hello world"}
2. API server writes tweet to persistent store + author's own post index
   ZADD posts:{alice_id}  {timestamp}  {tweet_id}
3. Done. O(1) write cost regardless of follower count.

4. Bob opens his feed:
   a. Fetch Bob's following list: [alice_id, carol_id, dave_id, ...]  (300 entries)
   b. For each followed account, fetch recent post IDs:
      ZREVRANGE posts:{account_id}  0  49  (parallel, pipeline)
   c. Merge all returned lists into one sorted list by timestamp
   d. De-duplicate (a user may follow someone who retweeted)
   e. Rank/score (optional — engagement score, personalization)
   f. Hydrate top N posts from tweet cache
   g. Return to client
```

```
                          WRITE PATH
                          ----------
  Alice POSTs tweet
        |
        v
  +----------+       +-------------------+
  | API Layer|------>| Author Post Index |  ZADD posts:{alice_id} ts tweet_id
  +----------+       | (Redis sorted set)|
        |            +-------------------+
        v
  +--------------+
  | Tweet Store  |  (durable storage)
  +--------------+

                          READ PATH
                          ---------
  Bob requests feed
        |
        v
  +-------------+      +-----------------+
  | Following   |----->| Scatter-Gather  |
  | Service     |      | posts:{id} x300 |
  +-------------+      +-----------------+
                                |
                                v
                        +---------------+
                        | Merge & Rank  |
                        | (in-memory)   |
                        +---------------+
                                |
                                v
                        +---------------+
                        | Tweet Cache   |
                        | (hydration)   |
                        +---------------+
```

### Key Data Structures

| Structure | Used For | Operation | Complexity |
|---|---|---|---|
| Redis Sorted Set (ZSET) | User timeline cache | ZADD, ZREVRANGE | O(log N) |
| Redis ZSET | Author post index | ZADD, ZREVRANGE | O(log N) |
| Kafka Topic | Async write fan-out | Produce/Consume | O(1) per message |
| Hash (following list) | Social graph lookup | SMEMBERS / DB query | O(followers) |
| LRU Cache | Tweet content hydration | MGET | O(N) |

### Misconceptions

**❌ Misconception:** "Fan-out on write means writes are slow."
**✅ Reality:** The API ack is fast — you write to durable storage and publish to Kafka, then acknowledge the client. The actual fan-out to follower caches happens asynchronously. The user sees a fast POST response; the fan-out lag is typically 100ms–2 seconds, invisible to the poster.

**❌ Misconception:** "Fan-out on read is always slower."
**✅ Reality:** For a user following only 5 accounts, fan-out on read with a warm cache can be as fast as 10–15 ms. The performance cliff is proportional to the number of followed accounts.

**❌ Misconception:** "You pick one model and stick with it."
**✅ Reality:** Every production system above 1M DAU uses a hybrid. The cut-off threshold (e.g., 10K followers) is a tunable parameter, not a fixed rule.

**❌ Misconception:** "Redis sorted sets store the full tweet content."
**✅ Reality:** Timeline sorted sets store only tweet IDs scored by timestamp. Hydration is a separate MGET step against the tweet content cache (and ultimately the durable store on cache miss). This is critical for storage efficiency — storing 1,000 full tweets per user vs. 1,000 tweet IDs (8 bytes each) is a 1,000× storage difference.

## 3. Real-World Architecture Examples

### Twitter / X

**Scale trigger:** ~50M active users, 2010–2012. A tweet from @BarackObama (50M+ followers by 2012) generated more timeline read load than any engineering estimate had planned for.

**What they got wrong first:** Pure fan-out on read (2006–2009). Timeline reads required querying every followed account's post store and merging — all synchronously in the request path. When celebrities joined and follower counts reached millions, the scatter-gather queries caused cascading failures.

**First attempt at fix:** Pure fan-out on write ("Inbox" model). Every tweet pushed to all follower inboxes stored in Redis. This collapsed when celebrity accounts posted — 50M Redis writes per tweet created a backlog that could take hours to clear, meaning followers saw stale timelines.

**Final solution (2012–present):** Hybrid model.
- Users with fewer than ~10,000 followers: fan-out on write via a dedicated Fanout Service consuming from a Kafka-like queue (they used Kestrel initially, then migrated).
- Users with more than ~10,000 followers ("celebrities"): fan-out on read at request time. The Timeline Service fetches posts from the celebrity's post index and merges with the pre-computed timeline from regular accounts.
- Timeline Service: reads from Redis sorted sets (home timeline cache), fetches author objects from Memcached, returns in < 5 ms p50.
- Redis cluster: ~10,000 Redis instances, ~105 TB total RAM (2013 numbers; grew considerably since).
- Each user's home timeline cached up to 800 entries; eviction policy: ZREMRANGEBYRANK keeps newest N.

**Reference:** "The Architecture Twitter Uses to Deal with 150M Active Users, 300K QPS, a 22 MB/S Firehose, and Send Tweets in Under 5 Seconds" — High Scalability, July 2013.

---

### LinkedIn FollowFeed

**Scale trigger:** 400M+ members, 2016. LinkedIn's original feed was built as a monolith with direct DB queries per feed load.

**What they chose:** LinkedIn's FollowFeed explicitly went **fan-out on read** — counter to Twitter's direction. Their reasoning: they valued fast iteration on relevance experiments over raw read speed. With fan-out on write, changing the ranking algorithm requires re-computing cached feeds for millions of users. With fan-out on read, you just change the ranking logic and every subsequent read reflects it.

**How they made it fast:** A multi-tier caching strategy:
1. Content cache (Espresso, LinkedIn's own NoSQL): caches raw posts per author.
2. FollowFeed service: caches merged, scored timelines with short TTLs.
3. Realtime updates (Kafka-powered): cache invalidation so hot posts surface quickly.

**Result:** Feed latency ~20–30 ms p50 for the cached path; degraded to 200–300 ms on cold misses. Acceptable trade-off for a business-social network where feed freshness matters less than for Twitter.

**Reference:** "FollowFeed: LinkedIn's Feed Made Faster and Smarter," LinkedIn Engineering Blog, March 2016.

---

### Instagram

**Scale trigger:** 1B+ users, celebrity accounts with 100M–500M followers (Cristiano Ronaldo: ~600M). A single Ronaldo post cannot trigger 600M write operations.

**What they built:** Hybrid model similar to Twitter's but with Instagram-specific tuning:
- Regular accounts (< ~50K followers): fan-out on write to follower feed caches using Celery workers and a Cassandra-backed timeline store.
- High-follower accounts: posts stored in author's own shard; fetched and merged at read time.
- Feed ranking model (introduced 2016): moved from chronological to ML-ranked. This made pure pre-computation even harder — ranking signals (engagement velocity, relationship strength) are dynamic, so even fan-out on write timelines are re-scored at read time using pre-fetched features.

**What they got wrong:** Early Instagram (2010–2012) used a pure chronological fan-out on write model (similar to Twitter's Inbox). When accounts like Selena Gomez (100M+ followers by 2015) posted, the async fan-out queue would back up, causing some followers to see posts minutes or hours late — visible as "timeline lag."

**Fix:** Tiered fan-out with dynamic thresholds based on current system load, not just static follower count. If the fan-out queue is congested, more accounts get routed to the pull path temporarily.

### Design Questions to Ask Before Starting

1. What is the expected DAU / MAU? What follower-count distribution does the social graph have? (Pareto? Long-tail? Roughly equal?)
2. Is the feed chronological or ranked? Ranked feeds reduce the value of pre-computation because scores change.
3. What is the acceptable read latency SLA? (< 50 ms? < 200 ms?)
4. What is the write latency SLA for post publishing? (Does the poster need to see their own post immediately?)
5. What is the fan-out lag tolerance? (Can followers see a post up to 5 seconds late? 30 seconds? Minutes?)
6. Do you need to support feed backfill? (New follower sees historical posts.)
7. What is the storage budget? Pre-computed timelines consume O(users × timeline_depth) bytes of cache.
8. Are there multi-media attachments? (Does the timeline cache store IDs only, or blobs?)

### Scale Evolution

**1K → 10K Users**
- Single Redis instance, no fan-out workers needed.
- Fan-out on write inline in the API request path: synchronous ZADD to each follower.
- No Kafka. No async. Keep it simple.
- Read: ZREVRANGE + MGET, all under 10 ms.

**10K → 100K Users**
- Move fan-out off the synchronous request path into a background task (Celery, RQ, or a simple worker process).
- Redis starts to matter: multiple Redis instances, sentinel for HA.
- Follower lists still fit in memory.
- Introduction of a max timeline depth (1,000 entries) to cap storage.
- No celebrity problem yet — follower counts are low.

**100K → 1M Users**
- Fan-out becomes a first-class service. Introduce Kafka for decoupling.
- Introduce the celebrity threshold (~1,000–5,000 followers at this scale).
- Start tracking fan-out queue depth as a key SLI.
- Redis cluster (multiple shards, consistent hashing on user_id).
- Introduce an author post index for the pull path.
- Read latency SLA requires a p99 budget: identify and separate hot paths.

**1M → 100M Users**
- Hybrid model mandatory. Threshold tuning is now operational work.
- Separate Fanout Service with auto-scaling fan-out worker pools.
- Redis cluster: dozens of shards, replication factor 3.
- Timeline depth limit revisited: 500–1,000 entries typical (AWS ElastiCache cost at this scale is material).
- Celebrity registry as a separate lookup service (cached, updated async when follower count crosses threshold).
- Feed ranking layer introduced: ML model scores post list at read time against real-time engagement signals.
- Geographic sharding of timelines to reduce cross-datacenter latency.
- Introduce "seen" tracking: timeline cursors per user so pagination works correctly across sessions.

## 5. Code / Implementation Perspective

### Python Implementation Sketch — Hybrid Fan-out Service

```python
import redis
import json
from kafka import KafkaConsumer, KafkaProducer
from typing import List

r = redis.RedisCluster(startup_nodes=[{"host": "redis-cluster", "port": 6379}])

CELEBRITY_THRESHOLD = 10_000   # tunable
TIMELINE_MAX_DEPTH  = 1_000    # entries per user timeline
FEED_PAGE_SIZE      = 50


# ---------- WRITE PATH ----------

def publish_post(author_id: int, post_id: int, timestamp: float) -> None:
    """Called by API layer after writing post to durable store."""
    # Always update author's own post index (used for pull path)
    r.zadd(f"posts:{author_id}", {str(post_id): timestamp})
    r.zremrangebyrank(f"posts:{author_id}", 0, -(TIMELINE_MAX_DEPTH + 1))

    # Decide push vs skip based on follower count
    follower_count = r.get(f"follower_count:{author_id}") or 0
    if int(follower_count) < CELEBRITY_THRESHOLD:
        # Publish fanout task to Kafka; workers handle distribution
        producer.send("fanout-tasks", {
            "author_id": author_id,
            "post_id": post_id,
            "timestamp": timestamp,
        })
    # else: celebrity — no push fanout; read path handles it


def fanout_worker_loop() -> None:
    """Kafka consumer: pushes post_id into each follower's timeline ZSET."""
    consumer = KafkaConsumer("fanout-tasks", group_id="fanout-workers",
                             value_deserializer=lambda m: json.loads(m))
    for msg in consumer:
        task = msg.value
        author_id  = task["author_id"]
        post_id    = task["post_id"]
        timestamp  = task["timestamp"]
        followers: List[int] = get_followers(author_id)  # paginated DB call

        pipe = r.pipeline(transaction=False)
        for fid in followers:
            pipe.zadd(f"timeline:{fid}", {str(post_id): timestamp})
            pipe.zremrangebyrank(f"timeline:{fid}", 0, -(TIMELINE_MAX_DEPTH + 1))
        pipe.execute()                # one round-trip per batch of followers


# ---------- READ PATH ----------

def get_feed(user_id: int, cursor: float = float("+inf"),
             limit: int = FEED_PAGE_SIZE) -> List[dict]:
    """
    Returns a merged, time-sorted feed for user_id.
    cursor: oldest timestamp seen in previous page (for pagination).
    """
    # 1. Pull pre-computed timeline from Redis ZSET (regular accounts)
    raw_ids = r.zrevrangebyscore(
        f"timeline:{user_id}", cursor, "-inf",
        start=0, num=limit, withscores=True
    )
    regular_posts = [(int(pid), ts) for pid, ts in raw_ids]

    # 2. Fetch celebrity posts the user follows (pull path)
    celebrity_ids: List[int] = get_followed_celebrities(user_id)  # cached
    celebrity_posts: List[tuple] = []
    if celebrity_ids:
        pipe = r.pipeline(transaction=False)
        for cid in celebrity_ids:
            pipe.zrevrangebyscore(
                f"posts:{cid}", cursor, "-inf",
                start=0, num=limit, withscores=True
            )
        for result in pipe.execute():
            celebrity_posts += [(int(pid), ts) for pid, ts in result]

    # 3. Merge, deduplicate, sort by timestamp descending
    all_posts = list({pid: ts for pid, ts in
                     regular_posts + celebrity_posts}.items())
    all_posts.sort(key=lambda x: x[1], reverse=True)
    top_ids = [pid for pid, _ in all_posts[:limit]]

    # 4. Hydrate post content (pipeline MGET for throughput)
    pipe = r.pipeline(transaction=False)
    for pid in top_ids:
        pipe.get(f"post:{pid}")
    raw = pipe.execute()

    return [json.loads(p) for p in raw if p is not None]
```

### Language-Agnostic Pattern

The pattern is: **write-time materialization vs. read-time computation, with a threshold-based router.**

Key invariants regardless of language:
1. The author post index (`posts:{author_id}`) must always be written regardless of push/pull decision — it is the source of truth for the pull path.
2. Fan-out tasks must be idempotent — if a worker crashes mid-fan-out and replays the Kafka message, `ZADD` is a safe re-apply (it's a set operation with no double-counting).
3. Timeline ZSET trim (`ZREMRANGEBYRANK`) must happen atomically with `ZADD` to avoid unbounded memory growth.
4. Celebrity registry must be eventually consistent, not strongly consistent — a 30-second lag before a new celebrity is reclassified causes at most 30 seconds of unnecessary push fan-out. Acceptable.

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Pure Fan-out on Write** | Low-to-moderate follower counts (< 5K avg), simple chronological feeds, feed freshness is critical | Write amplification scales linearly with followers; celebrity problem is fatal | Early Twitter (inbox model), small social apps |
| **Pure Fan-out on Read** | Content feeds (not social graphs), small following lists (< 20), relevance changes faster than you can re-compute | Read latency is proportional to accounts followed; scatter-gather collapses at scale | LinkedIn FollowFeed (with caching), email digest systems, RSS aggregators |
| **Hybrid (push/pull)** | Any social platform with follower skew (Pareto distribution), > 100K DAU | Operational complexity: two code paths, celebrity registry must stay in sync | Twitter, Instagram, Facebook, TikTok |
| **Pre-ranking at write time** | Algorithmic feed where ranking signals are stable (e.g., content quality score computed offline) | Stale rankings; personalization is limited | YouTube recommendations cache |
| **Polling (client-side pull)** | Notification systems, low-frequency updates, IoT | Wasteful if polling interval is short; simple to implement | Legacy email clients, low-budget systems |
| **Server-Sent Events / WebSocket push** | Real-time notification delivery after fan-out is done | Requires persistent connections, complex at scale; solves delivery, not fan-out itself | Slack, Discord, Twitter live streaming |
| **Outsourced (GetStream / Activity Feed SaaS)** | < 10 engineers, < 50M MAU, speed-to-market priority | Vendor lock-in; expensive at scale; limited customization of ranking | Product Hunt, Bandcamp, many startups |

### Opinionated Recommendation

**Use the hybrid model.** Pure fan-out on write and pure fan-out on read are both theoretical positions that collapse at production scale for any social product with Pareto-distributed follower counts.

The hybrid is not "the complicated option" — it is the correct default architecture for any product that expects to have both regular users (hundreds of followers) and high-follower accounts. Design it in from day one, even if you set the celebrity threshold at 1 million followers initially. The code path split is small; the operational infrastructure is the same either way.

If you are a startup with fewer than 10 engineers, use GetStream.io or a similar SaaS. The engineering cost of building, operating, and tuning a hybrid fan-out system with Redis clusters and Kafka is not worth it below ~1M DAU.

## 8. Trade-offs (Be Opinionated)

### Benefits of Fan-out on Write (Push)

- **Read latency is excellent:** p50 reads typically 1–5 ms. ZREVRANGE on a pre-populated sorted set is a single Redis round-trip. Feeds feel instant.
- **Reads are compute-cheap:** No scatter-gather, no merge logic. Timeline Service is near-stateless and trivially horizontally scalable.
- **Algorithmic feed integration is possible:** Pre-computed timeline can be scored offline using ML signals and stored as weighted sorted set entries.
- **Predictable cache hit rate:** The pre-computed timeline is always populated for active users (it is written at post time, not on demand). No cold-start read latency.

### Benefits of Fan-out on Read (Pull)

- **Write path is simple:** Posting a tweet is always O(1). No queue, no workers, no celebrity routing. Single ZADD to author's post index.
- **Ranking freshness:** Changing the ranking algorithm affects all subsequent reads immediately. No need to re-compute cached timelines.
- **Storage efficiency:** No per-user timeline cache. Author post indices are the single source of truth. For a platform with 1 billion users where most are inactive, fan-out on write would fill billions of Redis sorted sets that are never read.
- **Avoids write amplification:** A celebrity with 100M followers posting does not generate 100M writes. The write cost is constant.

### Costs and Limitations

**Fan-out on Write:**
- **Write amplification:** User with 1M followers posts once = 1M Redis ZADD operations. At 200,000 ZADD/sec per Redis shard, that is a minimum of 5 seconds of write bandwidth from a single post, on a single shard.
- **Fan-out lag:** The async nature means followers may not see posts for seconds or minutes if the fan-out queue is backlogged. Visible to users as "timeline lag."
- **Celebrity problem:** Without the hybrid model, the write path is fatally bottlenecked by high-follower accounts. This is not hypothetical — Twitter experienced outages because of it.
- **Storage cost:** Storing 1,000 post IDs per active user at 1 billion users = 8 bytes × 1,000 × 1B = ~8 TB of sorted set data minimum, before replication.
- **Stale timelines on following new account:** When Bob follows Alice, Alice's historical posts do not appear in Bob's pre-computed timeline. Backfill logic is needed.

**Fan-out on Read:**
- **Read latency degrades with following count:** User following 500 accounts requires 500 parallel Redis reads + merge. At p99 this can exceed 200–500 ms even with an efficient scatter-gather.
- **Read amplification:** 50,000 feed reads/sec × 300 avg. following = 15M Redis operations/sec. This overwhelms Redis at modest scale.
- **Repeated computation:** The same merge is re-computed for each feed refresh. No shared work.
- **Cold read latency:** For inactive users who return after weeks, their author post indices may not be cached, causing DB fallback on every post lookup.

### Core Tension

**The fundamental tension is: where do you pay the latency tax — at write time or read time?**

Social networks have asymmetric access patterns: posts are written once, read many times. This makes write-time computation (push) the natural economic choice for typical users. But the Pareto distribution of follower counts means a small fraction of users (celebrities) would generate a disproportionate fraction of write cost — reversing the economics for those accounts.

### My Recommendation

**Default to hybrid.** Use fan-out on write for accounts below a dynamically tuned threshold (start at 10,000 followers; tune down if your write path is healthy, tune up if fan-out lag increases). Use fan-out on read for accounts above the threshold.

Set the threshold based on system load, not just a fixed number. Implement a circuit breaker: if fan-out queue depth exceeds X messages or fan-out lag exceeds Y seconds, temporarily raise the celebrity threshold so more accounts are routed to the pull path, reducing write pressure.

Do not use ranked/ML-scored feeds with pure fan-out on write — ranking signals change in real-time and your pre-computed scores go stale within minutes. Combine pre-computed post ID lists (fan-out on write for recency) with read-time re-ranking using cached feature vectors (a practical middle ground used by Instagram post-2016).

## 9. Failure Modes — What Goes Wrong

### Fan-out Queue Backlog ("Timeline Lag")

**Trigger:** A celebrity (or a coordinated group of users) posts within a short time window. Fan-out workers are processing faster than Kafka messages can be consumed. Typically triggered by: viral events, scheduled posts by large influencers, or sudden spikes in follows (breaking news causes mass follow of a journalist).

**Symptoms:** Followers open the app and see posts from 5, 10, or 30 minutes ago. The poster can see their own post (it is written to durable storage immediately), but followers cannot. User-visible complaint: "the feed is broken / not updating."

**Detection:**
- Monitor `kafka_consumer_group_lag` on the fanout-tasks topic. Alert if lag > 100K messages.
- Monitor `fanout_p99_delay_seconds` (time from Kafka message production to last ZADD for that post). Alert if > 10 seconds.
- Monitor Redis ZADD error rate and pipeline latency.

**Recovery:**
- Short term: scale up fanout worker pods horizontally (Kafka consumer group auto-rebalances).
- Medium term: raise the celebrity threshold temporarily (dynamic threshold adjustment via feature flag) to shed load off the push path.
- Long term: partition the fan-out Kafka topic by author follower count bucket, so high-follower accounts use separate consumer groups with dedicated worker pools.

**Real Example:** Twitter, 2012. Before the hybrid model was fully implemented, tweets from high-profile accounts (Obama 2012 election night) caused multi-hour fan-out queue backlogs. Followers received tweets hours late. Post-mortem led directly to the current hybrid architecture.

---

### Redis Timeline Cache Stampede

**Trigger:** A popular user's timeline cache entry expires (TTL hit) or is evicted (LRU under memory pressure). Simultaneously, thousands of followers attempt to load their feeds. Each request finds a cache miss, initiates a scatter-gather rebuild, and the resulting load hammers the backing database.

**Symptoms:** Sudden spike in DB read QPS (10–100× normal), read latency spike to seconds, possible cascading failure if DB connection pool exhausts. Redis MISS rate spikes on `timeline:*` keys.

**Detection:**
- `cache_miss_rate` for timeline keys. Alert if > 5% in any 1-minute window.
- DB read QPS sudden increase (>3× baseline in 30 seconds).
- Correlation: cache miss rate spike followed by DB latency spike.

**Recovery:**
- Short term: probabilistic cache refresh ("cache aside with jitter") — add ±5–10% random TTL jitter to avoid synchronized expiry.
- Implement a "lock-then-compute" pattern: use a Redis distributed lock (`SET lock:{user_id} NX PX 1000`) so only one request rebuilds the cache for a given user; others wait or return a stale result.
- Long term: use Redis `PERSIST` for hot timelines (no TTL) and instead expire timelines for inactive users via a background process that tracks last-active timestamps.

**Real Example:** Instagram, 2015. A targeted cache eviction event (a Memcached cluster rebalance) caused a cascade on the backing MySQL read replicas during a high-traffic event. The fix was implementing staggered cache warming and distributed locks around cache rebuilds. Details referenced in Instagram Engineering Blog post on infrastructure.

---

### Write Amplification Overload ("Celebrity Bomb")

**Trigger:** A user account unexpectedly crosses the celebrity threshold (e.g., a previously normal account goes viral and gains 1M followers in one hour) but is still being routed through the push fan-out path because the celebrity registry has not updated.

**Symptoms:** Fan-out worker pods crash-loop or become unresponsive. Kafka consumer lag for that partition grows linearly. Downstream: Redis write errors / connection refused. CPU on Redis nodes spikes to 100%.

**Detection:**
- Monitor follower count growth rate per author. Alert if any account gains > 50K followers in 10 minutes (viral signal).
- Fan-out worker crash rate. Alert on > 3 pod restarts in 5 minutes.
- Redis `connected_clients` near max value.

**Recovery:**
- Immediate: add a write-path guard in the fanout worker — before processing the follower list for an author, re-check current follower count. If above threshold, skip push and log a metric. This is a fast circuit-breaker.
- Short term: update celebrity registry to include the newly viral account within 60 seconds. Implement a real-time follower count stream (Kafka or Flink job updating the registry).
- Long term: make the threshold check authoritative in the Kafka message itself (API layer sets a `celebrity=true` flag at time of publishing, based on a cached follower count), so fanout workers do not need to re-query follower count mid-processing.

**Real Example:** Twitter, multiple times (2012–2015). Accounts that went viral during breaking news events (e.g., Alyssa Milano during the #MeToo movement in 2017, gaining hundreds of thousands of followers in hours) caused fan-out system instability until real-time threshold reclassification was implemented.

---

### Follower List Hotspot (Graph DB Bottleneck)

**Trigger:** Fan-out workers fetching follower lists for popular accounts overwhelm the social graph database. Even at moderate follower counts (100K), fetching and paginating a 100K-row follower list under a tight deadline saturates read replicas.

**Symptoms:** Fan-out worker latency spikes. Kafka consumer lag grows. Social graph DB read replica CPU at 100%. Timeouts on `get_followers()` calls.

**Detection:**
- Monitor social graph DB read latency, specifically for `SELECT follower_id FROM follows WHERE author_id = ?` queries.
- Alert if p99 of this query > 50 ms or per-worker follower-fetch duration > 500 ms.

**Recovery:**
- Short term: cache follower lists in Redis (`SMEMBERS followers:{author_id}`) with a 5-minute TTL. Acceptable stale window for fan-out purposes.
- Medium term: partition follower list fetching across multiple shards by author_id range. Use consistent hashing to ensure fan-out workers co-locate with the social graph shard for their assigned author range.
- Long term: pre-shard follower lists into fixed-size "buckets" stored as adjacent rows. Fan-out workers can fetch one bucket per Kafka message (parallel fan-out across buckets).

## 10. When To Use vs. When To Avoid

### Use Fan-out on Write When:

- **Your read QPS >> write QPS** (true for almost every social platform: 10:1 to 100:1 read-to-write ratio is common). The economics favor pre-computation.
- **Follower distribution is roughly normal** (median follower count is low, most users have < 1,000 followers). Write amplification is bounded and manageable.
- **Feed freshness is a core product requirement.** Users expect to see posts appear in their feed within seconds of publication.
- **Your feed is chronological or lightly ranked** (ranking signals are stable, not highly dynamic). Pre-computed timelines do not go stale quickly.
- **You have a clear latency SLA** (< 50 ms p99 for feed reads). Only fan-out on write (or hybrid) can reliably meet this.

### Do NOT Use Pure Fan-out on Write When:

- **Your social graph has extreme Pareto skew** (celebrities with 10M+ followers) and you have not implemented the hybrid model. Pure push will collapse.
- **Your feed is heavily ranked with real-time personalization signals** (engagement velocity, freshness decay, user relationship score). Pre-computed lists go stale within minutes; the ranking layer needs fresh signals at read time.
- **Your users are primarily inactive** (social apps where most users log in less than once a week). Pre-computing timelines for dormant users wastes cache capacity that could serve active users.
- **You have very high write rates with long follower lists.** Content platforms (think a news broadcaster posting 200 tweets/day with 50M followers) generate catastrophic write amplification (200 × 50M = 10 billion Redis writes/day from a single account).

### Avoid Fan-out on Read As Your Primary Strategy When:

- **Average following count is high** (> 50 accounts followed). Scatter-gather at read time becomes unacceptably expensive.
- **Read latency SLA is aggressive** (< 100 ms p99). Scatter-gather cannot reliably meet this without extensive caching.
- **You have real-time feed requirements** (new posts should appear within 1 second of publication). On-demand scatter-gather does not cache results long enough to provide low latency.

### The #1 Mistake Engineers Make

**Picking a strategy based on write-time cost alone, without modeling the fan-out lag under peak load.**

Engineers see "fan-out on write means 1M writes for a 1M-follower account" and immediately decide on fan-out on read. Then, at scale, they discover that their scatter-gather reads are 300–500 ms, unacceptable for a social product, and they scramble to add caching — which eventually converges toward the hybrid model anyway, but with worse code quality and no clean abstraction.

**Design the hybrid model from the beginning.** It is not significantly more complex to implement. Set the initial celebrity threshold conservatively high (e.g., 1M followers) so the pull path is rarely exercised early on, but the infrastructure exists.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a Twitter-like social feed system."
- "How would you design the news feed for a platform with 100 million users?"
- "Your social app has both regular users and celebrities. How do you handle timeline generation at scale?"
- "We have a feed system and it's slow at read time. How would you improve it?"
- "How did Twitter solve the celebrity problem in their timeline system?"
- "Design the feed for Instagram, focusing on the write/read trade-off."

### What the Interviewer Is Evaluating

1. **Ability to identify the core trade-off** (write amplification vs. read latency) without prompting.
2. **Knowledge of concrete data structures** (Redis sorted sets, Kafka consumer groups) — not just abstract "use a cache."
3. **Understanding of the celebrity / Pareto distribution problem** — do you proactively mention it or wait to be told?
4. **Hybrid thinking** — do you immediately go to one extreme (pure push or pure pull) or do you correctly conclude that a hybrid is required?
5. **Scale reasoning** — can you estimate write amplification with numbers? (5,000 posts/sec × 300 followers = 1.5M writes/sec)
6. **Operational thinking** — do you mention monitoring, failure modes, and degradation gracefully?

### Questions YOU Ask Before Answering

These demonstrate senior thinking. Ask them before diving into design:

1. "What is the expected follower distribution? Is this a celebrity-heavy platform like Twitter/Instagram, or a friend-graph platform like early Facebook?"
2. "Is the feed chronological, or algorithmically ranked?"
3. "What is the read latency SLA? Under 100 ms? Under 50 ms?"
4. "What is the acceptable fan-out lag? Can followers see posts up to 5 seconds late?"
5. "Do we need to support feed backfill when a user follows a new account?"

### Junior Answer (L3–L4)

Identifies the two approaches. Can describe fan-out on write (push) vs. fan-out on read (pull) at a conceptual level. Mentions Redis for caching. May not know the celebrity threshold or hybrid pattern without prompting. Talks about read/write trade-offs. Does not mention Kafka, consumer groups, or specific Redis operations.

*Expected depth:* Conceptual explanation with basic data model. No specific numbers. No failure modes.

### Senior Answer (L5)

Immediately identifies both approaches, explains the celebrity problem unprompted, and proposes the hybrid model with a specific threshold (10K followers). Can describe:
- ZADD / ZREVRANGE operations and why sorted sets are the right data structure.
- Kafka consumer groups for async fan-out decoupling.
- Author post index as the backing for the pull path.
- Fan-out lag as an SLI and how to monitor it.

Can estimate write amplification: "If we have 5,000 posts/sec with average 300 followers, that is 1.5M Redis writes/sec. A Redis instance handles ~100K-200K writes/sec, so we need ~8-15 shards for fan-out alone."

*Expected depth:* Full data model, component design, key trade-offs with numbers, celebrity problem addressed.

### Staff Answer (L6+)

Goes beyond the standard hybrid model to address:
- **Operationalizing the threshold:** Celebrity threshold should be dynamic, not static — based on current fan-out queue depth and Redis write saturation. Implemented as a feature flag with real-time feedback loop.
- **Fan-out lag SLA:** Defines an SLO (e.g., "99% of non-celebrity posts must appear in follower timelines within 3 seconds"). Designs monitoring and alerting around it.
- **Ranked feeds and the interaction with fan-out:** Notes that ML-ranked feeds partially invalidate the value of pre-computation, leading to a "pre-fetch post IDs (push) + re-rank at read time (pull)" hybrid within the hybrid.
- **Cross-DC fan-out:** In a multi-region setup, fan-out workers in each region need to handle local shards. Discusses consistency model for cross-region timelines.
- **Cache warming for new follows:** When Bob follows Alice, Alice's N most recent posts should be backfilled into Bob's timeline. This is a fan-out from Alice to Bob, but triggered by a social graph event, not a post event.
- **Storage cost analysis:** 1B users × 1,000 post IDs × 8 bytes = 8 TB raw timeline data before replication. At Redis replication factor 3 across 3 AZs, this is ~25 TB of RAM. Staff candidate knows this number matters for budget approval.
- **Failure mode awareness:** Proactively discusses fan-out queue backlog and celebrity bomb scenarios with mitigations.

### Key Numbers to Memorize

| Fact | Value | Why It Matters |
|---|---|---|
| Redis ZADD throughput | ~100K–200K ops/sec per node | Sizing fan-out write capacity |
| Redis ZREVRANGE latency | ~0.1–0.5 ms | Justifying read path SLA |
| Twitter Redis fleet (2013) | ~10,000 instances, ~105 TB RAM | Conveying scale of fan-out caching |
| Twitter home timeline depth | 800 entries | Typical cache depth limit |
| Celebrity threshold (common) | 10,000 followers | Standard interview answer |
| Fan-out amplification (example) | 5,000 posts/sec × 300 followers = 1.5M writes/sec | Quick estimation |
| LinkedIn FollowFeed approach | Fan-out on read (with caching) | Counterexample to Twitter's approach |
| Kafka throughput | ~1M+ messages/sec per cluster | Fan-out task queue capacity |
| Typical read-to-write ratio | 10:1 to 100:1 | Why pre-computation (push) is usually worth it |
