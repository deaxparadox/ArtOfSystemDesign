## 1. What Is It? (Theory)

### Plain English

Caching is the act of storing a computed or fetched result closer to the consumer so that the same question does not require the same expensive work twice. "Closer" can mean physically (a CDN edge node in Singapore vs. your origin in Virginia) or architecturally (memory vs. disk, application tier vs. database tier).

Every cache in existence is a deliberate trade: you sacrifice **freshness** (the cache might be stale) and **complexity** (now you have two sources of truth) in exchange for **speed** and **reduced load on the bottleneck beneath it**.

### The Problem It Solves at Scale

Without caching, every request executes the full computation stack. At 1,000 requests per second hitting a typical PostgreSQL instance, you will saturate connection pools around 500-1,000 concurrent connections. At 100,000 req/s, you need roughly 100 read replicas just to serve identical queries — an enormous cost with zero benefit over caching the results once.

A single Redis node on commodity hardware handles **1 million operations per second** with sub-millisecond latency. A PostgreSQL server on similar hardware handles roughly **50,000-100,000** simple SELECT queries per second under ideal conditions. That is a 10-20x throughput gap before you account for query complexity, joins, or disk I/O.

### Why It Was Invented

Early web systems hit a wall when page assembly required dozens of database round trips. The 1998-era Squid HTTP cache and early Varnish deployments were attempts to serve static-ish content without hitting the app server at all. As sites became dynamic, caching moved inward: from HTTP caches at the edge, to application-level object caches (Memcached, born at LiveJournal in 2003), to query result caches inside the database itself. Each layer was invented to remove a specific bottleneck that the layer above it could not eliminate.

### Real-World Analogy

Think of a hospital pharmacy. The central warehouse (your database) holds every possible drug. A pharmacist (application server) must travel to the warehouse, verify the prescription, and return — this takes 20 minutes. So the pharmacy keeps a small cabinet of the 50 most-prescribed drugs on the counter (application cache). The nurse's station on each floor keeps the 5 drugs used hourly (CDN / edge). A patient's bedside table holds the specific pills prescribed this morning (client cache). Each layer saves time by keeping frequently needed items physically closer to the point of use.

### Concrete Example with Real Numbers

A product page at an e-commerce site requires:
- 1x database query for product details: **15ms**
- 3x database queries for related products: **45ms total**
- 1x external API call for inventory: **80ms**
- Template rendering: **5ms**
- **Total uncached: ~145ms per request**

With caching layers:
- Product details in Redis (app cache): **0.5ms** (30x faster)
- Related products in Redis: **0.5ms**
- Inventory in CDN edge cache with 60s TTL: **2ms** (TTFB from edge)
- **Total cached: ~3ms** — a **48x latency reduction**

At 10,000 req/s this also reduces database load from 40,000 queries/s to roughly 5 queries/s (on cache miss/expiry). That is the difference between 40 database read replicas and a single primary.

## 2. How It Actually Works (Deep Mechanics)

### The Four Cache Layers — Step by Step

A request travels through these layers in order, stopping at the first hit:

```
User's Browser
    │
    ▼
┌─────────────────────────────┐
│  Layer 1: Client Cache      │  ← Memory, disk, localStorage
│  Latency: 0ms               │  ← No network at all
│  Scope: single user         │
└─────────────┬───────────────┘
              │ MISS
              ▼
┌─────────────────────────────┐
│  Layer 2: CDN / Edge Cache  │  ← PoP near user (20-50ms RTT)
│  Latency: 2-20ms            │  ← Shared across all users in region
│  Scope: geographic region   │
└─────────────┬───────────────┘
              │ MISS
              ▼
┌─────────────────────────────┐
│  Layer 3: Application Cache │  ← Redis / Memcached in same DC
│  Latency: 0.3-2ms           │  ← Shared across all app instances
│  Scope: entire application  │
└─────────────┬───────────────┘
              │ MISS
              ▼
┌─────────────────────────────┐
│  Layer 4: DB Query Cache /  │  ← Buffer pool, query result cache
│  DB Buffer Pool             │  ← Shared across DB connections
│  Latency: 0.5-5ms (hot)    │
│           10-100ms (cold)   │
└─────────────┬───────────────┘
              │ MISS
              ▼
┌─────────────────────────────┐
│  Storage: Disk / SSD        │  ← The ground truth
│  Latency: 1-10ms (SSD)     │
│           5-20ms (HDD)      │
└─────────────────────────────┘
```

### Layer 1 — Client Cache

**Browser HTTP cache** operates via response headers:
- `Cache-Control: max-age=3600` — cache for 1 hour client-side
- `ETag: "abc123"` — fingerprint for conditional revalidation (`If-None-Match`)
- `Last-Modified` + `If-Modified-Since` — time-based revalidation

When a cached response expires, the browser sends a **conditional GET**. If the resource is unchanged, the server returns `304 Not Modified` with no body — saving bandwidth but not the round-trip itself.

**Service Workers** extend this further: a JS-controlled cache that can serve responses even when offline, intercept fetch events, and implement custom eviction policies. Used by Twitter Lite, Starbucks PWA, and others to achieve near-instant navigations on repeat visits.

**Mobile app caches** (SQLite on device, NSCache on iOS, Room on Android) operate similarly but with finer programmer control over eviction.

### Layer 2 — CDN / Edge Cache

CDN edge nodes sit inside or adjacent to ISP networks. A request from London to a Cloudflare origin in Virginia without CDN is ~80ms RTT. With CDN, the response may be served from Frankfurt at ~5ms RTT.

How CDN caching works:
1. First request to an edge node **misses** — the PoP fetches from origin.
2. PoP stores the response keyed by URL (+ Vary headers, query params, cookies if configured).
3. Subsequent requests within TTL return from PoP memory — no origin hit.
4. Cache-Control response headers from origin dictate TTL behavior.
5. `Cache-Control: s-maxage=300` sets the CDN TTL to 5 minutes independently of the browser TTL set by `max-age`.

**Tiered CDN caching** (Cloudflare's Argo, Fastly's shielding, CloudFront's Origin Shield): requests that miss at the edge PoP travel to a mid-tier "shield" PoP before hitting origin. This collapses many simultaneous cache misses from different PoPs into a single origin request — critical at viral scale.

**Edge computing** (Cloudflare Workers, Fastly Compute) allows running code at the PoP. You can now cache dynamic, user-aware responses by computing them at the edge, not the origin. Personalization without origin round-trips.

### Layer 3 — Application / Distributed Cache

The most commonly discussed layer. Redis and Memcached sit in the same data center as your application servers, connected via gigabit LAN.

```
App Server 1 ─────┐
App Server 2 ─────┤──► Redis Cluster ──► Database
App Server 3 ─────┘    (shared state)
```

A **look-aside** (lazy loading) pattern:
1. App checks cache: `GET product:42`
2. HIT → return cached value. Done in ~0.5ms.
3. MISS → query DB (15ms), store in cache (`SET product:42 <data> EX 3600`), return.

A **write-through** pattern: on every write, update cache AND DB atomically before returning success. Cache is always populated; no cold-start problem.

A **read-through** pattern: cache itself fetches from DB on miss. App only talks to cache. Requires a cache client library that understands the source-of-truth (e.g., Spring Cache with JPA).

### Layer 4 — Database Cache (Buffer Pool / Query Cache)

**Buffer Pool** (InnoDB, Postgres shared_buffers): the database's own in-memory page cache. A 100GB dataset with a 32GB buffer pool means ~32% of your data is hot-cached in RAM. Reads against cached pages cost ~0.1-0.5ms; reads requiring disk I/O cost 5-20ms.

**Query result cache**: MySQL had one (deprecated in 8.0 due to contention bugs). PostgreSQL does not have a native query result cache — this is intentional. At write-heavy workloads, the invalidation overhead of maintaining a query result cache exceeds its benefit.

**Read replicas as a cache layer**: for analytical/reporting queries that are too large for Redis, a read replica with `synchronous_commit = off` gives you near-real-time data with zero lag and isolation from OLTP traffic.

### Key Algorithms

**LRU (Least Recently Used)**: evict the item not accessed for the longest time. Standard in Redis (approximated via sampled LRU since Redis 2.8 for O(1) amortized cost, exact LRU since Redis 4.0 optional).

**LFU (Least Frequently Used)**: evict the item accessed least often. Redis `allkeys-lfu` / `volatile-lfu` policies. Better for skewed access patterns (Zipf distribution, which is what real workloads look like).

**ARC (Adaptive Replacement Cache)**: balances recency and frequency dynamically. Used in ZFS, IBM storage. Not in Redis natively but implemented in some cache proxies.

**XFetch (Probabilistic early expiration)**: recomputes cache before it expires using a probabilistic trigger. Prevents stampedes at the cost of slightly higher cache miss rate. Used at Meta for News Feed.

### Real Numbers with Units

| Layer | Read Latency (p50) | Read Latency (p99) | Throughput (single node) | Hit Rate (typical) |
|---|---|---|---|---|
| Browser cache (memory) | 0 ms | 0 ms | N/A (local) | 70-90% static sites |
| CDN edge (cached) | 2-10 ms | 15-30 ms | Unlimited (distributed) | 85-96% (static), 40-70% (dynamic) |
| Redis (same AZ) | 0.3 ms | 1-2 ms | 1M ops/sec | 95-99% (well-tuned) |
| Postgres (buffer pool hit) | 0.5 ms | 3 ms | 50-100K qps | Depends on working set |
| Postgres (disk read, SSD) | 5 ms | 25 ms | 5-20K qps | — |

### Misconceptions

**❌ Misconception: A higher cache hit rate is always better.**
**✅ Reality:** A 2024 Redis Labs study found that above a certain hit rate threshold, forcing higher hit rates can *reduce* throughput by keeping stale large objects in cache that displace hot small objects. Optimize for hit rate *on your hot working set*, not global hit rate.

**❌ Misconception: CDN caches only work for static assets.**
**✅ Reality:** Modern CDNs cache API responses, HTML fragments, and even personalized content (with Vary headers or edge compute). Stripe, GitHub, and Shopify all serve dynamic API responses from CDN cache on cache-able endpoints.

**❌ Misconception: Redis is your source of truth with fallback to DB.**
**✅ Reality:** Redis is a cache — a derived copy. Your database is the source of truth. If Redis goes down, you get a thundering herd on your DB, not data loss. Design accordingly.

**❌ Misconception: The database query cache (MySQL) solves the problem.**
**✅ Reality:** MySQL's query cache was so contentious under concurrent writes that it was deprecated in MySQL 8.0 (2018) and removed entirely. Never use it. Use application-level caching instead.

## 3. Real-World Architecture Examples

### Meta (Facebook) — Scaling Memcache

**Scale trigger:** 1 billion daily active users, >1 trillion social graph edges, ~1 billion reads per second on user data.

**What they built:** Meta's 2013 NSDI paper "Scaling Memcache at Facebook" is the canonical reference. They run **thousands of Memcached servers** organized into pools. Each pool serves a different data type (user data, feed, graph). They wrote **McRouter**, a Memcached proxy that handles routing, replication, and failover, open-sourced in 2014.

**L1/L2 architecture:** Regional clusters have L1 caches local to each web cluster (smaller, lower latency). A shared L2 cluster serves as the fallback. L1 hit → ~0.5ms. L2 hit → ~2ms. DB hit → ~15ms.

**What they got wrong first:** Early deployments had severe cache stampede problems during cold start (deploys, node restarts). They solved this with a **lease mechanism**: on a cache miss, Memcached issues a lease (a unique token) to exactly one client, which then fetches from DB and populates. Other concurrent clients for the same key wait and retry, getting the cached value 10-100ms later.

**TAO:** For the social graph specifically, Meta built TAO (The Associations and Objects cache) — a purpose-built, distributed cache that understands graph queries. It maintains consistency with MySQL using a write-invalidation protocol and achieves 10ms global cache invalidation.

**Key stat:** Meta's Memcache cluster serves billions of reads per second at a cache hit rate of ~99%, reducing MySQL query volume by ~100x.

### Cloudflare — CDN at the Edge

**Scale trigger:** Serving 1+ trillion requests per month across 310+ PoP locations. At that scale, origin infrastructure cannot physically serve all requests.

**What they built:** Cloudflare's CDN stores cached content in NVMe SSD at each PoP. Their proprietary caching logic considers popularity, object size, and TTL to decide what to cache. Their **cache purge** system achieves global purge (by tag, hostname, or prefix) in **<150ms average** — an engineering feat at their PoP count.

**Tiered caching (Argo):** Requests that miss at local PoP travel to a "parent" PoP before hitting origin. This means during a cache cold-start (new content, deploy), origin receives 1 request per parent PoP instead of 1 per edge PoP — reducing origin thundering herd by a factor of 5-10x.

**What they got wrong:** In January 2023, a code change managing service tokens caused Cloudflare's own cache purge requests to fail at 20-70 req/s for 121 minutes. This demonstrated that the cache management plane itself is a critical path that needs the same reliability treatment as the data plane.

**Key stat:** For typical web properties using Cloudflare, cache hit rates of 85-92% are achievable for mixed (static + dynamic) content. Pure static: 95-99%.

### Netflix — Tiered Caching for Video Streaming

**Scale trigger:** 238 million subscribers, 100M+ hours of content streamed daily. A single viral new show release can require serving the same video segment to millions of concurrent viewers within minutes.

**EVCache:** Netflix built **EVCache** (Ephemeral Volatile Cache), an open-source distributed caching system built on top of Memcached with custom replication across AWS Availability Zones. It is used for member profile data, homepage personalization data, and playback state.

**What they got wrong first:** Early single-region caching failed during AZ outages. A single Memcached node going down would cascade — all traffic would hit the origin, which could not handle the load. EVCache solves this by replicating across 3 AZs: a read always hits the local AZ cache; writes are async-replicated to others. An AZ failure means the remaining two AZs absorb traffic with a pre-warmed cache.

**Open Connect (CDN):** Netflix's own CDN, deployed inside ISP networks. Video files are pre-positioned (cache warmed) nightly based on predicted demand. Hit rates on Open Connect exceed 99% for popular content. A cache miss means streaming from an AWS S3 bucket — expensive and slower.

**Key stat:** Netflix's Open Connect serves ~95% of Netflix traffic in countries where it's deployed. Avoiding that 95% S3 egress cost saves Netflix tens of millions of dollars monthly.

### Stripe — API Response Caching with Strong Consistency Requirements

**Scale trigger:** Processing hundreds of billions of dollars per year. APIs must be idempotent and consistent — you cannot serve a stale "payment succeeded" response.

**What they do:** Stripe uses CDN caching aggressively for read-heavy, non-sensitive API endpoints (e.g., list of currencies, fee schedules, webhook event schemas). For mutable resources (charges, payment intents), they use short TTLs (5-30s) with strong cache-busting on writes. Idempotency keys are stored in a distributed cache to ensure duplicate payment requests return the same response within a 24-hour window.

**Key insight from Stripe's engineering blog:** They treat the CDN as "the last mile of correctness" — the origin always writes the correct state to the DB and invalidates any CDN cache entry for mutable resources before returning the response to the client. No cache serves stale payment state.

### Design Questions to Ask Before Starting

1. **What is the read:write ratio?** Caching is most valuable above 80:20. At 50:50, cache invalidation complexity often outweighs benefit.
2. **What is the tolerable staleness?** 0ms (financial transactions), 1s (social feed), 60s (product catalog), 24h (analytics reports)?
3. **What is the working set size?** 80% of reads hitting 20% of data is normal (Zipf distribution). Does that 20% fit in your cache budget?
4. **What is the cost of a cache miss?** If a miss causes a 500ms DB query, you have higher urgency to cache. If it causes a 5ms query, the ROI is lower.
5. **Is the data user-specific or shared?** Shared data (product catalog, config) has enormous cache efficiency. Per-user data (session, cart) has lower efficiency but can still matter at scale.
6. **What happens during cache failure?** Your origin must be able to handle the fallback load or you have a latent bomb.

### Scale Evolution

**1K users/day (~0.01 req/s average, 1-5 req/s peak)**
- No distributed cache needed. DB buffer pool handles it.
- HTTP cache headers on static assets. That's it.
- Redis would be premature optimization.

**100K users/day (~1 req/s average, 50-100 req/s peak)**
- A single Redis instance (1-4GB RAM) for session storage and hot objects.
- CDN for static assets (S3 + CloudFront or Cloudflare free tier).
- Consider in-process LRU cache (e.g., `cachetools` in Python) for very hot config objects.
- DB: default buffer pool size is usually fine.

**1M users/day (~10 req/s average, 500-1,000 req/s peak)**
- Redis with replication (primary + 1 replica) for HA.
- CDN caching of API responses where TTL > 5s is acceptable.
- Start tracking cache hit rates — target >90% for hot data.
- Tune DB `shared_buffers` to 25% of RAM; `effective_cache_size` to 75%.
- Introduce read replicas for analytics queries.

**100M users/day (~1,000 req/s average, 50,000-100,000 req/s peak)**
- Redis Cluster (6+ nodes, 3 shards x 2 replicas minimum).
- L1 in-process cache (10-50MB per app server) to avoid Redis for hyperlocal hot keys.
- CDN with tiered caching (origin shield) to prevent thundering herd on cache cold-starts.
- Database write path must invalidate cache synchronously before returning success.
- Cache-aside for reads; write-invalidation (not write-through) for writes at this scale.
- Separate Redis clusters by data domain (user sessions vs. product data vs. rate limiting) to isolate failure domains.
- Consider purpose-built solutions: EVCache (Netflix-style), Pelikan (Twitter-style) for specific hot data.

## 5. Code / Implementation Perspective

### Python: Look-Aside Cache with Stampede Protection

```python
import time
import random
import hashlib
import redis
import json
from typing import Optional, Any, Callable

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

LOCK_TIMEOUT_SEC = 5   # max time another process waits for lock holder
RECOMPUTE_BETA   = 1.0 # XFetch beta — higher = more aggressive early recompute

def xfetch_should_recompute(ttl: int, delta: float, beta: float) -> bool:
    """
    Probabilistic early expiration (XFetch algorithm — Vattani et al.).
    Returns True if we should proactively recompute before TTL expires.
    delta: time (seconds) it took to compute the value originally
    """
    remaining = ttl  # seconds until expiry
    return -delta * beta * (random.random() ** 0.5) > remaining - time.time()

def get_with_stampede_protection(
    key: str,
    compute_fn: Callable[[], Any],
    ttl_sec: int = 300,
    delta_key: Optional[str] = None,
) -> Any:
    """
    Look-aside cache with mutex-based stampede protection.
    - On MISS: one caller acquires a lock, fetches from source, populates cache.
    - Other callers on the same key WAIT and retry rather than all hitting DB.
    """
    raw = r.get(key)
    if raw is not None:
        return json.loads(raw)

    lock_key = f"lock:{key}"
    lock_acquired = r.set(lock_key, "1", nx=True, ex=LOCK_TIMEOUT_SEC)

    if lock_acquired:
        try:
            start = time.time()
            value = compute_fn()          # expensive: DB query, API call, etc.
            delta = time.time() - start

            pipe = r.pipeline()
            pipe.set(key, json.dumps(value), ex=ttl_sec)
            if delta_key:
                pipe.set(delta_key, str(delta), ex=ttl_sec * 2)
            pipe.execute()
            return value
        finally:
            r.delete(lock_key)
    else:
        # Spin-wait up to LOCK_TIMEOUT_SEC for the lock holder to populate
        deadline = time.time() + LOCK_TIMEOUT_SEC
        while time.time() < deadline:
            time.sleep(0.05)
            raw = r.get(key)
            if raw is not None:
                return json.loads(raw)
        # If lock holder failed, fall through and compute ourselves
        value = compute_fn()
        r.set(key, json.dumps(value), ex=ttl_sec)
        return value

# ── Usage ──────────────────────────────────────────────────────────────────────
def get_product(product_id: int) -> dict:
    key = f"product:{product_id}"
    return get_with_stampede_protection(
        key=key,
        compute_fn=lambda: fetch_product_from_db(product_id),
        ttl_sec=3600,
    )

def fetch_product_from_db(product_id: int) -> dict:
    # Simulate 15ms DB query
    time.sleep(0.015)
    return {"id": product_id, "name": "Widget", "price": 9.99}
```

### Redis Command Reference for Common Patterns

```bash
# Set with TTL
SET product:42 '{"name":"Widget"}' EX 3600

# Get (returns nil on miss)
GET product:42

# Conditional SET (only if key does not exist — used for locks)
SET lock:product:42 1 NX EX 5

# Hash for structured objects (more memory-efficient than JSON string)
HSET product:42 name "Widget" price "9.99" stock "100"
HGETALL product:42
EXPIRE product:42 3600

# TTL check (useful for debugging)
TTL product:42  # -1 = no expiry, -2 = key gone, >0 = seconds remaining

# Lua script for atomic check-and-set (prevents race conditions)
EVAL "
  local val = redis.call('GET', KEYS[1])
  if val == ARGV[1] then
    return redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
  end
  return 0
" 1 product:42 '{"old":"val"}' '{"new":"val"}' 3600
```

### Language-Agnostic Pattern

```
FUNCTION get_cached(key, compute_fn, ttl):
    value = cache.get(key)
    IF value IS NOT NULL:
        RETURN value             ← fast path: ~0.5ms

    lock = acquire_lock(key + ":lock", timeout=5s)
    IF lock acquired:
        value = compute_fn()     ← slow path: 10-100ms
        cache.set(key, value, ttl=ttl)
        release_lock(lock)
    ELSE:
        value = wait_for_cache(key, timeout=5s)
        IF value IS NULL:
            value = compute_fn() ← fallback
    RETURN value
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **In-process cache (local memory)** | Config data, reference tables, objects accessed >10K/s on same instance | No network hop (fastest), but stale between instances; not shared | All major apps use this for config/feature flags |
| **Distributed cache (Redis/Memcached)** | Shared state across instances, user sessions, computed objects | Shared and consistent across nodes, but adds network hop (0.5-2ms) | Instagram, Twitter, GitHub, Shopify |
| **CDN caching** | Public, URL-addressable content with acceptable TTL | Massive geographic scale, but limited to HTTP semantics | Netflix, Airbnb, Shopify, GitHub |
| **Read replicas (DB-level)** | Analytical/reporting queries too large for in-memory cache | Zero application-layer change, but adds DB infrastructure cost and replication lag | Shopify, GitLab, Basecamp |
| **Materialized views** | Pre-computed aggregations, denormalized read models | Always fresh (or schedule-refreshed), but writes are slower, more storage | Redshift, BigQuery, Postgres |
| **Client-side caching (SWR/React Query)** | SPAs where user navigates between pages frequently | Zero server load for repeat views, but stale data risk on long sessions | Vercel, many React apps |
| **Edge compute caching** | Personalized responses that must still be fast globally | Eliminates round-trip to origin, but adds edge code complexity | Cloudflare Workers users, Fastly Compute |

**Opinionated recommendation:** For 90% of backend services, a **distributed cache (Redis/Valkey) with look-aside reads and write-invalidation** is the correct default. In-process L1 caching (10-50MB per instance) should be layered on top for the top 0.1% hottest keys. CDN should be layered below the application for public content. You should not reach for CDN or DB-layer solutions before you have properly tuned your application-level cache — they solve different problems and adding them before you understand your hit/miss patterns leads to over-engineered systems that are harder to debug.

Do **not** use a distributed cache as your source of truth. Do **not** use MySQL's built-in query cache. Do **not** use Redis Cluster before you need it — a single Redis primary with one replica handles 200,000+ req/s safely.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Latency reduction:** 15-100ms DB queries become 0.3-2ms Redis reads. That is a 10-100x improvement on the critical path.
- **Throughput multiplication:** A single Redis node can absorb 1M ops/s vs. 50-100K qps for a Postgres read replica. You get ~10-20x throughput per dollar.
- **Cost reduction:** Organizations that properly tune application caches report 20-35% reduction in cloud infrastructure spend (primarily compute and DB instance costs).
- **Availability improvement:** A well-designed cache layer absorbs load spikes without DB connection exhaustion. A viral post that generates 50x normal traffic hits the cache, not the DB.
- **Write offload:** Techniques like write-behind (async writes through cache to DB) can absorb write bursts, though at consistency cost.

### Costs and Limitations

- **Stale data:** Every cache has a window of staleness. For financial data, that window is 0ms (you should not cache it). For social feeds, 1-5s is typically acceptable. Confusing these is a category error.
- **Cold start problem:** After a deploy, cache flush, or cache node restart, all requests hit the DB simultaneously. A fresh Redis cluster on a 1M req/s system can generate a short but severe DB overload spike. Design for this explicitly.
- **Cache invalidation complexity:** The most under-estimated cost. "There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton. Every write path must now also update or invalidate the cache. Cross-entity invalidation (invalidating a product list when one product changes) is genuinely hard.
- **Memory cost:** Redis memory is expensive. A 64GB Redis r7g.2xlarge on AWS costs ~$1,000/month. Budget this explicitly.
- **Operational overhead:** A Redis cluster under production load requires monitoring (hit rate, evictions, memory fragmentation, replication lag), tuning (eviction policy, maxmemory-policy, slowlog), and runbook planning for failure scenarios.
- **The 99th percentile problem:** If your cache hit rate is 95%, 5% of requests still hit the DB at full latency. Your p99 response time is dominated by cache misses, not cache hits. Optimize for p99, not average.

### Core Tension

**Freshness vs. Availability.** Every cache is a stale copy. The shorter the TTL, the fresher the data — but the higher the DB load (more misses per unit time) and the lower the benefit of caching. The longer the TTL, the more inconsistent your system becomes. This tension has no universal resolution — it must be decided per data type and business requirement.

### My Recommendation

Use caching aggressively for **read-heavy, high-traffic, high-latency data** where you can clearly define the staleness tolerance. Use short TTLs (5-60s) rather than explicit invalidation wherever possible — it is far simpler operationally and "good enough" for most use cases.

Avoid caching **anything financial, security-critical (auth tokens, permissions), or that requires strong read-after-write consistency** unless you have explicit invalidation (not TTL-based expiry) and understand the failure modes.

Invest in **cache observability first**: track hit rate per key prefix, eviction rate, memory usage, and connection count before you add a second Redis cluster. You will be surprised how often the first bottleneck is a poorly-chosen TTL or a cache key that is too broad, not infrastructure capacity.

## 9. Failure Modes — What Goes Wrong

### Cache Stampede (Thundering Herd)

**Trigger:** A popular cached key expires (or is flushed). Hundreds or thousands of concurrent requests all get a cache miss simultaneously and each independently queries the database for the same data.

**Symptoms:** Sudden spike in DB query latency (from 2ms to 500ms+). DB CPU spikes to 100%. Application error rates rise. Redis hit rate drops to near zero for the affected key. Alerts fire on DB connection pool exhaustion.

**Detection:** Monitor `cache_miss_rate` by key prefix per second. If a single key generates >10 misses/second on a 300s TTL, you have a high-traffic key that needs stampede protection. Redis `MONITOR` command (use sparingly) shows all commands in real time.

**Recovery:**
1. Immediately: Manually re-populate the cache key (`SET key <value> EX 300`) from a known-good source to stop the hemorrhage.
2. Short term: Add mutex-based stampede protection (lock on miss, one fetcher, others wait).
3. Long term: Implement XFetch (probabilistic early expiration) so the cache proactively refreshes before it expires.

**Real Example:** Facebook's 2010 news feed stampede. When a data center came back online after maintenance, every user's news feed cache was cold. The simultaneous re-population caused cascading MySQL failures for hours. This drove the development of the lease mechanism in Facebook's Memcache, described in their NSDI 2013 paper.

---

### Cache Poisoning / Security Misconfiguration

**Trigger:** A CDN or reverse proxy cache stores a response that contains sensitive user-specific data (session info, PII, financial records) keyed by a URL or path that is shared across users.

**Symptoms:** User A sees User B's data. Support tickets about wrong account data. Security audit findings about data leakage. In severe cases, authentication bypass.

**Detection:** Penetration testing. Anomaly detection on response sizes (a login page that usually returns 2KB suddenly returns 50KB may indicate it cached an authenticated session). Header audit for responses lacking `Cache-Control: private` or `no-store` on sensitive endpoints.

**Recovery:**
1. Immediately: Purge all cached responses for the affected URL pattern.
2. Audit all CDN cache rules — add `Cache-Control: private, no-store` to every response that contains user-specific data.
3. Add `Vary: Cookie, Authorization` headers to prevent CDN from caching responses that differ by auth state.

**Real Example:** Railway.app CDN caching incident. An edge cache misconfiguration caused Railway's CDN to serve authenticated user content (deployment logs, environment variables) to unauthenticated requests for the same URL. The incident resulted in a public post-mortem and a complete audit of Railway's CDN caching rules.

---

### Cold Cache After Deploy / Restart

**Trigger:** A Redis cluster is restarted, flushed (e.g., `FLUSHALL` run by accident or during a migration), or a new cluster is provisioned without warming. All application servers now have a cache with 0% hit rate.

**Symptoms:** Immediate 10-100x increase in DB query volume. DB connection pool exhaustion within seconds to minutes. Application latency rises from <5ms to 100-500ms. Alert storm on DB CPU, connection count, and application error rate.

**Detection:** Watch cache hit rate: a drop from 95% to <5% within a 1-minute window is the signal. Also watch DB connection count as a secondary indicator.

**Recovery:**
1. **Cache warming script:** Pre-populate the cache with the top N hot keys from a recent DB scan or from application access logs before cutting over to the new cluster.
2. **Gradual traffic shift:** Route 5% of traffic to the new cluster, watch DB load, then increase.
3. **Circuit breaker:** Application should detect DB overload and reject non-critical requests (return 503) rather than queue indefinitely.

**Real Example:** Cloudflare November 2024 incident. A temporary 5-minute misconfiguration caused buffers to increase by 40x. This was not a cache flush specifically, but the principle is identical: when a caching layer is suddenly bypassed or degraded, the origin must be able to absorb the full load or the system collapses. Cloudflare's Buftee clusters were not provisioned for the resulting load, causing a multi-hour recovery.

---

### Cache Eviction Under Memory Pressure

**Trigger:** Cache memory fills up. Redis begins evicting keys according to the configured `maxmemory-policy` (default: `noeviction`, which rejects writes — almost certainly wrong for a cache). Under `allkeys-lru`, Redis evicts the least recently used keys to make space.

**Symptoms:** Gradual increase in cache miss rate (from 3% to 15% over hours/days). Corresponding gradual increase in DB load. If `maxmemory-policy = noeviction` (mis-configured), application starts receiving `OOM command not allowed` errors and all cache writes fail.

**Detection:** Monitor Redis `used_memory` vs. `maxmemory`. Monitor `evicted_keys` counter — any non-zero value means you are under memory pressure. Monitor `mem_fragmentation_ratio` — above 1.5 indicates fragmentation waste; above 2.0 requires a `MEMORY PURGE` or restart.

**Recovery:**
1. Immediately: Add memory to the Redis node or expand the cluster.
2. Audit TTLs: Are you setting TTLs on all keys? Keys without TTLs accumulate indefinitely.
3. Audit object sizes: Use `redis-cli --bigkeys` to find large keys consuming disproportionate memory.
4. Consider `allkeys-lfu` instead of `allkeys-lru` for skewed workloads — it retains frequently-used objects even if not recently accessed.

**Real Example:** A 2023 post-mortem documented by DZone: a production service had `maxmemory-policy = noeviction` (the default). As data grew, Redis began rejecting all write operations. The application silently swallowed Redis write errors (no exception handling). The cache stopped updating. After 12 hours, data was so stale that users began seeing orders from 2 weeks ago as "pending." The fix required both correcting the eviction policy and adding proper error handling for cache write failures.

## 10. When To Use vs. When To Avoid

**✅ Use caching when:**

1. **Read:write ratio is above 80:20 for the data type.** Product catalogs, user profiles, reference data, configuration — all are read far more often than written. Caching these is high-ROI.
2. **Computation is expensive and deterministic.** If computing the response requires multiple DB joins, external API calls, or heavy template rendering, and the output is the same for a given set of inputs, it is a strong cache candidate.
3. **You have measurable latency or throughput problems** at the DB or API layer. Cache as an optimization with a measurable target (e.g., "reduce DB CPU from 80% to 20%"), not as a preemptive abstraction.
4. **Staleness is tolerable.** Even a 5-second TTL on a heavily-read endpoint eliminates the thundering herd effect for most traffic bursts.
5. **CDN caching applies.** Any publicly accessible URL with content that does not change per user is a CDN cache candidate. This includes API responses, HTML pages, and images.

**❌ Do NOT use caching when:**

1. **The data requires strong consistency for correctness.** Financial balances, inventory counts for purchasing, access control decisions (authorization), medical records — these must never be served from a stale cache. The cost of a wrong answer exceeds all latency benefits.
2. **The write rate is high relative to read rate.** If every user action writes and then reads the same data, you are invalidating the cache nearly as fast as you fill it. The overhead is not worth the marginal latency improvement.
3. **The data is already fast enough.** If your uncached response time is 2ms (e.g., a simple primary-key lookup in a hot DB buffer pool), caching adds complexity for a sub-millisecond gain. Profile before caching.
4. **You do not have cache invalidation figured out.** A cache with no invalidation strategy and long TTLs is a correctness time bomb. Do not add cache unless you know how writes will update it.

**⚠️ The #1 Mistake Engineers Make:**

Treating the distributed cache as a **primary data store** rather than a derived cache. This manifests as: no TTLs set on keys (memory fills up), no fallback if Redis is unavailable (app crashes instead of degrading gracefully), and writes going to Redis but not the underlying DB (data loss on Redis restart or flush). Redis does have persistence (RDB/AOF) but it is designed for fast recovery, not durability. Your database is your source of truth. Your cache is expendable.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a URL shortener — how would you handle the redirect lookup at scale?"
- "Design Twitter's timeline feed — where would you cache, and how would you invalidate the cache when a new tweet is posted?"
- "We're seeing 90% of our DB load coming from the same 10 product pages. How would you reduce this?"
- "Walk me through the caching layers in your last production system."
- "What happens when your Redis cache goes down in production?"
- "We have a 99% cache hit rate but our p99 latency is still 800ms. What do you investigate?"
- "Design a system that requires data to be no more than 5 seconds stale — what's your caching approach?"

### What the Interviewer Evaluates

1. **Layered thinking:** Do you instinctively think about multiple cache layers (client, CDN, app, DB) or do you jump straight to "add Redis"?
2. **Failure mode awareness:** Do you mention stampede protection, cold cache recovery, stale data risks?
3. **Numbers:** Can you give latency figures, hit rate targets, and cost estimates? Or do you speak in pure abstractions?
4. **Trade-off articulation:** Do you name the core tension (freshness vs. availability) and make an opinionated call for the specific scenario?
5. **Invalidation strategy:** Do you think about how writes interact with the cache, or only the read path?

### Questions YOU Ask Before Answering

- "What's the read:write ratio for this data?"
- "What's the acceptable staleness window — seconds, minutes, hours?"
- "Is this data user-specific or shared across users?"
- "What's the current bottleneck — latency or throughput?"
- "What happens if a user sees stale data? What's the worst case?"
- "Is there a consistency requirement (e.g., read-after-write in the same session)?"

### Answer Examples by Level

**Junior (L3-L4) — Minimum Bar:**
> "I'd add Redis as a cache in front of the database. On a read, check Redis first; on a miss, hit the database and store the result in Redis with a TTL. This reduces DB load."

*What's missing:* Stampede protection, invalidation strategy, failure modes, TTL reasoning, observability.

---

**Senior (L5) — Expected Level:**
> "For a product catalog with 100M reads/day and maybe 1K writes/day, I'd use Redis with a look-aside pattern. TTL of 1 hour — catalog data changes rarely. I'd use key prefix `product:{id}` and invalidate explicitly on write. I'd add a mutex on cache miss to prevent stampede — one goroutine fetches, others wait. I'd set `allkeys-lru` eviction so Redis behaves like a cache under memory pressure, not a DB. For CDN, I'd set `Cache-Control: s-maxage=300` on the API response to also cache at the edge.
>
> Failure mode: if Redis goes down, the app falls back to DB — I'd configure the Redis client with a 200ms connection timeout and no retries so it fails fast. I'd pre-warm the cache after deploys using a background job that fetches top-1000 product IDs."

*What's missing:* Specific node sizing, replication topology.

---

**Staff (L6+) — Full Picture:**
> "Let me think about this in layers. First, what's the staleness tolerance? For catalog data, 5 minutes is fine; for inventory counts used in checkout, 0 seconds.
>
> Layer 1: CDN caching (`s-maxage=300`) for public product pages. This absorbs 80% of traffic before it hits my infrastructure — free throughput.
>
> Layer 2: Application cache (Redis Cluster). Key: `product:{id}`. TTL: 1 hour. Pattern: look-aside reads, write-invalidation on updates (not write-through — at this scale, the extra write latency of write-through is not worth it). Stampede protection via Redlock or a simpler singleflight pattern in the app layer. Eviction: `allkeys-lfu` because product access is Zipf-distributed — the top 1% of products get 60% of reads.
>
> Layer 3: In-process L1 cache (50MB per app server, 30-second TTL) for the top-100 products. These are so hot that even 0.5ms Redis latency matters at 50K req/s.
>
> Failure modes I'm designing for: (1) cold cache on deploy — background warmer pre-populates top-10K products before traffic shift; (2) Redis OOM — configured maxmemory + allkeys-lfu + alert at 75% usage; (3) cache stampede — singleflight/mutex pattern on miss.
>
> Observability: hit rate per key prefix, eviction rate, Redis memory usage, DB query volume as a secondary signal. I want to be paged if global hit rate drops below 90% — that almost always signals a bug in TTL or invalidation logic.
>
> For inventory specifically — I'd remove it from Redis entirely and serve it from a strongly-consistent read with short-circuit memoization only within a single request (not across requests). The cost of overselling due to stale inventory exceeds all latency benefits."
