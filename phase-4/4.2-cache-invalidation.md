## 1. What Is It? (Theory)

### Plain English

A cache is a fast copy of slower data. Cache invalidation is the process of deciding **when that copy is no longer trustworthy and what to do about it**. It is the answer to the question: "My source of truth changed — how do I make sure nobody reads the old value?"

Phil Karlton's famous quip — *"There are only two hard things in computer science: cache invalidation and naming things"* — is funny precisely because it is true. The hard part is not storing data in a cache. The hard part is knowing when the cached data is wrong and removing or replacing it before a caller reads it.

### The Problem It Solves at Scale

At small scale (1 server, 1 database, 1 cache node) you can afford to be lazy: put data in cache, give it a 60-second TTL, and accept that for up to 60 seconds some users see old data. This works fine for a blog's post view count.

At large scale this breaks down in three ways:

1. **Multiple writers** — 100 application servers may write the same database row concurrently; the cache must be consistent across all of them.
2. **Multiple cache nodes** — With a Redis cluster of 20 shards, invalidation must reach every node that holds a copy of the changed key.
3. **Cross-service data** — A user profile update in the `users` service must invalidate cached user objects in the `recommendations` service, the `feeds` service, and the `notifications` service simultaneously.

Without explicit invalidation strategy, you are left choosing between two bad options: serve stale data indefinitely, or set TTLs so short that cache hit rates collapse and your database gets hammered.

### Real-World Analogy

Think of a city's printed street map. The moment a new road opens, every copy of that map is wrong. You have several options:

- **TTL approach**: Throw out all maps after 1 year and reprint them — simple, but a road opening today means maps are wrong for up to 11 months.
- **Write-through approach**: When any road changes, immediately reprint and redistribute the map — always accurate but expensive.
- **Event-driven approach**: Install a digital notification system; anyone with a subscribed copy gets an "invalidate block 42" message the moment the road opens — fast and precise, but requires the notification infrastructure.
- **Stale-while-revalidate**: Give users the old map but hand them a new one when they next visit city hall — users never have to wait, eventual consistency.

### Why It Was Invented

Before explicit invalidation strategies, the only mechanism was TTL. TTL works but is a blunt instrument: it cannot react to a change, only to the passage of time. Event-driven and write-through invalidation were developed as systems scaled to the point where TTL alone produced unacceptable staleness (financial prices, social feeds, inventory levels) or unacceptable miss rates (setting TTL to 5 seconds at 100K RPS means 20,000 cache misses per second, which saturates a typical RDBMS).

### Concrete Example with Numbers

Suppose a product catalog item costs $49.99 and is cached at 1M RPS with a 5-minute TTL. A flash sale drops the price to $29.99. With pure TTL:

- For up to 5 minutes, every request returns $49.99.
- At 1M RPS × 300 seconds × 70% cache hit rate = **210 million requests** that see the wrong price.
- Revenue impact: customers who see $49.99 will not click "Buy". Customers who already paid $49.99 may request refunds.

With event-driven invalidation triggered by the price update:
- The old cache entry is deleted within ~50ms of the database write.
- The next ~5,000 requests (at 1M RPS × 5ms repopulation window) get a cache miss, hit the DB, and repopulate the cache.
- 210 million wrong-price responses → 5,000 cache misses. The cost is measurable but tiny.

## 2. How It Actually Works (Deep Mechanics)

### The Five Core Strategies

There are five fundamental approaches. Everything else is a combination or variant of these.

#### Strategy 1 — TTL (Time-To-Live)

1. Data is written to cache with a fixed expiry: `SET key value EX 300` (300 seconds).
2. All reads serve the cached value until it expires.
3. On expiry, the next read is a cache miss; the application fetches from DB and re-populates cache.
4. No explicit invalidation is ever sent.

```
Client         Cache           Database
  |--GET key-->|               |
  |            |--- miss ----->|
  |            |<-- row value -|
  |<-- value --|               |
                               |
  [... 300 seconds later ...]  |
                               | (row updated in DB)
  |--GET key-->|               |
  |            | key expired   |
  |            |--- miss ----->|
  |            |<-- new value -|
  |<-- new  --|               |
```

Key parameters: `max-age` / `EX` value. Short TTL = higher DB load + fresher data. Long TTL = lower DB load + staler data.

#### Strategy 2 — Write-Through

1. Every write goes **simultaneously** to cache and database.
2. The write is not acknowledged to the caller until both succeed.
3. Reads always hit cache (which is always current).

```
Client         App Server      Cache           Database
  |--PUT /item-|               |               |
  |            |--SET key val->|               |
  |            |--INSERT row----------------->|
  |            |<--OK----------|               |
  |            |<--OK----------------------------|
  |<--200 OK---|               |               |
```

Write latency = `max(cache_write_latency, db_write_latency)`. Typically: Redis write ~0.5ms, DB write ~5-15ms → effective latency ~15ms (dominated by DB). Cache write adds ~0.5ms overhead, which is usually acceptable.

#### Strategy 3 — Write-Around (Write-Invalidate)

1. Every write goes only to the database.
2. The application simultaneously deletes (or invalidates) the corresponding cache key.
3. The next read repopulates from the DB.

```
Client         App Server      Cache           Database
  |--PUT /item-|               |               |
  |            |--DEL key----->|               |
  |            |--UPDATE row----------------->|
  |<--200 OK---|               |               |
  |            |               |               |
  |--GET /item-|               |               |
  |            |--GET key----->|               |
  |            |  (miss)       |               |
  |            |--SELECT row----------------->|
  |            |<--new value--------------------|
  |            |--SET key new_val->|            |
  |<--new val--|               |               |
```

This is also called **cache-aside with invalidation** or **lazy loading**. It is the most common pattern in practice.

#### Strategy 4 — Event-Driven Invalidation (CDC)

1. Application writes only to the database.
2. A Change Data Capture (CDC) agent reads the database's write-ahead log (WAL).
3. WAL events are streamed to a message broker (Kafka, Redis Streams).
4. A cache invalidation consumer subscribes to the stream, reads change events, and issues `DEL` or `SET` commands to the cache.

```
App Server     Database        CDC Agent       Kafka           Cache Consumer     Cache
    |--INSERT-->|               |               |               |                  |
                |--WAL event--->|               |               |                  |
                                |--produce----->|               |                  |
                                                |--consume----->|                  |
                                                                |--DEL key-------->|
```

End-to-end invalidation latency with this pattern is typically **50–200ms** (WAL lag + Kafka propagation + consumer processing). The database write and cache invalidation are **decoupled**: the application write is fast (~5ms), and invalidation happens asynchronously.

#### Strategy 5 — Stale-While-Revalidate (SWR)

1. Cache stores both the value and a logical expiry time (separate from the physical TTL).
2. When a request arrives after logical expiry but before physical TTL:
   - Serve the stale value immediately (p99 latency: ~1ms from cache).
   - Trigger an **asynchronous** background refresh from the DB.
3. The physical TTL acts as an absolute upper bound on staleness.

```
Time:  0s        60s (logical)       90s (physical TTL)
       |---------|-------------------|
       |         |                   |
       | Fresh   | Stale, serve +    | Key expires,
       |         | revalidate async  | mandatory miss
```

HTTP header syntax: `Cache-Control: max-age=60, stale-while-revalidate=30`

This is a standard defined in RFC 5861 and implemented by Fastly, Cloudflare, Varnish, Nginx, and browser caches.

### ASCII Architecture — Write-Through vs CDC

```
┌─────────────────── WRITE-THROUGH ────────────────────┐
│                                                        │
│  Client ──→ App Server ──→ Cache (Redis)              │
│                    └──────→ Database (PostgreSQL)     │
│                                                        │
│  Pros: Zero staleness, simple mental model            │
│  Cons: Write latency = cache_write + db_write         │
└────────────────────────────────────────────────────────┘

┌──────────────────── CDC INVALIDATION ────────────────────┐
│                                                           │
│  Client ──→ App Server ──→ Database (PostgreSQL)         │
│                                 │                         │
│                             WAL │                         │
│                                 ▼                         │
│                        Debezium / CDC Agent               │
│                                 │                         │
│                           Kafka │ topic: db.changes       │
│                                 ▼                         │
│                     Cache Invalidation Service            │
│                                 │                         │
│                           DEL / │ SET                     │
│                                 ▼                         │
│                          Cache (Redis)                    │
│                                                           │
│  Pros: App write is fast; precise; works across services  │

```

### Key Numbers to Know

| Metric | Value |
|---|---|
| Redis `SET` / `DEL` latency (LAN) | < 0.5ms p99 |
| Redis `SET` / `DEL` latency (cross-region) | 10–80ms |
| Typical DB write latency (PostgreSQL, same AZ) | 2–15ms |
| CDC (Debezium) lag from commit to Kafka event | 10–100ms |
| Kafka consumer processing latency | 5–50ms |
| End-to-end CDC invalidation (same region) | 50–200ms |
| TTL jitter benefit | Reduces stampede likelihood by ~80% |
| SWR async refresh overhead | < 2ms background goroutine/thread |

### Misconceptions

**❌ Misconception:** "Just delete the key on every write and everything is fine."

**✅ Reality:** In distributed systems, the `DEL` and the `UPDATE` are two separate operations. If the `DEL` succeeds but the `UPDATE` fails (or vice versa), you now have either a stale cache entry or an empty cache that repopulates with old data. You need either a two-phase approach (delete-before-write + delete-after-write) or idempotent versioned writes.

---

**❌ Misconception:** "Write-through is always the safest strategy."

**✅ Reality:** Write-through serializes cache and DB writes. If the cache node is unavailable, your write fails entirely even if the DB is healthy. This turns a cache outage into a full write outage. You must handle partial write failure explicitly — most write-through implementations degrade to write-around when the cache is unreachable.

---

**❌ Misconception:** "Event-driven invalidation gives you strong consistency."

**✅ Reality:** CDC-based invalidation is **eventual consistency** with a 50–200ms window. Between the DB commit and the cache invalidation event being processed, some reads will get stale data. For financial systems requiring read-your-own-writes consistency, this is often unacceptable.

## 3. Real-World Architecture Examples

### Meta — TAO Cache Consistency at 10 Nines

**Scale trigger:** Meta's TAO (The Associations and Objects) system serves the social graph for 3 billion+ users. It is one of the largest cache deployments in the world. At this scale, even a "six nines" (99.9999%) consistency rate means millions of stale reads per day.

**What they built:** Meta engineered a system to achieve **99.99999999% (10 nines)** cache consistency. The architecture combines:

1. **Invalidation-on-write:** When a database row is mutated, invalidation messages are sent along with the MySQL replication stream. Cache servers consume these messages and evict entries.
2. **Lease mechanism:** To prevent thundering herds, when a cache key is invalidated, the first requesting client receives a "lease token." Only the lease holder can repopulate the key. Other concurrent requests either wait or are served a slightly stale fallback.
3. **Polaris monitoring:** A stateful tracing library logs every cache mutation (fill, invalidate, update). Polaris identifies anomalies and fires alarms in near-real-time, allowing on-call engineers to find cache inconsistency bugs within 30 minutes.

**What they got wrong first:** Before Polaris, race conditions in the invalidation pipeline were invisible for days or weeks. A client could: (1) read a key as "miss", (2) read from DB, (3) receive an invalidation for that same key (from a concurrent write), (4) write the now-stale value back to cache. This "post-invalidation fill" race was extremely hard to detect without instrumentation.

**Key lesson:** Invalidation without observability is not enough. You need tooling that can trace the order of events across fill, invalidate, and refill operations.

*Source: [Cache made consistent — Engineering at Meta (2022)](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)*

---

### Netflix — EVCache with Kafka-Based Cross-Region Invalidation

**Scale trigger:** Netflix operates a multi-region active-active architecture on AWS. EVCache (Ephemeral Volatile Cache) — their Memcached-based system — runs **200+ clusters, 22,000+ instances**, handling **400 million operations per second** with **14.3 PB of cached data**. When a movie metadata record changes, that change must propagate to cache clusters in us-east-1, us-west-2, eu-west-1, and ap-southeast-1 within seconds.

**What they built:** Netflix uses **CDC via Kafka** for cross-region cache invalidation:
1. A source-of-truth database emits change events to Kafka.
2. Each region subscribes to the Kafka topic.
3. Regional EVCache clusters receive `DEL` messages and evict keys.
4. The next regional read miss re-populates from the nearest data source.

For popular content (new show launches), they additionally use **proactive cache warming**: ML models trained on access logs predict which content keys will spike and pre-populate them hours before the traffic wave arrives. During popular releases, cache hit rates reach **99.99%**.

**What they got wrong first:** Early cross-region invalidation used a broadcast model — a change in us-east-1 would immediately purge the key everywhere. This created massive thundering herds when content metadata was updated during a release event (a single metadata update for a new season would fire 22,000 simultaneous DB reads across all clusters). They shifted to regional-level coalescing: multiple invalidation events for the same key within a 100ms window are deduplicated before being applied.

**Key lesson:** Invalidation at massive scale must include event deduplication. Streaming 10 metadata updates for the same key in 100ms should produce exactly 1 cache miss, not 10.

*Sources: [Netflix TechBlog — Caching for a Global Netflix](https://medium.com/netflix-techblog/caching-for-a-global-netflix-7bcc457012f1), [EVCache GitHub](https://github.com/Netflix/EVCache)*

---

### Cloudflare — Instant Purge with Sub-150ms Global CDN Invalidation

**Scale trigger:** Cloudflare caches content across 300+ PoPs (Points of Presence). When a customer triggers a cache purge (e.g., publishing a new blog post, deploying a new JS bundle, correcting a pricing page), the invalidation must propagate globally in milliseconds — not hours.

**What they built:** Cloudflare's "Instant Purge" architecture achieves sub-150ms global cache invalidation. The system:
1. Uses **cache tags** (called `Cache-Tag` or `Surrogate-Key` headers) to group related objects. A single `POST /cache/purge` API call specifying a tag cascades to all cached objects with that tag across all PoPs.
2. Internally, each PoP runs a lightweight messaging bus. A purge request fans out to all 300+ PoPs via a coreless, edge-computed broadcast — not via a central hub (which would create a single point of failure and a latency bottleneck).
3. Tag-based purging allows surgical invalidation: purging `product-catalog-region-apac` doesn't touch `product-catalog-region-emea`.

**What they got wrong first (and what still goes wrong for users):** The most common customer mistake is using `Purge Everything` instead of tag-based purging. A "purge everything" call invalidates all cached content globally — a blunt instrument that works for small sites but causes massive origin traffic spikes for high-volume customers. Cloudflare's own engineering guidance strongly recommends tag-based invalidation for any site serving > 10K RPM.

**Key lesson:** Cache invalidation granularity matters enormously at CDN scale. Design your tagging strategy before you cache, not after.

*Sources: [Cloudflare — Instant Purge (sub-150ms)](https://blog.cloudflare.com/instant-purge/), [Cloudflare — Coreless Purge Architecture](https://blog.cloudflare.com/part1-coreless-purge/)*

### Design Questions to Ask Before Starting

Before choosing a cache invalidation strategy, answer these:

1. **What is the acceptable staleness window?** Financial prices: 0ms. News headlines: 60s. User profile avatars: 24h. This directly determines your strategy.
2. **Who are the writers?** Single service? Multiple services? Third-party events (webhooks, CDC)? Multiple writers complicate write-through.
3. **Is read-your-own-writes consistency required?** A user who just updated their bio must see the new bio immediately. This rules out TTL-only and often rules out async CDC.
4. **What is the cache topology?** Single node, cluster, multi-region? More nodes = more invalidation messages to send = higher invalidation overhead.
5. **What is the write-to-read ratio?** If writes >> reads, caching may not help at all, and invalidation overhead may exceed caching benefits.
6. **What happens on cache failure?** If the cache is down, do writes still succeed? Does the application fall back to direct DB reads?

### Scale Evolution

#### 1K users/day

Single app server, single Redis node, single database. Cache-aside with a 5-minute TTL on all reads. No explicit invalidation. Write-through for anything requiring freshness. Total Redis memory: < 1 GB. DB query volume: ~100 QPS — no problem.

**Cache changes:** None. TTL is fine. Don't over-engineer.

#### 100K users/day (~500 RPS)

Multiple app servers. Same Redis node. Now writes from one app server do **not** automatically invalidate what another app server wrote to cache. Race conditions are now possible. Two simultaneous writes to the same DB row result in two `SET` calls to Redis — whichever arrives last "wins," but this may not match the DB state.

**Cache changes:**
- Add explicit `DEL key` on every write, before or after the DB write.
- Add TTL jitter (±20%) to prevent synchronized expiry stampedes.
- Start monitoring hit rates and cache key size distribution.

#### 1M users/day (~5,000 RPS)

Redis is now the critical path. Cache cluster required (3–6 shards). Multiple services share some cached data (user profiles cached in both the `feeds` service and the `notifications` service).

**Cache changes:**
- Introduce event-driven invalidation. The `users` service publishes a `user.updated` event on write. The `feeds` and `notifications` services subscribe and issue `DEL` commands.
- Add a secondary TTL as a safety net (even with events, you want a ceiling on how long stale data can survive a missed event).
- Implement distributed locking (`SET key px 200 NX`) to prevent stampedes on high-traffic keys.

#### 100M users/day (~50,000–500,000 RPS)

Multi-region deployment. Cache clusters in 3+ AWS regions. Invalidation must cross regions.

**Cache changes:**
- Adopt CDC (Debezium + Kafka) for reliable, replayable invalidation streams.
- Use tag-based invalidation at CDN layer for static/semi-static content.
- Implement version numbers in cache keys: `user:42:v7` instead of `user:42`. On write, increment the version in DB and let old keys expire via TTL. This eliminates the need to `DEL` keys entirely (the old key simply becomes unreachable and expires).
- Add Polaris-style consistency monitors: randomly sample cache vs DB values on a background thread to detect stale data.

## 5. Code / Implementation Perspective

### Python — Cache-Aside with Write-Invalidation + Distributed Lock

```python
import time
import redis
import hashlib
from contextlib import contextmanager
from typing import Optional, Any, Callable

r = redis.Redis(host="cache.internal", port=6379, decode_responses=True)

CACHE_TTL = 300          # 5 minutes default TTL
LOCK_TTL_MS = 500        # 500ms lock to prevent stampede
STALE_TTL_EXTENSION = 30 # extra seconds to serve while revalidating


def cache_key(entity: str, entity_id: int) -> str:
    return f"{entity}:{entity_id}"


@contextmanager
def redis_lock(key: str, timeout_ms: int = LOCK_TTL_MS):
    """Distributed lock using SET NX PX — prevents thundering herd."""
    lock_key = f"lock:{key}"
    acquired = r.set(lock_key, "1", px=timeout_ms, nx=True)
    try:
        yield acquired
    finally:
        if acquired:
            r.delete(lock_key)


def get_with_stale_revalidate(
    cache_key: str,
    fetch_fn: Callable[[], Any],
    ttl: int = CACHE_TTL,
) -> Any:
    """
    Stale-while-revalidate pattern:
    - Logical expiry stored as a separate key (cache_key:exp)
    - Physical TTL is ttl + STALE_TTL_EXTENSION
    - Serve stale data + trigger async refresh in background
    """
    value = r.get(cache_key)
    logical_exp = r.get(f"{cache_key}:exp")
    now = time.time()

    if value is not None:
        if logical_exp and float(logical_exp) < now:
            # Within stale window: serve stale + revalidate asynchronously
            with redis_lock(cache_key) as acquired:
                if acquired:
                    # Only one worker refreshes; others get stale value
                    import threading
                    threading.Thread(
                        target=_populate_cache,
                        args=(cache_key, fetch_fn, ttl),
                        daemon=True,
                    ).start()
        return value  # Return (possibly stale) value immediately

    # Hard miss: block and populate
    with redis_lock(cache_key) as acquired:
        if acquired:
            return _populate_cache(cache_key, fetch_fn, ttl)
        else:
            # Another worker is populating; wait briefly then retry
            time.sleep(0.05)
            return r.get(cache_key) or _populate_cache(cache_key, fetch_fn, ttl)


def _populate_cache(key: str, fetch_fn: Callable, ttl: int) -> Any:
    value = fetch_fn()
    if value is not None:
        pipe = r.pipeline()
        pipe.set(key, value, ex=ttl + STALE_TTL_EXTENSION)
        pipe.set(f"{key}:exp", time.time() + ttl)
        pipe.execute()
    return value


def invalidate(entity: str, entity_id: int) -> None:
    """Call this on every write to the source-of-truth database."""
    key = cache_key(entity, entity_id)
    pipe = r.pipeline()
    pipe.delete(key)
    pipe.delete(f"{key}:exp")
    pipe.execute()


# --- Usage example ---
def get_user(user_id: int) -> Optional[dict]:
    key = cache_key("user", user_id)
    return get_with_stale_revalidate(
        cache_key=key,
        fetch_fn=lambda: db_fetch_user(user_id),   # your DB call
        ttl=300,
    )

def update_user(user_id: int, data: dict) -> None:
    db_update_user(user_id, data)   # write to DB first
    invalidate("user", user_id)     # then invalidate cache
```

### Language-Agnostic Algorithm Description

**Write-Invalidate (most common):**
```
ON WRITE:
  1. Write to database (or fail fast)
  2. DELETE cache_key (fire-and-forget or with error handling)
  3. (Optional) DELETE cache_key again after DB commit confirms
     — the "double-delete" pattern handles race conditions

ON READ:
  1. GET cache_key
  2. IF hit: return value
  3. IF miss: SELECT from DB, SET cache_key with TTL, return value
```

**Double-Delete Pattern** (handles the post-invalidation fill race):
```
1. DEL cache_key              ← before DB write
2. UPDATE db_row
3. DEL cache_key              ← after DB write (async, best-effort)
```
This ensures that even if a request fills the cache between steps 1 and 2 with old data, step 3 clears it.

### Redis Commands Reference

```bash
# Basic TTL-based set
SET user:42 '{"name":"Alice"}' EX 300

# Conditional set (only if key doesn't exist — for locks)
SET lock:user:42 1 PX 500 NX

# Atomic pipeline (invalidate key + logical expiry together)
MULTI
DEL user:42
DEL user:42:exp
EXEC

# Tag-based invalidation using Redis Sets (manual tag grouping)
SADD tag:product-catalog user:42 item:7 listing:99
# On product catalog change:
SMEMBERS tag:product-catalog   # get all keys
# Then DEL each key in the returned set
```

### Kafka Consumer for CDC-Based Invalidation

```python
from confluent_kafka import Consumer
import json

consumer = Consumer({
    "bootstrap.servers": "kafka:9092",
    "group.id": "cache-invalidation-service",
    "auto.offset.reset": "earliest",
})
consumer.subscribe(["db.public.users", "db.public.products"])

while True:
    msg = consumer.poll(timeout=1.0)
    if msg is None or msg.error():
        continue

    event = json.loads(msg.value())
    table = event["source"]["table"]
    row_id = event["after"]["id"] if event["after"] else event["before"]["id"]

    key = f"{table}:{row_id}"
    r.delete(key)
    r.delete(f"{key}:exp")
    consumer.commit(asynchronous=False)
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **TTL-only** | Static/semi-static data (product thumbnails, config values); acceptable staleness > 60s; simple architecture | Simple but blunt — cannot react to changes, only time | Nearly universal as a safety net alongside other strategies |
| **Write-Through** | Financial systems requiring read-after-write consistency; single-service writers; write volume < 5K RPS | Zero staleness + write latency overhead (~0.5ms Redis round-trip); cache failure blocks writes | Stripe (payment state), banking systems |
| **Write-Invalidate (cache-aside + DEL)** | Most web applications; multiple writers; acceptable < 50ms staleness; cache miss rate is manageable | Simplest explicit invalidation; brief inconsistency window between DEL and next read refill | Facebook (early), Reddit, most mid-scale SaaS |
| **Event-Driven / CDC** | Multi-service architectures; cross-region invalidation; write patterns you do not control (3rd-party); high consistency requirements | 50–200ms eventual consistency; significant infra complexity (CDC agent, Kafka, consumer service) | Netflix, Airbnb, LinkedIn |
| **Stale-While-Revalidate** | Read-heavy workloads where most users tolerate N-second-old data; CDN/edge caching; recommendation feeds | Near-zero user-perceived latency; data can be stale up to stale window; not suitable for transactional data | Cloudflare, Fastly, Next.js (ISR), Vercel |
| **Version-Based Key Rotation** | High-churn data where DEL is error-prone; systems where you want provably immutable cache values | No invalidation needed — old keys expire naturally; increased key namespace size; client must know current version | Meta (content hashing), CDN static assets |

### Opinionated Recommendation

**Start with write-invalidate (cache-aside + `DEL` on write)**. It is the correct default for 80% of web applications. It is simple, debuggable, and well-understood.

**Add TTL as a mandatory safety net** regardless of which invalidation strategy you use. Even if you have event-driven invalidation, a TTL ceiling (e.g., 24h) ensures that a missed event or a bug in your invalidation pipeline does not serve stale data forever.

**Move to CDC/event-driven** only when you have demonstrated that write-invalidate is insufficient (usually because you have multiple services that share data and cannot all reliably issue `DEL` calls) and when you have the operational maturity to run a Kafka + CDC pipeline.

**Avoid write-through** unless you have a genuine read-after-write consistency requirement and a single writer. Write-through's failure mode — cache outage causes write outage — is often worse than brief staleness.

## 8. Trade-offs (Be Opinionated)

### Benefits (Specific, with Numbers)

- **Explicit TTL**: Predictable staleness ceiling; < 1ms overhead; no additional infrastructure.
- **Write-invalidate**: Eliminates stale reads after the ~5ms DB write completes; `DEL` costs < 0.5ms; no write latency impact.
- **Write-through**: Zero staleness (read-after-write consistent); eliminates cache-miss on the next read (~50ms saved on every post-write read).
- **SWR**: 100% of requests served from cache (including stale); background refresh adds < 2ms overhead per request to the refreshing thread; perceived latency stays < 1ms at all times.
- **CDC-based**: Precise, sub-second invalidation across services without application code coupling; replayable event stream allows rebuilding cache state after a failure.

### Costs & Limitations (Honest, with Numbers)

- **TTL**: At 60s TTL and 1M RPS, you serve up to ~60 million stale reads per data change. You are trading accuracy for simplicity.
- **Write-invalidate**: 50ms–200ms window of potential staleness (between `DEL` and cache repopulation). Under high concurrency, a 200-thread stampede after a popular key deletion can generate 200 simultaneous DB queries.
- **Write-through**: Adds ~0.5ms to every write. Cache unavailability blocks writes. Cache must be treated as a required dependency, not an optional optimization.
- **SWR**: Clients that arrive exactly at logical expiry time get stale data. If the background refresh fails (DB timeout, network issue), the stale data continues being served until physical TTL.
- **CDC**: Requires running Debezium, Kafka, and a consumer service. Adds ~3 operational components, each with its own failure modes. Typical team cost: 1–2 weeks of initial setup + ongoing SRE attention.

### Core Tension

**Consistency vs. Complexity vs. Write Latency.**

Every cache invalidation strategy is a negotiation between three forces:
- More consistency → more write-path complexity or higher write latency.
- Less complexity → less consistency or more write latency.
- Lower write latency → some form of eventual consistency.

You cannot fully optimize all three. Chose two.

### My Recommendation

**TTL + write-invalidate is the correct default for 95% of production systems.** Use a TTL of 5–60 minutes depending on data change frequency. Issue `DEL` on every write. Add TTL jitter (±20%) to prevent synchronized stampedes. This is boring, proven, and debuggable at 3am.

Invest in CDC-based invalidation only if your cross-service data consistency requirements have been demonstrated to be unmet by write-invalidate, and only if you have an SRE team capable of operating Kafka reliably. The "cool" architecture is not always the correct architecture.

## 9. Failure Modes — What Goes Wrong

### Cache Stampede (Thundering Herd)

- **Trigger:** A high-traffic cache key expires (or is explicitly deleted). Hundreds or thousands of concurrent requests all find a cache miss and simultaneously query the database to rebuild the key.
- **Symptoms:** DB CPU spikes from ~20% to 100% in under 1 second. DB connection pool exhausted. Application response times jump from 5ms to 500ms+. In extreme cases the DB crashes and takes the entire application offline.
- **Detection:** Alert on DB connection pool utilization > 80%. Alert on sudden p99 latency jump > 10x baseline. Track cache miss rate — a spike from 2% to 30%+ in 5 seconds is a signal.
- **Recovery:** (1) Immediately: add mutex/lock so only one request rebuilds the key. (2) Short-term: pre-warm the key if you know it will be evicted. (3) Long-term: add TTL jitter, implement stale-while-revalidate for hot keys, use probabilistic early expiration (PER algorithm).
- **Real Example:** Twitter documented thundering herd problems when popular tweet caches expired during viral events. A single tweet going viral could spike from 0 to 500K RPS within 30 seconds; if the tweet's cache key happened to expire during that window, the origin database would receive hundreds of thousands of simultaneous read requests.

---

### Stale Cache After Failed Invalidation

- **Trigger:** A `DEL` command is sent to the cache but fails silently (network timeout, Redis node restart, wrong shard routing). The database row is updated, but the cache continues serving the old value indefinitely (until TTL expires, which may be 24+ hours).
- **Symptoms:** A user updates their email address and continues to receive emails at the old address. A product's price shows as $99 in the cache but $49 in the database. Subtle data divergence that is hard to detect without explicit monitoring.
- **Detection:** Build a consistency checker: periodically sample 0.1% of cache reads and compare against the DB value. Alert when divergence rate exceeds 0.01%. Emit a metric per-key on every successful invalidation and alert on invalidation error rates.
- **Recovery:** (1) Flush the specific key manually. (2) Lower the TTL for the affected key class as a temporary mitigation. (3) Re-run the event through the CDC pipeline if using event-driven invalidation. (4) Long-term: use the double-delete pattern (DEL before write + DEL after write) to reduce window.
- **Real Example:** Meta's Polaris system was built specifically to detect this class of bug. Before Polaris, a race condition bug in their invalidation pipeline went undetected for days because the divergence was below the threshold that user complaints would surface.

---

### Invalidation Event Storm

- **Trigger:** A mass update operation (bulk DB migration, A/B test flag change, configuration deployment) triggers thousands or millions of simultaneous invalidation events. The cache is effectively flushed, and all traffic falls through to the database simultaneously.
- **Symptoms:** Indistinguishable from a cache stampede. DB load spikes. Response times degrade. Looks like a DDoS but is self-inflicted.
- **Detection:** Alert on invalidation message throughput. A sudden spike of > 10,000 invalidation events/second is abnormal and warrants investigation before the effects hit the DB.
- **Recovery:** (1) Implement rate-limiting on invalidation consumers — process at most N invalidations per second, queue the rest. (2) Use staggered bulk updates instead of batch updates. (3) For planned events, pre-warm the cache for the most-affected keys before triggering the invalidation.
- **Real Example:** A common e-commerce failure pattern: a price update job runs `UPDATE products SET price = ... WHERE category = 'electronics'` — this updates 50,000 rows atomically. If each row triggers a CDC event, the invalidation service receives 50,000 events in < 100ms, flushing the entire electronics category cache simultaneously. The next 50,000 product page loads all miss cache and hit the DB at once.

---

### Cross-Region Cache Inconsistency

- **Trigger:** A user writes data in Region A (us-east-1). The write updates the DB in us-east-1 and invalidates the cache in us-east-1. The cross-region replication of the invalidation event to eu-west-1 is delayed or dropped.
- **Symptoms:** A user in Europe sees stale data after making a change. Different users in different regions see different versions of the same data simultaneously.
- **Detection:** Track cross-region invalidation lag as a metric. Alert when average lag exceeds 500ms. Build a canary key that is written every 30 seconds and compare its value across all regional caches.
- **Recovery:** (1) Increase TTL so stale data expires even without invalidation. (2) Implement a reconciliation process that re-applies missed invalidation events from the WAL. (3) For critical data (financial, identity), bypass the regional cache and route reads to the primary region.
- **Real Example:** Netflix's initial cross-region EVCache deployment used synchronous replication. A network partition between us-east-1 and ap-southeast-1 caused all writes to fail until they switched to asynchronous replication, accepting eventual consistency in exchange for availability.

---

## 10. When To Use vs. When To Avoid

### Use When

✅ **Your data changes infrequently relative to read volume.** Product catalog items change rarely but are read millions of times. Cache hit rates of 90%+ justify the invalidation overhead.

✅ **You can tolerate bounded staleness (even if small).** If 50ms staleness is acceptable for your use case, write-invalidate is safe and simple. If 200ms staleness is acceptable, CDC is a viable option.

✅ **You have a clear owner for cache writes and deletes.** The service that writes to the database should also own cache invalidation for those keys. If ownership is clear, write-invalidate is clean and maintainable.

✅ **Your read latency matters more than write latency.** If the application is read-heavy (> 10:1 read-to-write ratio) and DB read latency is a bottleneck (> 10ms p99), caching with invalidation will meaningfully improve user experience.

---

### Do NOT Use When

❌ **Your data changes with every read.** Real-time analytics counters, live bid prices in high-frequency trading, or live sensor telemetry. The write-to-read ratio makes caching counterproductive — you will invalidate more than you hit.

❌ **You require strict read-after-write consistency across all clients.** A financial transaction system where every API call must see the most recent committed state is not a fit for any asynchronous invalidation strategy. Use strong consistency primitives (read from DB directly, or use synchronous write-through with a fallback).

❌ **Your cache invalidation path is more complex than your business logic.** If you are building more invalidation logic than application logic, you are probably over-caching. Step back and ask whether the DB (with proper indexes and connection pooling) can handle the read volume directly.

❌ **You cannot monitor and alert on cache inconsistency.** Caching without observability is dangerous. If you cannot tell when your cache is serving stale data, you will find out from users — usually at the worst possible time.

---

### The #1 Mistake Engineers Make

⚠️ **Invalidating the cache after the write instead of before, without understanding the race condition window.**

The sequence `UPDATE db_row → DEL cache_key` has a race window:

```
Thread A                          Thread B
UPDATE db_row (old→new)
                                  GET cache_key → HIT (old value)
DEL cache_key
                                  [Thread B read the stale value]
```

Thread B read the old value even though the DB had already been updated. For many workloads this is acceptable. But if you care about consistency, use **delete-before-write + delete-after-write (double-delete)**, or use **versioned keys** so stale keys can never be re-read after a write.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a system to cache user profile data. How would you handle invalidation?"
- "We're seeing stale data in our cache. Walk me through how you'd diagnose and fix it."
- "What is the thundering herd problem and how would you solve it in a distributed cache?"
- "Design a cache invalidation system for a multi-region e-commerce platform."
- "What are the trade-offs between TTL-based and event-driven cache invalidation?"
- "How did Meta achieve 10-nines cache consistency? What were the key mechanisms?"

### What the Interviewer Is Evaluating

1. **Do you know the failure modes?** — Can you enumerate what goes wrong, not just what goes right?
2. **Do you know when NOT to cache?** — Inexperienced engineers cache everything; experienced engineers know when to skip it.
3. **Can you reason about consistency levels?** — Strong, eventual, read-your-own-writes — do you know the differences and when each applies?
4. **Do you think about operational complexity?** — CDC is technically correct; is it right for a team of 3?
5. **Can you give concrete numbers?** — "It's faster" is a junior answer; "write-through adds < 0.5ms write latency but eliminates ~50ms on the next read" is a senior answer.

### Questions YOU Ask Before Answering

Before proposing a solution, ask:
1. "What is the acceptable staleness window for this data?"
2. "Is read-after-write consistency required, or is eventual consistency acceptable?"
3. "How many services read and write this data?"
4. "What is the write-to-read ratio?"
5. "What happens if the cache is temporarily down — does the application degrade gracefully?"

### Answer Quality Benchmarks

#### Junior (L3–L4)

> "I would put the data in Redis with a TTL. When the data changes, I'd delete the cache key so the next request repopulates it. For high-traffic keys I'd be careful about cache stampedes and add a lock."

This is correct but generic. No numbers, no failure modes beyond stampede, no discussion of distributed systems issues.

#### Senior (L5)

> "I'd use write-invalidate as the base pattern: on every DB write, issue a `DEL`. I'd add TTL as a safety net — even if the `DEL` is missed, data won't be stale forever. For hot keys, I'd add a distributed lock (Redis `SET NX PX 500`) to prevent thundering herd. I'd implement the double-delete pattern (delete before and after write) to close the race window. For monitoring, I'd track cache hit rate and set up a consistency checker that samples 0.1% of reads and compares against DB. If we go multi-region, I'd evaluate CDC with Debezium + Kafka for cross-region invalidation propagation, accepting 50–200ms eventual consistency."

This demonstrates awareness of failure modes, specific technical choices with reasoning, and operational considerations.

#### Staff (L6+)

> "The right invalidation strategy depends on several dimensions we need to nail down first: acceptable staleness, read-your-own-writes requirement, number of services touching this data, and write-to-read ratio. Let me walk through a decision tree...
>
> If staleness > 60s is acceptable and this is single-service: TTL-only, done. If we need < 10s staleness but not sub-second: write-invalidate with double-delete plus a 60s safety TTL. If we have cross-service data with multi-region requirements: CDC (Debezium/Kafka) with a consumer service that issues `DEL` commands — we accept 50–200ms eventual consistency in exchange for application-layer decoupling. I'd add Polaris-style consistency monitors (randomly compare cache vs DB values on a background thread) regardless of which strategy we pick.
>
> I'd argue against write-through for this system because it turns a cache outage into a write outage. That's a worse failure mode than 50ms of staleness. The key architectural principle is: **caches should degrade gracefully when unavailable, not cause hard failures.**
>
> For the thundering herd mitigation specifically, I'd combine three techniques: distributed locks for expensive rebuilds, TTL jitter (±20%) to prevent synchronized expiry, and stale-while-revalidate for high-read-volume keys where even a miss is too expensive. These compose well and each is independently debuggable."

This answer demonstrates: design tradeoffs before implementation, specific numbers, awareness of operational failure modes, architectural principles (graceful degradation), and a clear mental model of when each strategy applies.
