## 1. What Is It? (Theory)

### Plain English

Imagine a grocery store with one entrance. For three hours on a Saturday, the automatic door is broken — nobody can get in. When the mechanic finally fixes it, every single person who had been waiting outside rushes in simultaneously. The checkout lanes collapse, the deli counter can't keep up, and the store grinds to a halt.

That is a thundering herd. In distributed systems, the "broken door" is your cache key expiring. The "waiting crowd" is every concurrent request that hits the cache miss at the same moment. The "collapsed checkout lane" is your database.

**Formal definition:** A **cache stampede** (also called *thundering herd*, *dogpile effect*, or *cache miss storm*) occurs when a popular cached value expires and multiple concurrent readers simultaneously discover the miss, each independently deciding to regenerate the value from the source of truth — typically a database, an expensive API call, or a heavy computation.

### The Scale Problem

At low traffic (say, 10 RPS), if a cache key expires, you get 1–2 concurrent misses. Your database absorbs it trivially.

At high traffic (say, 10,000 RPS), the same expiration triggers 10,000 simultaneous database queries within the span of a single millisecond. Your database, which was designed to handle perhaps 500–1,000 queries/second, receives a 10–20x spike in load with zero warning. It either saturates, starts queuing, returns errors, or crashes outright. The cache never gets re-populated because every regeneration request is also failing.

This is not a theoretical concern. At 10,000 concurrent requests hitting a single expired key:
- **No protection:** 10,000 DB queries, p99 latency 8,920ms, 15% error rate
- **Mutex lock:** 1 DB query, p99 latency 1,240ms, 0% errors
- **XFetch (probabilistic):** 3–5 DB queries, p99 latency 45ms, 0% errors

### Why It Was Invented / Why It Matters

Caching was invented to absorb read traffic from slow data stores. Cache stampede is the ironic failure mode where the protective layer itself causes the outage. Every system that uses TTL-based caching is vulnerable. The faster your read traffic grows, the more catastrophic the stampede when it happens.

The problem was formally studied at scale starting around 2013 when Facebook documented it in their Memcache paper, and Vattani, Chierichetti & Lowenstein published the XFetch algorithm in 2015 (VLDB Endowment). It has caused documented outages at Discord, Twitter, Reddit, and countless smaller companies.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step Mechanics

**Normal cache-hit path (no problem):**
```
Request → Cache → HIT → Return value (< 1ms from Redis)
```

**The stampede sequence:**

```
T=0ms    : Cache key "user:profile:42" expires (TTL=300s)
T=0ms    : 500 requests/sec are already in-flight toward this key
T=1ms    : Request #1 checks cache → MISS → starts DB query (begins 50ms query)
T=1ms    : Request #2 checks cache → MISS → starts DB query (same 50ms query)
T=1ms    : Request #3–500 check cache → MISS → all start the same DB query
T=2ms    : 500 DB queries are now in-flight. DB connection pool exhausted.
T=10ms   : DB starts queuing. Latency climbs from 5ms → 100ms → 500ms.
T=50ms   : First DB query returns. Cache populated. But 499 more still running.
T=100ms  : DB CPU hits 100%. New queries start timing out.
T=200ms  : Application servers report database connection errors.
T=500ms  : Cascading failure: cache is populated but application is returning 500s.
T=1000ms : Alerting fires. On-call engineer paged.
```

```
        │  DB connection pool: 100 max → 400 queued           │
        │  DB CPU: 5% → 100% in 10ms                          │
        └─────────────────────────────────────────────────────┘
```

### Why Locks Don't Always Save You

A common misunderstanding is that a local (in-process) mutex is sufficient. It is not.

```
Application Server 1 (20 worker threads)
└── Local mutex → allows 1 thread through → 1 DB query

Application Server 2 (20 worker threads)
└── Local mutex → allows 1 thread through → 1 DB query

... (30 application servers total) ...

Application Server 30 (20 worker threads)
└── Local mutex → allows 1 thread through → 1 DB query

Net result: 30 simultaneous DB queries (still a stampede at scale)
```

A **distributed lock** (Redis SETNX) reduces this to exactly 1 DB query across all servers — but introduces a new problem: all other requests must wait, queue, or fail while that one regeneration is in-progress.

### Key Numbers to Internalize

| Scenario | DB Queries | p50 Latency | p99 Latency | DB CPU | Error Rate |
|---|---|---|---|---|---|
| Cache hit (baseline) | 0 | 1ms | 3ms | 2% | 0% |
| No protection, 10K RPS | 10,000 | 2,340ms | 8,920ms | 100% | 15% |
| Local mutex only | ~30–50 (one per server) | 580ms | 1,240ms | 15% | 0% |
| Distributed lock | 1 | 580ms | 1,240ms | 5% | 0% |
| XFetch (beta=1.0) | 3–5 | 12ms | 45ms | 2% | 0% |
| Stale-while-revalidate | 1 (background) | 1ms | 5ms | 2% | 0% |

### Common Misconceptions

**❌ Misconception: "This only happens if my cache is completely down."**
**✅ Reality:** The stampede happens at normal TTL expiration of any popular key. Your cache is healthy. The problem is the gap between "key expires" and "key is re-populated."

**❌ Misconception: "Setting a very short TTL reduces stampede risk because the cache refreshes quickly."**
**✅ Reality:** A shorter TTL means more frequent expirations, which means more frequent stampede opportunities. A 10-second TTL on a 10,000 RPS key means every 10 seconds you risk a stampede. Longer TTLs with proactive refresh are safer.

**❌ Misconception: "My load balancer will distribute the traffic so no single server hits the DB hard."**
**✅ Reality:** Load balancers distribute requests across application servers, but all of those servers query the *same* database for the *same* missing key. Load balancing does not prevent stampedes.

**❌ Misconception: "I can just add more database replicas."**
**✅ Reality:** Adding read replicas helps with baseline load but does not prevent the spike pattern. All replicas get hit simultaneously, and the spike is multiplicative.

## 3. Real-World Architecture Examples

### Meta (Facebook) — News Feed & Memcache Leases

Meta's 2013 USENIX paper "Scaling Memcache at Facebook" describes one of the most influential public solutions to cache stampede at planetary scale.

The problem: Facebook's News Feed ranking is computationally expensive (hundreds of milliseconds to rebuild). When a popular user's feed key expires in Memcache, thousands of PHP front-end servers simultaneously discover the miss. Each PHP server has no visibility into what the others are doing. Without protection, the same expensive feed computation runs hundreds of times in parallel.

**Meta's solution: Leases.** When a memcache server receives a GET for a missing key, it returns a *lease token* (a unique 64-bit integer) to exactly one client and a "wait" response to all others. Only the client holding the lease is permitted to SET the value. Others either poll briefly or receive stale data. This is distributed locking with built-in coordination baked into the cache protocol itself — eliminating the need for application-level lock management.

Meta also separately developed and open-sourced **XFetch** for cases where probabilistic early expiration is preferred over strict locking, particularly for News Feed ranking data and friend suggestion caches.

**Scale:** At the time of the paper, Facebook was running ~150M RPS through Memcache. The lease mechanism prevented what would otherwise be millions of redundant computation jobs per day.

### Discord — Session Service Thundering Herd (March 2017)

Discord's March 2017 outage is a textbook example of the thundering herd pattern appearing outside of traditional cache expiration — at the connection layer.

Discord's presence service (which tracks online/offline status) became momentarily disconnected from its cluster. The session service nodes — all of them simultaneously — detected the disconnection and attempted to reconnect. This created a synchronized reconnection storm: thousands of sessions all hitting the presence cluster at the same instant.

The reconnection flood overwhelmed memory queues on session nodes. Once queues filled, session nodes ran out of memory and crashed. When they came back up, they *again* tried to reconnect simultaneously, repeating the pattern.

**Impact:** 1/3 of all connected Discord sessions stalled. Full outage requiring a system-wide restart.

**Discord's fix:** Exponential backoff with jitter on reconnection attempts. Rather than all nodes retrying at the same 1-second interval, they retry at random intervals within a window (e.g., random(1s, 30s)), spreading the reconnection load over time. This is the connection-layer equivalent of TTL jitter.

**Key metric:** Recovery took under 16 minutes, but the root cause was a thundering herd from 0 coordination between reconnecting nodes.

### Twitter — Hot Key & Timeline Stampede

Twitter's timeline storage system (built on top of a distributed cache) exposed a specific variant: the **hot key** problem. A "hot key" is a cache entry so popular it saturates a *single* Redis/Memcache shard, regardless of stampede.

Twitter built a dedicated hotkey detection system as part of their timeline storage migration. The system detects keys being accessed at anomalous rates (e.g., a celebrity's timeline at 50,000 RPS vs. a normal user's timeline at 5 RPS) and signals this back to the caching layer, which then applies local replication: instead of one shard holding the hot key, the key is mirrored to multiple shards, and requests are spread across them.

This is a different attack than classic stampede (it affects running systems, not just expiring keys), but the thundering herd pattern is the same: too many coordinated requests at a single point.

**Twitter's recommendation:** Combine hotkey detection with local in-process caching (in-memory LRU in each application server) for the top N hottest keys. Even a 100ms in-process TTL reduces Redis load by orders of magnitude for trending content.

### Cloudflare — Request Collapsing at the Edge

Cloudflare handles cache stampede at the CDN layer through a mechanism called **request collapsing** (also called request coalescing). When a cache key expires at a Cloudflare edge datacenter and multiple requests arrive simultaneously:

1. One request is forwarded to the origin server.
2. All other requests are held ("collapsed") at the edge node.
3. When the origin responds, the single response is served to all waiting requests simultaneously.

This reduces origin traffic by 90%+ during stampede events. It also uses TTL jitter at the CDN layer to prevent synchronized expiration across different edge datacenters — a global cache warming event at Cloudflare scale would otherwise trigger a worldwide stampede toward origin servers.

Per Cloudflare's engineering blog on lock-free probabilistic caching ("Sometimes I Cache"), their edge layer combines request collapsing with probabilistic early expiration for popular assets, effectively eliminating database-hitting stampedes for most content types.

### Scale Evolution

#### 1K Users/Day (~1 RPS sustained)
At 1 RPS, cache expiration triggers at most 1–2 simultaneous misses. A single in-process mutex per server is sufficient. Stampede risk: near zero.

**Appropriate solution:** Simple cache-aside with no stampede protection. Premature optimization here wastes engineering time.

#### 100K Users/Day (~10 RPS sustained, 50 RPS peak)
At 50 RPS peak, a single expiration generates 5–10 simultaneous misses. Still manageable for most databases, but trending toward risk.

**Appropriate solution:** Add TTL jitter (±10–20% of base TTL). This spreads expiration events and eliminates the synchronized burst. Zero code complexity added. `ttl = base_ttl + random(0, base_ttl * 0.2)`.

#### 1M Users/Day (~100 RPS sustained, 500 RPS peak)
At 500 RPS, a single popular key expiring sends 50–100 simultaneous DB queries. Most databases saturate at this kind of sudden spike.

**Appropriate solution:**
- TTL jitter (always on)
- Distributed mutex lock (Redis SETNX) for top-10 most expensive cache keys
- Stale-while-revalidate for user-facing data where <5s staleness is acceptable

#### 100M Users/Day (~10K RPS sustained, 50K–100K RPS peak)
At 10K–100K RPS, even a distributed lock introduces significant queuing latency (all non-winning requests wait 50–500ms). Users feel this.

**Appropriate solution:**
- TTL jitter (always on)
- XFetch probabilistic early expiration for all cache keys with TTL > 60s
- Local in-process LRU cache (50–100ms TTL) on each application server for top-N hottest keys
- Background async refresh with stale-while-revalidate for user-facing data
- Hotkey detection + shard replication for single-key saturation events
- Circuit breaker on the database connection pool to prevent cascade failure

### Naive (Broken) Cache-Aside — What Everyone Starts With

```python
import redis
import time

r = redis.Redis(host="localhost", port=6379)

def get_user_feed(user_id: int) -> dict:
    key = f"feed:{user_id}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)

    # BUG: 10,000 concurrent requests all reach here simultaneously
    # when key expires. All of them execute expensive_db_query().
    feed = expensive_db_query(user_id)  # 50ms, CPU-intensive
    r.setex(key, 300, json.dumps(feed))
    return feed
```

### Solution 1 — Distributed Mutex Lock (Good for <1M RPS)

```python
import redis
import json
import time
import random

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

LOCK_TTL_MS = 5_000   # 5s — must exceed max recompute time
WAIT_POLL_MS = 50     # poll every 50ms while waiting
MAX_WAIT_MS  = 3_000  # give up after 3s waiting

def get_user_feed(user_id: int) -> dict:
    key      = f"feed:{user_id}"
    lock_key = f"lock:feed:{user_id}"

    # L1: Check cache first (fast path — ~1ms)
    cached = r.get(key)
    if cached:
        return json.loads(cached)

    # L2: Try to acquire distributed lock (atomic SET NX PX)
    # Only ONE server across the entire cluster wins this.
    lock_token = f"{time.time()}-{random.random()}"
    acquired = r.set(lock_key, lock_token, nx=True, px=LOCK_TTL_MS)

    if acquired:
        try:
            # Double-check: another server may have populated while we waited
            cached = r.get(key)
            if cached:
                return json.loads(cached)

            # We are the ONE winner — do the expensive work
            feed = expensive_db_query(user_id)     # ~50ms
            ttl  = 300 + random.randint(0, 60)     # jitter ±20%
            r.setex(key, ttl, json.dumps(feed))
            return feed
        finally:
            # Release lock ONLY if we still own it (prevents accidental release
            # of a lock re-acquired by another process after our TTL expired)
            current = r.get(lock_key)
            if current == lock_token:
                r.delete(lock_key)
    else:
        # We lost the lock race — wait and retry or return stale
        deadline = time.time() + MAX_WAIT_MS / 1000
        while time.time() < deadline:
            time.sleep(WAIT_POLL_MS / 1000)
            cached = r.get(key)
            if cached:
                return json.loads(cached)

        # Fallback: return stale data if available, else raise
        stale = r.get(f"stale:{key}")
        if stale:
            return json.loads(stale)
        raise CacheUnavailableError(f"Could not get feed for {user_id}")
```

### Solution 2 — XFetch Probabilistic Early Expiration (Best for High Traffic)

```python
import redis
import json
import time
import math
import random

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def xfetch_should_recompute(
    ttl_remaining: float,   # seconds until current value expires
    delta: float,           # seconds it takes to recompute the value
    beta: float = 1.0,      # tuning knob: higher = more aggressive early refresh
) -> bool:
    """
    XFetch algorithm from Vattani, Chierichetti & Lowenstein (VLDB 2015).
    Returns True if THIS request should trigger an early recomputation.
    
    The probability of returning True increases as ttl_remaining approaches 0.
    At TTL=0, always returns True. At TTL >> delta, almost always False.
    
    beta=0.5: conservative, refreshes ~5s before expiry on a 60s TTL
    beta=1.0: balanced (recommended default)
    beta=2.0: aggressive, refreshes ~30s before expiry on a 60s TTL
    """
    if ttl_remaining <= 0:
        return True
    # XFetch core formula: recompute if current_time - delta*beta*ln(rand) >= expiry
    return -delta * beta * math.log(random.random()) >= ttl_remaining

def get_with_xfetch(
    key: str,
    recompute_fn,           # callable that returns (value, compute_time_seconds)
    base_ttl: int = 300,    # seconds
    beta: float = 1.0,
) -> dict:
    """
    Cache-aside read with XFetch probabilistic early expiration.
    
    Stores compute time (delta) alongside the value so XFetch can
    calibrate how aggressively to pre-warm based on actual cost.
    """
    meta_key = f"meta:{key}"

    raw   = r.get(key)
    meta  = r.get(meta_key)
    ttl_r = r.ttl(key)      # seconds remaining (-1 = no expiry, -2 = missing)

    if raw and meta:
        delta = float(json.loads(meta)["delta"])
        # Should this request proactively refresh?
        if xfetch_should_recompute(ttl_r, delta, beta):
            # This request "volunteers" to refresh — others keep reading stale
            t_start = time.monotonic()
            fresh_value = recompute_fn()
            actual_delta = time.monotonic() - t_start

            jittered_ttl = base_ttl + random.randint(0, int(base_ttl * 0.15))
            pipe = r.pipeline()
            pipe.setex(key, jittered_ttl, json.dumps(fresh_value))
            pipe.setex(meta_key, jittered_ttl + 60,
                       json.dumps({"delta": actual_delta}))
            pipe.execute()
            return fresh_value
        # Normal hit — return cached value with no DB interaction
        return json.loads(raw)

    # True cold miss — must recompute (first time or full expiry)
    t_start = time.monotonic()
    value   = recompute_fn()
    delta   = time.monotonic() - t_start

    jittered_ttl = base_ttl + random.randint(0, int(base_ttl * 0.15))
    pipe = r.pipeline()
    pipe.setex(key, jittered_ttl, json.dumps(value))
    pipe.setex(meta_key, jittered_ttl + 60, json.dumps({"delta": delta}))
    pipe.execute()
    return value
```

### Solution 3 — Stale-While-Revalidate (Best UX, Requires Async)

```python
import asyncio
import redis.asyncio as aioredis
import json, time, random

r = aioredis.Redis(host="localhost", port=6379)

# Background refresh task set — prevents duplicate background refreshes
_refresh_in_progress: set[str] = set()

async def get_with_swr(
    key: str,
    recompute_coro,
    base_ttl: int = 300,
    stale_window: int = 60,    # serve stale data for up to 60s while refreshing
) -> dict:
    """
    Stale-While-Revalidate: always serve from cache (even if stale),
    trigger background refresh when data is in the stale_window.
    p50 latency: ~1ms (always a cache read). No user ever waits for DB.
    """
    raw = await r.get(key)
    ttl = await r.ttl(key)

    if raw:
        # Data exists — serve it immediately
        result = json.loads(raw)
        # If we're in the stale window AND no background refresh is running
        if ttl < stale_window and key not in _refresh_in_progress:
            _refresh_in_progress.add(key)
            asyncio.create_task(_background_refresh(key, recompute_coro, base_ttl))
        return result

    # True miss — must wait for recompute (cold start only)
    value = await recompute_coro()
    jittered = base_ttl + random.randint(0, int(base_ttl * 0.2))
    await r.setex(key, jittered, json.dumps(value))
    return value

async def _background_refresh(key, recompute_coro, base_ttl):
    try:
        value = await recompute_coro()
        jittered = base_ttl + random.randint(0, int(base_ttl * 0.2))
        await r.setex(key, jittered, json.dumps(value))
    finally:
        _refresh_in_progress.discard(key)
```

### Redis Commands Reference

```bash
# Atomic distributed lock (Redis 2.6.12+) — DO NOT use SETNX + EXPIRE (non-atomic)
SET lock:feed:42 "token-abc123" NX PX 5000

# Check lock owner before release (use Lua for atomicity in production)
GET lock:feed:42

# Lua script for safe lock release (atomic check-and-delete)
EVAL "if redis.call('get',KEYS[1]) == ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:feed:42 "token-abc123"

# TTL inspection for XFetch
TTL feed:user:42      -- remaining seconds (-2 = missing, -1 = no expiry)
PTTL feed:user:42     -- remaining milliseconds (more precise)

# Set with TTL jitter at write time
SET feed:user:42 "{...}" EX 345   -- base 300s + 45s jitter
```

### Language-Agnostic Pattern

```
function get_cached(key, recompute, ttl, strategy):
  value = cache.get(key)
  if value is FRESH:
    return value
  
  if strategy == MUTEX:
    if lock.acquire(key, ttl=5s):
      value = cache.get(key)   # double-check
      if not value:
        value = recompute()
        cache.set(key, value, ttl + jitter(ttl * 0.2))
      lock.release(key)
    else:
      wait_for_cache(key, timeout=3s)  # or return stale
  
  elif strategy == XFETCH:
    if xfetch_trigger(cache.ttl(key), recompute_delta, beta=1.0):
      value = recompute()      # this request voluntarily refreshes
      cache.set(key, value, ttl + jitter)
  
  elif strategy == SWR:
    if value is STALE:
      background(recompute, cache.set)  # async, non-blocking
      return value                       # serve stale immediately
    else:
      value = recompute()
      cache.set(key, value, ttl + jitter)
  
  return value
```

| **Nginx (proxy_cache_lock)** | Reverse proxy cache | Stampede prevention at HTTP layer | 100K+ RPS | No | Open-source (NGINX Plus for enterprise) | `proxy_cache_lock on` collapses simultaneous misses to one upstream request |
| **Memcached + lease protocol** | Distributed cache | Facebook-style lease-based locking | Millions of RPS (Memcached native) | No | Infrastructure cost | Less feature-rich than Redis; lease mechanism described in Facebook's 2013 paper |
| **Hazelcast / Apache Ignite** | In-memory data grid | JVM-native cache + lock | Horizontal scaling, JVM ecosystem | Both | Open-source + enterprise | Near-cache feature: local in-JVM copies of hot data with XFetch-like refresh |
| **Caffeine (Java)** | In-process LRU cache | L1 in-process cache | Single JVM, millions of RPS | No | Open-source | AsyncLoadingCache with SWR semantics built-in; 0 network latency |

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **TTL Jitter only** | Any scale; first line of defense; prevents synchronized bulk expiry across a fleet | Does not prevent stampede on a *single* popular key; just prevents fleet-wide synchronized expiry | Universal — Cloudflare, AWS CloudFront, virtually every CDN |
| **Local in-process mutex** | Single application server; dev/test environments; small-scale deployments | Race condition window exists between servers in a cluster; does not work in distributed systems | Simple web apps, single-server deployments |
| **Distributed lock (Redis SETNX)** | Medium-scale; expensive per-key regeneration; strict freshness required | Introduces lock wait latency (p99 spikes to 500ms–2s); lock owner can die holding lock | Facebook (leases variant), Reddit, Stripe |
| **XFetch probabilistic early expiration** | High-traffic systems; p99 latency is critical; freshness can be ~seconds-old | Requires storing compute delta alongside value; harder to reason about deterministically | Meta (News Feed), LinkedIn (recommendations), high-traffic e-commerce |
| **Stale-While-Revalidate (SWR)** | User-facing UIs; feeds, recommendations, dashboards; staleness acceptable | Data served is always N-seconds stale; not suitable for financial/inventory data | Cloudflare, Vercel, Twitter (timeline), most CDNs |
| **Background refresh / pre-warming** | Predictable traffic patterns; scheduled content (sports, TV, product launches) | Requires knowing what to pre-warm; over-warming wastes resources; misses cold traffic | Netflix (pre-warms CDN before new season drops), Ticketmaster (pre-warms before sale opens) |
| **Request coalescing (collapse)** | HTTP/CDN layer; reverse proxies; high-concurrency API gateways | Only works at request-level granularity; doesn't help with application-level recomputation | Cloudflare, Varnish, Nginx, AWS CloudFront |
| **Double-checked locking** | Any mutex-based solution; prevents lock acquisition after another server already repopulated | Minor code complexity; mandatory step when using any locking approach | Standard practice in all production mutex implementations |

**My opinionated recommendation:**

Layer these in order. Start with TTL jitter everywhere — it costs zero and prevents fleet-wide synchronized expiry. Add a distributed mutex for your top 5–10 most expensive and popular keys. Once you hit 1M RPS+, replace the mutex on hot keys with XFetch; the lock wait latency becomes your bottleneck before the DB does. Use stale-while-revalidate as your default pattern for user-facing APIs that tolerate 5–30s of staleness. Most teams over-engineer this — TTL jitter + distributed lock solves 95% of real-world cache stampede incidents.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Orders-of-magnitude reduction in peak DB load.** A distributed mutex takes 10,000 simultaneous DB queries down to 1. XFetch spreads the same load across 3–5 early refreshes over 30 seconds. The database never sees a spike.
- **Improved p99 tail latency.** Without protection, p99 during a stampede can reach 8–9 seconds. With XFetch, p99 stays at 45ms — a 200x improvement.
- **System resilience.** Stampede protection is what separates systems that survive traffic spikes from systems that don't. The cache is supposed to be your shield; stampede protection keeps the shield intact under fire.
- **Composability.** TTL jitter, distributed locks, XFetch, and SWR are additive. They don't conflict. You can layer all four simultaneously.

### Costs

- **Code complexity.** Naive cache-aside is 5 lines of code. Distributed mutex with proper lock release (Lua, token ownership, timeout) is 40–60 lines. XFetch requires storing metadata alongside values. Each layer adds cognitive overhead.
- **Stale data window.** XFetch and SWR both explicitly trade freshness for availability. In domains where freshness is contractual (financial data, inventory levels, authentication tokens), this is not a valid trade.
- **Distributed lock failure modes.** A Redis node failure during lock holding leaves the key locked until TTL expires (5s of blocking). Lua script failures can leak tokens. Over-aggressive lock TTLs cause timeouts. These are real production failure modes.
- **Redis as a SPOF for locks.** If you're using Redis to both cache data *and* to manage distributed locks, a Redis outage eliminates your cache *and* your stampede protection simultaneously.

### The Core Tension

The fundamental tension is: **freshness vs. throughput**. Every stampede prevention mechanism solves the problem by serving data that is slightly older than the "pure correct answer." Pure correctness at high concurrency requires every reader to wait for the writer, which destroys throughput. The engineering question is not *whether* to tolerate staleness but *how much staleness is acceptable for this particular piece of data*.

**My recommendation:** Define staleness tolerance per data type, not per system. Financial balances: 0s tolerance → use strong consistency, no caching. Product recommendations: 60s tolerance → XFetch with beta=1.0. Marketing content: 3600s tolerance → SWR with long stale window. Treat cache stampede protection as a first-class design decision alongside consistency requirements, not as an afterthought added when the pager fires.

## 9. Failure Modes — What Goes Wrong

### Failure Mode 1 — Lock Leak (Zombie Lock)

**Trigger:** The application server holding the distributed lock crashes, exits with an exception, or loses network connectivity to Redis after acquiring the lock but before releasing it. Alternatively, the lock TTL is set too low and the recomputation takes longer than expected.

**Symptoms:** All requests for the affected cache key queue behind a phantom lock. After the lock TTL expires (e.g., 5 seconds), one new request acquires the lock, recomputes, and releases. But if the original key's recomputation was only half-complete in the DB, the cache may be populated with partial data.

**Detection:** Monitor lock acquisition rate vs. lock release rate. Alert if `lock:*` keys persist beyond 2× the expected compute time. Use `SCAN` with pattern matching to detect long-lived lock keys.

**Recovery:** Lock TTL auto-expires. Normal operation resumes within the configured lock TTL. For persistent issues, add lock-age alerting and manual `DEL lock:key` as an operator runbook step.

**Real Example:** A Python web worker holding a 5-second Redis lock on a feed computation receives a SIGKILL from the OS (due to a memory limit breach). The lock sits in Redis for 5 seconds. All 3,000 requests/second for that feed key queue. After 5 seconds, a new worker acquires the lock. This appears in dashboards as a 5-second p99 latency spike on cache keys ending in the lock key pattern.

---

### Failure Mode 2 — Thundering Herd After Redis Restart

**Trigger:** A Redis node restart (upgrade, crash recovery, failover to replica) causes a large fraction of cached keys to be unavailable simultaneously. All requests that previously cached-hit now cache-miss simultaneously. The database receives the full request load with zero caching benefit — identical to every key expiring at once.

**Symptoms:** Redis restart at T=0 causes DB CPU to jump from 5% to 90%+ within 30 seconds. Application error rate spikes. Database connection pool exhausts. Even after Redis recovers, the database is too overloaded to serve cache-warming queries efficiently, so the cache takes 10–15 minutes to re-warm organically.

**Detection:** Correlate Redis node restart events (CloudWatch, Datadog) with simultaneous DB CPU and connection pool saturation.

**Recovery:** Pre-warm cache before Redis failover using a warming job. Implement circuit breakers at the application layer: when DB error rate > 20%, start serving cached stale data (if available from secondary storage) rather than hammering the DB. Stagger Redis rolling restarts (one node at a time with 60s wait between) to avoid full cluster unavailability.

**Real Example:** ElastiCache for Redis performs a maintenance window failover. The 90-second window during primary → replica promotion causes all application cache hits to miss. The backend Postgres receives 50× its normal query rate. Read replicas saturate. This is the "Redis restart thundering herd" — a stampede triggered not by TTL expiry but by cache layer unavailability.

---

### Failure Mode 3 — XFetch Beta Misconfiguration (Excessive Early Expiration)

**Trigger:** XFetch beta parameter set too high (e.g., beta=5.0 or beta=10.0) causing the algorithm to trigger recomputation 5–10 minutes before actual TTL expiry on a 5-minute TTL key. Net result: the cache key is being recomputed almost constantly, with each incoming request having a high probability of triggering an early refresh.

**Symptoms:** Database load is paradoxically *higher* with XFetch enabled than without it. Cache hit rate appears healthy, but DB query rate matches raw traffic rather than being suppressed by the cache. Compute cost spikes.

**Detection:** Track `delta` values stored in metadata keys. Calculate effective early-refresh window: `delta * beta`. Alert if `effective_window > 0.5 * base_ttl` — this means you're spending half the TTL window in "probabilistic refresh zone," defeating the purpose.

**Recovery:** Reduce beta to 1.0 (default). Validate that delta values stored in metadata are accurate — if your recompute function now takes 2× longer than it did when the metadata was last written, beta effectively doubles.

**Real Example:** An e-commerce site migrated from mutex locking to XFetch. Developer set beta=3.0 "to be safe." For product listing pages with a 5-minute TTL and 200ms recompute time, the effective refresh window was 200ms × 3.0 × (log factor) ≈ 3–4 minutes. The cache provided 1–2 minutes of true caching per 5-minute TTL cycle. DB load was 3× higher than before migration.

---

### Failure Mode 4 — Stale-While-Revalidate + Background Refresh Goroutine/Task Leak

**Trigger:** The background refresh coroutine/goroutine/task throws an unhandled exception or hangs indefinitely. The `_refresh_in_progress` tracking set becomes inconsistent. New background refreshes are blocked because the flag says one is already running. The cached value ages past the stale window. Effectively: the cache key is never refreshed, but all readers think a refresh is in progress.

**Symptoms:** Stale data ages indefinitely. Monitoring shows "background refresh task count" stuck at 1 for affected keys. The database shows zero queries for those keys (because background refresh never completes, so it never succeeds, but nothing triggers a synchronous refresh either).

**Detection:** Track background task count, task age, and last-successful-refresh timestamp per key. Alert if `last_refresh_age > 3 × stale_window`.

**Recovery:** Add timeout to background refresh tasks. Implement task heartbeat monitoring. Ensure `_refresh_in_progress.discard(key)` is always called in a `finally` block (not just on success path).

## 10. When To Use vs. When To Avoid

### Use Stampede Protection When

**✅ You have popular, expensive-to-compute cache keys.** If regenerating a key takes more than 20ms and the key receives more than 100 RPS, a cache miss will generate 2+ simultaneous DB queries per missed millisecond. At 10K RPS and 50ms recompute time, you'll get ~500 simultaneous DB queries on every cold miss.

**✅ Your system has "celebrity" or "hot" keys.** When a single cache key represents a viral post, a trending product, a celebrity profile, or a real-time event (sports score, stock price), that key can attract 1,000× more traffic than average. Stampede protection is non-negotiable at this disproportionate access pattern.

**✅ Traffic is spiky or event-driven.** If your traffic profile includes sudden spikes (TV ad breaks, product launches, sports events, news stories), your cache keys that were comfortable under normal load become stampede victims the instant the spike hits. Pre-warming + XFetch is the correct pattern here.

**✅ You operate at ≥ 100K RPS sustained or ≥ 1M RPS peak on any service.** At this scale, any unprotected cache miss is a potential incident. Stampede protection should be architectural, not an afterthought.

### Do NOT Use Stampede Protection When

**❌ Your data must be strongly consistent (financial, inventory, auth).** If staleness is unacceptable — bank account balances, stock levels, session validity — do not use TTL-based caching at all. Cache stampede protection is a mechanism for *managing staleness gracefully*, not eliminating it. Applying XFetch or SWR to financial data creates correctness bugs, not just performance quirks.

**❌ Your traffic is too low for it to matter.** If your service handles < 1,000 RPS and your database can handle 500+ QPS, a stampede will never saturate your DB. Premature stampede protection adds code complexity and operational burden for zero benefit. Add it when your p99 monitoring shows cache-miss-correlated latency spikes, not before.

**❌ You have a flat, uniformly distributed access pattern with no hot keys.** If every cache key receives roughly the same access rate and your key space is large enough that individual key expiry events are rare, stampede risk is low. This is common in per-user session caches where each user has their own key and you have millions of users.

### The #1 Mistake

**⚠️ Using a local (in-process) mutex as your only stampede protection in a distributed system.**

This is the most common mistake in production. A local mutex prevents multiple threads within a single server from simultaneously hitting the DB, but does nothing about the 20–50 other application server instances that are independently experiencing the same cache miss at the same time. Every server sends one DB query. With 30 application servers, you still get 30 simultaneous DB queries per cache miss.

If you're deploying more than one application server instance — you need a *distributed* lock (Redis SETNX) or a protocol-level solution (XFetch, SWR), not an in-process `threading.Lock()`.

## 11. Interview Perspective

### Real Question Phrasings

- "How would you handle a cache miss storm when a popular key expires?"
- "Your database is getting hammered every 5 minutes. How do you debug and fix it?"
- "Design a caching system for a viral news feed with 10M users — how do you handle sudden traffic spikes?"
- "What is the thundering herd problem and how would you solve it in a distributed system?"
- "Explain how you would implement cache stampede prevention at Twitter scale."
- "Walk me through how Facebook's Memcache lease mechanism works."

### What Interviewers Are Actually Evaluating

Interviewers are not testing whether you know the words "thundering herd." They are evaluating:

1. **Do you think in failure modes?** Can you identify *why* a naive cache implementation breaks at scale?
2. **Do you understand distributed vs. single-node behavior?** Do you call out that local mutexes are insufficient?
3. **Do you know multiple solutions and their trade-offs?** Can you compare mutex vs. XFetch vs. SWR without prompting?
4. **Can you quantify the problem?** Do you talk in concrete numbers (RPS, latency, QPS) or vague generalities?
5. **Are you opinionated?** Senior+ engineers have recommendations. "It depends" without a follow-up is a red flag.

### Junior Engineer Answer (Adequate)

> "Cache stampede happens when a cache key expires and multiple requests try to rebuild it at the same time. You can use a mutex lock so only one thread does the rebuild. Everyone else waits."

This is correct but incomplete. It misses distributed context and alternative approaches.

### Senior Engineer Answer (Good)

> "Cache stampede is when a popular key expires and N simultaneous requests all miss the cache and hammer the DB. A local mutex helps within one server, but in a distributed system you need a distributed lock — Redis SETNX with a TTL. Only one server wins the lock, does the DB query, populates the cache, then releases. Others wait or serve stale. Important detail: always do a double-check GET after acquiring the lock, because another server may have populated the key while you were acquiring.
>
> The downside of mutex is lock wait latency — p99 can spike to 1–2s. For high-traffic systems, I'd prefer XFetch: probabilistic early expiration where requests near TTL expiry have an increasing probability of triggering a background refresh. The original Vattani 2015 paper shows this is provably optimal. You also always add TTL jitter as a baseline — ±15–20% of base TTL — to prevent fleet-wide synchronized expiry."

### Staff Engineer Answer (What Interviewers Remember)

> "There are four distinct problems people call 'thundering herd,' and the solutions differ:
>
> **1. Single-key expiry storm:** Classic stampede. TTL jitter first (always), then distributed mutex for expensive keys, XFetch for high-traffic keys where lock wait latency is unacceptable. XFetch achieves p99 45ms vs. mutex's p99 1,240ms at 10K RPS — the numbers are from the original VLDB paper benchmarks.
>
> **2. Hot-key saturation:** The key hasn't expired; it's just getting 50,000 RPS on a single Redis shard. Solution: local in-process LRU cache with 50–100ms TTL for the top-N hottest keys. This is what Twitter built for celebrity timelines.
>
> **3. Cache warm-up after restart:** Redis restarts, all keys are cold simultaneously. This is fleet-wide stampede, not single-key. Solution: pre-warming jobs, circuit breakers, and staggered restarts. Same root cause, different intervention.
>
> **4. Reconnection thundering herd:** Discord's 2017 outage. Nothing to do with TTL — connection loss causes synchronized reconnection attempts. Solution: exponential backoff with jitter.
>
> For a real design interview, I'd ask: what's the staleness tolerance? Financial data: no caching at all. Recommendations/feeds: SWR with 30s stale window. Live counts: XFetch with beta=1.0. Product pages: TTL jitter + mutex on top 100 SKUs. The answer is always a layered strategy, not a single technique."
