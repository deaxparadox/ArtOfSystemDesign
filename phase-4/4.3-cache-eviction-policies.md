## 1. What Is It? (Theory)

### The Core Problem

Your cache has 8 GB of RAM. Your working set is 80 GB. You cannot fit everything.

Every time you add a new entry, you must potentially remove an old one. The question is: **which one?** That decision is your eviction policy — and it has more impact on system performance than almost any other cache tuning parameter.

A bad eviction policy can:
- Evict the hottest key right before a traffic spike
- Allow a one-time full-table scan to flush your entire working set
- Cause cache thrashing where the same expensive computation is re-run thousands of times per second

**Cache eviction policies are prediction algorithms.** They try to answer: "Which cached item is least likely to be requested again in the near future?" The better your prediction, the higher your hit rate, and the lower your backend load.

### The Library Analogy

Imagine a library reading room that can seat 100 books on the desk at once. You have 10,000 books in the back stacks. The librarian needs a policy for which books to keep on the desk:

- **FIFO**: The book that arrived first gets removed first (ignores whether anyone is reading it)
- **LRU**: Remove the book that hasn't been touched the longest
- **LFU**: Remove the book that has been read the fewest total times
- **ARC**: Adaptively balance between "recently read" and "frequently read" based on current demand
- **W-TinyLFU**: Keep a small "new arrivals" section with LRU and a large "popular" section with LFU, using a compact frequency sketch to decide admission

### Why This Is a Hard Problem

The "optimal" eviction algorithm (Belady's Algorithm / OPT) requires knowing the future — it evicts the item that will be requested furthest in the future. Since we cannot know the future, every real policy is an approximation backed by assumptions about access patterns.

Real-world access patterns are messy:
- **Zipf distribution** (power law): ~20% of keys receive ~80% of requests — most systems exhibit this
- **Temporal locality**: recently accessed items are likely to be accessed again soon
- **Scan pollution**: a one-time sequential read of 50 million records can flush your entire LRU cache
- **Burst patterns**: viral content causes sudden frequency spikes on keys that were previously cold

The gap between a naive policy (FIFO) and a good one (W-TinyLFU) can be **15–35% higher hit rate** on production workloads. At 1 million requests/second, that difference is 150,000–350,000 additional database queries every second.

## 2. How It Actually Works (Deep Mechanics)

### FIFO — First In, First Out

**Data structure**: A simple queue.

```
Insertion order:  [A] → [B] → [C] → [D] → [E]  (E is newest)
Eviction:          ^--- A is always next to be evicted
```

- O(1) insertion, O(1) eviction
- Zero overhead — no tracking of access patterns
- Terrible hit rate in almost all real workloads
- Use case: task queues, log buffers, NOT general caching

**❌ Misconception**: "FIFO is simple so it must be fast enough for caching."
**✅ Reality**: FIFO's hit rate on Zipfian workloads (which describe most real systems) is 10–20% worse than LRU. The CPU cost saved by avoiding access tracking is orders of magnitude smaller than the cost of the extra cache misses.

---

### LRU — Least Recently Used

**Data structure**: Hash map + doubly linked list.

```
MRU end                                       LRU end
[E] <-> [D] <-> [C] <-> [B] <-> [A]
 ^                                 ^
newest access                oldest access
 (keep)                        (evict next)
```

**How it works step by step**:

1. **Cache hit** (`GET key`): Find node in O(1) via hash map, detach from current position, prepend to MRU end. Cost: O(1).
2. **Cache miss + eviction needed**: Remove tail node (LRU end) from list AND from hash map. Insert new node at MRU end. Cost: O(1).
3. **Memory**: Each node stores key, value, prev pointer, next pointer. ~48–80 bytes of overhead per entry beyond the value itself.

**Redis's approximation**: True LRU requires a doubly linked list across all keys, which is expensive for millions of keys. Redis uses **probabilistic LRU**: when eviction is needed, it samples N random keys (default N=5, configurable to N=10), checks their `lru_clock` timestamp, and evicts the least recently used of that sample. This approximates true LRU with ~3–5% accuracy loss while avoiding O(N) overhead.

**Hit rate on Zipfian workloads with 10% cache ratio**: ~75–80%

**❌ Misconception**: "LRU keeps the most popular items in cache."
**✅ Reality**: LRU keeps the most *recently* accessed items. If a popular item was last accessed 60 seconds ago and a one-time scan accessed 10,000 items in the last 30 seconds, LRU will evict the popular item. This is called **scan pollution** and it is a real production problem.

---

### LFU — Least Frequently Used

**Data structure**: Hash map + frequency-sorted structure (min-heap or doubly linked list of frequency buckets).

```
Frequency buckets:
freq=1: [X, Y, Z]        <-- evict from here first
freq=5: [B, C]
freq=12: [A]
freq=47: [D, E]          <-- most popular, protected
```

**How it works**:

1. Every key carries a frequency counter.
2. On access: increment that key's counter and move it to the appropriate frequency bucket.
3. On eviction needed: remove a key from the lowest-frequency bucket (breaking ties with LRU within the bucket).

**The frequency decay problem**: LFU without decay has a critical flaw. A key accessed 1 million times 6 months ago and never touched since will be protected forever, while a key that just became viral today (accessed 50 times) will be evicted. This is called **frequency lock-in** or **cache pollution by historical frequency**.

**Redis LFU with decay**: Redis 4.0+ uses a decay mechanism controlled by `lfu-decay-time` (minutes). The counter is a logarithmic approximation (not raw count) that decreases by 1 for every `lfu-decay-time` minutes of no access. This balances historical frequency with recency.

```
Redis LFU counter decay formula:
counter -= elapsed_minutes / lfu_decay_time
```

**Hit rate on Zipfian workloads with 10% cache ratio**: ~78–83%

**❌ Misconception**: "LFU is always better than LRU."
**✅ Reality**: On workloads with rapidly shifting popularity (trending content, live sports, flash sales), LFU reacts slower than LRU because frequency counters must accumulate before new items get protection.

---

### ARC — Adaptive Replacement Cache

Developed at IBM Almaden Research Center (Megiddo & Modha, FAST 2003). Used in ZFS, NetApp ONTAP, and several database systems.

**The key insight**: Maintain two LRU lists plus their "ghost" histories:

```
┌─────────────────────────────────────────────────────────────┐
│                        ARC Cache                            │
│                                                             │
│  T1 (recency list)          T2 (frequency list)             │
│  ┌──────────────────┐       ┌──────────────────┐           │
│  │ A  B  C  D  E    │       │ X  Y  Z  W       │           │
│  │ (seen once)      │       │ (seen 2+ times)  │           │
│  └──────────────────┘       └──────────────────┘           │
│                                                             │
│  B1 (T1 ghost history)      B2 (T2 ghost history)          │
│  ┌──────────────────┐       ┌──────────────────┐           │
│  │ F  G  H  I  J   │       │ K  L  M           │           │
│  │ (evicted from T1)│       │ (evicted from T2) │          │
│  └──────────────────┘       └──────────────────┘           │
│                                                             │
│  Adaptive parameter p: controls T1/T2 size split           │
└─────────────────────────────────────────────────────────────┘
```

**Adaptation mechanics**:
- If a miss hits in B1 (recently evicted from T1): increase p → give more space to T1 (recency)
- If a miss hits in B2 (recently evicted from T2): decrease p → give more space to T2 (frequency)
- The algorithm continuously shifts the T1/T2 balance based on what is being missed

**Why it beats LRU and LFU in practice**:
- Workload shifts from recency-dominant to frequency-dominant (e.g., morning burst vs. sustained traffic): ARC adapts within seconds
- Scan pollution: scans only fill T1, never promote to T2, so they cannot evict frequently-used items

**Hit rate on mixed workloads**: 10–20% improvement over pure LRU. ZFS production benchmarks show 15–25% improvement on database workloads.

**Patent note**: IBM holds a patent on ARC (US Patent 6,996,676). This blocked open-source adoption and led to alternative implementations like CLOCK-Pro and CAR.

### W-TinyLFU — Window TinyLFU (The Modern Gold Standard)

Used by: **Caffeine** (Java), **Ristretto** (Go, used by Dgraph, Dgraph's Badger), **Apache Ignite**, and many others.

**The frequency sketch problem**: Maintaining exact frequency counts for millions of keys requires too much memory. TinyLFU uses a **Count-Min Sketch** — a probabilistic data structure that estimates frequency using a small fixed-size array of hash counters.

Count-Min Sketch memory: ~8 bytes per counter × 4 hash functions × (estimated_keys / epsilon) — for 1 million keys with 1% error rate, this is ~3.2 MB. Compare to storing exact counts: ~40 MB.

**W-TinyLFU architecture**:

```
                    Incoming requests
                           │
                    ┌──────▼──────┐
                    │Count-Min    │
                    │Sketch       │ ← frequency estimator
                    │(~3 MB for   │
                    │ 1M keys)    │
                    └──────┬──────┘
                           │ frequency estimate
                    ┌──────▼──────────────────────────┐
                    │                                  │
                    │  Window Cache (1% of capacity)   │
                    │  LRU eviction within this zone   │
                    │  "new arrivals" zone              │
                    └──────────────┬───────────────────┘
                                   │ candidate for admission
                                   │
                    ┌──────────────▼───────────────────┐
                    │   Admission Filter                │
                    │   if freq(candidate) >            │
                    │      freq(victim from main):      │
                    │      admit, else reject           │
                    └──────────────┬───────────────────┘
                                   │ admitted
                    ┌──────────────▼───────────────────┐
                    │                                   │
                    │  Main Cache (99% of capacity)     │
                    │  Segmented LRU (SLRU):            │
                    │    Protected segment (80%)        │
                    │    Probationary segment (20%)     │
                    │                                   │
                    └───────────────────────────────────┘
```

**Key properties**:
- New items always enter the Window Cache first (handles burst/new popularity)
- Items must prove frequency to graduate to Main Cache (handles scan pollution)
- Within Main Cache, SLRU gives a second chance before eviction
- Frequency sketch is reset periodically (halving all counters) to handle temporal shifts

**Hit rate on Zipfian workloads with 10% cache ratio**: ~85–92%

Benchmark on Caffeine (W-TinyLFU) vs. Guava (LRU) on real production traces from Wikipedia, YouTube, and Facebook storage systems: Caffeine achieves **20–40% higher hit rate** than Guava LRU with the same cache size.

### S3-FIFO — Simple, Scalable, Efficient (SOSP 2023)

Published at SOSP 2023 (Carnegie Mellon University). Adopted by Google, VMware, Redpanda, and multiple open-source libraries.

**The insight**: FIFO is highly concurrent (no pointer manipulation under locks), but has poor hit rates because it gives every item exactly one chance. S3-FIFO uses three queues to give objects a second chance while maintaining FIFO's concurrency advantages.

```
 Incoming items
      │
      ▼
┌──────────┐
│  Small   │  10% of capacity
│  FIFO    │  new items, 1-bit "accessed" flag
│  Queue   │
└────┬─────┘
     │
     │ item accessed again? → promote
     │ item accessed once?  → move to ghost
     │ item never accessed? → evict
     │
     ├──────────────────────────────────────▶ [Ghost Queue]
     │                                         tracks recently evicted
     │                                         keys (no values stored)
     ▼
┌──────────┐
│  Main    │  90% of capacity
│  FIFO    │  promoted items, 1-bit "accessed" flag
│  Queue   │  second chance on access before eviction
└──────────┘
```

**Performance**:
- **6x higher throughput** than LRU-based algorithms due to FIFO's lock-free design
- Lower miss ratio than LRU on 10 of 14 datasets in the SOSP 2023 paper
- Evaluated against 6,594 cache traces from 14 real-world datasets
- Ghost queue enables scan resistance: items evicted from Small FIFO without a second access are remembered, and if they reappear immediately (scan), they bypass the Main FIFO

### CLOCK — The Practical LRU Approximation

Used by: OS page table managers (Linux, Windows, macOS), PostgreSQL buffer pool.

```
         ┌─────────────────────────────────┐
         │    Clock Hand (pointer)         │
         │           ▼                     │
    ┌────┴──┬──────┬──────┬──────┬──────┐  │
    │  bit  │  1   │  0   │  1   │  1   │  │
    │  flag │  A   │  B   │  C   │  D   │  │
    └───────┴──────┴──────┴──────┴──────┘  │
                                           │
    Hand rotation:                         │
    - bit=1: clear bit, advance hand       │
    - bit=0: evict this entry              │
    └─────────────────────────────────────┘
```

Each cache entry has a "reference bit" set to 1 on access. The clock hand sweeps around. On first pass: clear the bit. On second pass: evict (bit is still 0 = not accessed since last sweep). This approximates LRU without the linked list overhead.

**Cost**: O(1) eviction, ~1 bit of overhead per entry. OS page caches use this extensively because they manage billions of pages and cannot afford linked list pointer overhead.

## 3. Real-World Architecture Examples

### 3.1 — Cloudflare CDN: Tiered Eviction at 50+ Tbps

Cloudflare serves tens of millions of requests per second from cache, equating to multiple terabytes per second globally. Their edge cache uses an LRU-variant eviction policy where content is evicted based on recency when memory pressure hits.

The critical insight from their engineering blog: **popularity varies by geography**. A viral video in Brazil may be cold in Japan. Each edge PoP (point of presence) runs independent cache instances with LRU, so eviction decisions are localized.

In 2022, Cloudflare launched **Cache Reserve** — a persistent, R2-backed tier specifically to handle items that would be evicted from edge LRU caches. The problem they were solving: LRU's recency bias causes perfectly valid, moderately popular content to be evicted from edge caches during traffic spikes from unrelated content. Cache Reserve acts as an L3 cache backed by cheap object storage, inserted between the edge LRU and the origin.

Architecture:
```
Client → Edge LRU Cache (RAM) → Cache Reserve (R2 Storage) → Origin
          hit rate: ~85%         hit rate: ~95%               (fallback)
```

Cloudflare engineering (2023) reports that Cache Reserve reduces origin egress costs by 60–80% for long-tail content that LRU would normally evict.

---

### 3.2 — Discord: Eviction Policy Selection for Message History Cache

Discord caches message history to serve their 150M+ daily active users. Their engineering team documented a specific challenge: message read patterns are highly non-uniform.

- **Hot servers** (large gaming communities): messages read by thousands of users seconds after posting — classic LRU behavior (recency wins)
- **Notification catchup**: user comes back after 8 hours and reads their last 50 messages — these keys are "cold" by LRU but will be accessed in bursts

Discord found that pure LRU evicted the "catchup" messages aggressively because they hadn't been read in hours. They moved toward **2Q (Two Queue)** variants that provide a probationary queue for recently evicted items, reducing re-fetch rates for notification catchup traffic by approximately 30%.

Discord also uses Redis with `allkeys-lru` for their presence cache (online status), where pure recency is the right signal: if you haven't been online in 5 minutes, your presence data can be evicted.

---

### 3.3 — Caffeine / Outbrain: W-TinyLFU in Production

Outbrain (content recommendation platform serving 300+ billion recommendations/month) published a detailed engineering post about migrating from Guava (LRU-based) to Caffeine (W-TinyLFU).

Their findings on production traffic:
- **15–25% higher hit rate** with the same cache size
- Scan pollution eliminated: their ML pipeline periodically scans all content metadata, which previously flushed Guava LRU caches. W-TinyLFU's window cache absorbs scans without polluting the main cache.
- CPU overhead: negligible — the Count-Min Sketch update is ~5ns per operation

Caffeine's own benchmarks on traces from Facebook's in-memory storage (RocksDB/Memcached workloads), Wikipedia CDN logs, and YouTube content delivery show:
- vs. Guava LRU: +20–40% hit rate
- vs. Redis LRU: +25% hit rate
- vs. ARC: +5–10% hit rate
- Memory overhead for frequency sketch: ~3 MB for 1 million cached keys

This makes W-TinyLFU the best general-purpose in-process cache algorithm available today.

---

### 3.4 — ZFS: ARC for Database-Scale Storage

Oracle/Sun's ZFS filesystem uses ARC as its primary buffer cache algorithm. ARC replaced a simpler LRU implementation specifically because database workloads mix sequential scans with random access:

- During a full-table scan (sequential), pure LRU would evict the hot index pages that were in use before the scan started
- ARC's T1/T2 separation means scan pages go into T1 (recently-seen-once) while critical index and working set pages are in T2 (frequently-seen)
- The adaptive parameter p shifts automatically as the workload changes throughout the day

**Real ZFS production numbers** (reported by storage engineers on FreeNAS/TrueNAS deployments):
- Database workloads: ARC achieves 15–25% higher hit rate vs. LRU on the same buffer sizes
- Sequential scan resistance: 100% — full table scans cannot pollute T2
- ARC size on typical NAS: 8–128 GB RAM dedicated to ARC, caching terabytes of spinning disk

## 5. Code / Implementation Perspective

### LRU Implementation from Scratch (Python)

```python
from collections import OrderedDict
from threading import Lock

class LRUCache:
    """
    O(1) get and put using OrderedDict (doubly linked list + hash map).
    Thread-safe via a single lock — use RWLock for read-heavy workloads.
    """

    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache: OrderedDict[str, any] = OrderedDict()
        self.lock = Lock()
        self.hits = 0
        self.misses = 0

    def get(self, key: str) -> any:
        with self.lock:
            if key not in self.cache:
                self.misses += 1
                return None
            self.cache.move_to_end(key)  # mark as most recently used
            self.hits += 1
            return self.cache[key]

    def put(self, key: str, value: any) -> None:
        with self.lock:
            if key in self.cache:
                self.cache.move_to_end(key)
            self.cache[key] = value
            if len(self.cache) > self.capacity:
                evicted_key, _ = self.cache.popitem(last=False)  # remove LRU end
                # log eviction for observability
                # metrics.increment("cache.evictions", tags={"key": evicted_key})

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total > 0 else 0.0


# Usage
cache = LRUCache(capacity=1000)
cache.put("user:123", {"name": "Alice", "plan": "premium"})
user = cache.get("user:123")   # hit, moves to MRU end
print(f"Hit rate: {cache.hit_rate:.1%}")
```

### LFU Implementation (Python)

```python
from collections import defaultdict, OrderedDict

class LFUCache:
    """
    O(1) get and put using frequency bucket map.
    Each bucket is an OrderedDict for LRU tie-breaking within same frequency.
    """

    def __init__(self, capacity: int):
        self.capacity = capacity
        self.min_freq = 0
        self.key_to_val: dict[str, any] = {}
        self.key_to_freq: dict[str, int] = {}
        self.freq_to_keys: dict[int, OrderedDict] = defaultdict(OrderedDict)

    def _update_freq(self, key: str) -> None:
        freq = self.key_to_freq[key]
        self.key_to_freq[key] = freq + 1
        del self.freq_to_keys[freq][key]
        if not self.freq_to_keys[freq] and freq == self.min_freq:
            self.min_freq += 1
        self.freq_to_keys[freq + 1][key] = None  # value doesn't matter here

    def get(self, key: str) -> any:
        if key not in self.key_to_val:
            return None
        self._update_freq(key)
        return self.key_to_val[key]

    def put(self, key: str, value: any) -> None:
        if self.capacity <= 0:
            return
        if key in self.key_to_val:
            self.key_to_val[key] = value
            self._update_freq(key)
            return
        if len(self.key_to_val) >= self.capacity:
            # evict least frequent, then least recent within that freq
            evict_key, _ = self.freq_to_keys[self.min_freq].popitem(last=False)
            del self.key_to_val[evict_key]
            del self.key_to_freq[evict_key]
        self.key_to_val[key] = value
        self.key_to_freq[key] = 1
        self.freq_to_keys[1][key] = None
        self.min_freq = 1
```

### Redis Configuration Patterns

```bash
# ─── Redis eviction policy configuration ───────────────────────

# Set maximum memory (required for eviction to trigger)
redis.conf:
  maxmemory 8gb
  maxmemory-policy allkeys-lru      # evict any key, LRU order
  maxmemory-samples 10              # sample 10 keys for LRU accuracy
                                    # (default 5, 10 costs ~5% more CPU)

# For workloads with clear hot/cold patterns (social feed, product catalog)
  maxmemory-policy allkeys-lfu
  lfu-log-factor 10                 # controls counter increment probability
                                    # lower = more sensitive to new traffic
  lfu-decay-time 1                  # halve counters every 1 minute

# For mixed workloads with both cached and non-cached keys
  maxmemory-policy volatile-lru     # only evict keys WITH an expiry set
  # Keys without TTL are NEVER evicted — use for permanent data

# Verify policy at runtime
redis-cli CONFIG GET maxmemory-policy
redis-cli CONFIG SET maxmemory-policy allkeys-lfu   # live change, no restart

# Monitor evictions
redis-cli INFO stats | grep evicted_keys
redis-cli INFO memory | grep used_memory_human

# Watch eviction rate in real-time
redis-cli --stat
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **FIFO** | Task queues, log buffers, ordered processing | Zero intelligence about access patterns; worst hit rate | Message queues (Kafka, SQS) — not caches |
| **LRU** | General caching, session data, time-windowed hot content | Fast to implement, good default; vulnerable to scan pollution | Redis (default), Nginx, Varnish, most CDNs |
| **LFU** | Stable hot keys (product catalog, user profiles), Zipfian workloads | Better hit rate than LRU on stable patterns; slow to react to new hotness | Redis 4.0+, some CDN implementations |
| **ARC** | Database buffer pools, mixed sequential + random workloads | Excellent hit rate; IBM-patented, complex to implement | ZFS, NetApp ONTAP, some database buffer caches |
| **W-TinyLFU** | In-process caches, JVM/Go services, highest hit rate required | Best hit rate on Zipfian workloads; more complex implementation | Caffeine (Java), Ristretto (Go), Apache Ignite |
| **S3-FIFO** | High-concurrency systems, multi-threaded caches, throughput > hit rate | 6x throughput vs. LRU due to lock-free FIFO; newer, less battle-tested | Google (internal), VMware, Redpanda |
| **CLOCK / Clock-Pro** | OS page caches, large flat caches where linked list overhead matters | Good LRU approximation with minimal memory; less accurate than LRU | Linux page cache, PostgreSQL buffer pool, Windows |
| **2Q / SLRU** | Admission control for external caches, avoiding one-time scans | Good scan resistance; simpler than ARC | Many CDNs, Redis Cluster internally |
| **TTL-only (no eviction)** | Small caches where you control size via TTL, not capacity | No intelligence at all — items expire but never get evicted by pressure | Simple API response caches with short TTLs |

**My recommendation:**

- **Default for most teams**: Redis with `allkeys-lru` and `maxmemory-samples=10`. It is battle-tested, observable, and handles 90% of use cases.
- **If you have JVM/Go in-process caches**: Use Caffeine (Java) or Ristretto (Go) with W-TinyLFU. The hit rate improvement is real, the implementation cost is zero (it's a library), and the memory overhead is negligible.
- **If you need maximum Redis hit rate**: Switch to `allkeys-lfu` only after you have measured that your workload is Zipfian and that popular items are being evicted by LRU. Don't switch speculatively.
- **If you need high-concurrency cache throughput** (multi-threaded cache, >5M ops/sec): Evaluate S3-FIFO. The lock-free design matters at extreme concurrency.
- **Avoid ARC in new systems**: The IBM patent creates legal risk and the hit rate advantage over W-TinyLFU is marginal (5–10%). Use W-TinyLFU instead.

## 8. Trade-offs (Be Opinionated)

### Benefits of Advanced Eviction Policies (LFU, W-TinyLFU, ARC)

- **Higher hit rates**: 15–40% improvement over FIFO/simple-LRU on real workloads means proportionally fewer database round trips
- **Scan resistance**: Sequential scans cannot flush your hot working set — critical for any system running both OLTP and analytics
- **Automatic adaptation**: ARC and W-TinyLFU adapt to changing access patterns without manual tuning
- **Database protection**: Every 1% improvement in cache hit rate at 1M req/sec = 10,000 fewer DB queries/sec — the difference between a healthy database and one that's on fire

### Costs of Advanced Eviction Policies

- **Implementation complexity**: W-TinyLFU requires a Count-Min Sketch, SLRU, and a window cache — more moving parts, more failure modes
- **Debugging difficulty**: "Why was this key evicted?" is much harder to answer for LFU (need to know the frequency counter state at eviction time) vs. LRU (simply the oldest key)
- **Memory overhead**: LFU counters (Redis uses ~8 bytes per key for LFU state), Count-Min Sketch (~3 MB for 1M keys) — not free but usually acceptable
- **Counter decay tuning**: LFU without decay gets worse over time (historical frequency dominates); tuning `lfu-decay-time` in Redis requires load testing
- **Latency spikes under eviction pressure**: Under heavy eviction load, even approximate LRU requires sampling N keys and comparing timestamps — at extreme rates this can add 1–5 µs to write latency

### The Core Tension

**Recency vs. Frequency**: No single policy is optimal for all workloads.

- Trending content (news, social media, sports scores): recency wins → LRU is better because last access is the best predictor of next access
- Stable hot keys (product catalog, user settings, dictionary data): frequency wins → LFU/W-TinyLFU are better
- Mixed workloads: ARC or W-TinyLFU adapt, but require more overhead

**My recommendation**: Start with LRU (Redis `allkeys-lru`). Instrument hit rates and eviction rates with Prometheus from day one. Upgrade to LFU or W-TinyLFU only when you can *measure* that LRU is evicting popular items. The policy decision should be data-driven, not theoretical.

Never tolerate an uninstrumented cache in production. You are flying blind.

## 9. Failure Modes — What Goes Wrong

### Failure Mode 1: Scan Pollution / Cache Thrash

**Trigger**: A background job, analytics query, or migration script reads a large number of keys sequentially in a short time window (e.g., iterating 50 million user records for a weekly report).

**Symptoms**:
- Sudden drop in cache hit rate from 90% to 20–40% within minutes
- Spike in database QPS immediately following the scan
- Redis `evicted_keys` counter shows a large spike
- P99 latency increases 3–10x as uncached requests hit the database

**Detection**:
- Alert on: `cache hit rate < 70%` for more than 60 seconds
- Alert on: `redis evicted_keys rate > 5% of total keyspace per minute`
- Grafana dashboard: plot cache miss rate alongside evicted_keys rate — they should correlate during scan events

**Recovery**:
- Immediate: Temporarily increase `maxmemory` if headroom exists in the host
- Short-term: Migrate to W-TinyLFU (Caffeine) for in-process caches or switch Redis to `allkeys-lfu`
- Long-term: Run scan-heavy jobs during off-peak hours; use a separate Redis instance with a different eviction policy for analytics keys; implement 2Q or SLRU to create a protected zone

**Real Example**: The Outbrain engineering blog described exactly this pattern — their ML feature computation scanned all content metadata daily, flushing their Guava LRU cache and causing a 20% spike in database load for 30–45 minutes post-scan. Migrating to Caffeine (W-TinyLFU) eliminated this completely.

---

### Failure Mode 2: Hot Key Eviction (LRU Blindness)

**Trigger**: Under `allkeys-lru`, a sustained traffic spike from a new but infrequently-touched key set (e.g., a viral marketing email directs 500K users to a single landing page) causes Redis to evict hot user profile keys (which are accessed frequently but not *most recently*).

**Symptoms**:
- Specific key namespace shows dramatically higher miss rate
- User-facing latency for authenticated requests increases (profile cache misses)
- Database shows increased load on user profile queries specifically

**Detection**:
- Per-key-namespace hit rate monitoring: `redis-cli --hotkeys` (requires `maxmemory-policy allkeys-lfu`)
- Application-level hit rate tracking per cache domain (session, profile, catalog)
- Alert: "Profile cache miss rate > 15% for 5 minutes"

**Recovery**:
- Switch to `allkeys-lfu`: `CONFIG SET maxmemory-policy allkeys-lfu`
- Add an L1 in-process Caffeine cache for the most critical hot keys (user profiles) with a short TTL (30–60 seconds) — this survives Redis eviction storms
- Use `volatile-lru` and explicitly mark business-critical keys with no TTL (`PERSIST key`) so they are never evicted

**Real Example**: An incident postmortem shared by a backend engineer at a fintech company described losing user session data under `allkeys-lru` during a viral growth event. Traffic from a press mention hit new keys hard, pushing out session keys that were accessed frequently but slightly less recently than the viral content keys.

---

### Failure Mode 3: LFU Frequency Lock-In / Stale Hot Keys

**Trigger**: Using `allkeys-lfu` without proper decay configuration (`lfu-decay-time` too high), or in a system where popularity patterns change dramatically (e.g., seasonal products, discontinued items).

**Symptoms**:
- Old, no-longer-popular keys remain in cache indefinitely
- New viral or trending content has poor hit rates despite high recent access
- Cache effective hit rate declines over weeks/months even without memory changes
- `redis-cli --hotkeys` shows keys you *know* are no longer popular

**Detection**:
- Compare LFU counter values against actual recent access rate (hard to do in Redis directly)
- Monitor: "cache miss rate for new content types trending upward over 2-week window"
- Use `DEBUG OBJECT key` in Redis to inspect the `lru_seconds_idle` and `freq` fields

**Recovery**:
- Tune `lfu-decay-time` to a lower value (e.g., 1 minute instead of default) to increase recency sensitivity
- Consider switching back to `allkeys-lru` if popularity shifts are rapid and unpredictable
- Add TTL to all cached keys as a backstop — even with LFU, a max TTL of 1 hour ensures stale frequency counters eventually expire

**Real Example**: A Redis Labs case study describes an e-commerce platform that enabled `allkeys-lfu` during peak season. After the season ended, the top LFU keys were holiday product pages that no longer generated traffic, while spring product pages were being evicted. The fix was setting `lfu-decay-time 1` and adding 6-hour TTLs to product cache keys.

---

### Failure Mode 4: Memory Fragmentation Defeating Eviction

**Trigger**: Redis attempts to evict keys to stay under `maxmemory`, but memory fragmentation means the freed memory is not returned to the OS or made available for new allocations.

**Symptoms**:
- `INFO memory`: `mem_allocator_frag_ratio > 1.5` (severe fragmentation)
- `used_memory` is below `maxmemory` but Redis still rejects writes with OOM error
- `evicted_keys` counter increases but `used_memory_rss` (RSS) stays high

**Detection**:
- Alert: `mem_allocator_frag_ratio > 1.3` for more than 10 minutes
- Alert: OOM errors in Redis logs despite `used_memory < maxmemory`

**Recovery**:
- Enable active defragmentation (Redis 4.0+): `CONFIG SET activedefrag yes`
- Set `active-defrag-threshold-lower 10` (start defrag at 10% fragmentation)
- Restart Redis with `slaveof no one` if fragmentation is extreme (last resort)

## 10. When To Use vs. When To Avoid

### Use Eviction Policies When

**✅ Your cache is bounded by memory**: You have a fixed RAM budget and need intelligent item management. Every production cache should have eviction configured — running without `maxmemory` in Redis is a recipe for OOM crashes.

**✅ Access patterns follow Zipf / power law**: If 20% of your keys receive 80% of requests (typical for user-facing applications), LFU or W-TinyLFU will dramatically outperform naive FIFO. Measure your key distribution — if it's Zipfian, invest in a smarter policy.

**✅ Your database cannot absorb the load from cache misses**: If every cache miss translates to a 5–50ms database query, and you have 10,000 cache misses/second due to poor eviction policy, that is 50,000–500,000 ms of unnecessary database load per second. The ROI on eviction tuning is enormous.

**✅ You have background scan or batch processing jobs**: Any system that periodically scans large datasets (ML pipelines, analytics, data migrations) must use scan-resistant eviction (W-TinyLFU, ARC, or at minimum 2Q) or run scans against a separate cache instance.

### Do NOT Use / Avoid When

**❌ You have a tiny working set that fits in cache**: If your entire dataset is 2 GB and your cache is 8 GB, you will never hit eviction. Spending engineering time on eviction policy tuning here is pure waste. Focus on correctness (TTL, invalidation) instead.

**❌ Eviction correctness matters more than eviction intelligence**: If evicting the wrong key causes data inconsistency (not just a cache miss but an incorrect cache hit from a stale item), eviction policy is not your problem — cache invalidation strategy is. Fix invalidation first.

**❌ You are debugging a correctness bug**: Do not change eviction policies while investigating a data corruption or stale-read bug. Eviction changes hit rate; they do not cause incorrect values. Separate the concerns.

**❌ You expect to use `volatile-lru`/`volatile-lfu` but don't set TTLs consistently**: If you use `volatile-lru` but only 30% of your keys have TTLs, 70% of your keys are permanently unaffected by memory pressure. This is a silent footgun — Redis will refuse to evict when memory is full because there are not enough eligible keys.

### The #1 Mistake Engineers Make

**⚠️ Running Redis without `maxmemory` set.**

Without `maxmemory`, Redis will grow until it exhausts all available system memory. The OOM killer will then terminate the Redis process (or worse, a different critical process). This takes down your entire caching layer, and the resulting cache stampede will likely take down your database too.

Always set `maxmemory`. Always set `maxmemory-policy`. These are not optional configurations. The default policy `noeviction` (which simply returns errors when memory is full) is appropriate only if you treat Redis as a primary data store, not a cache.

### Junior Answer — "Design an LRU Cache"

```
"I'd use a hash map pointing to nodes in a doubly linked list.
 The head is MRU, the tail is LRU. On get: move the node to head.
 On put: add to head, remove tail if over capacity.
 Both operations are O(1) time."
```
This passes the coding round. It does not demonstrate system design depth.

---

### Senior Answer — "Which eviction policy for a product catalog cache?"

```
"I'd start with allkeys-lru in Redis as the default — it's well
 understood, observable, and handles most cases. Product catalogs
 have Zipfian access patterns (top 1% of SKUs get 60%+ of traffic),
 so LFU would theoretically be better. I'd add monitoring from day
 one: keyspace_hits/keyspace_misses ratio in Prometheus, and alert
 if hit rate drops below 80%.

 If I see popular items being evicted under load, I'd switch to
 allkeys-lfu with lfu-decay-time=1 and monitor the improvement.
 I'd also add an in-process Caffeine cache (W-TinyLFU) in front of
 Redis for the top 1,000 SKUs — that handles the ultra-hot keys
 regardless of what Redis evicts."
```

---

### Staff Answer — "Scan pollution is killing our cache performance"

```
"This is a classic scan pollution problem. Here's the diagnosis
 and fix:

 Root cause: LRU treats scan pages and hot pages equally — the
 scan replaces your working set in O(scan_size / cache_size) time.
 At 50M records × 1KB each = 50 GB scan through an 8 GB cache,
 you get ~6 complete cache flushes.

 Fixes in priority order:
 1. Immediate: run the batch job against a read replica, not the
    primary. Use a separate Redis instance with a larger maxmemory
    and allkeys-lru for the batch job.

 2. Short-term: migrate the application cache to Caffeine
    (W-TinyLFU). The window cache absorbs scan traffic without
    polluting the main SLRU. This eliminates the problem entirely.

 3. Long-term: if Redis is required, consider 2Q or SLRU-based
    admission: new keys start in a probationary queue and must be
    accessed twice to enter the protected queue. This is effectively
    what W-TinyLFU does.

 I'd also add a circuit breaker: if the batch job detects it's
 causing cache evictions faster than 1,000 keys/sec, it backs
 off and sleeps 100ms between batches.

 Key metrics to prove the fix worked: cache miss rate timeline
 correlated with batch job execution window — before and after."
```
