## 1. What Is It? (Theory)

### The Core Problem

Every system with a cache faces the same existential question: **when the application writes new data, where does it go first — the cache, the database, or both simultaneously?**

This is not a read problem. It is a write problem. And the answer you choose determines your system's consistency, durability, latency, and failure blast radius. Getting it wrong means either a cache that lies to your users (serving stale data) or a database that is crushed under write load you could have absorbed.

### The Notebook Analogy

Imagine a doctor who takes patient notes on a desk notepad (cache) and needs those notes permanently filed in a cabinet (database).

- **Write-Through:** The doctor writes the note and immediately files a copy in the cabinet before moving on. Every note is in both places. If the notepad burns, nothing is lost. But every write takes longer because you must wait for the filing.
- **Write-Back (Write-Behind):** The doctor writes on the notepad immediately and continues seeing patients. An assistant periodically takes the notes and files them. Faster consultations, but if there is a fire before the assistant files, you lose the recent notes.
- **Write-Around:** The doctor skips the notepad entirely and files everything directly in the cabinet. The notepad is only used when a nurse reads out a file from the cabinet later. The notepad never gets full of one-time notes, but re-reading recent data always requires going back to the cabinet.

### Why These Patterns Exist

Before the mid-2000s, most web applications wrote directly to a relational database. As traffic scaled past 10,000 requests per second, databases became bottlenecks — not because of reads (which caches like Memcached had already solved with cache-aside patterns) but because of writes:

- **Write contention**: Multiple transactions locking the same rows
- **Replication lag**: Writes propagating slowly to read replicas
- **Disk I/O saturation**: Relational databases on spinning disks maxing out at ~3,000–5,000 IOPS

Write caching strategies emerged as a solution. Write-through came first (borrowed from CPU L1/L2 cache design in the 1980s). Write-back (called write-behind in distributed systems) came later, prioritizing throughput. Write-around emerged as a specialization for write-heavy workloads where the written data is rarely re-read immediately.

## 2. How It Actually Works (Deep Mechanics)

### Write-Through

**Step-by-step flow:**

```
Client                  Application              Cache (Redis)            Database (Postgres)
  |                          |                        |                          |
  |--- POST /update -------->|                        |                          |
  |                          |--- WRITE to cache ---->|                          |
  |                          |   (synchronous)        |--- WRITE to DB --------->|
  |                          |                        |   (synchronous)          |
  |                          |<--- ACK from DB -------|<--- ACK from cache ------|
  |<--- 200 OK --------------|                        |                          |
  |                          |                        |                          |
  |--- GET /data ----------->|                        |                          |
  |                          |--- READ cache -------->|                          |
  |                          |<--- HIT (fresh data) --|                          |
  |<--- data (from cache) ---|                        |                          |
```

**Key property:** The write is NOT acknowledged to the client until BOTH the cache and database have confirmed the write. This is synchronous in the critical path.

**Real numbers:**
- Redis SET latency (local network): ~0.1–0.5 ms
- Postgres INSERT latency (local network, indexed table): ~1–5 ms
- Total write-through overhead vs. DB-only: +0.1–0.5 ms per write
- Write-through read hit rate: typically 95–99% (cache always warm)

### Write-Back (Write-Behind)

**Step-by-step flow:**

```
Client                  Application              Cache (Redis)            Database (Postgres)
  |                          |                        |                          |
  |--- POST /update -------->|                        |                          |
  |                          |--- WRITE to cache ---->|                          |
  |                          |   (synchronous)        |                          |
  |<--- 200 OK (immediate) --|<--- ACK from cache ----|                          |
  |                          |                        |                          |
  |                          |          [background flush every N ms / N writes] |
  |                          |                        |--- BATCH WRITE to DB --->|
  |                          |                        |<--- ACK from DB ---------|
  |                          |                        |                          |
```

**Key property:** The write is acknowledged to the client as soon as the cache confirms. The database write happens asynchronously in the background — in batches of N writes or every T milliseconds.

**Real numbers:**
- Write-back write latency: ~0.1–0.5 ms (cache only)
- Write-back throughput: 5–10x higher than write-through for burst traffic
- Flush interval: typically 100 ms–5 s depending on durability tolerance
- Risk window: all writes in the flush buffer are at risk if cache crashes before flush

### Write-Around

**Step-by-step flow:**

```
Client                  Application              Cache (Redis)            Database (Postgres)
  |                          |                        |                          |
  |--- POST /write --------->|                        |                          |
  |                          |--- WRITE SKIPS cache --|-->  DIRECT to DB ------->|
  |<--- 200 OK --------------|<--- ACK from DB -------|<-------------------------|
  |                          |                        |   (cache NOT updated)    |
  |                          |                        |                          |
  |--- GET /data ----------->|                        |                          |
  |                          |--- READ cache -------->|                          |
  |                          |<--- MISS --------------|                          |
  |                          |--- READ from DB ---------------------------------------->|
  |                          |--- POPULATE cache ---->|                          |
  |<--- data (populated) ----|                        |                          |
```

**Key property:** Writes go straight to the database, bypassing the cache entirely. The cache is only populated on a subsequent read miss. This is identical to cache-aside for the write path.

**Real numbers:**
- First read after write: full DB latency (~1–10 ms)
- Subsequent reads (after first miss populates cache): ~0.1–0.5 ms
- Cache memory pressure: significantly lower for write-heavy workloads
- Optimal for: data with a write:read ratio > 10:1 where most writes are never re-read

### Misconceptions

**❌ Misconception: Write-through guarantees zero data loss**
**✅ Reality:** Write-through guarantees that cache and DB are consistent at the time of the write. But it does NOT protect against race conditions between concurrent writers, replication lag, or application-layer failures that occur between the cache write and DB write in a non-transactional implementation.

**❌ Misconception: Write-back (write-behind) is dangerous and should be avoided**
**✅ Reality:** Write-back is used in production by Netflix (EVCache), Discord (message counters), and every modern SSD controller. The risk is real but manageable with persistent write buffers (Redis AOF), replication, and careful flush tuning. The risk is proportional to your flush interval — 100 ms flush interval means at most 100 ms of writes are at risk, not your entire dataset.

**❌ Misconception: Write-around is just "don't cache writes"**
**✅ Reality:** Write-around is a deliberate strategy that prevents cache pollution. Systems like Elasticsearch indexing pipelines and analytics databases explicitly choose write-around because the freshly-written data is consumed by a batch reader hours later — caching it would waste RAM and cause evictions of genuinely hot read data.

**❌ Misconception: You must pick one strategy for your entire system**
**✅ Reality:** Production systems routinely mix strategies. Stripe uses write-through for payment state (consistency critical) and write-around for audit log writes (never re-read immediately). Netflix uses write-back for view count updates and write-through for user preference data.

## 3. Real-World Architecture Examples

### Meta — TAO Cache Consistency (Cache-with-Write-Through + CDC)

Meta's social graph runs on TAO (The Associations and Objects), a distributed cache layer sitting in front of MySQL. As documented in their 2022 engineering blog post ["Cache made consistent"](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/), Meta faced a fundamental challenge: write-through alone at their scale (billions of objects, thousands of cache servers) made it impossible to guarantee that all cache replicas stayed synchronized with the database.

Their solution: **write-through + CDC (Change Data Capture) invalidation**. When a write occurs:
1. Application writes directly to MySQL (write-around the cache, in fact)
2. A CDC pipeline reads the MySQL binlog and publishes invalidation events
3. TAO caches receive those events and evict the stale keys
4. The next read repopulates from MySQL

The result: Meta improved TAO cache consistency from 99.9999% (six nines) to **99.99999999% (ten nines)** — a 10,000x improvement in consistency. This illustrates that write-around + event-driven invalidation can outperform naive write-through at hyperscale.

**Key insight:** At Meta's scale (~1 billion daily active users), even write-through creates consistency windows because cache replication across 100+ data centers is not atomic.

### Netflix — EVCache Write-Back for Scale Events

Netflix runs EVCache, a distributed Memcached-based caching layer that handles tens of millions of requests per second per region. For their streaming infrastructure:

- **User preferences (language, autoplay settings):** Write-through — must be durable, read on every stream start
- **View count / progress tracking:** Write-back with a 5-second flush interval — high write frequency, small durability window acceptable
- **Content metadata:** Write-around — the CMS writes directly to Cassandra; EVCache populates on first read

During the Tyson vs. Paul fight in November 2024 (65 million concurrent streams), Netflix used write-through caching of video chunks via EVCache to achieve read-write separation and sustain 200 Gbps+ throughput — demonstrating that write-through at the CDN layer can protect the origin even under extreme burst load.

**Key insight:** Netflix does not use a single write strategy. They categorize data by durability requirement and access pattern and apply the appropriate strategy per data type.

### Stripe — Write-Through for Financial Consistency

Stripe processes hundreds of billions of dollars annually. Their caching architecture for payment state is deliberately conservative: **write-through with strong consistency guarantees**.

Every payment state transition is written synchronously to both the cache and the database (backed by a Spanner-like distributed SQL system). The additional ~0.5 ms write latency is a non-negotiable cost for a system where a cache miss that returns stale "payment pending" state when the real state is "payment failed" could result in double-charges or fraudulent transactions.

Stripe's write-through implementation also includes:
- **Optimistic locking** at the DB layer to prevent concurrent write races
- **Cache key versioning** — each write increments a version counter; readers reject cached values with stale versions
- **Circuit breakers** — if the DB write fails, the cache write is rolled back (the inverse of eventual consistency)

**Key insight:** For financial data, the ~0.5 ms write-through overhead is completely worth it. The cost of a consistency bug in payments is orders of magnitude higher than the infrastructure cost savings from write-back.

### Cloudflare — Write-Around at the CDN Edge (Cache Reserve)

Cloudflare's CDN uses a write-around pattern for its Cache Reserve feature. When a CDN edge node receives a write (an origin server publishing new content), the content is written directly to R2 object storage (Cloudflare's persistent tier). Edge nodes only populate their local caches when they receive read requests.

This is write-around by design: content written to origin is NOT proactively pushed to 300+ edge PoPs. Instead, each PoP lazily populates on the first cache miss in its region. Cloudflare's tiered cache architecture (lower-tier PoPs ask upper-tier PoPs before asking origin) means that the write-around miss cost is absorbed at the upper-tier, not at the origin — reducing origin load by 70%+ for large content libraries.

**Key insight:** Write-around is the natural pattern for CDN architectures where "write" means "origin publishes new content" and the question is when/whether to push it to the edge. Write-through (proactive edge push) is reserved for critical low-latency content like API responses at Cloudflare Workers.

### Scale Evolution

#### 1K Users/day (~10 req/s)

At this scale, you probably do not need a write caching strategy at all. A single Postgres instance on a 4-core VM handles ~5,000 writes/second comfortably. Cache-aside for reads is sufficient.

**Recommended:** No write caching. Direct DB writes. Cache-aside reads.

#### 100K Users/day (~1,000 req/s)

Write contention starts appearing on hot rows (user profile updates, inventory counts, leaderboard scores). A single Postgres primary begins hitting CPU limits at peak.

**Recommended:** Introduce write-through for frequently-read data (user sessions, preferences). Use Redis as the cache. Write overhead of ~0.5 ms/write is acceptable. Begin separating hot-key writes from cold writes.

Expected improvement: 40–60% reduction in DB write load as cache absorbs repeat writes to the same keys.

#### 1M Users/day (~10,000 req/s)

Database write IOPS becomes a bottleneck. Read replicas help reads but not writes. Connection pool exhaustion under write bursts.

**Recommended:** Migrate high-frequency low-durability writes (counters, soft state, ephemeral data) to write-back with 500 ms–1 s flush interval. Keep financial/critical state on write-through. Introduce write-around for analytics, logs, and audit events that are write-once-read-never in real time.

Expected improvement: Write-back reduces DB write IOPS by 70–90% for counter-type workloads (e.g., 10,000 counter increments/second becomes ~20 batch writes/second).

#### 100M Users/day (~1M req/s)

Single-region cache becomes a bottleneck. Multi-region replication creates consistency windows. CDC pipelines become required for cross-region cache invalidation.

**Recommended:** Adopt Meta's write-around + CDC model for social/relational data. Use write-back with persistent queues (Redis Streams + durable flush workers) for high-throughput counters. Implement cache key versioning to handle concurrent writes. Separate write strategies by data domain — do not use one strategy for all data.

Expected infrastructure: 3+ Redis clusters (write buffer, hot read, warm read), CDC pipeline (Debezium + Kafka), cache invalidation service with at-least-once delivery guarantees.

## 5. Code / Implementation Perspective

### Python Sketch — All Three Strategies

```python
import time
import threading
from collections import defaultdict
from typing import Any, Optional

import redis
import psycopg2

# --- shared infrastructure ---
cache = redis.Redis(host="localhost", port=6379, decode_responses=True)
db = psycopg2.connect("dbname=app user=app password=app host=localhost")

TTL_SECONDS = 300  # 5-minute TTL on all cached keys


# ─────────────────────────────────────────────
# STRATEGY 1: WRITE-THROUGH
# ─────────────────────────────────────────────
def write_through(key: str, value: str) -> None:
    """Write to cache AND database synchronously. Return only after both succeed."""
    # Step 1: write to cache
    cache.set(key, value, ex=TTL_SECONDS)

    # Step 2: write to database (synchronous — caller waits for both)
    with db.cursor() as cur:
        cur.execute(
            "INSERT INTO kv_store (key, value) VALUES (%s, %s) "
            "ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value",
            (key, value),
        )
    db.commit()
    # ACK returned to caller only after BOTH writes succeed


# ─────────────────────────────────────────────
# STRATEGY 2: WRITE-BACK (WRITE-BEHIND)
# ─────────────────────────────────────────────
dirty_keys: dict[str, str] = {}  # in-memory dirty buffer (use Redis HASH in prod)
dirty_lock = threading.Lock()
FLUSH_INTERVAL_MS = 500  # flush every 500 ms


def write_back(key: str, value: str) -> None:
    """Write to cache immediately. Database flush happens asynchronously."""
    # Step 1: write to cache immediately
    cache.set(key, value, ex=TTL_SECONDS)

    # Step 2: mark as dirty — do NOT write to DB yet
    with dirty_lock:
        dirty_keys[key] = value
    # ACK returned to caller here — DB write happens later


def _flush_dirty_to_db() -> None:
    """Background thread: flush dirty keys to DB every FLUSH_INTERVAL_MS."""
    while True:
        time.sleep(FLUSH_INTERVAL_MS / 1000.0)
        with dirty_lock:
            if not dirty_keys:
                continue
            batch = dict(dirty_keys)
            dirty_keys.clear()

        # batch upsert to DB
        with db.cursor() as cur:
            for key, value in batch.items():
                cur.execute(
                    "INSERT INTO kv_store (key, value) VALUES (%s, %s) "
                    "ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value",
                    (key, value),
                )
        db.commit()
        print(f"[flush] wrote {len(batch)} dirty keys to DB")


# start flush thread (in production: use a dedicated worker process, not a thread)
flush_thread = threading.Thread(target=_flush_dirty_to_db, daemon=True)
flush_thread.start()


# ─────────────────────────────────────────────
# STRATEGY 3: WRITE-AROUND
# ─────────────────────────────────────────────
def write_around(key: str, value: str) -> None:
    """Write directly to DB. Cache is NOT updated. Populated lazily on next read."""
    with db.cursor() as cur:
        cur.execute(
            "INSERT INTO kv_store (key, value) VALUES (%s, %s) "
            "ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value",
            (key, value),
        )
    db.commit()
    # cache NOT updated — next read will be a miss and will populate from DB


def read_with_lazy_populate(key: str) -> Optional[str]:
    """Read: check cache first, fall back to DB and populate on miss."""
    val = cache.get(key)
    if val is not None:
        return val  # cache hit

    # cache miss: read from DB and populate cache
    with db.cursor() as cur:
        cur.execute("SELECT value FROM kv_store WHERE key = %s", (key,))
        row = cur.fetchone()

    if row:
        cache.set(key, row[0], ex=TTL_SECONDS)  # lazy populate
        return row[0]
    return None
```

### Redis Commands Reference

```bash
# Write-through: set in Redis then call your ORM/DB
REDIS> SET user:1001:profile '{"name":"Alice","tier":"premium"}' EX 300

# Write-back: write to cache, mark dirty in a sorted set (score = epoch)
REDIS> SET user:1001:counter 42 EX 300
REDIS> ZADD dirty_keys 1718000000 "user:1001:counter"

# Flush worker: scan dirty keys with scores older than N seconds
REDIS> ZRANGEBYSCORE dirty_keys 0 1718000500  # get all dirty keys older than 500s
REDIS> ZREM dirty_keys "user:1001:counter"    # remove after successful DB write

# Write-around: no Redis commands on the write path
# Read path with lazy populate:
REDIS> GET user:1001:counter                  # returns nil on first read
# (app reads from DB, then:)
REDIS> SET user:1001:counter 42 EX 300        # populate after DB read
```

### Language-Agnostic Pattern Summary

```
WRITE-THROUGH:
  function write(key, value):
    cache.set(key, value)
    database.upsert(key, value)   // blocks until both succeed
    return ACK

WRITE-BACK:
  function write(key, value):
    cache.set(key, value)
    dirty_queue.enqueue(key, value)
    return ACK                    // returns immediately
  
  background flush_worker():
    while true:
      sleep(flush_interval)
      batch = dirty_queue.drain()
      database.batch_upsert(batch)

WRITE-AROUND:
  function write(key, value):
    database.upsert(key, value)   // blocks until DB write succeeds
    return ACK                    // cache NOT updated

  function read(key):
    if cache.exists(key):
      return cache.get(key)       // cache hit
    value = database.get(key)
    cache.set(key, value)         // lazy populate
    return value
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Write-Through** | Financial data, user preferences, any data where stale cache = user-visible bug | +durability, +consistency / -write latency (~0.5 ms overhead) | Stripe (payment state), Netflix (user prefs), most e-commerce |
| **Write-Back (Write-Behind)** | High-frequency low-durability writes: counters, soft state, leaderboards, gaming scores | +throughput (5–10x higher write ops/s) / -durability (flush window data loss risk) | Discord (message counters), gaming platforms, IoT telemetry |
| **Write-Around** | Write-heavy analytics, logs, audit trails, time-series data rarely re-read immediately | +no cache pollution / -first-read latency (always a miss after write) | Elasticsearch ingestion pipelines, Cloudflare CDN, data lakes |
| **Cache-Aside (Lazy Loading)** | Read-heavy, write-infrequent, any data where eventual consistency is fine | +simple implementation / -thundering herd on cold starts, -stale reads until TTL | Most CRUD apps at 100K–10M users scale, the "default" choice |
| **Read-Through** | Same as cache-aside but cache manages DB reads | +cache handles all DB logic / -harder to debug cache misses | Typically combined with write-through in frameworks like Spring Cache |
| **Event-Driven Invalidation + Write-Around** | Social graphs, complex relational data, multi-region deployments | +strongest consistency at scale / -operational complexity (CDC pipeline, Kafka) | Meta (TAO), large social platforms |

### Opinionated Recommendation

**Default to write-through.** Unless you have measured evidence that the ~0.5 ms write-through overhead is a bottleneck in your p99 latency budget, write-through's simplicity and consistency guarantee is worth the cost. The failure mode of write-back (data loss on cache crash) requires careful engineering to mitigate. Most teams underestimate the operational complexity of a correct write-back implementation.

**Use write-back only when you have:**
1. Measured that DB write IOPS is a real bottleneck (not hypothetical)
2. A defined durability SLA that the flush interval satisfies (e.g., "we can tolerate losing 1 second of counter updates")
3. Persistent write buffers (Redis AOF/RDB, not just in-memory dirty queues)
4. A recovery playbook for "cache crashed with 5 seconds of unflushed writes"

**Use write-around when:**
Your write:read ratio for a data category is > 5:1 in the short term (minutes to hours). If you know that freshly-written data will not be re-read within the TTL window, caching it wastes memory and evicts genuinely hot data.

## 8. Trade-offs (Be Opinionated)

### Write-Through

**Benefits:**
- Cache is always consistent with the database — no stale reads after writes
- Reads after writes always hit the cache (high cache hit rate)
- Simple mental model: if it is in the cache, it is correct
- No durability risk — database is always authoritative

**Costs:**
- Every write is slower by the cache write latency (~0.1–0.5 ms in-region, ~5–20 ms cross-region)
- Under write-heavy burst traffic, cache can become the bottleneck instead of the DB
- Hot keys can create write contention on the cache tier itself
- Not suitable when writes vastly outnumber reads (cache is wasted for data that will never be read)

**Core tension:** You are paying a latency tax on every write to buy consistency on every read. This is the right trade for most user-facing data. It is the wrong trade for high-frequency background writes.

**My recommendation:** Write-through should be your **default starting strategy**. You should have to justify deviating from it with production metrics, not theoretical throughput arguments.

---

### Write-Back (Write-Behind)

**Benefits:**
- Write latency drops to cache-only speed (~0.1–0.5 ms vs. ~2–10 ms for DB write)
- Write throughput can be 5–10x higher for burst workloads
- Natural batching — multiple writes to the same key within the flush window are collapsed into one DB write (e.g., 1,000 counter increments become 1 DB update)
- Protects the database from write spikes

**Costs:**
- Data loss risk: any writes in the dirty buffer that have not been flushed are lost on cache failure
- Operational complexity: requires persistent dirty queues, flush workers, at-least-once delivery guarantees
- Debugging is harder: at any moment, cache and DB are potentially out of sync
- Recovery is complex: if cache crashes, you must reconstruct state from the last DB flush + any surviving WAL

**Core tension:** You are betting durability against throughput. This bet can pay off enormously for the right workload (gaming leaderboards, social counters) and catastrophically for the wrong one (financial balances, inventory counts).

**My recommendation:** Write-back is a **specialist tool**. Use it when you have measured that DB write throughput is the actual bottleneck, and only after implementing persistent write buffers and a tested recovery runbook.

---

### Write-Around

**Benefits:**
- Cache is never polluted with write-only or write-heavy data
- Reduces cache memory pressure — only data that is actually read gets cached
- Full DB write throughput — no cache overhead on the write path
- Simple: writes behave exactly like a non-cached system

**Costs:**
- First read after any write is always a cache miss — full DB latency on that read
- Systems with write-then-immediately-read patterns suffer repeated misses
- No consistency benefit between writes and reads — stale data can persist until the first read

**Core tension:** You are trading cache efficiency (no pollution) against first-read latency. The pattern only wins when writes and subsequent reads are temporally separated.

**My recommendation:** Write-around is **underused and underrated** for analytics and logging pipelines. Stop caching your log writes and metric writes. They will never be read immediately. Use write-around to keep your cache full of actually-hot data.

---

## 9. Failure Modes — What Goes Wrong

### Failure Mode 1: Write-Back Cache Crash with Unflushed Dirty Keys

**Trigger:** Redis instance or cluster fails (OOM kill, hardware failure, network partition) while dirty write buffer contains unflushed keys. This is most likely during traffic spikes when write volume is highest and cache memory pressure is highest — the exact worst time to lose data.

**Symptoms:**
- Application logs show "cache write succeeded" but DB shows stale values after recovery
- User-reported: "I changed my setting and it reverted"
- DB counter values are days behind the cached values after failover

**Detection:**
- Monitor the size of your dirty queue (ZCARD dirty_keys) — alert if it exceeds a threshold (e.g., > 10,000 entries) suggesting flush worker backlog
- Compare cache counter values vs. DB values for canary keys on a 30-second cron
- Alert on unexpected cache restart events (Redis RESTARTED in logs)

**Recovery:**
1. On cache crash: do NOT immediately reconnect users to a cold cache — they will overwrite the last-known-good DB state with stale cached values
2. If using Redis AOF persistence: replay AOF log to reconstruct dirty buffer
3. If no AOF: accept data loss, set DB as authoritative, rebuild cache from DB reads
4. Post-recovery: replay missed writes from application-level write-ahead log if implemented

**Real Example:** In a post-mortem published on Medium (2026), a SaaS engineering team described how a Redis OOM kill during a traffic spike caused the loss of ~45 seconds of user-generated content updates. Their write-back flush interval was 30 seconds and they had disabled Redis AOF for performance. Total data loss: ~1,500 user preference updates. Resolution: re-enabled AOF with fsync=everysec and reduced flush interval to 5 seconds.

---

### Failure Mode 2: Write-Through Race Condition (Cache-DB Write Non-Atomicity)

**Trigger:** In a non-transactional write-through implementation, the cache write succeeds but the DB write fails (timeout, connection error, constraint violation). The cache now contains data that does not exist in the database.

**Symptoms:**
- Cache returns a value that does not exist in the DB
- On cache expiry or eviction, the value "disappears" from the user's perspective
- DB read replicas and cache return different values for the same key

**Detection:**
- Log and alert on any write-through where cache write succeeds but DB write fails
- Implement reconciliation jobs that compare cache values vs. DB values for hot keys on a 5-minute interval
- Track "write-through partial failure" as a named metric in your APM

**Recovery:**
1. On partial failure (cache write succeeded, DB write failed): issue a cache DEL immediately to prevent stale reads
2. Return an error to the caller — do NOT silently swallow the DB failure
3. If cache DEL also fails: apply a short TTL (5–10 seconds) as a safeguard so the inconsistency self-heals

**Real Example:** The Optijara engineering post-mortem (2025) described a write-through implementation where cache writes used fire-and-forget (no error checking) and DB writes used synchronous calls. During a Postgres replication failover (primary went down, new primary elected in ~15 seconds), ~800 write-through operations wrote to cache but received DB errors that were silently swallowed. Result: 800 user records appeared valid to the application (cache hits) but were not persisted. Detected only when cache evicted the keys 5 minutes later and reads returned 404s.

---

### Failure Mode 3: Write-Around "Read My Own Writes" Violation

**Trigger:** A user writes data (write-around → DB) and immediately reads it back within the same request. The cache miss causes a DB read, but if the DB read hits a read replica with replication lag, the user sees stale data — potentially their own write.

**Symptoms:**
- User updates profile photo; page refresh shows old photo
- User adds item to cart; cart count shows old value
- "Phantom write" — write appeared to succeed (200 OK) but data is not visible

**Detection:**
- Measure DB replication lag (pg_stat_replication lag_bytes / lag_seconds)
- Track "read-your-own-writes" violations using session IDs: log writes with session ID and check if the next read within the same session returned the written value
- Alert if read-replica replication lag exceeds 500 ms

**Recovery:**
1. Route reads-after-writes to the primary DB, not a read replica (session pinning)
2. Introduce a short-lived write token: after a write, store a token in the cache with a 2-second TTL; during that window, route reads to primary
3. Or: after a write-around write, populate the cache immediately (converting to write-through behavior for that key for one read cycle)

**Real Example:** Scaling Discord — Discord's message architecture routes write operations through a primary Cassandra node and reads through replicas. For message delivery confirmation ("message sent" vs. "message received"), they explicitly route the read-your-own-write check to the primary coordinator to avoid replication lag violations, accepting the ~3 ms latency cost for that specific read path.

---

### Failure Mode 4: Write-Back Dirty Queue Saturation

**Trigger:** Flush worker falls behind the write rate. The dirty queue grows unboundedly. Eventually the cache runs out of memory, starts evicting dirty (unflushed) keys — and those writes are permanently lost before they reach the DB.

**Symptoms:**
- Flush worker logs show increasing batch sizes and flush durations
- Redis memory usage approaching maxmemory limit
- Cache eviction counter increasing (INFO stats evicted_keys)
- DB is behind by hours, not seconds

**Detection:**
- Alert: flush worker processing time > 80% of flush interval (worker can't keep up)
- Alert: dirty queue depth > N entries (depends on your write volume, but e.g. > 100K is a red flag)
- Alert: Redis evicted_keys delta > 0 when write-back dirty keys are present

**Recovery:**
1. Emergency: switch to write-through temporarily to stop dirty queue growth
2. Scale flush workers horizontally (multiple workers consuming from different queue partitions)
3. Increase flush worker DB write parallelism (async batch inserts)
4. Do NOT increase maxmemory as a first response — diagnose why the queue is growing

---

## 10. When To Use vs. When To Avoid

### Write-Through

**✅ Use When:**
- Data consistency is a hard requirement (financial transactions, payment state, inventory counts)
- Your read:write ratio is > 3:1 — writes are frequent enough to keep the cache warm but reads dominate
- The ~0.5 ms write overhead fits within your p99 latency SLA
- You need simple cache invalidation semantics — write-through means you never need to explicitly invalidate on writes

**❌ Do NOT Use When:**
- Your write rate exceeds 50,000/second per cache node and you are measuring write latency as a bottleneck
- Data is write-only or write-once (audit logs, append-only event streams) — you are paying write overhead for data that will never be read from cache
- Cross-region deployments where "write to cache AND DB" means "write to cache in us-east-1 AND replicate to eu-west-1" — the latency adds up to 100+ ms

**⚠️ #1 Mistake:** Implementing write-through without atomicity guarantees. If your cache write and DB write are two independent calls (not wrapped in a transaction or compensating logic), you will have partial failure states. Always handle the case where one succeeds and the other fails.

---

### Write-Back (Write-Behind)

**✅ Use When:**
- DB write throughput (IOPS) is a confirmed production bottleneck (not theoretical)
- The data has a clear durability tolerance: "losing up to N seconds of writes is acceptable"
- Writes batch naturally: same key written many times per second (counters, scores, last-seen timestamps)
- You have implemented persistent dirty queues and tested crash recovery

**❌ Do NOT Use When:**
- Data loss is never acceptable (financial balances, medical records, legal documents)
- Your team does not have experience operating Redis AOF persistence and write-back recovery
- You are at < 100K users/day — the added complexity far outweighs the benefit at small scale
- The data is written once and read many times (low update frequency) — you get no batching benefit

**⚠️ #1 Mistake:** Using in-memory dirty queues (Python dict, HashMap) without Redis persistence. When the process crashes (and it will), the queue is gone. Always use Redis Streams, Redis Sorted Sets, or a message queue (Kafka, SQS) as your dirty buffer — something that survives a process restart.

---

### Write-Around

**✅ Use When:**
- Write:read ratio > 5:1 for a data category (most writes are never immediately re-read)
- You are dealing with append-only data: logs, audit trails, time-series metrics, event streams
- Cache pollution is measured as a problem: eviction rates are high and the evicted data is write-heavy but not read-heavy
- The write path is throughput-critical and even 0.5 ms of cache overhead is unacceptable

**❌ Do NOT Use When:**
- Users expect read-your-own-writes semantics (profile updates, settings changes)
- The same data is written and then immediately queried (e.g., write product, immediately show product in search results)
- Your system relies on the cache being pre-warmed — write-around means cold starts are always cache misses

**⚠️ #1 Mistake:** Using write-around for user-facing write operations (profile updates, preference changes) and not handling the read-your-own-writes problem. The user changes their username, refreshes the page, and sees the old username. This is a consistency violation that is invisible in testing (tests don't check replication lag) and immediately visible to users.

## 11. Interview Perspective

### Real Question Phrasings You Will Hear

1. "How would you design the write path for a high-traffic e-commerce product catalog?"
2. "Our database is getting crushed by writes at peak. Walk me through your options."
3. "What is the difference between write-through and write-back? When would you use each?"
4. "You are designing Twitter's tweet storage. Tweets are written once and read millions of times. What caching strategy would you use on the write path?"
5. "How does Meta keep Facebook's cache consistent at scale?"
6. "If we use write-back caching and our Redis cluster goes down, what happens?"
7. "We are building a gaming leaderboard that gets 50,000 score updates per second. How do you design this?"

---

### What the Interviewer Is Actually Evaluating

1. **Do you know the three strategies by name and mechanics?** (table stakes)
2. **Can you articulate the trade-off triangle?** Latency vs. consistency vs. durability — not just memorized pros/cons
3. **Do you default to write-through or write-back?** (Red flag: defaulting to write-back without justification signals "optimized prematurely")
4. **Can you identify when write-around is the right choice?** Most candidates forget it exists
5. **Do you think about failure modes?** A strong candidate immediately asks "what happens if the cache crashes between the cache write and the DB write?"
6. **Can you name real companies and real decisions?** Meta + CDC, Netflix + EVCache, Stripe + write-through for payments

---

### Junior vs. Senior vs. Staff Answer Quality

**Question: "How would you handle caching in a system with 100K writes/second?"**

**Junior Answer:**
> "I would use write-through caching — write to both the cache and the database at the same time. That way the cache is always up to date."

*What is missing:* No awareness of the write overhead at 100K/s, no discussion of when write-through becomes a bottleneck, no mention of alternatives.

---

**Senior Answer:**
> "It depends on the data. For user-facing data where consistency matters — profile data, cart state — I would use write-through. The ~0.5 ms overhead per write is acceptable at this scale. For high-frequency counters like view counts or like counts, I would use write-back with a 500 ms flush interval — those writes batch naturally and losing 500 ms of counter updates is acceptable. I would use write-around for analytics events and logs, since they are never read back immediately."

*What is good:* Differentiates by data category. Knows the overhead numbers. Thinks about acceptable durability windows.

---

**Staff Answer:**
> "Let me start by segmenting the write workload. 100K writes/second is a high-level number — first question is whether these are 100K writes to 100K distinct keys, or 100K writes to 1K hot keys. The answer changes everything.
>
> For distinct-key writes: write-through is fine up to ~200K writes/second for a well-tuned Redis cluster. The bottleneck is typically the DB, not the cache. I would use write-through with connection pooling and pipeline batching to reduce per-write RTT.
>
> For hot-key writes (same key updated thousands of times per second — classic counters, leaderboards): write-back is the right tool. I would implement a Redis Sorted Set as the dirty queue, flush every 100 ms, and use Redis AOF with fsync=everysec so I lose at most 1 second of updates on a crash. I would also monitor dirty queue depth and alert at 10K entries to catch flush worker lag early.
>
> For write-only data (analytics, audit logs): write-around entirely. Do not touch the cache — write directly to the analytical store (Kafka + S3 + Athena, or ClickHouse). Caching analytics writes wastes RAM and the data is never read in real time anyway.
>
> At this scale I would also consider whether some of these writes can be coalesced at the application layer before hitting either the cache or DB — client-side batching can reduce the actual write rate by 10-50x for certain workloads."

*What is excellent:* Breaks down the assumption in the question. Knows specific Redis data structures (Sorted Set for dirty queue). Knows specific Redis persistence settings. Thinks about monitoring. Considers application-layer optimization. Uses write-around correctly for analytics.
