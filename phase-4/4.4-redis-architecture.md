## 1. What Is It? (Theory)

### Plain English

Redis is an in-memory data structure server. Not just a key-value cache — a server that holds your data in RAM and exposes a rich set of data structures (strings, lists, sets, sorted sets, hashes, streams, bitmaps, HyperLogLogs) over a TCP protocol. It processes commands one at a time on a single thread, persists optionally to disk, and replicates asynchronously to replicas.

Think of Redis as a **supercharged hash map that lives in RAM, speaks TCP, and never forgets** (with persistence enabled).

### The Analogy

Imagine a world-class librarian who memorizes the entire card catalogue — they can retrieve any book's location in under a millisecond because it's all in their head. A traditional database is like running to a filing cabinet on a different floor, opening the drawer, scanning the folder, and walking back. Redis is the librarian.

### The Problem Redis Solves at Scale

A PostgreSQL `SELECT` on a well-indexed table averages 1–5 ms. A Redis `GET` averages 0.1–0.3 ms. That sounds small until you realize:

- Your authentication service makes 10 DB calls per request
- You serve 50,000 requests/second at peak
- That is 500,000 DB queries/second — impossible without caching

At 1 million users concurrently: your database will collapse. Redis absorbs the traffic, slashing DB load by 80–99%.

### Why Redis Was Invented

Salvatore Sanfilippo (antirez) created Redis in 2009 while building a real-time analytics tool in Sicily. He needed a data structure server — not just a cache. The key insight: expose server-side data structures (sorted sets, lists, sets) so the client does not need to fetch-compute-write-back cycles. The server mutates data atomically, in memory, without network round-trips for transformation.

## 2. How It Actually Works (Deep Mechanics)

### The Single-Threaded Event Loop

Redis processes all commands on **one thread**. This is not a limitation — it is a deliberate design that eliminates lock contention, context-switching overhead, and synchronization bugs.

```
Client A ──┐
Client B ──┤──► [Multiplexed I/O]──► [Event Queue] ──► [Command Processor] ──► [Response Buffer]
Client C ──┘         epoll/kqueue         FIFO           Single Thread           Per-client
```

Step-by-step request lifecycle:

1. **Network accept**: The OS multiplexes thousands of TCP connections via `epoll` (Linux) or `kqueue` (BSD/macOS). Each connection is a file descriptor.
2. **Read event fires**: When a client sends bytes, the event loop wakes up, reads the data from the socket into a read buffer (not blocking).
3. **Command parsing**: Redis parses the RESP (REdis Serialization Protocol) format. `*3\r\n$3\r\nSET\r\n$5\r\nhello\r\n$5\r\nworld\r\n` = `SET hello world`.
4. **Command dispatch**: The parsed command is looked up in a command table (hash map of ~200 commands). The corresponding C function is called.
5. **Data structure mutation**: The command runs against the in-memory data structure. A `ZADD` on a sorted set mutates a skip list + hash table combo in nanoseconds.
6. **Write to response buffer**: The result is serialized into RESP format and buffered.
7. **Write event fires**: The event loop drains the response buffer back to the client socket.

Total time for steps 3–6 (CPU work): **~1–5 microseconds**.
Total end-to-end latency (including network): **~100–300 microseconds** on localhost.

### Internal Data Structures

| Redis Type | Small Encoding | Large Encoding | Threshold |
|---|---|---|---|
| String | embstr (≤44 bytes) | raw (SDS) | 44 bytes |
| Hash | listpack | hashtable | 128 fields or 64-byte values |
| List | listpack | quicklist | 128 elements or 64-byte values |
| Set | listpack | hashtable | 128 members |
| Sorted Set | listpack | skiplist + hashtable | 128 members or 64-byte values |
| Stream | listpack blocks | rax + listpack | configurable |

**SDS (Simple Dynamic String)**: Redis does not use C's null-terminated strings. SDS prepends a header with length, free space, and type — enabling O(1) `STRLEN` and safe binary storage (nulls in values are valid).

**Listpack (Redis 7.0+, replacing ziplist)**: A single contiguous memory allocation. Each entry stores: `[encoding][data][backlen]`. No cascading update problem — backward traversal uses backlen suffix rather than previous-entry-length. This eliminates a historical O(n) worst case that ziplist had on deletion/insertion.

**Skip List (Sorted Sets)**: A probabilistic data structure with O(log n) insert, delete, and range query. Redis uses a 32-level skip list. This enables `ZRANGE`, `ZRANGEBYSCORE`, and `ZRANK` in O(log n + k) time, where k is the number of returned elements. An AVL or B-tree would have similar complexity but more complex implementation.

```
Level 4: HEAD ──────────────────────────────────────── score:90 ──► NULL
Level 3: HEAD ───────────── score:30 ───────────────── score:90 ──► NULL
Level 2: HEAD ─── score:10 ─ score:30 ─── score:60 ─── score:90 ──► NULL
Level 1: HEAD ─── score:10 ─ score:30 ─ score:50 ─ score:60 ─ score:90 ──► NULL
```

**Sorted Set Dual Encoding**: When large, a sorted set uses BOTH a skip list (for O(log n) rank queries and range scans) AND a hash table (for O(1) score lookups by member). Memory doubles, but all operations are fast.

### Threading Model (Post Redis 6.0)

Redis 6.0 introduced **threaded I/O** — an important nuance:

```
                    ┌─── I/O Thread 1 (read/parse)
Main Event Loop ────┼─── I/O Thread 2 (read/parse)   ──► Command Queue ──► Main Thread (execute)
                    └─── I/O Thread 3 (write responses)
```

- **Command execution** remains single-threaded (the main thread).
- **Network I/O** (reading from sockets, writing responses) can be parallelized.
- Enable with: `io-threads 4` and `io-threads-do-reads yes` in redis.conf.
- Benefit: On high-bandwidth scenarios, I/O threads improve throughput by 2–3x with no concurrency bugs in command processing.

### Persistence: RDB vs AOF

**RDB (Redis Database Backup)** — Point-in-time snapshots:

```
Main Process ──► fork() ──► Child Process
     │                           │
     │ continues serving         │ iterates entire dataset
     │ requests (CoW memory)     │ writes .rdb binary file
     │                           │ (compact, LZF-compressed)
     └───────────────────────────┘ child exits
```

- `fork()` uses Linux Copy-on-Write (CoW): child reads parent's memory pages without copying until a page is written.
- RDB file: dense binary, loads fast on restart (~10 GB/minute read speed).
- Data loss on crash: up to the interval between snapshots (default: 5 minutes if 100+ writes).
- Config: `save 900 1` (save after 900 sec if 1 key changed), `save 300 10`, `save 60 10000`.

**AOF (Append-Only File)** — Write-ahead log:

```
Client ──► SET foo bar ──► [Command Processor] ──► [Memory Update] + [AOF Buffer]
                                                                           │
                                                               fsync policy:
                                                               always  = fsync every write (~1ms overhead)
                                                               everysec = fsync every 1 second (default)
                                                               no       = OS decides (fastest, least durable)
```

- AOF stores raw Redis commands as RESP text. On restart, Redis replays every command.
- AOF rewrite: Redis forks a child to rebuild the AOF from the current dataset (eliminating redundant SET/DEL pairs). Triggered at `auto-aof-rewrite-percentage 100` (when file doubles in size).
- Data loss: at most 1 second (with `everysec` policy).
- Trade-off: AOF files are 3–5x larger than RDB and replay is slower.

**Hybrid Persistence (Redis 4.0+)**: AOF files can contain an RDB snapshot at the start, followed by incremental AOF commands. Faster restarts than pure AOF, better durability than pure RDB. Enable with `aof-use-rdb-preamble yes`.

### Misconceptions

**❌ Misconception: Redis is just a cache.**
**✅ Reality:** Redis is a data structure server. It has streams (Kafka-lite), pub/sub, geospatial indexing, HyperLogLog (cardinality estimation), Lua scripting, transactions, and server-side Lua functions. Many companies use Redis as their primary database for session state, rate limiting counters, and leaderboards — not just a read-aside cache.

**❌ Misconception: Single-threaded means slow.**
**✅ Reality:** Redis handles 100,000–1,000,000 operations/second on a single core. The bottleneck is almost always network bandwidth or memory bandwidth, not CPU. Removing lock overhead, context switching, and cache line invalidation makes a single-threaded, event-driven model faster than naive multi-threading for I/O-bound workloads.

**❌ Misconception: Redis loses all data on restart.**
**✅ Reality:** With AOF (everysec) enabled, Redis loses at most ~1 second of data. With `always` fsync, Redis is as durable as PostgreSQL with synchronous_commit=on, albeit with worse write throughput.

**❌ Misconception: Redis replication is synchronous (safe).**
**✅ Reality:** Redis replication is asynchronous by default. A master can acknowledge a write to the client before any replica has received it. The `WAIT numreplicas timeout` command blocks until N replicas confirm, but this is opt-in per-command.

## 3. Real-World Architecture Examples

### Discord — Session State and Rate Limiting at 19 Million Concurrent Users

Discord uses Redis clusters for:
- **Shard mapping cache**: When a message needs routing, Discord uses `MGET` on Redis to look up the shard responsible for a given guild, avoiding a slow Cassandra read on every message delivery.
- **Load-aware shard allocation**: A Redis sorted set tracks shard load scores. New connections call `ZRANGEBYSCORE` to find the least-loaded shard. Score updates are atomic `ZINCRBY` — no locking needed.
- **Rate limiting**: Sliding window rate limiters using sorted sets. Score = Unix timestamp in milliseconds, member = request UUID. `ZREMRANGEBYSCORE` prunes old entries, `ZCARD` counts current requests.

Discord's engineering blog ("How Discord Indexes Billions of Messages") notes they used Redis's expiring hashmap to control Elasticsearch refresh cycles — tracking per-shard guild refresh queues with `HSETNX` + `EXPIRE`.

### Netflix — EVCache (Their Redis Fork at Scale)

Netflix runs **EVCache**, an open-source memcached-based system, but also operates Redis clusters for:
- **Playback state**: Current playback position, watched history — must survive regional failures.
- **Feature flags and A/B test assignments**: Billions of key-value reads, sub-millisecond latency required.
- **Pre-warming**: Before a popular show drops, Netflix's ML pipeline predicts which content metadata keys will be hot. Redis clusters are pre-populated hours in advance, achieving **>99.99% cache hit rates** during peak launch traffic when 10+ million concurrent users hit simultaneously.

Netflix engineers noted (InfoQ 2024) that their stateful cache systems handle **>1 million QPS** at steady state, with p99 latency under 5 ms across global regions.

### Stripe — Idempotency Keys and Rate Limiting

Stripe uses Redis for:
- **Idempotency key storage**: When a payment API call is retried, Stripe checks Redis for the original response keyed by idempotency key. Keys are retained for 24 hours with a Redis TTL. `SET idempotency:{key} {response_json} EX 86400 NX` — atomic set-if-not-exists prevents duplicate processing.
- **API rate limiting**: Token bucket and sliding window rate limiters implemented as Lua scripts on Redis, ensuring atomic check-and-decrement without race conditions across Stripe's multi-server environment. Handles **500,000+ API requests per minute** at peak.
- **Distributed locks**: `SET lock:{resource} {owner} NX PX {timeout_ms}` — the Redlock pattern for distributed mutual exclusion on payment processing pipelines.

Stripe engineers chose Redis over a database-backed rate limiter because a single Redis round-trip (0.3 ms) is 10–50x faster than a PostgreSQL row lock (3–15 ms) under contention.

### Cloudflare — Edge Caching and Workers KV

Cloudflare's Workers KV is a globally distributed, eventually consistent key-value store built on top of Redis-compatible internals. For edge rate limiting (32 trillion requests/day), Cloudflare uses Redis at each PoP (Point of Presence):
- Each PoP maintains local Redis for per-edge rate limit counters.
- Counters sync to a central store every 60 seconds, providing approximate global rate limiting without cross-region latency.
- This architecture allows **sub-millisecond rate limit decisions** at 200+ global edge locations.

## 4. Design Deep Dive

### Architecture Modes

#### Single Instance (Development / Low Traffic)

```
Application ──────────────────► Redis (single node)
                                   │
                               [RAM: ~8 GB]
                               [Persistence: RDB hourly]
                               [No replication]
```

Single point of failure. Acceptable for dev/staging. Never use in production for critical data.

#### Sentinel HA (Primary + Replicas, Automatic Failover)

```
                        ┌─── Sentinel 1
Application             ├─── Sentinel 2     (quorum = 2 of 3)
    │                   └─── Sentinel 3
    │                           │ monitors
    ▼                           ▼
[Primary Redis] ──async repl──► [Replica 1]
      │                          [Replica 2]
      │
  (if primary dies)
      │
Sentinel promotes Replica 1 ──► new primary
Application notified via Sentinel API
```

- Sentinel uses Raft-like quorum. Majority of Sentinels must agree before triggering failover.
- Failover time: 15–30 seconds by default (configurable via `down-after-milliseconds`).
- During failover: writes fail (no primary). Reads from replicas can continue if configured.
- Use case: Single primary dataset that must survive node failures. Up to ~100 GB RAM.

#### Redis Cluster (Horizontal Sharding + HA)

```
               Client (cluster-aware)
              /         |          \
       Shard A       Shard B       Shard C
    [Primary A]   [Primary B]   [Primary C]
    slots 0-5460  slots 5461-10922  slots 10923-16383
    [Replica A1]  [Replica B1]  [Replica C1]
    [Replica A2]  [Replica B2]  [Replica C2]
```

- Redis Cluster uses **consistent hashing with hash slots**: 16,384 slots, each key maps to a slot via `CRC16(key) % 16384`.
- Hash tags: `{user}.profile` and `{user}.settings` share the same slot (the key inside `{}` is used for hashing). This ensures multi-key operations on logically related keys hit the same shard.
- Cluster gossip protocol: nodes communicate every 100 ms to detect failures. A node is marked failing if a majority of masters agree it is unreachable.
- Cluster can scale to 1,000 nodes (Redis documentation), 200–300 practical sweet spot for operations overhead.
- Cross-slot operations (MGET spanning multiple shards) require client-side scatter-gather.

### Scale Evolution

```
Users        Architecture              Redis Setup              Write Throughput
─────────────────────────────────────────────────────────────────────────────────
1K–10K      Monolith + single Redis   1x r6g.large (16GB RAM)  ~50K ops/sec

100K–1M     Redis Cluster             3–6 shards, 2 replicas   ~1M ops/sec
            Microservices caching     each, 64–128 GB total     Cross-shard
            Per-service Redis DBs     Auto-failover             ops avoided
            Hot key detection         Cluster-aware clients     via hash tags

1M–100M     Regional Redis Clusters   Multi-region active-      >10M ops/sec
            Active-active (CRDTs)     active with Redis         per region

```

### Memory Sizing Rule of Thumb

```
Keys:         10 million
Avg key size: 20 bytes
Avg val size: 200 bytes
Overhead:     ~50 bytes per key (dict entry, expire, encoding headers)

Total:        10M * (20 + 200 + 50) = 2.7 GB raw data

Redis overhead factor: ~1.5x–2x for hash tables, robj wrappers, jemalloc fragmentation

Production sizing: 2.7 GB * 2 = ~5.4 GB
Add 25% headroom for peaks + fork memory during RDB save: ~7 GB

Choose: r6g.xlarge (32 GB RAM) for comfort, with maxmemory set to 20 GB
```

## 5. Code / Implementation Perspective

### Language-Agnostic Pattern: Cache-Aside with Redis

The most common Redis pattern in production:

```python
import redis
import json
import hashlib
import time
from functools import wraps
from typing import Optional, Any, Callable

# Redis connection pool — critical for production
# Never create a new connection per request
pool = redis.ConnectionPool(
    host="redis-primary.internal",
    port=6379,
    db=0,
    max_connections=50,        # tune to your thread pool size
    socket_timeout=0.5,        # fail fast: 500ms timeout
    socket_connect_timeout=1.0,
    decode_responses=True
)
client = redis.Redis(connection_pool=pool)


def cache_aside(
    key_fn: Callable,
    ttl_seconds: int = 300,
    fallback_ttl: int = 10     # short TTL for "not found" results
):
    """
    Decorator implementing cache-aside (lazy loading) pattern.
    Uses jitter on TTL to prevent thundering herd on mass expiry.
    """
    def decorator(fn: Callable) -> Callable:
        @wraps(fn)
        def wrapper(*args, **kwargs) -> Any:
            cache_key = key_fn(*args, **kwargs)

            # 1. Check cache first
            cached = client.get(cache_key)
            if cached is not None:
                return json.loads(cached)  # cache hit

            # 2. Cache miss — fetch from source of truth
            result = fn(*args, **kwargs)

            # 3. Write to cache with jitter (±10% of TTL)
            import random
            jitter = int(ttl_seconds * 0.1 * random.random())
            effective_ttl = ttl_seconds + jitter

            if result is None:
                # Cache negative results briefly to prevent DB hammering
                client.setex(cache_key, fallback_ttl, "null")
            else:
                client.setex(cache_key, effective_ttl, json.dumps(result))

            return result
        return wrapper
    return decorator


@cache_aside(
    key_fn=lambda user_id: f"user:profile:{user_id}",
    ttl_seconds=300
)
def get_user_profile(user_id: int) -> Optional[dict]:
    """Fetches user from PostgreSQL — only called on cache miss."""
    return db.query("SELECT * FROM users WHERE id = %s", user_id)


# Sorted Set leaderboard — atomic, server-side ranking
def update_leaderboard(player_id: str, score: float):
    client.zadd("leaderboard:global", {player_id: score})

def get_top_players(count: int = 10) -> list:
    # ZREVRANGEBYSCORE with scores — O(log N + K)
    return client.zrevrange("leaderboard:global", 0, count - 1, withscores=True)


# Sliding window rate limiter using sorted set — atomic via pipeline
def is_rate_limited(user_id: str, limit: int = 100, window_seconds: int = 60) -> bool:
    key = f"ratelimit:{user_id}"
    now = time.time()
    window_start = now - window_seconds

    pipe = client.pipeline()
    pipe.zremrangebyscore(key, 0, window_start)   # remove old entries
    pipe.zadd(key, {str(now): now})               # add current request
    pipe.zcard(key)                                # count in window
    pipe.expire(key, window_seconds)               # TTL cleanup
    results = pipe.execute()

    request_count = results[2]
    return request_count > limit


# Distributed lock (simplified Redlock for single node)
def acquire_lock(resource: str, ttl_ms: int = 5000) -> Optional[str]:
    lock_key = f"lock:{resource}"
    owner = hashlib.sha256(str(time.time()).encode()).hexdigest()[:16]
    # SET key value NX PX ttl — atomic acquire
    acquired = client.set(lock_key, owner, nx=True, px=ttl_ms)
    return owner if acquired else None

def release_lock(resource: str, owner: str) -> bool:
    # Lua script: check owner matches before deleting — atomic
    lua = """
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
    """
    result = client.eval(lua, 1, f"lock:{resource}", owner)
    return bool(result)
```

### Redis Commands Reference for Common Patterns

```bash
# String — with TTL
SET user:session:abc123 '{"uid":42,"role":"admin"}' EX 3600 NX

# Hash — store object fields separately (field-level TTL in Redis 7.4+)
HSET user:42 name "Alice" email "alice@example.com" plan "pro"
HGET user:42 name
HMGET user:42 name email

# Sorted Set — leaderboard
ZADD leaderboard:2024 NX 9850 "player:alice"
ZREVRANK leaderboard:2024 "player:alice"    # O(log N) rank
ZREVRANGE leaderboard:2024 0 9 WITHSCORES   # top 10

# List — message queue (FIFO)
LPUSH queue:emails '{"to":"a@b.com","subject":"Welcome"}'
BRPOP queue:emails 0   # blocking pop, 0 = wait forever

# HyperLogLog — count unique visitors (uses ~12 KB regardless of cardinality)
PFADD unique:visitors:2024-01-15 user123 user456 user789
PFCOUNT unique:visitors:2024-01-15   # approximate, ~0.81% error

# Pub/Sub
SUBSCRIBE channel:notifications    # subscriber
PUBLISH channel:notifications '{"type":"alert","msg":"Server down"}'

# Lua scripting — atomic compare-and-set
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('SET',KEYS[1],ARGV[2]) else return 0 end" 1 mykey oldval newval

# Cluster-aware multi-key: hash tag forces same slot
MSET {user:42}.profile '...' {user:42}.settings '...'
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Redis** | Default choice for caching, sessions, leaderboards, pub/sub, rate limiting | Single-threaded (though I/O threaded in 6.0+); AGPL license in v8.0 | Discord, Stripe, GitHub, Airbnb, Twitter |
| **Memcached** | Pure string cache, multi-threaded required, simplest possible cache | No persistence, no complex data structures, no pub/sub, no replication built-in | Facebook (TAO uses custom), YouTube historical |
| **Valkey 8.x** | Open-source-first teams, cost-sensitive, AWS/GCP managed environments | Newer ecosystem, fewer community resources, some Redis modules not yet ported | AWS (ElastiCache default in 2024), GCP Memorystore |
| **Dragonfly** | High-core-count servers (32+ cores), memory-constrained, Memcached compat | BSL license (not fully open-source), newer and less battle-tested | Early adopters, startups optimizing cost |
| **Hazelcast** | Java shops, distributed computing, data grid with compute | JVM memory overhead, complex cluster management | Large Java enterprises |
| **Apache Ignite** | Distributed SQL + cache hybrid, compute grid | High operational complexity, JVM-only | Financial services, complex data grids |
| **DynamoDB DAX** | Already on DynamoDB, need microsecond cache, AWS-locked | Proprietary, AWS-only, limited query patterns | AWS-native applications |
| **In-process cache (Caffeine/Guava)** | Same JVM, single service, low cardinality hot keys | Per-instance, no sharing across pods, cold start on restarts | Any service's L1 cache before Redis L2 |

**My recommendation:** Start with Redis OSS (or Valkey on AWS/GCP). Use Memcached only if you have measured that Redis's single-threaded execution is your bottleneck — in practice, fewer than 1% of teams hit this. Never choose Memcached for new projects because you will eventually need persistence, pub/sub, or sorted sets, and migrating is painful. Evaluate Dragonfly only if you have >32 cores on a single node and have profiled that Redis is the bottleneck.

## 8. Trade-offs (Be Opinionated)

### Benefits

**Speed**: Sub-millisecond latency at p99 is achievable with Redis in the same datacenter. This is not magic — it is RAM access times (50–100 ns) plus TCP loopback (~10–20 µs) plus RESP parsing (~1–5 µs).

**Rich Data Structures**: Server-side sorted sets, HyperLogLog, streams, and bitmaps eliminate entire categories of client-side complexity. A leaderboard that would require a client fetch + sort + write-back becomes a single `ZADD` + `ZREVRANGE`.

**Atomicity via Lua and Pipelines**: Lua scripts run atomically — no other command executes between the first and last line of your script. This enables correct distributed rate limiters, compare-and-swap operations, and read-modify-write patterns without application-level locking.

**Ecosystem**: Every language has a production-grade Redis client. Mature observability (INFO command, Prometheus exporter), battle-tested clustering, and extensive documentation.

### Costs

**Memory is expensive**: RAM costs 10–100x more per GB than SSD at the cloud provider level. Storing 1 TB in Redis on AWS costs ~$30,000/month in EC2 compute. Storing 1 TB in RDS (SSD) costs ~$200/month in storage alone.

**Single-threaded bottleneck on CPU-heavy operations**: SORT on a 1M-element list, KEYS *, SMEMBERS on a giant set — these block all other clients for their duration. This is why `KEYS *` is banned in production.

**Fork overhead on large datasets**: RDB snapshots call `fork()`. On a 32 GB Redis instance, the OS must copy the page table (~64 MB) and may trigger CoW page copies under write load. Memory usage can spike to 1.5–2x during a snapshot on a write-heavy workload.

**Async replication means data loss is possible**: Under network partition or primary failure, the last acknowledged writes may not have reached any replica. In financial systems, this requires `WAIT` commands or accepting the risk.

### Core Tension

**Speed vs. Durability**: Every step you take toward durability (AOF always > AOF everysec > RDB > no persistence) adds latency and reduces throughput. AOF with `always` fsync cuts write throughput by ~70% but gives you PostgreSQL-level durability. The default `everysec` is the right balance for 95% of use cases — you lose at most 1 second of writes on a crash, which is acceptable for caches and sessions.

### My Recommendation

Use Redis with:
- `appendonly yes`, `appendfsync everysec` for most production workloads
- `maxmemory-policy allkeys-lru` for pure caches
- `maxmemory-policy volatile-lru` if you mix cached and permanent data
- Sentinel (3 nodes) for HA at up to ~50 GB total dataset
- Redis Cluster for datasets >50 GB or >500K ops/sec
- Connection pooling at the application layer — never open a new Redis connection per request
- Avoid `KEYS *`, `SORT` without LIMIT, `SMEMBERS` on sets >10K members in production

On new projects in 2025: seriously evaluate Valkey on managed cloud (AWS ElastiCache or GCP Memorystore). It is API-compatible, costs less, and has better open-source licensing. Only choose Redis OSS if you need Redis-specific modules (RedisSearch, RedisJSON, RedisTimeSeries) that have not yet landed in Valkey.

## 9. Failure Modes — What Goes Wrong

### Failure Mode 1: Hot Key Saturation

**Trigger**: A single Redis key receives a disproportionate share of traffic (e.g., a viral tweet's like counter, a celebrity user's session, a globally-shared feature flag). All requests for that key serialize on the single-threaded Redis command processor.

**Symptoms**: Redis CPU at 100% on one core. Other key access latency spikes to 50–500 ms. Application logs show Redis timeout errors. The hot key's latency is paradoxically fine (it completes instantly), but queue depth behind it grows.

**Detection**: `redis-cli --hotkeys` (requires `maxmemory-policy allkeys-lfu`). Or monitor with `redis-cli MONITOR` (warning: 50%+ performance hit on production). Better: use `redis-cli --intrinsic-latency 60` to establish baseline. Application-side: track per-key request rates in metrics.

**Recovery**:
1. **Local read-through cache**: Cache the hot key value in-process (Caffeine, TTL = 1 second) across all application pods. Redis still gets ~1 req/pod/sec instead of 10K req/sec.
2. **Key sharding**: Shard hot key into N copies: `feature_flag:dark_mode:shard:{random(0,N)}`. Read from random shard. Write to all N shards (or accept eventual consistency with TTL).
3. **Read replicas**: Route reads to replicas. Redis Cluster promotes replicas as read targets with `READONLY` command.

**Real Example**: Discord observed hot keys on popular guild shard mappings during viral events (e.g., a game release). Resolution: local in-memory cache of shard maps with 5-second TTL, refreshed lazily on miss.

---

### Failure Mode 2: Memory Exhaustion and Eviction Thrashing

**Trigger**: Dataset grows beyond `maxmemory` limit. Redis begins evicting keys. If eviction rate equals or exceeds write rate, Redis enters a loop of evict-write-evict with no useful keys surviving.

**Symptoms**: `used_memory` at `maxmemory`. `evicted_keys` counter climbing continuously in `INFO stats`. Cache hit rate drops from 95% to 30–50%. Database CPU spikes as previously cached queries return to DB. Redis latency increases as LRU sampling runs on every write.

**Detection**: Alert on `evicted_keys` rate > 100/sec. Alert on `used_memory_rss` / `maxmemory` > 0.95. Monitor `keyspace_hits` / (`keyspace_hits` + `keyspace_misses`) — this is your cache hit rate.

**Recovery**:
1. Increase `maxmemory` (vertical scaling) or add Redis Cluster shards (horizontal).
2. Audit key sizes: `redis-cli --bigkeys`. Large values (>1 MB) are memory hogs.
3. Switch eviction policy: `allkeys-lfu` often outperforms `allkeys-lru` for skewed access patterns (frequently-accessed keys are retained over recency).
4. Compress values: JSON `{"user_id": 12345, "name": "Alice"}` → MessagePack binary (50–70% smaller).

**Real Example**: A startup cached full HTML page renders (200–800 KB each) in Redis. 10K pages filled the 8 GB Redis instance. Eviction thrashing hit when the 10,001st page was cached. Fix: store only the data, render server-side; per-value size limit enforced in application layer before writing to Redis.

---

### Failure Mode 3: Replication Lag and Stale Reads

**Trigger**: High write rate on primary (>100K writes/sec), or replica is under-resourced (CPU/network saturated). The replication backlog (`repl_backlog_size`, default 1 MB) fills up. If a replica disconnects and reconnects, it may need a full resync rather than partial sync (PSYNC), causing a fork on the primary.

**Symptoms**: `replica_lag` in `INFO replication` grows (seconds or minutes behind). Stale reads from replica — cache returns value that was overwritten 30 seconds ago on primary. Application sees data inconsistency (user updates profile, refreshes, sees old profile because the request hit the lagging replica).

**Detection**: Monitor `master_repl_offset - replica_repl_offset` per replica. Alert if lag > 500 ms. Use `INFO replication` in dashboards.

**Recovery**:
1. Increase `repl-backlog-size` (e.g., 256 MB) to handle replica disconnects without full resync.
2. Route write-sensitive reads to primary: `client.set_master_for_key(key)` — or use read-your-writes routing in application.
3. Reduce replica count: more replicas = more replication streams = more primary CPU.
4. Add `min-replicas-to-write 1` + `min-replicas-max-lag 5` to reject writes when replicas are too far behind (trade availability for consistency).

**Real Example**: GitHub's Resque (Redis-based job queue) experienced replication lag during backup windows. RDB fork caused CoW page pressure, slowing the primary's ability to push replication stream. Fix: schedule RDB saves during off-peak hours, increase `repl-backlog-size` from 1 MB to 64 MB.

---

### Failure Mode 4: KEYS * in Production (Catastrophic Blocking)

**Trigger**: A developer or monitoring script runs `KEYS *` on a production Redis instance with 10 million keys. The command scans the entire keyspace on the single-threaded main loop.

**Symptoms**: Redis blocks for 100–5000 ms (depending on keyspace size). All other commands queue behind it. Application experiences total Redis unavailability for the duration. Connection timeouts cascade. Application falls back to database, which collapses under load.

**Detection**: `slowlog get 100` shows a `KEYS *` command with duration > 1000000 µs. Post-incident only.

**Recovery**: Immediate: nothing (command completes). Prevention: ACL restrictions (`ACL SETUSER monitor ~* +@read -keys`) to block `KEYS` command for non-admin users. Use `SCAN cursor COUNT 100` for iterative, non-blocking key enumeration.

**Real Example**: The "14-Hour Outage Because I Didn't Understand Redis" post-mortem (Medium, widely shared) describes a monitoring script that ran `KEYS *` every minute on a 50M-key Redis instance, causing ~800 ms blockage every 60 seconds — enough to trigger cascading timeouts in a microservices chain.

---

### Failure Mode 5: Split-Brain on Sentinel Failover (Network Partition)

**Trigger**: A network partition separates the primary Redis node from the Sentinel quorum and application servers. The Sentinel quorum (which can reach replicas) elects a new primary. The original primary is now isolated — still serving writes to application servers that can reach it directly.

**Symptoms**: Two Redis primaries exist simultaneously. Application servers are split: some write to old primary, some to new primary. After partition heals, one primary's data is discarded. Data loss proportional to partition duration.

**Detection**: `INFO replication` shows `role:master` on two nodes. Application-side: inconsistent reads immediately post-failover.

**Recovery**: Configure `min-replicas-to-write 1` on primary — the primary refuses writes if it cannot replicate to at least one replica, self-isolating during partition. Use Redis Cluster's built-in partition handling (Cluster halts writes if too many primaries are unreachable) for stronger guarantees.

**Real Example**: Described in Redis documentation and multiple production post-mortems — a misconfigured Sentinel quorum (2 Sentinels total, requiring 1 to trigger failover) on an even split caused dual-primary split-brain. Fix: always run an odd number of Sentinels (3 or 5) with quorum set to majority.

## 10. When To Use vs. When To Avoid

### Use Redis When

**✅ Sub-millisecond read latency is required** — leaderboards, session lookups, feature flags, real-time presence, autocomplete. If your p99 latency budget is < 5 ms, Redis is almost always the right cache layer.

**✅ You need server-side data structure operations** — rate limiting with sorted sets (sliding window), cardinality estimation with HyperLogLog, fan-out notifications with pub/sub, time-series aggregation with streams. These eliminate network round-trips that would be required if you fetched data, computed on the client, and wrote back.

**✅ Distributed coordination between stateless application servers** — distributed locks, idempotency keys, leader election. Redis provides the shared mutable state that makes stateless horizontal scaling possible.

**✅ Cache with complex invalidation patterns** — Redis's pub/sub or keyspace notifications let you build sophisticated invalidation without polling. One service publishes `user:42:updated`, subscribers delete relevant cache keys atomically.

**✅ You need persistence with cache semantics** — sessions, OAuth tokens, short-lived compute results that must survive pod restarts. AOF gives you durability; TTLs give you automatic cleanup.

---

### Do NOT Use Redis When

**❌ Your dataset exceeds available RAM** — Redis is memory-bound. Storing 10 TB of data in Redis costs $300,000+/month on cloud. Use a disk-based store (PostgreSQL, DynamoDB, Cassandra) and cache the hot working set (typically 20% of data serves 80% of reads — Pareto principle holds here empirically).

**❌ You need ACID transactions with complex queries** — Redis transactions (`MULTI`/`EXEC`) are optimistic and only batch commands without conditional branching. You cannot express "transfer $100 from account A to B if A has sufficient balance" safely without Lua scripting. Use a relational database for financial data integrity.

**❌ You need rich query capabilities** — Redis has no secondary indexes, no joins, no aggregation pipeline. You can build these manually with sorted sets and hashes, but the complexity is not worth it. Use PostgreSQL, Elasticsearch, or MongoDB depending on your query pattern.

**❌ You need strong consistency across replicas** — Redis replication is async. For distributed locks with strong consistency guarantees, consider etcd (Raft consensus) or Zookeeper. Redlock is probabilistic, not provably correct in all partition scenarios (Martin Kleppmann's Redlock critique is worth reading before using Redis for distributed locking in safety-critical systems).

---

### ⚠️ The #1 Mistake: Treating Redis as a Database, Not a Cache

Engineers architect systems with Redis on the critical read path, set `maxmemory-policy noeviction` (Redis blocks writes when full rather than evicting), and put no persistence strategy in place.

When Redis runs out of memory or restarts (planned or unplanned), the application has no fallback — it errors out completely rather than degrading gracefully to the database. The fix: always design Redis as an acceleration layer with the source of truth in a durable database. Build your read path to handle Redis misses gracefully. Validate your cache-miss path handles 10x normal database load (that's what happens if Redis dies during a traffic spike).

## 11. Interview Perspective

### How the Question Is Phrased

- "Walk me through how Redis works internally."
- "Why is Redis single-threaded but fast?"
- "How would you scale Redis from one server to handle 10M ops/sec?"
- "Design a distributed rate limiter using Redis."
- "What's the difference between Redis Sentinel and Redis Cluster?"
- "How does Redis persistence work, and what are the trade-offs?"
- "What happens when your Redis node runs out of memory?"
- "How would you handle a hot key in Redis?"

### What the Interviewer Is Actually Evaluating

1. **Depth of understanding**: Do you know the event loop, the data structure encoding, or just the commands?
2. **Trade-off articulation**: Can you explain AOF vs. RDB, single-threaded vs. multi-threaded, Sentinel vs. Cluster without hand-waving?
3. **Production experience**: Do you know about hot keys, eviction thrashing, fork memory spikes, and the dangers of `KEYS *`?
4. **System design judgment**: Do you know when NOT to use Redis?

### Junior vs. Senior vs. Staff Answers

**Question: "Why is Redis fast?"**

**Junior Answer:**
"Redis stores data in memory, so it doesn't need to read from disk. Memory access is much faster than disk access."

*Assessment: Correct but surface-level. Knows the what, not the how.*

**Senior Answer:**
"Redis is fast for three reasons. First, it's in-memory — RAM access is ~100 ns vs. SSD at ~100 µs. Second, it's single-threaded, which eliminates lock contention and context-switching overhead. A single thread processing requests serially is faster than multi-threaded lock-contended processing for I/O-bound workloads. Third, its data structures are carefully engineered: SDS strings, listpack for small collections, and skip lists for sorted sets minimize allocations and CPU cache misses. Redis also batches I/O with epoll and RESP protocol parsing is extremely efficient."

*Assessment: Solid. Demonstrates understanding of threading model and data structures.*

**Staff Answer:**
"Redis's performance comes from the intersection of hardware, OS, and algorithmic choices. In-memory storage eliminates storage I/O (100 ns DRAM vs. 100 µs NVMe). The event loop on a single thread means every request gets the full CPU's L1/L2 cache — no cache invalidation from context switching between threads working on different data. RESP protocol is human-readable but trivially parseable in 2–3 pointer increments. Epoll at the OS level means we only wake up when data is available — no busy-waiting.

But the real answer is: Redis is fast because of what it doesn't do. No row locking, no MVCC, no query planning, no B-tree traversal, no WAL fsync per operation by default. When you strip away all relational database machinery, you're left with a hash table in RAM — and that's what Redis is at its core.

I'd also nuance 'fast': Redis is fast for small values. A 10 MB value in a GET command blocks the event loop for milliseconds while it's serialized and written to the socket. Fast is relative — Redis is designed for small, frequent operations. You need to shard large values or use a different tool for bulk data."

*Assessment: Excellent. Understands the hardware model, the negative case (what not doing makes it fast), and the limitations.*

---

**Question: "How would you design a rate limiter with Redis?"**

**Junior Answer:**
"Use a counter with INCR and EXPIRE. Increment on each request, check if it exceeds the limit."

*Assessment: Knows the basic approach but misses the race condition: INCR and EXPIRE are not atomic together. A burst of concurrent requests can all read 0, all INCR to 1, and all succeed before EXPIRE is set.*

**Senior Answer:**
"Use a Lua script for atomicity or a pipeline with INCR + EXPIRE + checking the result. For fixed window: `INCR ratelimit:{user}:{window}`, then `EXPIRE` if it's the first request. For sliding window: sorted set approach — store request timestamps as members with Unix timestamp as score. On each request: ZREMRANGEBYSCORE to remove old entries, ZADD new entry, ZCARD to count, EXPIRE the set. All wrapped in a pipeline or Lua for atomicity."

*Assessment: Correct. Knows the race condition, knows sliding vs. fixed window trade-offs.*

**Staff Answer:**
"Same sliding window sorted set pattern as described above, but I'd go further: what's the trade-off? Sorted sets use O(log N) per ZADD and O(k) per ZREMRANGEBYSCORE where k is removed entries. Under high load (10K req/sec per user), the sorted set for one user's window can have thousands of entries. The memory is bounded (window_seconds * max_rps per user), but ZREMRANGEBYSCORE is O(k + log N), and k can be large.

Alternative: use a token bucket with a hash. `HGETALL ratelimit:{user}` returns `{tokens, last_refill_timestamp}`. A Lua script refills tokens based on elapsed time since last refill, then checks/decrements. This is O(1) per request but requires Lua scripting and clock-dependent logic.

For production at Stripe's scale: I'd use Redis Cluster with rate limit keys sharded by user ID, each node handling ~1K req/sec per key. I'd also add a local in-process token bucket as an L1 check — 99% of non-abusive traffic is cleared locally without touching Redis, only Redis is consulted when the local bucket empties. This reduces Redis load by 10–100x."

*Assessment: Staff-level. Articulates Big-O, memory trade-offs, multi-layer architecture, and real-world scale concerns.*
