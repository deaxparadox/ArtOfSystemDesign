## 1. What Is It? (Theory)

### Plain English

Authentication answers: **"Who are you?"**
Authorization answers: **"What are you allowed to do?"**

At a startup with 1,000 users, you can get away with a username + password stored in a database and a server-side session cookie. At 10 million users across mobile apps, SPAs, third-party integrations, and microservices — that model collapses. You need a **federated, token-based, standards-driven identity system** that works across trust boundaries without sharing passwords.

**OAuth 2.0** (RFC 6749) is a **delegation protocol** — it allows one application to act on behalf of a user without exposing that user's credentials. It answers: "App B wants to access my Google Calendar. Can it, and how much of it?"

**OpenID Connect (OIDC)** is an identity layer built on top of OAuth 2.0. It adds the concept of **who the user is**, not just what they're allowed to do. OIDC introduces the `id_token` — a signed JWT containing user identity claims (name, email, sub).

**JSON Web Tokens (JWT)** (RFC 7519) are the **currency** of the modern auth ecosystem. A JWT is a compact, cryptographically-signed assertion that carries claims about a subject. It enables **stateless verification** — any service holding the public key can verify a token without calling back to the auth server.

### The Threat This Addresses at Scale

Without a proper auth framework, at scale you face:
- **Password sprawl**: Users re-use credentials across services, one breach cascades everywhere
- **Credential stuffing at scale**: Attackers run automated password sprays against millions of accounts; in 2023, credential stuffing attacks represented ~40% of all login traffic on large consumer platforms
- **Delegation without exposure**: Third-party integrations need access without getting the user's password
- **Cross-service identity**: 50+ microservices each authenticating independently creates 50 attack surfaces

### The Real-World Analogy

OAuth 2.0 is like a **hotel key card system**. When you check in (authenticate with the Identity Provider), the front desk gives you a key card (access token). This key card opens your room (resource server) but not the manager's office. You didn't give the hotel your house keys — you got a limited-time, scoped credential. If you lose the key card, the hotel revokes it without changing the locks on your house.

OIDC extends this: the key card now also has your photo and name printed on it (identity claims), so the staff can verify who you are, not just that you have a valid card.

JWT is the key card format itself — a standard, tamper-evident card that any reader can verify by checking the cryptographic signature without calling the front desk.

### Concrete Example: The CircleCI Incident (January 2023)

In December 2022, malware was deployed on a CircleCI engineer's laptop. Because the engineer had 2FA-backed SSO sessions, the attacker stole the **session token** directly from the machine — bypassing 2FA entirely. The attacker used this to access CircleCI's production infrastructure, exfiltrate customer environment variables, secrets, and **GitHub OAuth tokens**.

CircleCI had to rotate all customer GitHub OAuth tokens on December 31, 2022, and notify thousands of customers. The lesson: OAuth tokens are high-value targets. Token storage security, rotation, and revocation are not optional.

**Impact**: Downstream supply chain compromise at potentially hundreds of organizations. Demonstrates that even with OAuth/2FA in place, token lifecycle management is a critical attack surface.

## 2. How It Actually Works (Deep Mechanics)

### 2.1 The JWT Structure

A JWT has three Base64URL-encoded parts separated by dots:

```
Header.Payload.Signature
```

**Header** (algorithm + token type):
```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2024-signing-key-v3"
}
```

**Payload** (claims):
```json
{
  "iss": "https://auth.example.com",
  "sub": "user_01HQ7ZXKB9",
  "aud": "api.example.com",
  "exp": 1735689600,
  "iat": 1735686000,
  "nbf": 1735686000,
  "scope": "read:orders write:cart",
  "email": "alice@example.com",
  "org_id": "org_acme_corp"
}
```

**Signature** (RS256 example):
```
RSA_SIGN(
  SHA256(Base64URL(header) + "." + Base64URL(payload)),
  private_key
)
```

A typical RS256 JWT is **~500–900 bytes**. An ES256 JWT is slightly smaller (~450–700 bytes) due to shorter ECDSA signatures.

### 2.2 OAuth 2.0 Authorization Code Flow with PKCE

This is the **only flow you should use** for user-facing applications (mobile, SPA, server-side web). The Implicit Flow is deprecated (RFC 9700).

```
Client (Browser/App)          Authorization Server          Resource Server
      |                               |                           |
      |---(1) Generate random---------+                           |
      |    code_verifier (43-128      |                           |
      |    chars, cryptographically   |                           |
      |    random)                    |                           |
      |                               |                           |
      |    code_challenge =           |                           |
      |    BASE64URL(SHA256(          |                           |
      |      code_verifier))          |                           |
      |                               |                           |
      |---(2) GET /authorize?---------►                           |
      |    response_type=code         |                           |
      |    client_id=abc123           |                           |
      |    redirect_uri=https://...   |                           |
      |    scope=openid profile email |                           |
      |    state=<random-csrf-token>  |                           |
      |    code_challenge=<hash>      |                           |
      |    code_challenge_method=S256 |                           |
      |                               |                           |
      |       (User logs in, consents)|                           |
      |                               |                           |
      |◄--(3) 302 redirect to----------                           |
      |    redirect_uri?              |                           |
      |    code=AUTH_CODE_XYZ         |                           |
      |    state=<random-csrf-token>  |                           |
      |                               |                           |
      |---(4) Validate state matches  |                           |
      |    original (CSRF check)      |                           |
      |                               |                           |
      |---(5) POST /token--------------►                          |
      |    grant_type=authorization_code                          |
      |    code=AUTH_CODE_XYZ         |                           |
      |    redirect_uri=https://...   |                           |
      |    client_id=abc123           |                           |
      |    code_verifier=<original>   |                           |
      |                               |                           |
      |    Server computes:           |                           |
      |    SHA256(code_verifier) ==   |                           |
      |      code_challenge? YES      |                           |
      |                               |                           |
      |◄--(6) {access_token,----------                            |
      |    refresh_token, id_token,   |                           |
      |    expires_in: 300}           |                           |
      |                               |                           |
      |---(7) GET /api/orders---------+---------------------------►
      |    Authorization: Bearer      |                           |
      |    <access_token>             |                           |
      |                               |                           |
      |                               |       Verify JWT sig,     |
      |                               |       exp, aud, iss       |
      |                               |       using cached JWKS   |
      |◄--(8) 200 OK orders data------+---------------------------
```

**Why PKCE protects against code injection**: Even if an attacker intercepts the authorization code (via a malicious redirect or referrer header leak), they cannot exchange it for tokens because they don't know the `code_verifier` that was only ever in the client's memory.

### 2.3 Token Refresh Flow

```
Client                    Authorization Server
  |                               |
  |--POST /token------------------►
  |  grant_type=refresh_token     |
  |  refresh_token=<RT>           |
  |  client_id=abc123             |
  |                               |
  |  Server: validate RT,         |
  |  check not revoked,           |
  |  ROTATE: invalidate old RT    |
  |                               |
  |◄-{access_token (new),----------
  |   refresh_token (new),        |
  |   expires_in: 300}            |
  |                               |
  |  [Old refresh token is now    |
  |   dead. Replay = 401]         |
```

**Refresh token rotation** (RFC 6749 + OAuth Security BCP) ensures that if a refresh token is stolen, using the old one triggers detection when the legitimate client tries to use it next.

### 2.4 OIDC Discovery & JWKS

OIDC mandates a well-known discovery endpoint:

```
GET https://auth.example.com/.well-known/openid-configuration

Response:
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "userinfo_endpoint": "https://auth.example.com/userinfo",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "id_token_signing_alg_values_supported": ["RS256", "ES256"],
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"]
}
```

The JWKS (JSON Web Key Set) endpoint provides public keys for token verification:

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "2024-signing-key-v3",
      "alg": "RS256",
      "n": "0vx7agoebGcQSuuPiLJXZptN9nndrQmbXEps2aiAFbWhM...",
      "e": "AQAB"
    }
  ]
}
```

Resource servers **cache** the JWKS (typically with a 1-hour TTL) to avoid a round-trip on every request. Key rotation is zero-downtime: add the new key to the JWKS, wait for cache TTL to expire, then remove the old key.

### 2.5 Cryptographic Primitives

| Algorithm | Type | Key Size | Signature Size | Use Case |
|-----------|------|----------|----------------|----------|
| HS256 | HMAC-SHA256 | 256-bit shared secret | 32 bytes | Single-service, shared secret |
| RS256 | RSA-PKCS1v1.5 + SHA256 | 2048-bit RSA | 256 bytes | Standard public-key JWT |
| RS512 | RSA-PKCS1v1.5 + SHA512 | 2048-bit RSA | 256 bytes | Higher security hash |
| ES256 | ECDSA + P-256 + SHA256 | 256-bit EC | 64 bytes | Preferred: smaller, fast |
| PS256 | RSA-PSS + SHA256 | 2048-bit RSA | 256 bytes | More secure than RS256 |
| EdDSA | Ed25519 | 256-bit | 64 bytes | Modern, fastest |

**Staff-level recommendation**: Use **ES256 (P-256)** or **EdDSA (Ed25519)** for new systems. RS256 is legacy and produces 4x larger signatures than ES256 for equivalent security.

### 2.6 JWT Validation Algorithm — Every Request

A resource server MUST perform all these checks, in order:

```
1. Parse JWT structure (3 parts, Base64URL decode)
2. Read alg from header — WHITELIST CHECK (reject if not in ["ES256", "RS256"])
   → REJECT "none", REJECT HS* for public APIs
3. Look up kid in cached JWKS → fetch JWKS if kid unknown
4. Verify cryptographic signature using public key
5. Check exp > now (reject expired tokens)
6. Check nbf <= now (not yet valid)
7. Check iss == expected issuer (exact string match)
8. Check aud contains this service's audience
9. Check required claims present (sub, scope)
10. Check scope contains required permission for this endpoint
→ Only then: trust the claims and process the request
```

### 2.7 Misconceptions

**❌ Misconception: "JWT tokens are encrypted, so they're safe to store sensitive data in"**
✅ Reality: JWTs are signed, not encrypted by default. The payload is Base64URL-encoded — anyone who has the token can read all claims. Use JWE (JSON Web Encryption) if you need encryption, or keep sensitive data out of tokens entirely.

**❌ Misconception: "Stateless JWTs cannot be revoked, so I don't need a revocation mechanism"**
✅ Reality: Short-lived tokens (5-15 min) minimize the revocation window. For true revocation (user logout, compromised token), maintain a token deny-list (Redis with TTL matching token expiry) or use short access tokens + refresh token rotation.

**❌ Misconception: "HTTPS means my tokens are safe in localStorage"**
✅ Reality: XSS attacks bypass HTTPS entirely. Any JavaScript on the page — including third-party scripts — can read localStorage. Use HttpOnly cookies (inaccessible to JavaScript) for refresh tokens.

**❌ Misconception: "OAuth 2.0 handles authentication"**
✅ Reality: OAuth 2.0 is an authorization protocol. It tells you what a client can do, not who the user is. OIDC (built on OAuth 2.0) handles authentication via the `id_token` and the `sub` claim.

## 3. Real-World Architecture Examples

### 3.1 Netflix — Edge Authentication with Token-Agnostic Identity Propagation

Netflix serves 250+ million subscribers across thousands of device types (smart TVs, iOS, Android, browsers, game consoles), each using different authentication token formats. Their 2021 blog post describes one of the most sophisticated auth architectures in the industry.

**The Problem**: Different device types sent different token types (session tokens, OAuth tokens, device certificates). Each downstream microservice had to understand and validate every token format — creating N×M complexity across 500+ microservices.

**The Solution**: Netflix built an **Edge Authentication Service (EAS)** that terminates all external token types at the API gateway (Zuul). The EAS validates the incoming token (whatever format the device uses) and generates an internal **"Passport"** — a cryptographically-signed, token-agnostic identity object. Every internal microservice only deals with Passport objects.

```
Device (TV/Mobile/Browser)         Netflix Edge
  [OAuth token / Session /] ------► Zuul Gateway
  [Device Certificate      ]        │
                                     ▼
                              Edge Auth Service (EAS)
                              - Validate external token
                              - Resolve user/device identity
                              - Generate internal Passport
                              - Sign with internal key
                                     │
                              ┌──────▼──────────────────┐
                              │  Internal Microservices  │
                              │  All receive Passport    │
                              │  (uniform identity obj)  │
                              │  Never see external token│
                              └──────────────────────────┘
```

**Key Security Decision**: External tokens never traverse past the edge boundary. A compromised internal service cannot leak external tokens.

**Outcome**: Reduced token-handling complexity for service owners, centralized revocation, improved audit trails, and a single team responsible for auth security rather than 500+ teams each independently validating tokens.

### 3.2 Dropbox — The 2022 GitHub OAuth Token Compromise

In November 2022, a threat actor sent a phishing email impersonating CircleCI (Dropbox used CircleCI for CI/CD). The phishing page harvested Dropbox's GitHub credentials. The attacker then used these to access Dropbox's GitHub organization and clone **130 private source code repositories**.

**What the attacker found**: Plain-text secrets committed to code — including API keys and OAuth tokens.

**The cascade**:
1. CI/CD compromise → GitHub credentials stolen
2. Source code cloned → API keys and secrets found in code
3. Those secrets granted further access

**Dropbox's response and post-breach improvements**:
- Enforced hardware security keys (FIDO2/WebAuthn) for all internal systems
- Mandatory secret scanning in all repositories (preventing future hardcoded credentials)
- Enhanced phishing-resistant MFA replacing software TOTP

**Lesson**: OAuth tokens in source code repositories are catastrophic. Secret scanning and never-committing-credentials rules are security-critical, not just good hygiene. In 2024, Dropbox Sign suffered a separate breach where hashed passwords, MFA details, API keys, and OAuth tokens were stolen from a compromised service account.

### 3.3 CircleCI — January 2023: Malware-Mediated Session Token Theft

CircleCI's incident report (January 4, 2023) is a masterclass in how sophisticated attackers bypass OAuth and 2FA through session hijacking.

**Attack vector**: Malware deployed on a CircleCI engineer's laptop. The engineer had a valid, 2FA-backed GitHub SSO session. Malware extracted the **session token directly from the browser's session storage** — a token that had already passed 2FA authentication.

**What was compromised**: Customer environment variables (CI/CD secrets), OAuth tokens customers had granted CircleCI access to, and API keys.

**Impact**: CircleCI rotated all customer GitHub OAuth tokens on December 31, 2022. Thousands of customers had to rotate every secret stored in CircleCI.

**Key insight**: 2FA protects the login event, not the resulting session. Once a session token is issued, it's just bytes in memory/storage. Device compromise bypasses the entire OAuth/OIDC flow. This is why **short-lived tokens** and **continuous device health checks** (ZTA) matter more than just having OAuth.

**What CircleCI changed**:
- Enhanced endpoint detection and response (EDR) on all developer machines
- Reduced token TTLs
- Added anomaly detection for unusual access patterns on OAuth tokens

### 3.4 GitHub — OAuth App Token Scoping and the Heroku/Travis CI Incident (April 2022)

An attacker obtained a stolen OAuth user token from Heroku and Travis CI's integration with GitHub. GitHub investigates this as part of its security incident response, affecting GitHub's npm infrastructure.

**Attack**: The attacker used the stolen OAuth token to clone private repositories from dozens of organizations that had Heroku or Travis CI OAuth apps authorized.

**GitHub's response**:
- Revoked the compromised OAuth tokens immediately on discovery
- Notified affected organizations within 72 hours
- Enhanced OAuth app token audit logging

**Lesson**: Third-party OAuth app authorizations are a persistent risk. Every OAuth app you grant access to is a potential lateral movement path. Principle of least privilege in OAuth scopes is critical — a CI integration that only needs `repo:read` should never have `repo:write` or `admin:org`.

### 4.2 Security Questions to Ask Before Designing

1. **Who are your clients?** SPA, mobile, server-to-server, third-party? Each needs different flow (auth code + PKCE for SPA/mobile, client credentials for M2M)
2. **What is your token lifetime strategy?** Access token TTL, refresh token TTL, rotation policy?
3. **Where do tokens live?** HttpOnly cookies vs memory vs localStorage — each has different XSS/CSRF tradeoffs
4. **What is your revocation story?** Short TTL? Deny-list? Token introspection?
5. **Multi-tenancy?** Does your audience (`aud`) claim encode tenant context?
6. **Key rotation?** How do you rotate signing keys without downtime? (Answer: JWKS with kid)
7. **What can a compromised token do?** Scope minimization, resource server segmentation?

### 4.3 How Auth Architecture Evolves

**Startup (0-100K users):**
```
Simple: Username/password → bcrypt/Argon2id hash → Server-side session → Cookie
Auth provider: None (DIY or start with Auth0 free tier)
Biggest mistake: Storing passwords in plaintext or with MD5
```

**Growth (100K-10M users):**
```
Add: OAuth 2.0 for third-party integrations
Add: Social login (Google/GitHub OIDC) to reduce password management
Add: MFA (TOTP) for sensitive accounts
JWT: Start issuing JWTs (RS256 signed, 15-min access tokens)
Key concern: Token storage in SPAs, PKCE everywhere
```

**Scale (10M+ users, microservices):**
```
Add: Dedicated Auth Service (Keycloak, Auth0, custom)
Add: Edge JWT verification (API Gateway validates, services trust)
Add: Token introspection endpoint for real-time revocation
Add: Continuous Access Evaluation Protocol (CAEP/RFC)
Add: Refresh token rotation + detection of reuse attacks
Key concern: JWKS caching strategy, key rotation, deny-list performance
```

**Enterprise (compliance, B2B, regulated):**
```
Add: SAML federation (enterprise SSO) alongside OIDC
Add: Hardware-bound tokens (DPoP — Demonstrating Proof of Possession)
Add: Continuous authentication signals (device health, location anomalies)
Add: Token binding to specific IPs or device fingerprints
Add: SIEM integration for all auth events
```

### 4.4 Decision Points and Trade-offs

| Decision | Option A | Option B | Recommendation |
|----------|----------|----------|----------------|
| Token format | Opaque (random string) | JWT (self-contained) | JWT for distributed, opaque for single-service |
| Signing algorithm | RS256 | ES256 | ES256 — smaller, equally secure |
| Access token TTL | 5 minutes | 1 hour | 5-15 minutes max |
| Refresh token storage | HttpOnly cookie | Encrypted DB + session | HttpOnly cookie for web, encrypted DB for mobile |
| Token revocation | Short TTL only | Deny-list in Redis | Both: short TTL + deny-list for critical ops |
| PKCE | Optional | Mandatory | Mandatory for all clients (RFC 9700) |

## 5. Code / Implementation Perspective

### 5.1 JWT Validation — Python (FastAPI)

```python
import time
import httpx
from functools import lru_cache
from typing import Optional
from fastapi import HTTPException, Security, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt  # PyJWT >= 2.0
from jwt import PyJWKClient

ISSUER = "https://auth.example.com"
AUDIENCE = "api.example.com"
JWKS_URI = f"{ISSUER}/.well-known/jwks.json"
ALLOWED_ALGORITHMS = ["RS256", "ES256"]  # Explicit whitelist, never "none"

# PyJWT's PyJWKClient handles key caching and rotation automatically
# It fetches JWKS on first call, caches with TTL, auto-rotates on unknown kid
jwks_client = PyJWKClient(JWKS_URI, cache_jwk_set=True, lifespan=3600)

security = HTTPBearer()

def verify_token(
    credentials: HTTPAuthorizationCredentials = Security(security),
) -> dict:
    token = credentials.credentials

    try:
        # Step 1: Decode header without verification to get kid + alg
        # DO NOT trust yet — this is just to select the right key
        unverified_header = jwt.get_unverified_header(token)

        # Step 2: Explicit algorithm whitelist check BEFORE verification
        alg = unverified_header.get("alg", "")
        if alg not in ALLOWED_ALGORITHMS:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail=f"Algorithm '{alg}' is not permitted",
            )

        # Step 3: Fetch signing key from JWKS (cached, keyed by kid)
        signing_key = jwks_client.get_signing_key_from_jwt(token)

        # Step 4: Full verification — signature, exp, nbf, iss, aud
        payload = jwt.decode(
            token,
            signing_key.key,
            algorithms=ALLOWED_ALGORITHMS,  # Whitelist enforced here too
            audience=AUDIENCE,
            issuer=ISSUER,
            options={
                "require": ["exp", "iat", "iss", "aud", "sub"],
                "verify_exp": True,
                "verify_nbf": True,
                "verify_iss": True,
                "verify_aud": True,
            },
            leeway=30,  # 30-second clock skew tolerance only
        )

        # Step 5: Check token is not in deny-list (for revocation support)
        jti = payload.get("jti")
        if jti and is_token_revoked(jti):
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Token has been revoked",
            )

        return payload

    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expired")
    except jwt.InvalidAudienceError:
        raise HTTPException(status_code=401, detail="Invalid audience")
    except jwt.InvalidIssuerError:
        raise HTTPException(status_code=401, detail="Invalid issuer")
    except jwt.PyJWTError as e:
        raise HTTPException(status_code=401, detail=f"Invalid token: {e}")


def require_scope(required_scope: str):
    """Dependency factory for scope-based authorization."""
    def scope_checker(payload: dict = Security(verify_token)) -> dict:
        token_scopes = payload.get("scope", "").split()
        if required_scope not in token_scopes:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"Missing required scope: {required_scope}",
            )
        return payload
    return scope_checker


def is_token_revoked(jti: str) -> bool:
    """Check Redis deny-list. TTL matches token expiry."""
    import redis
    r = redis.Redis(host="redis", port=6379, db=1)
    return r.exists(f"revoked:jti:{jti}") > 0


# Usage in FastAPI route:
# @app.get("/orders")
# def list_orders(claims = Security(require_scope("read:orders"))):
#     user_id = claims["sub"]
#     ...
```

### 5.2 PKCE Flow — Client Side (Language-Agnostic Pattern)

```python
import os, hashlib, base64, secrets

def generate_pkce_pair() -> tuple[str, str]:
    """Generate code_verifier and code_challenge for PKCE."""
    # RFC 7636: 43-128 chars from [A-Za-z0-9._~-]
    code_verifier = base64.urlsafe_b64encode(
        os.urandom(32)
    ).rstrip(b"=").decode("ascii")

    # S256 method: SHA256(verifier), then Base64URL-encode without padding
    digest = hashlib.sha256(code_verifier.encode("ascii")).digest()
    code_challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")

    return code_verifier, code_challenge

def generate_state() -> str:
    """CSRF protection token — must be validated on callback."""
    return secrets.token_urlsafe(32)
```

### 5.3 Nginx JWT Validation Configuration

```nginx
# Using nginx-plus or lua-resty-jwt for edge JWT verification
# Example: OpenResty / nginx with lua-jwt validation

location /api/ {
    # Enforce HTTPS
    if ($scheme != "https") {
        return 301 https://$host$request_uri;
    }

    # Pass to auth_request subrequest for JWT validation
    auth_request /auth/verify;
    auth_request_set $auth_sub $upstream_http_x_auth_sub;

    # Forward verified identity to upstream
    proxy_set_header X-Auth-Sub $auth_sub;
    proxy_set_header X-Auth-Scope $auth_scope;

}

}
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **OAuth2 + OIDC + JWT** (stateless) | Distributed systems, microservices, SPAs, mobile | No instant revocation without deny-list; tokens leak to anyone who has them | Google, Stripe, GitHub, Auth0 |
| **Opaque tokens + introspection** | High-security contexts needing instant revocation | Every request requires a network call to introspect endpoint (latency cost ~5-20ms) | Internal bank APIs, healthcare |
| **Server-side sessions + cookies** | Simple monoliths, low-scale, admin tools | Sticky sessions or Redis required; doesn't scale across origins; CSRF risk | Classic Rails/Django apps |
| **SAML 2.0** | Enterprise B2B SSO, legacy enterprise IdPs | XML bloat (~15KB vs ~500B JWT); complex spec; no mobile support | Enterprise (Salesforce, Workday) |
| **mTLS (mutual TLS)** | Service-to-service (M2M) only, zero-trust | Certificate management overhead; not suitable for user-facing auth | Netflix internal, Google BeyondCorp |
| **API Keys** | Simple integrations, webhooks, M2M without user context | No expiry by default; no standard revocation; coarse-grained | Stripe, Twilio, AWS (long-term) |
| **WebAuthn/Passkeys** | Passwordless user auth (complements OAuth) | New UX paradigm; device-bound; limited enterprise federation | Apple, Google, GitHub (2023+) |

### Opinionated Recommendation

For new systems in 2025+:
- **User-facing web/mobile**: Authorization Code + PKCE → JWT access tokens (ES256, 15-min TTL) → HttpOnly cookie refresh tokens with rotation. Use Auth0 or Keycloak rather than rolling your own.
- **Service-to-service (M2M)**: Client Credentials grant → short-lived JWT. Consider mTLS for highest-trust internal paths.
- **Enterprise B2B**: OIDC as the primary standard; SAML federation only when the customer's IdP literally cannot do OIDC (legacy AD FS setups). Avoid SAML for greenfield.
- **Never**: Implicit flow (deprecated), `alg: none`, passwords in query parameters, tokens in URLs.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Stateless verification at scale**: A 500-byte JWT can be verified by any service in ~1ms using a cached public key. Compare this to a session lookup in Redis at ~1-5ms per request. At 100K RPS across 50 services, the difference is millions of Redis calls per second avoided.
- **Cross-domain and cross-service identity**: JWTs work across different origins, services, and infrastructure. Bearer tokens in Authorization headers bypass Same-Origin Policy restrictions that cookies have.
- **Delegated authorization model**: OAuth scopes allow precise permission delegation. A user can grant "read:contacts" without granting "write:contacts" — impossible with a shared password.
- **Ecosystem maturity**: OAuth 2.0 (2012) and OIDC (2014) are universally supported. Every major cloud, every framework, every language has a library. The protocol risk is essentially zero.
- **Audit trail and traceability**: JWT claims (`sub`, `jti`, `iat`, `scope`) provide built-in audit context for every request without additional lookups.

### Costs & Limitations

- **No built-in revocation**: A stolen JWT is valid until expiry. A 1-hour access token stolen in a breach is useful to an attacker for 59 more minutes. This is the fundamental tension of stateless tokens.
- **Token size overhead**: Every HTTP request carries 500-900 bytes of JWT in the Authorization header. At 100K RPS, that's 50-90 MB/s of token data in headers alone. With HTTP/2 header compression, this is less painful, but it's non-zero.
- **Clock skew**: JWT expiry (`exp`) is time-based. Services with misconfigured system clocks will incorrectly reject or accept tokens. Require NTP synchronization and allow only 30-60 seconds of leeway.
- **Spec complexity**: OAuth 2.0 is a framework, not a protocol — it specifies extension points and leaves details to implementers. This has led to a proliferation of flows, grant types, and extensions (PKCE, DPoP, PAR, JAR). Getting OAuth right is genuinely hard; library bugs are frequent.
- **Key management overhead**: Asymmetric key signing requires key generation, storage, rotation, and JWKS publication. Rotate too rarely and a compromise is long-lived; rotate too often and you break cached JWKS lookups.

### Core Tension

**Security vs. Usability**: Short-lived tokens maximize security but require frequent refresh operations, adding latency and complexity. Long-lived tokens improve UX but maximize attacker utility on compromise. The industry has converged on: **15-minute access tokens + 90-day rotating refresh tokens** as a reasonable balance for consumer apps.

**Stateless vs. Revocability**: Pure stateless JWTs (no deny-list) can't be revoked before expiry. Pure opaque tokens (full revocation) require a network call per request. The practical solution is hybrid: stateless JWTs with a deny-list checked on sensitive operations and on refresh.

### My Recommendation

**Use short-lived ES256 JWTs (10-15 minute TTL) for access tokens, never store them in localStorage.** For SPAs: keep access tokens in memory only, use HttpOnly cookies for refresh tokens with `SameSite=Strict` and `Secure` flags. Implement refresh token rotation and monitor for reuse attacks. Deploy JWKS caching at the API gateway level with a 1-hour TTL and automated cache invalidation on key rotation events. This gives you 95% of the performance benefits of stateless auth while limiting breach impact to a 15-minute window.

## 9. Failure Modes — What Goes Wrong

### 9.1 Algorithm Confusion Attack (CVE-2024-54150)

**Trigger:** A JWT library that does not explicitly whitelist accepted algorithms. An attacker modifies the JWT header from `"alg": "RS256"` to `"alg": "HS256"`, then signs the forged token using the server's **public key** (which is public) as the HMAC secret. The server, seeing `HS256` in the header, validates the HMAC signature using what it thinks is its shared secret — but is actually the public key. Signature validates. Attacker is now authenticated as any user.

**Symptoms:** Unauthorized API access; requests succeeding with crafted tokens; no login events in auth logs.

**Detection:**
- Monitor for JWTs with `alg` values not in your approved list
- Log and alert on any `alg: none` attempt (these should never occur in production)
- WAF rules: reject any JWT where header `alg` is not RS256 or ES256
- Regular pen testing of auth endpoints

**Recovery:**
1. Immediately invalidate all outstanding tokens (emergency key rotation)
2. Deploy patched library with explicit algorithm whitelist
3. Audit all auth events in the window of vulnerability for unauthorized access
4. Notify affected users if PII was accessed

**Real Example:** CVE-2024-54150 in the pac4j-jwt library allowed JWT authentication bypass via JWE processing path manipulation. The vulnerability allowed attackers to impersonate arbitrary users. CVSS score: Critical.

---

### 9.2 Refresh Token Reuse (Replay Attack)

**Trigger:** A refresh token is stolen (via XSS, device compromise, or MITM on an insecure channel). The attacker uses it to obtain a new access token. If the server uses **non-rotating** refresh tokens, the attacker now has indefinite access until the legitimate user logs out.

Even with rotation, if the stolen token is used before the legitimate client uses it, the legitimate client gets a revoked-token error — but may silently fall back to re-authentication, making the attack invisible.

**Symptoms:**
- User reports "random logouts" (legitimate client's RT was revoked after attacker used it first)
- Login spikes from unusual geographic locations on the same account
- Two concurrent active sessions for the same user from different IPs

**Detection:**
- Implement **refresh token family tracking**: group all tokens in a chain. If a revoked token in the family is replayed, immediately revoke the entire family.
- Alert on RT use from geographically impossible locations (same user, London → Singapore in 10 minutes)
- Log all RT issuances and uses with IP and user-agent

**Recovery:**
1. Invalidate entire token family on detected reuse
2. Force user re-authentication (MFA)
3. Notify user of suspicious activity
4. Investigate source of token theft

**Real Example:** The CircleCI January 2023 incident. Stolen GitHub OAuth tokens were used by attackers to access customer repositories. CircleCI rotated all GitHub OAuth tokens to remediate. The reuse was only detectable because GitHub noticed anomalous access patterns.

---

### 9.3 Token Stored in Insecure Location (XSS to Token Theft)

**Trigger:** Access token or refresh token stored in `localStorage` or `sessionStorage`. An XSS vulnerability anywhere on the application — including third-party analytics scripts, ad networks, or CDN-hosted libraries — can execute `localStorage.getItem('access_token')` and exfiltrate it.

**Symptoms:**
- Attacker uses stolen token from a different IP/user-agent
- API requests made at unusual times with the victim's identity
- No evidence of credential compromise (user's password is fine)

**Detection:**
- Content Security Policy (CSP) violations in your CSP reporting endpoint
- Token usage from IPs/user-agents inconsistent with the user's history
- Subresource Integrity (SRI) failures for CDN-hosted scripts

**Recovery:**
1. Revoke compromised tokens immediately
2. Fix the XSS vulnerability (not just the token storage)
3. Migrate tokens to HttpOnly cookies before re-enabling

**Prevention:**
```http
Set-Cookie: refresh_token=<token>; HttpOnly; Secure; SameSite=Strict; Path=/auth/token; Max-Age=7776000
```
HttpOnly cookies cannot be read by JavaScript — any JavaScript. Not even your own.

**Real Example:** The 2024 Dropbox Sign breach included exfiltration of OAuth tokens from a compromised service account. While this was a server-side compromise rather than XSS, the pattern of token exfiltration and subsequent impersonation is identical.

---

### 9.4 JWKS Cache Poisoning / Key Confusion

**Trigger:** A resource service fetches JWKS from a URL specified in the JWT header (`jku` claim) rather than from a hardcoded trusted JWKS URI. An attacker creates their own JWKS endpoint, hosts a key pair they control, and sets `jku` in the JWT header to point to their endpoint. The server fetches the attacker's keys, validates the signature (which is valid against the attacker's key), and accepts the forged token.

**Symptoms:** Authentication bypass with no corresponding login event at the real IdP.

**Detection:**
- Never trust `jku`, `x5u`, or `jwks_uri` claims in JWT headers
- JWKS URI must be configured server-side, never derived from the token

**Recovery:**
1. Deploy fix: ignore `jku` header claim, use only configured JWKS URI
2. Revoke all tokens; force re-authentication
3. Audit all requests that may have been authenticated using forged tokens

**Real Example:** This class of attack (JWKS injection / `jku` header injection) is documented in multiple CVEs against JWT libraries and has been demonstrated against enterprise auth systems including some cloud-hosted identity services.

## 10. When To Use vs. When To Avoid

### Use When

**✅ Distributed systems with multiple services**: When 10+ microservices all need to verify caller identity, stateless JWTs eliminate the need for every service to call a central auth service per request. The public key is cached; verification is local.

**✅ Third-party integrations and API platforms**: When you need to let external developers build applications that access your users' data on their behalf (GitHub Apps, Stripe Connect, Google Workspace Marketplace), OAuth 2.0 is the only sane answer. Alternatives (API keys, passwords) don't support scoped delegation.

**✅ Mobile applications**: Mobile apps cannot store a client secret securely (it's in the binary). Authorization Code + PKCE was designed specifically for this. Confidential clients (server-side) use the same flow with the addition of a client secret.

**✅ Cross-domain / cross-origin scenarios**: JWTs in Authorization headers work across origins. Cookies are Same-Origin by default. For a SPA on `app.example.com` calling `api.example.com`, bearer tokens are cleaner than CORS-complicated cookie sharing.

### Do NOT Use When (Anti-Patterns)

**❌ Short-lived internal microservice calls where a service mesh is deployed**: If you have Istio or Linkerd with mTLS, service-to-service calls are already authenticated by the mesh. Adding JWT verification is redundant overhead. Use mTLS for M2M authentication and JWT only for user-context propagation.

**❌ Simple monolith with no cross-origin requirements**: A traditional server-rendered Rails app with one domain doesn't need OAuth. Server-side sessions + secure cookies are simpler, more battle-tested, and have fewer security foot-guns.

**❌ When you cannot implement proper key management**: If your team cannot reliably rotate keys, monitor JWKS endpoints, and maintain a deny-list, the operational complexity of JWT auth will create vulnerabilities. Start with opaque tokens + introspection (simpler mental model, instant revocation) until your security posture matures.

### The #1 Security Mistake Engineers Make

**Storing tokens in localStorage and using long-lived access tokens.**

This is the single most common OAuth/JWT mistake in production applications. Engineers see LocalStorage as "simple" and set 24-hour access token TTLs because "it reduces API calls." The result: any XSS vulnerability — including from a third-party script you don't control — can steal a token that's valid for 24 hours.

The correct architecture: **access token lives only in JavaScript memory (a module-scoped variable), refresh token lives in an HttpOnly cookie**. Yes, this means the token is lost on page refresh — that's what the refresh flow is for. Silent token renewal using an iframe (or a background fetch) on page load retrieves a new access token using the HttpOnly cookie refresh token, invisibly to the user.

## 11. Interview Perspective

### How This Shows Up in Interviews

**System Design**: "Design an authentication system for a platform with 50M users." You'll need to articulate token types, flows, storage, revocation, and how auth integrates with your API gateway and microservices.

**Security Design**: "How would you prevent token theft in a SPA?" — tests your depth on XSS, CSRF, storage options, and CSP.

**Debugging**: "A user reports they're getting logged out every 15 minutes." — tests whether you understand token refresh flows, TTL configuration, and clock skew.

### What the Interviewer Evaluates

- Do you know the difference between authentication and authorization?
- Can you explain PKCE and why it replaces the implicit flow?
- Do you understand why short TTLs matter (revocation window)?
- Can you articulate the XSS vs. CSRF trade-off (localStorage vs. cookies)?
- Do you know which algorithm to use and why (ES256 vs RS256)?
- Do you think about failure modes (stolen tokens, compromised secrets)?

### Questions You Ask Before Answering

1. "What kind of clients do we have — SPA, mobile, server-side, third-party integrations?"
2. "Do we have compliance requirements (HIPAA, PCI-DSS) that mandate specific revocation guarantees?"
3. "Are we building for consumers or enterprises? Enterprise usually requires SAML federation."
4. "Do we need fine-grained authorization (ABAC) or is role/scope-based sufficient?"
5. "What's the acceptable security vs. UX trade-off on session length?"

### Answer Level Benchmarks

**Junior (L3-L4):**
> "OAuth 2.0 is for authorization, OIDC adds authentication. JWT is a token format with a header, payload, and signature. The authorization code flow is most secure. I'd use RS256 or ES256 to sign tokens. Access tokens should expire in 15 minutes, and refresh tokens handle renewals. I wouldn't store tokens in localStorage because of XSS risks."

**Senior (L5):**
> "I'd implement Auth Code + PKCE for all clients — PKCE is now required even for confidential clients per RFC 9700. Access tokens: ES256-signed JWTs with 10-minute TTL. Refresh tokens: rotating, stored in HttpOnly SameSite=Strict cookies, with family-level revocation on reuse detection. At the API gateway, I'd cache JWKS with a 1-hour TTL and verify ES256 signatures before routing to services. Downstream services trust the gateway's verified token and check audience/scope. For revocation, I maintain a Redis deny-list keyed by JTI with TTL = token expiry. Key rotation is zero-downtime via JWKS kid rotation."

**Staff (L6+):**
> "The interesting problems at scale are: JWKS cache coherence during key rotation (add new key, wait 2× cache TTL before retiring old — typically 2 hours), refresh token reuse detection across multiple app servers (centralized token family state in Redis with atomic CAS operations), and the token storage paradox for SPAs (access token in memory only, refresh in HttpOnly cookie, but this means tokens don't survive page refresh — solved by a synchronous silent renewal on load via the refresh cookie before rendering protected routes). I'd also add DPoP (Demonstrating Proof of Possession) for high-value API endpoints — binds the token to the client's ephemeral key pair so stolen tokens cannot be replayed from a different client. For the revocation story: tokens under 10 minutes don't need deny-listing for most threat models; reserve the deny-list overhead for refresh tokens and elevated-privilege tokens."
