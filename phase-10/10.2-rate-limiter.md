> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Distributed counting across servers, race conditions in Redis, sliding window accuracy vs cost

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

A rate limiter controls how many requests a client or user can send to a service within a defined time window, rejecting excess requests with an HTTP 429 (Too Many Requests) response. It protects backend services from abuse, DoS attacks, and unintentional thundering herds while enforcing fair usage across tenants.

At real scale: Stripe processes ~100 million API calls/day; Cloudflare enforces rate limits across 250+ PoPs for millions of customer domains; Twitter's API enforces per-app and per-user limits across hundreds of billions of requests per month.

---

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Enforce per-client limits** — reject requests exceeding N calls per time window (e.g., 1,000 req/min per API key).
2. **Multiple limit dimensions** — support limiting by user ID, IP address, API key, endpoint, and tenant.
3. **Multiple time granularities** — support second, minute, hour, and day windows simultaneously.
4. **Informative rejection** — return 429 with `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers.
5. **Configurable rules** — allow operators to define and hot-reload limit rules without a service restart.
6. **Distributed enforcement** — limits must be consistent across all API server replicas (not per-instance).

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% (52 min downtime/year) |
| Latency added | p99 < 5 ms on the hot path |
| Accuracy | Allow at most 0.1% over-allowance under race conditions |
| Throughput | Handle 500,000 rate-check RPS at peak |
| Consistency | Strong within a region; eventual cross-region |
| Durability | Counter state survives a single Redis replica failure |

### Out of Scope

- Application-layer DDoS mitigation (handled by WAF / CDN upstream)
- Content-based throttling (e.g., throttling large request bodies)
- Billing metering (similar mechanics but different storage/aggregation requirements)
- Cross-region global counters with strict consistency (covered in Scale section)
- Authentication and authorization

### Clarifying Questions to Ask the Interviewer

1. **"Are we building this as a standalone service, a library, or a sidecar/API-gateway middleware?"**
   — Changes deployment model. Standalone = network hop. Library = no network hop but per-process state. Gateway = single enforcement point.

2. **"Should limits be enforced across all regions simultaneously, or is per-region enforcement acceptable?"**
   — Cross-region strong consistency requires distributed atomic counters (expensive). Per-region is a common, practical trade-off.

3. **"What happens when the rate-limit datastore is unavailable — fail open or fail closed?"**
   — Security-sensitive endpoints (login, payments) should fail closed. General APIs can fail open with local fallback.

4. **"Do we need to support burst allowances above the sustained rate?"**
   — Token bucket allows bursts; leaky bucket doesn't. The answer shapes algorithm choice.

5. **"What is the cardinality of rate-limit keys?"**
   — 10M API keys × 3 dimensions × 5 window granularities = 150M Redis keys. Memory sizing depends on this.

6. **"Is the rate limiter in the read path (synchronous, blocks requests) or write path (async, best-effort)?"**
   — Synchronous is required for hard limits. Async is acceptable for soft limits with retroactive enforcement.

7. **"Do we need to support dynamic rule changes without deploying code?"**
   — If yes, we need a rules configuration service with pub/sub push to rate-limiter nodes.

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

- **Active API clients**: 10 million active API keys
- **Average requests per client per day**: 10,000
- **Peak-to-average ratio**: 5x (traffic spikes during business hours)
- **Number of API server replicas**: 100
- **Number of rate-limit check dimensions per request**: 3 (user, IP, API key)
- **Rate-limit window granularities**: 3 (per-second, per-minute, per-hour)

### QPS Calculations

```
Total daily requests = 10M clients × 10,000 req/day = 100B req/day

Average API request QPS    = 100B / 86,400s        ≈ 1,157,000 QPS
Peak API request QPS       = 1,157,000 × 5         ≈ 5,785,000 QPS

Rate-limit checks per request = 3 dimensions × 3 windows = 9 checks
Average rate-limit check QPS  = 1,157,000 × 9            ≈ 10.4M checks/sec
Peak rate-limit check QPS     = 5,785,000 × 9            ≈ 52M checks/sec

Note: Each "check" is typically one atomic Lua script call to Redis.
With Redis cluster sharding across 50 nodes:
  Peak per-node check QPS = 52M / 50 = 1.04M QPS/node
  Redis single-node throughput ≈ 1M simple ops/sec → tight, need pipelining
```

### Storage Calculations

**Sliding Window Counter (two integers per key):**

```
Key format: "{userId}:{window_type}:{epoch_bucket}"
Key size:   ~64 bytes (key) + 16 bytes (two int64 counters) = 80 bytes/key

Active keys at any moment:
  = 10M clients × 3 dimensions × 3 windows × 2 epochs (current + prev)
  = 180M keys

Storage per key (Redis overhead) ≈ 200 bytes (key + value + Redis object overhead)
Total Redis memory = 180M × 200 bytes = 36 GB

With 3x replication factor = 108 GB total cluster memory
Use 6 primary + 6 replica Redis nodes with 32 GB RAM each → 192 GB available ✓
```

**Token Bucket per key (two floats):**
```
Keys = 10M × 3 dimensions = 30M keys (no epoch, state persists)
Storage = 30M × 200 bytes = 6 GB — significantly cheaper
```

### Bandwidth

```
Average request payload to rate-limit service: 256 bytes (key + metadata)
Average response payload: 64 bytes (allow/deny + headers)

Ingress: 1,157,000 QPS × 256 bytes = 296 MB/s average
Egress:  1,157,000 QPS × 64 bytes  = 74 MB/s average
Peak ingress: 296 × 5 = 1.48 GB/s → need 10 GbE NICs
```

### Server Count Estimate

```
Rate-limit service (if deployed as sidecar per API server):
  = 100 API servers × 1 sidecar = 100 sidecar processes
  Each sidecar handles local pre-filtering and batches Redis calls

Redis cluster:
  = 6 primary nodes (for throughput + sharding) + 6 replicas (HA)
  = 12 Redis nodes, 32 GB RAM, 8 vCPU each

Rules configuration service:
  = 3 nodes (stateless, with PostgreSQL backend for rules)
```

### Component Explanations

**Load Balancer** — Layer 7 LB (nginx or AWS ALB) terminates TLS and routes requests to API servers. It does NOT enforce rate limits itself because it lacks access to per-user state. It provides IP-level connection limiting as a coarse first filter.

**API Server + Rate Limit Sidecar** — Each API server runs a collocated sidecar process (or in-process library). The sidecar intercepts every inbound request, extracts the rate-limit key (API key, user ID, IP), checks the limit via an atomic Redis Lua script, and either allows the request through or returns a 429. Using a sidecar avoids a separate network hop to a standalone service while still centralizing all counter state in Redis.

**Local In-Process Cache** — The sidecar caches each key's token count for ~100 ms to absorb bursts without hitting Redis on every request. This introduces at most 100 ms of over-allowance but reduces Redis load by ~10x. Cache invalidation is time-based (TTL), not event-based.

**Redis Cluster** — Central source of truth for all rate-limit counters. Uses a 6-shard cluster (each primary + replica). All counter operations are atomic Lua scripts to eliminate read-modify-write races. Keys are hash-tagged so all keys for a given client land on the same shard.

**Rules Configuration Service** — Stores rate-limit rules (e.g., "API key tier: free = 100 req/min, paid = 10,000 req/min") in PostgreSQL. When rules change, it publishes to a Redis Pub/Sub channel. All rate-limiter sidecars subscribe and hot-reload rules within 1 second of a change.

## Step 4 — Data Model

### Core Entities

#### 1. Rate Limit Rules (PostgreSQL)

```sql
CREATE TABLE rate_limit_rules (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rule_name     VARCHAR(128) NOT NULL UNIQUE,          -- e.g., "free_tier_minute"
    dimension     VARCHAR(32)  NOT NULL,                 -- "api_key" | "user_id" | "ip"
    endpoint      VARCHAR(256),                          -- NULL = applies to all endpoints
    window_type   VARCHAR(16)  NOT NULL,                 -- "second" | "minute" | "hour" | "day"
    window_size   INT          NOT NULL,                 -- e.g., 60 (seconds)
    limit_count   INT          NOT NULL,                 -- e.g., 1000 (max requests)
    burst_allowed INT          NOT NULL DEFAULT 0,       -- extra tokens for token bucket
    algorithm     VARCHAR(32)  NOT NULL DEFAULT 'sliding_window_counter',
    priority      INT          NOT NULL DEFAULT 100,     -- lower = higher priority
    active        BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Index for fast rule lookup by dimension and endpoint
CREATE INDEX idx_rl_rules_dimension_endpoint ON rate_limit_rules(dimension, endpoint);
CREATE INDEX idx_rl_rules_active ON rate_limit_rules(active) WHERE active = TRUE;
```

#### 2. Rate Limit Counters (Redis)

**Sliding Window Counter** (two integers — current bucket + previous bucket):

```
Key pattern:  rl:{dimension}:{client_id}:{endpoint_hash}:{epoch_bucket}
Key example:  rl:api_key:sk_live_abc123:all:1700000060

Fields:
  count (INT64) — number of requests in this window bucket
  
TTL:  2 × window_size (auto-expire stale buckets)

Memory: ~80 bytes per key (Redis overhead + value)
```

**Token Bucket** (two floats):

```
Key pattern:  tb:{dimension}:{client_id}:{endpoint_hash}
Key example:  tb:api_key:sk_live_abc123:all

Hash fields:
  tokens         (FLOAT64) — current token count
  last_refill_ts (INT64)   — Unix timestamp in microseconds of last refill

TTL:  set on every access to 2 × refill_interval
Memory: ~120 bytes per key
```

#### 3. Block List (Redis Set — for hard-banned clients)

```
Key:    bl:blocked_keys
Type:   Redis SET
Value:  Set of API keys / IPs that are permanently blocked
TTL:    None (persistent until removed)
Use:    SISMEMBER check before rate-limit check, O(1) time
```

### Indexes and Why

| Index | Location | Purpose |
|---|---|---|
| `idx_rl_rules_dimension_endpoint` | PostgreSQL | Fast rule lookup on every request (< 1 ms) |
| Redis hash tags `{client_id}` | Redis Cluster | Co-locate all keys for one client on same shard |
| TTL on all counter keys | Redis | Automatic garbage collection, prevents memory leak |
| Sorted set by score = timestamp | Redis (sliding log variant) | O(log N) range removal of expired entries |

### Database Choice Justification

| Component | Database | Reason |
|---|---|---|
| Rate rules | PostgreSQL | Rules are structured, rare writes, need ACID, human-readable |
| Counters | Redis | Sub-millisecond read/write, TTL native, Lua for atomicity, in-memory |
| Block list | Redis Set | O(1) membership check, low cardinality, fast |
| Audit log | Apache Kafka → S3 | High write throughput, append-only, cheap cold storage |

## Step 6 — Deep Dive: Algorithm Selection and Atomic Counter Implementation

This is the hardest component. The algorithm determines accuracy, memory cost, burst behavior, and susceptibility to race conditions. Getting this wrong in a distributed environment results in limits being bypassed under load.

### Layer 1: Algorithm Trade-offs

#### Fixed Window Counter

```
Concept: bucket = floor(now / window_size)
Key: rl:key:{bucket}
Increment and check. Reset when bucket changes.

[window 1: 0-60s] [window 2: 60-120s]
     ↑                    ↑
  counter=1000         counter=0

Problem — boundary burst:
At t=59s: 1000 requests (at limit for window 1)
At t=61s: 1000 requests (new window, counter reset)
Effective rate: 2000 req in 2 seconds → 2x the intended limit
```

**When to use:** Internal services with non-adversarial callers. Never for public APIs.

#### Sliding Window Log

```
Concept: store exact timestamp of every request in a sorted set.
Key: rl:key (sorted set, score = timestamp)

On each request:
1. ZREMRANGEBYSCORE key 0 (now - window_size)  -- remove expired
2. count = ZCARD key                            -- count remaining
3. if count < limit: ZADD key now req_id        -- add this request
4. EXPIRE key window_size

Memory: O(count) per key — can be 1000+ entries per user
```

**When to use:** Low-traffic APIs where exact accuracy is critical (e.g., financial transaction limits).
**Problem:** 1000 req/min limit = 1000 sorted set entries per user per window. At 10M users = 10B Redis entries. Unacceptable at scale.

#### Sliding Window Counter (Best Default)

```
Concept: approximate sliding window using two fixed-window buckets.

          prev window          curr window
         [t-2w .. t-w]        [t-w .. t]
              count_prev            count_curr

Approximate request count in last window:
  elapsed_fraction = (now % window_size) / window_size
  approx_count = count_prev × (1 - elapsed_fraction) + count_curr

  Example: window=60s, elapsed=45s (75% into current window)
  count_prev=800, count_curr=400
  approx = 800 × 0.25 + 400 = 600 requests

Memory: O(1) per key (just two integers)
Accuracy: ±0.1% error in practice for random traffic
Burst: bounded — no boundary burst larger than ~15%
```

This is what Cloudflare uses. Two counter buckets per key, weighted approximation.

#### Token Bucket

```
Concept: bucket has capacity C. Refills at rate R tokens/second.
Each request consumes 1 token (or more for expensive ops).

State: (tokens_remaining, last_refill_timestamp)

On each request:
  elapsed = now - last_refill_ts
  new_tokens = min(capacity, tokens + elapsed × rate)
  if new_tokens >= cost: allow, tokens = new_tokens - cost
  else: deny

Allows controlled bursts (capacity > sustained rate).
Memory: O(1) per key — just two values.
```

**When to use:** APIs where brief legitimate bursts are expected (payment SDKs retrying, mobile apps reconnecting). Used by Stripe.

#### Leaky Bucket

```
Concept: requests enter a FIFO queue; output drains at fixed rate.
Excess requests are dropped at the input.

Best for: traffic shaping, not fairness.
Problem: adds latency (requests wait in queue). Not appropriate for APIs.
```

### Layer 2: The Race Condition Problem

**Naive implementation (broken under concurrency):**

```
// Running on 10 different API servers concurrently:
count = redis.GET("rl:key:bucket")   // all 10 read count=999
count++                               // all 10 compute 1000
redis.SET("rl:key:bucket", count)    // all 10 write 1000
// Result: 10 requests let through when limit was 1. 10x bypass.
```

**Solution: Atomic Lua Script**

Redis executes Lua scripts atomically — no other command runs between a script's reads and writes, because Redis is single-threaded. This makes Lua the correct tool for read-modify-write counter operations.

```lua
-- Sliding Window Counter Lua Script
-- KEYS[1] = current bucket key  (e.g., rl:api_key:abc:1700001060)
-- KEYS[2] = previous bucket key (e.g., rl:api_key:abc:1700001000)
-- ARGV[1] = limit
-- ARGV[2] = current bucket start time
-- ARGV[3] = window size in seconds
-- ARGV[4] = elapsed fraction of current window (0.0 to 1.0)
-- ARGV[5] = request cost (usually 1)
-- Returns: {allowed (0/1), approx_count, remaining}

local curr_count  = tonumber(redis.call('GET', KEYS[1])) or 0
local prev_count  = tonumber(redis.call('GET', KEYS[2])) or 0
local limit       = tonumber(ARGV[1])
local elapsed_frac = tonumber(ARGV[4])
local cost        = tonumber(ARGV[5])

-- Sliding approximation
local approx = math.floor(prev_count * (1 - elapsed_frac) + curr_count)

if approx + cost > limit then
    return {0, approx, 0}  -- denied
end

-- Increment current bucket and set TTL
local new_curr = redis.call('INCRBY', KEYS[1], cost)
if new_curr == cost then
    -- First request in this bucket — set expiry
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[3]) * 2)
end

local remaining = limit - (approx + cost)
return {1, approx + cost, remaining}
```

**Token Bucket Lua Script:**

```lua
-- Token Bucket Lua Script
-- KEYS[1] = bucket key
-- ARGV[1] = capacity, ARGV[2] = refill_rate (tokens/sec)
-- ARGV[3] = now (microseconds), ARGV[4] = cost
-- Returns: {allowed, tokens_remaining}

local bucket     = redis.call('HMGET', KEYS[1], 'tokens', 'last_refill_ts')
local capacity   = tonumber(ARGV[1])
local rate       = tonumber(ARGV[2])
local now        = tonumber(ARGV[3])
local cost       = tonumber(ARGV[4])

local tokens     = tonumber(bucket[1]) or capacity
local last_ts    = tonumber(bucket[2]) or now

-- Refill tokens based on elapsed time
local elapsed_sec = (now - last_ts) / 1000000.0
local new_tokens  = math.min(capacity, tokens + elapsed_sec * rate)

if new_tokens < cost then
    -- Update state even on deny (refill still happened)
    redis.call('HMSET', KEYS[1], 'tokens', new_tokens, 'last_refill_ts', now)
    redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
    return {0, math.floor(new_tokens)}
end

new_tokens = new_tokens - cost
redis.call('HMSET', KEYS[1], 'tokens', new_tokens, 'last_refill_ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
return {1, math.floor(new_tokens)}
```

### Layer 3: Redis Cluster Sharding and Hash Tags

In Redis Cluster, a key's hash slot determines which shard handles it. Lua scripts must operate on keys that all hash to the same slot — otherwise Redis returns a `CROSSSLOT` error.

**Problem:** For a user with 3 dimensions × 3 windows = 9 keys, each key could hash to a different shard, making a single Lua script impossible.

**Solution: Hash Tags**

Redis hash tags use curly braces to force the slot calculation to use only the substring inside `{}`:

```
Without hash tags:
  rl:user123:minute:1700001060  → shard 3
  rl:user123:hour:1700001060    → shard 7   ← different shard! Lua fails.

With hash tags:
  rl:{user123}:minute:1700001060 → hash(user123) → shard 5
  rl:{user123}:hour:1700001060   → hash(user123) → shard 5   ← same shard ✓
  rl:{user123}:second:1700001060 → hash(user123) → shard 5   ← same shard ✓

All keys for user123 hash to the same shard.
One Lua EVAL can atomically update all three windows simultaneously.
```

**Caveat:** Hot-key problem. If one user generates 100x traffic, all their keys land on one shard. Solution: add a random suffix to distribute within the shard, or use local in-process counters to absorb spikes and batch Redis updates.

### Algorithm Selection Matrix

| Algorithm | Memory | Accuracy | Burst | Complexity | Best For |
|---|---|---|---|---|---|
| Fixed Window | O(1) | Low (±100%) | Yes (boundary) | Low | Internal, non-adversarial |
| Sliding Window Log | O(N) | Exact | No | Medium | Low-traffic, financial |
| **Sliding Window Counter** | **O(1)** | **~98%** | **Bounded** | **Medium** | **Most APIs** |
| Token Bucket | O(1) | High | Yes (controlled) | Medium | Dev APIs, payment SDKs |
| Leaky Bucket | O(queue) | Exact | No (drops) | Medium | Traffic shaping |

## Step 7 — Deep Dive: Distributed Consistency and Failure Handling

This is the second hardest component. The rate limiter sits in every request's hot path. If Redis becomes slow, the entire API slows. If Redis goes down, what happens?

### Layer 1: The Local Cache Trade-off

Each API server sidecar maintains a small in-process LRU cache of counter states (e.g., using a Go `sync.Map` or Java `CaffeineCache`):

```
Request arrives
      │
      ▼
Check local cache (TTL: 100ms)
      │
   Hit?─────YES──► Return cached count
      │
     NO
      ▼
Lua script → Redis (1-3ms RTT)
      │
      ▼
Update local cache + return result
```

**Trade-off analysis:**

```
Without local cache:
  100K RPS × 1 API server × 9 Redis calls = 900K Redis ops/sec per server
  × 100 servers = 90M Redis ops/sec total → Redis saturated

With 100ms local cache:
  Each key is checked at most 10 times/sec via Redis
  100K RPS × (1/10 cache miss rate) × 9 calls = 90K Redis ops/sec per server
  × 100 servers = 9M Redis ops/sec total → 10x reduction ✓

Over-allowance from cache:
  100ms window × 100K RPS = 10,000 extra requests possible if cache is stale
  For a 1,000 req/min limit: at most 1 extra window (100ms) × RPS = minimal
```

### Layer 2: Redis Failure Modes and Mitigation

**Failure Mode 1: Redis Primary Fails**

Redis Sentinel (for standalone) or Redis Cluster failover promotes a replica to primary within ~5-15 seconds. During failover:
- New writes to the failed primary are lost
- Rate limit state is partially lost → some counters reset to 0
- Effect: brief over-allowance during the failover window

**Mitigation:** Accept the brief over-allowance. For security-critical limits (login attempts), use a secondary in-memory counter that survives a single Redis failover:

```
rate_check(key):
  redis_result = redis_check(key)          // authoritative
  local_count  = local_counter.increment(key)  // local guard

  // Fail-closed: deny if EITHER limit exceeded
  if redis_result.denied OR local_count > local_limit:
      return DENY
  return ALLOW
```

**Failure Mode 2: Redis Cluster Network Partition**

Some shards become unreachable. Keys on those shards cannot be checked.

**Strategy (configurable per rule):**

```go
func (rl *RateLimiter) Check(key string) (Decision, error) {
    result, err := rl.redisCheck(key)
    if err != nil {
        rl.circuitBreaker.RecordFailure()
        if rl.config.FailPolicy == FailClosed {
            return Deny, nil   // security-critical: deny on uncertainty
        }
        // Fail-open: use local in-memory fallback
        return rl.localFallback.Check(key), nil
    }
    rl.circuitBreaker.RecordSuccess()
    return result, nil
}
```

**Failure Mode 3: Redis Latency Spike (not a full failure)**

Redis p99 latency spikes to 50ms due to GC pause, memory compaction, or network blip. This adds 50ms to every API response.

**Mitigation: Hedging with Timeout**

```
Set Redis client timeout to 5ms.
On timeout: use local fallback (same as fail-open).
Log metric: "redis_rate_limit_timeout_total".
Alert if timeout rate > 0.1%.
```

**Failure Mode 4: Clock Skew Between API Servers**

Sliding window counter uses epoch buckets calculated from `floor(now / window_size)`. If Server A's clock is 3 seconds ahead of Server B, they compute different bucket keys for the same request, fragmenting the counter.

**Mitigation:** Use Redis's own clock via `TIME` command:

```lua
-- At the start of the Lua script:
local redis_time = redis.call('TIME')  -- returns {seconds, microseconds}
local now = tonumber(redis_time[1]) * 1000000 + tonumber(redis_time[2])
-- Use 'now' for all calculations — single source of truth
```

This eliminates clock skew entirely since all counter operations use the Redis server's clock.

### Layer 3: Multi-Region Rate Limiting

```
                 ┌────────────────────────────────────────────┐
                 │              Global Traffic                  │
                 └────────┬──────────────────┬─────────────────┘
                          │                  │
              ┌───────────▼──┐       ┌───────▼──────────┐
              │  US-EAST-1    │       │   EU-WEST-1       │
              │  Redis Cluster│◄─────►│   Redis Cluster   │
              │  local counts │  Async│   local counts    │
              │               │  sync │                   │
              └───────────────┘       └───────────────────┘
```

**Option A: Regional Limits (most common)**

Each region enforces `limit / num_regions`. If limit is 1,000/min globally and there are 2 regions, each region enforces 500/min. Simple, no cross-region coordination. Downside: a user hitting one region doesn't count against the other.

**Option B: Gossip-Based Global Approximate Counter**

Each region periodically (every 5 seconds) gossips its local counter totals to all other regions. Each node combines:

```
global_approx = sum(local_count[region] for region in regions)
```

Used by Cloudflare. ~5-second staleness is acceptable for most rate limiting use cases. Not suitable for hard security limits (use Option A fail-closed for those).

**Option C: Global Atomic Counter via CRDTs (Redis Active-Active)**

Redis Enterprise's Active-Active geo-replication uses CRDT-based counters that merge automatically. Consistency within ~100ms across regions. Expensive — typically only for enterprise customers.

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (10M RPS peak)

**Bottleneck:** Redis Cluster — at 52M → 520M rate-limit checks/second, each shard receives ~10M ops/sec. Redis single-threaded at ~1M ops/sec per core.

**Specific fix:**
1. Increase local cache TTL from 100ms → 500ms. This reduces Redis calls by 5x, bringing actual Redis load to ~100M ops/sec → 2M per shard on 50 shards. Manageable.
2. Switch from per-request Redis calls to batch "token reservation": each sidecar reserves 100 tokens at once from Redis and distributes them locally, going back only when exhausted. Called "pre-fetching" or "local quota delegation."

```
local_reserve = redis.DECRBY("tokens:user123", 100)  // grab 100 at once
// serve next 100 requests locally without Redis call
```

### At 100x Current Load (100M RPS peak)

**Bottleneck:** Redis Cluster network bandwidth. Each counter update is ~100 bytes. 520M updates/sec × 100 bytes = 52 GB/s aggregate. Modern 10 GbE NIC maxes at ~1.25 GB/s per node.

**Specific fix:** Move to hierarchical rate limiting.

```
Tier 1 (per-process, in-memory, ~100K ops/sec, no network):
  Sidecar maintains local token bucket per client.
  Enforces 10% of the global limit locally.
  High-speed, no coordination.

Tier 2 (per-PoP, Redis, ~10K ops/sec per key):
  Local Redis per PoP aggregates traffic from all processes in that PoP.
  Enforces 60% of the global limit at PoP level.

Tier 3 (global, CRDTs or gossip, eventual):
  Global Redis or gossip enforces the remaining 30% of the global limit.
  ~5 second staleness acceptable.
```

This reduces cross-datacenter coordination by 10x.

### At 1000x Current Load (1B RPS peak — Cloudflare scale)

**Bottleneck:** The assumption that all requests for a client go through a shared counter breaks down. At this scale, a single rate-limit key for a popular client receives millions of operations per second. Even Redis Cluster with 1,000 shards would have hot-key problems.

**Fundamental changes required:**

1. **Abandon centralized atomic counters entirely.** Accept ~5% over-allowance and use probabilistic counting.

2. **Per-PoP local enforcement** — each PoP gets an allocated quota. Traffic from a client is routed (via consistent hashing at DNS/BGP level) to the same PoP. One PoP's Redis sees all traffic for that client.

3. **Bloom filter pre-screening** — maintain a probabilistic count-min sketch per client. O(1) space and O(1) lookup. 1-2% false positive rate is acceptable for most rate limiting.

4. **Streaming aggregation** — use Apache Flink or Kafka Streams to aggregate counters in near-real-time. Rate limiter reads the aggregated view (5-10 second lag) and enforces limits based on that.

5. **Stateless rate limiting with cryptographic proofs** — issue clients a signed token that encodes remaining quota. Client presents token with each request. No centralized state at all. Trades network calls for token refreshes (every N seconds).

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Algorithm | Sliding window counter | Sliding window log | Log uses O(N) memory per key; counter uses O(1) with ~98% accuracy — acceptable trade-off at scale |
| Counter storage | Redis Cluster | PostgreSQL, Cassandra | Sub-millisecond latency, native TTL, Lua atomicity — Redis is uniquely suited |
| Atomicity mechanism | Lua scripts | Redis WATCH/MULTI/EXEC (optimistic locking) | Lua is always atomic; WATCH fails under high contention and requires retries |
| Deployment model | Sidecar per API server | Standalone service | Sidecar avoids extra network hop (2-3ms saved); standalone would be simpler operationally |
| Local cache TTL | 100ms | 0ms (no cache) | Without cache, Redis is saturated; 100ms introduces <0.2% over-allowance — acceptable |
| Clock source | Redis `TIME` command | Application server `time.now()` | Eliminates clock skew; all nodes agree on epoch boundaries |
| Cross-region | Regional limits (limit/N per region) | Global CRDT counter | CRDTs add latency and cost; regional limits are simpler and sufficient for most APIs |
| Redis failure policy | Fail-open for general API, fail-closed for auth | Always fail-open | Security-sensitive limits (login brute force) must fail-closed; API degradation is better than security hole |
| Rules storage | PostgreSQL + Redis pub/sub | In-code config files | Hot-reload without deploy; audit log of rule changes; multi-tenant rule management |

## Step 10 — How Real Companies Solved This

### Cloudflare

**Problem:** Rate limiting for millions of customer domains across 250+ PoPs, each with thousands of servers. Cross-PoP coordination is impossible at their scale.

**Architecture:**

Cloudflare's key insight (from their 2019 engineering blog) was that **under normal routing conditions, traffic from a single client IP consistently hits the same PoP** — because BGP routing is stable. So they could enforce rate limits per-PoP without cross-PoP coordination, accepting that a VPN-hopping attacker could get more than their limit.

Inside each PoP, they built a Twemproxy + Memcached cluster. Twemproxy distributed keys across Memcached nodes using consistent hashing. All servers in the PoP sent their rate-limit checks to this shared Memcached cluster.

They implemented the **sliding window counter approximation** — two integer counters per key (current epoch + previous epoch), weighted sum for the approximation. This bounded memory to O(1) per key regardless of traffic rate.

**What they got wrong first:** Initially tried per-server counters (no coordination). This allowed adversarial clients to send 100x their limit by distributing requests across 100 PoP servers. Fixed by centralizing within a PoP.

**Key insight:** "Approximate is sufficient. A 1% over-allowance is acceptable if it means 10x less infrastructure." — Cloudflare Engineering Blog, 2019.

**Source:** [How we built rate limiting capable of scaling to millions of domains](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)

---

### Stripe

**Problem:** Protect payment API from developer bugs (retry loops), abusive integrations, and occasional traffic spikes — without blocking legitimate payment processing.

**Architecture:**

Stripe published their approach showing they use **4 distinct rate limiter types in production simultaneously**:

1. **Request rate limiter** — per API key, 100 req/s per endpoint. Token bucket algorithm. Allows short bursts for payment retry storms.
2. **Concurrent request limiter** — prevents a single key from holding more than N simultaneous connections. Implemented with Redis Sorted Set (add on request start, remove on completion, ZCARD to count).
3. **Fleet usage load shedder** — monitors Redis queue depth and sheds 10% of non-critical traffic (list charges, search) when the fleet is >80% utilized. Reserves 20% of capacity for critical paths (create charge, create refund).
4. **Worker utilization load shedder** — per-machine CPU monitoring. If a machine exceeds 90% CPU, it sheds non-critical requests locally without Redis.

**What they got wrong first:** Early version had no concurrency limiter, only rate limiter. A client could open 10,000 simultaneous connections with 1 req/sec each — total rate was within limit but the system was overwhelmed by open connections.

**Key insight:** Rate limiting by request count per second is insufficient. You also need concurrency limits (simultaneous open connections) and load-based shedding at multiple levels.

**Source:** [This Is How Stripe Does Rate Limiting](https://newsletter.systemdesign.one/p/rate-limiter) / Stripe Engineering Blog

---

### Twitter/X API

**Problem:** Tiered API access — free, basic, pro, and enterprise tiers — each with different limits per endpoint. Rate limits are enforced per-app AND per-user-within-app.

**Architecture:**

Twitter enforces **hierarchical limits**:
```
App-level limit:    15 reads/15min window (free tier)
User-level limit:   15 reads/15min window per user within the app

Both are checked. Whichever is more restrictive wins.
```

They use the **sliding window log** algorithm for their developer-facing APIs (because developer API calls are low-volume and exactness matters for compliance) and **sliding window counter** for internal services.

**Key decision:** Headers are as important as enforcement. Twitter returns `x-rate-limit-limit`, `x-rate-limit-remaining`, and `x-rate-limit-reset` on every response so developers can implement intelligent backoff without guessing. This dramatically reduced support tickets about rate limiting.

**What they got wrong first:** Original v1 API used fixed windows. Clients that hit the limit at :59 of one minute and :01 of the next got 2000 requests in 2 seconds. Fixed in v2 API with sliding windows.

## Interview Perspective

### What the Interviewer Is Evaluating

This problem specifically tests:
1. **Distributed systems knowledge** — can you identify and solve the race condition in multi-server environments?
2. **Algorithm depth** — do you know more than just "token bucket exists"? Can you compare trade-offs?
3. **Redis expertise** — do you know about Lua atomicity, cluster sharding, hash tags?
4. **Failure mode thinking** — what happens when Redis is down? Do you have a principled fail-open vs fail-closed answer?
5. **Production mindset** — do you mention headers, monitoring, hot-reload of rules, TTL-based GC?

---

### Junior (L3-L4) Answer

**What they say:** "We store a counter in Redis. On each request, we increment it and check against the limit. If over, return 429."

**Depth reached:** Names Redis. Knows what a rate limiter does. Might mention token bucket as an algorithm name.

**What they miss:**
- Race conditions in multi-server environments
- Why INCR alone is not atomic enough for sliding windows
- Clock skew between servers
- What happens when Redis is down
- Memory GC (TTL on keys)
- Response headers (`Retry-After`, `X-RateLimit-Reset`)
- Multiple dimensions (user, IP, API key simultaneously)

---

### Senior (L5) Answer

**What they add:**
- Compares at least 3 algorithms with trade-offs (fixed window, sliding window, token bucket)
- Mentions Lua scripts for atomicity and explains why
- Recognizes the sidecar vs standalone service deployment trade-off
- Discusses what happens on Redis failure (fail-open vs fail-closed)
- Estimates memory: "at 10M users × 3 dimensions × 200 bytes = ~6 GB in Redis"
- Mentions TTL for key expiry
- Talks about response headers for client backoff

**Specific depth on this problem:**
- Explains the boundary burst problem of fixed windows with a concrete example (2x rate in 2 seconds)
- Explains why Lua scripts are atomic (Redis single-threaded event loop)

---

### Staff (L6+) Answer

**What they drive to unprompted:**

1. **Algorithm selection is use-case dependent** — "For a payment API like Stripe, I'd use token bucket to allow burst retries. For a scraping protection endpoint, I'd use sliding window counter with no burst. For internal service mesh, fixed window is sufficient and cheap."

2. **Hot-key problem in Redis Cluster** — "If one client generates 100K RPS, all their keys hash to one shard and saturate it. I'd use local quota pre-fetching: each sidecar reserves a block of 100 tokens at once, reducing Redis calls by 100x."

3. **Cross-region consistency** — "Strong global consistency requires ~100ms cross-region RTT on every request path, which doubles API latency. I'd do regional limits (each region gets 1/N of global limit) and accept that a VPN-switching attacker can multiply their limit by N. For auth endpoints, I'd use a global CRDT counter and accept 5-second staleness."

4. **Operational cost reasoning** — "The sliding window log is exact but at 10M users × 1000 req/min limit, you're storing 10B Redis entries. At 100 bytes each, that's 1 TB just for rate limit state. Sliding window counter drops this to 36 GB. The 2% accuracy difference isn't worth 28x the memory cost."

5. **Monitoring** — "I'd instrument: rate_limit_allowed_total, rate_limit_denied_total (labeled by client_tier and dimension), redis_lua_duration_p99, local_cache_hit_rate, redis_timeout_rate. Alert on redis_timeout_rate > 0.1% as early warning of Redis degradation."

---

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **Forgetting the race condition entirely.** Saying "store a counter in Redis and increment it" without mentioning that INCR + GET is not atomic for the check-and-act pattern. A common follow-up: "What if two requests arrive at the same time?" — many candidates have no answer.

2. **Proposing a standalone rate-limit service without analyzing the latency cost.** A dedicated rate-limit microservice adds one network round-trip (2-5ms) to every API call. At p99, this can double response times. Interviewers will probe this; you need to propose sidecar deployment or middleware as the alternative.

3. **Not knowing the fixed window boundary burst problem.** Candidates say "fixed window is simpler, I'd use that." Interviewer asks: "What happens at the boundary between two windows?" — candidates who haven't thought about this have no answer. Always demonstrate you understand why sliding windows exist.

4. **Treating Redis as magic (no failure analysis).** Saying "Redis handles it" without discussing what happens when Redis is unreachable. Is it fail-open or fail-closed? What's the fallback? Interviewers specifically probe this because the answer reveals whether you've run production systems.

5. **Ignoring the client experience.** Designing the denial mechanism (429) without mentioning `Retry-After` and `X-RateLimit-Reset` headers. Rate limiters that don't tell clients when to retry cause thundering herds — every denied client retries immediately, creating a load spike exactly when the system is already overloaded.

| Fact | Number |

## Summary

A production-grade rate limiter for a major API platform requires:

- **Algorithm:** Sliding window counter (default) or token bucket (burst-tolerant APIs). Never fixed window for public APIs.
- **Atomicity:** Redis Lua scripts for read-modify-write. Not WATCH/MULTI/EXEC (too much retry under contention).
- **Deployment:** Sidecar collocated with API servers, not a standalone service, to avoid network hop on every request.
- **Sharding:** Redis Cluster with hash tags to co-locate all keys for one client on one shard.
- **Failure policy:** Fail-open with local fallback for general APIs; fail-closed for auth/payment endpoints.
- **Clock:** Use Redis `TIME` command inside Lua scripts to eliminate cross-server clock skew.
- **Client UX:** Always return `Retry-After`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` — clients that don't know when to retry create thundering herds.
