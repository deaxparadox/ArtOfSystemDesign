# 10.9 — Design a Ride-Sharing Service — Uber Model

> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Real-time driver location at scale, geospatial indexing (quadtree/geohash/H3), matching algorithm, trip state machine, WebSocket dispatch

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

Design a ride-sharing platform where riders can request on-demand transportation and nearby drivers can accept those requests, with the system responsible for real-time location tracking, intelligent driver matching, route guidance, fare calculation, and payment settlement.

**Real scale (Uber, 2024):** 156 million monthly active users, 7.1 million active drivers, ~31 million trips/day, operating in 10,000+ cities across 70 countries. Location updates arrive at ~250,000 writes/second during peak hours. The dispatch cycle — from rider tap to driver notification — must complete in under 2 seconds.

---

## Step 1 — Clarify Requirements (5–10 min in interview)

### Functional Requirements

1. **Rider side:** A rider opens the app, sees nearby drivers, requests a ride, gets matched with a driver, tracks the driver in real time, completes the trip, and pays automatically.
2. **Driver side:** A driver goes online, receives ride requests, accepts/declines, navigates to the pickup, starts/ends the trip, and receives earnings.
3. **Real-time location sharing:** Both parties can see each other's position on the map during relevant trip phases.
4. **Driver matching:** System selects the optimal nearby available driver within a configurable radius and timeout window.
5. **Fare calculation:** Estimate fare before the trip; compute final fare based on actual distance, time, and surge multiplier.
6. **Trip lifecycle management:** Track the full state of a trip from request to payment settlement.

### Non-Functional Requirements

| Requirement | Target |
|---|---|
| Availability | 99.99% (52 min/year downtime) |
| Location update ingestion latency | < 100ms p99 |
| Dispatch cycle (request → driver notified) | < 2 seconds p99 |
| Driver ETA accuracy | ± 30 seconds for short trips |
| Trip data durability | 99.9999% (6 nines) — financial record |
| Consistency model | Strong consistency for trip state; eventual for location |
| Read QPS for location queries | ~500K reads/second during peak |
| Write QPS for location updates | ~250K writes/second during peak |

### Out of Scope

- Driver background checks and onboarding
- In-app chat between rider and driver
- Scheduled rides (future rides, not on-demand)
- Multi-stop trips and package delivery
- Surge pricing algorithm internals (just the data model)
- Fraud detection and payments processing internals
- Driver earnings tax reporting

### Clarifying Questions to Ask the Interviewer

1. **"How many concurrent drivers are online at peak?"** — This determines location update write QPS, which drives the choice of database for the location index (Redis vs. PostGIS vs. Cassandra). 1M concurrent drivers at 1 update/4s = 250K writes/second — a traditional RDBMS will fall over.

2. **"Should matching be exact (single best driver) or can we show multiple options?"** — Uber-style is single best match dispatched sequentially; some products show a choice. This changes whether you need a priority queue or a bipartite matching solver.

3. **"What is the acceptable matching timeout before the request is cancelled?"** — Typically 30–60 seconds total, with 10–15 seconds per driver offer. This determines how many driver candidates you need to pre-rank.

4. **"Do we need to support shared rides (pooling)?"** — Pooling is a fundamentally harder problem (multi-rider, multi-stop routing) and changes the matching algorithm significantly.

5. **"What regions are we supporting — single city, single country, global?"** — Global means multi-region deployment, data residency concerns, and sharding strategy by city/region.

6. **"Do we need surge pricing?"** — This requires a real-time supply/demand aggregation pipeline per geospatial cell, adding significant complexity.

7. **"What are the constraints on driver notification — push only, or also SMS fallback?"** — Push requires WebSocket/APNs/FCM infrastructure; SMS adds Twilio-style fallback complexity and cost.

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

```
Users:
  Monthly Active Users (MAU): 150M
  Daily Active Users (DAU): 30M riders + 5M active drivers
  Peak concurrent drivers online: 1,000,000
  Peak concurrent riders with active trips: 500,000

Rides:
  Trips per day: 30M
  Average trip duration: 15 minutes
  Peak hour factor: 3x average → ~6.25M trips/hour at peak
  Trips per second at peak: 6,250,000 / 3600 ≈ 1,735 trips/second
```

### Write QPS (Location Updates — the Dominant Write Load)

```
Driver sends GPS update every 4 seconds
Peak concurrent online drivers: 1,000,000

Location write QPS = 1,000,000 / 4 = 250,000 writes/second

Each location update: 50 bytes (driver_id UUID=16B, lat=8B, lon=8B, heading=4B, speed=4B, timestamp=8B, status=2B)

Location write bandwidth = 250,000 × 50B = 12.5 MB/second ingress
```

### Read QPS (Location Queries)

```
Rider opens app → sees nearby drivers: 1 geospatial query
Polling rate for rider tracking an en-route driver: 1 query/second × 500K active trips = 500,000 reads/second

Dispatch queries (finding candidates for new requests):
  1,735 new trips/second × 1 geospatial search = 1,735 reads/second (negligible vs. tracking reads)

Peak location read QPS ≈ 502,000 reads/second
```

### Trip Service QPS

```
State transitions per trip: ~6 (requested, matched, driver_arrived, in_progress, completed, settled)
Trip state writes = 1,735 trips/second × 6 transitions = 10,400 writes/second

Trip state reads = 2x writes (read-before-write for CAS) = 20,800 reads/second
```

### Storage

```
Per trip record: ~2 KB (metadata + route polyline + fare breakdown)
Per day:  30M trips × 2 KB = 60 GB/day
Per year: 60 GB × 365 = 21.9 TB/year
5 years:  109 TB

Per driver location event (for historical audit): 50 bytes
Active driver locations retained (last known): 1M × 50B = 50 MB → fits entirely in RAM

Route history (GPS breadcrumbs per trip): 15 min × 1 point/4s × 20B = 4,500 points × 20B = 90 KB/trip
Route history per day: 30M × 90 KB = 2.7 TB/day → store compressed in object storage (S3)

Total operational DB storage (5 years): ~110 TB
Object storage (route history, 5 years): ~5 PB
```

### Cache Sizing

```
Hot trip cache (last 24 hours active trips): 1M trips × 2 KB = 2 GB (trivially cacheable)
Driver location index (entire in-memory geospatial): 1M drivers × 50B = 50 MB per replica
Surge pricing map (per H3 cell): ~5M cells × 8B = 40 MB per replica
```

### Server Count Estimate

```
Location ingestion servers (Go, 50K writes/s each): 250,000 / 50,000 = 5 servers + 3x headroom = 15 servers
API servers (Node/Go, 10K rps each): 502,000 / 10,000 = 51 + headroom = 100 servers
Dispatch/matching workers: 1,735 dispatches/second, each takes ~50ms = 87 concurrent workers → 20 servers
Redis cluster for location: 500K ops/s, Redis handles 100K ops/s per node → 5 primary + 5 replica nodes
PostgreSQL for trips: 31K ops/s, Postgres handles ~5K TPS → 7 primaries with read replicas
```

### Component Responsibilities

**API Gateway:** Terminates TLS, validates JWT tokens, applies per-user rate limits (100 req/min), routes to the correct microservice. Runs as Envoy proxies behind an AWS ALB.

**Location Service:** Receives driver GPS heartbeats via HTTP POST (every 4 seconds). Writes to Redis using `GEOADD drivers <lon> <lat> <driver_id>`. Publishes location events to Kafka for downstream consumers (analytics, map-matching). This service is stateless — all state lives in Redis.

**Dispatch Service:** The matchmaker. When a ride request comes in, it queries Redis for nearby available drivers, scores them, and opens a WebSocket offer to the best candidate. Maintains long-lived WebSocket connections to all online drivers. Uses Redis distributed locks (`SETNX`) to prevent double-assignment.

**Trip Service:** Owns the trip state machine. All state transitions write to PostgreSQL with optimistic locking. Emits trip events to Kafka (for payments, notifications, analytics). This is the "source of truth" for what happened.

**Surge Pricing Service (Kafka Consumer):** Consumes location and trip events, aggregates supply/demand ratios per H3 cell (resolution 7, ~5 km² cells), and writes surge multipliers back to Redis with a short TTL (30 seconds). Riders see the surge multiplier when they open the fare estimate screen.

**Notification Service:** Consumes trip events from Kafka and delivers push notifications via FCM (Android), APNs (iOS), or SMS fallback. Keeps delivery receipts so failed pushes can trigger fallback.

**Redis Data Structures**

```
# Driver live location index (geospatial sorted set)
Key: "drivers:geo:{vehicle_type}"    # e.g., "drivers:geo:economy"
Type: Sorted Set (GEOADD)
Value: driver_id → encoded (lat, lon) geohash score
TTL: None (updated continuously; evicted if driver goes offline)

# Driver status hash
Key: "driver:{driver_id}:status"
Type: Hash
Fields: lat, lon, heading, speed, status, last_seen, trip_id
TTL: 60 seconds (auto-evict if driver stops sending heartbeats)

# Dispatch lock (prevent double-assignment)
Key: "lock:driver:{driver_id}"
Type: String (SETNX)
Value: trip_id
TTL: 20 seconds (offer window duration)

# Surge multiplier per H3 cell
Key: "surge:h3:{h3_cell_id}"
Type: String (Float)
Value: 1.3 (surge multiplier)
TTL: 30 seconds (recomputed by surge service)

# WebSocket server affinity (which dispatch server a driver is connected to)
Key: "driver:{driver_id}:ws_server"
Type: String
Value: "dispatch-server-07"
TTL: 30 seconds (refreshed by heartbeat)
```

**Database Choice Justification**

| Data | Database | Why |
|---|---|---|
| Drivers, Riders, Trips | PostgreSQL | Strong ACID guarantees, complex queries, foreign key integrity, optimistic locking via `version` column |
| Live driver locations | Redis (sorted set) | 250K writes/second, O(log N) GEOADD, sub-millisecond GEOSEARCH — no RDBMS can match this write rate |
| Driver availability status | Redis (hash + TTL) | TTL auto-expiry = implicit "driver went offline" detection without cron jobs |
| Surge pricing per cell | Redis (string + TTL) | Recomputed every 30s, needs instant read by API servers, 40 MB total |
| Trip event log | Kafka + S3 | Append-only, high throughput, feeds downstream consumers |
| Route GPS breadcrumbs | S3 (Parquet) | Write-once, large volume (2.7 TB/day), queried for analytics not real-time |

## Step 6 — Deep Dive: Real-Time Driver Location & Geospatial Matching

This is the hardest component. The naive solution (PostGIS + PostgreSQL) breaks at 250K writes/second. Getting this right wins the interview.

### Layer 1: The Write Path — GPS Ingestion Pipeline

```
Driver App
    │
    │ HTTP POST /v1/driver/location  (every 4 seconds)
    │ Body: { lat, lon, heading, speed }
    │
    ▼
Location Ingestion Service (Go, stateless)
    │
    ├── Validate: lat in [-90,90], lon in [-180,180], speed < 300 km/h
    │
    ├── GEOADD drivers:geo:{vehicle_type} <lon> <lat> <driver_id>  (Redis)
    │   └── O(log N) time, completes in < 1ms
    │
    ├── HSET driver:{driver_id}:status lat <lat> lon <lon> ...     (Redis)
    │   EXPIRE driver:{driver_id}:status 60
    │   └── 60s TTL: if driver stops sending, auto-evicted (gone "offline")
    │
    └── Publish to Kafka topic: "driver-locations"
        └── Key: driver_id (ensures ordering per driver)
            Value: { driver_id, lat, lon, heading, speed, ts }
```

**Why Redis `GEOADD` and not PostGIS?**

PostGIS stores geometries in a B-tree spatial index (R-tree). Each update requires removing the old entry and inserting the new one — two R-tree operations. At 250K updates/second, this saturates a single Postgres write path at ~10K–20K writes/second.

Redis `GEOADD` uses a sorted set internally. Coordinates are encoded into a 52-bit geohash score using the Haversine encoding scheme. An upsert is a single sorted-set update — O(log N). A 32-core Redis instance handles 200K+ geospatial ops/second.

**The Kafka pipeline** decouples the hot write path from downstream consumers. Analytics, map-matching, and surge calculation consume from Kafka asynchronously without adding latency to the write path.

### Layer 2: The Geospatial Index — H3 vs. Geohash vs. Quadtree

**Why Uber chose H3 (Hexagonal Hierarchical Spatial Index):**

The fundamental problem with rectangular grids (geohash) is boundary distortion: a driver 10m east of a cell boundary belongs to a completely different geohash cell than a driver 10m west of it, even though they are 20m apart. You must always query neighboring cells to avoid missing nearby drivers.

Hexagons solve this: every hexagon has exactly 6 equidistant neighbors. The center of each neighbor cell is the same distance from the center of any given cell. This makes radial search uniform. Redis `GEOSEARCH` with `BYRADIUS` works the same way but using a circular approximation — H3 is superior for analytics and surge computation.

```
H3 Resolution Table (approximate cell sizes):
  Resolution 3:  ~86,700 km²  (continent-level)
  Resolution 5:  ~252 km²     (city-level, used for demand forecasting)
  Resolution 7:  ~5.1 km²     (neighborhood-level, used for SURGE pricing)
  Resolution 9:  ~0.1 km²     (block-level, used for DISPATCH matching)
  Resolution 12: ~0.0003 km²  (very precise, used for pickup/dropoff)
```

**In Redis: Dispatch uses `GEOSEARCH`, Analytics uses H3**

For real-time dispatch, Redis `GEOSEARCH` (formerly `GEORADIUSBYMEMBER`) is sufficient and much simpler than maintaining a separate H3 index in Redis:

```
GEOSEARCH drivers:geo:economy
  FROMMEMBER <driver_id>       -- OR FROMLONLAT <lon> <lat>
  BYRADIUS 3 km
  ASC
  COUNT 20
  WITHDIST WITHCOORD
```

This returns the 20 nearest economy drivers within 3 km, sorted by distance, in one Redis call.

### Layer 3: The Dispatch Algorithm — Matching and Offer Flow

```
Rider Requests Ride
       │
       ▼
Dispatch Service receives event (via Kafka or direct gRPC call)
       │
       ├── 1. GEOSEARCH Redis for top-20 nearby available drivers
       │         Filter: driver status == 'available', vehicle_type matches
       │
       ├── 2. For each candidate, fetch from Redis:
       │         driver status hash → lat, lon, heading
       │         → compute road-network ETA (routing engine call)
       │         → score = α × ETA + β × acceptance_rate_penalty
       │
       ├── 3. Sort by score, build ordered offer queue [d1, d2, ... d20]
       │
       ├── 4. SETNX "lock:driver:{d1.id}" {trip_id} EX 15
       │         If SETNX returns 0 → driver just got locked by another dispatch
       │         → try d2
       │
       ├── 5. Send offer to d1 via WebSocket:
       │         { trip_id, rider_name, pickup_location, estimated_fare }
       │
       ├── 6. Start 10-second offer timer
       │         If driver accepts → transition trip to 'matched', DEL lock key
       │         If driver declines → DEL lock key, try d2
       │         If timer fires (no response) → DEL lock key, try d2
       │
       └── 7. If all 20 candidates exhausted and no match → 
                 retry with radius expansion to 5 km
                 After 60 seconds total → status = 'no_driver_available'
```

**WebSocket Server Affinity — The Hidden Problem**

Every online driver maintains a persistent WebSocket connection to exactly one Dispatch Service instance. When the Dispatch Service needs to send an offer to driver `D`, it must find which instance holds `D`'s connection.

Solution: when a driver establishes a WebSocket connection, the Dispatch instance writes:
```
SET driver:{driver_id}:ws_server "dispatch-server-07" EX 30
```
This key is refreshed every heartbeat. When another Dispatch instance needs to notify a driver, it looks up the ws_server key and forwards the message to the correct instance via internal gRPC. If the key is expired, the driver is considered offline.

**The Double-Assignment Race Condition**

Two riders request rides simultaneously. The same driver D appears in both candidate lists. Both Dispatch workers try to offer D the ride at the same time.

Fix: `SETNX "lock:driver:{driver_id}" {trip_id} EX 15` (Set-if-Not-Exists, atomic). Only one caller wins. The loser must skip to the next candidate. This is a Redis distributed lock pattern (a simplified Redlock for single-master, which is sufficient here because losing a lock just means the driver gets one offer at a time).

## Step 7 — Deep Dive: Trip State Machine

The trip state machine is the second hardest component because it involves distributed state, optimistic locking, idempotency, and event ordering.

### Layer 1: The State Diagram

```
                    ┌─────────────┐
                    │  REQUESTED  │ ← Rider taps "Request"
                    └──────┬──────┘
                           │ Dispatch begins
                           ▼
                    ┌─────────────┐
                    │  SEARCHING  │ ← System looking for driver
                    └──────┬──────┘
                           │ Driver accepts offer
                           ▼
                    ┌─────────────┐
            ┌──────►│   MATCHED   │ ← driver_id set, rider notified
            │       └──────┬──────┘
            │              │ Driver reaches pickup
            │              ▼
            │       ┌─────────────┐
            │       │   ARRIVED   │ ← Driver taps "I'm here"
            │       └──────┬──────┘
            │              │ Rider enters car
            │              ▼
            │       ┌─────────────┐
            │       │ IN_PROGRESS │ ← Fare meter running, GPS recording
            │       └──────┬──────┘
            │              │ Arrival at dropoff
            │              ▼
            │       ┌─────────────┐
            │       │  COMPLETED  │ ← Fare computed, driver frees up
            │       └──────┬──────┘
            │              │ Payment processed
            │              ▼
            │       ┌─────────────┐
            │       │   SETTLED   │ ← Payment confirmed, final record
            │       └─────────────┘
            │
            │  Any state before IN_PROGRESS:
            └── CANCELLED ← Rider cancels or no driver found
```

### Layer 2: Optimistic Locking to Prevent Race Conditions

The `trips` table has a `version` column. Every update uses CAS (Compare-And-Swap):

```sql
-- Transition from MATCHED to ARRIVED
UPDATE trips
   SET status = 'driver_arrived',
       updated_at = NOW(),
       version = version + 1
 WHERE id = $1
   AND status = 'matched'          -- guard: must be in the expected state
   AND version = $2                -- guard: no concurrent update occurred
RETURNING *;

-- If 0 rows returned: concurrent update won, retry or return 409 Conflict
```

This is safer than SELECT FOR UPDATE (which holds a lock) because it doesn't block concurrent readers and handles the case where an event arrives out of order (e.g., a "driver arrived" event that arrives after a "trip completed" event due to network delays).

### Layer 3: Idempotency and Event Ordering

**Problem:** Mobile networks are unreliable. The driver taps "Start Trip" but the request fails due to a timeout. The app retries. The Trip Service receives two `start_trip` events for the same trip. Without idempotency, the trip gets double-started.

**Solution:** Every state-changing API call includes an `idempotency_key` header (UUID generated by the client). The Trip Service stores processed idempotency keys in Redis with a 24-hour TTL:

```
Key: "idempotency:{trip_id}:{idempotency_key}"
Value: { status_code, response_body }
TTL: 86400 seconds
```

If the same idempotency key arrives twice, the Trip Service returns the cached response without reprocessing the state transition.

**Event sourcing for the audit trail:** Every state transition appends a row to `trip_events`. This gives a complete audit trail for dispute resolution, fraud detection, and fare adjustments. The events are also published to Kafka so downstream systems (payments, analytics) can react.

**Payment settlement flow:**
```
trip.status = 'completed'
    │
    ▼ (Kafka event consumed by Payment Service)
Payment Service:
    1. Read final_fare from trips table
    2. Call Stripe: capture PaymentIntent (authorized at ride-request time)
    3. On success: UPDATE trips SET payment_status='charged', status='settled'
    4. On failure: retry 3x with exponential backoff
                   If all fail: flag for manual review, notify rider
```

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (100M DAU, 300M trips/day, 10M concurrent drivers)

**Bottleneck: Redis write throughput for location updates**

10M concurrent drivers × (1 update / 4 sec) = **2.5M writes/second** into Redis.

A single Redis primary (even a 32-core machine) tops out at ~500K geospatial ops/second.

**Fix: Partition the geo index by city/region**

Instead of one `drivers:geo:economy` key, use:
```
drivers:geo:economy:san_francisco
drivers:geo:economy:new_york
drivers:geo:economy:london
```

Each key maps to a Redis instance in the nearest data center. A driver's update goes to the shard for their current city. A GEOSEARCH query for nearby drivers only hits one shard. This reduces per-shard load by the number of cities (10,000+) — easily back within limits.

**Secondary bottleneck: Dispatch Service fan-out**

At 10x load, 17,350 new dispatch jobs/second. Each dispatch job makes a Redis call + 20 routing engine calls (for ETA scoring). 20 routing calls × 17,350 dispatches/second = 347,000 routing engine requests/second.

**Fix:** Cache ETA estimates for driver-to-cell pairs. H3 cell resolution 9 (~100m²) cells are small enough that a driver's ETA to any point within a cell is approximately constant for 30 seconds. Cache: `eta:{driver_id}:{h3_cell}` → ETA in seconds, TTL 30s.

### At 100x Current Load (1B+ DAU, 3B trips/day)

**Bottleneck: PostgreSQL Trip Service write throughput**

3B trips/day × 6 state transitions = 18B writes/day = 208K writes/second to PostgreSQL.

A well-tuned PostgreSQL primary handles ~20K–40K writes/second. We are 5-10x over capacity.

**Fix: Shard trips by city/region**

Each city cluster gets its own PostgreSQL primary + replicas. A trip in San Francisco never touches the New York database. Add a routing layer (Vitess or a custom router) that maps `trip_id → shard_id` using consistent hashing with the city embedded in the trip_id prefix.

**Fix 2: Move to Google Cloud Spanner for the trips table**

Uber actually did this — published "Building Uber's Fulfillment Platform for Planet-Scale using Google Cloud Spanner" in 2022. Spanner provides globally consistent ACID transactions across regions with 99.999% availability and horizontal scaling via automatic sharding. The cost is higher, but at 1B+ DAU the engineering cost of managing custom sharding exceeds Spanner's pricing.

**Secondary bottleneck: Kafka topic partition exhaustion**

At 100x load, the `driver-locations` Kafka topic processes 25M events/second. Standard Kafka partitions max out at ~100K events/second per partition, requiring 250 partitions per topic. Consumer groups for surge pricing and analytics must be able to keep up.

**Fix:** Switch to a tiered storage model — Kafka for hot data (last 1 hour), offload to S3/Iceberg for historical. Use Flink for real-time aggregation (surge calculation) to avoid reading from Kafka raw.

### At 1000x Current Load (Global dominance, all taxis)

**Fundamental challenge: Cross-region consistency**

At 1000x, every region becomes a fully independent cluster. But what happens when a rider's app is roaming (e.g., from US to Mexico)? The trip data lives in the US cluster. The Mexican driver is in the MX cluster.

**Required architectural changes:**

1. **Trip portability:** Trips get a globally unique ID with a region prefix. The originating region is authoritative. Cross-region reads go through a global routing layer.

2. **Active-active multi-region:** Each region handles its own dispatch, location index, and trip state independently. A global Kafka backbone (using replication) propagates events for analytics and cross-region features (e.g., airport pickups where a driver from one zone picks up in another).

3. **H3 cell ownership:** Each H3 cell at resolution 5 (city-level, ~252 km²) is owned by exactly one region for surge computation. Drivers moving between cells trigger a ownership-transfer event.

4. **CRDT for driver availability:** Instead of single-writer locks, use a Conflict-Free Replicated Data Type for the driver availability flag, allowing each region to independently mark a driver as unavailable and converge without central coordination.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Live driver location store | Redis sorted set (GEOADD) | PostgreSQL + PostGIS | Redis handles 250K writes/sec; Postgres saturates at ~20K |
| Geospatial indexing for analytics | Uber H3 hexagonal grid | Geohash (rectangular cells) | Hexagons have equidistant neighbors; no boundary distortion; equal-area cells |
| Driver-rider matching | Sequential greedy (best ETA → offer → timeout → next) | Global optimal bipartite matching | Greedy is O(K) per dispatch; global optimal is NP-hard at this scale |
| Trip state consistency | Optimistic locking (version column) | Pessimistic locking (SELECT FOR UPDATE) | Optimistic lock doesn't block readers; handles out-of-order events gracefully |
| Driver notification channel | WebSocket (persistent connection) | HTTP Long-Poll / SSE | WebSocket enables sub-second bidirectional messaging; Long-Poll adds latency |
| WebSocket affinity tracking | Redis key with TTL | Consistent hashing on driver_id | Drivers can reconnect to any server; Redis key adapts; consistent hashing requires sticky routing |
| Trip database | PostgreSQL (ACID, strong consistency) | Cassandra (eventually consistent) | Trip records are financial; double-charges and missed payments require strong consistency |
| Surge pricing update frequency | 30-second window per H3 cell | Real-time per-request calculation | Prevents price flickering; 30s is fast enough for supply-demand signals; reduces computation |
| Event bus | Kafka (durable, ordered per partition) | RabbitMQ / SQS | Kafka retains events for replay; trip events need to be replayable for analytics |
| Payment authorization timing | At ride-request time (pre-auth) | At trip completion | Pre-auth reduces payment failures at dropoff; rider is more committed to the ride |

## Step 10 — How Real Companies Solved This

### Uber

**What they built and when:**

Uber's original dispatch system was a monolithic Python service. By 2015, it was processing hundreds of thousands of requests per day and the Python GIL (Global Interpreter Lock) was creating serious concurrency bottlenecks. In 2015, Uber rewrote their geofence service in Go and it became the company's highest-QPS service out of hundreds in production — handling ~100K+ QPS with far fewer servers than the Python version.

**H3 — born from dispatch pain:**

Uber's geofence and dispatch teams were using geohash-based indexing, but the rectangular cell boundary problem caused drivers to disappear from the nearest-driver index if they crossed a cell line. Engineers developed H3 (Hexagonal Hierarchical Spatial Index) internally. It was open-sourced in 2018. H3 is now used for surge pricing computation (resolution 7 cells), driver supply heat maps, and demand forecasting. At resolution 9, each cell is ~0.1 km² — small enough for accurate driver-to-pickup matching.

**What they got wrong first:**

Uber ran a single-region active-passive setup until an AWS outage in 2015 took down the entire platform in the US. They then moved to active-active multi-region. In 2022, Uber published that they migrated the Fulfillment Platform (trip matching and booking) to **Google Cloud Spanner** to achieve globally consistent transactions without managing custom sharding. Their blog post cited "billions of database transactions per day" as the scale driver.

**Key engineering blog citations:**
- "How We Built Uber Engineering's Highest Query per Second Service Using Go" (Uber Blog, 2015)
- "H3: Uber's Hexagonal Hierarchical Spatial Index" (Uber Blog, 2018)
- "Building Uber's Fulfillment Platform for Planet-Scale using Google Cloud Spanner" (Uber Blog, 2022)
- "Real-time Data Infrastructure at Uber" (SIGMOD 2021, arXiv:2104.00087)

### Lyft

**What Lyft built differently:**

Lyft initially used PostGIS (PostgreSQL with geospatial extension) for driver location storage. This worked at small scale. As the platform grew, write amplification from spatial index updates on every driver location change caused disk I/O saturation. The PostGIS index had to be rebuilt periodically, causing latency spikes.

The fix: Lyft migrated the live location index to Redis geospatial commands (GEOADD / GEOSEARCH), keeping PostGIS only for persistent historical queries and reporting. The separation of concerns — fast in-memory index for real-time ops, durable relational DB for records — became a key architectural principle.

**Lyft's data platform at scale:**

Lyft processes terabytes of real-time data daily through their data platform. In 2023, they published a post on migrating from Druid to ClickHouse for sub-second analytics queries. Their real-time data pipeline uses Kafka for event ingestion, with Flink for stream processing (surge calculation, demand forecasting). ClickHouse enables their data science team to run ad-hoc queries on driver location history without impacting operational systems.

**What they got wrong first:**

Lyft attempted to use a shared database for both the location index and trip records, with a single PostgreSQL cluster. At growth, the write workload from location updates crowded out trip record writes. The lesson: write patterns for location (250K high-frequency tiny writes) and trip records (10K low-frequency large writes) are fundamentally incompatible, and sharing a database introduces resource contention that is very hard to tune away.

**Key citation:** "How Lyft Localizes Millions of Users" — Lyft Engineering Blog, discusses geospatial challenges in production.

## Interview Perspective

### What the Interviewer Is Evaluating

For this specific problem, interviewers are testing:

1. **Do you know why a relational DB fails for location writes?** — Can you articulate write amplification, index rebuild cost, and why Redis sorted sets are the right tool?
2. **Can you describe the dispatch algorithm in enough detail to implement it?** — Not just "find nearby drivers" but the offer queue, timeout, lock mechanism, and cascade logic.
3. **Do you understand the trip state machine as a distributed system problem?** — Optimistic locking, idempotency, out-of-order events.
4. **Do you understand WebSocket server affinity?** — The hidden problem that many candidates miss. A driver connects to Server A. The dispatch job runs on Server B. How does Server B notify the driver?
5. **Can you reason about the specific bottlenecks at scale?** — Not "add more servers" but "the Redis GEOADD key becomes a hot spot at 10x, partition it by city."

### Junior (L3–L4) Answer

**What they say:** Designs a system with a MySQL database storing driver locations, updated on each GPS ping. Uses a cron job to query `SELECT * FROM drivers WHERE distance(lat, lon, pickup_lat, pickup_lon) < 3000`. Knows they need a mobile app and a backend. May mention WebSocket for real-time updates.

**Depth reached:** Single-region, single-database architecture. Can draw a basic architecture diagram. Knows they need to notify drivers somehow.

**What they miss:** The fundamental write throughput problem with relational DBs. Geospatial indexing. The dispatch offer/timeout/cascade flow. Optimistic locking. WebSocket affinity. Surge pricing data model.

### Senior (L5) Answer

**What they add:**
- Immediately calls out that location writes need Redis or a time-series DB, not MySQL.
- Describes `GEOADD` and `GEOSEARCH` by name.
- Designs the dispatch offer queue with timeout and cascade logic.
- Mentions distributed locks (Redis SETNX) to prevent double-assignment.
- Uses optimistic locking (`version` column) for the trip state machine.
- Designs a Kafka pipeline to decouple location ingestion from analytics.
- Partitions the Redis geo index by vehicle type.

**Separating depth on this problem:** Can explain *why* hexagonal indexing is better than rectangular (equidistant neighbors, no boundary distortion). Can estimate 250K writes/second from first principles. Can describe the WebSocket affinity problem and its Redis-based solution.

### Staff (L6+) Answer

**What they drive to unprompted:**

1. **Cost reasoning:** "Redis cluster for 1M drivers costs ~$15K/month on AWS. At 10x scale, partitioning by city reduces per-shard cost and also improves fault isolation — a Redis failure in Singapore doesn't affect London."

2. **Failure modes:** "What happens if the Dispatch Service restarts mid-dispatch? The Redis lock TTL ensures the driver becomes available again in 15 seconds. But what if the rider's trip is stuck in 'searching' in PostgreSQL? We need a Watchdog service that scans for trips in 'searching' state for >120 seconds and either re-dispatches or cancels them."

3. **Operational concerns:** "GPS spoofing is a real attack. Drivers can fake their location to appear at the airport even when they're not. The Location Service should validate GPS plausibility: if a driver's reported speed exceeds 200 km/h, or if they teleport 10 km in 4 seconds, flag the update and hold the previous verified position."

4. **The matching quality problem:** "Greedy matching (lowest ETA to pickup) is locally optimal but globally suboptimal. If 20 drivers cluster near one pickup and ignore another pickup 500m away, Uber uses a deferred batching window (200ms) to collect incoming requests and run a batch optimization pass before dispatching. This improves pooling efficiency and reduces total vehicle miles traveled."

5. **Regulatory compliance:** "In the EU, driver location data is GDPR-sensitive. Location events in Kafka must be encrypted with a per-driver key. Driver data deletion requests require purging the Kafka log (using log compaction tombstones) and the S3 route history. This must be designed upfront, not bolted on."

### The 4–5 Mistakes Candidates Make On This Specific Problem

1. **Putting driver locations in MySQL or PostgreSQL.** This is the single most common mistake. The write rate (250K/s) is 10x what a well-tuned PostgreSQL can sustain. If you design this with a relational DB for live locations, you will fail the interview at a senior level.

2. **Forgetting WebSocket server affinity.** Candidates design a Dispatch Service and say "send a notification to the driver's WebSocket." They don't explain how they find which server holds the driver's connection. Without this, the design is incomplete for real deployment.

3. **Using polling instead of WebSocket for driver notification.** "The driver app polls every 2 seconds for new offers" means 5M drivers × 0.5 req/s = 2.5M polling requests/second just for driver offer checks, with most returning nothing. WebSocket eliminates this entirely.

4. **No idempotency on state transitions.** Mobile networks cause duplicate requests. Without idempotency keys, a driver tapping "Start Trip" twice starts the fare meter twice. This is a critical correctness bug in a financial system.

5. **Designing geospatial search with a square bounding box and no indexing.** "Select drivers within ±0.03 degrees of latitude/longitude" is not a scalable approach. It misses the geospatial index entirely and results in a full table scan or a slow range scan that doesn't use the spatial index efficiently.

### Key Numbers to Have Memorized for This Problem

| Number | What It Is | Why It Matters |
|---|---|---|
| **250,000 writes/sec** | Peak location update throughput (1M drivers ÷ 4s) | Immediately rules out any relational DB for the location index |
| **< 2 seconds** | Target dispatch cycle time (request → driver notified) | Forces in-memory geospatial query; no disk I/O allowed in the hot path |
| **10–15 seconds** | Driver offer timeout window | Determines cascade logic; must be in Redis lock TTL |
| **4 seconds** | Driver GPS heartbeat interval | Baseline for staleness tolerance and write rate calculation |
| **31 million** | Uber's daily trips (Q3 2024) | Grounds your "at scale" estimates in real numbers |
| **7.1 million** | Uber's active global drivers (2024) | Baseline for concurrent driver calculations |
| **~0.1 km²** | H3 resolution 9 cell size | The granularity at which driver-to-pickup matching operates |
| **60-second TTL** | Driver status key expiry in Redis | The implicit "driver went offline" detection mechanism |
