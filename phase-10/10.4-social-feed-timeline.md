> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Fan-out at scale, celebrity/high-follower hybrid model, feed ranking, real-time vs eventual consistency

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

Design a social feed system where users can post content (tweets, photos, status updates) and see a personalized, time-ordered (or ranked) stream of posts from the accounts they follow. This is the core product loop of Twitter, Instagram, Facebook, and LinkedIn — get it wrong and everything else fails.

At Twitter's peak (pre-Musk), ~500 million tweets were posted per day by ~238 million monetizable daily active users, with home timelines generating ~300,000 reads per second. Instagram crossed 2 billion monthly active users in 2022, with over 100 million photos and videos uploaded daily. The fan-out problem — propagating a single write to millions of readers efficiently — is the defining architectural challenge of this class of system.

---

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Post creation** — Users can create posts (text up to 280 chars, or photo/video with caption). A post is immutable after creation (no edits, or edits tracked separately).
2. **Follow graph** — Users can follow and unfollow other users. The relationship is directed (A follows B does not imply B follows A).
3. **Home timeline** — A logged-in user sees a feed of posts from accounts they follow, ordered by recency (or a ranked relevance score in the ML-enhanced version).
4. **User timeline** — Viewing any public user's own post history, reverse-chronological.
5. **Like / Engagement signals** — Users can like posts; engagement counts are visible. (Retweet/share is a stretch goal.)
6. **Real-time delivery** — New posts from followed accounts should appear in a user's feed within a few seconds of being posted.

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% (4 nines) — feed is core revenue surface |
| Write latency (post creation ACK) | p99 < 500 ms |
| Read latency (home timeline load) | p99 < 200 ms (cached), p99 < 800 ms (cold) |
| Fan-out delivery (post visible in follower feed) | p95 < 5 seconds |
| Consistency model | Eventual — followers may see a post up to 5–10 s late |
| Durability | Posts must never be lost after ACK (sync write to primary DB) |
| Scale | 500M posts/day, 300K timeline read QPS at peak |
| Feed size served per request | Most recent 20 posts (one page), up to 800 cached in memory |

### Out of Scope

- Ads ranking / sponsored content insertion
- Video transcoding pipeline (assume CDN serves pre-encoded video)
- Full-text search over posts
- DM / direct messaging
- Trending topics / hashtag indexing
- Account verification and trust & safety systems
- Rate limiting and spam prevention details

### Clarifying Questions to Ask the Interviewer

1. **Chronological vs. ranked feed?** — "Are we building a pure reverse-chronological feed (Twitter's original model) or a relevance-ranked feed (Instagram, Facebook)? Ranking adds ML infrastructure complexity." This answer doubles the scope if ranked.

2. **What is the expected follower distribution?** — "Do we expect a long-tail power law — most users have < 500 followers, but celebrities have 50M+? That drives the fan-out strategy fundamentally." Almost always yes.

3. **Read:write ratio?** — "Rough target: 100:1 reads to writes? More?" Confirms that the system is read-heavy, which means investing in the read path.

4. **Should inactive users still receive fan-out?** — "If I haven't opened the app in 30 days, should posts still be pushed into my feed cache? Or should we skip them and do lazy pull on next login?" Skipping inactive users dramatically reduces write amplification.

5. **Consistency requirements for counts?** — "Can a post show 1,247 likes when the real number is 1,249? Or do we need exact counts?" Near-exact is almost always acceptable; it affects counter architecture.

6. **Multi-region?** — "Are we building for a single region (US) or globally distributed with regional feeds?" Multi-region introduces cross-region replication lag and partitioned social graph complexity.

7. **Edit / delete?** — "Can users delete posts? Can they edit? Deletion must propagate to all cached timelines, which is a non-trivial invalidation problem." Usually delete yes, edit controversial.

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

| Parameter | Value | Reasoning |
|---|---|---|
| Daily Active Users (DAU) | 300 million | Twitter-scale |
| Monthly Active Users (MAU) | 800 million | ~37% DAU/MAU ratio |
| Average follows per user | 200 | Typical power law median |
| Posts created per day | 500 million | ~300M DAU × 1.67 posts/day |
| Average post size (text) | 300 bytes | 280-char tweet + metadata |
| Average post with media | 150 KB (thumbnail ref) | Photo stored in object storage |
| % posts with media | 30% | Industry estimate |
| Peak:average traffic ratio | 3× | Morning/evening spikes |

### Write QPS

```
Posts per second (avg)  = 500M / 86,400 s  ≈  5,800 posts/s
Posts per second (peak) = 5,800 × 3        ≈ 17,500 posts/s
```

### Read QPS (Home Timeline)

```
Timeline requests/day   = 300M DAU × 10 sessions × 3 refreshes/session
                        = 300M × 30 = 9 billion reads/day
Avg read QPS            = 9B / 86,400  ≈ 104,000 QPS
Peak read QPS           = 104K × 3    ≈ 312,000 QPS  (≈ 300K QPS)
```

This ~53:1 read:write ratio confirms the system is overwhelmingly read-heavy.

### Fan-out Write Amplification

```
Writes injected into timeline cache:
  = posts/s × avg followers
  = 5,800 × 200
  = 1,160,000 cache writes/s (avg)
  = 3,480,000 cache writes/s (peak)

A single celebrity tweet (50M followers) generates:
  = 50,000,000 Redis SET operations
  → must be handled asynchronously, or it blocks the system
```

### Storage

**Post storage (Cassandra / distributed DB):**
```
Text posts:    500M/day × 300 bytes     = 150 GB/day
Media refs:    500M × 30% × 200 bytes   =  30 GB/day  (just the ref, not the blob)
Metadata:      500M × 500 bytes         = 250 GB/day
                                        ─────────────
Total/day:                              ≈ 430 GB/day
Per year:                               ≈ 157 TB/year
5 years (3× replication factor):        ≈ 2.4 PB
```

**Media blob storage (S3/GCS):**
```
Photos: 500M × 30% × 3 resolutions × 200 KB  ≈ 90 TB/day
Videos (stretch):  not in scope
5-year photo storage (no replication):        ≈ 164 PB
```

**Timeline cache (Redis):**
```
Users with active caches:   ~100M (active in last 7 days)
Entries per user:           800 (tweet IDs only, 8 bytes each)
Per-user cache size:        800 × 8 bytes = 6.4 KB
Total Redis footprint:      100M × 6.4 KB = 640 GB
With 2× overhead (hash meta, expiry, encoding):  ≈ 1.5 TB Redis
→ Fits in a Redis cluster of 10-20 nodes (100 GB RAM each)
```

**Social graph (follower/following):**
```
Edges: 300M users × 200 follows = 60B edges
Per edge: ~20 bytes (user_id pairs + timestamp)
Raw storage: 60B × 20 = 1.2 TB
With indexes: ≈ 3 TB
```

### Bandwidth

```
Ingress (post creation):  17,500 posts/s × 300 bytes  ≈ 5 MB/s
Egress (timeline reads):  312,000 QPS × 20 posts × 400 bytes/post  ≈ 2.5 GB/s
```

### Server Count

```
API servers (timeline read, 10K req/s each): 300K / 10K = 30 servers
Fanout workers (async, 50K fan-out writes/s each): 3.5M / 50K = 70 workers
Redis nodes (100 GB RAM each, 1.5 TB needed): ~15-20 nodes
Cassandra nodes (10 TB usable per node, 157 TB/yr): ~20 nodes initially
```

### Write Path (Post Creation)

```
User submits post
      │
      ▼
POST /api/v1/posts  (Write API Server)
      │
      ├── 1. Validate (auth, content, rate limit)
      ├── 2. Generate post_id (Snowflake-style, timestamp-embedded)
      ├── 3. Write post to Cassandra (synchronous, durability)
      ├── 4. Return 201 Created to client  ← ACK here, rest is async
      │
      └── 5. Publish PostCreatedEvent to Kafka topic "post-events"
                │
                ▼
          Fanout Service (Kafka consumer group, 70+ workers)
                │
                ├── a. Read author's follower list from Social Graph Service
                ├── b. Classify: regular user (<10K followers) vs celebrity
                │
                ├── [Regular User]
                │     └── For each follower_id:
                │           - ZADD timeline:{follower_id} {timestamp} {post_id}
                │           - ZREMRANGEBYRANK (keep only top 800)
                │
                └── [Celebrity] → skip fan-out
                      └── Post stored in author's Cassandra post table only
                          (followers pull at read time)
```

### Read Path (Home Timeline)

```
GET /api/v1/timeline/home  (Read API Server → Timeline Service)
      │
      ├── 1. Authenticate user, get user_id
      ├── 2. ZREVRANGE timeline:{user_id} 0 19  → Redis
      │         │
      │         ├── [Cache HIT, ~99% of traffic]
      │         │     └── Returns list of post_ids
      │         │
      │         └── [Cache MISS, cold start / first login]
      │               └── Query Cassandra: SELECT post_id FROM user_timeline
      │                   WHERE user_id = ? ORDER BY created_at DESC LIMIT 800
      │                   → Backfill Redis cache
      │
      ├── 3. Fetch celebrity posts (ALWAYS, even on cache hit):
      │     - Get user's celebrity follows list (from Social Graph)
      │     - For each celebrity: fetch last 10 posts from their Cassandra post table
      │     - Merge with Redis results by timestamp → sorted candidate list
      │
      ├── 4. Hydrate post_ids → full post objects
      │     - Batch GET from Redis post cache (post:{post_id})
      │     - For misses: fetch from Cassandra posts table, cache result
      │
      ├── 5. [Optional] Pass top-100 candidates to Ranking Service
      │     - ML model scores each post (recency, engagement, affinity)
      │     - Returns reordered list of post_ids
      │
      └── 6. Return paginated response (20 posts + next_cursor)
```

### Component Responsibilities

| Component | Why It Exists |
|---|---|
| **Kafka** | Decouples write path from fan-out; buffers bursts; enables replay if fanout workers crash |
| **Fanout Service** | Translates 1 post write into N timeline cache writes; handles the hybrid celebrity logic |
| **Redis Timeline Cache** | Serves 99%+ of timeline reads at sub-ms latency without touching the DB |
| **Cassandra (posts)** | Durable post storage; wide-column layout optimized for time-range queries by user |
| **Social Graph Service** | Provides follower/following lookups; separate service because graph ops are distinct from post ops |
| **Ranking Service** | Optional ML reranking; isolated so algorithmic changes don't require feed infra changes |
| **CDN** | Serves static media (photos, videos) at edge; offloads media bandwidth from origin |

## Step 4 — Data Model

### Core Entities

**posts** (Cassandra, partitioned by `author_id`, clustered by `post_id` DESC)

```
post_id        UUID (Snowflake: time bits + machine bits + seq bits)
author_id      UUID
content        TEXT (max 280 chars for text; null for media-only)
media_urls     LIST<TEXT> (up to 4 CDN URLs)
created_at     TIMESTAMP
like_count     COUNTER (approximate, denormalized)
repost_count   COUNTER
reply_count    COUNTER
is_deleted     BOOLEAN
```

Access patterns:
- Get all posts by user (user timeline): `WHERE author_id = ?` — served by partition key
- Get single post: `WHERE author_id = ? AND post_id = ?`

**user_timeline** (Cassandra, for cold-start backfill only)

```
user_id        UUID  (partition key)
post_id        UUID  (clustering key, DESC)
author_id      UUID
created_at     TIMESTAMP
```

This is a pre-materialized view of the fan-out result, written at fan-out time. Used only when Redis is cold (user hasn't opened app in >7 days). For hot users, Redis is the source of truth.

**users** (PostgreSQL — relational, low write rate, needs ACID for auth)

```
user_id        UUID  PRIMARY KEY
username       VARCHAR(50) UNIQUE
display_name   VARCHAR(100)
avatar_url     TEXT
bio            TEXT
follower_count INTEGER (approximate, updated async)
following_count INTEGER
is_verified    BOOLEAN
created_at     TIMESTAMP
```

**follows** (Social graph — Cassandra or specialized graph store)

```
-- For "who follows user X" (needed for fan-out and follower count)
followers_by_user:
  user_id        UUID  (partition key = the person being followed)
  follower_id    UUID  (clustering key)
  followed_at    TIMESTAMP

-- For "who does user X follow" (needed for timeline read, following list)
following_by_user:
  user_id        UUID  (partition key = the person following)
  followee_id    UUID  (clustering key)
  followed_at    TIMESTAMP
```

Both tables maintained in sync. Write both on follow/unfollow (two-phase with idempotency).

**likes** (Cassandra)

```
post_id        UUID  (partition key)
user_id        UUID  (clustering key)
liked_at       TIMESTAMP
```

Query: "Has user X liked post Y?" — `WHERE post_id = ? AND user_id = ?`

### Important Indexes and Why

| Index | On | Reason |
|---|---|---|
| Primary key on `posts` | `(author_id, post_id DESC)` | Efficient user timeline scan with time ordering |
| Secondary on `users.username` | `username` | Username lookup for @mentions and profile pages |
| `followers_by_user` partition | `user_id` | O(1) lookup for "get all followers of user X" during fan-out |
| `following_by_user` partition | `user_id` | O(1) lookup for "who does user X follow" during timeline merge |

### Database Choice Justification

| Entity | Database | Reason |
|---|---|---|
| Posts | **Cassandra** | Write-heavy, append-only, needs linear horizontal scale, time-series access pattern |
| User profiles | **PostgreSQL** | Low write rate, needs ACID for auth tokens, complex queries (joins with verified status) |
| Social graph | **Cassandra** (Twitter) or **TAO** (Meta) | Huge edge count (60B+), simple lookup patterns, needs horizontal scale |
| Timeline cache | **Redis Sorted Set** | In-memory, O(log N) insert/range-query, native sorted set maps perfectly to time-ordered feed |
| Post cache (hydration) | **Redis Hash** | Hot post objects cached at post_id key for sub-ms hydration |
| Media blobs | **S3 / GCS + CDN** | Object storage for immutable media; CDN for global low-latency delivery |

## Step 6 — Deep Dive: Fan-Out Service (The Hardest Component)

This is where the interview is won or lost. The fan-out service is the engine that converts one write into millions of reads, and every architectural decision in the system traces back to how well you handle this.

### Layer 1 — The Core Problem

When user A (200 followers) posts a tweet:
- The tweet is written once to Cassandra.
- The fanout service must inject `post_id` into 200 separate Redis sorted sets (one per follower).
- At 5,800 posts/second × 200 followers = **1.16 million Redis writes per second** in the average case.

When a celebrity with 50M followers posts:
- Naive fanout: 50M Redis ZADD operations.
- At 100K Redis ops/second per node: requires 500 node-seconds of Redis capacity.
- If the celebrity tweets 10x/hour during an event: system falls over.

### Layer 2 — The Hybrid Strategy (Production Solution)

The production answer is a **hybrid fan-out** with a hard threshold (commonly 10,000 followers at Twitter, ~5,000 at some systems):

```
                    ┌─────────────────────────────────────────────────┐
                    │              FANOUT SERVICE WORKER               │
                    │                                                   │
                    │  Event consumed from Kafka:                       │
                    │  { post_id, author_id, created_ts }              │
                    │                                                   │
                    │  1. Fetch author's follower_count                 │
                    │                                                   │
                    │  2. IF follower_count <= 10,000 (regular user):   │
                    │     ┌──────────────────────────────────┐         │
                    │     │  PUSH FAN-OUT (write fan-out)    │         │
                    │     │                                  │         │
                    │     │  followers = graph.get_followers │         │
                    │     │               (author_id)        │         │
                    │     │                                  │         │
                    │     │  // Filter: skip inactive users  │         │
                    │     │  active = [f for f in followers  │         │
                    │     │    if last_active[f] > 30 days]  │         │
                    │     │                                  │         │
                    │     │  // Batch write to Redis         │         │
                    │     │  PIPELINE:                       │         │
                    │     │    for follower_id in active:    │         │
                    │     │      ZADD timeline:{follower_id} │         │
                    │     │           {created_ts} {post_id} │         │
                    │     │      ZREMRANGEBYRANK             │         │
                    │     │           timeline:{follower_id} │         │
                    │     │           0 -801  (keep top 800) │         │
                    │     └──────────────────────────────────┘         │
                    │                                                   │
                    │  3. ELSE (celebrity, follower_count > 10,000):   │
                    │     ┌──────────────────────────────────┐         │
                    │     │  NO FAN-OUT — skip Redis writes  │         │
                    │     │                                  │         │
                    │     │  Post is stored in Cassandra     │         │
                    │     │  posts table only.               │         │
                    │     │                                  │         │
                    │     │  At read time, Timeline Service  │         │
                    │     │  fetches celebrity posts and     │         │
                    │     │  merges with pre-built feed.     │         │
                    │     └──────────────────────────────────┘         │
                    └─────────────────────────────────────────────────┘
```

**Why this threshold works:**
- A user with 10,000 followers generates at most 10,000 Redis ops per tweet.
- At peak, a prolific regular user might post 50 tweets/day × 10K followers = 500K daily Redis ops — affordable.
- Celebrities are rare (maybe 50,000 accounts on Twitter have >10K followers) but disproportionately read.

### Layer 3 — Read Merge for Celebrity Posts

At read time, the Timeline Service performs a merge step:

```
READ PATH MERGE ALGORITHM
─────────────────────────

Input:
  - Redis feed: post_ids for user (from fan-out of regular users they follow)
    [(post_id_1, ts_1), (post_id_2, ts_2), ..., (post_id_800, ts_800)]
  - Celebrity follows: 0-20 celebrity accounts this user follows
    celebrity_ids = [id_1, id_2, ..., id_k]

Step 1: Fetch candidate set from Redis (O(log N + page_size)):
    ZREVRANGEBYSCORE timeline:{user_id} +inf -inf LIMIT 0 100
    → 100 regular-user post_ids, each with timestamp as score

Step 2: Parallel Cassandra fetches for celebrities:
    For each celebrity_id in celebrity_ids:
        SELECT post_id, created_at FROM posts
        WHERE author_id = celebrity_id
        ORDER BY post_id DESC LIMIT 10
    (Executed as concurrent async requests, bounded by ~20 celebrities)

Step 3: Merge by timestamp (k-way merge, O(N log k)):
    min_heap on (timestamp, post_id)
    Extract top 100 posts from merged stream

Step 4: Hydrate post objects:
    Batch MGET post:{post_id} from Redis post cache
    Cassandra fallback for misses (rare for recent posts)

Step 5: Optional ranking:
    Pass 100 candidates to ML ranking service
    Returns reordered list with personalized scores

Step 6: Return first 20 results + cursor

Total p99 latency target: < 200 ms
  - Redis read:              ~2 ms
  - Celebrity Cassandra:    ~20 ms (parallel, so bottleneck = slowest celebrity fetch)
  - Post hydration:          ~5 ms (Redis pipeline)
  - Ranking service:        ~50 ms (co-located, GPU if needed)
  - Network + serialization: ~10 ms
  ─────────────────────────────────
  Total:                    ~87 ms (well under 200 ms)
```

### Why Not Pure Fan-Out-on-Read?

Pull-only (no Redis cache, build feed at read time by fetching all followed users' posts):
- 300K reads/s × 200 follows × 1 Cassandra query = **60 billion Cassandra queries/second**
- Impossible. Cassandra can handle ~1M queries/sec across a large cluster.
- Read latency would be O(follows) × Cassandra latency = seconds per request.

### Why Not Pure Fan-Out-on-Write for All Users?

Push-only (fan-out to every follower including celebrities):
- Celebrity with 50M followers tweets once = 50M Redis writes.
- 50M × 8 bytes per entry = 400 MB of Redis writes for one tweet.
- Twitter's Beyoncé outage in 2013: celebrity post caused cascading Redis cluster failures when multiple celebrities posted simultaneously during a live event. This is the "celebrity problem" failure mode.

### Inactive User Optimization

Twitter skips fan-out for users who haven't been active in >30 days:

```python
def should_fanout(follower_id):
    last_active = redis.get(f"last_active:{follower_id}")
    if last_active is None:
        return False  # Never active, skip
    days_inactive = (now() - last_active).days
    return days_inactive < 30
```

At Twitter's scale, ~40% of registered users are inactive. Skipping them reduces fan-out writes by ~40%, which is significant at 1.16M writes/second.

**When inactive user returns:** Timeline Service detects Redis cache miss, falls back to Cassandra `user_timeline` table (which is written during fan-out as a durable backup), reconstructs Redis cache from last 800 entries.

### Fanout Worker Scaling

```
Kafka Topic: "post-events"
  - 200 partitions (partition key = author_user_id % 200)
  - 70 fanout worker processes, each consuming multiple partitions
  - Each worker handles ~50,000 fan-out writes/second
  - Auto-scales on Kafka consumer lag metric

Worker internals:
  1. Consume batch of 100 PostCreatedEvents from Kafka
  2. For each event:
     a. Fetch follower list (chunked: 1000 followers at a time from Social Graph)
     b. Classify followers (active/inactive, regular/celebrity)
     c. Build Redis PIPELINE batch (one pipeline per 1000 followers)
     d. Execute pipeline
  3. Commit Kafka offsets only after all Redis writes succeed
  4. On failure: Kafka offset not committed → retry from last checkpoint
```

This gives exactly-once delivery semantics for feed updates (at-least-once delivery + idempotent ZADD = effectively exactly-once).

## Step 7 — Deep Dive: Feed Ranking (Second Hardest Component)

Pure reverse-chronological feeds were abandoned by Facebook in 2009, Instagram in 2016, and Twitter (partially) in 2016-2022. The reason: when a user follows 200 accounts, recency alone produces a bad experience — the most popular/relevant posts get buried under noise.

### Layer 1 — What Ranking Solves

```
Without ranking (reverse-chronological):
  - User follows 200 accounts.
  - A breaking-news account they added last week posts 50 times/day.
  - The feed is dominated by that account.
  - Close friends' posts from 2 hours ago are buried 80 positions down.
  - Engagement drops; user churns.

With ranking:
  - System predicts P(user engages with post) for each candidate post.
  - Reorders the 100 candidate posts by predicted engagement.
  - User sees friends' content near the top, breaking-news in between.
  - Engagement increases ~30-40% (Facebook's reported number for EdgeRank).
```

### Layer 3 — Ranking at Scale

**Problem:** 312K timeline reads/second × ML inference per request = impossible without caching.

**Solution 1: Pre-compute rankings for active users (Twitter's approach)**

```
Background job (runs every 30 min for each active user):
  1. Fetch latest 100 candidate posts from Redis timeline cache
  2. Run ranking model
  3. Store ranked_feed:{user_id} in Redis (TTL 30 min)
  4. On timeline read: serve ranked_feed:{user_id} directly

Tradeoff: ranked feed is up to 30 min stale
          vs
          live ranking: always fresh but 10× more expensive
```

**Solution 2: Approximate ranking using pre-computed scores**

```
At fan-out time, store not just {post_id, timestamp} but also a
"virality score" for the post:
  ZADD timeline:{follower_id}  {virality_score * recency_weight}  {post_id}

This uses Redis's native score for approximate ranking without a separate
ML inference step at read time.
Tradeoff: less personalized (same virality score for all viewers)
          but O(1) reads instead of O(N) ML inference
```

**Solution 3: Hybrid (Instagram's approach)**

```
- For power users (open app > 5x/day): run live ML ranking on each request
  (these users notice staleness; personalization ROI is high)
- For casual users (< 2x/day): serve pre-computed ranked feed (TTL 2h)
- Segment at read time based on user activity profile
```

### Feed Refresh and Cursor Design

```
Cursor-based pagination using Snowflake post_id:

  First load:  GET /timeline/home → returns posts 1-20, cursor = post_id[20]
  Scroll:      GET /timeline/home?cursor=<cursor> → returns posts 21-40

  Snowflake ID structure:
    [41 bits: milliseconds since epoch] [10 bits: machine id] [12 bits: seq]
    → IDs are monotonically increasing, time-ordered
    → cursor = last seen post_id → "give me posts older than this ID"
    → consistent pagination even as new posts arrive (new posts get higher IDs)

  Redis query:
    ZRANGEBYSCORE timeline:{user_id} -inf (cursor LIMIT 0 20
    (exclusive lower bound using open-interval syntax)
```

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load

**Scale:** 3M posts/day → 5M posts/day (already at 50M posts/day at 10x), 3M QPS reads.

**Bottleneck: Redis timeline cache write throughput.**

The fan-out service generates 12M writes/second to Redis. A single Redis node handles ~100K ops/second. Even with 200 Redis nodes, 12M/200 = 60K ops/node — workable, but any hot shard (a follower who follows many prolific users) becomes a bottleneck.

**Fix:**
- Shard Redis timeline by consistent hashing on `user_id`.
- Use Redis Cluster (16,384 hash slots) — handles hot shards by rebalancing.
- Increase fan-out worker pool proportionally (1,000 workers instead of 70).
- Re-evaluate celebrity threshold: lower from 10K to 5K followers to reduce per-tweet fan-out.

**Bottleneck 2: Cassandra post table write throughput.**

50M posts/day = 580 writes/second at 10x → manageable, but media metadata grows. Add Cassandra nodes (horizontal scale is the design guarantee).

### At 100x Current Load

**Scale:** 500M posts/day → 50B posts/day (unrealistic but educational), 30M QPS reads.

**Bottleneck: Social graph service — follower list reads.**

Fan-out workers must fetch follower lists for every post. At 100x, fan-out is running 700K workers querying the social graph at 70M reads/second. Even with Cassandra, this saturates the social graph cluster.

**Fix:**
- **Cache follower lists** in Redis at fan-out workers (local L1 cache per worker, 5-second TTL).
  - 99% of follower list reads are for recently-active users who just posted.
  - TTL of 5s means follow/unfollow propagation delay of 5s max.
- **Shard fanout workers by author_id** — each author's posts always processed by the same worker, so its follower list stays warm in that worker's local cache.
- **Pre-compute celebrity classification** — store a `is_celebrity` flag on the user record, updated async when follower count crosses threshold. Avoid real-time classification on every post.

**Bottleneck 3: Network bandwidth between fan-out workers and Redis.**

30M write QPS × 100 bytes per write = 3 GB/s network egress from fan-out workers. Standard 10 Gbps NICs are at capacity.

**Fix:** Switch to 25 Gbps NICs; deploy fan-out workers in same datacenter rack as Redis nodes (intra-rack bandwidth is 100+ Gbps).

### At 1000x Current Load

**Scale:** 300B QPS reads. This is beyond any single platform today, but the architectural changes are instructive.

**Fundamental change required: Geo-partitioned feeds.**

You cannot serve 300B QPS from a single region. The fundamental architecture must shift:

1. **Regional fan-out:** Partition users into geographic regions (US, EU, APAC). Fan-out only within a user's home region. A Seoul-based user following a New York-based celebrity gets their posts via a cross-region feed sync, not direct fan-out.

2. **Hierarchical cache:** Global → Regional → City-level CDN for extremely hot posts (viral content read by millions of users in the same region can be cached at CDN edge, not Redis).

3. **Federated social graph:** The 60B edge social graph must be sharded by geographic region with cross-region replication only for inter-region follows (rare: most users follow people in their own region).

4. **Write-ahead fan-out log:** Instead of Redis sorted sets, switch to an append-only feed log (like Apache Pulsar or Kafka itself as the feed storage), with consumers materializing views on demand. This enables replaying the feed from any point without backfill.

5. **CRDT-based engagement counters:** At this scale, exact like counts require distributed transactions. Use CRDTs (Grow-Only Counters) that converge eventually without coordination.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Fan-out strategy | Hybrid (push for regular, pull for celebrity) | Pure push or pure pull | Pure push breaks on celebrity problem; pure pull too slow for read QPS |
| Timeline storage | Redis sorted set (post_ids only) | Store full post in cache | Post IDs are 8 bytes; full posts are 400 bytes. 50× memory savings; hydrate on read |
| Timeline cache size | 800 entries per user | Infinite / full history | 99% of reads are for top-20. 800 entries covers 40 pages; sufficient for any session |
| Celebrity threshold | 10,000 followers | 100K or adaptive | Low enough to protect against moderate influencers; high enough not to penalize normal growth |
| Post ID generation | Snowflake (time-ordered UUID) | Auto-increment PostgreSQL | Distributed ID generation without coordination; time-ordering enables cursor pagination |
| Primary post DB | Cassandra | MySQL / PostgreSQL | Time-series append-only writes, horizontal sharding, no JOINS required |
| User profile DB | PostgreSQL | Cassandra | ACID needed for auth; complex queries; low write rate fits RDBMS well |
| Feed ranking | Optional ML layer on top of recency | Pure chronological | Chronological is simpler but engagement is 30-40% lower per Facebook data |
| Inactive user fanout | Skip users inactive >30 days | Fan-out to all | 40% write reduction for no UX cost; inactive users rebuilt from Cassandra on return |
| Delete propagation | Async Kafka event, lazy ZREM | Synchronous delete from all caches | Synchronous delete of celebrity post from 50M caches would take minutes and block writes |
| Consistency model | Eventual (5-10s) | Strong consistency | Strong consistency requires distributed transactions; not needed for social feeds |
| Engagement counters | Redis INCR (approximate) + async persist | DB COUNT(*) | COUNT(*) at 300K QPS is database-killing; Redis INCR is O(1), ~±0.01% error acceptable |

## Step 10 — How Real Companies Solved This

### Twitter / X

**Initial architecture (2006-2010):**
Twitter's original design was a MySQL monolith with a single `tweets` table. The home timeline was generated at read time with a SQL JOIN: `SELECT tweets.* FROM tweets JOIN follows ON tweets.user_id = follows.followee_id WHERE follows.follower_id = ? ORDER BY created_at DESC LIMIT 20`. This worked for 1M users. At 10M users, the JOIN destroyed MySQL.

**First real-time system (2010-2012):**
Twitter rebuilt the timeline service around Redis. Each user's home timeline became a sorted set of tweet IDs in Redis. A background fanout service, consuming from a MySQL binlog, pushed tweet IDs into follower timelines. This is the architecture Raffi Krikorian described at QCon 2012 — "consuming ~4,600 write requests/second with fanout expanding to ~345,000 write requests/second."

**The celebrity problem failure (2013):**
A single celebrity tweet to 50M followers would generate 50M Redis ZADD commands. Multiple simultaneous celebrity tweets during Super Bowl halftime caused Redis cluster saturation and a partial outage. This forced the hybrid fan-out solution: celebrities above a threshold would not trigger write fan-out. Their tweets are fetched at read time and merged. Twitter publicly discussed this at OSCON 2013.

**FlockDB for the social graph:**
Twitter open-sourced FlockDB in 2010 — a graph database storing adjacency lists (follower/following edges). By 2012 it stored 13 billion edges with 20K write QPS and 100K read QPS. It was eventually replaced by internal systems as Twitter moved toward Manhattan.

**Manhattan database (2014+):**
Twitter's internal real-time distributed KV store, replacing MySQL for most workloads. It serves 10s of millions of read QPS across read-only clusters. Built on top of RocksDB with a distributed coordination layer.

**Key lesson:** The evolution was always driven by a specific bottleneck — JOIN at scale → Redis sorted sets solved read QPS; celebrity writes → hybrid fanout solved write amplification; single-cluster Redis → Redis Cluster with consistent hashing solved hot shard issues. Each fix was targeted, not a full rewrite.

### Instagram / Meta

**Early architecture (2012):**
Instagram's original feed was pure pull: when you opened the app, it fetched the 20 most recent posts from everyone you follow via PostgreSQL. This worked for 1M users. At 10M users during explosive post-Facebook-acquisition growth, the PostgreSQL queries on the follows JOIN became unmanageable.

**PostgreSQL to Cassandra migration (2012-2014):**
Instagram migrated post storage to Cassandra for its write scalability and flexible schema. They retained PostgreSQL for user accounts (where ACID matters) and moved the social graph to an internal system. Instagram engineering wrote publicly about using "a separate follower/following store" (likely a Cassandra-backed service similar to Twitter's social graph service).

**TAO (The Associations and Objects):**
Meta's open-source description of TAO describes it as a write-through cache built on top of MySQL shards, purpose-built for social graph traversals. Facebook uses TAO for all social graph queries — who follows whom, who liked what. TAO runs on thousands of servers and handles billions of reads per day with sub-ms latency for cache hits.

**Feed ranking — EdgeRank (2009) to ML:**
Facebook introduced EdgeRank in 2009 as three signals: Affinity Score (user-author relationship strength), Edge Weight (post type value), and Time Decay (recency penalty). By 2011 they had moved to a machine learning system with 100,000+ features, but the three core signals remain the foundation. Instagram adopted a version of this ranking in 2016 when it moved off chronological feed — a controversial decision that was partially reversed in 2022 when Instagram reintroduced a "Following" chronological option alongside the ranked feed.

**RocksDB-backed Cassandra:**
Instagram engineering published a blog post describing how they replaced Cassandra's default storage engine with RocksDB, improving storage efficiency by ~75% and reducing P99 latency. This is a production engineering optimization that shows up in real interviews: "how do you handle storage cost at Instagram's scale?" — tiered storage with RocksDB compaction.

**Key lesson:** Meta/Instagram's advantage is the shared infrastructure (TAO, Memcached fleet, Cassandra) across Facebook and Instagram. Instagram's rapid scaling (1M to 1B users in ~7 years) was partly possible because it adopted Meta's proven infra rather than building from scratch. The feed ranking investment paid off in engagement — Meta reported that moving to ranked feed increased time-on-platform by 40-70% in A/B tests.

### LinkedIn

**Distinct problem: professional network effects.**
LinkedIn's feed is different because the graph is symmetric (connections, not followers) and the content cadence is lower (people post professionally, not constantly). This means the celebrity problem is less acute (even the most-connected CEOs have ~10M connections, not 100M followers).

**Feed relevance model:**
LinkedIn published details about their "Feed Relevance" system (Xinran He et al., 2014). They use a gradient boosted decision tree (GBDT) to score posts on: connection distance (1st/2nd degree), engagement velocity, content freshness, and user-specific interaction history. The GBDT runs at serving time on a reduced feature set (~50 features), keeping inference to <10ms.

**Key difference from Twitter/Instagram:** LinkedIn treats the feed as a discovery mechanism for professional content, not just a social connection tool. They explicitly boost content from outside your immediate network if it has high engagement — a deliberate product decision that changes the ranking architecture.

## Interview Perspective

### What the Interviewer Is Evaluating

This specific problem tests:
1. **Fan-out intuition** — Do you understand why naive push OR pull fails? Can you arrive at hybrid independently?
2. **Data structure knowledge** — Do you know Redis sorted sets well enough to describe the ZADD/ZREVRANGE pattern?
3. **Scale reasoning** — Can you calculate fan-out amplification and identify where it breaks?
4. **The celebrity problem** — Do you bring this up unprompted? It's the canonical gotcha in this problem.
5. **Consistency/freshness tradeoffs** — Do you understand why eventual consistency is acceptable here?
6. **Ranking awareness** — Do you know that ranked feeds are more complex than chronological, and can you describe why companies invest in it?

### Junior (L3-L4) Answer

**What they say:** "We can use a database to store posts, and when a user requests their feed, we query all the users they follow and merge the results." Maybe mentions caching. Describes push vs. pull but picks one without reasoning about why the other fails.

**Depth they reach:** One-layer deep. Can draw a basic architecture with a DB and cache. Correctly identifies that we need an index on `(author_id, created_at)`. Doesn't bring up the celebrity problem.

**What they miss:**
- The celebrity problem (50M followers → write amplification disaster)
- Inactive user optimization
- Redis sorted sets as the specific data structure
- Fan-out write amplification math
- Why Cassandra over MySQL for posts
- Cursor-based pagination (proposes OFFSET instead)

### Senior (L5) Answer

**What they add:**
- Arrives at hybrid fan-out without being prompted: "users with many followers are a special case — we shouldn't fan-out to their followers, we pull instead."
- Correctly identifies the threshold concept (even if exact number varies).
- Describes Redis sorted sets explicitly: "ZADD timeline:{user_id} with score = timestamp."
- Discusses Cassandra for post storage with reasoning: "append-heavy, no JOINs, horizontal scale."
- Calculates fan-out amplification in rough numbers: "5K writes/s × 200 followers = 1M Redis ops/s."
- Mentions Kafka for async fan-out decoupling.

**Depth they reach:** Two layers deep on fan-out. Can explain why the hybrid exists. Correctly handles the read merge path for celebrity posts.

### Staff (L6+) Answer

**What they drive to unprompted:**
- **Inactive user skip optimization** — "We don't fan-out to users inactive for >30 days. Reduces write amplification by 40% at Twitter. On re-activation, we rebuild from Cassandra." Nobody mentions this at L5.
- **Exactly-once semantics for fan-out** — "We commit Kafka offsets only after Redis writes succeed. If fan-out worker dies, it replays from last committed offset. ZADD is idempotent, so replaying is safe."
- **Cold start / cache miss path** — "Redis TTL evicts timelines for inactive users. We maintain a durable Cassandra `user_timeline` table as the cold-start source. Without this, returning users see an empty feed."
- **Delete propagation** — "Deleting a celebrity's post requires ZREM from up to 50M timelines. We handle this lazily: tombstone the post in Cassandra, filter at read time. The ZREM happens async over hours."
- **Cost reasoning** — "1.5TB Redis cluster at $0.30/GB-hour for ElastiCache r6g = ~$13K/month. We can cut this by 60% by switching post IDs from 8-byte int to 5-byte packed int (post IDs fit in 40 bits with our Snowflake scheme) and using Redis List instead of Sorted Set for pure-chronological feeds."
- **Ranking feedback loops** — "ML ranking requires training data. We log (user_id, post_id, action, position) in Kafka → Flink → data warehouse. The position matters: a like from position 1 is weak signal (they saw it first anyway); a like from position 15 is strong signal. Position-adjusted CTR models."

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **Proposing fan-out-on-write for all users** — The most common mistake. Candidates build the fan-out system correctly for normal users, then when asked "what if a user has 50 million followers?" they say "it's the same, just more writes." This shows they haven't thought through write amplification at scale. The correct answer is: that user is a celebrity; we don't fan-out; we pull at read time.

2. **Storing full post content in the timeline cache** — Candidates will say "store the tweet text in Redis so reads are fast." This is wrong. The timeline cache should only hold `post_id` values (8 bytes each). Full posts are 400+ bytes. At 800 entries × 100M users, storing full content would require 32 TB of Redis vs 640 GB for IDs only. Hydration is a separate step.

3. **Forgetting the cold-start / cache miss path** — The happy path is Redis HIT. Candidates who only design the happy path miss the scenario where a user returns after 30 days and their Redis timeline has expired. Without a Cassandra-backed `user_timeline` table, you either serve an empty feed or make an extremely expensive social graph + post fetch.

4. **Proposing OFFSET pagination** — "Return the next 20 posts with OFFSET 20." This is catastrophically slow in any database at scale (Cassandra and Redis both require scanning to OFFSET). The correct answer is cursor-based pagination using the Snowflake post ID as the cursor — efficient, stable under concurrent inserts, and O(log N) in Redis.

5. **Ignoring delete and invalidation** — Designing only the happy write path. Real systems deal with post deletion, account suspension, and content moderation. A post from a suspended account should not appear in timelines. The naive approach (ZREM from all follower caches) is O(followers) and catastrophically slow for celebrities. The correct answer is: tombstone in DB, filter at read time for celebrities; lazy ZREM for regular users via async queue.

### Key Numbers to Have Memorized for This Problem

| Number | Value | Context |
|---|---|---|
| Twitter peak timeline read QPS | ~300,000 QPS | The read target this architecture must serve |
| Redis timeline cache size per user | 800 entries | Twitter's published limit; 8 bytes per entry = 6.4 KB/user |
| Celebrity fan-out threshold | ~10,000 followers | Switch from write fan-out to read-at-merge |
| Fan-out amplification | 5,800 writes/s × 200 = 1.16M cache writes/s | Shows why fan-out is expensive |
| Inactive user cutoff | 30 days | Skipping inactive users reduces writes by ~40% |
| EdgeRank time decay half-life | ~7 hours | Posts lose ~50% of their score in 7 hours |
| Single Redis node throughput | ~100,000 ops/second | Sizing Redis cluster: 1.16M ops/s → 12+ nodes |
| Cassandra write throughput per node | ~10-50K writes/s | Sizing the post storage cluster |

## Summary

The social feed timeline is a microcosm of distributed systems engineering: a fundamentally read-heavy problem that requires write-time investment (fan-out) to make reads fast, but that write-time investment creates its own catastrophic failure mode (celebrity problem) that can only be solved by selectively reverting to read-time work. The final architecture is a hybrid that does neither purely — and understanding why both extremes fail, and exactly where to draw the hybrid boundary, is what separates candidates who have thought deeply about this from those who have only surface knowledge.

The two other problems this question is really asking about are:
1. **Data structure selection** — Redis sorted sets are not generic "caching," they are a specific data structure with specific complexity guarantees that happen to map perfectly to time-ordered feeds.
2. **Eventual consistency as a feature** — Social feeds do not need strong consistency. A 5-second delivery delay is acceptable and enables the entire async fan-out architecture. Candidates who over-engineer consistency (synchronous fan-out, distributed transactions for counters) will fail the scale analysis.
