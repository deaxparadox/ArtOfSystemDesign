## Problem Statement

Design a search autocomplete system (typeahead) that suggests the top-K relevant completions as a user types into a search box, returning results within 100ms so suggestions appear to update instantaneously with each keystroke.

This system powers Google Search (8.5 billion queries/day), Bing, YouTube search, LinkedIn people search, Amazon product search, and every major search experience on the internet. At Google scale, the autocomplete system must serve ~100,000 requests per second with sub-50ms p99 latency while keeping suggestions fresh enough to surface trending queries within minutes to hours.

---

## Step 1 — Clarify Requirements

### Functional Requirements

1. **Prefix-based suggestions**: Given a typed prefix (e.g., "twit"), return the top-5 completions (e.g., "twitter", "twitch", "twitter login", ...) ranked by global search frequency.
2. **Ranking**: Suggestions are sorted by popularity (search frequency) descending. The most searched completions for a given prefix appear first.
3. **Freshness**: New trending queries (e.g., a breaking news event) should surface in suggestions within a configurable window — target: within 15 minutes for major trends, within 24 hours for normal queries.
4. **Personalization (optional)**: For logged-in users, blend personal search history with global frequencies. Treat this as optional scope.
5. **Multi-language support**: Support ASCII and Unicode prefixes (Chinese, Arabic, etc.).
6. **Safe search filtering**: Suppress adult, harmful, or policy-violating completions.

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% (4.3 min downtime/month) — search autocomplete is user-facing |
| Read latency (p99) | < 100ms end-to-end; < 10ms at the service level (excluding network) |
| Write latency | Eventual — frequency updates can be asynchronous |
| Consistency | Eventual consistency is acceptable — a slightly stale suggestion is fine |
| Durability | Trie snapshot must be recoverable; losing 15 min of frequency updates is acceptable |
| Throughput | Handle 100K read QPS at peak; 1K write events/sec for frequency updates |
| Result count | Return exactly top-5 suggestions per prefix |

### Out of Scope

- Full-text search (returns documents, not query suggestions)
- Spell-check / "did you mean" correction
- Semantic/vector search for suggestions
- Ads injection into suggestions
- Real-time personalization at query time (we may pre-compute personal tries)
- A/B testing framework for suggestion ranking

### Clarifying Questions to Ask the Interviewer

1. **How many suggestions to return?** "I'll assume top-5 for now — similar to Google. Does that match your expectation?" — This determines how much data you cache at each trie node.

2. **How fresh must suggestions be?** "Should a trending query appear within seconds, minutes, or hours?" — This fundamentally changes the write path: seconds requires a streaming approach; hours allows batch MapReduce.

3. **Is personalization in scope?** "Should a user's own search history influence their suggestions?" — Personalization requires per-user storage and query-time blending, significantly increasing complexity.

4. **Is the query space bounded?** "Are we autocompleting over a fixed catalog (products, people) or open-ended search queries?" — A fixed catalog allows pre-indexing all strings. Open-ended requires handling arbitrary new queries.

5. **What is the expected character set?** "ASCII-only, or full Unicode?" — Unicode requires handling multi-byte characters in the trie and changes storage estimates significantly.

6. **Is query filtering/moderation required?** "Do we need to suppress harmful or adult suggestions?" — If yes, we need a denylist layer and a content moderation pipeline.

7. **Mobile vs. desktop latency budget?** "Is the 100ms budget measured from client keypress to suggestion rendered, or at the backend service boundary?" — Mobile adds ~40-80ms RTT; this determines how aggressively we need to cache at CDN or client.

## Step 2 — Capacity Estimation

### Assumptions

```
DAU                     = 500 million users
Searches per user/day   = 5 searches
Keystrokes per search   = avg 4 characters typed before selecting a suggestion
Autocomplete requests   = 500M × 5 × 4 = 10 billion requests/day
```

### Read QPS

```
Peak read QPS  = 10B / 86,400 seconds × 2 (peak factor) ≈ 230,000 QPS
Steady-state   ≈ 115,000 QPS
Design target  = 150,000 read QPS (with room for growth)
```

### Write QPS (frequency updates)

```
Completed searches (signals) = 500M × 5 = 2.5 billion events/day
Write QPS (raw events)       = 2.5B / 86,400 ≈ 29,000 events/sec (peak ~58K)
After batch aggregation      = we batch in 1-min windows → ~2.5B / (60 × 86,400) ≈ not applicable
Stream processing throughput = ~30,000 events/sec ingress to Kafka
Trie update frequency        = once per 10-15 minutes (batch rollup) → ~100 trie writes/min
```

### Storage

```
Unique query strings in index    = 5 billion (Google-scale; we'll design for 500M)
Average query length             = 20 characters
Raw query storage                = 500M × 20 bytes = 10 GB

Trie node storage:
  - Each node: character (1B) + children pointers (8B × 26 avg) + top-5 suggestions (5 × 50B) = ~470B/node
  - Nodes in trie                ≈ 500M × 20 chars × 0.5 (sharing factor) = 5 billion nodes
  - This is too large for memory; we cap the trie to top 10M queries
  
Capped trie (top 10M queries):
  - Nodes                       ≈ 10M × 20 × 0.3 = 60M nodes
  - Storage per node            ≈ 470 bytes
  - Total trie memory           ≈ 60M × 470B = 28 GB (fits on 1-2 servers with modern RAM)

Frequency database (all queries):
  - 500M queries × (20B key + 8B count + 8B timestamp) = ~18 GB
  - With indexes × 3                                   ≈ 54 GB (fits in a moderate Cassandra cluster)

Query log (Kafka / raw events):
  - 30,000 events/sec × 100 bytes/event               = 3 MB/sec
  - Daily raw log                                      = 3 MB × 86,400 ≈ 260 GB/day
  - Retain 30 days                                     ≈ 7.8 TB (Kafka retention on cheap storage)
```

### Bandwidth

```
Request payload  = 50 bytes (prefix string)
Response payload = 5 suggestions × 50 bytes avg = 250 bytes
Total per req    = 300 bytes

Egress bandwidth = 150,000 req/sec × 250 bytes = 37.5 MB/sec ≈ 300 Mbps
Ingress bandwidth = 150,000 × 50 bytes = 7.5 MB/sec ≈ 60 Mbps
```

### Cache Sizing

```
Top 1% of prefixes handle 80% of traffic (Zipfian distribution)
Unique prefixes actively queried: ~1M distinct prefixes in a 5-min window
Cache entry size: prefix (20B) + 5 suggestions (250B) = 270 bytes
Cache size needed: 1M × 270B = 270 MB — fits in a single Redis instance
```

### Server Estimate

```
Each API server handles ~5,000 req/sec (at 50ms avg latency, 250 concurrent)
Servers needed for 150K QPS: 150,000 / 5,000 = 30 API servers
Trie servers: 2-4 (one active, one hot standby per shard)
Cache servers: 3-5 Redis nodes (270MB data, replicated)
```

### Component Responsibilities

**CDN Layer**: Caches responses for the most popular prefixes at geographic edge nodes. At Google scale, ~40% of autocomplete requests are for very common prefixes ("the", "how to", "weather"). A 60-second TTL gives acceptable freshness while dramatically reducing origin load.

**Load Balancer**: Uses consistent hashing on the first 2 characters of the prefix to route requests to the same set of API servers. This increases Redis cache hit rates because the same server/cache node always handles "tw\*" prefixes.

**API Servers**: Stateless Go/Java services. Each request: (1) check Redis cache, (2) if miss, query Trie Service via gRPC, (3) apply Filter Service denylist, (4) return top-5.

**Redis Cache**: Stores the fully computed top-5 suggestion list for a given prefix. This is the hot path — a cache hit avoids all downstream calls. TTL of 5 minutes balances freshness with hit rate.

**Trie Service**: Hosts the in-memory trie data structure. Can be embedded in-process with the API server (avoids gRPC overhead) or run as a separate gRPC sidecar loaded from a snapshot. On startup, loads a serialized snapshot from S3 in ~30 seconds.

**Filter Service**: Maintains a bloom filter of policy-violating query strings. Applied as a post-filter on trie results before returning to the client.

**Kafka**: Decouples the write path. Search completion events are published to Kafka so the autocomplete service never blocks on frequency updates.

**Stream Processor (Flink)**: Consumes Kafka events, maintains approximate frequency counts using Count-Min Sketch, enables near-real-time trending detection.

**Batch Processor (Spark)**: Runs every 15 minutes on the full event log in Cassandra, producing accurate global counts used to rebuild the trie.

**Trie Builder**: Reads the top-10M queries by frequency from Cassandra, builds a new trie in memory, serializes it to S3, and signals Trie Service instances to hot-reload it.

## Step 4 — Data Model

### Core Entities

#### 1. `query_frequency` (Cassandra)

```
Table: query_frequency
Partition key: (query_text)          -- VARCHAR, normalized to lowercase
Columns:
  query_text        VARCHAR          -- "twitter login"
  global_count      COUNTER          -- total searches, all time
  window_count_1h   BIGINT           -- searches in last 1 hour (for trending)
  window_count_24h  BIGINT           -- searches in last 24 hours
  last_seen_ts      TIMESTAMP        -- when last searched
  language          VARCHAR(5)       -- "en", "zh", "ar"
  safe_search_ok    BOOLEAN          -- false if filtered

Primary Key: (query_text)
Clustering: none needed (direct lookup by exact key)

Secondary index: (global_count DESC) -- for top-K queries scan during trie rebuild
```

Why Cassandra: High write throughput for counter updates (COUNTER type is atomic in Cassandra), linear horizontal scalability, tunable consistency (write with ONE, read with LOCAL_QUORUM for trie rebuild).

#### 2. `search_event` (Kafka + S3/Parquet archive)

```
Kafka message schema (Avro):
  event_id          UUID
  user_id           UUID (nullable for anonymous)
  session_id        UUID
  query_text        VARCHAR
  timestamp_ms      BIGINT
  locale            VARCHAR(10)     -- "en-US"
  platform          ENUM(WEB, IOS, ANDROID)
  result_selected   BOOLEAN         -- did user click a suggestion?
  selected_rank     INT             -- which suggestion (1-5) was clicked
```

Why Kafka: Decouples write path. Producers (API servers logging search completions) never block. Consumers (Flink, Spark) process at their own pace. 30-day retention on cheap S3-backed storage.

#### 3. Trie Node (in-memory, not a DB table)

```
struct TrieNode {
  children:         map[rune]*TrieNode    // char -> child node
  top_suggestions:  []Suggestion          // top-5 pre-computed (sorted desc by freq)
  is_terminal:      bool                  // marks end of a valid query string
}

struct Suggestion {
  query_text:       string
  frequency:        uint64
}
```

#### 4. `trie_snapshot` (S3)

```
S3 key: s3://autocomplete-snapshots/trie-{language}-{build_timestamp}.pb.zst

Serialized as Protocol Buffers, compressed with Zstandard.
Typical size: 28GB raw → ~4GB compressed (Zstd level 3)
Build frequency: every 15 minutes
Retention: 3 most recent snapshots (rollback capability)
```

### Important Indexes

- `query_frequency` has no secondary index in Cassandra (secondary indexes in Cassandra are anti-patterns at scale). Instead, the Trie Builder does a full table scan with `SELECT * FROM query_frequency LIMIT 10000000` sorted by `global_count` — this is a batch operation done offline.
- For the Redis cache, keys are `autocomplete:{language}:{normalized_prefix}` — the language prefix allows per-locale caches without key collision.

## Step 6 — Deep Dive: Trie Data Structure and Top-K Suggestions

This is the hardest component. Interviewers expect you to go three levels deep: the data structure itself, how top-K is maintained, and how the trie is rebuilt without downtime.

### Layer 1: The Trie Structure

A trie (prefix tree) is a tree where each node represents one character, and the path from root to a node spells out a prefix. Every autocomplete query traverses the trie from root to the end of the typed prefix in O(|prefix|) time — typically O(4) to O(10) steps, which is effectively constant.

```
Root
├── 't'
│    └── 'w'
│         └── 'i'
│              └── 't'                   ← node for prefix "twit"
│                   ├── top_suggestions: [twitter(9.8M), twitch(7.2M), ...]
│                   ├── 't'
│                   │    └── 'e'
│                   │         └── 'r'   ← terminal node "twitter"
│                   └── 'c'
│                        └── 'h'        ← terminal node "twitch"
├── 'h'
│    └── 'o'
│         └── 'w'                       ← node for prefix "how"
│              └── top_suggestions: [how to tie a tie(12M), how to lose weight(8M), ...]
```

**Key insight**: We store the top-5 pre-computed suggestions at every internal node, not just at leaves. This means a query for prefix "tw" returns suggestions instantly from the "tw" node without traversing the subtree. This pre-computation trades memory for O(1) query time after reaching the prefix node.

### Layer 2: Maintaining Top-K at Every Node

**Naive approach**: At each node, store all query strings in that subtree and compute top-5 at query time. This is correct but O(subtree size) per query — unusable at scale.

**Production approach — pre-computed top-5 at every node**:

```
Algorithm for building top-K at node N:
1. Collect top-K from each child node (already computed recursively)
2. If N is terminal (end of a valid query), include N's own query
3. Merge all candidates, keeping only top-K by frequency (min-heap of size K)
4. Store this sorted list at N

Time to build: O(total_nodes × K × log(K)) -- linear in tree size
Space at each node: O(K) = O(5) -- constant
Query time: O(|prefix|) to reach the node, O(1) to return stored list
```

**Concrete example**:

```
Node "twi" has children: "twit", "twin", "twice"
  - "twit" node has top-5: [twitter(9.8M), twitch(7.2M), twitter login(4.1M), ...]
  - "twin" node has top-5: [twin peaks(500K), twins(480K), ...]
  - "twice" node has top-5: [twice(700K), twice kpop(400K), ...]

"twi" node merges all, keeps top-5 by frequency:
  → [twitter(9.8M), twitch(7.2M), twitter login(4.1M), twitter down(2.8M), twitch tv(1.9M)]
  (twin and twice entries fall outside top-5)
```

**Character encoding**: Use rune (Unicode code point) as the key in the children map, not byte. This correctly handles multi-byte UTF-8 characters — Chinese characters, Arabic script, emoji. The map is `map[rune]*TrieNode`, not an array of 26 characters.

### Layer 3: Zero-Downtime Trie Reload

The trie is a 28GB in-memory structure. Rebuilding it takes 3-5 minutes. During rebuild, we cannot serve stale data from an old trie forever, but we cannot drop requests either.

**Solution: Blue-Green Trie Switching**

```
Trie Service (single host, simplified):

┌────────────────────────────────────────────────┐
│  Trie Service Process                          │
│                                                │
│  ┌──────────────┐      ┌──────────────────┐   │
│  │ Active Trie  │      │ Loading Trie     │   │
│  │ (Blue)       │      │ (Green)          │   │
│  │ Built: 10:15 │      │ Building from    │   │
│  │ Serving all  │      │ S3 snapshot...   │   │
│  │ traffic now  │      │ 40% loaded       │   │
│  └──────────────┘      └──────────────────┘   │
│         ▲                        │             │
│         │   atomic pointer swap  │             │
│         └────────────────────────┘             │
│              When Green is 100% loaded         │
│              swap pointer, GC Blue             │
└────────────────────────────────────────────────┘
```

**Steps**:
1. Trie Builder completes a new trie snapshot, writes to S3 with a new timestamp key.
2. Trie Builder notifies all Trie Service instances via a control channel (Redis pub/sub or ZooKeeper watch).
3. Each Trie Service instance begins loading the new snapshot into a second in-memory trie object while the old one continues serving all traffic. This requires 2× peak RAM during the switchover window (~5 minutes).
4. Once loading completes and validation passes (spot-check a few known prefixes), the service atomically swaps the active pointer from old trie to new trie. In Go: `atomic.StorePointer`.
5. The old trie is dereferenced and garbage collected.
6. RAM requirement during switchover: 28GB × 2 = 56GB — plan accordingly.

**Validation before swap**:
```go
func validateTrie(t *Trie) error {
    golden := []struct{ prefix string; minResults int }{
        {"the ", 5}, {"how to", 5}, {"weather", 5}, {"amazon", 5},
    }
    for _, g := range golden {
        results := t.Search(g.prefix, 5)
        if len(results) < g.minResults {
            return fmt.Errorf("prefix %q returned %d results, want %d", 
                             g.prefix, len(results), g.minResults)
        }
    }
    return nil
}
```

### Trie Partitioning for Scale

A single 28GB trie won't scale to 500M unique queries without hitting memory limits. Use range-based trie partitioning:

```
Shard 0: prefixes starting with a-f  (6/26 ≈ 23% of queries)
Shard 1: prefixes starting with g-n  (8/26 ≈ 31%)
Shard 2: prefixes starting with o-z  (12/26 ≈ 46%)

Each shard: 2 instances (primary + hot standby)
Total: 6 trie server instances

Load Balancer routes:
  first_char in [a-f] → Trie Shard 0
  first_char in [g-n] → Trie Shard 1
  first_char in [o-z] → Trie Shard 2

CJK characters → Shard dedicated to CJK (separate trie per language)
```

**Rebalancing**: Shards are not perfectly equal (far more "a-f" queries than "x-z"). Monitor query distribution and adjust shard boundaries. Use a lookup table (prefix_char → shard_id) rather than hard-coded ranges so boundaries can be changed without code deploys.

## Step 7 — Deep Dive: Real-Time Frequency Updates

Keeping suggestions fresh is the second hardest problem. The system must detect that "World Cup 2026" is suddenly trending and surface it in suggestions within minutes, not hours.

### Layer 1: The Two-Path Architecture

We run two parallel frequency-update pipelines that serve different purposes:

```
Kafka (search events)
        │
        ├──────────────────────────────────────► Flink Stream Processor
        │                                        (near-real-time, approximate)
        │                                              │
        │                                              ▼
        │                                       Count-Min Sketch
        │                                       (per 15-min window)
        │                                              │
        │                                              ▼
        │                                       Trending Detector
        │                                       (spike vs baseline)
        │                                              │
        │                                              ▼
        │                                       Emergency Trie Update
        │                                       (inject trending queries)
        │
        └──────────────────────────────────────► Spark Batch Job (every 15 min)
                                                 (accurate, complete)
                                                       │
                                                       ▼
                                                 Update Cassandra
                                                 global_count
                                                       │
                                                       ▼
                                                 Trie Builder
                                                 (full rebuild)
                                                       │
                                                       ▼
                                                 New Trie Snapshot → S3
                                                 → Hot reload all Trie Services
```

### Layer 2: Count-Min Sketch for Approximate Real-Time Counts

Tracking exact frequency for millions of concurrent queries in real-time is prohibitively expensive. Count-Min Sketch provides approximate counts in O(1) update and O(1) query time with bounded error.

```
Count-Min Sketch structure:
  d hash functions × w counters each (d rows, w columns)
  
  Typical parameters: d=5, w=2048
  Memory: d × w × 4 bytes = 5 × 2048 × 4 = 40 KB per sketch

  Update("twitter"):
    For each hash function h_i:
      counters[i][h_i("twitter") % w] += 1

  Query("twitter"):
    return min(counters[i][h_i("twitter") % w] for i in range(d))
    
  Error bound: with probability 1 - (1/2)^d, the estimate is within
               (actual_count + epsilon × N) where epsilon = e/w and N = total events
```

We maintain one Count-Min Sketch per 15-minute time window. The Flink processor:
1. Consumes search events from Kafka.
2. Updates the current window's CMS.
3. Every minute, compares top-N queries in CMS with their historical baseline from Cassandra.
4. Queries where `current_rate / historical_rate > threshold` (e.g., 5×) are flagged as trending.

### Layer 3: Trending Injection Without Full Rebuild

When a query starts trending explosively (breaking news, viral moment), we cannot wait 15 minutes for a full trie rebuild. We implement a **trending override layer**:

```
Request serving path with trending:

  Client request → Redis cache check
       │
       ├── Cache HIT → return cached result
       │
       └── Cache MISS → query Trie Service
                              │
                              ▼
                    Get base suggestions from trie
                    (may not include trending query yet)
                              │
                              ▼
                    Fetch trending queries for this prefix
                    from Trending Store (Redis Sorted Set)
                              │
                              ▼
                    Merge: blend trending queries into
                    base suggestions using blending score:
                      blend_score = historical_score × 0.3
                                  + trending_score × 0.7
                              │
                              ▼
                    Return top-5 blended results
```

**Trending Store in Redis**:
```
Key: trending:{locale}:{prefix_first_2_chars}
Type: Redis Sorted Set
Score: current_window_count
Members: query strings

ZADD trending:en-US:wo 8500000 "world cup 2026"
ZRANGEBYSCORE trending:en-US:wo +inf -inf LIMIT 0 5
```

This allows injecting trending queries into results within ~1 minute of trend detection (Flink detects → writes to Redis → next uncached request picks it up), without rebuilding the full trie.

**Expiry**: Each trending sorted set has a TTL of 4 hours. Queries that stop trending fall out naturally.

**Anti-gaming**: Before adding to trending, the Flink processor checks:
1. The query must appear from at least N distinct IP addresses (prevents bot spam).
2. The query must not be on the denylist.
3. The query's velocity (events per minute) must exceed 3σ above its 30-day baseline.

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (1.5M read QPS)

**Specific bottleneck**: Redis cache becomes the hot spot. At 1.5M QPS, even with consistent hashing, each Redis node is processing ~300K ops/sec. Redis single-threaded command processing maxes out around 200K ops/sec per core.

**Specific fix**: 
1. Add a local in-process LRU cache on each API server (e.g., 10,000 entries, 5-second TTL using Caffeine/Ristretto). This absorbs 60-70% of requests before they hit Redis. At 1.5M QPS with 30 API servers, each server handles 50K QPS. A 70% local hit rate reduces Redis load to 15K ops/sec per server → 450K total — well within 5-node Redis cluster capacity.
2. Increase API server count from 30 to 300.
3. Shard Redis from 3 to 15 nodes.

### At 100x Current Load (15M read QPS)

**Specific bottleneck**: Trie Service cannot handle this through vertical scaling. Even with 6 shards, each shard must handle 2.5M QPS of gRPC calls. The trie lookup itself is fast (~microseconds), but gRPC connection overhead, serialization, and OS scheduling limit throughput to ~500K gRPC calls/sec per server under realistic conditions.

**Specific fix**: Embed the trie directly in the API server process (no gRPC hop). Each API server loads a local copy of its shard's trie in-memory. The trie snapshot (4GB compressed) is distributed via a shared NFS mount or S3 with local disk caching. Trie servers become trie snapshot distributors, not query handlers. This eliminates the network round-trip entirely — trie lookup is now a function call, not an RPC.

**New memory requirement**: 30 → 3,000 API servers, each holding a 5-7GB trie shard in RAM. Total RAM: 3,000 × 7GB = 21TB across the fleet. This is expensive but achievable on c5.4xlarge instances at AWS.

### At 1000x Current Load (150M read QPS)

**Fundamental change required**: The trie snapshot-based model breaks down because:
1. Building a trie over 5 billion unique queries (10x our current index) would take 45+ minutes, making 15-minute refresh cycles impossible.
2. Distributing a 280GB trie snapshot to 30,000 servers every 15 minutes requires 280GB × 30,000 = 8.4 PB of internal bandwidth per refresh — clearly impossible.

**Solution: Hierarchical Trie + Distributed Serving**

Split the problem into two tiers:
- **Tier 1 (Hot Trie)**: Top 100K queries by global frequency. Fits in ~50MB. Distributed to every server. Refreshed every minute. Serves ~95% of traffic.
- **Tier 2 (Warm Trie)**: Top 10M queries. 4GB compressed. Stored on dedicated Trie Nodes, served via gRPC. Serves ~4.9% of traffic.
- **Tier 3 (Cold Path)**: Queries outside top 10M. Served by Elasticsearch cluster (inverted index with `search_as_you_type` mapping). Serves ~0.1% of traffic.

This mirrors how CDNs work (L1/L2/L3 cache hierarchy) applied to autocomplete.

Additionally, at this scale, geographic sharding becomes necessary: maintain separate tries per region (North America, Europe, Asia-Pacific). Queries from Japan should be ranked by Japanese search frequency, not global.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Core data structure | Trie with pre-computed top-K at every node | Inverted index (Elasticsearch) | Trie gives O(prefix_len) lookup with O(1) top-K retrieval; Elasticsearch has higher latency (10-30ms) and is better for full-text search |
| Top-K pre-computation | Store top-5 at each trie node (space-time trade-off) | Compute top-K at query time by scanning subtree | Query-time scanning is O(subtree_size) — too slow; pre-computation makes it O(1) at the cost of 5× memory |
| Frequency update strategy | Dual path: Flink (real-time approx) + Spark batch (accurate) | Real-time only (Kafka Streams) or batch only (nightly job) | Real-time alone gives approximate counts with drift; batch alone misses trends. Dual path gives best of both |
| Frequency counting | Count-Min Sketch for streaming | Exact counts in Redis | Exact counts in Redis for 500M unique queries = 40GB+ Redis memory; CMS gives same accuracy for trending detection at 40KB |
| Trie update | Full rebuild every 15 min (Blue-Green swap) | Incremental node updates | Incremental updates introduce subtle bugs (partial consistency, top-K recalculation cascading up the tree); full rebuild is simpler and correctness is easier to verify |
| Trending handling | Trending override layer (Redis sorted sets) blended at query time | Wait for next full rebuild | Full rebuild latency (15 min) is too slow for viral moments; trending injection reduces latency to ~1 minute |
| Caching strategy | 3-tier: Client → CDN → Redis → Trie | Single cache layer | Single layer cannot absorb 150K QPS; tiered caching achieves 85%+ hit rate before reaching the trie |
| Query index size | Cap at top-10M queries | Index all queries | Indexing all 500M queries requires 280GB trie RAM — impractical; long-tail queries are served by Elasticsearch fallback |
| Trie partitioning | Range-based sharding on first character | Hash-based sharding | Hash-based sharding distributes load evenly but destroys prefix locality; range-based allows a single shard to own all "tw*" queries |
| Personalization | Global suggestions only (out of scope) | Per-user personalized tries | Per-user tries require 500M separate data structures or expensive query-time blending; design separately |

## Step 10 — How Real Companies Solved This

### Google Search Autocomplete

Google processes ~8.5 billion queries per day, and their autocomplete runs at ~100,000 QPS sustained with sub-50ms p99 latency globally.

**What they actually built**: Google's Suggest system (internally called Borg-served trie services) stores the trie in distributed RAM across thousands of servers. Each server owns a shard of the trie based on prefix range. The trie is pre-computed from query logs via MapReduce jobs (Google's original use case for MapReduce was processing search logs).

**Freshness system**: Google introduced a "freshness layer" that can surface trending queries within hours. Their 2022 blog post confirmed they use real-time signals alongside historical frequency. The freshness system can temporarily override raw volume signals — if "World Cup semifinal" is being searched at 10× its baseline, it surfaces even if its absolute count is lower than perennial queries like "weather."

**What they got wrong first**: Early versions refreshed tries daily (overnight batch job). This meant that breaking news events (Michael Jackson's death in 2009 is often cited internally) did not appear in suggestions until the next day's refresh. The incident drove the investment in near-real-time trie updates.

**Key insight**: Google applies geographic segmentation of their trie. Someone searching in Brazil sees Brazilian Portuguese suggestions ranked by Brazilian search frequency, not global frequency. The trie is sharded by (prefix, locale) — this is a massive operational complexity increase but necessary for quality.

**Source**: [Google Autocomplete Official Blog](https://blog.google/products/search/how-google-autocomplete-works-search/), [GeeksforGeeks HLD](https://www.geeksforgeeks.org/system-design/googles-search-autocomplete-high-level-designhld/)

---

### LinkedIn — Cleo

LinkedIn's scale for typeahead: hundreds of millions of members, typeahead is used for People Search, Company Search, Job Search, Message recipient search — each requiring different ranking signals.

**What they actually built**: LinkedIn open-sourced their typeahead library called **Cleo** (Flexible, partial, out-of-order and real-time typeahead search). Unlike a pure trie, Cleo uses a four-component architecture per partition:

1. **Inverted Index (Adjacency List)**: Maps 4-character prefixes to lists of document IDs. Example: prefix "link" → [doc_id_1, doc_id_2, ...] (all LinkedIn profiles whose names contain "link" as a prefix).

2. **Bloom Filter per document**: Each document has an 8-byte bloom filter encoding all the character 4-grams of its terms. To check if document D matches query "linked", compute the bloom filter of "linked" and check if it's a subset of D's bloom filter. False positives are possible; false negatives are not.

3. **Forward Index**: The actual indexed terms per document, used to verify bloom filter positives. Rejects false positives from step 2.

4. **Scorer**: External scores (connection degree, profile completeness, recency) injected at query time for personalized ranking.

**What they got wrong first**: LinkedIn's first typeahead required full-string matches ("John Smith" only matched if you typed "John" or "Smith" exactly). Users who typed "Jo Sm" got no results. Cleo was built specifically to handle out-of-order, partial prefix matching — "Jo Sm" correctly matches "John Smith" because it finds documents containing both prefix "Jo" and prefix "Sm".

**Key insight**: The 4-character prefix cap in the inverted index is a deliberate engineering trade-off. Longer prefixes (e.g., 8 characters) would reduce false positives at the cost of a larger index. 4 characters was empirically found to give the best balance of index size vs. false positive rate for LinkedIn's corpus.

**Source**: [LinkedIn Engineering — Cleo](https://engineering.linkedin.com/open-source/cleo-open-source-technology-behind-linkedins-typeahead-search), [LinkedIn Search Federation Architecture](https://www.linkedin.com/blog/engineering/search/search-federation-architecture-at-linkedin)

## Interview Perspective

### What the Interviewer Is Evaluating

This problem specifically tests:

1. **Data structure depth**: Do you know how a trie works internally? Can you explain pre-computed top-K at nodes without being prompted?
2. **Write path design**: Most candidates handle reads well but struggle with how frequency counts get updated. Do you know about Count-Min Sketch?
3. **Operational thinking**: How do you reload a 28GB trie without downtime? Can you describe Blue-Green switching?
4. **Scale intuition**: At what point does the trie become too large? What's your fallback (Elasticsearch for long-tail)?
5. **Freshness vs accuracy trade-off**: Do you understand why you need both a streaming path (approximate) and a batch path (accurate)?

---

### Junior (L3-L4) Answer

**What they say**: "I'd use a trie. Each node stores characters. When the user types a prefix, we traverse the trie to the matching node and then do a DFS/BFS to find all words in the subtree, rank by frequency, return top-5."

**What depth they reach**: Basic trie traversal, simple database for frequencies, maybe Redis caching. They get the read path right.

**What they miss**: 
- DFS on the subtree is O(subtree_size) — for common prefixes like "a", the subtree has millions of nodes. This is unusable.
- No discussion of how frequency counts are updated.
- No discussion of trie rebuild strategy or downtime.
- Single cache layer without discussing hit rates or the 3-tier hierarchy.
- No mention of Count-Min Sketch, Blue-Green switching, or trending detection.

---

### Senior (L5) Answer

**What they add**:
- "We pre-compute top-K at every trie node during build time, so retrieval is O(prefix_length), not O(subtree_size)."
- "Frequency updates go through a Kafka pipeline so the write path doesn't block reads."
- "The trie is rebuilt from a batch job every 15 minutes and hot-loaded via Blue-Green switching."
- "I'd cap the trie to top-10M queries by frequency and fall back to Elasticsearch for long-tail."
- "Redis cache with consistent hashing on the prefix's first 2 characters increases cache locality."

**What still separates them from staff**: They describe the system correctly but don't spontaneously discuss Count-Min Sketch, the cost of 2× RAM during trie switchover, trending injection as a separate overlay layer, or geographic segmentation of tries.

---

### Staff (L6+) Answer

**What they drive to unprompted**:

1. **Operational cost of 2× RAM**: "During Blue-Green switchover, we hold two 28GB tries in memory simultaneously for ~5 minutes. This means our trie servers need 64GB RAM minimum, not 32GB. We size for switchover, not steady state."

2. **Trending detection with statistical rigor**: "Count-Min Sketch is great for frequency estimation, but for trending detection I use a ratio: current 15-min rate vs 30-day baseline for the same time-of-day and day-of-week. A query that's always popular on Sunday afternoons shouldn't trigger a trending alert on Sunday afternoon."

3. **Geographic and locale sharding**: "At Google-scale, a global trie is wrong — search frequency varies dramatically by locale. 'Premier League' is far more popular in the UK. The trie should be sharded by (shard_key, locale). This means 26 language tries × 6 prefix shards = 156 trie instances. That's an operational burden worth discussing."

4. **Cost analysis**: "The biggest cost in this system is RAM. 28GB × 156 instances = 4.4TB of RAM just for tries. At $0.012/GB/hr on AWS, that's ~$52/hour. Can we compress? Trie nodes are pointer-heavy and don't compress well. The alternative is keeping fewer queries in the hot trie and accepting higher Elasticsearch fallback rates."

5. **Cache stampede protection**: "When a trie reloads, the Redis TTLs haven't changed. If the reload happens right when many keys are expiring simultaneously, all requests miss cache and hammer the new trie. We stagger TTLs with jitter: `TTL = base_ttl + random(0, base_ttl × 0.1)` to spread expirations."

---

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **Scanning the subtree at query time**: Saying "traverse the trie to the prefix node and then DFS the subtree to find all words" is a critical mistake. A subtree for prefix "a" contains millions of words. Pre-computed top-K at each node is the correct answer — always name this explicitly.

2. **Ignoring the write path**: Designing a beautiful read system then saying "and we update the trie whenever a user searches" without explaining how (asynchronously via Kafka? directly? batch?) leaves a giant gap. The interviewer is waiting for this.

3. **Treating trie reload as free**: Saying "just rebuild the trie every hour" without discussing (a) how long it takes, (b) what serves traffic during the rebuild, (c) the memory spike during Blue-Green switchover. Operational correctness is expected at senior level.

4. **Proposing Elasticsearch first**: Elasticsearch (or Solr) is a legitimate choice for autocomplete, but it has 10-30ms query latency — 3-10× worse than an in-memory trie. If you propose it without comparing latency, the interviewer will push back. Know the trade-off: trie is fast but operationally complex; Elasticsearch is slower but operationally simpler. Use trie for hot tier, Elasticsearch for long-tail cold tier.

5. **Forgetting trending/freshness**: Designing a system that can only surface queries from the previous 24-hour batch job misses a core product requirement. Breaking news must surface in minutes. The Count-Min Sketch + trending override layer is the answer, but most candidates never discuss it unless prompted.
