> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Chunked upload resumability, deduplication (content-hash), sync across devices, conflict resolution

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

Design a cloud file storage and synchronization service that allows users to upload, download, organize, and sync files across multiple devices. The system must handle large file uploads reliably, deduplicate identical content to minimize storage, and propagate changes to all of a user's devices in near-real-time — analogous to Dropbox (consumer sync) or Amazon S3 (raw object store).

**Who uses it and at what scale:**
- Dropbox: 700 million registered users, 15 million paying users, 500+ petabytes of user data, 1.2 billion file uploads per day (2023)
- Amazon S3: 100+ trillion objects stored, 300 million+ requests per second peak, 11 nines (99.999999999%) durability
- Google Drive: 1 billion+ users, 15 GB free per account, petabytes added daily

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Upload** — Users can upload files of arbitrary size (up to 5 TB per file, S3 limit). Upload must be resumable (survive network interruption).
2. **Download** — Users can download any file they own or have been shared with, by URL or API.
3. **File Organization** — Users can create folders, move, rename, and delete files. Versioning: keep at least the last N versions of each file.
4. **Cross-Device Sync** — Changes made on one device propagate to all other connected devices within seconds (delta sync — only changed chunks are transferred).
5. **Sharing** — Users can share files or folders with other users (view/edit permissions) or generate public links.
6. **Deduplication** — Identical file content (across all users) is stored only once. Identical blocks within different files share storage.

### Non-Functional Requirements

| Attribute | Target |
|---|---|
| Availability | 99.99% (52 minutes downtime/year) for upload/download APIs |
| Durability | 99.999999999% (eleven 9s) — no data loss after acknowledgment |
| Upload latency | First byte acknowledged < 200ms; complete 1 GB file < 60s on 200 Mbps |
| Sync latency | Change visible on second device < 3 seconds (p99) |
| Consistency | Eventual consistency across devices; strong consistency for metadata within a user session |
| Read/Write ratio | 60% reads, 40% writes (consumer sync is write-heavy vs. general web) |
| Max file size | 5 TB per object (S3 multipart limit) |
| Storage per user | 15 GB free, up to 2 TB paid |

### Out of Scope

- Real-time collaborative editing (Google Docs style — operational transformation)
- Full-text search inside file contents
- Video transcoding or image thumbnail generation (separate media processing pipeline)
- On-premise or hybrid deployment
- Billing and payment systems

### Clarifying Questions to Ask the Interviewer

1. **"Is this consumer sync (Dropbox) or raw object storage (S3)?"** — Consumer sync requires a sync client, conflict resolution, and device tracking. S3 requires only HTTP PUT/GET with a flat namespace. The architectures diverge significantly.
2. **"Should we support versioning, and for how many versions?"** — Versioning changes the delete model (soft delete, version chains) and storage costs significantly.
3. **"Cross-user deduplication or per-user only?"** — Cross-user deduplication (hashmap across all users) is more complex but saves far more storage. Raises privacy questions (hash-proof-of-ownership attacks).
4. **"What is the expected file size distribution?"** — If 80% of files are < 1 MB, chunk size optimization differs from a system dominated by video files (1-50 GB). Both exist in Dropbox.
5. **"What consistency guarantee for sync?"** — "I upload on laptop, open on phone immediately" — does phone always see the file? Or is a few-second delay acceptable? This drives push-vs-poll design.
6. **"Do we need mobile clients?"** — Mobile has bandwidth and battery constraints. Delta sync becomes critical; aggressive deduplication and compression change chunk size choices.
7. **"What geography?"** — Single-region simplifies the design enormously. Multi-region requires active-active replication, which fundamentally changes how we handle conflict detection.

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

```
DAU:              50 million (10% of 500M registered)
MAU:              200 million
Average files/user: 2,000 files
Average file size:  5 MB (median; mean skewed higher by videos)
Uploads/day:      1.2 billion (given from Dropbox numbers)
Downloads/day:    3.0 billion (reads > writes; downloads include syncs)
```

### QPS

```
Upload QPS:
  1.2 billion / 86,400 = ~14,000 upload operations/sec (avg)
  Peak (3x): ~42,000 uploads/sec

Download QPS:
  3.0 billion / 86,400 = ~35,000 download operations/sec (avg)
  Peak (3x): ~105,000 downloads/sec

Chunk upload QPS (each file split into ~N chunks of 5 MB):
  Average file 5 MB → 1 chunk; 10% of files > 50 MB (10+ chunks)
  Effective chunk upload rate: ~25,000 chunk writes/sec
```

### Storage

```
New uploads per day:
  1.2 billion files × 5 MB (avg) = 6,000 TB = 6 PB/day (gross)

After deduplication (Dropbox reports ~30-40% dedup ratio):
  6 PB × 0.65 = ~3.9 PB net new data/day

Replication factor: 3 (or equivalent erasure coding 1.5x):
  3.9 PB × 1.5 (erasure coding overhead) = ~5.85 PB/day stored

Per year: 5.85 PB × 365 = ~2.1 EB/year
Over 5 years: ~10.5 EB (10.5 exabytes)

Metadata storage:
  Each file record: ~1 KB (file metadata + chunk list)
  Total files: 50M users × 2,000 files = 100 billion files
  100B × 1 KB = 100 TB metadata (fits in a distributed SQL cluster)
```

### Bandwidth

```
Ingress (uploads):
  25,000 chunk writes/sec × 5 MB = 125 GB/sec peak ingress

Egress (downloads):
  105,000 downloads/sec × 5 MB = 525 GB/sec peak egress

CDN offload:
  Popular shared files cached at CDN → assume 60% CDN hit rate
  Origin egress: 525 GB/sec × 0.4 = 210 GB/sec from origin

Sync notifications (small payloads):
  50M DAU × 5 file changes/day = 250M notifications/day
  250M / 86,400 = ~2,900 notification messages/sec
```

### Server Count (Rough)

```
Upload API servers (each handles ~1,000 concurrent uploads):
  42,000 peak uploads / 1,000 = ~42 API servers
  Add headroom: 80 API servers

Storage nodes (each holds ~200 TB raw):
  At 10.5 EB over 5 years: 10,500 PB / 200 TB = ~52,500 storage nodes
  (This matches Dropbox's scale — they have tens of thousands of nodes)

Metadata DB servers:
  100 TB metadata across sharded PostgreSQL or TiDB
  At 5 TB per node: ~20 metadata DB nodes (with 3x replication = 60 total)
```

### Component Explanations

**Clients (File Watcher + Chunker):** The client is not a dumb HTTP client. It runs a local daemon that watches the filesystem for changes (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows). When a change is detected, it computes SHA-256 hashes of changed chunks and sends only the chunk list to the metadata service — not the bytes — to determine which chunks are already known to the server (dedup check). This is where bandwidth savings happen.

**CDN:** Download traffic for popular shared files (e.g., a document shared with 1,000 people in a company) is served from CDN edge. This eliminates 60%+ of download traffic from origin. Upload goes directly to origin (CDN cannot help with writes).

**Load Balancer (L7):** Routes by URL path prefix. Upload service handles multipart coordination; metadata service handles file tree operations; WebSocket connections for sync go to a sticky connection pool.

**Upload Service:** Stateless API servers. They do not store data — they coordinate. They generate presigned S3-style URLs (or direct write tokens) so the client can write chunks directly to block storage, bypassing the upload service for the actual data transfer. This is the S3 presigned URL pattern and is critical for scalability: data does not flow through API servers.

**Block Store (Chunk Store):** The physical storage for file content. Content-addressed: the key is the SHA-256 of the chunk bytes. This enables deduplication automatically — two files with the same chunk store it once. Dropbox built Magic Pocket for this. S3 uses its internal ShardStore (written in Rust, LSM-tree based) for each storage node.

**Metadata DB:** Stores file metadata (filename, parent folder, owner, permissions, version history, list of chunk hashes in order). Does NOT store file bytes. Sharded by user_id to keep user's file tree co-located. Must be strongly consistent per user (you should not see a file disappear and reappear when making consecutive reads).

**Kafka (Message Queue):** Decouples upload acknowledgment from sync propagation. When a file commit succeeds, the metadata service publishes a `file.committed` event. Sync workers consume this to trigger notifications. This makes the upload path fast and the sync path eventually consistent — the right tradeoff.

**Notification Service:** Maintains persistent connections (WebSocket or SSE) to each active device. When a file change event arrives from Kafka, it pushes a lightweight "something changed, please sync" message to all devices connected for that user. The device then fetches the full change list from the metadata service.

## Step 4 — Data Model

### Core Entities

#### users

```sql
users (
  user_id       UUID          PRIMARY KEY,
  email         VARCHAR(255)  UNIQUE NOT NULL,
  display_name  VARCHAR(255),
  plan_type     ENUM('free','pro','business'),
  quota_bytes   BIGINT        DEFAULT 15_000_000_000,  -- 15 GB
  used_bytes    BIGINT        DEFAULT 0,
  created_at    TIMESTAMPTZ,
  updated_at    TIMESTAMPTZ
)
```

#### files

```sql
files (
  file_id       UUID          PRIMARY KEY,
  user_id       UUID          NOT NULL,   -- FK to users
  parent_id     UUID,                     -- NULL = root folder; FK to files
  name          VARCHAR(1024) NOT NULL,
  is_folder     BOOLEAN       DEFAULT FALSE,
  is_deleted    BOOLEAN       DEFAULT FALSE,  -- soft delete
  size_bytes    BIGINT,
  content_hash  CHAR(64),     -- SHA-256 of full file (for quick equality check)
  created_at    TIMESTAMPTZ,
  modified_at   TIMESTAMPTZ,
  version       BIGINT        DEFAULT 1,      -- monotonically increasing
  current_rev   UUID                           -- FK to file_revisions
)

INDEX idx_files_user_parent ON files(user_id, parent_id, is_deleted)
INDEX idx_files_content_hash ON files(content_hash)   -- for dedup lookup
INDEX idx_files_modified ON files(user_id, modified_at DESC)  -- sync delta
```

**Why these indexes:**
- `(user_id, parent_id, is_deleted)` — every folder listing query; must be fast
- `(content_hash)` — cross-user dedup check; "does this file already exist anywhere?"
- `(user_id, modified_at DESC)` — incremental sync: "give me all files changed after timestamp T"

#### file_revisions

```sql
file_revisions (
  revision_id   UUID          PRIMARY KEY,
  file_id       UUID          NOT NULL,
  version       BIGINT        NOT NULL,
  chunk_ids     UUID[]        NOT NULL,   -- ordered list of chunk IDs
  size_bytes    BIGINT,
  content_hash  CHAR(64),
  created_by    UUID,         -- user_id of who made this version
  created_at    TIMESTAMPTZ,
  is_current    BOOLEAN
)

INDEX idx_revisions_file ON file_revisions(file_id, version DESC)
```

#### chunks

```sql
chunks (
  chunk_id      CHAR(64)      PRIMARY KEY,  -- SHA-256 = the key (content-addressed)
  size_bytes    INT           NOT NULL,
  storage_path  VARCHAR(512),  -- path in block store (bucket/shard/hash prefix)
  ref_count     INT           DEFAULT 0,    -- how many revisions reference this chunk
  created_at    TIMESTAMPTZ,
  last_verified TIMESTAMPTZ   -- last checksum verification
)
```

**Note:** `chunk_id` IS the SHA-256 hash. There is no separate hash column. The primary key IS the content address. This makes dedup trivial: INSERT or IGNORE (chunk already exists).

#### devices

```sql
devices (
  device_id     UUID          PRIMARY KEY,
  user_id       UUID          NOT NULL,
  device_name   VARCHAR(255),
  os_type       ENUM('macos','windows','linux','ios','android','web'),
  last_sync_at  TIMESTAMPTZ,
  last_seen_at  TIMESTAMPTZ,
  cursor        BIGINT        -- last sync version number seen by this device
)

INDEX idx_devices_user ON devices(user_id)
```

The `cursor` field is critical for incremental sync — the device tells the server its last known cursor, and the server returns all file changes after that cursor.

### Database Choices

| Entity | Database | Justification |
|---|---|---|
| users, files, file_revisions | PostgreSQL (sharded via Vitess or Citus) | Strong consistency for metadata; complex relational queries for folder trees |
| chunks | PostgreSQL or DynamoDB | Simple key-value (SHA-256 → storage_path); high write throughput on INSERT OR IGNORE; DynamoDB excellent for this pattern |
| devices / sessions | Redis (primary) + PostgreSQL (backup) | Low-latency reads; device state is ephemeral; WebSocket routing info |
| Notification routing | Redis pub/sub | Which WebSocket server holds which device connection |
| Block store (actual bytes) | Custom (Dropbox Magic Pocket) or S3 | Object store for raw bytes; content-addressed via SHA-256 key |

## Step 6 — Deep Dive: Chunked Upload with Deduplication

This is where the interview is won or lost. Every candidate says "split into chunks." Fewer explain the full dedup protocol or how the client/server negotiate efficiently.

### Layer 1: Why Chunks? (The Basic Answer)

Files larger than a few MB should not be uploaded as a single stream because:
- Network interruption = restart from scratch
- No parallelism
- Server must buffer entire file before writing to storage
- No incremental dedup

Chunk size selection involves real trade-offs:

```
Chunk size  | Overhead/file | Parallelism | Dedup effectiveness
------------|---------------|-------------|---------------------
256 KB      | High (many chunks) | High   | High (fine-grained)
4 MB        | Medium        | Medium      | Medium
16 MB       | Low           | Lower       | Low (coarser)
```

**Dropbox uses 4 MB chunks** (they call them "blocks"). AWS S3 minimum multipart part size is 5 MB. For general-purpose cloud storage, 5-16 MB is the sweet spot.

### Layer 2: The Deduplication Protocol (The Deeper Answer)

Naive approach: upload file → server hashes it → compare to known hashes. Problem: you waste bandwidth uploading what might already exist.

**Correct approach (content-addressed, server-side dedup):**

```
Step 1: Client splits file into chunks
        chunk_i = file_bytes[i*CHUNK_SIZE : (i+1)*CHUNK_SIZE]
        hash_i  = SHA-256(chunk_i)

Step 2: Client sends ONLY the hash list to upload/init API
        (No bytes transmitted yet — just 32 bytes per chunk)
        Payload for a 1 GB file = 1GB/5MB * 32 bytes = ~6.4 KB

Step 3: Server checks chunks table:
        SELECT chunk_id FROM chunks WHERE chunk_id IN (hash_0, hash_1, ..., hash_N)
        Returns the set of hashes it ALREADY has.

Step 4: Client uploads ONLY the missing chunks (direct to block store via presigned URL)

Step 5: Client calls commit when all missing chunks are uploaded.
        Server creates file_revisions record with ordered chunk_id list.

Step 6: GC ref-counting:
        For each chunk_id in the new revision, ref_count++
        When a revision is deleted, ref_count--
        When ref_count == 0, chunk is eligible for deletion
```

**Real number:** Dropbox reports that in practice, ~30-40% of uploaded data is already stored (because users re-upload the same files, or files share common chunks like PDF header bytes). This translates directly to 30-40% bandwidth savings for users and equivalent cost savings for Dropbox.

### Layer 3: Hash-Proof-of-Ownership and Security

If the dedup check is purely hash-based, a malicious user who knows the SHA-256 of a file they do NOT own can call `upload/init` with that hash and skip the upload entirely, gaining access to the block without authorization. This is called a **hash proof-of-ownership attack**.

**Mitigations:**

```
Option A: Per-user dedup only (simple)
  - Dedup is scoped to a single user's files
  - No cross-user dedup — safer but wastes storage
  - Dropbox moved toward this after privacy concerns were raised ~2012

Option B: Challenge-response (more complex)
  - Server sends back a random byte range challenge: "Send me bytes 1,048,576 to 1,048,592 of the file"
  - Only the true owner can answer this without storing the full file
  - Client must actually have the file to respond

Option C: Client-side encryption (E2E)
  - Client encrypts chunks before hashing; the hash is of ciphertext
  - Server stores ciphertext; cannot read content
  - Dedup is preserved within a user (same plaintext encrypted with same key = same ciphertext)
  - Cross-user dedup is impossible (different keys = different ciphertexts for same plaintext)
  - This is what Tresorit and encrypted Dropbox use
```

**Interview insight:** Most candidates stop at SHA-256 dedup. Explaining the hash-proof-of-ownership attack and its mitigations immediately signals senior-level understanding.

## Step 7 — Deep Dive: Cross-Device Sync and Conflict Resolution

### Layer 1: The Sync Protocol (The Basic Answer)

When device A changes a file, device B needs to see it quickly. Naive approach: device B polls every 30 seconds. This is how early Dropbox worked, but it does not scale to 50M DAU and introduces 30s latency.

**Correct approach: push notifications + pull delta**

```
Device A                  Sync Service          Notification Svc       Device B
   │                           │                       │                  │
   │ Upload + commit           │                       │                  │
   │─────────────────────────► │                       │                  │
   │ ◄── 200 OK                │                       │                  │
   │                           │ Publish file.committed│                  │
   │                           │──────────────────────►│ (via Kafka)      │
   │                           │                       │                  │
   │                           │                       │ WebSocket push   │
   │                           │                       │─────────────────►│
   │                           │                       │ {type:"changed"} │
   │                           │                       │                  │
   │                           │         GET /sync/delta?since=cursor     │
   │                           │◄─────────────────────────────────────────│
   │                           │         ─────────────────────────────────►
   │                           │         200 {entries: [...], cursor: N}  │
   │                           │                                          │ Apply changes
```

**Why two steps (push notification + pull delta)?**

The push is tiny — just "something changed." The device then fetches the full delta. This is intentional:
- If the WebSocket message is lost, the device polls on reconnect anyway
- The delta endpoint is the single source of truth
- Push notifications do not need to be durable (Kafka consumer restarts can replay)

### Layer 2: Cursor-Based Delta Sync

The `cursor` stored per device is a monotonically increasing version number in the metadata database. Every write to the `files` table increments a global version counter per user (or per shared namespace).

```
files table:
  ...
  version   BIGINT   -- this is the user-level logical clock

When device requests delta:
  SELECT * FROM files
  WHERE user_id = $user_id
    AND version > $device_cursor
  ORDER BY version ASC
  LIMIT 1000

Response includes the new max version as the next cursor.
```

**Edge case: cursor must be monotonically increasing, not timestamp-based.** Timestamps fail when:
- Clock skew across DB nodes causes a write at t=100ms to be committed before a write at t=95ms
- The device might miss events with timestamps in the past

Logical clocks (sequence numbers, Lamport timestamps) are the correct solution. This is a detail that separates senior from junior candidates.

### Layer 3: Conflict Resolution

Conflict = two devices modify the same file before either syncs.

```
Timeline:
  t=0: File "budget.xlsx" at version 5 on both devices
  t=1: Device A edits → local version 6 (not yet synced)
  t=2: Device B edits → local version 6 (not yet synced)
  t=3: Device A syncs (commits version 6-A)
  t=4: Device B tries to commit version 6-B — SERVER DETECTS CONFLICT
         (B's base_version=5, but current version=6 from A's commit)
```

**Conflict Resolution Strategies:**

```
Strategy 1: Last Writer Wins (LWW)
  - Whoever commits last wins. A's version is overwritten.
  - Simple, but A's work is lost without warning.
  - Used in S3 (it's an object store, no conflict concept).

Strategy 2: Conflicted Copy (Dropbox approach)
  - Server accepts B's commit but creates a new file named
    "budget (Nitish's conflicted copy 2024-01-15).xlsx"
  - Original file = A's version (winner)
  - Conflicted copy = B's version (loser, but preserved)
  - User sees both files and manually resolves
  - Simple to implement; no data loss; used by Dropbox to this day

Strategy 3: Three-Way Merge (Google Docs style)
  - Find common ancestor (version 5), compute diff(ancestor, A) and diff(ancestor, B)
  - Merge the two diffs; flag sections with irresolvable overlap
  - Requires understanding file format (works for text/code; fails for binary)
  - Extremely complex for binary files (Excel, PSD, etc.)

Strategy 4: Application-Level CRDT
  - File format itself designed for merge (e.g., collaborative text editors)
  - Out of scope for generic file storage
```

**What Dropbox actually does:** Conflicted copies. Simple, predictable, no data loss, user-visible. Engineering complexity is low; user experience is imperfect but acceptable. They explicitly chose not to do three-way merge for arbitrary file formats because it is impossible to merge binary files correctly.

**API contract for conflict detection:**

```
POST /v1/files/upload/commit
{
  "upload_id": "uuid",
  "base_version": 5    // ← "I based my changes on version 5"
}

Server logic:
  current_version = SELECT version FROM files WHERE file_id = $file_id
  IF current_version != base_version:
    // conflict
    OPTION A: Return 409 Conflict → client creates a new file with "_conflict" suffix
    OPTION B: Auto-create conflicted copy on server → return 200 with conflict metadata
```

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load

```
Current: 42,000 upload ops/sec, 50M DAU
At 10x:  420,000 upload ops/sec, 500M DAU
```

**Bottleneck 1: Metadata DB — Hot User Partitions**

The dedup hash check (`SELECT chunk_id FROM chunks WHERE chunk_id IN (...)`) runs on every upload. At 10x volume, the chunks table has ~1 trillion rows and the bulk SELECT becomes slow.

**Fix:** Add a Bloom filter layer in front of the chunks table. A Bloom filter for 1 trillion chunks requires ~10 bits/entry = 1.25 TB of RAM — too much. Use a sharded Bloom filter: 1,000 shards × 1.25 GB each, distributed across a Redis cluster. False positive rate ~1% (means 1% of already-stored chunks get re-uploaded — acceptable cost vs. a lookup on 1 trillion rows).

**Bottleneck 2: Notification Service — Connection Count**

At 500M DAU with 3 devices each = 1.5 billion persistent WebSocket connections. Each connection server can hold ~50,000 connections. That is 30,000 connection servers. Redis pub/sub for routing does not scale to 30,000 subscribers per channel.

**Fix:** Replace Redis pub/sub with a dedicated connection routing layer (e.g., a consistent-hash ring on user_id to connection server). When a file.committed event arrives, look up which connection server holds user B's connections and send directly. Dropbox uses a dedicated routing service for this.

### At 100x Current Load

```
Current: 42,000 upload ops/sec, 50M DAU
At 100x: 4.2 million upload ops/sec, 5B DAU
```

**Bottleneck: Block Store Write Throughput**

A single region's block store cluster cannot absorb 4.2M chunks/sec × 5 MB = 21 TB/sec ingress. Physical network and disk I/O limits are the constraint.

**Fix:** Geographic sharding of block storage. Split users into geographic zones (US-West, US-East, EU, APAC). Each zone has its own block store cluster. Cross-zone file shares are handled by reference with async replication of needed blocks. This is what Dropbox Magic Pocket does: three independent zones (West, Central, East US), with each block stored in at least two zones for durability without requiring all three to participate in every write.

**Second Bottleneck: Chunk Reference Counting for GC**

At 100x, garbage collection (decrementing ref_count to 0 and deleting orphan chunks) runs behind. At 4.2M uploads/sec with ~30% dedup rate, 1.26M new chunks/sec are created and chunks are deleted at similar rate. A transactional UPDATE on ref_count for every operation creates a hot-spot.

**Fix:** Replace synchronous ref_count updates with tombstone-based GC. Mark chunks as deletion-eligible when a revision is deleted. A separate GC job runs a mark-and-sweep: walks all active revisions, builds a set of live chunk IDs, deletes chunks not in the live set. Runs every 24 hours. This trades storage efficiency (orphan chunks accumulate for up to 24h) for write throughput (no per-chunk locking on upload path).

### At 1000x Current Load

```
Current: 42,000 upload ops/sec, 50M DAU
At 1000x: 42 million upload ops/sec, 50B DAU (implausible today, but directionally correct)
```

**Fundamental changes required:**

1. **Hierarchical storage (hot/warm/cold tiering):** Not all data needs the same storage class. Files not accessed in 30 days go to warm storage (cheaper HDDs, higher latency). After 90 days, cold storage (tape or Glacier equivalent). Dropbox Magic Pocket implements cold storage optimization explicitly. This is a cost necessity at exabyte scale, not optional.

2. **Erasure coding over replication:** At 3x replication, 10.5 EB of data requires 31.5 EB of physical storage. Erasure coding (e.g., Reed-Solomon 9+3 — store 9 data shards + 3 parity shards) achieves the same durability at 1.33x overhead (10.5 EB × 1.33 = ~14 EB). Google Colossus uses Reed-Solomon. The trade-off: reconstruction requires reading from multiple nodes (higher read latency under disk failure).

3. **Serverless upload coordination:** At 42M uploads/sec, stateful upload coordination servers become a bottleneck. Move to a stateless, Lambda-style architecture where upload state is stored in a distributed KV store (DynamoDB) rather than in-memory on a coordination server. Each chunk upload is independently resumable without any server holding session state.

4. **Global namespace with region-local routing:** Users in Tokyo should upload to an APAC edge cluster and sync with other Tokyo users locally. Only cross-region shares require inter-datacenter traffic. Requires a global namespace service that maps user_id → home region.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Chunk size | 5 MB | 256 KB or 64 MB | Balance between parallelism overhead, dedup granularity, and S3 minimum multipart size (5 MB) |
| Dedup scope | Per-user dedup | Cross-user dedup | Privacy: cross-user dedup enables hash-proof-of-ownership attacks; per-user is safer |
| Conflict resolution | Conflicted copy | LWW or three-way merge | No data loss; no binary merge complexity; user resolves manually |
| Metadata DB | PostgreSQL + Vitess sharding | Cassandra or DynamoDB | Relational queries for folder trees are natural in SQL; Cassandra lacks joins |
| Block storage key | SHA-256 content hash | UUID | Content-addressing enables dedup automatically; immutable keys simplify caching |
| Chunk ref counting | Background GC with tombstones | Synchronous ref_count++ | Removes ref_count from write critical path; accepts up to 24h orphan chunk window |
| Sync notification | WebSocket push + pull delta | Polling or pure push | Push is fast; pull delta is the authoritative source; decouples reliability concerns |
| Presigned URLs for upload | Client writes directly to block store | API server proxies bytes | Eliminates API server as data bandwidth bottleneck; scales independently |
| Consistency model | Eventual consistency (device sync) | Strong consistency globally | Strong global consistency requires distributed transactions; impractical at this scale |
| Erasure coding | 9+3 Reed-Solomon at scale | 3x replication | 1.33x vs 3x storage overhead; massive cost saving at exabyte scale |

## Step 10 — How Real Companies Solved This

### Dropbox: Magic Pocket

Dropbox launched in 2007 storing everything on Amazon S3. By 2012-2013, their S3 bill was enormous — reportedly hundreds of millions of dollars annually. They built Magic Pocket, their custom blob store, and migrated 90% of user data off S3 by 2016 — a multi-year engineering effort.

**What they got wrong first:** They initially tried a single distributed file system approach. It could not handle their write amplification: Dropbox's workload is dominated by small, frequent updates (users save documents frequently). A traditional distributed FS was optimized for large sequential reads. They ultimately chose a block-level object store with content addressing.

**Key architectural decisions:**
- Blocks up to 4 MB, compressed and encrypted at rest
- Blocks aggregated into 1 GB logical containers called "buckets" for efficient disk layout
- Three independent zones (West, Central, East US); each block stored in at least 2 zones
- Erasure coding for cold storage (lower durability SLA but far cheaper)
- First major tech company to deploy SMR (Shingled Magnetic Recording) HDDs — higher density, 25% lower cost per TB, but write performance is catastrophic for random writes (SMR requires large sequential writes, which their bucket-append model fit perfectly)
- Annual data durability: 99.9999999999% (twelve 9s)

**Engineering blog reference:** "Inside the Magic Pocket" (dropbox.tech, 2016) is required reading. The Magic Pocket infrastructure post from the same year documents the zone architecture.

### Amazon S3: ShardStore and Scalable Metadata

S3 launched in 2006 as the first major cloud object store. Its internal architecture has evolved significantly.

**What they got wrong first:** Early S3 used a simple partitioning scheme where objects were distributed by key prefix. This meant that if you named all your objects with the same prefix (e.g., timestamps: `2024-01-15-00001`, `2024-01-15-00002`, ...), they all landed on the same partition — a hot partition problem. This was a widely documented issue until S3 introduced automatic partitioning in 2018, where S3 detects hot prefixes and automatically splits them across more storage nodes without user intervention.

**Key architectural decisions (2023 disclosures from re:Invent):**
- Storage nodes now use ShardStore — a custom key-value store written in Rust using an LSM-tree (append-only log-structured merge tree). Rust was chosen for memory safety and predictable latency
- Metadata is stored in a separate scalable metadata subsystem, decoupled from the data plane
- Multipart upload: minimum 5 MB parts, up to 10,000 parts, maximum object size 5 TB
- S3 Intelligent-Tiering automatically moves objects between frequent-access and infrequent-access tiers based on access patterns, reducing storage costs by up to 40%
- 300 million+ requests per second handled by the system

**The 11 nines durability claim:** S3 achieves this through synchronous replication across at least 3 Availability Zones within a region before acknowledging a write. Each AZ is an independent physical datacenter with separate power, networking, and cooling. The probability of losing data requires losing all 3 AZs simultaneously — which is what the eleven 9s mathematically encodes.

### Google Drive / Colossus

Google did not publish the full Google Drive architecture, but the Colossus file system (successor to GFS, published ~2010, enhanced throughout 2010s) underpins Google Drive, YouTube, and Gmail.

**Key decisions:**
- Decentralized metadata: Unlike GFS which had a single master (scalability limit), Colossus uses Curators — a horizontally scalable metadata service backed by Bigtable
- Clients communicate directly with D Servers (data servers) for reads and writes; metadata path is separate
- Custodians handle background operations: disk rebalancing, RAID reconstruction, garbage collection
- Reed-Solomon erasure coding for durability with ~1.5x storage overhead vs. 3x for full replication
- Scale: Some individual Colossus clusters exceed 10 exabytes of raw storage

## Interview Perspective

### What the Interviewer Is Evaluating

Specific to this problem:

1. **Do you understand that the client is intelligent?** Dropbox's insight is that the client does work (chunking, hashing, detecting changes via file watcher). Many candidates design a dumb client that uploads raw bytes to an API — this misses the entire architectural foundation.
2. **Can you explain deduplication correctly?** Hash-before-upload, not hash-after-upload. The client sends the hash list first. This is the key protocol insight.
3. **Do you know the difference between metadata and block storage?** Files are not stored in a database. The DB stores metadata (chunk list, version, permissions). The block store holds raw bytes. These scale independently.
4. **Do you understand the sync model?** Push notification + pull delta is the correct answer. Pure polling or pure push are both wrong at scale.
5. **Can you explain conflict resolution trade-offs?** "Last writer wins" vs. "conflicted copies" vs. "three-way merge" — what are the trade-offs and why does Dropbox choose conflicted copies?

### Junior (L3-L4) Answer

- Explains file upload to a server, stored in a database or S3
- Mentions chunking but does not explain the dedup protocol
- Designs a polling-based sync model
- Does not differentiate metadata store from block store
- API design is correct but shallow
- Misses: presigned URLs, client-side chunking, hash-before-upload, content addressing, conflict resolution

### Senior (L5) Answer

- Client-side chunking, SHA-256 per chunk, hash-before-upload protocol
- Presigned URLs for direct client-to-block-store upload (no API server in data path)
- Separate metadata DB and block store with clear justification
- Cursor-based delta sync with WebSocket push notifications
- Conflicted copy resolution strategy with explanation of alternatives
- Basic capacity math showing storage and bandwidth at scale
- Mentions dedup reduces storage costs substantially
- May briefly discuss erasure coding vs. replication

### Staff (L6+) Answer

Drives to these unprompted:

- **Security:** Hash-proof-of-ownership attack and mitigation strategy (per-user dedup or challenge-response)
- **Operational cost:** Erasure coding (9+3) vs. 3x replication — quantifies the storage cost difference at exabyte scale; ties to hot/warm/cold tiering
- **Garbage collection:** Why synchronous ref-counting breaks at scale and how to replace it with background mark-and-sweep with tombstones
- **Cursor monotonicity:** Why timestamp-based cursors fail (clock skew) and logical clocks are correct
- **Migration path:** How you migrate from naive design to Magic Pocket-style block store without downtime (dual-write, backfill, cutover pattern)
- **SMR drive optimization:** Append-only block store design that fits SMR write characteristics
- **Sync edge cases:** What happens when a device is offline for 6 months and has accumulated thousands of local changes — "slow client" problem and truncated delta responses with full-state fallback

### The 4-5 Mistakes Candidates Make On This Specific Problem

**Mistake 1: Storing files in a relational database or in a message queue**
Storing blobs in PostgreSQL or MySQL does not scale past a few TB. File bytes must go to a dedicated object store. Metadata goes in the DB. These are separate systems.

**Mistake 2: Dedup check happens AFTER upload**
Many candidates: "client uploads file → server hashes it → compares to known hashes." This wastes the entire bandwidth of uploading a file that already exists. The correct protocol is: client sends hashes → server checks → client uploads only missing chunks.

**Mistake 3: Designing pure polling for sync**
"Each device polls every 60 seconds" is the answer of someone who has not thought about scale. At 50M DAU with 3 devices each = 150M devices. Even at 60-second intervals, that is 2.5M requests/sec just for polling — wasteful and slow. WebSocket push + pull delta is correct.

**Mistake 4: Ignoring conflict resolution entirely**
"Two users edit the same file at the same time" is asked in almost every Dropbox system design interview. Candidates who say "the last write wins" without discussing the trade-off (data loss) miss the point. Candidates who over-engineer "CRDT for Excel files" demonstrate poor engineering judgment.

**Mistake 5: Not separating the upload coordination path from the data path**
Many candidates route file bytes through their API servers: Client → API Server → Block Store. This means every API server must have 10+ Gbps network capacity dedicated to proxying bytes. The correct design is presigned URLs: Client → Block Store directly, with API server only issuing the token. This is how S3 works, how Dropbox worked, and is a critical scalability insight.

## Summary

Designing a file storage system requires understanding five distinct hard problems that compound each other:

1. **Chunked upload resumability** — content-addressed chunks, hash-before-upload protocol, presigned URLs
2. **Deduplication** — SHA-256 per chunk, server-side dedup check, ref counting GC (with the security implication of per-user scope)
3. **Cross-device sync** — cursor-based logical clock, WebSocket push + pull delta, not polling
4. **Conflict resolution** — conflicted copies for binary files, three-way merge only for text, and why LWW loses data silently
5. **Scale** — separating metadata from block storage, erasure coding over replication, hot/warm/cold tiering, geographic sharding at exabyte scale

The companies that built this at scale (Dropbox, Amazon, Google) all arrived at similar architectural conclusions from different starting points: content-addressed immutable block storage, decoupled metadata service, event-driven sync, and multi-zone replication with erasure coding.
