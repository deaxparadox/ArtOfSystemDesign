# 10.1 — Design a URL Shortener

> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** ID generation without collision, sub-10ms redirect latency, async click analytics

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

A URL shortener converts an arbitrarily long URL into a short, fixed-length alias (e.g., `bit.ly/3xK9pQ`) and redirects anyone who visits that alias to the original URL. The system must handle billions of redirects per day with sub-10ms latency while also recording per-click analytics (geo, device, referrer) without slowing down the redirect path.

**Who uses it and at what scale:**
- Bitly: ~600 million links shortened per month, hundreds of billions of redirects served historically, 10+ billion clicks tracked per month, serving Fortune 500 companies and individual users across 190+ countries
- TinyURL: older service, simpler feature set, estimated tens of millions of active links
- Twitter/X internal: t.co processes every URL posted on the platform — at peak ~6,000 tweet QPS each potentially containing a link
- Instagram, LinkedIn, and every major social platform run their own link-shortening layer internally

---

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Create short URL**: Given a long URL, the system returns a unique short URL (e.g., `https://sho.rt/abc123`).
2. **Redirect**: A GET request to the short URL redirects the browser to the original long URL.
3. **Custom aliases**: Users can optionally specify a preferred short code (vanity URL), subject to availability.
4. **Expiration**: Short URLs can have a TTL (e.g., 30 days, 1 year, or never expire).
5. **Click analytics**: Track clicks with metadata — timestamp, referrer, user-agent, IP/geo — without affecting redirect latency.
6. **Link management**: Authenticated users can list, update destination, and delete their own short URLs.

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% uptime (~52 min downtime/year) |
| Redirect latency (p50) | < 5 ms |
| Redirect latency (p99) | < 20 ms |
| Write latency (URL creation) | < 200 ms p99 |
| Consistency model | Eventual (new links visible within ~1 s globally) |
| Durability | No link loss after write acknowledgment |
| Short code length | 6-8 characters (base62) |
| URL expiry enforcement | Best-effort within 60 seconds of expiry time |
| Analytics freshness | Near-real-time, within 30 seconds for dashboards |

### Out of Scope

- Full marketing analytics platform (A/B testing, conversion funnels) — just click tracking
- QR code generation (extension of the same ID, but separate service concern)
- Link-in-bio pages (Bitly's newer product)
- Browser extension or mobile SDK
- Fraud/phishing link detection (mentioned in trade-offs but not designed in detail here)
- OAuth provider integrations beyond standard JWT auth

### Clarifying Questions to Ask the Interviewer

1. **"Do short codes need to be opaque/random, or can they be sequential?"**
   *Reason: Sequential codes leak information (total link count, creation order). Most real services prefer opaque codes.*

2. **"Is this a public service (anyone can shorten) or authenticated-only?"**
   *Reason: Dramatically changes abuse surface area, rate limiting strategy, and whether we need per-user link quotas.*

3. **"What is the required lifespan for links — do they expire?"**
   *Reason: Affects storage growth projections and whether we need a background expiry job.*

4. **"Do we need real-time analytics or is eventual consistency (minutes) acceptable?"**
   *Reason: Real-time analytics require a streaming pipeline (Kafka + ClickHouse); batch analytics can use simpler Lambda architecture.*

5. **"What's the expected read/write ratio?"**
   *Reason: URL shorteners are extremely read-heavy (redirects >> creations). This drives our caching strategy.*

6. **"Do we need geographic distribution? Is this global or single-region?"**
   *Reason: Global distribution requires CDN or multi-region deployments with replication lag trade-offs.*

7. **"Are custom aliases (vanity URLs) required, and what is the collision handling strategy?"**
   *Reason: Custom aliases require a uniqueness check path that differs from auto-generated IDs.*

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

```
DAU (Daily Active Users): 100 million
Monthly Active Users (MAU): 500 million
URL creations per day: 100 million DAU × 0.1 writes/user/day = 10 million new URLs/day
Redirects per day: 100 million DAU × 10 clicks/user/day = 1 billion redirects/day
Read/Write ratio: 1,000,000,000 / 10,000,000 = 100:1 (heavily read)
```

### QPS Calculations

```
Write QPS (URL creation):
  10,000,000 URLs/day ÷ 86,400 s/day = ~116 writes/s
  Peak write QPS (5× average) = ~580 writes/s

Read QPS (redirects):
  1,000,000,000 redirects/day ÷ 86,400 s/day = ~11,574 reads/s ≈ 11,600 reads/s
  Peak read QPS (5× average) = ~58,000 reads/s
```

### Storage Calculations

```
Per URL record:
  short_code:    8 bytes
  long_url:      2,048 bytes (max URL length)
  user_id:       8 bytes (bigint)
  created_at:    8 bytes (timestamp)
  expires_at:    8 bytes (timestamp, nullable)
  click_count:   8 bytes (bigint)
  title:         256 bytes (optional page title)
  Overhead:      ~150 bytes (indexes, metadata)
  ─────────────────────────────────────────────
  Total/record: ~2,500 bytes ≈ 2.5 KB

Daily storage for new URLs:
  10,000,000 URLs × 2,500 bytes = 25 GB/day

Annual storage:
  25 GB/day × 365 = 9.1 TB/year

5-year storage:
  9.1 TB/year × 5 = ~45 TB total (URL metadata only)

Analytics event storage (click events):
  Per click event: ~200 bytes (short_code, timestamp, ip, country, device, referrer, ua)
  1,000,000,000 clicks/day × 200 bytes = 200 GB/day
  Annual click data: 73 TB/year
  → Use tiered storage: hot 30 days in ClickHouse, archive to S3/Glacier
```

### Bandwidth Calculations

```
Ingress (URL creation):
  116 writes/s × 2,500 bytes = 290 KB/s ≈ ~0.3 MB/s  (negligible)

Egress (redirect responses):
  Each redirect response: HTTP 302 header ~500 bytes
  11,600 reads/s × 500 bytes = 5.8 MB/s
  Peak: 58,000 reads/s × 500 bytes = 29 MB/s

Analytics ingress (Kafka):
  11,600 events/s × 200 bytes = 2.3 MB/s to Kafka
```

### Cache Sizing

```
Hot working set (Zipf's law: top 20% of URLs serve 80% of traffic):
  Active links in system: 10M URLs/day × 365 days = 3.65 billion total
  Hot working set (top 20%): 3.65B × 0.20 = 730 million links
  Cache size needed: 730M × 2,500 bytes = 1.825 TB

  With Redis cluster (128 GB nodes): need ~15 nodes
  Practical approach: cache top 10 million hottest links (Zipf means tiny fraction drives huge traffic)
  10M links × 2,500 bytes = 25 GB → fits in a single large Redis node or small cluster

Cache hit rate expectation: 95%+ (Zipf distribution)
Cache-effective read QPS to DB: 11,600 × 0.05 = 580 reads/s to database
```

### Server Count Estimate

```
Redirect servers (each handles ~5,000 req/s with Redis cache lookups):
  58,000 peak RPS ÷ 5,000 RPS/server = 12 servers
  With headroom (50% util target): 24 redirect servers

Write/API servers (lower traffic):
  580 peak writes/s, each write hits DB: 4-6 write API servers
```

### Component Rationale

**CDN (CloudFront/Akamai):** The redirect path is the most latency-sensitive and most trafficked operation. By caching the redirect response at the edge (using 301 for permanent links or 302 with short TTL for mutable links), a significant fraction of redirects never touch our origin servers. Akamai and CloudFront have PoPs within ~10ms of most users globally.

**Layer-7 Load Balancer:** Routes by URL path prefix — `/api/*` to write servers, `/:code` to redirect servers. This allows independent scaling of the two very different workloads. SSL termination here keeps backend servers simple.

**Separate Write and Redirect Clusters:** Redirect servers are read-only and stateless. They do not need write access to the database. Separating them allows redirect servers to be scaled and deployed independently, and they can be brought to zero downtime during URL creation failures.

**In-Process L1 Cache (Caffeine/Guava):** Each redirect server keeps a small (1-5 GB heap) local LRU cache of the hottest short codes. Zipf's law guarantees that a few hundred thousand codes absorb ~50% of all traffic. This eliminates the network round-trip to Redis for the very hottest links, bringing latency under 1ms.

**Redis Cluster (L2 Cache):** For the vast majority of links not in the L1 cache. Redis gives ~0.5ms lookup with a network hop. Using Redis Cluster (hash slots) provides horizontal scaling and no single point of failure.

**PostgreSQL (Primary + Read Replicas):** Only hit on cache miss (~5% of traffic). PostgreSQL provides strong consistency for writes, good index performance, and ACID guarantees for URL creation (important for collision avoidance with custom aliases). Read replicas serve the cold-path reads and analytics queries against the URL metadata.

**Kafka:** Decouples the redirect path from analytics writes. The redirect server emits a tiny click event (< 200 bytes) to Kafka fire-and-forget, adding < 1ms to the redirect path. Without this decoupling, synchronous analytics writes would slow every redirect by 10-50ms.

**ClickHouse:** Columnar OLAP database optimized for high-ingest append-only analytics. Can ingest millions of rows per second and run aggregation queries over billions of rows in seconds. Better fit for analytics than PostgreSQL for time-series click data.

## Step 4 — Data Model

### Core Entities

#### `urls` table (PostgreSQL)

```sql
CREATE TABLE urls (
    short_code       VARCHAR(10)     PRIMARY KEY,
    long_url         TEXT            NOT NULL,          -- max 8KB
    user_id          BIGINT          REFERENCES users(id) ON DELETE SET NULL,
    created_at       TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    expires_at       TIMESTAMPTZ,                       -- NULL = never expires
    is_active        BOOLEAN         NOT NULL DEFAULT TRUE,
    is_custom        BOOLEAN         NOT NULL DEFAULT FALSE,  -- vanity URL flag
    title            VARCHAR(512),                      -- page title for dashboard
    meta_tags        JSONB,                             -- og:image, description, etc.
    click_count      BIGINT          NOT NULL DEFAULT 0  -- denormalized counter
);

-- Lookup by short_code is the hottest query (redirect path)
-- PRIMARY KEY already covers this

-- List user's links ordered by recency
CREATE INDEX idx_urls_user_created ON urls (user_id, created_at DESC)
    WHERE is_active = TRUE;

-- Expiry sweeper query
CREATE INDEX idx_urls_expires ON urls (expires_at)
    WHERE expires_at IS NOT NULL AND is_active = TRUE;

-- Full-text search on long_url domain (for deduplication check)
CREATE INDEX idx_urls_long_url_hash ON urls (md5(long_url));
```

**Why PostgreSQL for this table:**
- Short code uniqueness is a hard constraint — needs ACID on insert
- Custom alias check-and-reserve must be atomic (SELECT FOR UPDATE or INSERT ... ON CONFLICT)
- Volume is manageable: 10M inserts/day × 365 = 3.65B rows/year → partition by `created_at` range

#### `users` table (PostgreSQL)

```sql
CREATE TABLE users (
    id               BIGINT          PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    email            VARCHAR(320)    UNIQUE NOT NULL,
    password_hash    VARCHAR(256),
    plan             VARCHAR(32)     NOT NULL DEFAULT 'free',  -- free, pro, enterprise
    created_at       TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    rate_limit_tier  SMALLINT        NOT NULL DEFAULT 1
);
```

#### `click_events` table (ClickHouse)

```sql
CREATE TABLE click_events (
    short_code       String,
    clicked_at       DateTime,          -- event time (second precision)
    ip_hash          String,            -- HMAC-SHA256 of IP (privacy-preserving)
    country_code     LowCardinality(String),
    city             String,
    device_type      LowCardinality(String),  -- desktop, mobile, tablet, bot
    browser          LowCardinality(String),
    os               LowCardinality(String),
    referrer_domain  String,
    user_agent_hash  String             -- for bot dedup without storing full UA
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(clicked_at)
ORDER BY (short_code, clicked_at)
TTL clicked_at + INTERVAL 2 YEAR DELETE;
```

**Why ClickHouse for click events:**
- Append-only, never updated — perfect fit for columnar storage
- Queries like "clicks per country for link X in the last 7 days" run in milliseconds on billions of rows
- MergeTree engine handles high-ingest (millions of rows/s) naturally
- ORDER BY `(short_code, clicked_at)` makes per-link time-range queries use the primary index directly

#### `click_aggregates` table (ClickHouse — materialized view)

```sql
CREATE MATERIALIZED VIEW click_aggregates
ENGINE = SummingMergeTree()
PARTITION BY toYYYYMM(day)
ORDER BY (short_code, day, country_code, device_type)
AS SELECT
    short_code,
    toDate(clicked_at)      AS day,
    country_code,
    device_type,
    count()                 AS clicks
FROM click_events
GROUP BY short_code, day, country_code, device_type;
```

Pre-aggregated daily rollups for fast dashboard queries without scanning raw events.

#### ID Range Allocations table (PostgreSQL — for ID generation)

```sql
CREATE TABLE id_ranges (

    range_start      BIGINT          NOT NULL,
    range_end        BIGINT          NOT NULL,
    range_current    BIGINT          NOT NULL,
    allocated_at     TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
```

## Step 6 — Deep Dive: ID Generation (The Hardest Component)

This is where most candidates go shallow. The real challenge is generating 6-8 character unique short codes at 600 writes/s peak, globally, without collisions, while keeping codes opaque (non-sequential to external observers).

### Why This Is Hard

Three competing requirements create tension:

1. **Uniqueness**: Two different long URLs must never get the same short code.
2. **Non-sequential appearance**: Users should not be able to enumerate all links by incrementing a counter.
3. **Fixed length**: The code must be 6-8 characters (base62 gives 62^6 = 56.8 billion or 62^7 = 3.5 trillion possibilities for 6 or 7 chars).
4. **Speed**: ID generation must not be the bottleneck at 600 writes/s.

### Option A: Hash-Based (MD5/SHA-256 Truncation) — Rejected for Primary Path

```
long_url → SHA-256 → take first 43 bits → base62 encode → 7-char code
```

**The collision problem:**
Using the Birthday Paradox: with 43 bits of entropy (~8.8 trillion values) and 3.65 billion existing links after 1 year:
```
P(collision) ≈ n² / (2 × 2^43)
             = (3.65 × 10^9)² / (2 × 8.8 × 10^12)
             = 1.33 × 10^19 / 1.76 × 10^13
             ≈ 756,000  (expected collisions after 1 year!)
```
This is catastrophically bad. You would need to re-hash with a salt on each collision, adding retry loops that are hard to bound.

**Collision retry with salt:**
```python
def hash_url(long_url: str, attempt: int = 0) -> str:
    h = hashlib.sha256(f"{long_url}:{attempt}".encode()).digest()
    num = int.from_bytes(h[:6], 'big') % (62**7)
    return base62_encode(num)
```
This works but requires a DB round-trip check per attempt, which can cascade under load.

**Also problematic:** The same URL always hashes to the same code. If someone shortens `google.com` twice, they get the same code — which is a feature or a bug depending on requirements (deduplication vs. independent tracking per campaign).

---

### Option B: Pure Auto-Increment Counter (Rejected for Security)

```
INSERT INTO urls → RETURNING id → base62_encode(id)
```

Sequential IDs are trivially enumerable. Anyone can crawl all shortened links by iterating codes. Discarded for any public-facing service.

---

### Option C: Snowflake-Inspired Distributed ID (Good but Long)

Twitter's Snowflake generates 64-bit IDs:
```
[41-bit timestamp][10-bit machine ID][12-bit sequence]
```

Base62 encoding of a 64-bit integer:
```
2^64 = 18.4 × 10^18
log_62(18.4 × 10^18) = 10.7 → 11 characters
```

This is too long (we want 6-7 chars). You cannot truncate a Snowflake ID without destroying the machine-ID or sequence bits, causing collisions.

---

### Option D: Pre-Allocated Range Counter (CHOSEN APPROACH — Production-Grade)

This is the approach used in production systems at scale. It combines the simplicity of sequential IDs with distributed generation and non-sequential appearance via Fisher-Yates shuffling of the ID space.

#### Step-by-step Algorithm

**Step 1: Range Pre-allocation from ZooKeeper**

Each write API server, on startup, claims a non-overlapping numeric range:

```python
import kazoo.client

class IDRangeManager:
    RANGE_SIZE = 5_000  # each server gets 5000 IDs per allocation

    def __init__(self, zk: KazooClient, server_id: str):
        self.zk = zk
        self.server_id = server_id
        self._current = 0
        self._end = 0
        self._lock = threading.Lock()

    def _allocate_range(self):
        """Atomically claim next unused range from ZooKeeper."""
        with self.zk.Lock("/id_counter_lock"):
            counter_bytes, _ = self.zk.get("/id_counter")
            start = int(counter_bytes.decode())
            end = start + self.RANGE_SIZE
            self.zk.set("/id_counter", str(end).encode())
            self._current = start
            self._end = end
            log.info(f"Allocated range [{start}, {end}) for {self.server_id}")

    def next_id(self) -> int:
        with self._lock:
            if self._current >= self._end:
                self._allocate_range()
            val = self._current
            self._current += 1
            return val
```

**Step 2: Feistel Cipher Scrambling**

A Feistel network is a symmetric block cipher structure. Using a 32-bit Feistel with our secret key, sequential integers map to pseudo-random values with zero collisions (it is a bijection):

```python
import struct, hmac, hashlib

SECRET_KEY = b"your-secret-key-here"  # stored in Vault / KMS

def feistel_round(value: int, round_key: bytes) -> int:
    """Single Feistel round function."""
    h = hmac.new(round_key, struct.pack('>I', value), hashlib.sha256).digest()
    return struct.unpack('>I', h[:4])[0]

def feistel_encrypt(num: int, num_rounds: int = 4) -> int:
    """
    32-bit Feistel cipher over a 32-bit integer.
    Input range: [0, 2^32)
    Output range: [0, 2^32) — bijective, no collisions
    """
    left  = (num >> 16) & 0xFFFF
    right =  num        & 0xFFFF
    for i in range(num_rounds):
        round_key = HMAC(SECRET_KEY, i.to_bytes(4, 'big'))
        new_right = left ^ feistel_round(right, round_key)
        left, right = right, new_right
    return (left << 16) | right

BASE62 = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

def encode_base62(n: int, length: int = 7) -> str:
    """Encode integer to fixed-length base62 string."""
    chars = []
    for _ in range(length):
        chars.append(BASE62[n % 62])
        n //= 62
    return ''.join(reversed(chars))

def generate_short_code(range_manager: IDRangeManager) -> str:
    num_id = range_manager.next_id()
    scrambled = feistel_encrypt(num_id)
    return encode_base62(scrambled)
```

**Step 3: Collision Guarantees**

With this approach, collision is **mathematically impossible** as long as:
- Each server's numeric range is non-overlapping (enforced by ZooKeeper)
- The Feistel cipher is collision-free (bijection over the integer space — guaranteed by cipher structure)

No DB round-trips needed to check uniqueness for auto-generated codes. This is the key performance advantage over hash-based approaches.

**Step 4: Custom Aliases (Vanity URLs)**

For user-specified codes, we use a standard DB unique constraint:

```sql
INSERT INTO urls (short_code, long_url, user_id, is_custom)
VALUES ($1, $2, $3, TRUE)
ON CONFLICT (short_code) DO NOTHING
RETURNING short_code;
```

If the INSERT returns null, the alias is taken → return 409 to the user. No ZooKeeper needed here.

#### Capacity of the ID Space

```
7-character base62: 62^7 = 3,521,614,606,208 ≈ 3.5 trillion unique codes
At 10M new URLs/day: 3.5T / 10M = 350,000 days ≈ 958 years of capacity
```

We will never exhaust the 7-character space in any reasonable time horizon.

#### ZooKeeper Failure Handling

If ZooKeeper is unavailable when a server needs a new range:
1. The server continues serving redirects (read path unaffected)
2. URL creation returns 503 with retry-after header
3. Each server pre-fetches the next range before exhausting the current one (at 80% utilization), making ZooKeeper downtime transparent in normal operation
4. Alternatively, persist the last claimed range to the server's local disk on allocation — restart recovery reads from disk

## Step 7 — Deep Dive: The Redirect Path (Second Hardest Component)

The redirect path is the hottest, most latency-sensitive operation in the system. At 58,000 peak QPS, it must complete in under 20ms p99 end-to-end, including the network round-trip from the user's location.

### The Three-Layer Cache Strategy

### Redirect Response Latency Breakdown

```
Scenario: CDN miss, L1 miss, Redis hit (most common hot path)

Client → CDN PoP:          ~8ms  (network, ~500 miles away)
CDN → Load Balancer:       ~2ms  (CDN PoP to our origin region)
Load Balancer processing:  ~0.5ms
Redirect server (L1 miss): ~0.1ms
Redirect server → Redis:   ~0.6ms (L2 hit)
Response back to CDN:      ~2ms
CDN → Client:              ~8ms
─────────────────────────────────
Total p50:                 ~13ms

With L1 cache hit:
CDN → origin round-trip replaced by 0.1ms local lookup
Total p50 with L1 hit:     ~1.5ms (for the origin portion)
User-perceived: ~10ms
```

### Async Click Tracking — Fire-and-Forget

This is the key architectural decision that enables sub-10ms redirect latency. Click analytics must never block the response.

```python
from fastapi import FastAPI, Request
from fastapi.responses import RedirectResponse
import asyncio
import aiokafka

app = FastAPI()
producer = aiokafka.AIOKafkaProducer(bootstrap_servers="kafka:9092")

@app.get("/{short_code}")
async def redirect(short_code: str, request: Request):
    # Critical path: cache lookup
    long_url = await cache_lookup(short_code)
    if long_url is None:
        long_url = await db_lookup(short_code)
        if long_url is None:
            return Response(status_code=404)
        await cache_populate(short_code, long_url)

    # Fire-and-forget: does NOT await this
    asyncio.create_task(
        emit_click_event(short_code, request)
    )

    # Return redirect immediately
    return RedirectResponse(
        url=long_url,
        status_code=302,
        headers={"Cache-Control": "no-store"}
    )

async def emit_click_event(short_code: str, request: Request):
    """This runs after response is sent. Does not block redirect."""
    event = {
        "short_code": short_code,
        "clicked_at": datetime.utcnow().isoformat(),
        "ip":         request.client.host,
        "user_agent": request.headers.get("user-agent", ""),
        "referrer":   request.headers.get("referer", ""),
    }
    await producer.send("click_events", value=orjson.dumps(event))
```

### Cache Invalidation on URL Update/Delete

When a URL is deactivated or its destination updated:

1. Write API server updates PostgreSQL (primary)
2. Publishes invalidation message to Redis Pub/Sub channel `cache:invalidate`
3. All redirect servers subscribed to that channel flush the key from their L1 cache
4. Redis key is deleted directly from the Redis cluster
5. CDN: issue a cache invalidation API call to CloudFront for that path (`/3xK9pQ`)

Total invalidation propagation time: ~100-500ms (CDN invalidation can take up to 60s at the edge but is irrelevant for delete since we tolerate brief 404 or stale redirect for deleted links).

### Handling the "Thundering Herd" on Cache Miss

When a popular link expires from cache (e.g., a viral link is featured on a news homepage):

```
Problem: 10,000 simultaneous requests all miss Redis and all hit DB concurrently

Solution: Redis SETNX-based mutex (single-flight pattern)

1. Thread 1 misses Redis
2. Thread 1 atomically sets "lock:3xK9pQ" with 500ms TTL using SETNX
3. Thread 1 fetches from DB and populates Redis
4. Thread 2-10000 miss Redis, fail SETNX, wait on a short sleep
5. Thread 2+ re-check Redis after lock releases, find cached value

Alternative: use Redis WAIT or a "probabilistic early expiration" algorithm:
  - Start background refresh when TTL drops below 10% of original
  - Never let the key fully expire under hot traffic
```

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (10× QPS = 116,000 peak redirect RPS)

**Bottleneck:** Redis cluster becomes the hot spot. At 116,000 RPS with 95% cache hit rate, Redis handles 110,000 ops/s. A single Redis node tops out at ~100,000 ops/s for GET commands.

**Fix:** Scale Redis cluster from 3 shards to 10 shards (rebalance hash slots). Simultaneously tune L1 in-process cache to hold 5M entries instead of 1M per server by increasing heap allocation. With good Zipf distribution, top 5M links in L1 cache absorb >60% of traffic before hitting Redis.

Also: CDN cache TTL tuning — increase from 5 minutes to 15 minutes for high-traffic links to reduce origin hit rate further.

### At 100x Current Load (1,160,000 peak redirect RPS)

**Bottleneck:** PostgreSQL read replicas cannot handle the remaining 5% of cache misses at this scale. At 1.16M RPS × 5% = 58,000 DB reads/s. A single PostgreSQL node handles ~10,000-50,000 simple PK lookups/s depending on hardware, but with replication lag and concurrent writes, you approach the limit.

**Fix 1:** Partition the `urls` table by the first character of `short_code` (62 partitions) and route each partition to a dedicated read replica. This distributes DB load across 62 read replicas.

**Fix 2:** Add a second-level in-process cache tier: a consistent-hashing layer where each redirect server "owns" a slice of the keyspace. Requests for `short_code` starting with `a-g` always go to servers 1-4, enabling better L1 cache utilization (each server's L1 only needs to cache its owned slice, increasing effective cache hit rate).

**Fix 3:** Move to a purpose-built KV store for the hot read path. Aerospike or ScyllaDB can sustain 1-2M reads/s per node on flash storage with < 1ms p99 latency, replacing PostgreSQL on the redirect read path (PostgreSQL becomes the write master and analytics source of truth only).

**Kafka bottleneck:** At 1.16M click events/s, Kafka at 3 brokers is near its ingest limit (~1-2M messages/s). Expand to 9-12 Kafka broker nodes and increase partitions from 24 to 96.

### At 1000x Current Load (11.6 million peak redirect RPS)

**This requires fundamental architectural changes:**

1. **Global edge computing:** Move the redirect logic itself to the CDN edge (CloudFront Functions, Cloudflare Workers). These execute JavaScript in < 1ms at 300+ edge locations. The redirect becomes a KV lookup at the edge using Cloudflare Workers KV or similar distributed edge KV store. No origin hit at all for cached links.

2. **Stateless URL database at edge:** Replicate the URL → destination mapping to an edge-distributed KV store (Cloudflare Workers KV provides eventual consistency to ~300 locations in ~10s). At 11.6M RPS, this is the only way to avoid origin bottlenecks without 1000+ origin servers.

3. **Write path separate region:** URL creation still hits a central origin for consistency, but reads become fully edge-served.

4. **Analytics at this scale:** ClickHouse ingest exceeds single-cluster capacity at 11.6M events/s. Require a distributed ClickHouse cluster with 20+ shards, or switch to Apache Druid which was designed for this write throughput.

5. **Cost inflection point:** At 11.6M RPS, hosting costs exceed $5M/month without edge architecture. The economic driver alone forces edge-native design.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| ID generation | Range-counter + Feistel cipher | Hash-based (MD5 truncation) | Zero-collision guarantee without DB round-trip; hashing has birthday collision problem at scale |
| Short code length | 7 characters (base62) | 6 characters | 62^7 = 3.5T codes (centuries of capacity); 62^6 = 56B (runs out in ~15 years at growth) |
| Redirect response type | HTTP 302 (temporary) | HTTP 301 (permanent) | 302 enables click tracking and allows destination updates; 301 caches at browser, breaking analytics and updates |
| Primary database | PostgreSQL | Cassandra/DynamoDB | URL creation needs ACID (custom alias uniqueness, atomic inserts); NoSQL would require application-level collision handling |
| Analytics database | ClickHouse (columnar OLAP) | PostgreSQL, BigQuery | ClickHouse handles 1M+ events/s ingest and sub-second aggregations; PostgreSQL can't sustain analytics write throughput alongside OLTP |
| Analytics pipeline | Kafka + stream processing | Synchronous writes | Async decoupling keeps redirect latency < 10ms; synchronous would add 10-50ms per click |
| Cache invalidation | Redis Pub/Sub + CDN API | TTL expiry only | Immediate consistency on deletes; TTL-only means deleted links redirect for up to 5 min |
| ZooKeeper for ID ranges | ZooKeeper | Database sequence | ZooKeeper provides distributed coordination primitive; DB sequences are a serialization bottleneck at high write rates |
| Redirect server L1 cache | Caffeine in-process LRU | External cache only | Eliminates Redis network hop for hot keys; sub-millisecond lookup for top ~1M links |
| Custom aliases collision | INSERT ... ON CONFLICT | Distributed lock | Database unique constraint is the most reliable collision avoidance for user-provided strings |
| Click event schema | HMAC of IP (privacy) | Raw IP storage | GDPR/CCPA compliance; raw IPs are PII; HMAC preserves deduplication capability |

## Step 10 — How Real Companies Solved This

### Bitly

**Architecture Evolution:**

Bitly's early architecture (2008-2013) used MySQL as the primary store for URL mappings. The first scaling problem they hit was **MySQL becoming read-saturated** as click traffic grew. Their solution was aggressive Memcached caching, which shifted load distribution to ~98% cache hits.

**The Python to Go Migration:**

Bitly famously migrated their redirect service from Python to Go around 2012-2013 (one of the earliest high-profile Go production deployments). The Go implementation handled concurrent redirect requests with goroutines instead of Python threads, dramatically reducing memory per connection and enabling the same hardware to handle 10× more concurrent connections. Their blog post "Writing a High Performance URL Shortener in Go" documented this.

**Analytics Pipeline:**

Bitly built their own analytics pipeline called "NSQ" (a message queue they open-sourced in 2012) before Kafka was widely adopted. NSQ was Go-native and designed for their specific event fan-out patterns. They eventually moved toward Kafka for newer services.

**Key insight from Bitly engineering:** The redirect path and the analytics path must be completely decoupled from day one. Their first architecture had synchronous click counting — a single slow database write query caused redirect latency spikes that frustrated users. The async pipeline was retrofitted, which is why they always advise designing it decoupled from the start.

**Scale numbers (public):** 600M+ links shortened monthly, 10B clicks tracked monthly. Their infrastructure uses AWS with ELB, multiple availability zones, and CloudFront for CDN.

**What they got wrong first:** Custom domains caused unexpected complexity. When Bitly added custom branded domains (e.g., `cnn.it` for CNN), each domain needed its own SSL certificate, DNS configuration, and routing rule. They initially handled this with a mapping table but ran into SSL certificate management at scale — managing thousands of domains. The solution was wildcard certs and automated Let's Encrypt certificate provisioning.

---

### Twitter/X — t.co

**The problem Twitter solved:** When Twitter introduced t.co (2011), every URL posted in a tweet had to be shortened, regardless of length. This was non-optional — Twitter needed to track all external link traffic.

**Architecture constraint:** t.co processes every single tweet that contains a URL. At peak Twitter scale (6,000 tweets/s × ~30% contain URLs = ~1,800 URL creations/s, plus 100× more clicks), the system must be highly available as a dependency of the tweet-creation pipeline.

**Key design decision:** t.co performs URL expansion at tweet creation time (eager expansion), not lazily at click time. When you post a tweet, Twitter immediately resolves the short URL chain, follows redirects, and stores the final destination. This prevents malicious redirect chains (A → B → phishing site) from being discovered only at click time.

**Abuse protection:** t.co has deep integration with Twitter's Trust & Safety infrastructure. Every URL is scanned against Google Safe Browsing and Twitter's own malicious URL database before the tweet is published. URLs that fail scanning result in tweet creation failure, not just a disabled link.

**What they got wrong:** The "pre-expand on creation" approach means tweet creation latency spikes when upstream URLs are slow. If you post a link to a slow website, your tweet takes longer to post because t.co is waiting for the HEAD request to resolve the destination. This was mitigated with aggressive timeouts (500ms max) and fallback behavior (accept the URL unvalidated if it times out, scan async).

**Key engineering insight:** For a URL shortener that is a dependency of a write path (tweet creation), you must design for the shortener to never block. Async creation with eventual consistency is better than synchronous creation with blocking behavior. Twitter learned this the hard way when t.co slowness cascaded to tweet creation failures.

## Interview Perspective

### What the Interviewer Is Evaluating

This problem is specifically testing:

1. **ID generation strategy** — Do you know why hashing fails at scale? Can you articulate the birthday paradox problem? Do you know the Feistel/range-counter approach?
2. **Cache layering** — Can you design a multi-tier cache (L1/L2/L3) and explain the hit rate economics?
3. **Async decoupling** — Do you instinctively separate the redirect path from analytics, or do you try to do it synchronously?
4. **301 vs. 302 trade-off** — This is a well-known trick question. If you say "301 is faster, use 301" without discussing analytics implications, you lose points.
5. **Scale reasoning** — Can you identify the specific bottleneck at each scale tier (Redis throughput, DB read capacity, Kafka ingest)?

### Junior (L3-L4) Answer

**What they say:** "Hash the URL with MD5, take first 6 characters, store in MySQL with short_code as primary key. Use Redis to cache popular lookups."

**Depth reached:** High-level happy path. Basic caching and database.

**What they miss:**
- Hash collision probability (think birthday paradox — collisions are near-certain at scale)
- Analytics pipeline entirely (or propose synchronous writes)
- 301 vs. 302 distinction
- Custom alias conflict handling
- URL expiration cleanup
- Any discussion of the write vs. read path being different problems

### Senior (L5) Answer

**What they add:**
- Recognizes MD5 collision problem, proposes either retry-with-salt or range-counter approach
- Separates write cluster from read cluster
- Proposes Kafka-based async analytics pipeline
- Discusses 301 vs. 302 trade-off correctly
- Mentions consistent hashing for Redis cluster
- Estimates capacity (DAU, QPS, storage)
- Handles URL expiration with a background sweeper

**Specific depth on this problem:**
- Can explain why base62 with 7 characters gives 3.5 trillion possible codes
- Knows that ZooKeeper or a distributed counter service eliminates the collision problem without retries
- Understands cache warming strategies and Zipf distribution implications

### Staff (L6+) Answer

**What they drive to unprompted:**

1. **Operational concerns:** "How do we handle ZooKeeper unavailability? The write path must degrade gracefully — serve 503 for new URL creation but never affect redirects."

2. **Cost reasoning:** "At 100K+ RPS, CDN costs become significant. We can reduce CDN costs by setting longer cache TTLs on stable links, but this conflicts with our ability to update destinations. We'd want a segmented TTL policy: recently-created links get 5-minute TTL, links older than 30 days with consistent traffic get 1-hour TTL."

3. **Security / abuse surface:** "Short URLs are weaponized for phishing because they obscure the destination. We need to scan every new URL against Google Safe Browsing API, implement rate limiting per user and per IP for creation, and have a SafePreview mode that shows users the destination before redirecting."

4. **Click counting accuracy:** "Our Redis-based click counter will have race conditions at high concurrency. We should use Redis INCR (atomic) for the counter, not a read-modify-write. For the analytics database, we should deduplicate clicks from the same (short_code, ip_hash) within a 1-hour window to avoid inflating counts from bots."

5. **Multi-region and data residency:** "For enterprise customers in the EU, we may need link data to reside in EU data centers. This means our PostgreSQL primary-replica topology needs to be region-aware, with EU writes going to an EU primary and US writes going to a US primary — a multi-master or CRDT-based consistency model for the URL table."

6. **Monitoring and SLOs:** "The redirect p99 latency is our core SLO. We should instrument L1 cache hit rate, L2 cache hit rate, and DB read latency as separate metrics with alerting. A drop in L1 hit rate from 50% to 30% is an early warning that our in-process cache is too small or that traffic patterns have changed."

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **Using MD5/SHA-256 hash without acknowledging birthday collisions.** Saying "just hash the URL" without understanding that at 3 billion links, the collision probability with 43-bit codes is near-100% is a red flag. Always mention the birthday paradox and explain how you handle it.

2. **Using 301 (Permanent Redirect) without qualification.** Many candidates default to 301 because "it's cached and therefore faster." But 301 is cached by the browser forever — the user's browser will never contact your server again for that link, meaning you can't update the destination, can't delete the link, and can't track clicks. The correct answer for a tracking-enabled shortener is **302 with CDN caching**.

3. **Writing analytics synchronously in the redirect path.** Candidates will say "record the click in the database when the redirect happens." At 11,600 req/s, a 5ms synchronous DB write per click adds 5ms to every redirect. Fire-and-forget to Kafka is the correct pattern.

4. **Forgetting about URL expiration and garbage collection.** At 10 million new URLs per day, without expiration and cleanup, the database grows by 25 GB/day indefinitely. Candidates forget to design the background sweeper that marks expired URLs inactive and evicts them from cache.

5. **Not handling the custom alias race condition.** When two users simultaneously request the same custom alias, a naive implementation has a TOCTOU (time-of-check-time-of-use) race. The only correct solution is to use a database-level unique constraint and handle the constraint violation at the application layer — not application-level locking.
