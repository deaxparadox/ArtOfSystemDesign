> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Multi-channel delivery (push/email/SMS), fan-out to millions, delivery guarantees, user preferences per channel

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

A notification system is a platform that accepts trigger events from upstream services and reliably delivers messages to users across multiple channels — push notifications, email, SMS, and in-app — according to each user's preferences, at massive scale.

Uber sends ~15 million push notifications per day. Facebook sends hundreds of millions of notifications daily across channels. LinkedIn's notification platform processes billions of events per month across email, push, and in-app, while ensuring that no single user receives more than a configured threshold of messages per hour. The defining challenge is the intersection of _scale_ (fan-out to millions of devices), _reliability_ (guaranteed delivery even through provider outages), and _personalization_ (user opt-outs, channel preferences, do-not-disturb windows, frequency caps).

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Multi-channel delivery**: Send notifications via push (APNs/FCM), email (SendGrid/SES), SMS (Twilio/Vonage), and in-app.
2. **User preference management**: Users can opt out of specific channels or notification categories. Critical/transactional alerts bypass opt-outs.
3. **Guaranteed at-least-once delivery**: Every triggered notification must be delivered at least once; the system must retry on failure.
4. **Scheduled and delayed notifications**: Support sending a notification at a future timestamp, not just immediately.
5. **Priority tiers**: Transactional alerts (OTP, security alerts) get higher priority and bypass rate limits; marketing messages get lower priority and are rate-limited.
6. **Delivery tracking and analytics**: Record sent/delivered/opened/failed status per notification for observability and product feedback.

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% (< 52 min/year downtime) |
| Throughput | 1 million notifications/minute peak |
| Delivery latency (push) | p99 < 5 seconds end-to-end |
| Delivery latency (email/SMS) | p99 < 30 seconds |
| Durability | Zero message loss after accepted |
| Idempotency | At-most-one visible delivery (dedup window: 24 h) |
| Scalability | Linear horizontal scale for workers |

### Out of Scope

- Building the upstream event producers (order service, social graph, etc.)
- End-user device firmware or OS push infrastructure (APNs, FCM are treated as external dependencies)
- Rich media / attachment storage beyond reference URLs
- Real-time streaming protocols (WebSocket, SSE) for in-app delivery — those belong to a chat/streaming system design
- A/B testing and content personalization engine (assumed to be an upstream content service)
- Email deliverability tuning (DKIM, SPF, bounce handling in depth)

### Clarifying Questions to Ask the Interviewer

1. **Scale of writes**: How many notification events per second at peak? This determines Kafka partition count and worker fleet size. (Start with 10,000/s = ~864M/day)
2. **Channel mix**: What percentage of traffic goes to each channel? Push is cheap; SMS is expensive. Cost drives architecture. (Assume 60% push, 30% email, 10% SMS)
3. **Delivery guarantee level**: Is at-least-once acceptable, or do we need exactly-once visible delivery? Exactly-once requires distributed deduplication, which adds latency.
4. **Fan-out shape**: Is this a 1-to-1 notification (one event → one user) or a broadcast (one event → millions of users, like a platform announcement)? Broadcasts require a fundamentally different write-fan-out vs. read-fan-out decision.
5. **User preferences storage**: Do preferences need to be respected in real time, or can we tolerate a few minutes of staleness? Real-time requires a preference cache; staleness allows simpler polling.
6. **Regulatory requirements**: Are there regions with SMS regulations (GDPR opt-in, TCPA consent)? This affects the preference model complexity.
7. **SLA differentiation**: Do transactional messages (OTP, password reset) have a separate SLA from marketing? (Almost always yes — answer drives priority queue design.)

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

| Variable | Value | Reasoning |
|---|---|---|
| MAU | 500 million | Mid-size global platform |
| DAU | 200 million | 40% daily engagement |
| Avg notifications per DAU per day | 5 | Mix of social, transactional, marketing |
| Peak-to-average multiplier | 3x | Evening spike (7–10 PM local time) |
| Channel mix | 60% push, 30% email, 10% SMS | Industry typical |

### Write QPS (Notification Ingestion)

```
Daily notifications = 200M DAU × 5 = 1 billion/day
Average write QPS  = 1B / 86,400 s ≈ 11,574/s  ≈ 12,000/s
Peak write QPS     = 12,000 × 3     ≈ 36,000/s  (35K/s rounded)
```

### Read QPS (Preference Lookups)

Every notification triggers a preference lookup. Assume 100% cache hit rate after warm-up; cache still needs to handle:

```
Peak reads = 36,000/s (one preference check per notification)
```

### Channel Dispatch Breakdown (at peak)

```
Push notifications: 36,000 × 0.60 = 21,600/s → to FCM/APNs
Email:              36,000 × 0.30 = 10,800/s → to SendGrid/SES
SMS:                36,000 × 0.10 =  3,600/s → to Twilio/Vonage
```

### Storage Estimation

**Notification event log** (durability layer — Kafka retention 7 days):

```
Avg event size     = 1 KB (JSON payload + metadata)
Daily volume       = 1B × 1 KB = 1 TB/day
7-day Kafka retention = 7 TB (before replication)
Kafka replication factor 3 = 21 TB raw Kafka storage
```

**Notification history DB** (status tracking, 90-day window):

```
Per-record size    = 512 bytes (IDs + status + timestamps + channel)
Daily records      = 1 billion
90-day records     = 90 billion rows
90-day storage     = 90B × 512 B = 45 TB (before compression)
With 4:1 compression (columnar store) = ~11 TB
```

**User preference store**:

```
Users              = 500 million
Per-user prefs     = 256 bytes (channel flags, category map, DND window)
Total              = 500M × 256 B = 128 GB (fits comfortably in Redis)
```

**Device token store**:

```
Users with push    = 300 million (60% of MAU)
Avg tokens/user    = 2 (phone + tablet)
Per-token size     = 256 bytes
Total              = 600M × 256 B = 154 GB
```

### Bandwidth

```
Ingress (event intake):   36,000/s × 1 KB = 36 MB/s ≈ 288 Gbps/day volume
Egress (to 3rd-party APIs): Similar order of magnitude per channel
```

### Server Count Estimate

```
API Gateway (stateless, 5K req/s per server):     ceil(36K / 5K) = 8 servers  → 10 with headroom
Kafka brokers (1 GB/s throughput each):           ceil(36 MB/s / 1 GB/s) = 1 → 6 with replication
Push workers (500 FCM/APNs calls/s per worker):   ceil(21,600 / 500) = 44   → 50 workers
Email workers (200 SMTP calls/s per worker):      ceil(10,800 / 200) = 54   → 60 workers
SMS workers   (100 Twilio calls/s per worker):    ceil(3,600 / 100) = 36    → 40 workers
Preference cache (Redis, 128 GB fit in 2 nodes):  3 nodes (primary + 2 replicas)
```

### Component Walkthrough

**API Gateway / LB**: Terminates TLS, enforces per-producer rate limits (Order Service is allowed 10K/s; Marketing is capped at 1K/s), and routes to the Notification Service fleet. It exists because producers must be decoupled from internal topology.

**Notification Service (API Layer)**: The single write path. Every incoming notification is (1) deduplicated via a Redis SET NX on `idempotency_key` with 24-hour TTL, (2) written to an Outbox table inside the same MySQL transaction as the event record (Transactional Outbox pattern — ensures we never lose a message if the Kafka publish crashes), and (3) published to the `notifications.raw` Kafka topic. The Outbox guarantees durability; Kafka guarantees fan-out.

**Preference Engine (Fan-out Coordinator)**: Reads from `notifications.raw`, fetches user preferences from Redis (warm cache, 128 GB), applies frequency caps (Redis INCR with TTL per user per channel per hour), and re-publishes to per-channel Kafka topics. This is the routing brain. It exists as a separate service because the routing logic is complex, stateful (frequency caps), and needs to be updated independently of dispatch workers.

**Scheduler Service**: Uses Temporal/Cadence for durable delayed execution. Marketing teams schedule batches at 9 AM local time per user timezone. The scheduler stores scheduled jobs in MySQL, wakes them at the right time, and re-injects into the Preference Engine pipeline.

**Per-channel Workers (Push / Email / SMS)**: Stateless consumer pods each consuming from a dedicated Kafka topic. They call the respective third-party APIs (FCM, APNs, SendGrid, Twilio), handle retries with exponential backoff, and write delivery events to the Status Tracker's Kafka topic. Stateless so auto-scaling is trivial.

**Status Tracker**: Consumes delivery events and writes to Cassandra (high write throughput, time-series access pattern). Webhook receivers from FCM/APNs/Twilio call this service to update delivery status asynchronously.

**Device Token Store**: MySQL sharded by user_id with Redis read cache. Stores FCM registration tokens and APNs device tokens. Includes last-active timestamp for token expiry management.

## Step 4 — Data Model

### Core Entities

#### `notifications` table (MySQL, sharded by notification_id)

```sql
CREATE TABLE notifications (
    notification_id  CHAR(36)     NOT NULL,          -- UUID v4
    idempotency_key  VARCHAR(128) NOT NULL,           -- caller-supplied key
    producer_id      VARCHAR(64)  NOT NULL,           -- e.g. "order-service"
    user_id          BIGINT       NOT NULL,
    template_id      VARCHAR(64),                     -- NULL for ad-hoc
    channel          ENUM('push','email','sms','inapp') NOT NULL,
    priority         TINYINT      NOT NULL DEFAULT 5, -- 1=critical, 5=normal, 10=marketing
    payload          JSON         NOT NULL,           -- rendered content or template vars
    scheduled_at     DATETIME(3),                     -- NULL = immediate
    created_at       DATETIME(3)  NOT NULL DEFAULT NOW(3),
    PRIMARY KEY (notification_id),
    UNIQUE KEY uk_idempotency (idempotency_key),
    INDEX idx_user_created (user_id, created_at)
);
```

#### `notification_delivery` table (Cassandra, partition by notification_id)

```cql
CREATE TABLE notification_delivery (
    notification_id  UUID,
    attempt_num      INT,
    channel          TEXT,
    status           TEXT,      -- 'pending' | 'sent' | 'delivered' | 'failed' | 'bounced'
    provider         TEXT,      -- 'fcm' | 'apns' | 'sendgrid' | 'twilio'
    provider_msg_id  TEXT,      -- external message ID from provider
    error_code       TEXT,
    attempted_at     TIMESTAMP,
    delivered_at     TIMESTAMP,
    PRIMARY KEY (notification_id, attempt_num)
) WITH CLUSTERING ORDER BY (attempt_num ASC);
```

#### `user_preferences` table (MySQL, cached in Redis)

```sql
CREATE TABLE user_preferences (
    user_id          BIGINT       NOT NULL,
    channel          ENUM('push','email','sms','inapp') NOT NULL,
    category         VARCHAR(64)  NOT NULL,           -- 'social', 'transactional', 'marketing'
    opted_in         BOOLEAN      NOT NULL DEFAULT TRUE,
    dnd_start_hour   TINYINT,                         -- UTC hour, 0-23
    dnd_end_hour     TINYINT,
    frequency_cap    SMALLINT,                        -- max per day, NULL = no cap
    updated_at       DATETIME(3)  NOT NULL,
    PRIMARY KEY (user_id, channel, category)
);
```

#### `device_tokens` table (MySQL, cached in Redis)

```sql
CREATE TABLE device_tokens (
    token_id         BIGINT       NOT NULL AUTO_INCREMENT,
    user_id          BIGINT       NOT NULL,
    platform         ENUM('ios','android','web') NOT NULL,
    token            VARCHAR(512) NOT NULL,
    app_bundle_id    VARCHAR(128),
    is_active        BOOLEAN      NOT NULL DEFAULT TRUE,
    last_active_at   DATETIME(3)  NOT NULL,
    created_at       DATETIME(3)  NOT NULL,
    PRIMARY KEY (token_id),
    UNIQUE KEY uk_token (token),
    INDEX idx_user_platform (user_id, platform, is_active)
);
```

#### `notification_outbox` table (MySQL, same shard as producer's DB)

```sql
CREATE TABLE notification_outbox (
    outbox_id        BIGINT       NOT NULL AUTO_INCREMENT,
    notification_id  CHAR(36)     NOT NULL,
    payload          JSON         NOT NULL,
    published        BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at       DATETIME(3)  NOT NULL,
    PRIMARY KEY (outbox_id),
    INDEX idx_unpublished (published, created_at)
);
```

### Database Choices and Justification

| Data | Database | Reason |
|---|---|---|
| `notifications` | MySQL (sharded) | ACID transactions needed for Outbox pattern; schema is fixed |
| `notification_delivery` | Cassandra | High write throughput (1B rows/day), time-series access, no complex queries |
| `user_preferences` | MySQL + Redis | Preferences rarely change; Redis handles 36K reads/s at peak |
| `device_tokens` | MySQL + Redis | UNIQUE constraint on token value; lookups by user_id |
| Frequency caps | Redis | INCR + EXPIRE — atomic counter with TTL is Redis's sweet spot |
| Scheduled jobs | MySQL + Temporal | ACID durability for scheduled state; Temporal handles retry logic |

### Important Indexes

- `user_preferences(user_id, channel, category)` — the preference lookup hot path; composite primary key covers this
- `device_tokens(user_id, platform, is_active)` — fan-out to all active tokens per user per platform
- `notification_outbox(published, created_at)` — CDC/polling sweeper needs unpublished rows quickly
- `notifications(user_id, created_at)` — user notification history queries

## Step 6 — Deep Dive: Delivery Guarantees and the Outbox Pattern

This is where most candidates lose points. "Use Kafka" is not an answer — the problem is what happens in the gap between receiving a request and successfully publishing to Kafka.

### Layer 1: The Dual-Write Problem

Without careful design, every notification service has this race condition:

```
Notification Service:
  1. Write notification to DB        ← succeeds
  2. Publish event to Kafka          ← CRASHES HERE

Result: notification record in DB, but never delivered.
Or:
  1. Publish event to Kafka          ← succeeds
  2. Write to DB                     ← CRASHES HERE

Result: delivered but no record; can't audit, can't deduplicate.
```

Neither order is safe. The fix is the **Transactional Outbox Pattern**.

### Layer 2: Transactional Outbox + CDC Pipeline

```
┌──────────────────────────────────────────────────────────────────┐
│              NOTIFICATION SERVICE (single transaction)           │
│                                                                  │
│  BEGIN TRANSACTION;                                              │
│    INSERT INTO notifications   (notification_id, user_id, ...); │
│    INSERT INTO notification_outbox (notification_id, payload,   │
│                                     published=FALSE);            │
│  COMMIT;                                                         │
│                                                                  │
│  (Kafka publish attempted after commit — best effort)            │
└────────────────────────────────┬─────────────────────────────────┘
                                 │ If Kafka publish succeeds
                                 │ UPDATE outbox SET published=TRUE
                                 │
                 ┌───────────────▼────────────────┐
                 │      DEBEZIUM CDC CONNECTOR     │
                 │  Tails MySQL binlog              │
                 │  Detects outbox rows with        │
                 │  published=FALSE                 │
                 │  Publishes to Kafka              │
                 │  (guaranteed at-least-once)      │
                 └───────────────┬────────────────┘
                                 │
                                 ▼
                 ┌───────────────────────────────┐
                 │  Kafka: notifications.raw      │
                 │  (replication factor=3,        │
                 │   acks=all, min.insync.rep=2)  │
                 └───────────────────────────────┘
```

**Why this guarantees durability**: The COMMIT to MySQL is the durability point. Debezium reads MySQL binlogs — if the service crashes before publishing to Kafka, Debezium still sees the uncommitted outbox row and publishes it on restart. The worst case is at-least-once delivery to Kafka, never zero.

**Debezium lag**: Under normal operation, CDC lag is 50–200 ms. During high load, up to 2 seconds. This is acceptable for notifications. If the Kafka publish path is healthy (99.9% of the time), it publishes immediately after commit with ~5 ms lag; CDC is the safety net, not the fast path.

### Layer 3: End-to-End Deduplication

At-least-once Kafka delivery means duplicate messages can reach workers. A duplicate notification reaching Twilio means the user gets two SMS messages. The deduplication architecture operates at three checkpoints:

```
Checkpoint 1: API Ingestion
  Redis SET NX notification:{idempotency_key} EX 86400
  → Rejects duplicate API calls within 24 hours

Checkpoint 2: Preference Engine (Kafka consumer)
  Redis GET notification:{notification_id}:channel:{channel}:sent
  → Skip if already dispatched to this channel
  → SET with EX 86400 when dispatching

Checkpoint 3: Channel Worker (before calling provider API)
  Query Cassandra: SELECT status FROM notification_delivery
                   WHERE notification_id=? AND channel=?
  → Skip if status is already 'sent' or 'delivered'
  → Write status='sending' before calling provider (compare-and-swap)
```

**Performance cost of deduplication**: Each checkpoint adds ~1 ms (Redis) or ~2 ms (Cassandra). Total overhead per notification: ~4 ms. Acceptable given p99 target of 5 seconds.

**Idempotency key design**: Callers MUST supply an idempotency key. The Notification Service generates a fallback key as `SHA256(producer_id + user_id + template_id + content_hash)` for callers that do not supply one — this covers at-least 95% of natural duplicates from retries, but not intentional resends.

### Real Numbers From Production

- FCM processes millions of requests per second globally. Their API enforces a per-sender rate limit; batch calls are recommended (up to 500 tokens per multicast request).
- FCM recommends a minimum 10-second wait before first retry, with exponential backoff: 10s → 20s → 40s → 80s → 160s (max), with ±20% jitter.
- APNs connections are HTTP/2 persistent; each connection supports up to 1,500 concurrent streams. One worker should maintain a pool of persistent APNs connections, not open a new one per notification.
- Twilio's Messaging API returns a `MessageSid` immediately (async delivery); status comes via webhook to a registered callback URL. SMS delivery confirmation latency is 1–60 seconds depending on carrier.
- Tokens inactive for 270+ days are considered expired by FCM and will return `NotRegistered`. Workers must delete expired tokens from the device token store on this error.

## Step 7 — Deep Dive: Fan-Out and Frequency Capping

### Layer 1: Fan-Out Shapes

The Preference Engine must handle two distinct fan-out shapes, and conflating them is a design mistake.

```
Shape A: 1-to-1 Notification
  One event → one user → one or more channels
  Examples: "Your order shipped", "Someone liked your post"
  Volume: 99% of notifications
  Strategy: Direct dispatch — event contains user_id

Shape B: Broadcast Notification
  One event → millions of users
  Examples: "System maintenance at midnight", "New feature launched"
  Volume: rare but high-impact
  Strategy: Fan-out via user segment iteration
```

For **Shape A**, the Preference Engine reads one event, looks up preferences for one user, dispatches to channel topics. Simple.

For **Shape B**, naive processing would serialize over millions of users single-threaded. The correct approach:

```
┌──────────────────────────────────────────────────────┐
│              BROADCAST FAN-OUT PIPELINE               │
│                                                       │
│  1. Broadcast event written to broadcasts table       │
│     with segment_id = "all_users"                    │
│                                                       │
│  2. Broadcast Fan-out Service queries user segments   │
│     in pages of 10,000 users                         │
│                                                       │
│  3. For each page: publishes 10,000 individual        │
│     notification events to notifications.raw Kafka   │
│     (effectively converting broadcast → 200M         │
│      individual 1-to-1 events)                       │
│                                                       │
│  4. Standard Preference Engine + Workers process     │
│     normally — no special broadcast path needed      │
│     downstream                                        │
│                                                       │
│  5. Progress tracked in broadcasts table:             │
│     users_dispatched, users_total, status            │
└──────────────────────────────────────────────────────┘
```

Fan-out rate for a broadcast to 200M users at 10K users/page = 20,000 Kafka publish calls. At 10K publishes/second, a full broadcast takes 2,000 seconds (~33 minutes). This is acceptable for non-urgent broadcasts. For urgent broadcasts, increase fan-out concurrency to 100K publishes/second → full fan-out in 2,000 seconds still (the bottleneck shifts to Kafka ingestion capacity, not the fan-out service).

**Celebrity Problem in Notifications**: Not relevant here (unlike news feeds). Push notifications are delivered TO users, not pulled FROM senders. There is no concept of "a user with 100M followers sends a post and creates 100M push notifications" in standard notification design — that's a news feed problem. However, a similar problem exists with broadcast notifications from large platform events.

### Layer 2: Frequency Capping Implementation

Without rate limiting, a bug in Order Service can send 1,000 "order updated" events per second for one user, flooding their phone. Frequency caps are user-level safety valves.

```
Redis key schema:
  notif:freq:{user_id}:{channel}:{category}:{hour_bucket}

Algorithm (Preference Engine, per notification):

  bucket = floor(unix_timestamp / 3600)
  key = "notif:freq:{user_id}:push:social:{bucket}"

  count = INCR key
  if count == 1:
    EXPIRE key 7200   // 2 hours TTL (covers bucket rollover)

  if count > user_frequency_cap:   // e.g., 5/hour for social push
    DROP notification
    LOG to metrics: "frequency_cap_exceeded"
    return

  // Proceed to dispatch
```

**Why Redis INCR**: Atomic, O(1), survives Preference Engine restarts. The counter is lost only if Redis fails, which is acceptable (frequency cap is a guardrail, not a guarantee).

**Three-tier frequency cap hierarchy**:

```
Tier 1 (Global): 20 notifications/hour, any channel — hard limit
Tier 2 (Channel): 5 push/hour, 3 email/hour, 2 SMS/hour
Tier 3 (Category): 3 social push/hour, 1 marketing email/day

Evaluation order: Tier 1 → Tier 2 → Tier 3. Drop on first exceeded.
Critical/transactional notifications bypass all tiers.
```

### Layer 3: Do-Not-Disturb (DND) Windows

DND is checked after frequency cap validation:

```python
def is_in_dnd(user_id: str, channel: str) -> bool:
    prefs = redis.hgetall(f"prefs:{user_id}:{channel}")
    dnd_start = int(prefs.get('dnd_start_hour', -1))
    dnd_end   = int(prefs.get('dnd_end_hour',   -1))
    if dnd_start == -1:
        return False

    user_tz   = prefs.get('timezone', 'UTC')
    local_hour = datetime.now(pytz.timezone(user_tz)).hour

    if dnd_start < dnd_end:                      # e.g., 22:00 – 08:00
        return dnd_start <= local_hour < dnd_end
    else:                                        # wraps midnight
        return local_hour >= dnd_start or local_hour < dnd_end
```

**DND behavior options**:
1. **Drop**: Discard the notification (marketing messages)
2. **Delay to DND end**: Re-schedule for the first minute after DND end (social notifications)
3. **Bypass**: Always send regardless (critical/transactional)

The choice is stored per category in `user_preferences.dnd_behavior`. The Preference Engine evaluates and either drops, re-enqueues with `scheduled_at = DND_end_time`, or bypasses.

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (360K events/s, 10B notifications/day)

**Bottleneck**: Kafka `notifications.raw` topic throughput. A single Kafka topic with 100 partitions handles ~1 GB/s. At 360K/s × 1 KB = 360 MB/s, this is fine — but the Preference Engine consumer group (100 consumer instances) becomes the bottleneck. Each instance processes 3,600 events/s; at 10x load that's 36,000/s per instance, which exceeds a single-threaded consumer.

**Fix**: Increase partition count from 100 to 500. Add 500 Preference Engine instances (one per partition). This is linear horizontal scaling. Kafka supports up to 200K partitions per cluster — 500 is modest. Also separate `notifications.raw.critical` and `notifications.raw.normal` topics to ensure critical messages aren't head-of-line blocked by marketing flood.

**Second bottleneck at 10x**: Cassandra `notification_delivery` write throughput. At 10B writes/day × (2 attempts avg) = 20B rows/day. Cassandra handles this with 10 nodes (2B rows/node/day is well within capacity). Add 10 more nodes, rebalance. Cassandra scales linearly.

### At 100x Current Load (3.6M events/s, 100B notifications/day)

**Bottleneck**: The single MySQL `notifications` table (even sharded). At 100B writes/day, MySQL's IOPS ceiling is hit even with SSD and 64 shards. Each shard would see ~1.5B writes/day = ~17K writes/s — pushing InnoDB's limits.

**Fix**: Move the canonical notification record from MySQL to Cassandra (primary source of truth for the event log, using notification_id as partition key). Retain MySQL only for the Outbox table. Outbox rows are short-lived (deleted after CDC publishes them) so MySQL can handle the churn. This removes the MySQL write bottleneck on the hot path.

**Second bottleneck at 100x**: Preference Engine Redis cache. At 3.6M lookups/s, a single Redis cluster (standard 2-million-ops/s ceiling) saturates. **Fix**: Shard the preference cache by `user_id % N` across Redis clusters, or use a local L1 cache (in-process Caffeine, 1-minute TTL) in each Preference Engine pod. L1 cache with 200M users × 256 bytes = 51 GB — too big for in-process. Instead, L1 cache only the hottest 1% of users (2M users × 256 B = 512 MB per pod — feasible). Preference changes propagate via a separate preference-change Kafka topic that invalidates L1 entries.

**Third bottleneck at 100x**: FCM/APNs throughput limits. FCM throttles per sender project. At 100x load (2.16M push/s), even with multiple FCM projects (each capped at ~200K/s), this requires ~11 FCM sender accounts. This is a real operational concern — Google grants high-throughput access by application request, not automatically.

### At 1000x Current Load (36M events/s, 1T notifications/day)

**Fundamental changes required**:

1. **Regional decomposition**: At this scale, a global notification system must become multiple regional systems (NA, EU, APAC, etc.) with a global routing layer. Each region handles its own users' notifications. Cross-region is rare (e.g., admin broadcasts).

2. **Abandon the Outbox for fast-path**: At 36M events/s, even Debezium CDC cannot keep up with MySQL binlog parsing. The fast path becomes: write to Kafka directly with idempotent producer (Kafka exactly-once semantics with `enable.idempotence=true`), AND write to a distributed log (Apache Pulsar or Kafka itself as the system of record) — no MySQL Outbox. Durability comes from Kafka's replication, not a relational Outbox.

3. **Stateful stream processing**: Preference Engine becomes a Flink job with RocksDB state backend (local state, not Redis). Flink reads preferences into local state, processes streams at 36M events/s — Redis cannot handle 36M lookups/s at any price. Flink's checkpointing provides fault tolerance.

4. **Hierarchical fan-out for broadcasts**: With 1 billion+ users, even fan-out at 100K/s takes 2.7 hours. Solution: hierarchical fan-out where region coordinators further fan out to sub-region workers, each responsible for a user_id shard. Parallelizes to complete in minutes.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Durability mechanism | Transactional Outbox + Debezium CDC | Direct Kafka publish with producer retries | Outbox provides ACID durability even on service crash; direct publish risks dual-write failure |
| Message broker | Apache Kafka | RabbitMQ, AWS SQS | Kafka's partition model enables horizontal scaling and replay; SQS lacks replay; RabbitMQ lacks at-scale throughput |
| Delivery guarantee | At-least-once + deduplication = effectively-once | Exactly-once Kafka transactions end-to-end | True exactly-once adds 10-20% throughput penalty; dedup at the worker level achieves the same user-visible result |
| User preference storage | MySQL + Redis cache | Single Redis / DynamoDB | MySQL provides ACID guarantees for preference updates (opt-out must not be lost); Redis provides read performance |
| Notification history | Cassandra | MySQL, DynamoDB, ClickHouse | Cassandra optimized for high-write, time-series append access; 1B rows/day at scale |
| Fan-out architecture | Write-fan-out (1-to-1) + broadcast iterator | Read-fan-out (pull model) | Push notifications require server-initiated delivery; read-fan-out only works for inbox-style pull |
| Channel separation | Separate Kafka topics per channel | Single topic with channel field | Separate topics allow independent scaling and consumer isolation; push workers don't block behind slow email workers |
| Frequency cap implementation | Redis INCR with TTL | Database counter | Redis INCR is atomic, O(1), and handles 36K ops/s trivially; DB counters create hot-row contention |
| Scheduling engine | Temporal/Cadence | Cron jobs, DynamoDB TTL triggers | Temporal provides durable workflows with retry logic; cron has no per-user timezone support at scale |
| Status tracking | Cassandra with provider webhooks | Polling provider APIs | Webhooks provide near-real-time status; polling creates N×provider API calls; Cassandra handles write burst |

## Step 10 — How Real Companies Solved This

### Uber: Consumer Communication Gateway (CCG)

Uber Engineering published details on their CCG, which handles notifications from Marketing, Product, and City Operations teams.

**Architecture decisions**:
- A **Persistor** service accepts push notifications and writes them to sharded MySQL (the "Push Inbox"). This is their Outbox equivalent.
- A **Schedule Generator** fetches buffered pushes and uses Uber's ML platform (Michelangelo) to determine optimal send times per user — not just "send now" but "send at the time this user is most likely to engage."
- A **Scheduler** uses Cadence (Uber's open-source distributed workflow engine, now Temporal) with push notification assignments buffered into Kafka topics per hour.
- **Delivery validation** runs before every send: is the token still valid? Is the user still active? This pre-validation reduces FCM/APNs error rates significantly.

**What they got wrong first**: Early versions had Marketing, Product, and City Operations each sending notifications directly to FCM — no centralization, no deduplication, no frequency capping. A driver could receive 8 notifications in 10 seconds from three different teams. The CCG was built specifically to fix this: centralized gateway enforces policies across all senders.

**Key insight**: Separate the "when to send" decision (ML-optimized timing) from the "how to send" mechanism. Uber's ML layer can suppress a notification if it predicts the user won't engage — this reduces cost and improves user experience simultaneously.

### LinkedIn: Unified Notification Platform

LinkedIn's engineering blog describes a unified platform that handles email, push, in-app, and web notifications.

**Architecture decisions**:
- **Hermes** is LinkedIn's internal messaging platform built on top of Kafka. All notification events are published to Hermes, which provides durable, ordered delivery.
- **Preference Center**: LinkedIn treats notification preferences as a first-class product feature. The preference model is hierarchical: global opt-out > category opt-out > channel opt-out > individual notification type opt-out. This hierarchy is stored in Espresso (LinkedIn's distributed document store) and cached.
- **Tracking infrastructure**: LinkedIn uses the Kafka-based tracking pipeline to record opens, clicks, and unsubscribes. Every email includes a tracking pixel and click-redirect URLs. This data feeds back into frequency cap decisions (if a user has not opened any email in 30 days, frequency cap tightens automatically).
- **Batching and digest**: LinkedIn groups similar notifications into digest emails ("You have 15 new connection requests") rather than sending 15 individual emails. The batching window is configurable per notification type.

**What they got wrong first**: Initially, each LinkedIn product team (Connections, Messaging, Jobs, etc.) had its own notification pipeline. This created inconsistent user experience and made it impossible to enforce global frequency caps. The unified platform was a multi-year migration that required each team to onboard onto the central system.

**Key insight**: The notification **preference center** is a product feature as important as the notifications themselves. Users who can control their notifications don't unsubscribe — LinkedIn found that users with fine-grained control have significantly lower unsubscribe rates than those with only a global on/off toggle.

### Airbnb: Smart Notifications

Airbnb's notification system handles a complex mix: transactional (booking confirmations, payment receipts), operational (check-in reminders, host instructions), and marketing.

**Architecture decisions**:
- Airbnb uses **AWS SES** for email with custom tracking, **Twilio** for SMS, and **FCM/APNs** for push.
- Their **template engine** supports internationalization across 60+ languages with locale-specific formatting rules.
- **Delivery time optimization**: For non-urgent notifications, Airbnb's system learns each user's typical app-open times (from analytics) and schedules notifications to arrive just before that window — significantly improving open rates.
- **Fallback chains**: If push notification delivery fails (device offline, token expired), the system falls back to email; if email bounces, falls back to SMS for critical messages (booking confirmation). This fallback chain is configured per notification category.

**What they got wrong first**: Early Airbnb used generic send-immediately logic for all notifications. Check-in reminder emails were sent at booking time — sometimes 90 days before check-in — rather than 24 hours before. Users complained that notifications weren't timely. The scheduler service that considers "notification relevance window" was built to fix this.

**Key insight**: **Delivery timing is part of the product**. A notification sent at the wrong time is worse than no notification. Airbnb invests heavily in the scheduling layer — it's not just "send at 9 AM" but "send at the right moment for this specific notification type and this specific user."

## Interview Perspective

### What the Interviewer Is Evaluating

**Specific to this problem:**
1. **Do you understand the Outbox pattern?** Most candidates say "write to DB and publish to Kafka" without handling the crash-between-the-two case.
2. **Can you design the preference model?** The three-tier hierarchy (global → category → channel) with DND windows and frequency caps shows real-world thinking.
3. **Do you separate channel workers?** Single-queue-multiple-channels is a common mistake. Email workers should not block push workers.
4. **Can you articulate delivery guarantees?** At-least-once vs. exactly-once, and how deduplication bridges the gap.
5. **Do you handle token management?** Expired FCM tokens that return `NotRegistered` must be deleted; candidates who don't mention this reveal shallow push notification knowledge.

### Junior (L3-L4) Answer

**What they say**: "I'll have a service that accepts notifications and sends them to FCM/APNs, Twilio, and SendGrid. I'll use a message queue to decouple the sender from the workers. I'll store user preferences in a database and check them before sending."

**What depth they reach**: High-level component identification. They'll draw a box diagram with API → Queue → Workers → Providers.

**What they miss**:
- The Outbox pattern and durability guarantees
- Frequency capping and DND implementation
- Token expiry management
- Deduplication across retries
- The broadcast fan-out problem
- Status tracking with webhooks from providers
- Idempotency key design

**How to get to L5**: Volunteer to go deeper on one component rather than listing components. Ask "should I deep-dive on delivery guarantees?" and then actually go three layers deep.

### Senior (L5) Answer

**What they add**:
- Outbox pattern or equivalent durability mechanism (may describe it without naming it)
- Separate Kafka topics per channel with independent consumer groups
- Redis frequency capping with INCR + TTL
- Idempotency key at the API layer
- APNs connection pooling (persistent HTTP/2 connections)
- FCM token cleanup on `NotRegistered` response
- Status tracking design (Cassandra for high write throughput)
- DND window implementation

**Specific depth on this problem**: A strong L5 will proactively say "the hardest part is guaranteeing exactly-once delivery across a crash boundary" and walk through Outbox + CDC before being asked. They'll also distinguish broadcast vs. 1-to-1 fan-out without prompting.

### Staff (L6+) Answer

**What they drive to unprompted**:

1. **Cost reasoning**: "SMS at $0.0075/message × 1B messages = $7.5M/month. We need an aggressive frequency cap on SMS, and we should evaluate WhatsApp Business API as a cheaper alternative in markets where it's dominant."

2. **Operational concerns**: "FCM and APNs are dependencies we don't control. We need circuit breakers per provider, fallback to a secondary FCM sender account, and alerting on delivery rate drops below 95% so on-call gets paged before users notice."

3. **Compliance**: "For GDPR, opt-out records must be retained even if the user deletes their account. The preference table needs soft deletes and an audit log. For TCPA (US SMS), we need consent timestamps stored immutably."

4. **The celebrity problem for broadcasts**: "A broadcast to 200M users can't be completed in one pass — we need progress tracking, resumability (if the fan-out service crashes at 50M, it must restart from 50M, not 0), and rate limiting the fan-out itself so Kafka isn't overwhelmed."

5. **Multi-region**: "User data locality laws (GDPR) may require that EU users' notification preferences and history are stored only in EU regions. This means the preference lookup in the Preference Engine must route to the right regional store, which complicates the global frequency cap."

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **"I'll write to the DB then publish to Kafka"** — no crash handling, no Outbox, violates durability requirements. This is the most common mistake and shows lack of distributed systems experience.

2. **Single queue for all channels** — push, email, and SMS workers in one consumer group. A slow SMS provider (Twilio throttling) creates backpressure that delays push notifications by minutes. Channels must have separate topics.

3. **No frequency capping** — candidates design send-all-immediately without asking "what if a bug causes 10,000 events for one user?" Frequency caps are the safety valve that prevents user harassment and cost explosions.

4. **Ignoring token lifecycle** — treating FCM tokens as permanent. In production, 20-30% of tokens are stale within 6 months. Workers must handle `NotRegistered` errors by deleting tokens and `Unregistered` by invalidating them — otherwise push delivery rate degrades silently over months.

5. **Not distinguishing broadcast from 1-to-1** — designing a system that handles "send to user_id=12345" but breaks when asked "now send to all 200M users." The broadcast fan-out requires a fundamentally different pipeline (page-through user segments) that cannot be retrofitted onto the 1-to-1 path.

### Key Numbers to Have Memorized for This Problem

| Metric | Value | Context |
|---|---|---|
| FCM batch size limit | 500 tokens per multicast call | Batching is essential for efficiency |
| FCM recommended min retry wait | 10 seconds | Exponential backoff baseline |
| APNs concurrent HTTP/2 streams | 1,500 per connection | Connection pooling design |
| FCM token expiry threshold | 270 days inactive | When to mark token as expired |
| Kafka max partitions per cluster | ~200,000 (practical ceiling) | Scaling Kafka for 1000x load |
| SMS typical cost (Twilio US) | $0.0075 per message | Cost reasoning for frequency caps |
| Transactional Outbox CDC lag | 50–200 ms typical, 2s under load | Durability latency trade-off |
| Kafka exactly-once throughput penalty | 10–20% vs. at-least-once | Why we dedup at the worker instead |

## Summary

A notification system looks simple from the outside — accept events, call provider APIs — but hides profound distributed systems challenges at scale. The three areas that separate strong candidates:

1. **Durability**: Transactional Outbox + CDC is the correct answer to "how do you guarantee no message is lost across a crash boundary." Direct DB-then-Kafka or Kafka-then-DB both have failure windows.

2. **Routing correctness**: The Preference Engine must enforce frequency caps, DND windows, and opt-outs atomically (via Redis) without becoming a bottleneck. Understanding the three-tier cap hierarchy shows product empathy.

3. **Scale inflection points**: The design breaks in predictable, nameable ways — MySQL Outbox at 100x, Redis preference cache at 100x, FCM sender limits at 100x — and each has a specific, correct fix. Vague answers ("add more servers") reveal shallow scaling intuition.
