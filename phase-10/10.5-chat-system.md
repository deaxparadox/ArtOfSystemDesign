## Problem Statement

Design a real-time messaging system similar to WhatsApp that allows users to exchange 1-on-1 and group messages with guaranteed delivery, delivery receipt tracking (sent / delivered / read), and online presence indication.

WhatsApp serves 3.3 billion monthly active users, processes over 150 billion messages per day, handles 7 billion voice messages, and facilitates 15 billion minutes of calls daily as of 2026. At its pre-Meta acquisition peak the entire backend ran on approximately 50 engineers — a testament to the efficiency of the Erlang/BEAM architecture.

## Step 1 — Clarify Requirements

### Functional Requirements

1. **1-on-1 messaging** — Users can send and receive text messages in real time.
2. **Group messaging** — Groups of up to 1,024 members (WhatsApp's limit) can exchange messages.
3. **Delivery receipts** — Three-state acknowledgment: sent to server (single tick), delivered to recipient device (double tick), read by recipient (blue double tick).
4. **Media sharing** — Images, video, documents, and voice notes can be attached to messages.
5. **Online presence / last seen** — Users can see whether contacts are online or when they were last active.
6. **Message history** — Conversation history persists and is accessible when a user reinstalls or switches devices.

### Non-Functional Requirements

| Property | Target |
|---|---|
| Availability | 99.99% (< 52 min downtime/year) |
| Message delivery latency (p99) | < 200 ms sender-to-recipient on the same continent |
| Message ordering | Causal within a conversation; no out-of-order delivery visible to user |
| Durability | Messages survive server failure; 0 acknowledged messages lost |
| Consistency model | Eventual — a delivered message will eventually appear on all recipient devices |
| Presence latency | Online/offline propagated to contacts within 5 seconds |
| Media upload latency | p95 < 2 s for a 5 MB image |

### Out of Scope

- End-to-end encrypted message content (assume transport-level TLS; E2E key exchange is a separate crypto layer)
- Voice and video calling (uses WebRTC, a separate media plane)
- Payment features (WhatsApp Pay)
- Message translation
- Admin tooling and content moderation pipelines
- iOS / Android push notification deep-dive (APNs / FCM integration — mentioned but not fully designed)

### Clarifying Questions to Ask the Interviewer

1. **What is the maximum group size?**
   - *Reason:* Fan-out strategy completely changes at 200 vs 1,024 vs 100,000 members. WhatsApp caps at 1,024; Telegram allows 200,000. This single number drives multiple architectural decisions.

2. **Do we need message search?**
   - *Reason:* Full-text search requires an inverted index (Elasticsearch), a background indexing pipeline, and at least double the storage cost. Explicitly deferring it keeps focus on core delivery.

3. **Should messages be stored server-side permanently or deleted after delivery?**
   - *Reason:* WhatsApp originally stored messages only until delivery (no server-side history). Signal still works this way. Permanent storage (like iMessage backup) changes storage sizing by orders of magnitude.

4. **What is the expected read:write ratio?**
   - *Reason:* A chat system writes a message once and reads it potentially many times (multiple devices, message history). Affects caching strategy and replication factor.

5. **Do we need multi-device support?**
   - *Reason:* If one account can be logged into four devices simultaneously (WhatsApp now supports this), each device needs its own delivery confirmation, the ack logic becomes a multi-device fan-out problem, and the "delivered" tick only turns blue when all linked devices have confirmed.

6. **What geography are we targeting first?**
   - *Reason:* A single-region design can meet < 100 ms p99 domestically but will fail internationally. Knowing if we need multi-region in v1 versus v2 prevents over-engineering in the interview.

7. **What happens to messages sent to an offline user?**
   - *Reason:* Determines offline queue depth, TTL policy, and whether we rely on push notifications (APNs/FCM) as the fallback transport.

## Step 2 — Capacity Estimation

### Assumptions

```
DAU                         = 2 billion
MAU                         = 3.3 billion
Messages per active user/day = 40  (mix of sent + received)
Average message size (text)  = 1 KB  (UTF-8 text + metadata + headers)
Average media message size   = 500 KB  (after compression)
% media messages             = 10%
Group messages as % of total = 60%
Average group size           = 20 members
```

### Write QPS (messages sent)

```
Total messages sent/day = DAU × (40 messages / 2) = 2B × 20 = 40 billion messages/day
                        = 40 × 10^9 / 86,400 s
Write QPS               ≈ 463,000 messages/s  ≈ 500K writes/s
Peak (3× average)       ≈ 1.5 million writes/s
```

### Fan-out QPS (messages delivered to recipients)

```
1-on-1 messages (40%)   = 1 recipient per message
Group messages (60%)    = average 20 recipients

Effective fan-out QPS   = (40% × 1 + 60% × 20) × 500K writes/s
                        = (0.4 + 12) × 500K
                        = 12.4 × 500K
                        ≈ 6.2 million delivery events/s
```

### Read QPS (message history fetches)

```
Assumption: 5% of DAU fetch history per day, each fetching ~50 messages
History reads/day = 2B × 0.05 × 50 = 5 billion reads/day
Read QPS          = 5 × 10^9 / 86,400 ≈ 58,000 reads/s ≈ 60K reads/s
```

### Storage

```
Text messages per day   = 40B × 90% = 36B text messages × 1 KB = 36 TB/day
Media per day           = 40B × 10% = 4B media messages × 500 KB = 2,000 TB = 2 PB/day

Total raw storage/day   ≈ 2 PB/day
Per year                ≈ 730 PB  ≈ 0.73 EB
5-year projection       ≈ 3.65 EB

With 3× replication     ≈ 6 TB/day for text-only metadata in DB
                        (Media stored in object store, not in the message DB)

Message metadata in DB  = 36B messages × 200 bytes (metadata row) = 7.2 TB/day
With 3× replication     ≈ 21.6 TB/day in the message store
```

### Bandwidth

```
Ingress (uploads from senders):
  Text:  36B × 1 KB / 86,400 s  ≈ 417 GB/s
  Media: 4B × 500 KB / 86,400 s ≈ 23 TB/s (CDN-offloaded, chunked uploads)

Egress (delivery to recipients):
  Text fan-out: ≈ 417 GB/s × fan-out ratio ≈ 5 TB/s
  Media fan-out: stored separately; recipients download from CDN
```

### WebSocket Connections

```
DAU online simultaneously (peak 30% of DAU):
  = 2B × 0.30 = 600 million concurrent WebSocket connections

Connections per chat server:
  A well-tuned Go/Erlang process can hold ~100,000 WS connections
  Servers needed = 600M / 100K = 6,000 chat servers
  With 2× headroom = 12,000 chat servers
```

### Cache Sizing

```
Recent messages cache (last 30 messages per active conversation):
  Active conversations = 500M (rough estimate)
  30 messages × 1 KB  = 30 KB per conversation
  Total cache needed  = 500M × 30 KB = 15 TB

Use Redis cluster with 256 GB nodes → 60 nodes for message cache
Presence cache (online status, last-seen):
  2B users × 100 bytes = 200 GB → fits in ~2 Redis nodes (with replicas: 6 nodes)
```

### Component Walk-through

**Global Load Balancer (Layer-4)**
Uses IP-based consistent hashing to route a given user's WebSocket connection to the same chat server cluster. This is NOT for sticky sessions — WebSocket stickiness is maintained at the application layer. The L4 LB avoids breaking existing TCP connections during rolling deployments.

**Chat Server Pool**
Each chat server is a stateful process holding `N` WebSocket connections (target: 50K–100K per server). The server is written in Go or Erlang/Elixir — both handle hundreds of thousands of goroutines/processes cheaply. The server is responsible for:
- Accepting and maintaining WebSocket connections
- Authenticating the JWT on connection upgrade
- Receiving messages from clients and forwarding to Kafka
- Receiving delivery events from the fan-out workers and pushing them to the target connection

**Kafka Message Broker**
All message events (sends, acks, presence changes) are written to Kafka before any delivery attempt. This decouples ingestion speed from delivery speed and gives us a durable replay log. Topic partitioning by `conversation_id` guarantees ordering per conversation.

**Message Persistence Service**
Consumes from Kafka, writes the canonical message record to Cassandra/ScyllaDB. This is the source of truth. Writes are idempotent (uses `message_id` as the primary key).

**Fan-out Worker Pool**
Consumes from Kafka, resolves the set of recipient devices, and routes each message to either:
- The target chat server (if the recipient is online) via Redis pub/sub or gRPC
- The offline queue (if the recipient is offline) + triggers APNs/FCM

**Presence Service**
Maintains a real-time map of `user_id → {online, chat_server_id, last_seen_ts}` in Redis. Updated by heartbeat events from chat servers. Propagates status changes to the relevant contacts' connections via pub/sub.

## Step 4 — Data Model

### Messages Table (Cassandra / ScyllaDB)

```sql
-- Partitioned by conversation for co-location of a conversation's messages
-- Clustered by message time for efficient range scans (history pagination)

CREATE TABLE messages (
    conversation_id  UUID,          -- (user_a_id, user_b_id) sorted pair for 1:1;
                                    -- group_id for groups
    message_id       TIMEUUID,      -- globally unique; embeds wall-clock timestamp
    sender_id        UUID,
    message_type     TINYINT,       -- 1=text, 2=image, 3=video, 4=audio, 5=doc
    content          TEXT,          -- encrypted payload (if E2E) or plaintext
    media_url        TEXT,          -- nullable; CDN URL for media
    client_seq       BIGINT,        -- sender-assigned monotonic sequence per sender
    server_seq       BIGINT,        -- server-assigned sequence per conversation
    created_at       TIMESTAMP,
    ttl              INT,           -- optional: expiring messages (disappearing msgs)
    PRIMARY KEY (conversation_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC)
  AND default_time_to_live = 0;    -- 0 = keep forever; set TTL for ephemeral msgs

-- Compact metadata table for conversation list / last message preview
CREATE TABLE conversation_metadata (
    user_id          UUID,
    conversation_id  UUID,
    last_message_id  TIMEUUID,
    last_message_preview TEXT,
    unread_count     INT,
    updated_at       TIMESTAMP,
    PRIMARY KEY (user_id, updated_at, conversation_id)
) WITH CLUSTERING ORDER BY (updated_at DESC);
```

**Why Cassandra/ScyllaDB?**
- Write-heavy workload (150B msgs/day) needs a write-optimized LSM-tree storage engine
- Messages are append-only — no updates — which is a perfect fit for Cassandra's immutable SSTables
- Range scans by `conversation_id` for history pagination are the primary access pattern
- ScyllaDB (C++ rewrite of Cassandra) eliminates JVM GC pauses that killed Cassandra at Discord's scale

### Delivery Receipts Table

```sql
CREATE TABLE delivery_receipts (
    message_id      TIMEUUID,
    recipient_id    UUID,
    device_id       UUID,           -- for multi-device tracking
    status          TINYINT,        -- 1=server_ack, 2=delivered, 3=read
    status_at       TIMESTAMP,
    PRIMARY KEY (message_id, recipient_id, device_id)
);
```

**Index:** Secondary index on `(recipient_id, status)` enables the "how many unread messages" query. In practice this is served from Redis, not Cassandra.

```sql
CREATE TABLE users (
```

## Step 6 — Deep Dive: Message Ordering and Delivery Receipts

This is the hardest component in a chat system. Candidates who only say "use a message queue" are at L3 level. The real complexity is in how you get exactly-once delivery, causal ordering, and accurate three-state receipt tracking across distributed servers and flaky mobile networks.

### Layer 1 — The Problem

Consider this failure scenario:

```
Sender (Alice)                Server                  Recipient (Bob)
      │                          │                          │
      │── send "Hello" ─────────>│                          │
      │                          │── store in Cassandra ───>│ (async)
      │                          │                          │
      │                          │  [CRASH before ACK] ×    │
      │                          │                          │
      │  [No ACK received]        │                          │
      │── retransmit "Hello" ───>│ (new server)             │
      │                          │── store again? ─────────>│
      │<─ ACK (message_id=X) ────│                          │
                                 │── deliver X to Bob ─────>│
```

Without deduplication, Bob sees "Hello" twice. Without an explicit ACK from the server, Alice doesn't know if the message was received.

### Layer 2 — Message ID Strategy and Deduplication

**Two IDs per message:**

```
client_seq:  monotonic counter per (sender, conversation)
             - Assigned by client before sending
             - Rolls over at UINT64_MAX (effectively never)
             - Used for deduplication at the server

message_id:  TIMEUUID (version 1 UUID) generated by server on first receipt
             - Globally unique
             - Embeds a 100-nanosecond timestamp from the server's clock
             - Becomes the stable identifier for the message forever
```

**Deduplication flow:**

```
1. Alice sends: {client_seq: 42, content: "Hello", conversation_id: C}

2. Chat Server receives frame, checks Redis:
   GET dedup:{alice_id}:{conversation_id}:{client_seq=42}
   
   → Cache MISS: proceed to Kafka publish
   → SET dedup:{alice_id}:{conversation_id}:{client_seq=42} → message_id=X
      EX 86400  (24h TTL — Alice's client won't retry after 24h)

3. Chat Server publishes to Kafka topic `msg.1on1`, partition = hash(conversation_id)
   → Returns ACK {message_id: X, server_seq: 1001} to Alice immediately
   → Alice client marks message as "sent" (single tick)

4. If Alice retransmits (no ACK received due to network):
   → Chat Server checks Redis dedup key → HIT → returns same message_id=X
   → Does NOT republish to Kafka
   → Alice sees same single-tick (already sent)
```

**Why Kafka partition = hash(conversation_id)?**
All messages within a conversation go to the same Kafka partition, which is consumed by a single consumer. This guarantees that messages in conversation C are processed in the order they were produced, preserving causal ordering. If you partition by `sender_id` instead, Alice's message 1 and Bob's message 1 in the same conversation might be processed in undefined order.

### Layer 2b — Server Sequence Numbers

Each conversation has a monotonically increasing `server_seq`. The persistence service (Cassandra writer) maintains this counter in Redis:

```
INCR seq:{conversation_id}    → returns 1001
```

This counter is used to detect gaps when a client reconnects. If Bob was offline and his last delivered `server_seq` was 995, when he reconnects:
```
Alice: "What's your last_seq for conversation C?"
Bob:   "995"
Server: SELECT * FROM messages WHERE conversation_id=C AND server_seq > 995 LIMIT 50;
```

This catch-up query is served from Cassandra (or the Redis recent-message cache if the gap is small).

### Layer 3 — Three-State Delivery Receipt Tracking

```
State Machine per message per recipient device:

  [NONE] ──send ACK──> [SENT] ──delivered ack──> [DELIVERED] ──read event──> [READ]
                        (✓)                         (✓✓)                       (✓✓ blue)
```

**Sent (single grey tick):**
- Server has acknowledged the `send` call and assigned `message_id`
- Message is in Kafka and being processed
- Server writes to Redis: `SET receipt:{message_id}:{bob_device_id} 1`
- Server sends `{type: "sent_ack", message_id: X}` over Alice's WebSocket

**Delivered (double grey tick):**
- Fan-out worker successfully pushed the message to Bob's WebSocket connection
  OR inserted it into Bob's offline queue
- Bob's device client sends `{type: "delivery_ack", message_id: X}` over Bob's WebSocket
- Chat server processes ack, writes to Cassandra delivery_receipts table
- Fan-out worker routes the `delivery_ack` event to Alice's chat server
- Alice's chat server pushes `{type: "delivery_update", message_id: X, status: "delivered"}` to Alice's WebSocket
- Alice's client upgrades the tick to double grey

**Read (double blue tick):**
- Bob's app is foregrounded and the message is visible on screen
- Bob's client batches read events (debounced 1 second) and sends:
  `{type: "read", conversation_id: C, up_to_server_seq: 1001}`
- Chat server processes, writes read cursor to Cassandra
- Fan-out pushes read update to Alice

**Multi-device complexity:**
If Bob has both a phone and a desktop logged in:
- Message delivered to phone only → double tick (delivered to ≥ 1 device)
- Message NOT changed to delivered until at least one device acks
- Read tick only when the device where Bob actually read it sends the read event
- WhatsApp's rule: "delivered" = delivered to phone (primary device); linked devices secondary

```
Delivery Receipt Flow — sequence diagram:

Alice's App    Chat-Srv-1      Kafka      Fan-out Worker   Chat-Srv-2    Bob's App
     │              │             │              │               │             │
     │─ send msg ──>│             │              │               │             │
     │              │─ publish ──>│              │               │             │
     │<─ sent_ack ──│             │              │               │             │
     │ (single tick)│             │─ consume ───>│               │             │
     │              │             │              │─ lookup Bob ──>             │
     │              │             │              │  on Srv-2    │             │
     │              │             │              │─ push frame ─>│             │
     │              │             │              │               │─ deliver ──>│
     │              │             │              │<── deliv_ack ─│<── ack ────│
     │              │<─ route ack─│<─ publish ───│               │             │
     │<─ deliv_upd ─│             │              │               │             │
     │ (double tick)│             │              │               │             │
     │              │             │              │               │             │
     │              │             │              │<─ read_ack ───│<── read ───│
     │              │<─ route ack─│<─ publish ───│               │             │
     │<─ read_upd ──│             │              │               │             │
     │ (blue tick)  │             │              │               │             │
```

**Key insight:** The receipt events flow back through Kafka on the `delivery.acks` topic, not via direct server-to-server calls. This means every ack is durable (not lost if Chat-Srv-2 crashes mid-routing) and is traceable.

## Step 7 — Deep Dive: WebSocket Connection Management and Presence

### Layer 1 — The Connection Lifecycle Problem

12,000 chat servers each holding 50K connections. When Alice sends a message to Bob, the fan-out worker needs to know:
1. Is Bob online?
2. If online, which of the 12,000 servers holds his connection?
3. How do we route the message to that server with sub-10ms latency?
4. What if Bob's server crashes between steps 2 and 3?

### Layer 2 — Connection Registry in Redis

Every chat server publishes its connections to a central Redis Cluster (not a single node — use Redis Cluster with 16 shards):

```
# On WebSocket connection establishment:
HSET connections:{user_id} {device_id} {chat_server_id}
EXPIRE connections:{user_id} 120   # refreshed by heartbeat

# On WebSocket disconnect:
HDEL connections:{user_id} {device_id}

# Example state:
connections:bob-uuid = {
  "phone-device-id":   "chat-srv-042",
  "desktop-device-id": "chat-srv-107"
}
```

The fan-out worker resolves Bob's chat server in O(1):
```
HGETALL connections:{bob_user_id}
→ {"phone-device-id": "chat-srv-042", "desktop-device-id": "chat-srv-107"}
```

Then routes to each server via **internal pub/sub channel per chat server:**
```
PUBLISH channel:chat-srv-042 {message_event_json}
PUBLISH channel:chat-srv-107 {message_event_json}
```

Each chat server subscribes to its own channel on startup and listens for delivery requests.

### Layer 2b — Heartbeat and Disconnection Detection

Mobile networks are unreliable. A TCP connection can be "half-open" — the server believes it's alive but the client's IP changed (switching from WiFi to 4G). Without explicit detection, the connection registry stays stale.

**Heartbeat protocol:**
```
Client → Server: PING frame every 30 seconds
Server → Client: PONG response

If server does NOT receive PING within 65 seconds:
  1. Server sends PING to client
  2. No PONG within 10 seconds → mark connection as dead
  3. HDEL connections:{user_id} {device_id}
  4. HSET presence:{user_id} status "offline", last_seen_ts NOW()
  5. Publish presence change to presence.events Kafka topic
```

**Graceful disconnect (app backgrounds on iOS/Android):**
```
Client sends CLOSE frame before backgrounding
Server handles CLOSE:
  1. Same cleanup as heartbeat timeout
  2. Faster: no 65s wait
```

**Reconnection with gap detection:**
```
Client reconnects after being offline:
  1. Sends CONNECT with JWT + last_received_server_seq per conversation
  2. Chat server fetches offline queue:
     LRANGE offline_queue:{user_id} 0 -1  (up to 500 events)
  3. For gaps beyond the offline queue, directs client to REST API for history fetch
  4. Client processes messages, sends bulk delivery_ack
  5. Server clears offline queue
```

### Layer 3 — Presence Fan-out at Scale

"Bob came online" must be propagated to all of Bob's contacts who are also currently online. This is a hard problem at scale — Bob could have 500 contacts, 200 of which are online right now.

**Naive approach (too slow):**
```
FOR contact IN bob.get_all_contacts():
    IF contact.is_online():
        push_presence_update(contact, {bob: "online"})
```
For 500 contacts × 6M presence events/day = 3 billion fan-out operations/day just for presence.

**Production approach — Interest-based subscription:**

```
When Alice connects, the chat server:
1. Fetches Alice's contact list (cached in Redis, refreshed daily)
2. For each contact, subscribes Alice's server to presence:{contact_user_id}
   → SUBSCRIBE presence:bob-uuid  (on the presence Redis cluster)

When Bob comes online:
1. Bob's chat server publishes:
   PUBLISH presence:bob-uuid {status: "online", ts: 1718000000}
2. Only chat servers that have at least one subscriber for bob-uuid receive this
3. Those servers push updates to their respective connections

Result: zero-cost for contacts not currently online
        single Redis PUBLISH per status change regardless of contact count
```

**Presence write optimization — batching:**
```
Presence events (heartbeats from 600M connections every 30s):
  = 600M / 30s = 20M heartbeat events/second

Writing 20M events/second to Redis is too expensive.

Solution: Write presence only on CHANGE (online→offline, offline→online)
          Use heartbeat to detect timeout (server-local, no Redis write)
          Result: ~1-2M presence writes/second (churn events only)
```

**Last-seen timestamp privacy:**
WhatsApp's "last seen" privacy settings require filtering at the Presence Service layer:
```
GET /v1/presence?user_ids=bob
  → Presence Service checks: does Alice have permission to see Bob's last_seen?
  → Rule engine: privacy_settings["last_seen"] ∈ {everyone, contacts_only, nobody}
  → Filters response accordingly
```

### Layer 3b — Group Presence (The Scaling Cliff)

When a user opens a group with 1,024 members, the client wants to show who's online. Naively, this is 1,024 Redis lookups — feasible. The problem is that 100,000 users viewing the same 1,024-member group triggers 100M Redis reads.

**Solution: Group presence is lazy-loaded, not pushed.**
```
Client requests: GET /v1/groups/{id}/presence
Server: HMGET presence:{member_1} ... presence:{member_1024}
       → Batched pipeline to Redis → single network round-trip
       → Returns subset of online members only

Server does NOT subscribe to presence changes for all 1,024 members.
Instead, client polls every 60s if group is visible on screen.
```

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load

**Current:** 500K writes/s, 6M delivery events/s, 600M concurrent WebSockets
**10x:** 5M writes/s, 60M delivery events/s, 6B concurrent WebSocket connections

**First bottleneck: Redis connection registry**

At 600M concurrent connections, the connection registry in Redis is under 1M writes/second (connection changes). At 6B connections this becomes 10M writes/second of connection registry updates plus 200M heartbeat checks/second.

**Fix:** Shard the connection registry by `user_id` range across 256 Redis Cluster shards (the maximum). Alternatively, replace the Redis-based registry with a distributed hash table backed by a custom gossip protocol (like Erlang's Mnesia), which is what WhatsApp actually does — each Erlang BEAM cluster node knows which process owns each connection via the process registry, with no external store needed.

**Second bottleneck: Kafka consumer lag on fan-out**

60M delivery events/s requires proportionally more Kafka partitions and consumer workers.

**Fix:** Increase partitions from 100 → 1,000. Add consumer worker pods (horizontal scale). Kafka itself scales horizontally; this is not a fundamental limit.

### At 100x Current Load

**100x:** 50M writes/s, 600M delivery events/s

**Bottleneck: Single-region database write throughput**

At 50M message writes/second, even ScyllaDB (which peaks around 1-2M writes/s per node on commodity hardware) requires 50+ nodes just for write throughput. The coordination overhead of Cassandra's replication (write must land on N=3 nodes, quorum of 2) becomes the ceiling.

**Fix:**
1. **Partition messages into "hot" and "cold" storage** — messages less than 30 days old go to a fast ScyllaDB cluster; older messages go to a tiered store (S3 + Parquet, query via Athena for history).
2. **Cell-based architecture** — partition the user base into independent cells (e.g., 10M users per cell), each with its own complete Kafka + ScyllaDB stack. Inter-cell messages route via a lightweight cell-routing service. This is the Meta WhatsApp architecture at scale.
3. **Write-ahead to Kafka as durable log** — treat Kafka as the primary store for the last 7 days; Cassandra is a derived secondary store. This removes the Cassandra write from the critical path.

### At 1000x Current Load

**1000x:** 500M writes/s — this is beyond any single cloud region

**Fundamental changes required:**

1. **Multi-region active-active with geo-partitioned users** — each user is "homed" to a region (based on their country). Messages between users in the same region never leave that region. Cross-region messages use a dedicated inter-datacenter replication bus.

2. **Edge-side message buffering** — deploy chat relay servers at Cloudflare Workers or PoP edge locations. The sender's message is ACK'd at the edge in < 10 ms; the edge durably queues it and forwards to the home region asynchronously. This decouples sender latency from global replication latency.

3. **Protocol switch for mobile** — at 1000x scale, raw WebSocket per connection consumes too much server memory for TCP state. Switch long-lived connections to QUIC (UDP-based) which is multiplexed and has 0-RTT reconnection. WhatsApp's mobile team migrated to a proprietary binary protocol over UDP for exactly this reason.

4. **Delivery guarantees via persistent client-side queue** — instead of the server routing to a specific chat server, clients have a durable outbox: every unsent message is written to the device's SQLite DB first. A background sync process handles sending with exponential backoff. This moves complex retry logic from server to client, reducing server state dramatically.

## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Real-time transport | WebSocket | Long-polling / SSE | WebSocket is bidirectional; polling wastes bandwidth and adds latency. SSE is server-push-only — can't receive client messages on same connection. |
| Message store | Cassandra / ScyllaDB | PostgreSQL / MySQL | Chat is write-heavy, append-only, and needs time-range scans. PostgreSQL can't sustain 500K writes/s without heroic sharding effort. Cassandra was built for this. |
| Message ordering | Kafka partition by conversation_id | Partition by sender_id | Conversation-level ordering guarantees messages arrive in causal order. Sender-level partitioning loses ordering between different senders in the same conversation. |
| Delivery receipt flow | Through Kafka (async, durable) | Direct server-to-server gRPC | Kafka acks survive server crashes; a direct gRPC call is lost if Chat-Srv-1 restarts between receipt and forwarding. |
| Presence storage | Redis with 65s TTL | Direct DB writes | Presence changes millions of times per second; Redis handles this; any SQL DB would immediately saturate. |
| Group fan-out threshold | Fan-out-on-write for < 200, queue for ≥ 200 | Always queue / always fan-out | Small groups benefit from lower latency (direct push); large groups need async processing to avoid holding the fan-out worker for seconds. |
| Media storage | Object store (S3) + CDN, separate from messages | Store blobs in Cassandra | BLOBs in Cassandra create huge sstable files, destroy compaction performance, and waste expensive NVMe storage. Object stores are designed for this. |
| Connection registry | Redis Cluster | Zookeeper / etcd | Redis HSET/HGET is O(1) and handles millions of ops/s. ZooKeeper is a coordination service (lock manager), not a high-throughput KV store. |
| Deduplication window | 24-hour client_seq + message_id cache in Redis | Idempotency key in DB | Redis dedup check is O(1) before any DB write; querying Cassandra for dedup would add 5-10ms to every message path. |

## Step 10 — How Real Companies Solved This

### WhatsApp

**Architecture:** WhatsApp chose Erlang/BEAM for their chat servers — a decision made in 2009 that proved prescient. Erlang's actor model means each user connection is an independent lightweight process (300 bytes of memory overhead). The BEAM VM was built for telecom switches that must run for years without downtime; WhatsApp needed the same guarantee.

**Ejabberd modification:** They forked the open-source XMPP server ejabberd and extended it with their own binary protocol (still XMPP-based but with custom extensions for delivery receipts, media references, and group mechanics). They kept using Erlang's built-in Mnesia database for the routing table (which server holds which user's connection) because Mnesia is distributed, in-memory, and native to Erlang — zero serialization cost.

**What they got wrong first:** Early WhatsApp ran a single Erlang cluster per region. As they grew, they discovered that Mnesia's replication protocol (which uses a full-table copy for new nodes) was too slow when adding capacity. They moved to a sharded architecture with multiple independent clusters, each serving a shard of users.

**Key engineering insight:** At peak, WhatsApp ran 50 engineers serving 1 billion users — roughly 20 million users per engineer. This was only possible because Erlang's fault tolerance (supervisor trees, hot code loading) meant the on-call burden was low. The lesson: choosing the right language runtime is a 10-year architectural decision, not a language-preference debate.

**Citation:** Jan Koum's talk at Stanford GSB (2013) and Rick Reed's "WhatsApp in the Cloud" presentation at EUC 2014 describe the Erlang architecture. WhatsApp confirmed 50 billion messages/day on Erlang in 2014; the system has scaled further since Meta's acquisition.

---

### Discord

**Architecture:** Discord started with MongoDB → Cassandra → ScyllaDB for message storage. Their public engineering blog documents each migration with the specific failure mode that triggered it.

**What they got wrong first (MongoDB):** Original message storage was MongoDB with a single document per message. As volume grew, MongoDB's in-memory working set no longer fit in RAM, and random read latency spiked to seconds. The fundamental mismatch: MongoDB's document model and indexing strategy was not designed for time-series append-mostly data with range scans.

**Cassandra migration:** They moved to Cassandra and it worked — for a while. Cassandra's LSM-tree write path was a perfect fit for append-only messages. The failure mode that eventually emerged: **JVM GC pauses.** At high traffic, Cassandra's Java garbage collector would pause for 10–30 seconds during full GC cycles. During this pause, all reads and writes to that node timed out, causing cascading failures. On-call engineers were regularly manually rebooting nodes.

**ScyllaDB migration (2023):** They rewrote their data migration tool in Rust (achieving 3.2M records/second throughput) and migrated trillions of messages from 177 Cassandra nodes to 72 ScyllaDB nodes — in 9 days without downtime. Results:
- p99 read latency: 40–125ms (Cassandra) → 15ms (ScyllaDB)
- p99 write latency: 5–70ms (Cassandra) → 5ms (ScyllaDB) — the lower floor AND elimination of the 70ms tail

**Key engineering insight:** Discord built a **data services layer** in Rust between their application servers and ScyllaDB. This service does request coalescing — if 1,000 users simultaneously request the same Discord channel's message history (e.g., a viral post), the data service deduplicates those 1,000 ScyllaDB reads into a single read and fans the result out. This eliminated hot-partition cascades that would previously take down Cassandra nodes.

**Citation:** Bo Ingram, "How Discord Stores Trillions of Messages," Discord Engineering Blog (2023). Available at discord.com/blog.

---

### Slack

**Architecture:** Slack's real-time messaging uses WebSockets but their connection management layer is more complex than WhatsApp's because Slack has "workspaces" (organizations) as a first-class concept. A single user's WebSocket connection must subscribe to dozens of channels across potentially multiple workspaces.

**What Slack got wrong first:** Early Slack used a single Gateway Service that maintained WebSocket connections AND subscribed to channel pub/sub topics. As channel count grew, a single Gateway Server might be subscribed to 10 million channels. The fanout from a popular channel message to all subscribed gateways created thundering-herd problems.

**The channel server architecture:** Slack separated concerns into Channel Servers (one logical server per channel, distributed via consistent hashing) and Gateway Servers (one per client connection). A message published to a channel is routed to that channel's Channel Server, which maintains the subscriber list for that specific channel and pushes to the relevant Gateway Servers. This is identical in principle to the Redis pub/sub per-connection design described in this document's architecture, but implemented as dedicated processes rather than Redis channels.

**Scale achieved:** Slack's system delivers messages globally in under 500ms p99, serves tens of millions of connected clients, and handles tens of millions of channels per host.

**Citation:** Michael Dearing and Soren Macbeth, "Real-Time Messaging at Slack," Slack Engineering Blog. slack.engineering/real-time-messaging.

## Interview Perspective

### What the Interviewer Is Evaluating

For this specific problem, the interviewer is NOT looking for generic "use a load balancer, add a cache" answers. They are looking for:

1. **Do you understand the stateful nature of WebSocket connections?** — Most systems are stateless; chat requires every message to find the right server holding a specific user's connection. How you solve this routing problem is the core technical challenge.
2. **Can you reason about message ordering in a distributed system?** — Kafka partition-by-conversation is the right answer; partition-by-sender is wrong. Do you know why?
3. **Do you understand delivery semantics?** — At-most-once (lose messages), exactly-once (expensive), at-least-once + client-side dedup (practical). Can you implement the dedup layer?
4. **Can you design the three-state receipt system?** — Most candidates can describe the states; few can draw the sequence diagram showing how the receipt flows back from recipient to sender through the system.
5. **Do you understand the group message fan-out problem?** — The threshold between synchronous fan-out and async queue fan-out is a concrete design decision with real numbers behind it.

---

### Junior (L3-L4) Answer

**What they say:**
- Users connect via WebSocket
- Messages stored in a database (often MySQL or MongoDB)
- "Use Redis for caching"
- "Use a message queue for async delivery"

**Depth reached:**
- Can draw the basic client → server → database flow
- Knows delivery receipts exist but cannot design them
- Describes presence as "store online status in Redis"

**What they miss:**
- How the fan-out worker finds the right chat server for a recipient
- Message deduplication (what happens on retry?)
- The sequence number / gap detection problem for offline catch-up
- Group fan-out at scale — treats 5 members the same as 1,000 members
- The race condition between delivery and the receipt propagation path

---

### Senior (L5) Answer

**What they add:**
- Explicitly chooses Cassandra over MySQL for the message store and explains why (write-heavy, time-range scans, no joins needed)
- Designs the connection registry in Redis and explains how the fan-out worker uses it
- Describes the dedup layer using `client_seq` + Redis idempotency key
- Draws the Kafka topic partitioned by `conversation_id` and explains why this matters for ordering
- Separates the receipt propagation path as a distinct concern flowing back through Kafka
- Distinguishes online delivery vs. offline queue + push notification paths

**Specific depth on this problem:**
- Knows that group membership lookups require an index on `user_id` in the memberships table, not just `group_id`
- Can describe what "at-least-once delivery with client-side dedup" means in practice
- Mentions that the delivered-tick timing (immediate vs. batch) is a product decision with UX implications

---

### Staff (L6+) Answer

**What they drive to unprompted:**

1. **Failure mode analysis:** "What happens if the fan-out worker crashes after writing to Cassandra but before pushing to the recipient's chat server?" → The message must be re-delivered from Kafka (idempotent consumer). How do we ensure the Cassandra write and the Kafka offset commit are atomic? (Answer: write to Cassandra first, then commit Kafka offset; duplicate delivery is handled by client dedup.)

2. **Cost reasoning:** "At 2 PB of media per day, object storage alone costs ~$40M/year at S3 standard pricing ($0.023/GB/month). We need a tiered policy: media deleted from CDN after 30 days, archived to Glacier for legal hold, with re-fetch-on-demand for older media." (Real WhatsApp does NOT store media long-term on their servers — it expires.)

3. **Cell-based architecture unprompted:** "For geo-compliance (GDPR, India's data localization), we need to ensure messages between Indian users never leave Indian data centers. A cell-based design where users are homed to a region cell handles this — it's also how WhatsApp's multi-datacenter architecture works after the Meta acquisition."

4. **Protocol efficiency:** "At 600M concurrent WebSocket connections, TCP state alone (kernel TCP buffer: 4KB × 600M = 2.4 PB of kernel memory) is unsustainable. We need to either (a) move to a multiplexed protocol like QUIC so one socket handles multiple users, or (b) use a tiered connection model where inactive users are switched to push notifications and only fully connected when active."

5. **Observability:** "We need per-conversation delivery SLO monitoring. If Alice's message to Bob has not been delivered within 10 seconds, fire an alert. This requires a streaming job (Flink) joining message_send events with delivery_ack events on message_id, with a 10-second watermark."

### The 4-5 Mistakes Candidates Make On This Specific Problem

**Mistake 1: Designing a stateless message server**
Putting messages in a queue and having any server pick them up for delivery ignores the fact that WebSocket connections are stateful — Bob's connection lives on exactly one server. If you don't design the routing layer (connection registry), you can't deliver messages to online users.

**Mistake 2: Partitioning Kafka by sender_id instead of conversation_id**
This sounds intuitive but is wrong. If Alice sends messages 1 and 2, and Bob sends message 3, all in the same conversation, Alice's messages go to partition A and Bob's to partition B. They're consumed by different workers in undefined order relative to each other. Partitioning by `conversation_id` means all three messages are on the same partition, consumed in order.

**Mistake 3: Using SQL database for message storage**
MySQL or PostgreSQL will work in demo, but at 500K writes/second it immediately becomes the bottleneck. The candidate must recognize that the access pattern (append-only, range-scan by time, no joins needed) is exactly what Cassandra/ScyllaDB was designed for.

**Mistake 4: Forgetting the offline user path**
Most candidates design only the happy path: Bob is online, gets the message. When asked "what if Bob is offline?", they improvise. The offline path (queue → push notification → reconnect → catch-up from gap) is a complete design problem in itself. Not having it ready signals shallow thinking.

**Mistake 5: Not connecting delivery receipts to the sender**
Candidates often say "store the receipt in the database." The interviewer will follow up: "How does Alice's phone update from single-tick to double-tick without polling?" The answer requires an event flowing back from Bob's chat server to Alice's chat server — a separate routing operation through the system. Missing this means you don't understand the bidirectional nature of the receipt protocol.
