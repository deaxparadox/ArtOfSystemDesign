# 10.7 — Design a Distributed Cache

> 📍 Phase 10 — Classic System Design Problems

> **Key Challenge:** Consistent hashing for distribution, stampede prevention, eviction under memory pressure, replication for HA

**Prerequisites:** All of Phases 1-9.

---

## Problem Statement

A distributed cache is an in-memory key-value store spread across multiple nodes that intercepts reads before they hit the primary datastore, dramatically reducing latency and database load. It is a critical infrastructure layer used by virtually every internet-scale company to serve billions of requests per day with sub-millisecond latency — Twitter, Netflix, Facebook, and Amazon all rely on distributed caches as the primary scaling lever for their read-heavy workloads.

---

## Step 1 — Clarify Requirements (5-10 min in interview)

### Functional Requirements

1. **Set(key, value, ttl)** — store a value with an optional time-to-live expiry
2. **Get(key)** — retrieve a cached value; return a cache miss signal if absent or expired
3. **Delete(key)** — explicit invalidation of a cache entry
4. **Bulk operations** — mGet / mSet for fetching or writing multiple keys in one round trip
5. **Eviction on memory pressure** — when the cache is full, automatically evict entries per a configured policy (LRU, LFU, TTL)
6. **Namespace / tenant isolation** — logically separate caches for different services sharing the same cluster

### Non-Functional Requirements

| Attribute | Target |
|---|---|
| Availability | 99.99% (52 min downtime/year) |
| Read latency | p50 < 1 ms, p99 < 5 ms |
| Write latency | p99 < 10 ms |
| Consistency model | Eventual consistency acceptable; cache may lag DB by seconds |
| Durability | Not required — cache is a best-effort layer; DB is source of truth |
| Throughput | 1 million ops/second per cluster; horizontally scalable |
| Cache hit ratio | Target > 80% in steady state |

### Out of Scope

- **Persistence / durability** — we are not designing a durable data store (Redis AOF/RDB or similar persistence is a separate concern)
- **Full-text search** — the cache stores opaque byte values; querying or indexing content is out of scope
- **Authentication and authorisation** — application-layer security is assumed at the API gateway
- **Client-side / browser caching** — we design only the server-side distributed tier
- **Cache warming at deployment** — automated warm-up pipelines are operational concerns, not architectural ones here

### Clarifying Questions to Ask the Interviewer

| # | Question | Why It Matters |
|---|---|---|
| 1 | What is the expected read-to-write ratio? | 100:1 vs 10:1 changes whether we optimise reads aggressively (replica reads, client-side caches) or writes (replication lag matters more) |
| 2 | Do we need multi-region support? | Multi-region replication changes the consistency model fundamentally — cross-region writes are expensive and require conflict resolution |
| 3 | What is the average and maximum value size? | Small values (< 1 KB) vs large values (100 KB blobs) change memory layout, network bandwidth, and serialisation cost dramatically |
| 4 | What is the cache hit ratio expectation, and is serving stale data acceptable? | If stale data is acceptable for seconds, we can use stale-while-revalidate and simplify stampede handling significantly |
| 5 | What eviction policy is preferred — LRU, LFU, or TTL-based? | LRU is correct for recency-driven workloads; LFU is better for Zipfian distributions with stable hot keys |
| 6 | Do clients need strong consistency between cache and DB on writes? | Write-through vs write-back vs cache-aside changes the API contract and failure modes |
| 7 | Are there known hot keys (a small number of extremely popular keys)? | Hot keys require special treatment — read replicas, local L1 caches, or key sharding — and change the architecture materially |

## Step 2 — Capacity Estimation (5 min in interview)

### Assumptions

- **100 million DAU**, each making ~50 cache lookups per day (across reads for profile, feed, settings, etc.)
- **Read:Write ratio** = 90:10 (heavily read-dominated)
- **Average key size**: 64 bytes
- **Average value size**: 1 KB (serialised JSON objects)
- **Target cache hit ratio**: 85%
- **TTL**: average 300 seconds (5 minutes)

### QPS

```
Total daily operations = 100M DAU × 50 ops/day = 5 billion ops/day

Peak multiplier = 3x (traffic is not uniform)

Peak ops/second = 5B / 86,400s × 3 = ~174,000 peak ops/sec → round to 200,000 ops/sec

Read ops/sec  = 200,000 × 0.90 = 180,000 reads/sec
Write ops/sec = 200,000 × 0.10 =  20,000 writes/sec
```

### Cache Storage

```
Working set = keys that are actually hot at any given time

Hot keys = 20% of all data accounts for 80% of traffic (Zipf's law)
Total dataset in DB = 500 GB (assume user data + feed metadata)
20% hot set = 100 GB

Per key memory overhead = key (64 B) + value (1 KB) + metadata (50 B) ≈ 1.1 KB
Number of entries to cache = 100 GB / 1.1 KB ≈ 95 million entries
Total raw memory = 95M × 1.1 KB ≈ 100 GB

Memory fragmentation factor = 1.25 (Redis typical overhead)
Actual memory required = 100 GB × 1.25 = 125 GB
```

### Server Count

```
Single cache server RAM = 64 GB (practical upper bound for cache nodes)
Number of servers = 125 GB / 64 GB = 2 servers (minimum)

With replication factor of 3 (1 primary + 2 replicas per shard):
Total servers = 2 primaries × 3 = 6 servers minimum

Add headroom for 50% buffer:
Recommended = 12 servers (6 primary shards × 2 replicas each)
```

### Bandwidth

```
Read bandwidth  = 180,000 reads/sec × 1.1 KB = ~200 MB/s ingress from clients
Write bandwidth = 20,000 writes/sec × 1.1 KB = ~22 MB/s write ingress
Replication     = 22 MB/s × 2 replicas = ~44 MB/s inter-node replication traffic

Total peak bandwidth per cluster ≈ 266 MB/s → well within 10 Gbps NIC capacity
```

### Component Walkthrough

**Cache Client Library** (runs in the application process)
- Maintains a consistent hash ring of all known cache nodes
- Routes each key to the correct node without a proxy hop (saves ~1 ms per request)
- Maintains a per-node connection pool (typically 10-50 connections per node)
- Implements retry logic with exponential backoff on transient failures
- Batches multiple keys into pipelined mGet requests to minimise round trips
- Why here: eliminating a proxy hop is the biggest single latency win; client-side routing is standard in production (Redis Cluster, Memcached Ketama)

**Cache Nodes (Shards + Replicas)**
- Each node is a single-threaded in-memory process (Redis architecture) or multi-threaded (Memcached architecture)
- Each primary shard owns a contiguous range of hash slots (16,384 slots total in Redis Cluster)
- Replicas receive asynchronous replication stream from their primary
- Replicas serve read traffic to scale read throughput (optional, configurable per use case)
- Why sharding: a single 64 GB node cannot handle 200,000 ops/sec without CPU saturation; sharding distributes both memory and CPU

**Gossip / Cluster Bus**
- Nodes exchange cluster state (who owns which slots, who is up/down) via a gossip protocol over a separate port
- Failure detection: a node is declared FAIL after PFAIL is confirmed by a quorum of other nodes
- Why gossip: avoids a single coordinator; decentralised failure detection with O(N) messages per epoch

**Primary Datastore**
- The source of truth; cache misses result in a synchronous read from the DB
- Write policy (cache-aside, write-through, write-back) determines how DB and cache stay in sync
- Why not rely on DB alone: even a fast DB (MySQL at 5 ms p99) is 5,000x slower than a cache hit (1 µs); caching is existential at scale

## Step 4 — Data Model

### Core Cache Entry

The cache stores opaque key-value pairs. Internally, each node maintains:

```
CacheEntry {
    key          : bytes        // variable length, max 512 bytes
    value        : bytes        // variable length, max configurable (default 512 MB in Redis)
    ttl_ms       : int64        // absolute expiry timestamp in epoch milliseconds; 0 = no expiry
    last_access  : int64        // epoch milliseconds, updated on every read (for LRU tracking)
    access_count : int32        // frequency counter for LFU eviction
    flags        : uint32       // client-defined flags (e.g., serialisation format)
    size_bytes   : int32        // pre-computed size for memory accounting
}
```

### Internal Data Structure: The Hash Table + LRU Doubly-Linked List

Redis uses a dictionary (hash table) for O(1) lookups combined with a doubly-linked list of all keys sorted by recency. This is the textbook LRU implementation:

```
Hash Table
┌───────────────────────────────────────────────────────┐
│  bucket[hash(key) % N]  →  CacheEntry → CacheEntry   │
│  bucket[...]            →  CacheEntry                 │
│  ...                                                  │
└───────────────────────────────────────────────────────┘
         ↓ pointer into LRU list
LRU Doubly-Linked List (MRU head ... LRU tail)
HEAD → [most_recent] ⟷ [recent] ⟷ ... ⟷ [oldest] ← TAIL
```

**Important:** Redis does not use a true LRU. It uses approximate LRU: on eviction, Redis samples `maxmemory-samples` (default 5) random keys and evicts the one with the oldest `last_access`. This is intentional — true LRU requires touching the LRU list on every GET, which adds memory bandwidth and lock contention.

### Cluster Slot Mapping

```
SlotMap {
    slot_id   : uint16         // 0–16383
    node_id   : string         // primary node identifier
    replicas  : []string       // replica node identifiers
    migrating : bool           // true during slot migration (resharding)
}
```

### No Persistent Schema

The cache does not have a schema — values are opaque bytes. Schema knowledge lives in the application layer. This is intentional: it allows the cache to serve arbitrary application data types without understanding their structure.

## Step 6 — Deep Dive: Consistent Hashing and the Hash Ring

This is where interviews are won or lost on distributed cache questions. The naive approach is `hash(key) % N`. The problem: adding or removing one node remaps ~(N-1)/N of all keys, causing a thundering herd of cache misses that floods the DB. Consistent hashing reduces this to ~1/N remapped keys.

### Layer 1: The Ring

Imagine a hash space of 0 to 2^32-1 arranged as a circle. Both nodes and keys are mapped to positions on this ring using the same hash function (MD5, MurmurHash3, xxHash).

```
                     0 (top of ring)
                     │
         ┌───────────┼───────────┐
         │           │           │
    Node A       Node B       Node C
   (pos 90°)   (pos 210°)   (pos 330°)
         │           │           │
    Keys between    Keys between Keys between
    330°-90°        90°-210°     210°-330°
    belong to A     belong to B  belong to C
```

**Key assignment rule:** a key is assigned to the first node encountered clockwise from the key's position on the ring.

**What happens on node removal (Node B fails):**
- Only keys in the range [Node A's position, Node B's position] need to be reassigned — to Node C
- All other keys stay with their current nodes
- Approximately 1/N of keys are remapped (where N = number of nodes)

### Layer 2: Virtual Nodes (Vnodes) — The Critical Insight

With 3 physical nodes and one ring position each, load distribution is highly uneven — one node might end up owning 50% of the key space by chance. **Virtual nodes** solve this by placing each physical node at multiple positions on the ring:

```
Hash Ring with Virtual Nodes (150 vnodes per physical node, 3 nodes = 450 ring positions)

     Physical Node A          Physical Node B          Physical Node C
     A1, A2, A3...A150        B1, B2, B3...B150        C1, C2, C3...C150

Ring (unrolled):
[A47][B3][C88][A12][B134][C7][A89][B62][C41]...[A1][B99][C150]
  ↑                                              ↑
 key "user:42" lands here (goes to A47)     key "session:7" lands here (goes to A1)
```

**Effect of 150 vnodes per node:**
- Standard deviation of load across nodes drops from ~18% (1 vnode) to ~1.5% (150 vnodes)
- When Node B is added, each existing vnode range is split — N/150 of B's vnodes come from A, N/150 from C, etc.
- Data redistribution is parallelised across all existing nodes

**Production numbers from Netflix EVCache:**
- Uses Ketama algorithm (consistent hashing with virtual nodes)
- 150 virtual nodes per physical node is standard in Memcached Ketama
- Redis Cluster uses a simpler fixed 16,384 hash slots instead of a continuous ring

### Layer 3: Redis Cluster's Hash Slot Approach (Flat Slots vs. Ring)

Redis Cluster diverges from the ring approach. It uses 16,384 fixed slots (`CRC16(key) % 16384`). This is equivalent to a ring with exactly 16,384 evenly-spaced positions.

```
Hash slot assignment in a 3-node cluster:

Node A: slots 0    – 5460    (33.3% of keyspace)
Node B: slots 5461 – 10922   (33.3% of keyspace)
Node C: slots 10923– 16383   (33.3% of keyspace)

Key routing: slot = CRC16("user:42:profile") % 16384 = 7423 → Node B
```

**Why 16,384?** Redis author antirez chose this number deliberately:
- 16,384 slots allows cluster state to be gossiped in a compact 2 KB bitmap (16,384 bits = 2,048 bytes)
- At 1,000 nodes (the practical max), each node owns ~16 slots — granular enough for even distribution
- CRC16 of 16 bits produces 65,536 values; 16,384 = 65,536 / 4 provides good distribution without wasted space

**Hash Tags:** `{user:42}:profile` and `{user:42}:settings` hash to the same slot (only the content inside `{}` is hashed). This enables multi-key operations (MGET, transactions) across keys that must co-locate.

### Resharding: Live Slot Migration

When a node is added, some slots are migrated to it:

```
Migration state machine per slot:

STABLE ──── begin_migration ────► MIGRATING (source node)
                                          │
                              keys served from source,
                              new writes go to destination
                                          │
                              IMPORTING  (destination node)
                                          │
                              all keys transferred
                                          │
STABLE ◄─── migration_complete ───────────┘
```

During migration, a key lookup on the source returns `ASK redirect` if the key has already moved:
```
MOVED 7423 192.168.1.2:6379     // slot permanently moved — update slot map
ASK   7423 192.168.1.3:6379     // slot being migrated — ask destination this once
```

Clients must handle both redirect types. `MOVED` updates the local slot map; `ASK` is a one-time redirect without updating the map.

## Step 7 — Deep Dive: Cache Stampede Prevention and Eviction Under Pressure

### Layer 1: The Problem — Cache Stampede (Thundering Herd)

A cache stampede occurs when:
1. A popular key expires (or is evicted)
2. Thousands of concurrent requests simultaneously experience a cache miss
3. All of them rush to the database to regenerate the same value
4. The DB is overwhelmed; response times spike; the cache is repopulated by the first responder, but too late

```
Timeline of a cache stampede:

T=0ms    Key "trending:feed" expires (TTL elapsed)
T=1ms    Request 1 → cache miss → starts DB query
T=1ms    Request 2 → cache miss → starts DB query
T=1ms    Request 3 → cache miss → starts DB query
...
T=1ms    Request 5000 → cache miss → starts DB query
         ↓
T=50ms   DB CPU at 100%; connection pool exhausted
T=60ms   DB query timeout → error propagates to all 5000 requests
T=60ms   Cache still empty (no writer succeeded)
         ↓ cascade failure
```

### Layer 2: Three Production-Grade Solutions

#### Solution 1: Mutex Lock (Distributed Lock)

Use a distributed lock (Redis SETNX with TTL) to ensure only one process recomputes the value:

```
Pseudocode:

function get_with_lock(key, db_fetch_fn, ttl):
    value = cache.get(key)
    if value is not None:
        return value                         // fast path: cache hit

    lock_key = "lock:" + key
    lock_acquired = cache.set(lock_key, 1, NX=True, PX=5000)  // 5s lock TTL

    if lock_acquired:
        try:
            value = db_fetch_fn(key)         // only one thread fetches from DB
            cache.set(key, value, EX=ttl)
            return value
        finally:
            cache.delete(lock_key)
    else:
        // Another thread holds the lock — wait briefly and retry
        sleep(50ms)
        return get_with_lock(key, db_fetch_fn, ttl)  // recurse
```

**Pros:** Zero duplicate DB queries for the locked key  
**Cons:** Waiting threads add latency (50ms sleep); lock expiry edge cases if DB query takes longer than lock TTL; lock contention under extreme load

**When to use:** Single very hot key (homepage, trending feed), where correctness matters more than p99 latency

#### Solution 2: Probabilistic Early Expiration (XFetch Algorithm)

Instead of waiting for expiry, proactively regenerate the cache entry before it expires. The probability of regeneration increases as the expiry approaches:

```
XFetch algorithm (Vattani et al., 2015):

function get_xfetch(key, db_fetch_fn, beta=1.0):
    value, expiry = cache.get_with_expiry(key)

    if value is None:
        // Hard miss — standard path
        value = db_fetch_fn(key)
        ttl = compute_ttl()
        cache.set(key, value, EX=ttl)
        return value

    // Check if we should proactively recompute
    time_to_expiry = expiry - now()          // in seconds
    delta = compute_time()                   // simulated fetch cost in seconds

    // Exponential random: if this evaluates to true, recompute now
    if now() - delta * beta * log(random()) >= expiry:
        // Background: recompute and refresh
        new_value = db_fetch_fn(key)
        cache.set(key, new_value, EX=ttl)
        return new_value

    return value                             // still fresh
```

**Key insight:** `log(random())` is always negative, so `now() - delta * beta * log(random()) > now()`. As `time_to_expiry` shrinks, this expression becomes true with increasing probability. When `time_to_expiry = 0`, it is always true.

**Beta parameter:** Higher beta = more aggressive early recomputation; `beta=1.0` is the recommended default.

**Pros:** No locking; no sleeping threads; load is spread over time rather than concentrated at expiry  
**Cons:** Slightly higher DB query rate (proactive refreshes); requires storing expiry timestamp separately (not just TTL)

#### Solution 3: Stale-While-Revalidate (SWR)

Serve the stale value immediately while triggering a background refresh:

```
Cache entry metadata:
{
  "value": <data>,
  "soft_ttl": T,      // after this, value is "stale but usable"
  "hard_ttl": T + 30s // after this, value is unusable
}

function get_swr(key, db_fetch_fn):
    entry = cache.get(key)

    if entry is None:
        // Hard miss — synchronous fetch
        return synchronous_fetch_and_cache(key, db_fetch_fn)

    if now() > entry.soft_ttl and not entry.refresh_in_progress:
        // Soft miss — serve stale, trigger background refresh
        entry.refresh_in_progress = True
        cache.set(key, entry)                // update flag atomically
        fire_and_forget(refresh_key, key, db_fetch_fn)

    return entry.value                       // always returns immediately
```

**Pros:** Zero added latency for the requester; no DB overload; simplest to implement  
**Cons:** Data can be stale for up to `hard_ttl - soft_ttl` seconds; unsuitable for financial or inventory data that must be fresh

### Layer 3: Eviction Under Memory Pressure

When memory reaches `maxmemory`, the cache must evict keys. The eviction policy is the most impactful configuration decision for cache efficiency.

**LRU Eviction — Mechanics:**

```
LRU Approximation (Redis implementation):

maxmemory-policy: allkeys-lru
maxmemory-samples: 10       // sample size (higher = more accurate but slower)

On each SET that would exceed maxmemory:
1. Sample 10 random keys from the hash table
2. Sort by last_access timestamp
3. Evict the key with the oldest last_access
4. Repeat until memory < maxmemory

True LRU would require a doubly-linked list, touching it on every GET:
  - GET "user:42" → move to head of LRU list → O(1) pointer manipulation
  - This adds memory bandwidth and potential lock contention at high QPS

Redis approximation avoids this: last_access is stored in the key metadata (3 bytes, 10-second precision)
Statistical analysis: with sample=10, eviction quality is within 2% of true LRU
```

**LFU Eviction — Mechanics:**

```
LFU (Least Frequently Used) — better for Zipfian workloads:

Each key has an access_counter with logarithmic decay:

counter = counter + 1 / (counter * lfu_log_factor + 1)
    // logarithmic increment: adding 1 to counter requires exponentially more hits

Decay: every lfu_decay_time minutes, counter is decremented by 1
    // this prevents old hot keys from dominating forever

Use allkeys-lfu when:
  - Access pattern is Zipfian (a few keys are extremely hot)
  - Hot key set is stable over time (consistent popular content)

Use allkeys-lru when:
  - Access patterns are recency-driven (recent events matter more than history)
  - Cache is warming up and popularity changes rapidly
```

**Eviction policy comparison:**

| Policy | Best For | Weakness | Redis Config |
|---|---|---|---|
| allkeys-lru | General workloads, session data | Evicts recently-set cold keys if they happen to be old | `maxmemory-policy allkeys-lru` |
| allkeys-lfu | Stable Zipfian hot key distribution | New keys start with low frequency; may be evicted early | `maxmemory-policy allkeys-lfu` |
| volatile-lru | Mixed TTL and non-TTL keys | Keys without TTL are never evicted (OOM risk) | `maxmemory-policy volatile-lru` |
| volatile-ttl | Explicit expiry-driven eviction | Shortest TTL may not be the least valuable key | `maxmemory-policy volatile-ttl` |
| noeviction | Data integrity (error on full) | Application errors when memory full | `maxmemory-policy noeviction` |

## Step 8 — Scale: Where This Design Breaks

### At 10x Current Load (2M ops/sec)

**Bottleneck: Single-threaded Redis CPU**

Redis is single-threaded for command processing (I/O threads are separate). A single Redis instance saturates at ~100,000–200,000 simple commands/second on a modern CPU core. At 2M ops/sec, a single-shard cluster cannot keep up even with fast hardware.

**Fix:**
- Increase shard count from 6 to 24 (or more) — each shard handles ~83,000 ops/sec
- Use Redis 6+ multi-threaded I/O (command parsing and response sending use thread pool; command execution remains single-threaded)
- Introduce **local L1 cache** in the application process (e.g., Caffeine in Java, LRU-Cache in Go) for the top 1,000 hottest keys. These are served from process memory at ~100 ns, never hitting Redis.

**Fix diagram:**
```
App Process
┌────────────────────────────────────────┐
│  L1 Cache (in-process, 1000 hot keys)  │  ← ~100 ns
│  ↓ miss                                │
│  L2 Cache (Redis Cluster, 12 nodes)    │  ← ~1 ms
│  ↓ miss                                │
│  Primary DB                            │  ← ~5 ms
└────────────────────────────────────────┘
```

### At 100x Current Load (20M ops/sec)

**Bottleneck: Hot Keys and Network**

Even with 24 shards, some keys receive disproportionate traffic. A viral post's cache entry might receive 500,000 reads/sec — all routed to one shard. No amount of horizontal sharding solves single-key hotspots.

**Fixes:**

1. **Read replicas for hot keys:** Route hot key reads to replicas (each shard has 2 replicas = 3x read capacity per shard). Detect hot keys using Redis's `hotkeys` command or client-side hit count metrics.

2. **Key mirroring / fanning:** Store the same hot value under multiple keys (`popular_post:9999:shard_0`, `popular_post:9999:shard_1`, ...) and route reads round-robin. The trade-off: write amplification (must update all copies on mutation).

3. **Local process cache (L1) with short TTL:** Cache the top ~1% of keys in the application process with a 1–5 second TTL. At 20M ops/sec across 1,000 app servers, each server handles 20,000 ops/sec; an L1 hit eliminates the network entirely.

4. **Network:** At 20M ops/sec with 1 KB average value, egress bandwidth = 20 GB/s. Require 25 Gbps NICs; move to jumbo frames; consider RDMA for ultra-low latency inter-node replication.

### At 1000x Current Load (200M ops/sec)

**Bottleneck: Fundamental Architecture — Memory Cost and Cross-DC Latency**

At 200M ops/sec, the in-memory model becomes cost-prohibitive. Holding a 1 TB working set in RAM requires hundreds of cache servers. Fundamental changes required:

1. **Tiered caching:** Add a second tier using NVMe SSDs (e.g., Facebook's CacheLib / RocksDB). L1 = DRAM (hot, tiny), L2 = NVMe (warm, large). NVMe latency is ~100 µs — 100x slower than DRAM but 50x cheaper per GB.

2. **Disaggregated memory (RDMA):** Separate compute and memory — cache nodes have 2–8 TB of DRAM; application nodes access them via RDMA (Remote Direct Memory Access) at ~5 µs round trip without involving the CPU on the memory node. Used by ByteDance and Alibaba at hyperscale.

3. **Geo-distributed caches with regional consistency:** Each region has its own cache cluster; writes invalidate remote caches via a pub/sub invalidation bus (Kafka). Cache reads are always local; cache consistency is eventual (2–5 second lag acceptable for most use cases).


## Step 9 — Trade-off Summary

| Decision | Choice Made | Alternative Considered | Reason |
|---|---|---|---|
| Routing | Client-side consistent hashing | Proxy-based routing (Twemproxy) | Eliminates proxy as latency and single-point-of-failure; saves 0.5–1 ms per request |
| Sharding algorithm | Consistent hashing with virtual nodes | Modular hashing (key % N) | Only 1/N keys remapped on node change vs. N-1/N; crucial for live resharding |
| Eviction policy | Approximate LRU (default) | True LRU doubly-linked list | True LRU adds memory bandwidth on every read; approximation is within 2% accuracy at sample=10 |
| Replication | Asynchronous primary-replica | Synchronous write | Sync write adds 2–10x write latency for durability we don't need (DB is truth); async replication is standard |
| Stampede prevention | XFetch probabilistic early expiry | Mutex lock per key | XFetch spreads load over time; mutex adds sleep latency and lock-expiry edge cases |
| Write policy | Cache-aside (lazy population) | Write-through | Cache-aside avoids caching data that is never re-read; simpler failure handling — DB write success does not depend on cache availability |
| Consistency | Eventual consistency | Strong consistency | Strong consistency requires synchronous cross-replica writes, doubling write latency; eventual is acceptable for read-heavy social/content workloads |
| Hash slots | 16,384 fixed slots (Redis Cluster) | Continuous ring (Ketama) | Fixed slots simplify cluster state gossip — slot assignment fits in a 2 KB bitmap |

## Step 10 — How Real Companies Solved This

### Netflix: EVCache

Netflix built EVCache (Ephemeral Volatile Cache) on top of Memcached because they needed multi-region, zone-aware replication that vanilla Memcached did not provide.

**Architecture decisions:**
- **Zone-isolated reads:** Each availability zone has its own Memcached cluster. Reads are always local (same AZ) to maximise throughput and minimise latency. This also provides AZ fault isolation — an AZ outage does not affect caches in other zones.
- **Fanout writes:** All write operations are broadcast to all AZ clusters simultaneously. The client write is acknowledged when at least one zone confirms. Other zones are updated asynchronously.
- **Ketama consistent hashing:** 150 virtual nodes per physical node for even distribution.
- **Scale:** 200 Memcached clusters, 22,000 server instances, 400 million ops/second, 14.3 PB of cached data across all clusters.

**What they got wrong first:**
Netflix initially used a single Memcached cluster per region without AZ isolation. When an AZ had elevated latency (a common AWS occurrence), all cache reads from that region were slow. Moving to per-AZ clusters with local reads reduced p99 latency by ~40%.

**Key insight:** "Replicate writes, localise reads" — the same principle used in database read replicas, applied to caches. Netflix published this in their Tech Blog: [Caching for a Global Netflix](https://netflixtechblog.com/caching-for-a-global-netflix-7bcc457012f1).

---

### Facebook: Scaling Memcache (2013 NSDI Paper)

Facebook's 2013 NSDI paper "Scaling Memcache at Facebook" is the canonical reference for distributed cache engineering at extreme scale. Key insights:

**Architecture decisions:**
- **Lease mechanism to prevent stampedes:** When a client gets a cache miss, the Memcache server grants a lease token (a 64-bit integer tied to the key). The client must present this token when writing back the computed value. If another client asks for the same key while a lease is outstanding, Memcache returns a "wait" response, causing the second client to wait 10ms and retry. This elegantly serialises DB reads without a separate lock service.
- **Demand-filled regional pools:** Facebook's traffic is global. Rather than replicate the full dataset to all regions, they define "regional pools" that are not replicated. Warm-up traffic fills these on demand. This saves significant memory at the cost of higher miss rates for cold keys in new regions.
- **Gutter machines:** A small pool of backup cache machines that absorb traffic when a primary Memcache server fails. Without gutter machines, the DB would absorb all traffic for a failed node's keyspace (potentially 1/N of all requests). Gutter machines have a short TTL (a few seconds) to avoid serving very stale data.
- **McSqueal / McFlusher for DB invalidation:** Facebook uses MySQL binlog replication to detect DB writes and automatically invalidate corresponding cache keys. Application code does not explicitly invalidate cache — the invalidation pipeline reads MySQL commit logs and deletes stale keys.

**What they got wrong first:**
Without the lease mechanism, Facebook's early Memcache clusters had severe thundering herd problems on popular pages. The lease solution reduced DB load by 95% for popular keys during stampede events.

**Key insight:** Cache invalidation driven by DB binlog (rather than application code) is far more reliable — it is impossible to forget to invalidate the cache if the pipeline is automatic. This also enables independent teams to update the DB schema without coordinating cache invalidation logic.

**Scale:** Facebook's Memcache cluster handled over 1 billion operations per second across the fleet at the time of the paper (2013).

---

### Twitter: Twemproxy + Redis

Twitter faced a different challenge: they had thousands of services each needing a small Redis allocation. Managing thousands of small Redis clusters was operationally expensive. Twemproxy solved this by providing a proxy that shards across multiple backend Redis/Memcached instances with a single connection endpoint.

**Architecture decisions:**
- **Twemproxy (nutcracker):** A stateless proxy that sits between clients and backend cache servers. Clients connect to Twemproxy using standard Redis protocol. Twemproxy hashes the key and forwards to the correct backend.
- **Connection multiplexing:** Twemproxy maintains a small connection pool to backends (typically 1-10 connections per backend) while accepting thousands of client connections. This prevents the N×M connection explosion where N services × M cache nodes = overwhelming socket pressure on backends.
- **Trade-off accepted:** Twemproxy adds ~0.1–0.5 ms latency per request vs. direct client-side routing. Twitter accepted this in exchange for operational simplicity (one place to configure sharding topology) and connection efficiency.

**What they got wrong first:**
Twitter initially used direct client connections to Redis, which worked at small scale. As they grew to hundreds of services, the connection count to Redis nodes became untenable — a single Redis node was receiving 50,000+ concurrent connections, spending most of its time on connection management rather than command processing. Twemproxy solved the connection explosion.

**Key insight:** At large polyglot microservices scale, the operational cost of managing client-side routing configuration across hundreds of services outweighs the latency cost of a proxy. Twemproxy is a pragmatic trade-off for teams that cannot standardise on a single smart client library.

## Interview Perspective

### What the Interviewer Is Evaluating

For this specific problem, interviewers want to see:

1. **You understand WHY consistent hashing matters** — not just that it exists, but that modular hashing causes cascading cache misses on node changes, and consistent hashing limits remapping to ~1/N keys
2. **You can explain cache stampedes concretely** — including the XFetch algorithm or lease mechanism, not just "use a lock"
3. **You have internalised the eviction policy trade-offs** — knowing when LRU vs LFU is appropriate and that Redis uses approximate LRU for a reason
4. **You understand the write policy spectrum** — cache-aside, read-through, write-through, write-back — and can defend your choice
5. **You can reason about hot keys** — a single key receiving millions of requests/sec is a fundamentally different problem from total throughput

---

### Junior (L3-L4) Answer

**What they say:**
- "Use Redis with multiple nodes for sharding"
- "Use LRU eviction when memory fills up"
- "Use consistent hashing so adding nodes doesn't invalidate everything"
- "Use replication for high availability"

**What depth they reach:**
- Names consistent hashing and can draw a simple ring diagram
- Knows LRU eviction exists
- Describes cache-aside pattern correctly
- Mentions TTL expiry

**What they miss:**
- Does not explain virtual nodes or why they matter for load balancing
- Cannot explain how Redis implements approximate LRU (vs. true LRU)
- No discussion of stampede prevention
- Does not distinguish between write policies or their consistency implications
- Capacity math is rough or missing
- No mention of hot keys

---

### Senior (L5) Answer

**What they add:**

- **Virtual nodes:** "Without virtual nodes, three nodes might own 60%, 30%, 10% of the keyspace by chance. With 150 virtual nodes per node, standard deviation drops from ~18% to ~1.5%."
- **Approximate LRU:** "Redis doesn't do true LRU because touching the LRU list on every GET adds memory bandwidth. Instead, it samples N random keys and evicts the oldest. At sample=10, it's within 2% of true LRU."
- **Stampede prevention:** Describes the mutex lock approach and its failure modes (lock expiry, sleeping threads). Mentions stale-while-revalidate as an alternative.
- **Write policies:** Can clearly differentiate cache-aside (lazy) from write-through (eager) and explain when each is appropriate.
- **Hash tags:** Mentions that Redis hash tags (curly brace syntax) allow co-locating related keys on the same slot for multi-key operations.
- **Capacity math:** Explicitly works through QPS, storage, and server count with units.

---

### Staff (L6+) Answer

**What they drive to unprompted:**

- **XFetch algorithm:** Explains the probabilistic early recomputation formula, the beta parameter, and why it's superior to mutex locks for high-throughput keys.
- **Hot key strategies:** Proactively identifies that consistent hashing doesn't help with single-key hotspots. Proposes L1 in-process cache with short TTL, read replicas, or key fanning.
- **Facebook binlog invalidation:** Proposes pipeline-driven invalidation rather than application-code invalidation for reliability at scale.
- **Operational cost reasoning:** "Twemproxy adds 0.3 ms latency but saves significant operational overhead managing client configuration across hundreds of services — worth it if you can't standardise on a single smart client."
- **Cost analysis:** "At 1000x load, RAM cost dominates. NVMe SSD-backed L2 cache is ~50x cheaper per GB — tiered caching is essential to keep infrastructure costs from exploding."
- **Failure mode enumeration:** Network partition splits cluster; split-brain promotes replica with stale data; what does the application do? Serve stale? Error? Fall through to DB?
- **Gossip convergence time:** "Redis cluster gossip converges in O(log N) rounds with N nodes. At 1,000 nodes, that's ~10 gossip rounds at 100ms each = ~1 second to detect a failure. During that second, requests to the failed node time out and hit the DB."

### The 4-5 Mistakes Candidates Make On This Specific Problem

1. **Treating consistent hashing as solved without addressing hot keys.** Consistent hashing distributes the keyspace evenly, but it cannot distribute load evenly if one key receives 100x more traffic than others. Candidates who say "consistent hashing solves the distribution problem" without addressing hot keys will lose points at every seniority level.

2. **Proposing a mutex lock for stampede prevention without knowing its failure modes.** The lock approach has two dangerous edge cases: (a) the process holding the lock crashes after acquiring it — the TTL must match the maximum expected DB query duration, which is hard to bound; (b) under extreme load, all 5,000 waiting threads retry simultaneously when the lock expires, causing a secondary stampede. Candidates who propose mutex locks should also explain XFetch or SWR as superior alternatives.

3. **Confusing eviction and expiry.** TTL expiry removes a key at a scheduled time regardless of memory pressure. Eviction removes keys under memory pressure according to a policy. These are orthogonal mechanisms. Many candidates describe LRU eviction but conflate it with TTL — they are different paths through the code.

4. **Not considering replication lag during write operations.** Asynchronous replication means a read replica may serve a stale value for 10–50 ms after a write. For most use cases this is acceptable, but candidates must proactively state this trade-off rather than assuming replication is instantaneous.

5. **Not discussing write policies explicitly.** A candidate who designs a cache without choosing between cache-aside, write-through, write-back, and write-around has not completed the design. The write policy determines the consistency guarantee, the blast radius of cache failures, and the coupling between the cache and DB layers.
