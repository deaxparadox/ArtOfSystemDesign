## 1. What Is It? (Theory)

### Plain English Definition

A **Content Delivery Network (CDN)** is a globally distributed network of servers — called **edge servers** or **Points of Presence (PoPs)** — that store copies of your content closer to the people requesting it.

When a user in Tokyo requests your website's logo, they do not need to wait for a server in Virginia to respond. A CDN edge server sitting inside a Tokyo data center answers instead — in under 5ms instead of 200ms.

The core insight: **data moves at the speed of light through fiber, and the speed of light is slow over 10,000 km.** Physics is the enemy. CDNs fight physics by placing data closer to users.

### The Problem It Solves at Scale

Without a CDN, every byte of your content travels from your **origin server** to every user in the world:

```
User in Sydney ──── 150ms ──── User in London ──── 100ms ──── Your Origin (Virginia)
                                                               ^
                                                               |
                                            User in Tokyo ─── 200ms ─┘
```

Every user pays full cross-ocean round-trip cost. Worse, every request hits your origin:
- A viral image shared on Reddit can receive 500,000 requests in one hour
- At 100KB per image, that is **50 GB of bandwidth** your origin must serve
- At $0.09/GB (AWS egress), that single viral moment costs **$4,500 in bandwidth alone**
- Your origin server, sized for normal traffic, collapses under 100x load

With a CDN:
- The image is stored at 300+ edge locations worldwide
- A user in Sydney hits an edge server in Sydney: **< 5ms TTFB**
- Your origin serves the image **once** to the CDN, not 500,000 times
- Origin bandwidth cost: **< $1** (one fetch, propagated to edges)
- Origin CPU load: near zero for cached content

### Why It Was Invented

The web in the late 1990s was exploding. MIT professor Tim Berners-Lee's simple vision became a monster of traffic. Akamai was founded in 1998 by MIT researchers Tom Leighton and Daniel Lewin specifically to solve this: **when a celebrity like Victoria's Secret ran a live webcast in 1999 and their single server fell over, the world needed a better model.** Akamai served the Wimbledon website during peak demand shortly after. The CDN industry was born.

### Real-World Analogy

Think of a CDN like a **convenience store chain** (7-Eleven, CVS).

- Your origin server is the manufacturer's warehouse in New Jersey
- Without a CDN: every customer drives to New Jersey to buy a Coke
- With a CDN: a 7-Eleven stocks Coke 2 miles from every customer

The manufacturer (origin) only restocks the stores (edge) periodically. Customers always buy from the nearest store. The manufacturer's warehouse is never overwhelmed by individual customer demand.

When a product changes (new formula), the warehouses push out new stock and old stock expires — that is **cache invalidation**.

### Real Numbers Example

A global e-commerce site without CDN, measured at p95 TTFB by region for a 200KB product image:
- **Virginia (same region as origin):** 12ms
- **London:** 140ms
- **Sydney:** 290ms
- **Tokyo:** 210ms

Same site after enabling a CDN with global PoPs:
- **Virginia:** 8ms (edge in same region)
- **London:** 6ms (edge in London)
- **Sydney:** 5ms (edge in Sydney)
- **Tokyo:** 4ms (edge in Tokyo)

**Average global p95 TTFB: 280ms → 6ms.** Origin traffic drops by 95%.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step Request Mechanics

**First Request (Cache Miss):**

```
1. User types example.com/image.png in browser
2. Browser resolves DNS: "what IP is cdn.example.com?"
3. CDN's authoritative DNS server checks user's IP geolocation
4. DNS returns IP of nearest edge PoP (e.g., PoP in Frankfurt for EU user)
5. Browser opens TCP connection to Frankfurt edge server
6. Browser sends HTTP GET /image.png
7. Frankfurt edge checks its local cache: MISS (not cached yet)
8. Frankfurt edge opens connection to origin server (Virginia)
9. Frankfurt fetches /image.png from origin (150ms cross-Atlantic RTT)
10. Frankfurt stores the response in its local cache
11. Frankfurt sends response to user
12. User receives image
```

**Subsequent Requests (Cache Hit):**

```
1. Any EU user requests example.com/image.png
2. DNS routes to Frankfurt edge
3. Frankfurt checks local cache: HIT
4. Frankfurt sends cached response immediately
5. User receives image in < 5ms
6. Origin server is never contacted
```

```
                                  └──────────────────┘
```

**Key observation:** With **tiered caching (shield PoP)**, even on a cache miss the outer edges fetch from a central shield PoP, not directly from origin. Only the shield fetches from origin. This reduces origin traffic by an additional 10-50x on top of regular caching.

### Routing Mechanisms

CDNs use three routing strategies, often combined:

**1. GeoDNS**
The CDN's authoritative DNS server returns a different IP based on the geographic location of the DNS resolver making the query. Fastest to implement, accurate to within ~50 km of a major PoP.

**Limitation:** GeoDNS sees the *resolver's* IP (often ISP's recursive resolver), not the user's actual IP. A Comcast resolver in New Jersey might serve users across the US East Coast.

**2. Anycast BGP Routing**
Multiple edge PoPs advertise the **same IP prefix** into the global BGP routing table. Internet routers naturally route packets to the "nearest" PoP in terms of BGP hop count. No DNS magic required — the network itself routes you there.

```
                Same IP: 104.16.1.1
                ┌───────────────────────────────────┐
                │                                   │
        PoP: 104.16.1.1                    PoP: 104.16.1.1
          (Frankfurt)                        (Singapore)
                │                                   │
     EU traffic ─┘                       Asia traffic ─┘
     routed by BGP                       routed by BGP
```

Cloudflare uses anycast for its entire network. Every PoP in its 310+ city network answers for the same IP space. This also makes DDoS mitigation trivial: traffic is absorbed globally instead of hitting a single IP.

**3. RTT-Based Load Balancing**
After initial routing, CDNs like Akamai measure actual real-user RTT to pick the *fastest* PoP, not just the geographically nearest one. A PoP 100 km away with heavy congestion loses to a PoP 500 km away on a clean fiber path.

### Cache Hit vs Miss Math

Understanding **cache hit ratio** is critical. CDN cost and performance both depend on it.

**Hit ratio** = (requests served from cache) / (total requests)

- Hit ratio 90%: origin sees 10% of traffic
- Hit ratio 99%: origin sees 1% of traffic
- Hit ratio 99.9%: origin sees 0.1% of traffic

What drives hit ratio:
- **TTL length**: longer TTL = more hits, but stale content risk
- **Object popularity**: a viral image has 99.99% hit ratio; a user profile page has ~0%
- **URL uniqueness**: `image.png?user_id=12345` creates N unique cache keys — catastrophic for hit ratio
- **Vary header**: `Vary: Accept-Encoding` creates separate cache entries per encoding — necessary but doubles storage
- **Cache key normalization**: `image.png?foo=1&bar=2` vs `image.png?bar=2&foo=1` are the same object but different cache keys without normalization

**Real numbers from production:**
- Static asset CDN (images, JS, CSS): typical hit ratio **95-99.9%**
- API gateway CDN with short TTLs: typical hit ratio **40-70%**
- Personalized content passed through CDN: hit ratio **< 5%** — almost entirely cache misses, and you are paying CDN egress for no benefit

### Cache Invalidation Mechanisms

1. **TTL Expiry (passive)**: Set `Cache-Control: max-age=86400` (24 hours). CDN serves stale content until TTL expires, then fetches fresh. Zero API calls needed, zero operational complexity. The right choice for content that can be slightly stale.

2. **Purge API (active)**: Issue an API call to the CDN to immediately delete cached objects by URL, tag, or prefix. Cloudflare: `DELETE /zones/{zone_id}/purge_cache`. CloudFront: create an invalidation request. This is fast (< 30 seconds globally for Cloudflare) but costs money and operational effort.

3. **Cache-busting via URL versioning (immunity from stale)**:
   ```
   /assets/app.js?v=abc123      ← unique hash per build
   /assets/app.abc123.js        ← hash in filename
   ```
   Content never expires because each deployment creates a new URL. Old URLs naturally drain from cache and clients always use new URLs. **This is the superior strategy for JS/CSS assets.** Zero purge API calls needed.

4. **Stale-while-revalidate**: Serve stale content immediately while fetching fresh content in the background. `Cache-Control: max-age=60, stale-while-revalidate=600`. Users never wait for a fetch; content is at most 10 minutes stale. Ideal for news feeds, product listings.

### Key Protocols

- **TLS Termination at Edge**: CDN terminates TLS at the nearest edge, reducing TLS handshake RTT for users. Origin-to-edge uses a persistent, pre-warmed TLS connection. This alone saves 100-300ms on first load.
- **HTTP/2 and HTTP/3**: CDN edges speak HTTP/2 or HTTP/3 (QUIC) to clients even if your origin only speaks HTTP/1.1. This is a free multiplexing win.
- **Brotli/Gzip Compression**: CDN compresses responses at the edge; some (Shopify's CDN via Cloudflare) compress automatically. Reduces payload 60-80%.
- **TCP Connection Reuse**: Edge server maintains persistent connections to origin. User pays no origin TCP handshake cost even on a cache miss.

### Misconceptions

**❌ Misconception: "CDN is just for big companies with global audiences."**
**✅ Reality:** A CDN improves performance even for regional deployments. If your origin is in us-east-1 and your users are in us-west-2, that is 70ms RTT vs 3ms from a CDN PoP on the west coast. The threshold for benefit is a single-digit percentage global user split.

**❌ Misconception: "Cache invalidation is instant."**
**✅ Reality:** Global propagation of a cache purge takes 10-60 seconds on fast CDNs (Cloudflare: ~30s, CloudFront: up to 15 minutes). Plan your deploy strategy around this. URL versioning sidesteps the problem entirely.

**❌ Misconception: "A CDN handles dynamic content well."**
**✅ Reality:** Dynamic content (personalized responses, auth-gated pages, real-time data) has near-zero cache hit ratio. Passing it through a CDN adds latency (one extra network hop) and cost without caching benefit. Use CDNs for dynamic content *only* if you need DDoS protection, TLS offload, or edge routing logic.

**❌ Misconception: "All CDNs are the same."**
**✅ Reality:** CDN PoP density, routing algorithm, cache storage size, and edge compute capabilities vary 10x between providers. Cloudflare has 310+ PoPs; a budget CDN might have 30. This matters enormously for users in Southeast Asia, Latin America, or Africa.

## 3. Real-World Architecture Examples

### Netflix — Open Connect (Custom CDN)

**Scale trigger:** By 2011, Netflix streaming accounted for ~30% of US peak internet traffic. Akamai and Limelight costs were hundreds of millions of dollars per year and Netflix had zero control over quality.

**Decision:** Netflix built its own CDN called **Open Connect** in 2012. Instead of building PoPs in data centers, Netflix placed **Open Connect Appliances (OCAs)** — custom FreeBSD servers with 100-250 TB of flash storage each — *inside ISP networks*, free of charge to qualifying ISPs (who benefit from not having Netflix traffic traverse expensive peering links).

**How it works:**
- Each OCA is pre-filled nightly via a **proactive push model** — Netflix predicts what content will be popular in each region based on viewing history and pre-loads it before users request it
- When a Netflix user in Tokyo hits play, their traffic goes to an OCA sitting *inside their ISP's network* — effectively 0ms CDN distance
- **95% of Netflix global traffic** flows through direct ISP-embedded OCAs; the remaining 5% goes through regional data centers
- A 4K Netflix title is ~20 GB. A single cold miss would cost the ISP 20 GB of transit bandwidth. Pre-loading eliminates cold misses.

**Key technical detail:** Netflix engineers implemented `sendfile()` (zero-copy) on FreeBSD for the OCAs. This bypasses user-space entirely — the kernel reads from disk and sends to network without CPU involvement. OCAs stream multiple gigabits per second per machine with minimal CPU load.

**What they got wrong first:** Early Open Connect used a pull model like traditional CDNs. Cold misses during peak evening hours (8-11pm) overwhelmed origin. They switched to proactive push in 2013, pre-filling OCAs during off-peak hours.

**Reference:** [Netflix Open Connect Overview PDF](https://openconnect.netflix.com/Open-Connect-Overview.pdf)

---

### Shopify — Cloudflare-Backed Multi-Tenant CDN

**Scale:** 2 million+ merchants globally, handling flash sales (Supreme, Kylie Cosmetics) with traffic spikes of 100,000+ requests/second in under a minute.

**Decision:** Shopify uses Cloudflare as its CDN layer but adds layers of control:
- Until 2023, static assets were served from `cdn.shopify.com` domain
- In 2023, Shopify migrated CDN URLs to the merchant's own domain (`example.com/cdn/shop/files/...`) — this improves SEO, reduces DNS lookup cost, and enables same-origin caching
- Shopify's CDN (via Cloudflare) automatically compresses assets with Brotli, serves via HTTP/3, and minifies JS/CSS
- Asset URLs include a content hash: `/assets/application.abc123.css` — cache-busting built in, 1-year `Cache-Control` headers

**Scale trigger for CDN strategy:** During flash sales (Supreme drops), a single product page generates 800,000+ requests in the first minute. Without CDN caching, Shopify's origin would need to handle all 800,000 requests. With CDN caching of the static page shell + assets, origin sees < 5% of that traffic.

**What they got wrong first:** Early Shopify used query-string-based versioning (`?v=123`) which some CDNs strip or handle inconsistently. They moved to path-based hashing for deterministic cache behavior.

---

### Cloudflare — Anycast-First Architecture

**Scale:** 3 trillion requests per day, 310+ cities, DDoS attacks up to 71 million rps (observed 2023).

**Decision:** Cloudflare made an unusual architectural choice: **every server in every PoP runs the full software stack** (CDN, WAF, DDoS mitigation, Bot Management, Workers compute). There is no routing tier that hands off to a specialized CDN tier. This is the opposite of Akamai's architecture where different PoPs serve different roles.

**Why this matters:**
- No single-tier dependency — if one PoP is overwhelmed, BGP reroutes to the next without any application-layer failover
- WAF and DDoS protection run at wire speed at every edge, not at a central scrubbing center
- Latency for security inspection is zero — it is in-path, not out-of-band

**Tiered Cache (Shield):** Cloudflare allows customers to designate a "cache reserve" or use the tiered cache feature. Outer PoPs check a regional shield PoP before hitting origin. This reduces origin requests by an additional 60-70% on top of standard caching.

**Reference:** [Cloudflare CDN Reference Architecture](https://developers.cloudflare.com/reference-architecture/architectures/cdn/)

---

### Fastly — Instant Purge as a Core Feature

**Decision differentiation:** Fastly built its CDN around the insight that **cache invalidation latency** is the primary reason companies keep TTLs short (which kills hit ratios). Fastly's "Instant Purge" propagates a purge globally in **< 150ms** (compared to CloudFront's up to 15 minutes). This unlocked a new use case: **CDN-cached HTML pages with frequent updates**.

Media companies (The Guardian, BuzzFeed, Financial Times) can cache their homepage HTML at Fastly with a 10-second TTL but use Instant Purge to push a new cache after each article publish. Hit ratio of 95%+ even on HTML pages that update every few minutes.

**What broke:** June 8, 2021. A software bug introduced in May 2021 was triggered when a single customer pushed a configuration update. **85% of Fastly's network returned errors for 49 minutes.** The Guardian, Reddit, Amazon, GitHub, BBC, PayPal all went offline or degraded. Root cause: a latent configuration parsing defect in Varnish configuration language (VCL) processing that caused edge nodes to crash and the cascading failure spread through the shared configuration service.

**Lesson:** CDN is a **single point of failure for your entire infrastructure** if you have no fallback. Organizations that had a second CDN (or a direct origin fallback with DNS TTL < 60s) recovered in minutes. Organizations with only Fastly were down for 49 minutes.

**Reference:** [Fastly Outage Post-Mortem (June 8, 2021)](https://www.fastly.com/blog/summary-of-june-8-outage)

### Design Questions to Ask Before Starting

1. **What is the cache hit ratio target?** If your content is highly dynamic/personalized, a CDN might not help with performance at all.
2. **What is the geographic distribution of your users?** If 95% of users are in one city, a CDN is less critical than if users span continents.
3. **What is the content type ratio?** 90% static assets? CDN is a slam dunk. 90% API calls? You need to evaluate carefully.
4. **What are your cache invalidation requirements?** Real-time data? You need short TTLs or Instant Purge. Immutable assets? 1-year TTL with URL versioning.
5. **Do you have a multi-CDN or fallback strategy?** Single CDN = single point of failure (see: Fastly 2021).
6. **Do you need DDoS protection?** CDNs absorb attack traffic at their network edge — this is often the *primary* reason to use them, separate from caching.
7. **What is your origin's egress cost?** AWS egress to internet: $0.09/GB. CDN egress: $0.01-0.04/GB. At > 10 TB/month, CDN saves real money.

### Scale Evolution

**1K → 10K users/month (startup)**
- Single origin server (EC2 or DigitalOcean)
- No CDN needed — latency is acceptable, cost is negligible
- Exception: if you have global users on day one, add Cloudflare free tier immediately
- Decision: serve static assets from the same server or S3 with CloudFront

**10K → 100K users/month**
- Add Cloudflare free/pro tier or CloudFront
- Cache static assets (images, CSS, JS) with long TTL + URL versioning
- Do not yet cache HTML pages — complexity not worth it
- Origin egress cost starts mattering (~$50-200/month saved)
- Decision: route `assets.example.com` through CDN, keep `api.example.com` direct

**100K → 1M users/month**
- CDN becomes critical infrastructure, not optimization
- Implement tiered caching (shield PoP) to protect origin
- Add CDN-level WAF and DDoS protection
- Measure cache hit ratio per content type; optimize TTLs
- Evaluate: cache API responses for non-personalized endpoints (product catalog, public prices) with short TTL (60-300 seconds)
- Decision: multi-CDN or fallback origin DNS for resilience

**1M → 100M users/month**
- CDN is your first line of defense, not your origin
- Cache hit ratio must be > 95% for static content, > 60% for semi-dynamic content
- Consider origin shield in each major region (not just one central shield)
- Evaluate edge compute (Cloudflare Workers, Fastly Compute) for auth, routing, A/B testing at edge — latency for these operations drops from 50ms to < 1ms
- Multi-CDN with traffic split: 70% primary, 30% secondary. Instant failover on outage.
- Decision: build or buy monitoring for CDN cache hit ratio, TTFB per region, origin error rate

## 5. Code / Implementation Perspective

### Python: Simulated CDN Edge Cache

```python
import hashlib
import time
from dataclasses import dataclass, field
from typing import Optional
import httpx  # pip install httpx

@dataclass
class CacheEntry:
    body: bytes
    content_type: str
    cached_at: float
    ttl: int  # seconds
    etag: str

    def is_stale(self) -> bool:
        return time.time() - self.cached_at > self.ttl

    def age(self) -> int:
        return int(time.time() - self.cached_at)


class EdgeCache:
    """
    Minimal CDN edge cache simulation.
    Implements: TTL expiry, conditional GET (ETag), stale-while-revalidate.
    """

    def __init__(self, origin_url: str, max_entries: int = 10_000):
        self.origin_url = origin_url
        self.cache: dict[str, CacheEntry] = {}
        self.max_entries = max_entries
        self.stats = {"hits": 0, "misses": 0, "revalidations": 0}

    def _cache_key(self, path: str, vary_headers: dict) -> str:
        """Normalize cache key. Vary headers (e.g., Accept-Encoding) create separate entries."""
        key_data = path + ":".join(f"{k}={v}" for k, v in sorted(vary_headers.items()))
        return hashlib.sha256(key_data.encode()).hexdigest()

    def _parse_ttl(self, cache_control: str) -> int:
        """Parse max-age from Cache-Control header."""
        for directive in cache_control.split(","):
            directive = directive.strip()
            if directive.startswith("max-age="):
                try:
                    return int(directive.split("=")[1])
                except ValueError:
                    pass
        return 0  # Not cacheable

    def _is_cacheable(self, cache_control: str, status_code: int) -> bool:
        if status_code not in (200, 203, 204, 206, 300, 301, 410):
            return False
        if "no-store" in cache_control or "private" in cache_control:
            return False
        return "max-age=" in cache_control or "s-maxage=" in cache_control

    async def get(self, path: str, request_headers: dict = None) -> tuple[bytes, dict]:
        request_headers = request_headers or {}
        vary_keys = {k: v for k, v in request_headers.items()
                     if k.lower() in ("accept-encoding", "accept-language")}
        key = self._cache_key(path, vary_keys)
        entry = self.cache.get(key)

        if entry and not entry.is_stale():
            self.stats["hits"] += 1
            return entry.body, {
                "X-Cache": "HIT",
                "Age": str(entry.age()),
                "Content-Type": entry.content_type,
            }

        # Cache miss or stale — fetch from origin
        self.stats["misses"] += 1
        headers = {}
        if entry:  # Stale: use conditional GET
            headers["If-None-Match"] = entry.etag
            self.stats["revalidations"] += 1

        async with httpx.AsyncClient() as client:
            resp = await client.get(f"{self.origin_url}{path}", headers=headers)

        if resp.status_code == 304 and entry:
            # Origin confirmed: still fresh. Reset TTL.
            entry.cached_at = time.time()
            return entry.body, {"X-Cache": "REVALIDATED", "Age": "0"}

        cache_control = resp.headers.get("Cache-Control", "")
        ttl = self._parse_ttl(cache_control)

        if self._is_cacheable(cache_control, resp.status_code) and ttl > 0:
            if len(self.cache) >= self.max_entries:
                # Evict oldest entry (LRU would be better in production)
                oldest = min(self.cache, key=lambda k: self.cache[k].cached_at)
                del self.cache[oldest]

            self.cache[key] = CacheEntry(
                body=resp.content,
                content_type=resp.headers.get("Content-Type", "application/octet-stream"),
                cached_at=time.time(),
                ttl=ttl,
                etag=resp.headers.get("ETag", ""),
            )

        return resp.content, {"X-Cache": "MISS", "Age": "0"}

    def hit_ratio(self) -> float:
        total = self.stats["hits"] + self.stats["misses"]
        return self.stats["hits"] / total if total > 0 else 0.0
```

### Cache-Control Header Strategy (Language-Agnostic)

```
Content Type                | Cache-Control Header                          | Strategy
----------------------------|-----------------------------------------------|------------------
Immutable assets (JS/CSS)   | max-age=31536000, immutable                   | URL versioning
Images (versioned URLs)     | max-age=31536000, immutable                   | URL versioning
HTML pages                  | max-age=0, must-revalidate                    | No CDN caching
API responses (public data) | max-age=60, s-maxage=300                      | Short TTL
API responses (private)     | private, no-store                             | Never cache
Video segments              | max-age=3600, s-maxage=86400                  | CDN long, browser short
```

Note: `s-maxage` overrides `max-age` **for shared caches (CDN)**. Set `max-age=60` (browser) and `s-maxage=3600` (CDN) independently.

### Nginx Configuration Example (Origin with CDN-Aware Headers)

```nginx
# /etc/nginx/sites-available/example.conf

server {
    listen 80;
    server_name origin.example.com;

    # Immutable static assets — served from /static/ path
    location /static/ {
        root /var/www;
        add_header Cache-Control "public, max-age=31536000, immutable";
        add_header Vary "Accept-Encoding";
        etag on;
        gzip_static on;
    }

    # API: short CDN TTL, never cache private data
    location /api/v1/public/ {
        proxy_pass http://app_servers;
        add_header Cache-Control "public, max-age=30, s-maxage=300, stale-while-revalidate=600";
        add_header Vary "Accept-Encoding, Accept";
    }

    # User-specific API: never cache at CDN
    location /api/v1/user/ {
        proxy_pass http://app_servers;
        add_header Cache-Control "private, no-store";
    }

    # HTML pages: let browser cache briefly, CDN must revalidate
    location / {
        proxy_pass http://app_servers;
        add_header Cache-Control "public, max-age=0, must-revalidate";
        add_header Surrogate-Control "max-age=3600";  # Fastly/Varnish read this
    }
}
```

### Cloudflare Cache Purge via API (Python)

```python
import httpx

async def purge_cloudflare_cache(zone_id: str, api_token: str, urls: list[str]) -> bool:
    """Purge specific URLs from Cloudflare cache. Propagates globally in < 30s."""
    async with httpx.AsyncClient() as client:
        resp = await client.post(
            f"https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache",
            headers={"Authorization": f"Bearer {api_token}", "Content-Type": "application/json"},
            json={"files": urls},
        )
    result = resp.json()
    return result.get("success", False)

# Usage: called from deploy pipeline after publishing new article

    zone_id="abc123",
    api_token="your-token",
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **CDN (global PoP network)** | Static content, global user base, DDoS exposure | Cost vs performance; complexity of invalidation | Netflix, Shopify, GitHub, The Guardian |
| **In-process memory cache (Redis/Memcached at origin)** | Dynamic data, same-region users, personalized content | No geographic distribution; still origin-bound | All major apps use this *alongside* CDN |
| **Multi-region origin replication** | Data locality, regulatory (GDPR), read-heavy workloads | Write complexity, replication lag, cost | Stripe, Google (Spanner), Cockroach Labs |
| **Reverse proxy with local caching (nginx)** | Single-region, cost-sensitive, on-prem | No geographic distribution; single PoP only | Self-hosted applications, internal tools |
| **Edge compute (Cloudflare Workers, Lambda@Edge)** | Business logic at the edge (auth, routing, A/B test) | Code complexity; stateless constraints; 128MB RAM limit | Cloudflare itself, large e-commerce |
| **P2P content delivery** | Large file distribution, BitTorrent-style | Complex client integration; privacy concerns | Software downloads (Blizzard, Steam), academic |
| **Service mesh + local caches** | Internal microservice traffic, no public internet | Not applicable for user-facing CDN use cases | Uber, Lyft (internally) |

### Opinionated Recommendation

For user-facing web applications: **CDN is not optional at scale — it is table stakes.** The question is not "CDN vs no CDN" but "which CDN strategy."

- Use a CDN for all static assets from day one, even at 1K users. The free tier of Cloudflare costs nothing and reduces your origin load immediately.
- Do **not** try to cache dynamic, personalized content at the CDN unless you have a clear hit ratio model showing > 50% hit rate. Below 50% hit rate, CDN for dynamic content is a cost center, not a performance win.
- The biggest miss I see in system design interviews: engineers add a CDN box to every diagram without explaining *what* is being cached, *what TTL* is appropriate, and *how invalidation works*. Adding a CDN without cache strategy is worse than no CDN — it gives false confidence.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Latency reduction:** p95 TTFB from 200-300ms (cross-ocean) to 3-8ms (local edge) — a 30-50x improvement for global users. This is physics, not engineering: nothing beats serving content from 5 km away.
- **Origin offload:** CDN absorbs 80-99% of origin traffic for well-cached content. Your origin infrastructure can be sized for the remaining 1-20%, reducing compute costs 5-10x.
- **DDoS resilience:** CDN edge absorbs volumetric attacks (1+ Tbps) that would instantly saturate a typical origin uplink. Cloudflare absorbed 71 million rps in 2023 — no origin server survives that.
- **Bandwidth cost reduction:** CDN egress is 2-10x cheaper than cloud provider egress (AWS: $0.09/GB; Cloudflare: $0/GB on their network, $0.05/GB egress to internet on paid plans). At 100 TB/month, this is $5,000-$8,000/month saved.
- **TLS/HTTP/2 offload:** CDN handles TLS termination and HTTP/2 multiplexing even for origins that do not support it, providing a free protocol upgrade.
- **Global availability:** Even if your origin has a partial outage, CDN can serve stale (cached) content to users — **stale-if-error** behavior provides graceful degradation.

### Costs & Limitations

- **Operational complexity:** Cache invalidation is hard. Wrong TTLs mean stale content reaching users or cache bypasses that destroy hit ratio. Every cache strategy decision is a trade-off.
- **Cold start on new PoPs:** First request to any edge node for a new URL pays full origin RTT + CDN overhead (~10-30ms extra). This is painful for low-traffic sites where every URL is a cold start.
- **Vendor lock-in:** CDN-specific headers (`Surrogate-Control`, `Fastly-Surrogate-Key`, Cloudflare Cache Rules) create migration friction. Budget 2-4 weeks to migrate between CDN providers.
- **Cost for dynamic content:** CDN request pricing ($0.01/10K requests) adds up fast if your hit ratio is low. At 90% miss rate, you pay CDN cost for 0 performance gain.
- **Security risk — cache poisoning:** Misconfigured CDN + ambiguous HTTP request parsing can result in attackers poisoning cached content served to all users. This has caused multiple major security incidents.
- **Debugging difficulty:** Production issues become harder to reproduce when behavior differs between edge nodes and origin. "It works on origin, not on CDN" is a real debugging category.

### The Core Tension

**Freshness vs. Performance.** The longer you cache, the better the performance. The shorter you cache, the fresher the content. There is no configuration that optimally satisfies both simultaneously. Every CDN strategy is a negotiated position on this axis.

URL versioning + long TTL is the only escape hatch from this tension, and it only works for assets you control (JS, CSS, images). For HTML, API responses, and user-generated content, you are always making a trade-off.

### My Recommendation

**Use Cloudflare by default** (free tier is genuinely excellent). Configure it on day one, not when you have a traffic problem. Add URL versioning for all static assets immediately — this is 2 hours of work and eliminates an entire category of stale content bugs forever.

**Set conservative TTLs on HTML pages** (`Cache-Control: max-age=0, must-revalidate`) until you have a tested invalidation strategy. Stale HTML served to users causes visible bugs (wrong prices, missing features, broken auth) that are hard to diagnose.

**Do not cache API responses at the CDN** unless you can articulate the exact TTL, the exact URLs being cached, and the exact invalidation strategy. I have seen teams accidentally cache user-specific data at the CDN and serve one user's data to another user. This is a data breach.

## 9. Failure Modes — What Goes Wrong

### Stale Content Served to Users

**Trigger:** TTL set too long; cache invalidation failed silently; deploy pushed without URL versioning; CDN purge API returned 200 but failed to propagate.

**Symptoms:** Users see old prices, old JS bundles (causing JS errors), old HTML with missing features. Support tickets spike post-deploy. Errors are inconsistent — some users (cache miss) see new version, others (cache hit) see old version.

**Detection:** Deploy canary with `Cache-Control: no-store` and compare responses. Monitor for elevated JS error rates post-deploy. Add `X-Cache-Version: <deploy-sha>` response header and alert on version mismatch.

**Recovery:** Issue CDN cache purge API for affected URLs. Verify propagation by testing from multiple geographic locations (use curl with `--resolve` to hit different PoPs). Add URL versioning to prevent recurrence.

**Real Example:** In 2018, a major e-commerce site accidentally cached a promotional price (`$0.00`) on a product page at a CDN with a 1-hour TTL. For 47 minutes, all users saw a free price. The company honored the orders placed during that window — a 6-figure cost. Root cause: a deploy script that updated the HTML cache key but not the JSON API cache key.

---

### CDN Provider Outage (Cascade Failure)

**Trigger:** CDN provider software bug, BGP route leak, configuration propagation error, upstream transit provider failure.

**Symptoms:** 5xx errors or timeouts globally or in specific regions. DNS resolution still succeeds but HTTP requests fail at edge. Traffic spike to origin if CDN fails open (passes through) rather than failing closed (returns error).

**Detection:** Synthetic monitoring from multiple geographic regions using a tool like Pingdom or ThousandEyes. Alert on TTFB > 5s or HTTP error rate > 1% from edge nodes. Check CDN provider status page (Cloudflare Status, Fastly Status).

**Recovery:** If CDN fails open (origin reachable): do nothing — origin serves traffic at degraded performance. If CDN fails closed (returns 503): switch DNS to point directly at origin (if origin can handle traffic) or to backup CDN. Pre-position `CNAME` or `A` records for the origin in your DNS provider with TTL < 60s so failover propagates in < 1 minute.

**Real Example:** Fastly outage, June 8, 2021. A customer configuration change triggered a dormant bug that cascaded across 85% of Fastly's network. Reddit, GitHub, AWS Console, The Guardian, Amazon, BBC — all offline for 49 minutes. Teams with a second CDN or direct origin fallback (low DNS TTL) recovered within 5 minutes.

---

### Cache Poisoning Attack

**Trigger:** Attacker finds a discrepancy between how the CDN and origin parse HTTP requests (path parameters, headers, request smuggling). Attacker crafts a request that causes the CDN to cache a malicious response and serve it to subsequent legitimate users.

**Symptoms:** Users receive unexpected content (malicious JS injected, wrong page served, credentials stolen). Error rates may not spike since the cache is serving a valid-looking HTTP 200. Detected via content integrity monitoring.

**Detection:** Add response body hashing for critical pages. Monitor for unexpected changes in cached page content. Use Content Security Policy (CSP) to detect injected scripts. Regular security audits of CDN configuration, especially for `Vary`, `X-Forwarded-*`, and custom header handling.

**Recovery:** Immediately purge the poisoned cache keys. Identify and fix the header parsing discrepancy (usually involves normalizing `Vary` headers and removing unkeyed headers from cache key consideration). Audit CDN cache key configuration with a security engineer.

**Real Example:** Researcher James Kettle (PortSwigger) demonstrated cache poisoning against multiple major CDN providers in 2018-2020. Several large e-commerce sites were vulnerable to having their CDN-cached homepage replaced with attacker-controlled content via crafted `X-Forwarded-Host` headers that the CDN included in cache key decisions incorrectly.

---

### Cache Stampede (Thundering Herd on Origin)

**Trigger:** A high-traffic cached object expires simultaneously across multiple edge nodes (TTL-synchronized expiry). All nodes simultaneously miss and simultaneously request the same object from origin. At 10,000 rps to an object, when TTL expires, origin receives 10,000 requests at once.

**Symptoms:** Origin CPU spike to 100% at precise TTL intervals. Origin database overwhelmed. Application errors correlated with cache TTL timing, not random.

**Detection:** Graph origin request rate over time — cache stampede shows as periodic spikes at TTL intervals. Correlate with CDN cache hit ratio dropping to zero momentarily.

**Recovery (mitigation):** 
1. **Probabilistic Early Expiration (PER):** Instead of expiring at TTL exactly, randomize expiry within a window. `actual_ttl = configured_ttl - random(0, 0.1 * configured_ttl)`. First edge to expire fetches fresh; others still hit cache.
2. **Request collapsing:** CDN feature where multiple simultaneous misses for the same object result in a single origin fetch. Cloudflare, Fastly, and Akamai all support this. Enable it.
3. **Stale-while-revalidate:** Serve stale content while revalidating in background. Eliminates the expiry window entirely.

**Real Example:** A major news site saw origin database crash every 5 minutes at exactly their article cache TTL. After adding `stale-while-revalidate=300` to their CDN headers, origin database load dropped 70% and the periodic crashes stopped.

## 10. When To Use vs. When To Avoid

### Use When

**✅ Your content is geographically distributed globally:** Users in Asia experiencing 300ms p99 TTFB on a US-hosted origin is a CDN problem. The fix is a CDN, not bigger servers.

**✅ You serve high-traffic static assets:** Images, JavaScript bundles, CSS files, video segments, and software downloads are ideal CDN candidates. They are cacheable, immutable or versioned, and consumed at massive scale. These assets can and should have 1-year TTLs with URL versioning.

**✅ You need DDoS protection:** Even if you have no global users and no caching benefit, a CDN absorbs DDoS traffic at the network edge. Your origin never sees the attack packets. This is worth CDN cost even at low traffic volumes if you are a likely target.

**✅ Your origin bandwidth/egress cost is significant:** When serving > 10 TB/month, CDN egress pricing (1-4 cents/GB) versus origin cloud egress pricing (8-9 cents/GB) saves 2-8x. At 100 TB/month, this is $5,000-$8,000/month.

**✅ You need TLS termination and HTTP/2 without changing your origin:** CDN gives you these protocol upgrades in an afternoon. Re-architecting your origin for the same benefit takes weeks.

### Do NOT Use When

**❌ Your content is highly personalized and cannot be cached:** User dashboards, bank balances, shopping carts, real-time trade data — these have near-zero cache hit ratios. Routing them through a CDN adds 5-20ms of extra latency (one additional network hop) and CDN request fees with zero caching benefit. Use the CDN for your static shell and fetch dynamic content directly from origin via API.

**❌ You need strict real-time data consistency:** If your users must see changes within seconds (financial trading, live inventory, real-time collaboration), CDN TTLs and propagation delays make CDN caching unusable. Even "Instant Purge" (< 150ms) is too slow for sub-second consistency requirements.

**❌ Your users are all in one region close to your origin:** If 95% of users are in the same city as your data center, CDN adds complexity with minimal latency benefit. A regional cache layer (Redis) is more appropriate.

**❌ Your content contains sensitive, user-specific data and you haven't fully audited your cache keys:** The risk of accidentally caching private data and serving it to wrong users is real and has caused data breaches. Do not add CDN to authenticated/personalized pages without a thorough security review of caching headers.

### The #1 Mistake Engineers Make

**⚠️ Setting long TTLs on dynamic/personalized content without URL versioning or a cache invalidation strategy.**

This is the most common and damaging CDN mistake. The pattern:
1. Engineer adds CDN to speed up the site
2. Sets `Cache-Control: max-age=3600` on all responses globally (easy to do)
3. After a deploy, users see stale HTML/prices/content for up to an hour
4. Team loses trust in CDN, sets TTL to 0 (eliminating all caching benefit)
5. CDN is now purely a pass-through with added latency and cost

**Fix:** Start with explicit, content-type-aware cache headers. Never use a blanket TTL rule. Use URL versioning for assets. Stale HTML should have `max-age=0` or a tested purge strategy before you consider caching it.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design YouTube / Netflix — how do you serve video content to millions of users globally?"
- "Design a CDN from scratch."
- "How would you reduce the latency of serving static assets to users in Southeast Asia when your origin is in Virginia?"
- "Your e-commerce site goes viral and origin servers crash. What do you do?"
- "How does cache invalidation work at scale? What are the trade-offs?"
- "Design the image serving infrastructure for Instagram."
- "How does Cloudflare route user traffic to the nearest edge node?"

### What the Interviewer Evaluates

1. **Do you know the difference between a cache hit and a cache miss, and can you quantify the performance impact?**
2. **Do you understand the cache-freshness trade-off and can you articulate it for a specific use case?**
3. **Can you identify which content types are CDN-cacheable vs which are not?**
4. **Do you know real-world numbers?** (latency cross-continent, CDN hit ratios, TTL values)
5. **Can you reason about failure modes?** CDN outage, cache poisoning, stale content — what is the impact and mitigation?
6. **Senior+: Do you think about multi-CDN, origin protection, and cache key design?**

### Questions YOU Should Ask Before Answering

These demonstrate senior-level thinking:
- "What is the ratio of static content to dynamic content in this system?"
- "What are the geographic user distribution requirements? Global or regional?"
- "What are the freshness requirements? Can users see data that is 60 seconds stale?"
- "Do we have DDoS concerns, or is this purely a performance optimization question?"
- "What is the expected peak traffic and what is the origin capacity?"
- "Are there regulatory or data residency requirements that affect where content can be cached?"

### Junior (L3-L4) Answer Example

**Question:** "How would you use a CDN to speed up a global e-commerce site?"

> "I would put a CDN in front of the origin server. Static assets like images, CSS, and JavaScript would be cached at CDN edge servers globally. When a user in Tokyo requests the site, they hit a Tokyo edge server instead of a server in Virginia, so latency drops from ~200ms to ~5ms. The CDN caches the files based on Cache-Control headers. When content changes, I can use the CDN's purge API to invalidate the cache."

This is correct but shallow. It covers the what but not the how, why, or trade-offs.

### Senior (L5) Answer Example

> "I'd start by separating content by cacheability. Static assets — JS bundles, CSS, images — get served from the CDN with 1-year TTLs and content-hash URLs (e.g., `app.a1b2c3.js`). Since the URL changes on every deploy, we never need to purge the cache — old URLs drain naturally. These should have hit ratios of 99%+.
>
> For HTML pages, I'd set `max-age=0, must-revalidate` until we have a validated purge strategy. Caching HTML without a purge mechanism is a recipe for stale-content incidents post-deploy.
>
> For the product catalog API — public, non-personalized data — I'd set `s-maxage=300, stale-while-revalidate=600`. The CDN caches for 5 minutes, serves stale during revalidation. Hit ratio 70-90% here.
>
> For cart, checkout, and user-specific data, `Cache-Control: private, no-store`. These never touch the CDN cache.
>
> I'd also implement tiered caching (shield PoP) to ensure origin only gets hit by a single region's requests on a miss, not all 300 edge PoPs simultaneously.
>
> For reliability, I'd run Cloudflare as primary and CloudFront as secondary with DNS failover at < 60s TTL. The Fastly 2021 outage is a reminder that CDN is a SPOF if you have no fallback."

### Staff (L6+) Answer Example

Staff-level adds the following dimensions to the senior answer:

> "Beyond the caching strategy, I'd design the cache key structure explicitly. Query parameters that are irrelevant to content (`utm_source`, `fbclid`) must be stripped from the cache key or you fragment the cache into millions of unique entries with hit ratio near zero. Most CDNs offer cache key normalization rules — I'd configure this on day one.
>
> For the origin protection model, I'd configure an origin shield (single regional PoP in front of origin) and implement request collapsing at both the shield and edge layer. This prevents cache stampedes when high-traffic items expire.
>
> At scale, I'd instrument cache hit ratio per content-type, TTFB p50/p95/p99 per geographic region, origin error rate, and CDN egress cost. These are separate SLIs — if hit ratio drops from 97% to 85%, that is a leading indicator of origin stress before the origin actually fails.
>
> For the video content specifically (product demo videos, marketing), I'd separate the CDN strategy: video uses range-request-aware caching with segment-level TTLs. A 4K video at 20 GB per title with 100K daily viewers means 2 PB/day — at this scale, negotiating dedicated CDN storage contracts (like Netflix's OCA model with ISPs) makes economic sense vs. standard CDN pricing.
>
> Finally, I'd have a runbook for CDN cache poisoning: automated content integrity checks (hash the home page HTML every 5 minutes, alert on unexpected changes), and a tested incident response playbook that includes 'purge all cache for affected URLs and rotate to backup CDN within 10 minutes.'"
