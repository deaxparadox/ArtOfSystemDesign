## 1. What Is It? (Theory)

### The Core Problem

Every distributed system faces the same fundamental challenge: **how do you move bytes from one machine to another reliably, quickly, and at scale?**

The Internet Protocol (IP) gives you raw packet delivery with a brutal guarantee: best-effort. It will try to route packets to the destination, but it makes zero promises about ordering, delivery, or duplication. If a packet is dropped, IP does not care. If two copies arrive, IP shrugs. If packets arrive in reverse order, IP moves on.

Every application that needs more than "best effort" has to implement that logic somewhere. TCP and UDP are the two dominant answers at Layer 4, representing opposite ends of a fundamental trade-off: **reliability versus latency**.

### TCP — Transmission Control Protocol

TCP was designed in 1974 by Cerf and Kahn specifically to solve the "unreliable IP" problem. Its charter was: **make the network look reliable to the application**, regardless of what the physical network does.

TCP delivers:
- **Ordered delivery**: bytes arrive in the exact sequence they were sent
- **Guaranteed delivery**: lost packets are automatically retransmitted
- **Duplicate suppression**: if a packet arrives twice, TCP deduplicates
- **Flow control**: sender won't overwhelm a slow receiver
- **Congestion control**: sender backs off when the network is congested

What this costs: **latency**. Every one of those guarantees requires waiting — waiting for ACKs, waiting for retransmissions, waiting for the receive window to open. The minimum cost of any TCP connection is **1 RTT** just to set up the connection before a single byte of application data is exchanged.

### UDP — User Datagram Protocol

UDP, defined in RFC 768 (1980), does almost nothing. It adds source/destination ports (so the OS can route packets to the right process) and an optional checksum. That is it. Jon Postel, its author, described it as a "thin veneer over IP."

UDP delivers:
- **Speed**: no handshake, no ACKs, no waiting — send and move on
- **Control**: the application decides what reliability it needs
- **Low overhead**: 8-byte header vs TCP's 20-byte minimum header

What this costs: **the application is on its own**. Packets can be lost, duplicated, or reordered. If you need reliability, you build it yourself on top of UDP.

### The Real-World Analogy

**TCP is like certified mail.** You fill out a form at the post office, the recipient must sign for the package, and you get confirmation it arrived. If it gets lost, the postal service resends it. You know with certainty your package arrived in good condition. But this takes longer — forms, signature requirements, tracking overhead.

**UDP is like dropping a postcard in a mailbox.** Fast, cheap, no ceremony. Maybe it arrives, maybe it doesn't. No one calls you to confirm. But if you're sending 10,000 postcards a second and only care that most of them arrive, this is dramatically more efficient.

### A Concrete Example With Numbers

Imagine you're building a multiplayer first-person shooter. Players send their position and input state to the server 60 times per second (every ~16.7ms).

**With TCP:**
- A single dropped packet (say, packet #42) triggers a retransmission request
- Packets #43, #44, #45 all queue up waiting for #42 to be retransmitted (this is **head-of-line blocking**)
- By the time #42 arrives, it's 50-200ms stale — the player has already moved
- The game renders the player teleporting backward to where they were 200ms ago
- This is perceptible lag, and in competitive play, it causes deaths

**With UDP:**
- Packet #42 is dropped — the server just never receives that position update
- Packets #43, #44, #45 arrive immediately with fresh position data
- The server uses the latest known position (packet #41) plus dead-reckoning to interpolate
- The resulting lag is 16-33ms — one or two frames — imperceptible at normal play

Fortnite, Valorant, Counter-Strike, and every major competitive shooter use UDP for exactly this reason.

## 2. How It Actually Works (Deep Mechanics)

### TCP Connection Lifecycle — Step by Step

**Connection Establishment (3-Way Handshake):**

```
Client                          Server
  |                               |
  |------- SYN (seq=x) --------> |   Step 1: Client announces ISN x
  |                               |
  | <---- SYN-ACK (seq=y,ack=x+1)|   Step 2: Server acknowledges, announces ISN y
  |                               |
  |------- ACK (ack=y+1) ------> |   Step 3: Client acknowledges server
  |                               |
  |====== DATA TRANSFER =========|   Now application data can flow
  |                               |
```

**Cost**: 1.5 RTT before the first byte of application data can be received by the server. On a cross-continental connection with 100ms RTT, that is **150ms of pure overhead** before "Hello" is sent.

**TCP Data Transfer with Acknowledgment:**

```
Client                          Server
  |                               |
  |-- Segment 1 (bytes 0-1459) -->|
  |-- Segment 2 (bytes 1460-2919)-|  Sender can have multiple in-flight
  |-- Segment 3 (bytes 2920-4379)-|  (limited by congestion window)
  |                               |
  | <------- ACK (seq=4380) ------|  Cumulative ACK: "I have everything up to byte 4380"
  |                               |
  |-- Segment 4 (bytes 4380-...) >|
  | <-- NACK / timeout detection --|  If segment 2 was lost:
  |-- Segment 2 (retransmit) ---> |  Segments 3, 4, 5... are all held back
  |                               |
```

**Head-of-Line Blocking in Action:**

```
Sender sends:  [Seg1] [Seg2] [Seg3] [Seg4] [Seg5]
                                ↓
               Seg3 is dropped in the network
                                ↓
Receiver has:  [Seg1] [Seg2] [    ] [Seg4] [Seg5]
                                ↓
App sees:      [Seg1] [Seg2]  BLOCKED  ← Seg4, Seg5 delivered but HELD by kernel
                                ↓
After retransmit + RTT:
App sees:      [Seg1] [Seg2] [Seg3] [Seg4] [Seg5]  — but 100-300ms later
```

**TCP Connection Teardown (4-Way):**

```
Client                          Server
  |------- FIN ----------------> |   Client: "done sending"
  | <------ ACK ----------------|   Server: "got it"
  | <------ FIN ----------------|   Server: "done sending too"
  |------- ACK ----------------> |   Client: "got it"
  |                               |
  [Client waits 2*MSL = ~60-120s TIME_WAIT]
```

The TIME_WAIT state means a TCP port pair cannot be immediately reused — relevant when building high-throughput servers that open many short-lived connections.

### UDP Packet Transmission — Step by Step

```
Client                          Server
  |                               |
  |-- UDP Datagram (seq=1) -----> |  No handshake. First packet IS the "connection."
  |-- UDP Datagram (seq=2) -----> |  Sender has no idea if any of these arrived.
  |-- UDP Datagram (seq=3) -----> |  Receiver gets them out of order? Application handles it.
  |                               |
  [seq=2 is dropped]
  |                               |
  |-- UDP Datagram (seq=4) -----> |  Delivered immediately to application.
  |-- UDP Datagram (seq=5) -----> |  Seq=2 is simply gone. Application decides what to do.
  |                               |
```

**UDP header (8 bytes total):**

```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|   Source Port   |  Destination Port|
+--------+--------+--------+--------+
|    Length       |    Checksum      |
+--------+--------+--------+--------+
|                                    |
|               DATA                 |
|                                    |
+------------------------------------+
```

**TCP header (20 bytes minimum, up to 60 bytes with options):**

```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|   Source Port   |  Destination Port|
+--------+--------+--------+--------+
|           Sequence Number          |
+--------+--------+--------+--------+
|         Acknowledgment Number      |
+--------+--------+--------+--------+
| HL|Res |Flags   |    Window Size   |
+--------+--------+--------+--------+
|      Checksum   |  Urgent Pointer  |
+--------+--------+--------+--------+
|              Options               |
+--------+--------+--------+--------+
```

### Key Algorithms Inside TCP

**Congestion Control (TCP Cubic / TCP BBR):**
- TCP starts slow (Slow Start: exponentially grows congestion window until packet loss detected)
- On loss, cuts window in half (Congestion Avoidance)
- TCP BBR (Google, 2016) uses bandwidth-delay product estimation instead of loss signals — 2-25x better throughput on high-latency paths
- This means TCP *intentionally throttles itself* when the network shows stress — UDP does not

**Selective Acknowledgment (SACK):**
- Without SACK, loss of one segment causes retransmission of everything from that segment forward
- With SACK (RFC 2018), receiver tells sender exactly which ranges arrived — sender only retransmits gaps
- SACK is enabled by default on Linux since kernel 2.4 (year 2001)

**Nagle's Algorithm:**
- TCP buffers small writes and combines them into fewer, larger segments
- Reduces chatty-protocol overhead (fewer segments on wire)
- **Causes ~40ms latency on interactive protocols** — must be disabled with `TCP_NODELAY` for anything real-time
- SSH, Redis, databases all set `TCP_NODELAY = 1`

### Real Numbers — Protocol Overhead

| Metric | TCP | UDP | Notes |
|---|---|---|---|
| Connection setup cost | 1 RTT (1.5 RTT for TLS) | 0 RTT | DNS query: ~1ms vs ~51ms (with TLS) |
| Header overhead | 20-60 bytes/segment | 8 bytes/datagram | ~4-7x more header bytes |
| Minimum latency (same DC) | ~0.1ms + 1 RTT handshake | < 0.05ms | No handshake, no ACK wait |
| Throughput (1Gbps LAN) | ~900 Mbps effective | ~950 Mbps effective | TCP overhead ~5-10% |
| Packet loss impact (1% loss) | ~30% throughput reduction (Mathis formula) | App-defined | TCP: retransmit + window shrink |
| Head-of-line blocking | Yes (severe) | No | UDP delivers what arrives immediately |
| Max message size | Unlimited (stream) | 65,507 bytes per datagram | UDP limited by IP datagram size |
| Ordering guarantee | Yes | No | Application must handle OOO with UDP |

### Common Misconceptions

**❌ Misconception: "UDP is unreliable, you can't use it for anything important"**
**✅ Reality:** UDP is *unmanaged*. Reliability is a quality you build on top. QUIC, WebRTC Data Channels, and SCTP all implement reliability on top of UDP — but *selectively*, only where the application needs it, not for every byte unconditionally.

**❌ Misconception: "TCP guarantees your data arrives in time"**
**✅ Reality:** TCP guarantees data arrives *eventually*, in order. It has no delivery deadline. On a congested or lossy link, TCP will retransmit indefinitely. A UDP application with custom timeout logic can deliver better real-time performance even under loss.

**❌ Misconception: "You can't have encryption over UDP"**
**✅ Reality:** DTLS (Datagram TLS) provides the same security guarantees as TLS but over UDP. WebRTC mandates DTLS. QUIC uses TLS 1.3 internally, over UDP.

**❌ Misconception: "TCP is slower than UDP in all cases"**
**✅ Reality:** On a perfect, zero-loss, low-latency LAN, TCP and UDP have similar throughput (within 10%). The performance gap grows with latency and packet loss. In a data center at < 1ms RTT with < 0.001% loss, TCP is "fast enough" for almost everything.

## 3. Real-World Architecture Examples

### Discord — Voice and Video Infrastructure

**The Decision (2017–2023):** Discord's voice service carries 2.5+ million concurrent voice users. Their architecture uses UDP for all real-time audio/video transport via their homegrown SFU (Selective Forwarding Unit) written in C++.

**What triggered it:** At 500K concurrent voice users, TCP-based signaling bottlenecks were causing 2-3 second delays in voice channel joins. More critically, head-of-line blocking on TCP caused audio glitches whenever a single TCP segment was dropped — the audio codec received stale data after the retransmission latency, causing audible artifacts and robotic voices.

**The first wrong attempt:** Discord initially used WebRTC's standard DTLS-SRTP stack (UDP with encryption), but ran into a NAT traversal problem: approximately 8-15% of users sit behind restrictive firewalls that block UDP entirely. Discord built a TCP fallback path — voice data tunneled over TCP port 443 (indistinguishable from HTTPS) — but flagged users on this path as having degraded quality expectations.

**What they got right:** The SFU architecture means the server receives UDP streams from N senders and forwards only the loudest 5 (voice activity detection) to each receiver. This means they never have M×N connections — each user has exactly 2 UDP flows. The protocol uses:
- UDP port range: 50,000–65,535 (configurable per voice region)
- SRTP for encryption
- RTCP for control/statistics (also UDP)
- TCP port 443 fallback for firewall-restricted users

**Scale outcome:** 2.5M concurrent voice users with median audio latency < 50ms, p99 < 150ms. TCP fallback users see p50 ~120ms, p99 ~400ms — about 3x worse.

**Source:** [Discord Engineering Blog — How Discord Handles Two and Half Million Concurrent Voice Users using WebRTC](https://discord.com/blog/how-discord-handles-two-and-half-million-concurrent-voice-users-using-webrtc)

---

### Cloudflare — QUIC/UDP for Tunnel and Proxy Infrastructure

**The Decision (2020–2024):** Cloudflare Tunnels (formerly Argo Tunnel) initially used TCP for the persistent tunnel connection between origin servers and Cloudflare's edge. In 2020, they began migrating tunnels to QUIC (UDP-based).

**What triggered it:** TCP-based tunnels suffered from a compounding head-of-line blocking problem: HTTP/2 multiplexes multiple streams over a single TCP connection, and a single dropped segment stalls *all* streams. In a tunnel scenario where the outer TCP connection loses a packet, every HTTP/2 stream inside the tunnel blocks — multiplying the latency impact.

**What they discovered:** Linux kernels at the time had heavily optimized TCP transmission paths (GRO, TSO, GSO) but relatively unoptimized UDP paths. Cloudflare published ["Accelerating UDP packet transmission for QUIC"](https://blog.cloudflare.com/accelerating-udp-packet-transmission-for-quic/) detailing how they contributed `sendmmsg()` batching optimizations to improve UDP throughput from ~200K packets/sec to ~1M packets/sec per CPU core.

**Scale outcome:** Cloudflare handles ~20% of all web traffic globally. After QUIC enablement across their network (QUIC v1 went live globally in 2021), they reported 8% reduction in mean page load time globally, and up to 13% in high-latency regions (Asia, South America).

**Current state:** As of 2024, HTTP/3 (QUIC) adoption sits at ~35% of web traffic globally (Cloudflare Radar data). Meta runs ~75% of its traffic on QUIC/HTTP/3. Google has served QUIC traffic since 2015.

---

### Netflix — TCP for VOD, Strategic QUIC Exploration for Live

**The Decision (2012–present):** Netflix serves 300M+ subscribers and is the largest source of internet traffic in North America during peak hours (~15% of all downstream traffic). They use HTTPS/TCP (via HTTP adaptive streaming — DASH) for all video-on-demand delivery.

**Why TCP for on-demand:** Netflix content is buffered ahead — typically 15-30 seconds of video is pre-fetched by the client player. This means TCP retransmissions *almost never* matter for playback quality: by the time the player needs segment N+20, a retransmission for segment N has long since completed. TCP's reliability removes a whole class of player-level error handling.

**The ABR strategy removes TCP's main weakness:** Netflix's Adaptive Bitrate (ABR) algorithm monitors TCP throughput estimates. When TCP slows down (congestion), the player drops to a lower bitrate *before* the buffer empties, not *because* it emptied. This turns TCP's slow-start and congestion backoff into *signals* the player actively uses.

**Where TCP fails Netflix:** Live streaming is different. Netflix Live (sports, events) cannot pre-buffer. They've explored QUIC for live delivery to eliminate head-of-line blocking latency. The SVTA (Streaming Video Technology Alliance) published a proof-of-concept in 2022 showing QUIC outperforming TCP by 20-40% in segment delivery latency under 2%+ packet loss conditions.

**The actual architecture:** Netflix uses Open Connect — their own CDN with ~17,000 servers in 1,000+ ISP networks worldwide. The CDN-to-client connection is TCP. The microservices backend (API, recommendation, auth) is also TCP/HTTPS. Netflix processes ~500 billion events per day through Kafka (also TCP-based).

**Key insight:** For Netflix's use case, the operational simplicity of TCP (no custom reliability layer, well-understood behavior, universal firewall compatibility) outweighs the latency benefits of UDP for on-demand content.

---

### Valve / Steam — Game Networking and the Source Engine

**The Decision:** Valve's Source engine (Counter-Strike: Global Offensive, Team Fortress 2, Dota 2) uses a custom UDP-based protocol called the **Valve Steam Datagram Relay (SDR)** for game networking.

**What they got wrong first:** CS:GO originally allowed players to connect directly (peer routing) over UDP. This exposed server IPs to players, leading to DDoS attacks against game servers. A single SYN flood over UDP amplification took down servers mid-tournament.

**What they built:** SDR is a global network of relay nodes (similar to Cloudflare's Anycast network but dedicated to gaming). Game packets flow through the nearest relay, masking server IPs. SDR also implements:
- **Custom congestion control** tuned for 64-tick and 128-tick server rates
- **Multi-path routing** — SDR picks the lowest-latency path among 4-6 relay candidates in real time
- **Packet prioritization** — input packets (player actions) get priority over world-state updates
- Result: p50 latency from North America to EU decreased from ~140ms to ~105ms after SDR rollout

**Key design insight:** The same system uses **both** UDP and TCP for different concerns. Real-time game state flows over UDP. Persistent, correctness-critical data (account, payment, match results) flows over TCP. This is not a choice between protocols — it is a deliberate layering.

### Design Questions to Ask Before Choosing a Protocol

1. **Is delivery order required, or is latest-value sufficient?** (game position = latest wins; bank transfer = order required)
2. **What is the tolerable latency for this data type?** (< 5ms? Use UDP. < 500ms acceptable? TCP is fine.)
3. **What happens when a packet is dropped?** (re-send old data? interpolate? fail transaction?)
4. **Will the data be consumed immediately or buffered?** (buffered → TCP retransmits are free; real-time → retransmits are poison)
5. **Are there firewalls/NATs between client and server?** (enterprise firewalls often block UDP; TCP 443 almost always passes)
6. **Is connection state a problem?** (millions of short-lived connections → TCP TIME_WAIT port exhaustion is real)
7. **Do you need multicast or broadcast?** (UDP supports it; TCP does not — TCP is always unicast point-to-point)

### Scale Evolution — Protocol Decisions at Each Stage

**1K users — Prototype:**
- TCP for everything. It is simpler. Connection-oriented semantics match your mental model.
- Latency: probably fine — 1K users on a single server, co-located.
- Decision: TCP, HTTPS, done. Focus on product.

**100K users — Growth:**
- TCP connection limits start to bite. Linux default ephemeral port range is 28,232 ports. With 100K concurrent connections to a single server, you hit `EAGAIN: address already in use`.
- Fix: `net.ipv4.ip_local_port_range = 1024 65535` and multiple server IPs.
- If you're building real-time features (chat, live updates), TCP keep-alives at scale are expensive — each idle TCP connection consumes ~4KB kernel memory. 100K connections = ~400MB just for socket state.
- Decision: start evaluating WebSockets (TCP-based long poll alternative) or UDP for latency-sensitive paths.

**1M users — Scaling:**
- TCP congestion control becomes a system-wide concern. A single misbehaving client triggering retransmits can affect throughput for adjacent connections in the same kernel TCP stack.
- Head-of-line blocking in HTTP/2 multiplexing starts causing p99 latency spikes.
- DNS at this scale: TTL tuning and UDP 512-byte limit for DNSSEC responses matters — some DNS responses exceed 512 bytes and fall back to TCP, adding 1 RTT.
- Decision: introduce a UDP-based protocol for real-time paths. Keep TCP for transactional/persistent data. Consider HTTP/3 (QUIC) for your public API.

**100M users — Hyperscale:**
- Protocol choice becomes infrastructure-level policy. Facebook (Meta) migrated ~75% of traffic to QUIC by 2022.
- At this scale, even 1% latency improvement translates to millions of dollars in CDN costs and measurable engagement metrics.
- TCP SYN flood attacks are existential — DDoS protection (IP reputation, SYN cookies, anycast scrubbing) becomes mandatory.
- Custom protocols: Valve's SDR, Google's QUIC, Meta's MPTCP deployments, AWS's SRD (Scalable Reliable Datagram for EFA networking) — all represent companies writing their own transport protocols because neither vanilla TCP nor UDP meets their needs.
- Decision: custom transport protocol with selective reliability, multi-path, and congestion control tuned to your workload.

## 5. Code / Implementation Perspective

### Python Implementation — UDP Game State Server

```python
import socket
import struct
import time
from dataclasses import dataclass, field
from collections import defaultdict

@dataclass
class PlayerState:
    x: float
    y: float
    seq: int
    timestamp: float = field(default_factory=time.monotonic)

# ---- UDP server: receive player positions, broadcast world state ----
def run_game_server(host: str = "0.0.0.0", port: int = 7777):
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    # Critical: set non-blocking so we can run the game tick independently
    sock.setblocking(False)
    sock.bind((host, port))

    players: dict[tuple, PlayerState] = {}
    TICK_RATE = 64  # ticks/sec → 15.6ms per tick
    TICK_INTERVAL = 1.0 / TICK_RATE

    print(f"Game server listening on UDP {host}:{port} at {TICK_RATE} tick/s")

    next_tick = time.monotonic()
    while True:
        # Drain all incoming UDP packets (non-blocking)
        try:
            while True:
                data, addr = sock.recvfrom(64)  # small fixed-size input packet
                if len(data) >= 16:
                    # Packet format: [seq:4B][x:4B][y:4B][timestamp:4B] = 16 bytes
                    seq, x_raw, y_raw, ts_raw = struct.unpack("!IffI", data[:16])
                    x = x_raw
                    y = y_raw
                    # Only apply update if seq is newer (handle out-of-order packets)
                    current = players.get(addr)
                    if current is None or seq > current.seq:
                        players[addr] = PlayerState(x=x, y=y, seq=seq)
        except BlockingIOError:
            pass  # No more packets in the buffer right now

        now = time.monotonic()
        if now >= next_tick:
            # Build world state snapshot and broadcast to all known players
            # Packet: [player_count:1B] + [addr_hash:4B][x:4f][y:4f] per player
            if players:
                world_state = struct.pack("!B", len(players))
                for addr, state in players.items():
                    pid = hash(addr) & 0xFFFFFFFF
                    world_state += struct.pack("!Iff", pid, state.x, state.y)
                for addr in list(players.keys()):
                    try:
                        sock.sendto(world_state, addr)
                    except OSError:
                        del players[addr]  # Stale client — no connection to clean up

            # Evict players not seen in 5 seconds (UDP has no "disconnect" signal)
            stale_cutoff = time.monotonic() - 5.0
            players = {a: s for a, s in players.items() if s.timestamp > stale_cutoff}

            next_tick += TICK_INTERVAL

if __name__ == "__main__":
    run_game_server()
```

**Key UDP-specific patterns in this code:**
1. **Non-blocking socket** — essential; blocking `recvfrom` would cause tick rate jitter
2. **Out-of-order handling** — `seq > current.seq` prevents older packets overwriting newer state
3. **No disconnect signal** — time-based eviction because UDP has no FIN/RST
4. **Drain loop** — read all queued packets before game tick, not one per tick

### TCP equivalent differences (for contrast):

```bash
# Increase UDP receive buffer (default 212992 → 26214400 = 25MB)
# Prevents packet drops when application can't drain fast enough

```

### Nginx Configuration — Protocol Routing

```nginx
# nginx.conf: route TCP vs UDP traffic appropriately

stream {
    # UDP for game state (pass-through, no termination)
    upstream game_servers {
        server 10.0.1.10:7777;
        server 10.0.1.11:7777;
        server 10.0.1.12:7777;
    }

    server {
        listen 7777 udp;          # Note: udp keyword
        proxy_pass game_servers;
        proxy_timeout 5s;          # Evict stale UDP "connections" after 5s silence
        proxy_responses 1;         # Each client datagram triggers 1 upstream send
    }
}

http {
    # TCP for REST API, auth, match results (HTTPS)
    upstream api_servers {
        server 10.0.2.10:8080;
        keepalive 64;              # Reuse TCP connections to backends
    }

    server {
        listen 443 ssl http2;
        location /api/ {
            proxy_pass http://api_servers;
            proxy_http_version 1.1;
            proxy_set_header Connection "";  # Enable keepalive
        }
    }
}
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Plain TCP** | Transactional data, file transfer, API calls, anything where reliability matters more than < 50ms latency | Simple, reliable, universal firewall support; costs 1 RTT per connection, head-of-line blocking under loss | Netflix (VOD), PostgreSQL, HTTP/1.1+2 APIs, Redis, Kafka |
| **Plain UDP** | Real-time game state, audio/video streaming, DNS queries, telemetry/metrics fire-and-forget | Zero setup latency, no HOL blocking; application must handle loss, ordering, security | DNS, NTP, SNMP, game engines (Unreal, Unity custom netcode) |
| **QUIC (HTTP/3)** | Web APIs and content delivery where both performance and reliability matter; replaces TCP for HTTP workloads | Combines UDP speed + TCP reliability + TLS 1.3 in one; complex implementation; UDP may be blocked in some networks | Cloudflare, Google, Meta (75% of traffic), YouTube |
| **WebRTC** | Browser-to-browser or browser-to-server real-time audio/video; P2P when possible | Standards-based, works in browsers without plugins; complex ICE/STUN/TURN negotiation, ~8-15% of users need TCP fallback | Discord, Zoom, Google Meet, Twilio, Agora |
| **WebSocket (over TCP)** | Bidirectional real-time communication from browsers; chat, live dashboards, collaborative editing | Works everywhere (TCP 443); subject to TCP HOL blocking; persistent connection overhead | Slack, Figma, multiplayer games via browser, financial tickers |
| **SCTP** | Telecom signaling, multi-stream ordered delivery, message framing | Multi-streaming (no per-stream HOL blocking), multi-homing; virtually no support in public clouds or NATs | 4G/5G core (SS7 over SCTP), rarely used in web-scale systems |
| **Custom UDP protocol** | Competitive gaming, video conferencing infrastructure, massive scale | Maximum control over reliability/ordering semantics; high engineering cost, protocol bugs are your problem | Valve SDR, Zoom's custom protocol, Cisco WebEx |

### My Opinionated Recommendation

**Start with TCP unless you have a specific, measured problem that TCP cannot solve.**

The engineers who switch to UDP prematurely spend 6-18 months reimplementing the parts of TCP they actually needed (reliability, ordering, congestion control) — but worse, because they're doing it in application code rather than the kernel.

**The right decision tree:**
1. Is latency < 20ms p99 a hard requirement? → Maybe UDP
2. Can you tolerate any packet loss at the application level? → Required for UDP
3. Are your clients primarily browsers? → WebSocket (TCP) or WebRTC/QUIC for media
4. Is this a microservice inside a data center? → TCP. Always. Data center loss rates < 0.01%, RTTs < 1ms — UDP gives zero benefit.
5. Is this gaming, live video, or voice? → UDP or QUIC. Not TCP.

**The modern answer for new web-facing services is QUIC (HTTP/3), not raw UDP.** It gives you UDP's per-stream non-blocking behavior with TCP-grade reliability and TLS built in. You do not have to implement retransmission logic yourself.

## 8. Trade-offs (Be Opinionated)

### TCP — Benefits

- **Universal firewall compatibility**: Every network on the planet passes TCP 443. UDP is blocked by ~15-20% of enterprise firewalls and some carrier-grade NATs.
- **Zero reliability code to write**: Retransmission, ordering, deduplication — all handled. You write 0 lines of reliability code.
- **Built-in congestion control**: TCP BBR/CUBIC adapts to network conditions automatically. A UDP application that ignores congestion will be a bad citizen on the internet and may have its traffic throttled by ISPs.
- **Mature ecosystem**: Every load balancer, proxy, firewall, monitoring tool, debugging tool (tcpdump, Wireshark, ss, netstat) has first-class TCP support.
- **Connection-oriented semantics match most business logic**: A "session" maps naturally to a TCP connection. Authentication, authorization, and billing align with connection lifecycle.

### TCP — Costs and Limitations

- **Minimum 1 RTT connection overhead**: On a 100ms RTT WAN link, every new TCP connection burns 100ms before data flows. With TLS: 250ms (1-RTT TLS 1.3) to 350ms (older TLS 1.2). At 10 connections/second from mobile users, this is the dominant latency cost.
- **Head-of-line blocking is severe under loss**: At 2% packet loss, a streaming HTTP/2 connection can see p99 latency increase by 300-500% compared to 0% loss conditions. Not theoretical — this happens routinely on mobile networks.
- **Congestion control penalizes bursty traffic**: TCP Slow Start means the first 10-20 packets of any new connection go out slowly. A CDN serving 100KB files spends a disproportionate fraction of transfer time in slow start.
- **TIME_WAIT exhaustion at scale**: Each closed TCP connection occupies kernel state for 60-120 seconds. A high-frequency service making 50,000 short connections/second will exhaust 28,232 default ephemeral ports in < 1 second. This is a production incident waiting to happen.
- **Nagle's Algorithm**: If you forget `TCP_NODELAY`, your interactive protocol suddenly has 40ms phantom latency. This has caused production incidents at many companies.

### UDP — Benefits

- **Zero connection setup latency**: First packet carries data. DNS servers answer 100M+ queries/day in part because each query-response is a single UDP round-trip with no handshake.
- **No head-of-line blocking**: Each datagram is independent. Packet loss affects only the application logic for that datagram, not subsequent ones.
- **Multicast and broadcast**: UDP can fan out to multiple receivers simultaneously. TCP cannot. IPTV, financial market data broadcast (FAST/UDP multicast), service discovery protocols (mDNS, SSDP) all rely on this.
- **Application-defined reliability**: You implement exactly the reliability semantics you need. Games use "best-effort with dead-reckoning." Video uses "FEC (forward error correction) with selective NACK." Neither needs full TCP reliability.

### UDP — Costs and Limitations

- **Firewall/NAT traversal is hard**: ~15% of enterprise users sit behind firewalls that block all UDP. Stateful NATs don't maintain UDP mappings after 30-90 seconds of silence (vs TCP which has explicit connection state). ICE/STUN/TURN protocols exist specifically to solve NAT traversal for UDP.
- **You must implement everything**: Congestion control, ordering, reliability, heartbeats, session management, security. Each of these is a source of bugs that took the TCP/IP community decades to get right.
- **No built-in congestion control means you're a bad internet citizen**: An uncongestion-controlled UDP application sending at line rate during network congestion will starve TCP flows. AWS, Cloudflare, and enterprise networks throttle or drop UDP flows that lack congestion signals. QUIC includes TCP-equivalent congestion control for this reason.
- **Debugging is harder**: No SYN/FIN packets to match in pcaps. No connection state in `ss -n`. Application-layer sequence numbers are invisible to network tools.

### Core Tension Being Navigated

**Reliability vs. Timeliness.** These are genuinely opposing properties. TCP achieves reliability by delaying delivery when the network drops data. UDP achieves timeliness by delivering what arrives and letting the application decide whether to wait for missing data. This is not a bug in either protocol — it reflects a fundamental theorem in distributed systems: you cannot simultaneously guarantee both delivery order and minimal latency under packet loss.

### My Recommendation

**For microservices within a data center: TCP always.** Data center networks have < 0.01% packet loss and < 1ms RTTs. UDP gives you no meaningful benefit and takes away kernel-level congestion control. This is not even a close call.

**For web-facing APIs: HTTP/3 (QUIC) for new systems, HTTP/2 over TCP for existing ones.** QUIC is now mature enough (35% of web traffic as of 2024, RFC 9000 published May 2021) that the ecosystem risk is manageable.

**For real-time gaming, voice, video: UDP (or QUIC for browser scenarios).** The head-of-line blocking penalty under even 1% loss makes TCP unacceptable for interactive media. This is not a performance preference — it is a correctness requirement.

**Never:** raw UDP for anything that needs reliability, without implementing your own congestion control. You will harm other users on the network and your traffic may be policed by ISPs.

## 9. Failure Modes — What Goes Wrong

### UDP Amplification DDoS Attack

**Trigger:** An attacker spoofs the victim's IP address as the source and sends small UDP requests to public services with high amplification factors (DNS: 28-54x, NTP: 556x, memcached: 51,000x). Reflected responses flood the victim.

**Symptoms:** Victim's network uplink is saturated. TCP and UDP traffic alike are affected at the network level. Servers appear down from external monitoring. ISP may null-route the victim's IP. The attack itself is hard to see from inside the victim's infrastructure — the attack traffic never reaches the application layer.

**Detection:** NetFlow/sFlow data showing extreme inbound traffic on UDP 53 (DNS), 123 (NTP), or 11211 (memcached) from thousands of source IPs. Traffic volume exceeds normal baseline by 100-10,000x. Cloudflare Radar reported a 3.8 Tbps UDP DDoS attack in 2024 — the largest ever recorded at the time.

**Recovery:** BGP blackholing (drops all traffic to the IP — stops the attack but also stops legitimate traffic). Anycast scrubbing via Cloudflare Magic Transit or AWS Shield Advanced. Rate-limiting UDP at the ISP or upstream router level. Long term: deploy BCP38 source address validation; use Cloudflare or AWS as proxy so your origin IPs are never public.

**Real Example:** GitHub was hit by a 1.35 Tbps memcached UDP amplification attack in February 2018 — the largest DDoS ever recorded at the time. GitHub was offline for 10 minutes before Akamai absorbed the traffic. The attacker used 45,000 memcached servers with port 11211 open to the internet as amplifiers, achieving a ~51,000x amplification ratio.

---

### TCP Head-of-Line Blocking Causing Latency Spikes

**Trigger:** A TCP connection experiences 1-3% packet loss (normal on mobile, WiFi, or long-haul WAN links). With HTTP/2 multiplexing, one lost TCP segment blocks all streams multiplexed on that connection.

**Symptoms:** p99 API latency spikes from 50ms to 500-2000ms. The spike is not correlated with CPU, memory, or server-side processing time. `tcpdump` shows TCP retransmissions followed by burst of ACKs. The issue is more pronounced on connections with high RTT (> 100ms).

**Detection:** Monitor TCP retransmit rate with `ss -s` (or `netstat -s | grep retransmit`). Alert on retransmit rate > 0.1% for data center connections (should be near 0), > 2% for WAN connections. Correlate p99 latency spikes with TCP retransmit spikes — a correlation coefficient > 0.7 is a strong signal.

**Recovery:** Short term: enable SACK (default on Linux), tune TCP socket buffers, enable BBR congestion control (`net.ipv4.tcp_congestion_control = bbr`). Long term: migrate affected traffic to HTTP/3 (QUIC) which eliminates per-connection HOL blocking. For internal microservices on lossy WiFi dev laptops connecting to prod — fix the WiFi, or VPN over a more reliable path.

**Real Example:** Cloudflare published that HTTP/3 vs HTTP/2 in a 2% packet loss scenario shows HTTP/3 delivering pages in 0.8 seconds vs HTTP/2's 1.5 seconds — a 47% improvement attributable entirely to eliminating TCP HOL blocking.

---

### TCP Port Exhaustion (TIME_WAIT Storms)

**Trigger:** A high-traffic service makes many short-lived outbound TCP connections — common in microservice architectures where a service makes hundreds of HTTP calls per second to downstream APIs. Each closed connection enters TIME_WAIT state for 60-120 seconds (2 × MSL), consuming an ephemeral port. Linux default range is 32,768–60,999 (28,231 ports). At 500 connections/second, TIME_WAIT ports are exhausted in < 60 seconds.

**Symptoms:** `connect()` calls return `EADDRNOTAVAIL`. Service logs show "Cannot assign requested address" errors. Outbound requests fail completely. Inbound requests continue to succeed (different port range). The issue appears suddenly when traffic crosses a threshold. `ss -s` shows TIME_WAIT count approaching 28,000+.

**Detection:** Monitor TIME_WAIT socket count: `ss -s | grep TIME-WAIT`. Alert when TIME_WAIT count exceeds 20,000 on a single server. Check ephemeral port range: `cat /proc/sys/net/ipv4/ip_local_port_range`.

**Recovery:** Immediate: `net.ipv4.tcp_tw_reuse = 1` (allows reuse of TIME_WAIT sockets for new outbound connections — safe in most cases). Expand ephemeral port range: `net.ipv4.ip_local_port_range = 1024 65535` (increases to ~64,000 ports). Architectural fix: use connection pooling (HTTP/1.1 keep-alive or HTTP/2) so connections are reused rather than opened/closed. UDP-based systems never have this problem — UDP has no connection state, no TIME_WAIT.

**Real Example:** This is one of the most common production incidents in microservice architectures. Any service doing fan-out to 100+ downstream services with short connection lifetimes will hit this. Stripe's engineering blog discusses connection pool management specifically to avoid this class of failure in their payment processing infrastructure.

---

### UDP Packet Reordering Mishandled at Application Layer

**Trigger:** An application naively processes UDP packets in arrival order without checking sequence numbers. Under network conditions with asymmetric routing (common in cloud environments), packets from the same source may take different paths with different latencies, arriving out of order by 5-50ms.

**Symptoms:** Game state appears to "jitter" or go backward. Video decoding artifacts (B-frame reordering failures). For position updates, players appear to teleport between positions that were sent 5-10 frames apart.

**Detection:** Add sequence number monitoring to your UDP protocol. Log and alert when `current_seq < last_seq` — this is a reordering event. Normal reordering rate should be < 0.1%; if > 1%, investigate routing asymmetry.

**Recovery:** Implement a reorder buffer with a configurable depth (e.g., hold packets for up to 10ms to allow out-of-order packets to arrive before processing). For game state, implement dead-reckoning so missing/delayed position updates do not cause visible teleportation. For video, implement RTP sequence number handling per RFC 3550.

**Real Example:** The AWS EC2 enhanced networking (ENA) driver documentation explicitly warns that packets between EC2 instances can arrive out of order when crossing availability zone boundaries. Applications using UDP between AZs without sequence number handling will see this in production under load.

## 10. When To Use vs. When To Avoid

### ✅ Use UDP When:

1. **Real-time interactive applications where stale data is worse than no data** — online games (Fortnite, CS:GO, Valorant), live video/audio (Discord, Zoom, WebRTC), VoIP (SIP/RTP), AR/VR applications where a 100ms retransmit would break presence more than a dropped frame
2. **Fire-and-forget telemetry or metrics at high volume** — sending 50,000 metrics/second to a StatsD server where losing 0.1% of samples is statistically insignificant but the overhead of TCP ACKs would double your bandwidth usage
3. **Simple request-response where the request is self-contained and small** — DNS queries (< 512 bytes), NTP time sync, DHCP, SNMP polling. The overhead of a TCP handshake (1 RTT = 20-200ms) would be larger than the actual data exchange (1 RTT for query + response = total round trip)
4. **Multicast/broadcast delivery** — IPTV, financial market data distribution (NYSE, NASDAQ use UDP multicast), service mesh discovery (mDNS), where you need one packet to reach many receivers simultaneously

### ❌ Do NOT Use UDP When:

1. **Data integrity is non-negotiable** — financial transactions, database writes, configuration updates, file transfers. If even a single byte of corruption (UDP checksum is 16-bit CRC, not cryptographic) or a dropped packet causes an incorrect state, you need TCP's reliability.
2. **Firewall/NAT compatibility matters for your user base** — enterprise customers, government networks, corporate VPNs. Approximately 15-20% of enterprise environments block UDP entirely. If your product targets enterprise users, a UDP-only protocol will generate immediate support escalations.
3. **You need connection-level semantics without implementing them yourself** — authentication tied to a session, ordered command execution, stateful protocols where request N must succeed before request N+1. Implementing this on UDP reliably is a multi-month project.

### ⚠️ The #1 Mistake Engineers Make

**Building a reliable protocol on top of UDP without implementing proper congestion control.**

It sounds counterintuitive — "I'm implementing reliability, why would I also need congestion control?" — but they are separate concerns:
- **Reliability** = "did my data arrive?"
- **Congestion control** = "am I sending faster than the network can handle?"

An application that retransmits lost UDP packets but does not back off under congestion will aggressively compete with TCP flows on the same network path, get throttled by ISPs, and ironically achieve *worse* throughput than TCP under load. This is not theoretical — video conferencing applications from the early 2010s routinely caused WiFi network degradation for all other users by doing exactly this.

The correct solution: use QUIC (which has TCP-equivalent congestion control built in) rather than rolling your own UDP reliability. Or if you must use raw UDP, implement BBR or CUBIC congestion control as part of your protocol. This is why custom-protocol work (Valve SDR, Zoom's protocol, Discord's voice) requires significant networking expertise — they all include custom congestion control implementations.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a real-time multiplayer game backend for 1 million concurrent players."
- "How would you design the networking layer for a video conferencing application like Zoom?"
- "Walk me through the trade-offs between TCP and UDP and when you'd pick each."
- "How does Discord handle voice for millions of users? Why is latency so low?"
- "Your API has p99 latency of 500ms and you've ruled out server-side bottlenecks. How do you diagnose and fix it?"
- "Design the networking architecture for a live sports streaming service with 10 million simultaneous viewers."

### What the Interviewer is Evaluating

1. **Do you understand the mechanics?** — Can you explain head-of-line blocking, the 3-way handshake, and why they matter?
2. **Do you make trade-off-driven decisions?** — "TCP for transactional, UDP for real-time" without understanding why is a red flag. The interviewer wants to hear *why*, with *numbers*.
3. **Do you know what companies actually do?** — Mentioning Discord/WebRTC, Netflix/DASH/TCP, QUIC/HTTP/3 demonstrates practical grounding beyond textbook knowledge.
4. **Do you know failure modes?** — What breaks? DDoS amplification, TIME_WAIT exhaustion, HOL blocking under loss — these show production experience.
5. **Do you ask the right questions?** — Strong candidates don't immediately answer; they ask clarifying questions first.

### Questions YOU Ask Before Answering

- "What is the latency requirement? Is this p50 or p99?"
- "What is the acceptable packet loss tolerance for the application?"
- "Are clients in browsers, mobile apps, or server-to-server?"
- "What is the expected geographic distribution of users?" (global = high RTT = QUIC matters more)
- "Do any users sit behind enterprise firewalls?" (if yes: TCP fallback is required)
- "Is this real-time interactive (game, voice) or buffered delivery (VOD, file download)?"

### Junior (L3–L4) Answer Example

**Question:** "Why would you use UDP instead of TCP?"

**Junior answer:** "UDP is faster because it doesn't have the overhead of TCP's handshake and acknowledgments. It's good for things like video games and streaming where you want low latency and can tolerate some packet loss. TCP is better when you need reliability like for file downloads or web requests."

**Why this passes at L3-L4:** Correct at a conceptual level. Shows awareness of the trade-off. Missing: specific numbers, head-of-line blocking, real company examples, failure modes.

### Senior (L5) Answer Example

**Question:** "Why would you use UDP instead of TCP?"

**Senior answer:** "The core trade-off is reliability vs. timeliness. TCP guarantees ordered, reliable delivery, but that guarantee costs you at minimum 1 RTT for connection setup and, critically, causes head-of-line blocking under packet loss — when one segment is dropped, all subsequent segments queue up waiting for the retransmission. On a link with even 1% loss, this can spike p99 latency by 3-5x.

UDP is stateless — no handshake, no ACKs — so each packet is independent. If one drops, the next arrives immediately. This is why Discord uses UDP for voice and WebRTC: a dropped audio packet means 20ms of silence, but a TCP retransmit would mean 100-300ms of silence followed by a burst — which is perceptibly worse.

The counter-case: Netflix uses TCP for VOD because they buffer 15-30 seconds ahead — retransmits complete long before the player needs the data. And for microservices in a data center with < 0.01% packet loss, TCP is 'fast enough' and you get reliability for free.

The modern answer for web-facing systems is often QUIC/HTTP/3: UDP underneath with per-stream reliability and TLS built in. 35% of web traffic uses it as of 2024."

### Staff (L6+) Answer Example

**Question:** "Design the networking layer for a competitive FPS game with 10M concurrent players globally."

**Staff answer:** "Before I design this, I need to understand a few things: What's the tick rate — 64 or 128Hz? What's the latency budget — is this a casual game (< 150ms acceptable) or competitive e-sport (< 30ms required)? What's the client platform distribution — PC, console, mobile?

Assuming competitive, 128Hz, global, PC-dominant:

**Transport layer:** UDP for all game state. TCP is non-negotiable for a 128Hz game — at 128 packets/second per player, a single dropped packet causes a 7.8ms update gap. With TCP retransmission adding 50-200ms on a congested WAN, that's 7-26 missed ticks worth of stale state — perceptible as rubber-banding.

**The architecture I'd build:**
1. Anycast edge nodes (Cloudflare/AWS Global Accelerator) absorb traffic close to players — reduces public internet traversal, which is where loss happens. This gets Valve-SDR-like benefits without building the relay network yourself.
2. Game servers in 8-12 regional clusters. Within a region, server-to-server communication is TCP (data center, low loss).
3. Custom UDP protocol with: sequence numbers (handle reordering), client-side dead-reckoning (interpolate through packet loss), lag compensation (server rewinds to client's perspective time for hit detection — Valorant does this up to 70ms).
4. TCP 443 fallback for the ~10-15% of users behind restrictive firewalls — they'll see higher latency but can play.
5. TCP for all non-game-state: auth, matchmaking, leaderboards, purchases.

**What I would not build:** Custom reliability on UDP without congestion control. Valve spent years getting SDR's congestion control right. I'd use QUIC for anything that needs reliability, and accept that raw game state is best-effort.

**Numbers that matter:** Competitive FPS needs < 50ms one-way latency (< 100ms RTT) for responsive play. With anycast edge nodes, 80% of global players can achieve this. The remaining 20% (rural areas, remote regions) need server-side lag compensation, not a protocol change.

**Key failure mode to design for:** UDP amplification DDoS. Game servers can't be on public IPs — they need Cloudflare Magic Transit or similar to absorb amplification attacks. GitHub's 1.35 Tbps attack in 2018 shows what happens otherwise."
