# 2.4 — Load Balancers (L4 vs L7)

> 📍 Phase 2 — Networking & Communication | Section 2.4

**Prerequisites** — Before reading this section you should be comfortable with:
- How TCP/IP works (3-way handshake, connection state, ports)
- The OSI model layers 4 (Transport) and 7 (Application)
- HTTP/1.1 request/response cycle and headers
- What DNS does and how A/CNAME records resolve (Section 2.3)
- Basic understanding of horizontal scaling (adding more servers)
- What a server process is and how it binds to a port

## 1. What Is It? (Theory)

### The Problem

Your application runs on one server. That server has limits: ~65 000 concurrent TCP connections, a fixed amount of CPU, a fixed amount of RAM. At some point — maybe 500 users, maybe 50 000 — it falls over.

The obvious answer is "run more servers." But now you have a new problem: **how does a client know which server to talk to?** You cannot give every user a list of 20 IP addresses and tell them to pick one.

A **load balancer** is the single entry point that clients connect to. It accepts incoming requests or connections and distributes them across a pool of backend servers (called "upstream" or "origin" servers) according to a routing algorithm. When a backend goes down, the load balancer stops sending traffic to it. When you add a backend, the load balancer starts using it. The client never knows any of this is happening.

### Why It Was Invented

In the mid-1990s, websites started exceeding the capacity of a single server. The first hardware load balancers (Cisco LocalDirector, 1996; F5 BIG-IP, 1997) were purpose-built devices placed in a data center rack in front of a server farm. They were expensive (~$50 000–$200 000 per device), but they worked. Software load balancers (HAProxy 2000, nginx 2004) democratised the pattern.

The key insight: **traffic distribution is a solved problem you should not reinvent at the application layer.**

### Real-World Analogy

Think of a bank with 10 teller windows. A greeter at the door watches all queues and directs each customer to the shortest one. If a teller goes on break, the greeter stops sending people there. If a new teller opens, the greeter immediately starts using that window.

- The greeter = the load balancer
- Teller windows = backend servers
- Customers = client requests/connections

The greeter in this analogy can operate at two levels of intelligence:

1. **L4 (dumb greeter):** "I see someone walking in — window 3, go." The greeter does not know or care whether the customer wants a mortgage or a withdrawal.
2. **L7 (smart greeter):** "You have paperwork — mortgage team, 2nd floor. You want cash — teller window 6, which specialises in cash." The greeter reads the customer's paperwork before routing.

### The Number That Forces The Decision

A single well-tuned Linux server can sustain roughly 50 000–100 000 HTTP requests/second (RPS) on commodity hardware before CPU becomes the bottleneck. A popular consumer application might hit 500 000 RPS at peak. Without a load balancer in front, you cannot spread that load across 10+ servers. With one, you can scale horizontally almost indefinitely.

## 2. How It Actually Works (Deep Mechanics)

### L4 Load Balancing — Transport Layer

An L4 load balancer (also called a **network load balancer** or **TCP load balancer**) operates at the Transport layer. It sees TCP or UDP packets and makes routing decisions based on the **5-tuple**: `{src_ip, src_port, dst_ip, dst_port, protocol}`.

It does **not** open the TCP payload. It does not parse HTTP. It does not read cookies. It just forwards packets.

**Step-by-step — one new TCP connection:**

```
1. Client sends SYN packet to VIP 203.0.113.10:443
2. L4 LB receives SYN at its NIC
3. LB hashes the 5-tuple → maps to backend B3 (192.168.1.13:443)
4. LB rewrites dst IP/port (DNAT) or tunnels via IP-in-IP
5. LB forwards the SYN to B3
6. B3 sends SYN-ACK → LB translates src IP back to VIP → client
7. 3-way handshake completes: client ↔ LB ↔ B3 (transparent)
8. All subsequent packets for this 5-tuple go to B3 (via connection table)
```

```
                    ┌──────────────────────────────────────┐
Client              │         L4 Load Balancer             │    Backend Pool
10.0.0.5:52341 ────►│  Connection Table                    │───► B1: 192.168.1.11:8080
                    │  ┌──────────────────────────────┐   │───► B2: 192.168.1.12:8080
                    │  │ 10.0.0.5:52341 → B3          │   │───► B3: 192.168.1.13:8080
                    │  │ 10.0.0.8:61002 → B1          │   │───► B4: 192.168.1.14:8080
                    │  │ 10.0.0.9:44312 → B2          │   │
                    │  └──────────────────────────────┘   │
                    │  (Maglev / consistent hash ring)     │
                    └──────────────────────────────────────┘
```

**Key properties of L4:**
- Does not terminate TLS — the TLS session is end-to-end between client and backend
- Cannot read HTTP headers, cookies, or paths
- Connection table must be replicated across LB instances (stateful)
- **Latency: 50–100 μs** added p99 (just a hash lookup + NAT)
- **Throughput: 10–40 Gbps per commodity node** (10–20 million packets/second)
- Cloudflare's XDP-based Unimog L4 LB processes **300+ million packets/second** during DDoS attacks
- Maintains **10+ million concurrent TCP connections** per instance

### L7 Load Balancing — Application Layer

An L7 load balancer (also called an **application load balancer** or **HTTP load balancer**) terminates TCP and TLS, parses the application protocol (HTTP/1.1, HTTP/2, gRPC, WebSocket), and routes based on application-level attributes.

**Step-by-step — one new HTTP request:**

```
1.  Client opens TCP connection to LB VIP: SYN → SYN-ACK → ACK
2.  Client sends TLS ClientHello
3.  LB terminates TLS (has the certificate + private key)
4.  LB reads HTTP request:
      GET /api/v2/users/123 HTTP/1.1
      Host: api.example.com
      Cookie: session=abc123
5.  LB evaluates routing rules:
      - Path starts with /api/ → api-backend pool
      - Cookie session=abc123 → sticky to server S7 (if session affinity on)
      - Header X-Region: eu → eu-backend pool
6.  LB opens (or reuses pooled) TCP connection to chosen backend
7.  LB forwards parsed HTTP request to backend
8.  Backend responds → LB buffers response → sends to client
```

```
Client                L7 Load Balancer                  Backend Pools
  │                         │                                │
  │──── TCP SYN ───────────►│                                │
  │◄─── SYN-ACK ────────────│                                │
  │──── TLS ClientHello ───►│  (TLS terminates here)         │
  │◄─── TLS ServerHello ────│                                │
  │                         │                                │
  │──── HTTP GET /api/v2 ──►│  Parse headers, path, cookies  │
  │                         │  Select pool: api-backend      │
  │                         │  Select server: least-conn     │
  │                         │──── HTTP GET /api/v2 ─────────►│ api-backend
  │                         │◄─── HTTP 200 OK ───────────────│
  │◄─── HTTP 200 OK ────────│                                │
```

**Key properties of L7:**
- Terminates TLS: the LB holds your certificate; backends can use plaintext internally
- Can route by: URL path, HTTP method, Host header, query params, cookies, source IP, custom headers, JWT claims
- Can rewrite headers, inject `X-Forwarded-For`, add CORS headers
- Can perform request/response buffering, compression (gzip/br), caching
- **Latency: 0.5–3 ms** added p99 (TLS termination + HTTP parse + connection pool lookup)
- **Throughput: 1–5 Gbps per commodity node** (1–2 million requests/second)
- **Concurrent connections: 100 000–1 000 000** per instance (limited by per-connection TLS state ~16 KB each)

### Core Routing Algorithms

| Algorithm | How It Works | Best For | Pitfall |
|---|---|---|---|
| **Round Robin** | Each request → next server in circular list | Homogeneous servers, uniform request cost | Short requests skip overloaded servers; ignores load |
| **Weighted Round Robin** | Same but servers have weights (e.g., 3:1:1) | Mixed server capacities | Weights must be tuned manually |
| **Least Connections** | Route to server with fewest active connections | Variable-duration requests (file uploads, streaming) | Connection count ≠ CPU load |
| **Weighted Least Connections** | Least connections adjusted by server weight | Mixed capacity + variable load | Same tuning complexity as weighted RR |
| **IP Hash** | `hash(src_ip) % N` selects server | Session affinity without cookies | Uneven distribution with NAT; breaks on backend count change |
| **Consistent Hashing** | Hash key maps to position on virtual ring; closest node wins | Session affinity that survives node additions/removals | Hotspots if keys cluster; requires tuning virtual nodes |
| **Power of Two Choices (P2C)** | Pick 2 random backends, send to less-loaded one | Large pools (>50 servers) where least-conn is expensive | Requires real-time load metric |
| **Random** | Pick any server uniformly at random | Very large homogeneous pools | No locality awareness |

### Consistent Hashing Deep Dive — Google Maglev

Google's **Maglev** (published at USENIX NSDI 2016) addressed a fundamental problem: when an L4 LB cluster loses a node, a simple modulo hash reassigns all flows. For TCP, this means dropping live connections.

Maglev's approach:
1. Build a **lookup table** of size M (prime number, default 65 537)
2. Each backend fills the table evenly using a permutation derived from its name
3. A 5-tuple hash maps directly to a table index → backend selection is O(1)
4. When a backend is added/removed, only ~1/N connections are remapped (vs. all connections with modulo hashing)

Facebook's **Katran** (open source) and Cloudflare's **Unimog** both use Maglev-style consistent hashing. AWS NLB uses a proprietary flow-hash algorithm with similar properties.

### Health Checks

Load balancers continuously probe backends to determine if they are healthy:

- **Passive health checks:** Observe real traffic. If a backend returns 5xx or times out, mark it degraded. Fast but lags behind actual failures.
- **Active health checks (preferred):** The LB itself sends synthetic requests (e.g., `GET /health`) on a schedule. Default cadence in HAProxy: every 2 seconds, 3 failures = unhealthy, 2 successes = healthy again.

```
HAProxy active check example:
option httpchk GET /health HTTP/1.1\r\nHost:\ localhost
http-check expect status 200
default-server inter 2s fall 3 rise 2
```

This means: check every 2 seconds; after 3 consecutive failures, remove from rotation (takes ~6 seconds); after 2 consecutive successes, restore (takes ~4 seconds).

### Misconceptions

**❌ Misconception:** "An L7 load balancer is strictly better than L4 — it does more."

**✅ Reality:** L7 is ~10–30x slower and uses far more CPU/memory per connection than L4. At 100 Gbps traffic volumes, L7 is not computationally feasible. At DDoS scale, you must absorb packets at L4 before they reach L7. Most production systems layer them: L4 at the edge for raw throughput, L7 behind it for routing intelligence.

---

**❌ Misconception:** "Load balancers are stateless, so they don't fail."

**✅ Reality:** L4 LBs maintain a connection tracking table (stateful). If the LB dies, all TCP connections to backends from that LB are reset. This is why real deployments run LBs in HA pairs (active-passive) or use consistent hashing so a secondary LB can pick up flows without losing connections.

---

**❌ Misconception:** "Round robin distributes load evenly."

**✅ Reality:** Round robin distributes *connections* evenly, not *work*. If request #1 is a fast health check (0.1 ms) and request #2 is a slow DB query (500 ms), both go to different backends but one backend is idle while the other is saturated. Least connections or P2C is almost always better for heterogeneous workloads.

## 3. Real-World Architecture Examples

### Cloudflare — Unimog (L4) + Custom L7

**Scale trigger:** Cloudflare handles **2+ trillion DNS queries per day** and has a global anycast network across 300+ data centers. Traditional per-rack hardware load balancers could not be deployed at that density without prohibitive hardware costs.

**What they built:** In 2020, Cloudflare published **Unimog**, an L4 load balancer that runs *on the same commodity Linux servers* that also serve application traffic. Unimog uses XDP (eXpress Data Path) — an eBPF hook in the Linux kernel that intercepts packets before they reach the normal network stack, at the driver level.

**The clever design decision:** Instead of a dedicated load-balancer tier, every Cloudflare edge server runs Unimog. It costs less than **1% of CPU utilisation** on the same machine that serves HTTP traffic. This eliminates an entire hardware tier.

**Consistent hashing:** Unimog uses a Maglev-style forwarding table. Global anycast routes client traffic to the nearest PoP via BGP; within the PoP, ECMP spreads flows across edge servers; Unimog on each edge server uses consistent hashing to forward to the correct backend.

**What they got wrong first:** Early anycast deployments had issues with **TCP flapping** — a client's routing path could change mid-connection, sending subsequent packets to a different PoP. Cloudflare solved this with careful BGP route dampening and connection tracking.

**Reference:** [Unimog — Cloudflare's edge load balancer](https://blog.cloudflare.com/unimog-cloudflares-edge-load-balancer/)

---

### Netflix — Zuul + AWS ELB Two-Tier Architecture

**Scale trigger:** Netflix streams to **238 million subscribers** globally. At peak, that represents ~15% of all internet downstream bandwidth. A single tier of routing cannot handle this volume with the routing intelligence needed.

**What they built:** Netflix uses a two-tier architecture:
1. **AWS NLB (L4)** at the outermost edge for raw TCP termination, DDoS absorption, and cross-AZ routing. NLBs route based on 5-tuple hash across availability zones.
2. **Zuul (L7 API Gateway)** built on Netty — a custom in-house L7 proxy running on EC2 in each region. Zuul routes based on URL paths, query params, A/B test cookies, and device type headers.

**Routing intelligence at L7:** Zuul enables Netflix's infamous A/B testing at routing time. A single request to `/api/v3/recommendations` can be routed to different backend clusters based on a `bucket` cookie, allowing simultaneous testing of multiple recommendation algorithm versions without client-side logic.

**What they got wrong first:** Netflix originally used a single-tier ELB. As they moved to microservices (~2012), ELB's lack of path-based routing forced every service to have its own DNS name and load balancer, creating ~700+ ELBs with corresponding costs and operational overhead. Zuul centralised L7 routing, reducing the ELB count dramatically.

**Reference:** [Netflix Zuul — Edge Service in the Cloud](https://netflixtechblog.com/zuul-2-the-netflix-journey-to-asynchronous-non-blocking-systems-45947377fb5c)

---

### Discord — From ELB to HAProxy for WebSocket at Scale

**Scale trigger:** Discord serves **~19 million concurrent users**. The vast majority maintain a persistent WebSocket connection for real-time messaging. Standard HTTP load balancers handle WebSocket upgrade, but the sticky session requirements are brutal: a dropped WebSocket means the client must re-authenticate and re-subscribe to all guilds.

**What they got wrong first (2018):** Discord was using AWS ALB for WebSocket load balancing. At their scale, ALB's connection limits per target were being hit, and the lack of granular connection drain control meant rolling deploys caused mass client disconnects.

**What they switched to:** HAProxy in L7 mode with `option http-server-close` disabled (keep connections alive) and `timeout tunnel 0` for WebSocket connections. HAProxy's `stick table` feature maintains session affinity by mapping a session token to a specific backend, surviving backend restarts via peer synchronisation.

**Scale lesson:** Discord found that for WebSocket workloads, the "right" algorithm is **least connections, not round robin**. A server that has been up longer has more accumulated WebSocket connections. Round robin would overload it with new connections while newer servers sit underutilised.

**Reference:** [Discord blog — How Discord Scaled Elixir to 5,000,000 Concurrent Users](https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users)

---

### GitHub — HAProxy at the Edge

GitHub has used HAProxy in production since 2012 and is one of its most-cited reference deployments. GitHub runs HAProxy instances at their edge, configured for both L4 (TCP mode for Git SSH) and L7 (HTTP mode for web/API traffic).

Their key configuration insight: **connection rate limiting per source IP at the load balancer level**, not at the application server level. This prevents a single abusive client from consuming backend connections.

### Design Questions to Ask Before Starting

Before choosing or designing a load balancing architecture, answer these:

1. **What protocol?** HTTP/HTTPS only, or also WebSocket, gRPC, raw TCP, UDP (gaming, VoIP)?
2. **Do you need SSL/TLS termination?** If yes, must be L7. If you need mTLS between services, where does it terminate?
3. **Is the workload stateless?** If backends hold session state in memory, you need sticky sessions or must externalise state to Redis.
4. **What are your SLOs?** < 1 ms p99 requires L4. < 10 ms p99 is achievable at L7.
5. **What is the traffic pattern?** Uniform short requests (REST API), long-lived connections (WebSocket), large uploads (multipart), streaming (video)?
6. **What is your failure blast radius?** If the load balancer dies, what percent of traffic is affected?
7. **Do you need observability?** L7 gives you per-request metrics (status codes, latency histograms, path breakdowns). L4 only gives you byte/packet counts.
8. **Managed vs. self-operated?** AWS ALB/NLB have a $0.008–$0.018/LCU-hour cost model; self-hosted HAProxy has ~$0 software cost but ops burden.

### Scale Evolution

#### 1 000 users — Single server, no LB needed
Traffic: ~50–200 RPS. A single well-tuned app server handles this easily.
Decision: Don't add a load balancer yet. Premature complexity. Use a CDN for static assets.

#### 100 000 users — First load balancer
Traffic: ~2 000–10 000 RPS. First vertical scaling, then horizontal.
**Introduce:** A single L7 load balancer (nginx or AWS ALB). Route all HTTP(S) traffic through it.
Key decisions: Do you terminate TLS at the LB or pass through? (Terminate at LB — simpler cert management.) Do you need sticky sessions? (Probably not if your app is stateless — design it to be.)

#### 1 000 000 users — HA load balancers + health checks
Traffic: ~20 000–100 000 RPS. A single LB is now a SPOF.
**Introduce:** HA pair (active-passive via VRRP, or active-active via DNS round-robin). L7 LBs behind an L4 LB or AWS NLB.
Key decisions: Which health check endpoint? (`GET /health` should check all dependencies, not just HTTP 200 from a static response.) What is your connection drain timeout? (30 seconds is standard — long enough for in-flight requests to complete.)

#### 100 000 000 users — Global load balancing + multi-tier
Traffic: ~2 000 000 RPS, global distribution. Single-region is now a SPOF.
**Introduce:** Anycast + GeoDNS to route users to the nearest region. Per-region L4 → L7 tiers. Consistent hashing at L4 to survive cluster membership changes without dropping connections. Service mesh (Envoy/Istio) at the microservice layer.
Key decisions: How do you handle cross-region failover? (DNS TTL 30s + health-check driven failover is the minimum. Anycast is better for L4.) How do you drain a region for maintenance without dropping connections?

## 5. Code / Implementation Perspective

### Python — Naive L7 Load Balancer (Least Connections)

This is runnable pseudocode that demonstrates the core algorithm. A production implementation would add TLS termination, connection pooling, and async I/O.

```python
import asyncio
import aiohttp
from dataclasses import dataclass, field
from typing import List
import time

@dataclass
class Backend:
    url: str
    active_connections: int = 0
    healthy: bool = True
    last_check: float = field(default_factory=time.time)
    consecutive_failures: int = 0

class LeastConnectionsLB:
    """
    L7 HTTP load balancer using least-connections algorithm.
    Includes active health checks every 5 seconds.
    """
    def __init__(self, backends: List[str], health_path: str = "/health"):
        self.backends = [Backend(url=b) for b in backends]
        self.health_path = health_path

    def select_backend(self) -> Backend | None:
        """
        Power of Two Choices variant:
        Pick the backend with the fewest active connections
        among all healthy backends.
        """
        healthy = [b for b in self.backends if b.healthy]
        if not healthy:
            return None
        return min(healthy, key=lambda b: b.active_connections)

    async def proxy_request(self, request_path: str, method: str = "GET") -> dict:
        backend = self.select_backend()
        if backend is None:
            raise RuntimeError("No healthy backends available")

        backend.active_connections += 1
        try:
            async with aiohttp.ClientSession() as session:
                async with session.request(
                    method,
                    f"{backend.url}{request_path}",
                    timeout=aiohttp.ClientTimeout(total=30)
                ) as resp:
                    return {
                        "status": resp.status,
                        "body": await resp.text(),
                        "backend": backend.url,
                    }
        except Exception as e:
            backend.consecutive_failures += 1
            if backend.consecutive_failures >= 3:
                backend.healthy = False
            raise
        finally:
            backend.active_connections -= 1

    async def health_check_loop(self):
        """Active health checks: probe every 5 seconds."""
        while True:
            await asyncio.gather(*[self._check(b) for b in self.backends])
            await asyncio.sleep(5)

    async def _check(self, backend: Backend):
        try:
            async with aiohttp.ClientSession() as session:
                async with session.get(
                    f"{backend.url}{self.health_path}",
                    timeout=aiohttp.ClientTimeout(total=2)
                ) as resp:
                    if resp.status == 200:
                        backend.consecutive_failures = 0
                        if not backend.healthy:
                            print(f"[RECOVERY] {backend.url} is back online")
                        backend.healthy = True
                    else:
                        backend.consecutive_failures += 1
        except Exception:
            backend.consecutive_failures += 1

        if backend.consecutive_failures >= 3 and backend.healthy:
            print(f"[FAIL] Marking {backend.url} as unhealthy")
            backend.healthy = False

# Usage
lb = LeastConnectionsLB(
    backends=["http://10.0.0.1:8080", "http://10.0.0.2:8080", "http://10.0.0.3:8080"]
)
```

### HAProxy Configuration Example (L7 with Health Checks)

```haproxy
global
    log stdout format raw local0
    maxconn 50000
    nbthread 4

defaults
    log     global
    mode    http
    option  httplog
    option  dontlognull
    option  forwardfor        # adds X-Forwarded-For header
    option  http-server-close # enables connection reuse
    timeout connect  5s
    timeout client   30s
    timeout server   30s

frontend api_frontend
    bind *:443 ssl crt /etc/ssl/certs/server.pem  # TLS termination at LB
    default_backend api_servers

    # L7 path-based routing
    acl is_admin  path_beg /admin
    use_backend   admin_servers  if is_admin

backend api_servers
    balance leastconn                          # algorithm: least connections
    option  httpchk GET /health HTTP/1.1       # active health check
    http-check send hdr Host localhost
    http-check expect status 200
    default-server inter 2s fall 3 rise 2 weight 1

    server api1 192.168.1.11:8080 check
    server api2 192.168.1.12:8080 check
    server api3 192.168.1.13:8080 check

backend admin_servers
    balance roundrobin
    option  httpchk GET /admin/health
    http-check expect status 200
    default-server inter 5s fall 2 rise 1

    server admin1 192.168.1.21:8080 check
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **DNS Round-Robin only** | Tiny deployments, < 1K RPS, stateless, tolerant of uneven load | Zero infrastructure cost vs. no health checks, TTL-delayed failover (60s+), uneven distribution | Legacy apps, internal tools |
| **L4 only (NLB/HAProxy TCP)** | Non-HTTP protocols, maximum throughput, no routing logic needed | 10–40 Gbps throughput vs. no path routing, no TLS termination, harder observability | Gaming servers, MQTT brokers, DB connection pools |
| **L7 only (ALB/nginx/HAProxy HTTP)** | Standard web apps, path routing needed, need request-level metrics | Rich routing and observability vs. 0.5–3 ms added latency, higher CPU cost | Most web apps/APIs |
| **L4 + L7 two-tier** | Production web at scale (>100K RPS), DDoS protection required | Best of both worlds vs. two failure domains, added complexity | Netflix, Cloudflare, Stripe |
| **Service mesh (Istio/Envoy sidecar)** | Microservices with mTLS, circuit breaking, distributed tracing needs | Zero-trust security + observability vs. 2–5 ms sidecar overhead, operational complexity | Uber, Lyft, Airbnb |
| **Client-side LB (gRPC, Ribbon)** | gRPC services, no network hop for LB, aware of backend health | Eliminates a network hop vs. logic lives in every client, version skew, harder ops | Netflix (Ribbon), gRPC-heavy microservices |
| **Anycast (BGP)** | CDN edge, DDoS absorption, global distribution | Absorbs massive attack traffic vs. requires BGP, complex operational setup, not available outside cloud/CDN providers | Cloudflare, Fastly, AWS Shield |

### My Opinionated Recommendation

For most teams shipping a web product or API:

**Use AWS ALB (L7)** if you are on AWS. It is managed, scales automatically, integrates natively with ACM for certs, ECS/EKS for container health, and WAF for security. The cost is predictable. You do not need to operate software load balancers until you need capabilities ALB cannot provide.

**Add NLB in front of ALB** only when you need a static IP (for IP whitelisting by customers), need to handle non-HTTP protocols on the same entry point, or are seeing DDoS traffic that ALB cannot absorb.

**Use HAProxy** when you are not on AWS, need sub-millisecond routing decisions, need custom ACL logic that managed LBs do not support, or have existing expertise. HAProxy's performance ceiling (~2M+ RPS on tuned hardware) exceeds any managed option.

**Do not reach for a service mesh** until you have >20 microservices and are actively struggling with mTLS management or distributed tracing gaps. The operational overhead is real.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **Horizontal scalability with zero client changes.** Add 10 more backends tonight and clients never know. No DNS change, no re-deploy, no config push to clients. This is the fundamental value proposition.
- **High availability without application-layer awareness.** A backend crash is invisible to users. Health checks detect failures in 6–10 seconds (3 × 2-second intervals); the LB removes the bad backend silently.
- **TLS offloading (L7)** reduces CPU on backend servers by 30–60% for TLS 1.3 workloads. Cert management is centralised; renewing a cert means updating one LB, not 50 backends.
- **Observability.** An L7 LB in the request path gives you per-path latency histograms, status code distributions, and request rates across all backends from a single choke point. This is an architectural advantage, not just a feature.
- **Traffic shaping.** Rate limiting, connection limits per IP, request queuing, and graceful drain during deploys are all easier to implement at the LB than inside application code.

### Costs and Limitations

- **Added latency.** Even a well-tuned L7 LB adds 0.5–3 ms p99. For < 1 ms SLOs (HFT, some gaming), this is a deal-breaker.
- **Single point of failure (if misconfigured).** A misconfigured health check that passes when backends are actually broken turns your LB into a request black hole, not a shield. The LB can be the most dangerous component in your stack.
- **SSL/TLS complexity.** L7 LB terminates TLS, so it must hold your private keys. Backend communication is often plaintext inside your VPC. This is a security trade-off: convenient cert management vs. unencrypted internal traffic (mitigated with mTLS or service mesh).
- **Cost at scale.** AWS ALB LCU pricing can exceed $10 000/month for high-traffic applications. At 10M RPS sustained, the ALB cost rivals running your own HAProxy fleet.
- **Sticky sessions are a footgun.** They re-introduce statefulness. A sticky-sessioned backend dying means those clients experience failures until they get re-routed. Prefer externalising session state to Redis.

### The Core Tension

**Routing intelligence (L7) vs. raw throughput (L4).**

Every layer of intelligence you add (parse HTTP, read headers, evaluate ACLs) has a cost in latency and CPU. The L4 ↔ L7 choice is always a point on this curve. You pay the L7 tax for path routing, TLS termination, and observability. If those are not requirements, L4 is the right answer.

### My Recommendation

**Start with managed L7 (AWS ALB or Cloudflare).** The operational overhead of self-hosted LBs is the main risk for teams under 20 engineers. A misconfigured HAProxy is worse than a slightly-more-expensive ALB.

**Add L4 (NLB) in front of L7 when** you need DDoS absorption, a static IP, or protocol flexibility. This is the tier that must never fail; managed options are safer than self-hosted.

**Run self-hosted HAProxy or nginx** only when you have a dedicated SRE team, need features managed LBs lack, or the cost delta justifies the ops burden. GitHub, Reddit, and many infrastructure-focused companies run HAProxy well — but they have deep networking expertise.

## 9. Failure Modes — What Goes Wrong

### Health Check Passes When Backend Is Actually Broken

**Trigger:** The health check endpoint (`/health`) returns HTTP 200 even though the application is unable to serve real traffic. Common causes: health endpoint does not check DB connectivity, cache, or downstream service health; health check runs on a different thread/process than the main request handler.

**Symptoms:** Load balancer keeps routing to the broken backend. Users see 500s or timeouts. Error rate rises gradually as traffic accumulates on the broken backend.

**Detection:** Alert on `5xx rate > 1%` per backend host. Use deep health checks that test a DB read: `SELECT 1`. Cross-reference LB backend health status with application error metrics.

**Recovery:** Fix the health endpoint to check actual dependencies. Add `http-check expect` to validate response body, not just status code. Temporarily force the backend out of rotation via LB admin API.

**Real Example:** A 2023 Cloudflare incident where a React bug caused excessive API calls; the backend service was technically "alive" (returned 200 on `/health`) but was returning errors on all real requests because an upstream dependency was timing out. The health check was too shallow.

---

### Thundering Herd on Backend Recovery

**Trigger:** A backend goes down, all its traffic redistributes to remaining backends. The failed backend recovers and passes health checks. The LB immediately sends all previously-held connections to the recovered backend at once.

**Symptoms:** Recovered backend immediately crashes again under the reconnection burst. The remaining healthy backends receive traffic spikes during each recovery attempt. The failure becomes self-perpetuating.

**Detection:** Alert on recovery loop: backend marked unhealthy → healthy → unhealthy within 2 minutes. Observe per-backend RPS spiking to 3–5× normal on recovery events.

**Recovery:** Use **slow-start** (HAProxy: `slowstart 60s` on server line). This ramps traffic to a recovering backend from 0 to full weight over 60 seconds, allowing it to warm up caches and JIT. Alternatively, cap connections with `maxconn` per server.

**Real Example:** Discord (2023) — a flapping service came back online and immediately received all reconnecting clients from ~19 million concurrent users. The frontend services ran out of memory filling internal queues. Post-mortem action: added exponential backoff with jitter on client reconnects and slow-start at the LB tier.

---

### Cascading Failure via Insufficient Connection Draining

**Trigger:** Rolling deploy begins. LB deregisters backend-1 (draining in progress). Backend-1 has `deregistration_delay` set to 0 (or too short). In-flight requests to backend-1 get reset. Clients retry immediately → spike to backend-2 and backend-3. If they are near capacity, they also start failing.

**Symptoms:** Error rate spikes during every deploy. Errors last 1–30 seconds then subside. Looks like a bug in the new code but is actually a connection-draining configuration issue.

**Detection:** Correlate deploy events with error rate graphs. Check that p99 error spikes align with deregistration events. Log in-flight connection count at drain start.

**Recovery:** Set `deregistration_delay` / `timeout server-fin` to at least 30 seconds (60–120 seconds for slow requests). Use connection drain, not hard kill. AWS ALB default is 300 seconds; many teams reduce this too aggressively.

**Real Example:** Amazon Kinesis (2020) — a frontend fleet change caused servers to start failing health checks simultaneously. Because drain was not properly configured, connections were dropped rather than drained. The cascading failure knocked out multiple AWS services for ~8 hours. Post-mortem: implement cell-based architecture to bound blast radius, ensure drain timeouts are never set below 60 seconds.

---

### Asymmetric Load Due to Misconfigured Consistent Hashing

**Trigger:** IP-hash or consistent hashing is configured for session affinity. A large percentage of clients are behind a corporate NAT (e.g., a university) and all appear as the same source IP. Alternatively, a small number of IP ranges are responsible for most traffic.

**Symptoms:** One backend receives 60–80% of traffic while others sit idle. CPU on the hot backend is pegged; others are near 0%. Autoscaling does not help because new instances get no traffic (hash doesn't include them without a re-hash).

**Detection:** Monitor per-backend RPS from the LB. Alert if any backend handles > 2× the average RPS. Plot the backend distribution histogram; it should be roughly uniform.

**Recovery:** Switch from IP-hash to a session cookie for affinity (L7 required). Use consistent hashing on a session ID or user ID from the application payload, not source IP. Add virtual nodes to the consistent hash ring to improve distribution.

**Real Example:** Many production HAProxy deployments behind enterprise networks. The fix is using `balance hdr(X-Session-ID)` or setting a sticky cookie via `cookie SERVER insert indirect nocache`.

## 10. When To Use vs. When To Avoid

### ✅ Use When

1. **You have more than one backend server handling the same workload.** This is the most obvious case. Even two servers need a load balancer to distribute traffic and handle failover automatically.

2. **You need zero-downtime deploys.** A load balancer enables rolling deployments: drain connections from backend-1 → deploy new version → re-register → repeat. Without a LB, any deploy causes a brief outage.

3. **You need automatic failure recovery.** If any backend process crashes, health checks detect it within 6–10 seconds and stop routing traffic to it. This is especially critical in containerised environments where pods restart frequently.

4. **You need TLS termination at a central point.** Managing SSL certificates on 50 backend servers is operationally painful. Centralising TLS at the LB means one cert, one renewal process, one place to enforce cipher suites and TLS version policy.

5. **You need routing by URL path, hostname, or other L7 attributes.** A single IP/domain can route to different backend pools based on `/api` vs `/web` vs `/admin`. Without an L7 LB, this requires separate DNS names or application-level dispatch logic.

6. **You need DDoS mitigation or rate limiting at the network edge.** An L4 LB (or Cloudflare in front) can absorb volumetric DDoS attacks before they reach application servers, which are expensive to scale for attack traffic.

### ❌ Do NOT Use When

1. **Your entire backend is a single function / serverless.** AWS Lambda + API Gateway, Cloudflare Workers, and Vercel edge functions all handle load distribution internally. Adding a load balancer in front adds latency without benefit.

2. **Latency SLOs are < 1 ms p99.** Any L7 LB adds 0.5–3 ms. For HFT (high-frequency trading), certain gaming scenarios, or real-time bidding, the LB latency budget is unacceptable. Use L4 kernel-bypass (DPDK, XDP) or no LB at all.

3. **You have a single backend handling stateful protocol sequences that cannot be interrupted.** Some legacy protocols (certain FTP modes, specific SMTP sequences) do not tolerate connection re-use or routing changes mid-session. Understand the protocol before inserting a LB.

4. **Simplicity is more important than scale (prototype/MVP).** A pre-product startup with 50 users does not need a load balancer. Every infrastructure component is a failure domain. Do not add them before you need them.

### ⚠️ #1 Mistake Engineers Make

**Enabling sticky sessions (session affinity) as the default, without externalising session state.**

Sticky sessions seem like an easy fix for stateful applications (user sessions stored in memory on the backend). They work until a backend restarts, fails, or is replaced during a deploy. Suddenly, all sessions on that backend are lost, and because clients were stuck to it, they all hit errors simultaneously rather than being smoothly redistributed.

The correct fix is: externalise session state to Redis or a DB. Make backends stateless. Then you never need sticky sessions, and the load balancer can freely redistribute traffic. This is the architectural fix; sticky sessions are a band-aid that makes failures worse and harder to debug.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a globally available API that can handle 1 million requests per second."
- "How does a load balancer work, and what's the difference between L4 and L7?"
- "You notice that one of your backend servers is receiving 70% of traffic while others are idle. What's wrong and how do you fix it?"
- "How would you implement zero-downtime deployments for a stateful application?"
- "Walk me through what happens when a user hits api.example.com and one of your backends is down."
- "What is consistent hashing and why do load balancers use it?"
- "How would you design the load balancing layer for a real-time multiplayer game?"

### What the Interviewer is Evaluating

- **Depth on the OSI model distinction:** Can you explain why L4 is faster, and why L7 is necessary for certain use cases, without just reciting definitions?
- **Operational thinking:** Do you mention health checks, drain timeouts, failure modes, and observability? Or just "route to the least-loaded server"?
- **Trade-off awareness:** When you describe consistent hashing, do you also mention its failure modes (hotspots)? When you describe L7, do you quantify the latency cost?
- **Real-world grounding:** Can you name a real tool (HAProxy, ALB, nginx, Envoy) and describe a specific configuration decision?

### Questions YOU Should Ask Before Answering

In a system design interview, asking clarifying questions before diving in demonstrates senior-level thinking:

1. "What protocols does the system need to support — HTTP only, or also WebSocket, gRPC, or raw TCP?"
2. "What are the latency requirements? Is this a user-facing API (< 100 ms p99) or a trading system (< 1 ms)?"
3. "Is the application stateless, or does it store session state in memory on the backend?"
4. "What is the geographic distribution of users — single region, multi-region, global?"
5. "Are there cost constraints, or is this a greenfield design on a major cloud provider?"

### Junior (L3–L4) Answer

A junior engineer should explain the core function clearly:

> "A load balancer sits in front of your backend servers and distributes incoming requests across them. If you have 3 servers, it sends roughly 1/3 of requests to each. If one server goes down, health checks detect it and the LB stops sending traffic there. L4 operates at the TCP layer and routes based on IP/port. L7 operates at the HTTP layer and can route based on URL paths or headers. For most web apps, you'd use an L7 load balancer like AWS ALB."

This demonstrates understanding of the basic value proposition and layer distinction.

### Senior (L5) Answer

A senior engineer goes deeper on mechanics and trade-offs:

> "I'd start by clarifying the protocol requirements. For HTTP/HTTPS traffic at typical API scale, I'd use an L7 load balancer — AWS ALB or nginx — because I need TLS termination, path-based routing, and per-request observability. The algorithm I'd choose depends on the workload: least connections for variable-duration requests (uploads, DB-heavy endpoints), round robin only for truly uniform short requests. Critical configuration: health checks must be deep (test the DB, not just return 200), and drain timeout should be at least 30 seconds to handle in-flight requests during deploys.
>
> For the session affinity question: I would not use sticky sessions. Instead, I'd externalise session state to Redis, making all backends stateless and letting the LB freely redistribute. This removes a class of failure entirely.
>
> At higher scale (>100K RPS), I'd put an L4 NLB in front of the L7 tier for DDoS absorption, static IP requirements, and raw throughput. L4 adds ~50–100 μs vs. L7's 0.5–3 ms, so the layered approach costs ~3 ms total — acceptable for web APIs."

### Staff (L6+) Answer

A staff engineer frames the decision in terms of system properties and failure domains:

> "Before choosing a load balancing architecture, I need to understand the failure modes we're designing around. A load balancer is both a single point of control and a potential single point of failure. Every design decision should ask: what fails, at what blast radius, and how quickly can we recover?
>
> For a global API at 1M RPS: I'd use a two-tier architecture. BGP anycast routes users to the nearest PoP (lowest latency, DDoS absorption). Within each PoP, an L4 LB (AWS NLB or HAProxy TCP mode) uses consistent hashing on the 5-tuple — specifically a Maglev-style algorithm — so that LB cluster membership changes don't reset live TCP connections, which is critical for WebSocket and long-lived connections. Behind that, an L7 tier (HAProxy HTTP mode or Envoy) handles path routing, TLS termination, and observability.
>
> For consistent hashing: Maglev gives O(1) lookup and ~1/N connection rehash when a backend is added or removed. The tradeoff is table memory (~512 KB for 65 537 entries) and the cold-start problem — a new backend starts with zero in-flight connections, so I'd use slow-start (60 seconds) to ramp it up.
>
> The hardest operational problem is not the algorithm — it's the thundering herd on recovery. When a backend comes back online after a failure, it will receive all previously-redistributed connections at once. Slow-start at the LB plus exponential backoff with jitter on client retries prevents this from turning into a self-perpetuating failure loop."
