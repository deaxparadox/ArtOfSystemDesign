# 2.2 — HTTP/1.1 vs HTTP/2 vs HTTP/3

> 📍 Phase 2 — Networking & Communication | Section 2.2

**Prerequisites** — Before reading this section, you should already know:
- What TCP and UDP are, and how they differ (Section 2.1)
- What TLS/SSL handshakes are and why HTTPS exists
- What a network round-trip time (RTT) means and how to estimate it (~50ms for same-country, ~150ms cross-continent)
- Basic client-server mental model: browser makes requests, server sends responses
- What DNS resolution is (a hostname lookup before the connection is made)

## 1. What Is It? (Theory)

### Plain English

HTTP (Hypertext Transfer Protocol) is the language that web clients (browsers, mobile apps, API consumers) and web servers use to talk to each other. Every time you load a webpage, fetch an API response, or stream a video, HTTP is the message format defining how those requests and responses are structured and exchanged.

HTTP/1.1, HTTP/2, and HTTP/3 are successive **versions of that same language** — each designed to fix performance bottlenecks that became crippling as the web scaled from simple text pages to complex applications loading 100+ resources per page.

### The Problem Each Version Solved

| Version | Year | The Problem It Solved |
|---|---|---|
| HTTP/1.0 | 1996 | One TCP connection per request (disconnect after every response) |
| HTTP/1.1 | 1997 | Added persistent connections, but requests still serialized on each connection |
| HTTP/2 | 2015 | Added multiplexing to fix application-level head-of-line blocking, but TCP still blocks |
| HTTP/3 | 2022 (RFC 9114) | Replaced TCP with QUIC over UDP to fix transport-level blocking |

### Why It Matters at Scale

Consider loading a modern webpage that requires 80 separate resources (HTML, CSS, JS bundles, fonts, images, API calls). With HTTP/1.1, a browser opens at most **6 TCP connections per domain** — a hard-coded browser limit. Those 80 resources must queue across 6 lanes. Each TCP connection requires a 1-RTT handshake + 1-RTT TLS handshake = **2 RTTs before the first byte of data**, or 3 RTTs with TLS 1.2. At 100ms RTT, that's 300ms wasted per new connection.

With HTTP/2, all 80 requests share **1 TCP connection** with multiplexed streams. With HTTP/3, they share **1 QUIC connection** where packet loss on one stream doesn't stall the others.

### Real-World Analogy

Imagine a restaurant:

- **HTTP/1.1**: One waiter who takes your order, goes to the kitchen, returns with your food, then takes the next order. The kitchen can only process 6 tables at a time. New tables wait outside in the cold.
- **HTTP/2**: One waiter who takes all orders from all tables at once, sends them all to the kitchen simultaneously, and delivers in any order. But if the kitchen door gets stuck (packet loss), every table waits.
- **HTTP/3**: Same as HTTP/2, but each table has its own kitchen hatch. If one hatch gets stuck, only that table waits — the rest keep receiving food.

### Real Numbers

On a page with 80 resources at 100ms RTT:

- **HTTP/1.1**: ~6 parallel connections, resources queue ~13 deep per connection → estimated 1,300ms+ of serialized wait time before multiplexing benefit
- **HTTP/2**: All 80 resources multiplexed on 1 connection. Connection setup: 1 RTT (TCP) + 1 RTT (TLS 1.3) = 200ms. Parallelism: all 80 in-flight simultaneously
- **HTTP/3 (QUIC)**: 0-RTT resumption possible for returning users, 1-RTT for new connections. Under 1% packet loss, 20-30% faster than HTTP/2 for resource-heavy pages

## 2. How It Actually Works (Deep Mechanics)

### HTTP/1.1 Mechanics

HTTP/1.1 introduced persistent connections (`Connection: keep-alive`) so the TCP socket stays open between requests. But it is fundamentally **request-response serial** per connection:

```
Client                  Server
  |                       |
  |-- GET /index.html --> |
  |<-- 200 OK HTML ------|
  |                       |
  |-- GET /style.css ---> |  (must wait for HTML response to start)
  |<-- 200 OK CSS --------|
  |                       |
  |-- GET /app.js ------> |  (must wait for CSS)
  |<-- 200 OK JS ---------|
```

**Pipelining** was specified in HTTP/1.1 but almost never used in practice because responses must arrive in order (application-level head-of-line blocking), and proxy/middlebox support was poor. Every major browser disabled it by default. Consider pipelining dead.

**The 6-connection workaround**: Browsers compensate by opening up to 6 TCP connections per hostname. This is a hack — 6 TCP connections mean 6 separate TLS handshakes, 6 separate congestion windows, and 6 × the server memory overhead.

```
Browser                            Server
  |                                  |
  |-- TCP conn 1: GET /a.css ------> |
  |-- TCP conn 2: GET /b.css ------> |
  |-- TCP conn 3: GET /c.js -------> |
  |-- TCP conn 4: GET /d.js -------> |
  |-- TCP conn 5: GET /font.woff --> |
  |-- TCP conn 6: GET /image.png --> |
  |                                  |
  | ... remaining 74 resources QUEUE |
```

**Key HTTP/1.1 numbers:**
- Max parallel requests per domain: 6 (Chrome/Firefox), 8 (IE11)
- TLS 1.3 handshake: 1 RTT (was 2 RTT for TLS 1.2)
- Header format: plain ASCII text, uncompressed, repeated every request
- Average header size per request: 500–800 bytes (repeated for every one of 80 requests = ~50KB wasted overhead)

### HTTP/2 Mechanics

HTTP/2's fundamental change is **binary framing** and **stream multiplexing** over a single TCP connection.

```
HTTP/2 Binary Framing Layer

+----------------------------+
|       HTTP/2 Frame         |
+--------+--------+----------+
| Length | Type   | Flags    |  (9-byte header)
+--------+--------+----------+
| Stream ID (31-bit)         |
+----------------------------+
| Frame Payload              |
+----------------------------+

Stream IDs: client-initiated = odd (1, 3, 5...)
            server-initiated = even (2, 4, 6...)
            Stream 0         = connection-level control
```

**Multiplexing on one TCP connection:**

```
Client                              Server
  |                                    |
  |-- HEADERS frame (stream 1) ------> |  GET /index.html
  |-- HEADERS frame (stream 3) ------> |  GET /style.css
  |-- HEADERS frame (stream 5) ------> |  GET /app.js
  |                                    |
  |<-- DATA frame (stream 3) ---------|  CSS arrives first (prioritized)
  |<-- DATA frame (stream 1) ---------|  HTML arrives
  |<-- DATA frame (stream 5) ---------|  JS arrives
  |                                    |
  (all interleaved on ONE TCP connection)
```

**HPACK header compression**: HTTP/2 compresses headers using a static table (common headers like `:method: GET`) and a dynamic table (headers seen in previous requests). A repeated `Cookie` header that would cost 400 bytes in HTTP/1.1 costs ~10 bytes after the first request.

**The TCP Head-of-Line Blocking Problem (HTTP/2's Achilles heel)**:

```
                      PACKET LOSS SCENARIO

Stream 1 data:  [pkt1][pkt2][ LOST ][pkt4][pkt5]
Stream 3 data:  [pkt6][pkt7][pkt8][ LOST ][pkt10]
Stream 5 data:  [pkt11][pkt12][pkt13][pkt14][ LOST ]

TCP view: ONE ordered byte stream.
When pkt3 (Stream 1) is lost:
  TCP retransmits pkt3.
  Stream 3 data (pkt6-pkt10) IS ALREADY IN RECEIVE BUFFER
  but TCP holds it until pkt3 arrives.
  Stream 5 data also held.
  ALL streams stall even though only Stream 1 lost a packet.
```

At 1% packet loss (common on mobile networks), HTTP/2's TCP-level HOL blocking causes ~40% of connections to experience stalls equivalent to HTTP/1.1 with multiple connections.

**HTTP/2 Server Push** (now effectively dead): The server could proactively push resources (e.g., push `style.css` when the browser requests `index.html`). Chrome removed support in Chrome 106 (October 2022). Firefox removed it in Firefox 132 (October 2024). The problem: servers pushed things browsers already cached, wasting bandwidth. The replacement is **103 Early Hints** (an informational status code sent before the 200 response, giving the browser link headers to preload).

### HTTP/3 Mechanics

HTTP/3 replaces TCP entirely with **QUIC** (RFC 9000), running over UDP.

```
Protocol Stack Comparison

HTTP/1.1 and HTTP/2:        HTTP/3:
+------------------+        +------------------+
|   HTTP/1.1       |        |   HTTP/3         |
+------------------+        +------------------+
|   TLS 1.3        |        |   QUIC           |
+------------------+        | (includes TLS    |
|   TCP            |        |  1.3 built-in)   |
+------------------+        +------------------+
|   IP             |        |   UDP            |
+------------------+        +------------------+
                            |   IP             |
                            +------------------+
```

**QUIC Stream Independence:**

```
QUIC Connection (over UDP)

Stream 1: [pkt1][pkt2][ LOST ][pkt4]  <-- only Stream 1 blocks
Stream 3: [pkt5][pkt6][pkt7][pkt8]    <-- delivers unaffected
Stream 5: [pkt9][pkt10][pkt11]        <-- delivers unaffected

Each stream has independent:
  - Flow control window
  - Loss recovery
  - Ordering guarantee
```

**Connection Establishment Speed:**

```
HTTP/2 New Connection (TLS 1.3):
  Client --> Server: TCP SYN                     [RTT 0 start]
  Client <-- Server: TCP SYN-ACK
  Client --> Server: TCP ACK + TLS ClientHello   [1 RTT]
  Client <-- Server: TLS ServerHello + cert
  Client --> Server: TLS Finished + HTTP request [2 RTTs to first byte]
  Client <-- Server: HTTP response

QUIC New Connection:
  Client --> Server: QUIC Initial (includes TLS ClientHello)  [RTT 0 start]
  Client <-- Server: QUIC Initial + TLS ServerHello + cert
  Client --> Server: HTTP/3 request (0-RTT if resuming)       [1 RTT to first byte]
  Client <-- Server: HTTP/3 response

QUIC 0-RTT Resumption (returning user):
  Client --> Server: QUIC 0-RTT + HTTP/3 request  [sends data immediately]
  Client <-- Server: HTTP/3 response               [0-RTT overhead]
```

**Connection Migration**: QUIC connections are identified by a **Connection ID** (64-bit), not by the 4-tuple (src IP, src port, dst IP, dst port). When a mobile device switches from Wi-Fi (192.168.1.5:52341) to cellular (10.0.0.1:49872), the Connection ID remains valid. The connection migrates without interruption. TCP connections break on IP change — a new TCP + TLS handshake is required.

**Key HTTP/3 numbers:**
- 0-RTT data send for resumed connections (vs 2 RTTs for new HTTP/2)
- 1 RTT for new QUIC connections (vs 2 RTTs for TCP+TLS 1.3)
- 12.4% lower TTFB than HTTP/2 in Cloudflare measurements (176ms vs 201ms average)
- 18% reduction in YouTube video rebuffer time (Google production data)
- Up to 15.7% throughput reduction vs HTTP/2 on high-bandwidth (>600 Mbps) paths due to CPU overhead
- ~231K kernel packet-receive calls per QUIC download vs ~15K for TCP download (explains CPU cost)

### Misconceptions

**❌ Misconception**: HTTP/2 eliminates head-of-line blocking entirely.
**✅ Reality**: HTTP/2 eliminates *application-level* HOL blocking (the HTTP/1.1 problem of one request blocking the next on a connection). But TCP itself still has transport-level HOL blocking — a single lost packet stalls all streams on the TCP connection until retransmission completes.

**❌ Misconception**: HTTP/3 is always faster than HTTP/2.
**✅ Reality**: On reliable high-bandwidth networks (>600 Mbps), HTTP/2 can outperform HTTP/3 by up to 15.7% due to QUIC's CPU overhead from user-space transport processing. HTTP/3 wins on lossy or high-latency paths (mobile, intercontinental, satellite).

**❌ Misconception**: HTTP/2 Server Push is a great optimization technique worth implementing.
**✅ Reality**: Server Push was removed from Chrome (v106, Oct 2022) and Firefox (v132, Oct 2024) because it hurt performance more than it helped. Use 103 Early Hints instead.

**❌ Misconception**: You need to change your application code to support HTTP/2 or HTTP/3.
**✅ Reality**: HTTP/2 and HTTP/3 are transport-level upgrades. Your application logic (REST endpoints, JSON responses) stays identical. Only your infrastructure layer (nginx, CDN, load balancer config) changes.

## 3. Real-World Architecture Examples

### Google — QUIC Origin Story

**Scale that triggered it**: Google serves billions of requests per day across Search, YouTube, Gmail. By 2012, SPDY (their HTTP/2 precursor) eliminated application-level HOL blocking. But TCP-level HOL blocking was still causing video rebuffering on YouTube, especially for mobile users with variable packet loss.

**Decision**: Google built QUIC internally starting in 2012, deployed it to Chrome in 2013, and by 2017 it carried over 30% of Google's total egress traffic. The protocol was standardized as RFC 9000 in 2021.

**What they got wrong first**: Early QUIC implementations were in user-space (the QUIC library ran in the application process). This incurred significantly higher CPU cost than kernel TCP. Google had to invest heavily in optimizing their QUIC implementation and work on kernel-bypass (using DPDK and similar techniques on high-throughput servers) to make it economically viable at scale.

**Measured results in production**:
- YouTube: 18% reduction in rebuffer rate for desktop, 15.3% for mobile
- YouTube: 30% fewer rebuffers specifically on mobile networks
- Google Search: 8% reduction in page latency for desktop, 3.5% for mobile
- By 2023: QUIC accounted for an estimated 7% of all internet traffic globally

**Source**: "The QUIC Transport Protocol: Design and Internet-Scale Deployment" (SIGCOMM 2017), Google Research

---

### Meta (Facebook/Instagram) — QUIC to 2 Billion Users

**Scale that triggered it**: Meta's apps run on highly variable mobile networks globally — 2G/3G in emerging markets, congested LTE, frequent Wi-Fi-to-cellular handoffs. TCP connection drops on network change require full reconnect + login re-authentication flow. At 2 billion daily active users, even a 1% improvement in session continuity is worth tens of millions of dollars.

**Decision**: Meta began QUIC deployment in 2017. By October 2020, they reported that over **75% of Facebook's traffic** was already running over QUIC. Facebook's engineering blog detailed that QUIC's connection migration meant users switching from Wi-Fi to LTE no longer dropped their feed update connection.

**What they got wrong first**: Meta initially underestimated the server-side CPU cost of QUIC. Their early deployment hit CPU bottlenecks on edge servers that were sized for TCP workloads. They had to re-provision server fleets and optimize their mvfst QUIC library (which they open-sourced) before full rollout.

**Measured results**:
- Significant improvement in "tail latency" (p99 latency) for users on lossy networks
- By June 2023, Facebook accounted for ~86% of QUIC traffic observed on European ISPs
- Connection migration eliminated a class of "session expired" errors on mobile apps

**Source**: "How Facebook is Bringing QUIC to Billions" — Engineering at Meta blog (October 2020)

---

### Cloudflare — HTTP/3 Infrastructure at Global Scale

**Scale that triggered it**: Cloudflare acts as a reverse proxy for millions of websites and handles a significant fraction of global web traffic. Their edge network spans 300+ cities. Any latency improvement at the edge compounds across all customer sites.

**Decision**: Cloudflare enabled HTTP/3 globally in September 2019 — the first major CDN to do so. They built quiche (a QUIC and HTTP/3 Rust library) and later tokio-quiche, which handles millions of HTTP/3 requests per second.

**What they got wrong first**: Initial deployment revealed that a meaningful percentage of enterprise and corporate traffic was being silently downgraded from HTTP/3 to HTTP/2 because UDP port 443 was blocked by enterprise firewalls. Cloudflare built extensive fallback logic and diagnostics to detect this. They also discovered that HTTP/3's performance advantage was uneven — significant on mobile and lossy paths, negligible or slightly negative on wired connections.

**Measured results from Cloudflare production data**:
- HTTP/3 TTFB: 176ms average vs 201ms for HTTP/2 — **12.4% improvement**
- At p95: **116ms faster connection establishment** with HTTP/3 enabled
- HTTP/3 adoption: peaked around 28% of Cloudflare traffic in May 2023, settled to ~21% by 2026 (fallback to HTTP/2 on blocked-UDP paths explains the ceiling)

**Source**: "Comparing HTTP/3 vs. HTTP/2 Performance" — Cloudflare Engineering Blog; "HTTP/3 usage one year on" — Cloudflare Radar

---

### LinkedIn — HTTP/2 Migration (The HTTP/1.1 → HTTP/2 Story)

**Scale that triggered it**: LinkedIn's profile pages had grown to 100+ resources. With HTTP/1.1's 6-connection limit, resources were queuing heavily. Perceived page load time was a key user acquisition metric.

**Decision**: LinkedIn migrated to HTTP/2 in 2016 across their infrastructure.

**Measured results**:
- **34% reduction in page load times** after HTTP/2 migration
- Header compression reduced per-request overhead from ~600 bytes to ~40 bytes for repeated requests

**Source**: LinkedIn Engineering blog, multiple conference presentations from 2016-2017

### Design Questions to Ask Before Choosing

1. **What is the primary client type?** Mobile apps on cellular benefit most from HTTP/3. Microservice-to-microservice on private networks get negligible benefit.
2. **What is the typical packet loss rate on the network path?** >0.5% loss → HTTP/3 wins significantly. <0.1% on fiber → HTTP/2 is fine.
3. **Do you control both client and server?** If yes, gRPC (HTTP/2-based) may be more appropriate than raw HTTP/3 for internal communication.
4. **Are your users behind enterprise firewalls?** If yes, expect 10–30% of HTTP/3 connections to fall back to HTTP/2 (UDP blocked).
5. **What is your server CPU budget?** HTTP/3 costs ~3-5x more CPU per gigabit than HTTP/2 at high throughput on current hardware.
6. **Is your traffic CDN-terminated?** If yes, just enable HTTP/3 on the CDN config — the CDN-to-origin leg stays HTTP/2. No origin changes needed.

### Scale Evolution: Protocol Decision Points

**1K users/day (startup)**:
- Use HTTP/2 behind nginx or Caddy (automatic with most modern web frameworks)
- TLS 1.3 is non-negotiable — configure it even at this scale
- HTTP/3: nice to have, no engineering effort needed if using Cloudflare's free tier
- Decision: Enable HTTPS with HTTP/2. Use Cloudflare free tier for HTTP/3 if you want it for zero cost.

**100K users/day (growth)**:
- HTTP/2 multiplexing becomes meaningfully important — pages with 50+ resources see real load time differences
- Measure your p95/p99 latency by network type. If >20% mobile users, HTTP/3 becomes worth evaluating
- Introduce CDN (CloudFront, Fastly, Cloudflare) — let CDN handle HTTP/3, keep origin on HTTP/2
- Decision: CDN-terminate TLS and QUIC. Origin stays HTTP/2.

**1M users/day (scale)**:
- HTTP/3 adoption on CDN edges is worth measuring with A/B testing (Alt-Svc canary)
- Monitor CDN metrics: what % of requests succeed via HTTP/3 vs fall back to HTTP/2
- Internal services: switch to gRPC (HTTP/2-based) for service-to-service communication — stream multiplexing matters for fan-out RPCs
- Decision: HTTP/3 on CDN edges, gRPC internally, HTTP/2 for CDN-to-origin.

**100M users/day (hyperscale)**:
- At this scale you are likely building/tuning your own QUIC stack or using battle-tested CDN infrastructure
- HTTP/3 is table stakes — you're fine-tuning: 0-RTT session resumption rates, QUIC connection migration success rates, QPACK header compression tuning
- You're also measuring protocol fallback rates by geography and ISP — some regions (corporate-heavy) will have 30%+ UDP-blocked users
- Decision: Operate both HTTP/2 and HTTP/3 paths simultaneously. Monitor per-protocol success rates. Invest in protocol observability.

## 5. Code / Implementation Perspective

### Python: Detecting and Negotiating HTTP Versions (ALPN)

```python
import ssl
import socket
import urllib.request
from typing import Literal

def check_server_http_version(
    hostname: str,
    port: int = 443
) -> dict:
    """
    Connect to a server and inspect which HTTP versions it supports
    via TLS ALPN negotiation.
    
    Returns dict with:
      - negotiated_protocol: the protocol actually chosen
      - alpn_protocols_offered: what the server advertised
    """
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    context.set_alpn_protocols(["h2", "http/1.1"])  # what we support
    context.check_hostname = True
    context.verify_mode = ssl.CERT_REQUIRED
    
    with socket.create_connection((hostname, port), timeout=5) as raw_sock:
        with context.wrap_socket(raw_sock, server_hostname=hostname) as tls_sock:
            negotiated = tls_sock.selected_alpn_protocol()
            return {
                "hostname": hostname,
                "negotiated_protocol": negotiated,
                "tls_version": tls_sock.version(),
            }

# Usage:
# result = check_server_http_version("www.cloudflare.com")
# >>> {"hostname": "www.cloudflare.com", "negotiated_protocol": "h2", "tls_version": "TLSv1.3"}


def make_http2_request_httpx(url: str) -> dict:
    """
    httpx is the Python HTTP client with HTTP/2 support.
    Install: pip install httpx[http2]
    
    For HTTP/3, use aioquic or the httpx-quic extension.
    """
    import httpx
    
    # httpx handles ALPN negotiation transparently
    with httpx.Client(http2=True) as client:
        response = client.get(url)
        return {
            "status": response.status_code,
            "http_version": response.http_version,   # "HTTP/2" or "HTTP/1.1"
            "headers": dict(response.headers),
        }


def parse_alt_svc_header(alt_svc: str) -> list[dict]:
    """
    Parse Alt-Svc header to detect HTTP/3 availability.
    
    Example header value:
    'h3=":443"; ma=86400, h3-29=":443"; ma=86400'
    
    This is how browsers discover HTTP/3 support on first HTTP/2 response.
    On subsequent connections, browser uses QUIC directly.
    """
    services = []
    for entry in alt_svc.split(","):
        entry = entry.strip()
        if not entry or entry == "clear":
            continue
        parts = entry.split(";")
        protocol_host = parts[0].strip()
        protocol, _, host = protocol_host.partition("=")
        max_age = 86400  # default
        for param in parts[1:]:
            param = param.strip()
            if param.startswith("ma="):
                max_age = int(param[3:])
        services.append({
            "protocol": protocol.strip('"'),
            "host": host.strip('" '),
            "max_age_seconds": max_age,
        })
    return services

# Example:
# parse_alt_svc_header('h3=":443"; ma=86400, h3-29=":443"; ma=86400')
# [{"protocol": "h3", "host": ":443", "max_age_seconds": 86400}, ...]
```

### Algorithm: HTTP/2 Stream Multiplexing Logic

The core multiplexing logic in HTTP/2 is conceptually:

1. Each request gets a unique **stream ID** (odd numbers for client-initiated)
2. The request is broken into **HEADERS frame** (compressed with HPACK) + one or more **DATA frames**
3. Frames from different streams interleave freely on the wire — a DATA frame from stream 1, then DATA from stream 3, then HEADERS from stream 7
4. The receiver reassembles frames by stream ID
5. Flow control: each stream has an independent window (default 65,535 bytes); the connection also has a window. A slow stream doesn't block others as long as the connection window isn't exhausted

### Nginx Configuration for HTTP/2 and HTTP/3

```nginx
# nginx.conf — enabling HTTP/2 and HTTP/3

http {
    # HTTP/2 — enabled automatically for HTTPS in nginx 1.9.5+
    server {
        listen 443 ssl;
        listen [::]:443 ssl;
        
        # HTTP/2 — just add "http2" parameter (nginx >= 1.25.1)
        http2 on;
        
        ssl_certificate     /etc/ssl/certs/example.com.crt;
        ssl_certificate_key /etc/ssl/private/example.com.key;
        ssl_protocols       TLSv1.3 TLSv1.2;
        
        # Advertise HTTP/3 support via Alt-Svc header
        # (tells browser to use QUIC on next visit)
        add_header Alt-Svc 'h3=":443"; ma=86400';
        
        location / {
            proxy_pass http://backend_upstream;
            proxy_http_version 1.1;          # nginx-to-upstream uses HTTP/1.1
            proxy_set_header Connection "";  # keep-alive to upstream
        }
    }
    
    # HTTP/3 — requires nginx-quic build or OpenResty with QUIC module
    # As of nginx 1.25.0, HTTP/3 is in mainline (experimental)
    server {
        listen 443 quic reuseport;   # UDP for QUIC
        listen 443 ssl;               # TCP fallback
        
        http3 on;
        http2 on;
        
        ssl_certificate     /etc/ssl/certs/example.com.crt;
        ssl_certificate_key /etc/ssl/private/example.com.key;
        
        add_header Alt-Svc 'h3=":443"; ma=86400' always;
    }
    
    upstream backend_upstream {
        server 127.0.0.1:8000;
        keepalive 32;  # maintain 32 idle connections to upstream
    }
}
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **HTTP/1.1** | Internal service mesh on private networks; legacy systems where upgrade cost exceeds benefit; debugging/tooling contexts | Simple, universally supported; every proxy/firewall/load balancer handles it perfectly. Zero multiplexing = connection overhead at scale | Every web service before 2015; still ~20% of web traffic |
| **HTTP/2** | Public-facing web servers today; CDN-to-origin links; gRPC internally | Eliminates app-level HOL blocking, header compression; TCP-level HOL blocking remains; excellent ecosystem support | LinkedIn, Nginx default, AWS ALB default, virtually all major CDNs |
| **HTTP/3 / QUIC** | Mobile-heavy apps; intercontinental paths; video streaming; global public APIs | Eliminates all HOL blocking, connection migration; higher CPU cost, UDP firewall issues, less mature ecosystem | Google, Meta, Cloudflare, Akamai, Fastly, Shopify (CDN edge) |
| **gRPC (HTTP/2-based)** | Service-to-service (microservices) where you control both client and server | Strongly-typed, bidirectional streaming, multiplexing; requires code generation, less browser-friendly | Google internal, Lyft/Envoy, Kubernetes API server, many fintech backends |
| **WebSockets over HTTP/1.1** | Real-time bidirectional communication (chat, live updates) | Full duplex, low latency; one connection per client, no multiplexing, higher memory per connection | Discord (voice/chat), Slack, trading platforms |
| **SSE (Server-Sent Events over HTTP/2)** | Server-push streaming (stock tickers, live feeds) where client doesn't send data back | Simple API, multiplexed on HTTP/2; unidirectional only | Many monitoring dashboards, GitHub live updates |
| **WebTransport (HTTP/3-based)** | Next-gen browser real-time APIs; gaming, live collaboration | QUIC streams + datagrams in browser; very early ecosystem, limited support | Experimental; Google Meet testing it |

### Opinionated Recommendation

For **public-facing web services today** (2024–2026): deploy HTTP/2 at minimum, HTTP/3 via CDN. The CDN handles the QUIC complexity; your origin speaks HTTP/2. This gives you the mobile performance benefits of HTTP/3 without taking on QUIC operational complexity at your origin servers. Do not run HTTP/3 natively on your origin unless you have dedicated infrastructure engineers and a compelling measured reason.

For **microservice communication**: use gRPC (HTTP/2-based). The type safety and streaming semantics are worth the protobuf learning curve. Do not use HTTP/3 for service mesh — the benefits don't apply on a private, low-latency, reliable network, and the complexity is not worth it.

## 8. Trade-offs (Be Opinionated)

### Benefits

**HTTP/2 over HTTP/1.1:**
- **Multiplexing**: 80 resources over 1 connection vs 80 queued over 6 connections. LinkedIn measured 34% load time improvement.
- **Header compression (HPACK)**: Eliminates repeated header overhead. A page with 80 requests saves ~40KB of redundant header data.
- **No more domain sharding**: HTTP/1.1 engineers sharded assets across `cdn1.example.com`, `cdn2.example.com` to open more connections. HTTP/2 makes this a performance anti-pattern (it forces new TLS handshakes).
- **Binary protocol**: Easier to parse, less error-prone than ASCII HTTP/1.1 headers.

**HTTP/3 over HTTP/2:**
- **Eliminates transport-level HOL blocking**: At 1% packet loss, HTTP/3 connections recover independently per stream vs HTTP/2 stalling all streams. Critical for mobile and lossy paths.
- **Faster connection setup**: 1 RTT vs 2 RTTs for new connections; 0-RTT for returning users. At 100ms RTT this saves 100–200ms.
- **Connection migration**: Mobile users switching Wi-Fi → cellular maintain session continuity. Prevents re-authentication flows.
- **QUIC built-in encryption**: No unencrypted QUIC in the wild — security is not optional.

### Costs and Limitations

**HTTP/2:**
- TCP HOL blocking remains. Under packet loss >0.5%, HTTP/2 can perform worse than HTTP/1.1 with multiple connections because all streams share one TCP buffer.
- Server Push is dead (removed from Chrome and Firefox). If you built infrastructure around it, that investment is gone.
- More complex to debug than HTTP/1.1 — binary frames require `nghttp2` or Wireshark dissectors.

**HTTP/3 / QUIC:**
- **CPU overhead**: Up to 15.7% throughput reduction on >600 Mbps paths. QUIC processes ~231K kernel receive calls per download vs ~15K for TCP. This is a real cost on high-throughput servers.
- **UDP firewall blocking**: ~10–30% of enterprise network users have UDP/443 blocked, silently falling back to HTTP/2. This means your HTTP/3 deployment has less reach than you expect.
- **Ecosystem maturity**: nginx HTTP/3 support is still marked experimental in mainline. Debugging QUIC requires specialized tooling. Not all server-side frameworks natively support it.
- **Load balancer complexity**: Stateful QUIC connections need consistent hashing to the same backend (connection migration means the source IP can change mid-connection, which breaks naive IP-hash load balancing).
- **Operational complexity**: Monitoring QUIC performance requires new metrics (streams per connection, connection migration events, 0-RTT accept rate).

### Core Tension

**The fundamental tension is transport reliability vs. transport flexibility.**

TCP's ordered byte stream gives you a simple, kernel-optimized, universally supported reliability primitive — but it couples unrelated application streams together in ways that cause blocking. QUIC decouples reliability at the stream level, but moves transport logic to user space, increasing CPU cost and complexity.

This is the same tension as consistency vs. availability in distributed systems — you're trading one kind of guarantee (network reliability via kernel TCP) for another kind of guarantee (application stream independence via QUIC).

### My Recommendation

**Use HTTP/2 everywhere today** — there is no reason to run HTTP/1.1 on a public-facing service in 2024. The ecosystem support is universal, the performance benefits are proven, and the operational overhead is zero with any modern web server or CDN.

**Use HTTP/3 at the CDN edge** — let Cloudflare, AWS CloudFront, or Fastly handle QUIC for you. This is free performance for your mobile users with zero engineering cost. Enable it in your CDN configuration.

**Do not run HTTP/3 natively at your origin** unless you have >1M mobile DAU, dedicated infra engineers, and measured evidence that CDN-terminated HTTP/3 is insufficient. The operational complexity and CPU overhead are not worth it for most organizations.

## 9. Failure Modes — What Goes Wrong

### UDP Port 443 Blocked at Enterprise Firewall

**Trigger**: Corporate firewalls, university networks, and some ISPs block UDP port 443 entirely or rate-limit UDP traffic to prevent amplification attacks. Since QUIC runs over UDP/443, HTTP/3 connections are silently dropped.

**Symptoms**: HTTP/3 clients see connection timeout (~3–5 seconds) before falling back to HTTP/2. Users on corporate networks report slightly slower initial page loads than mobile users. HTTP/3 adoption metrics plateau at 20–30% even after full deployment.

**Detection**: Monitor Alt-Svc upgrade success rate in CDN metrics. A large gap between "HTTP/3 attempted" and "HTTP/3 succeeded" indicates UDP blocking. Split metrics by user agent / network type. Test from behind enterprise networks explicitly.

**Recovery**: HTTP/3 clients (browsers, curl) automatically fall back to HTTP/2 when QUIC fails. This fallback is built into the protocol. The user experience degrades to HTTP/2 performance, not failure. Ensure your HTTP/2 path is fully optimized as the fallback.

**Real Example**: Cloudflare's own analysis showed HTTP/3 peaked at 28% of traffic in May 2023 and retreated to ~21% by 2026, partly attributable to the large fraction of enterprise and corporate traffic where UDP is blocked.

---

### HTTP/2 HPACK Compression State Desynchronization

**Trigger**: A connection reset (RST) between client and server leaves the HPACK dynamic header compression table in an inconsistent state. If a server reuses the connection without resetting the HPACK state (bug in implementation or improper error handling), subsequent responses may decompress to garbage data.

**Symptoms**: Downstream service receives HTTP/2 responses with malformed headers. Application layer sees `400 Bad Request` or mysterious decoding errors. The problem is intermittent (only affects connections that experienced a mid-stream reset).

**Detection**: `HPACK decompression error` messages in nghttp2 logs. HTTP/2 RST_STREAM frames with error code `COMPRESSION_ERROR` (0x9). Monitor for HTTP/2 GOAWAY frames, which signal connection-level failures.

**Recovery**: The connection should be torn down and re-established on COMPRESSION_ERROR. This is the correct behavior per RFC 7541. If your HTTP/2 implementation handles this gracefully, it self-recovers within one RTT. Incorrect implementations that try to continue on the same connection will see cascading decode failures.

**Real Example**: Several early HTTP/2 server implementations (including early versions of Go's `net/http` package) had subtle HPACK state bugs that manifested under load with concurrent stream resets. Fixed in Go 1.8+.

---

### QUIC CPU Exhaustion Under High Throughput

**Trigger**: Deploying HTTP/3 on origin servers that were sized for TCP workloads. QUIC's user-space transport processes ~231K kernel receive calls per gigabit vs ~15K for TCP (from academic measurement). On servers handling >1 Gbps sustained throughput, this can saturate CPU cores.

**Symptoms**: HTTP/3 server CPU utilization spikes 3–5x above HTTP/2 CPU at the same request rate. p99 latency degrades as CPU queues build up. Load balancer health checks start failing on QUIC-heavy backends. In extreme cases, the QUIC server falls over while the TCP/HTTP/2 path remains healthy.

**Detection**: Monitor CPU utilization split by protocol. Enable kernel-level UDP receive coalescing (GRO — Generic Receive Offload) to reduce per-packet overhead. Profile the QUIC library to confirm it is the dominant CPU consumer.

**Recovery**: Switch traffic back to HTTP/2 until QUIC implementation is optimized. Enable GSO (Generic Segmentation Offload) for UDP to batch small packets. Consider using SO_REUSEPORT to spread QUIC connections across multiple cores. Upgrade to QUIC implementations with kernel-bypass or io_uring support.

**Real Example**: Research paper "QUIC is not Quick Enough over Fast Internet" (arXiv 2310.09423, 2023) documented up to 45.2% throughput reduction for HTTP/3 vs HTTP/2 on high-bandwidth paths due to this CPU overhead issue. Google's own internal teams had to invest heavily in QUIC optimization before their 2017 production deployment.

---

### HTTP/2 Priority Inversion (Slow Resource Blocks Critical Resource)

**Trigger**: HTTP/2 stream priority (RFC 7540) allows a client to express that some streams are more important than others (e.g., render-blocking CSS > images). Some server implementations ignore priorities or implement them incorrectly, causing large lower-priority responses to delay small critical ones.

**Symptoms**: A page's render-blocking CSS file is delayed because a large image response on a lower-priority stream is consuming the connection's send window. Visually: blank/unstyled page for longer than expected before styles apply. Tools like WebPageTest show CSS loaded after images.

**Detection**: Waterfall chart analysis in WebPageTest or Chrome DevTools → Network tab. Look for small critical resources (CSS, critical JS) arriving later than large images on the same HTTP/2 connection.

**Recovery**: Configure your server to respect client-provided stream priorities. In nginx: `http2_chunk_size 8k` to prevent large responses from monopolizing the connection. Alternatively, separate origins (e.g., `static.example.com` for images) to isolate connections.

Note: HTTP/2's priority scheme was considered so complex and poorly implemented that HTTP/3 replaced it with a simpler "Extensible Priorities" scheme (RFC 9218).

## 10. When To Use vs. When To Avoid

### Use When

**HTTP/2:**
- ✅ Any public-facing HTTPS service today — the performance benefits are universal and the operational cost is zero with modern infrastructure.
- ✅ Your pages load 20+ resources — multiplexing benefits grow proportionally with resource count.
- ✅ You're replacing HTTP/1.1 domain-sharding hacks — HTTP/2 makes multi-subdomain CDN tricks a performance anti-pattern.
- ✅ You're deploying gRPC for microservices — gRPC runs on HTTP/2 and requires it.

**HTTP/3:**
- ✅ Your users are predominantly on mobile (LTE/5G) where packet loss and network changes are frequent.
- ✅ You're a global CDN or your service has users in high-latency geographies (cross-Pacific, emerging markets on 3G).
- ✅ You can enable it at the CDN layer with zero backend changes — the cost/benefit is favorable.
- ✅ You serve real-time media (video streaming) where rebuffer rate directly impacts user retention.

### Do NOT Use When

**HTTP/3:**
- ❌ Service-to-service communication on a private network — TCP on a reliable 0.01% loss internal network is faster (lower CPU) and simpler to debug.
- ❌ High-throughput bulk data transfer servers (>1 Gbps sustained per process) — QUIC's CPU overhead can reduce throughput by 15–45% vs TCP.
- ❌ Your user base is predominantly enterprise/corporate — UDP is frequently blocked, your HTTP/3 traffic will silently fall back to HTTP/2 anyway.
- ❌ You lack specialized QUIC operational expertise — debugging QUIC issues requires different tooling (qvis, quicly-tools) than TCP debugging (tcpdump, Wireshark with older dissectors).

**HTTP/1.1 (stick with it):**
- ❌ Never for new production public-facing services — there is no justification.
- The only valid cases: legacy protocol compatibility requirements, a debugging/introspection context where plain-text HTTP/1.1 is easier to inspect.

### The #1 Mistake Engineers Make

**Enabling HTTP/3 on the origin server instead of at the CDN edge.**

This is the mistake that causes CPU exhaustion incidents and QUIC debugging spirals. The correct architecture is: CDN handles QUIC (terminating at the edge, close to users, on hardened QUIC infrastructure), CDN-to-origin runs HTTP/2 (stable, predictable, well-understood). Engineers who skip the CDN and run HTTP/3 natively on their app servers inherit all of QUIC's operational complexity — UDP load balancing, connection migration handling, QUIC library maintenance — for marginal additional benefit beyond CDN-terminated HTTP/3.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Walk me through the evolution of HTTP and why each version was created."
- "If you're designing a system for a mobile-first global app, which HTTP version would you choose and why?"
- "What is head-of-line blocking? Does HTTP/2 solve it?"
- "Why did Google build QUIC? What problem does it solve that HTTP/2 couldn't?"
- "A client wants to migrate from HTTP/1.1 to HTTP/2. What do they actually need to change?"
- "What happened to HTTP/2 Server Push and why?"
- "Your service has 40% higher p99 latency after enabling HTTP/3. What do you investigate?"

### What the Interviewer Evaluates

1. **Depth vs. breadth**: Can you explain *why* each version was created, or just list feature bullets?
2. **Trade-off reasoning**: Do you know when HTTP/3 is *worse* than HTTP/2?
3. **Operational awareness**: Do you know what actually changes in production (nginx config, CDN settings) vs. what stays the same (application code)?
4. **Numbers**: Can you quantify performance differences rather than saying "faster"?

### Questions YOU Ask Before Answering

Before answering "which HTTP version should we use," ask:
1. "What is the primary client — browser, mobile app, or service-to-service?"
2. "What is the typical packet loss rate? Are users primarily on mobile cellular or enterprise wired?"
3. "Are we talking about client-facing or internal service communication?"
4. "Do we control both client and server, or just the server?"
5. "Is there a CDN in front of our origin?"

These questions signal that you understand context matters — a staff engineer doesn't give the same answer for a mobile fintech app and an internal batch data pipeline.

### Junior (L3–L4) Answer

> "HTTP/1.1 is the original protocol. HTTP/2 added multiplexing so multiple requests can share one connection. HTTP/3 uses UDP instead of TCP via QUIC, which is faster on mobile. I'd use HTTP/2 for most things and HTTP/3 via a CDN for mobile-heavy apps."

This is acceptable — correct, but surface-level. No numbers, no trade-offs, no failure modes.

### Senior (L5) Answer

> "HTTP/1.1's core limitation is head-of-line blocking — with 6 connections per domain, 80 resources queue 13 deep per connection. HTTP/2 fixed this at the application layer via multiplexing streams on one TCP connection. LinkedIn saw 34% load time improvement. But TCP still has transport-level HOL blocking — at 1% packet loss, one lost TCP segment stalls all HTTP/2 streams. That's why Google built QUIC: it runs on UDP, each stream is independently loss-recovered, and connection IDs survive network changes. For production today: HTTP/2 is baseline, HTTP/3 at the CDN edge for mobile users. I wouldn't run HTTP/3 natively at the origin because of QUIC's CPU overhead — up to 15.7% throughput reduction at >600 Mbps. HTTP/2 Server Push is dead — Chrome removed it in 2022. Use 103 Early Hints instead."

This is a strong L5 answer — specific numbers, trade-offs, current state of ecosystem.

### Staff (L6+) Answer

A staff-level answer adds:

> "The interesting architectural implication is where you terminate the protocol. HTTP/3 should be terminated at the CDN edge, not the origin. The CDN-to-origin path is a private, low-latency, reliable network — TCP is faster there. This means you get all the mobile benefits (connection migration, no transport HOL blocking) without running QUIC on your origin servers. For service-to-service, neither HTTP/2 nor HTTP/3 is the right answer — gRPC gives you typed contracts, streaming, and HTTP/2 multiplexing, which is what actually matters internally.
>
> The meta-point is that the 'which HTTP version' question is often the wrong question. The right questions are: what is the network path reliability, who controls both ends of the connection, and what is your team's capacity to operate the protocol stack? HTTP/3 at a CDN is a checkbox. HTTP/3 at your origin is an infrastructure project. Know which one you're signing up for.
>
> One more thing: 0-RTT in QUIC has a replay attack surface for non-idempotent requests. If you enable 0-RTT resumption on an endpoint that accepts POST requests, an adversary can replay those POST requests. Safe-by-default implementations restrict 0-RTT to GET requests only. This is the kind of implementation nuance that matters when you're actually deploying this."
