## 1. What Is It? (Theory)

### The Problem in Plain English

Every device on the internet has an IP address — a raw number like `142.250.80.46`. Humans can't remember thousands of IP addresses, and more critically, **IP addresses change**: servers get replaced, cloud providers shift traffic, companies migrate data centers, services scale horizontally across dozens of regions. If every client hardcoded IPs, any infrastructure change would break every user immediately and permanently.

**DNS (Domain Name System)** is the internet's distributed phone book. It translates human-readable names like `api.stripe.com` into the IP address(es) a client needs to actually connect. But at scale, it does far more than name resolution — it becomes a **traffic routing layer**, a **health-aware failover mechanism**, and a **global load balancer** before a single HTTP byte is exchanged.

### Why It Was Invented

Before DNS (pre-1983), every host on ARPANET maintained a single `HOSTS.TXT` file that mapped hostnames to IPs. Stanford Research Institute (SRI) distributed updates weekly. By 1983, with ~500 hosts, the file was already unmanageable — every change required SRI to redistribute the file manually, and name collisions were common. Paul Mockapetris designed DNS (RFC 882, 1983) as a distributed, hierarchical, delegated namespace to solve this.

Without DNS at scale:
- IP changes require coordinated client-side reconfiguration (impossible at internet scale)
- No geographic traffic distribution (everyone hits the same datacenter)
- No health-based failover (dead servers serve indefinitely)
- No blue-green deployments (you can't swap backends without breaking clients)

### The Real-World Analogy

DNS is the **airport routing system**. Your flight ticket says "New York" (the domain), not gate B27 (the IP). The routing system translates your destination into a specific gate at the last moment — and if gate B27 has a problem, ground control silently reroutes you to B29 before you even arrive. You never need to know the gate changed.

### A Concrete Example with Numbers

**Scenario:** `api.github.com` under load

- GitHub serves ~100M developer requests/day globally
- Without DNS, all traffic would hit a single IP in a single datacenter
- With GeoDNS + health checks, European users resolve to `140.82.121.5` (EU edge), US users resolve to `192.30.255.116` (US East)
- If US East goes unhealthy, Route53 health checks detect failure within **10-30 seconds**, stops advertising that IP, and Europe-routed traffic is the fallback
- TTL of 60s means clients are redirected within **60-90 seconds total** of a datacenter failure

## 2. How It Actually Works (Deep Mechanics)

### The Resolution Chain (Step by Step)

When your browser requests `api.example.com` for the first time:

```
Step 1: Browser checks its local DNS cache
        → Cache miss (first request, or TTL expired)

Step 2: OS checks /etc/hosts and its resolver cache
        → Cache miss

Step 3: OS forwards query to configured recursive resolver
        (e.g., 1.1.1.1 Cloudflare, 8.8.8.8 Google, or your ISP's resolver)

Step 4: Recursive resolver checks its own cache
        → Cache miss — begins iterative resolution

Step 5: Recursive resolver queries a Root Name Server
        (13 logical roots: a.root-servers.net through m.root-servers.net)
        Root responds: "I don't know api.example.com but .com TLD servers are at 192.5.6.30"

Step 6: Recursive resolver queries .com TLD authoritative server
        TLD responds: "I don't know api.example.com but example.com nameservers are at ns1.example.com / ns2.example.com"

Step 7: Recursive resolver queries example.com's authoritative server
        Authoritative server responds: "api.example.com → 203.0.113.42, TTL=60"

Step 8: Recursive resolver caches the answer for 60 seconds
        Returns 203.0.113.42 to the OS resolver

Step 9: OS resolver returns IP to the browser
        Browser opens TCP connection to 203.0.113.42:443
```

### Key Record Types

| Record | Purpose | Example |
|--------|---------|---------|
| **A** | Maps hostname → IPv4 | `api.example.com → 203.0.113.42` |
| **AAAA** | Maps hostname → IPv6 | `api.example.com → 2001:db8::1` |
| **CNAME** | Alias to another hostname | `www → example.com` |
| **MX** | Mail exchange servers | Priority + hostname |
| **NS** | Authoritative nameservers for zone | `ns1.example.com` |
| **TXT** | Arbitrary text (SPF, DKIM, verification) | `v=spf1 include:...` |
| **SOA** | Zone authority metadata | Serial, refresh, retry timers |
| **SRV** | Service discovery with port | `_https._tcp → host:port:priority` |
| **PTR** | Reverse DNS (IP → name) | `42.113.0.203.in-addr.arpa → api.example.com` |

### TTL: The Master Knob

**TTL (Time To Live)** is the number of seconds resolvers are permitted to cache a record. It is the single most consequential DNS configuration decision for availability:

```
TTL=3600  → resolvers cache for 1 hour
            → after a record change, old IPs persist for up to 1 hour globally
            → low query volume, low cost

TTL=60    → resolvers cache for 60 seconds
            → after a record change, propagation completes in ~60-90 seconds
            → 60× more queries than TTL=3600 (significant at scale)

TTL=0     → no caching permitted
            → every request hits your authoritative server
            → theoretically instant propagation
            → rarely used in practice; many resolvers enforce minimum TTLs of 30-60s
```

**The propagation math:** If your current TTL is 3600, and you change it to 60, you must wait **3600 seconds (1 hour)** for all existing caches to expire before the new TTL of 60 takes effect. Plan changes 24-48 hours ahead for TTL=86400 records.

### Real Performance Numbers

| Scenario | Latency |
|---------|---------|
| Cache hit at OS resolver | < 1 ms |
| Cache hit at recursive resolver (e.g., 1.1.1.1) | 1-10 ms |
| Full iterative resolution (cold cache) | 50-200 ms |
| Full resolution with DNSSEC validation | 100-400 ms |
| Root server query (anycast, same continent) | 5-30 ms |
| Authoritative server query (Route53, same region) | 1-15 ms |
| DNS-over-HTTPS (DoH) cold connection | 100-300 ms |

Recursive resolver cache hit rates for popular domains (Facebook, Google, Netflix): **> 99%**. Your average user never triggers a full resolution chain for major services.

### Misconceptions

**❌ Misconception: "DNS changes propagate in minutes globally"**
**✅ Reality:** DNS propagation = TTL expiry. If your current TTL is 24 hours (86400s), your old record persists for up to 24 hours in every resolver that cached it. "Global propagation" takes as long as the previous TTL allows, not some fixed internet-wide timer.

**❌ Misconception: "DNS uses TCP"**
**✅ Reality:** Standard DNS queries use UDP/53 for < 512 byte responses. Responses larger than 512 bytes (zone transfers, DNSSEC) fall back to TCP/53. DNS-over-HTTPS uses TCP/443. DNS-over-TLS uses TCP/853.

**❌ Misconception: "Setting TTL=0 gives instant failover"**
**✅ Reality:** Many resolvers (including major ISP resolvers) enforce a minimum TTL floor of 30-60 seconds regardless of what you set. Additionally, browsers maintain their own DNS cache with minimum TTLs. TTL=0 also eliminates all caching benefits and hammers your authoritative servers.

**❌ Misconception: "GeoDNS routes to the geographically closest server"**
**✅ Reality:** GeoDNS routes based on the **resolver's IP address**, not the end-user's IP. A user in Tokyo using a US-based corporate VPN resolver gets US DNS responses. This can cause significant routing inefficiency.

## 3. Real-World Architecture Examples

### Facebook — When DNS Depends on Your Own Infrastructure

**Scale:** 3.7 billion users, ~100,000+ servers, private backbone spanning 3 continents

**The October 4, 2021 Outage**

On October 4, 2021 at 15:39 UTC, Facebook withdrew BGP routes to its own IP prefixes from the global internet as a side effect of a routine backbone maintenance command. Within 11 minutes, Facebook's domains had expired from all major public resolver caches globally (since TTLs had rolled over during the outage). Facebook was completely unreachable for 6 hours.

The critical architectural failure: **Facebook's authoritative nameservers ran on the same network that was withdrawn from the internet.** When the BGP routes disappeared, the authoritative DNS servers became unreachable, making it impossible for resolvers to get fresh records even if they had tried.

The cascading failure: Facebook's internal operations tooling — the systems engineers needed to diagnose and fix the problem — also relied on Facebook's DNS and internal services. Physical badge readers for data center entry also depended on the same infrastructure. Engineers had to physically travel to data centers and restore BGP routes manually from inside the building.

**Lesson:** DNS infrastructure must be reachable via **out-of-band paths** independent of your primary network. Your operations tooling must never depend on the very DNS/routing infrastructure you might be trying to repair.

**What they changed afterward:**
- Authoritative nameservers are now reachable via multiple independent network paths
- Emergency operations tooling uses out-of-band access that bypasses internal DNS
- BGP route changes now require staged rollouts with automated rollback on anomaly detection
- DNS TTLs were reviewed; shorter TTLs give faster recovery once authoritative servers are reachable

### Cloudflare — The DNSSEC Root Zone Incident (October 2023)

**Scale:** 1.1.1.1 handles > 1 trillion DNS queries/day; ~10% of global DNS traffic

**The Incident**

In October 2023, ICANN added a new `ZONEMD` resource record type to the DNS root zone. This exposed a bug in Cloudflare's resolver validation logic: when the DNSSEC signatures on the root zone expired briefly, Cloudflare's resolver returned `SERVFAIL` for a significant portion of queries for roughly 3 hours.

The technical mechanism: Cloudflare's resolver cached the root zone DNSSEC signatures and did not gracefully handle the case where signature validation failed. Instead of falling back to unvalidated responses, it hard-failed all queries that touched the root zone during the validation failure window.

**Lesson:** DNSSEC validation, while important for security, introduces a failure mode that plain DNS doesn't have. Your validation logic must implement graceful degradation — serve stale-but-cached responses rather than `SERVFAIL` when validation fails due to infrastructure issues vs. actual tampering.

**Impact numbers:** ~3 hours of degraded resolution for Cloudflare 1.1.1.1 users, affecting an estimated tens of millions of end users.

---

### AWS Route53 — Cascading Failure from Recursive Resolver Flood (November 2020)

**Scale:** Route53 is AWS's globally distributed authoritative DNS service; handles DNS for the majority of AWS-hosted services

**The Incident**

In late November 2020, Route53 experienced a significant availability issue triggered by an unexpectedly large volume of DNS queries from recursive resolvers. The trigger: a small number of misbehaving recursive resolvers (non-AWS third-party) began re-querying Route53 authoritative servers in a rapid retry loop when they encountered any failure, instead of honoring negative caching (NXDOMAIN with TTL). This created a positive-feedback loop:

1. Route53 becomes slightly overloaded → some queries time out
2. Misbehaving resolvers retry immediately instead of backing off
3. Retry volume increases Route53 load further
4. More timeouts → more retries → amplification spiral

**Lesson:** DNS infrastructure must be designed for **query amplification attack scenarios** — whether accidental (buggy resolvers) or intentional (DNS amplification DDoS). Rate limiting per source IP at the resolver layer is essential.

**What Route53 changed:** Added adaptive rate limiting per source IP, improved automatic scaling triggers, and published guidance on resolver retry behavior in the AWS DNS Best Practices documentation.

### Design Questions to Ask Before Starting

Before you design a DNS strategy, answer these explicitly:

1. **What is your recovery time objective (RTO)?** Sub-minute requires TTL=30-60 and health checks. Hour-level allows TTL=3600.
2. **Are your users geographically distributed?** If 90% are in one region, GeoDNS adds complexity without benefit.
3. **What is your read-to-write ratio?** High-read workloads benefit most from geo-routing. Pure API services less so.
4. **Do you control your authoritative DNS, or is it hosted by your registrar?** Registrar DNS typically has no health checks, no low TTLs, no programmable routing.
5. **What happens if DNS itself fails?** Your app's DNS dependency is a single point of failure unless you use multiple DNS providers.
6. **Do you need DNSSEC?** Adds security against spoofing but adds validation latency (50-200ms overhead) and introduces new failure modes.
7. **What is your TTL budget for planned changes?** Migrations require pre-lowering TTL 24-48h in advance.

### Scale Evolution: DNS Strategy at Each Stage

#### 1K users — Single Region, Simple DNS

```
api.example.com → A record → 203.0.113.42 (single server)
TTL: 3600 (1 hour is fine, you're not deploying often)
Provider: Any registrar DNS (GoDaddy, Namecheap)
Cost: $0 extra
```

No health checks needed. Downtime during deploys is acceptable. The only concern is making sure your A record points to an Elastic IP (or equivalent) so it survives server replacements.

#### 100K users — Health Checks + Failover

At this scale, unplanned downtime has business impact. Add:

- **Managed DNS with health checks:** Move from registrar DNS to Route53, Cloudflare DNS, or similar
- **TTL reduction:** Drop API endpoints to TTL=60-120. Leave static/CDN records at TTL=3600
- **Primary + failover record:** Route53 failover routing policy with health-checked primary and standby secondary
- **Failover time target:** < 3 minutes (90s detection + 60s TTL expiry + 30s buffer)

```
api.example.com (primary)   → 203.0.113.42, health-checked, TTL=60
api.example.com (failover)  → 203.0.113.99, standby (only serves if primary fails)
```

#### 1M users — Multi-Region with GeoDNS

Now geography matters for latency. Users in Europe hitting US servers add 100-200ms of unnecessary network latency. Add:

- **Latency-based or geo-based routing:** Route European users to EU cluster, US users to US cluster
- **Regional health checks:** Each region is independently health-checked; failover routes to next-best region
- **Weighted routing for canary:** Use weighted records (95/5 split) to safely roll out new versions
- **Multiple NS records:** Use at least 2 different DNS providers for authoritative redundancy (Route53 + Cloudflare)

#### 100M users — Anycast + Global Traffic Management

At this scale, even DNS resolution latency matters. Add:

- **Anycast DNS:** Your authoritative servers advertise the same IP globally via BGP; queries route to nearest PoP automatically
- **Negative caching optimization:** Tune NXDOMAIN TTLs to prevent resolver amplification
- **DNS-based traffic shaping:** Use DNS response weights to gradually shift traffic between clusters (global load balancing)
- **Automated TTL management:** Lower TTLs before deploys programmatically, restore after
- **DNSSEC with HSM key management:** Protect against cache poisoning at this target profile

## 5. Code / Implementation Perspective

### Python: DNS Health Check + Dynamic Record Update

This is a realistic pattern for programmatic DNS failover using AWS Route53 via boto3:

```python
import boto3
import socket
import time
from typing import Optional

class DNSFailoverManager:
    """
    Monitors a primary endpoint and updates Route53 A records
    to failover IP when health checks fail.
    
    Real-world equivalent of what Route53 health checks do natively,
    but useful when you need custom health check logic beyond HTTP 200.
    """

    def __init__(self, hosted_zone_id: str, record_name: str, ttl: int = 60):
        self.client = boto3.client("route53")
        self.hosted_zone_id = hosted_zone_id
        self.record_name = record_name
        self.ttl = ttl
        self.failure_threshold = 3
        self.consecutive_failures = 0

    def check_health(self, ip: str, port: int = 443, timeout: float = 5.0) -> bool:
        """TCP connect health check. Returns True if healthy."""
        try:
            with socket.create_connection((ip, port), timeout=timeout):
                return True
        except (socket.timeout, ConnectionRefusedError, OSError):
            return False

    def get_current_ip(self) -> Optional[str]:
        """Read current A record value from Route53."""
        response = self.client.list_resource_record_sets(
            HostedZoneId=self.hosted_zone_id,
            StartRecordName=self.record_name,
            StartRecordType="A",
            MaxItems="1",
        )
        records = response.get("ResourceRecordSets", [])
        if records and records[0]["Name"].rstrip(".") == self.record_name.rstrip("."):
            return records[0]["ResourceRecords"][0]["Value"]
        return None

    def update_dns(self, new_ip: str) -> None:
        """Upsert A record to point to new_ip with configured TTL."""
        self.client.change_resource_record_sets(
            HostedZoneId=self.hosted_zone_id,
            ChangeBatch={
                "Comment": f"Automated failover to {new_ip}",
                "Changes": [{
                    "Action": "UPSERT",
                    "ResourceRecordSet": {
                        "Name": self.record_name,
                        "Type": "A",
                        "TTL": self.ttl,
                        "ResourceRecords": [{"Value": new_ip}],
                    },
                }],
            },
        )
        print(f"[DNS] Updated {self.record_name} → {new_ip} (TTL={self.ttl})")

    def run_monitor(self, primary_ip: str, failover_ip: str, interval: int = 30) -> None:
        """
        Poll primary IP every `interval` seconds.
        After `failure_threshold` consecutive failures, switch DNS to failover_ip.
        Recovery: switch back when primary is healthy again.
        """
        active_ip = primary_ip
        while True:
            healthy = self.check_health(primary_ip)
            if healthy:
                self.consecutive_failures = 0
                if active_ip != primary_ip:
                    print(f"[DNS] Primary {primary_ip} recovered, switching back")
                    self.update_dns(primary_ip)
                    active_ip = primary_ip
            else:
                self.consecutive_failures += 1
                print(f"[DNS] Primary unhealthy ({self.consecutive_failures}/{self.failure_threshold})")
                if self.consecutive_failures >= self.failure_threshold and active_ip != failover_ip:
                    print(f"[DNS] Threshold reached — failing over to {failover_ip}")
                    self.update_dns(failover_ip)
                    active_ip = failover_ip
            time.sleep(interval)


# Usage
manager = DNSFailoverManager(
    hosted_zone_id="Z1234567890ABC",
    record_name="api.example.com",
    ttl=60,
)
manager.run_monitor(
    primary_ip="203.0.113.42",
    failover_ip="203.0.113.99",
    interval=30,
)
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **GeoDNS** | Route users to nearest region based on geography | Resolver IP ≠ user IP (VPNs break it); no topology awareness | Netflix, Spotify, GitHub |
| **Anycast routing** | Route to nearest PoP based on BGP topology | Requires BGP infrastructure or provider support; harder to debug | Cloudflare, Google (8.8.8.8), Akamai |
| **DNS-based load balancing (Round-robin)** | Simple multi-IP distribution without a load balancer | No health awareness; clients cache one IP; uneven distribution | Small services, legacy setups |
| **Latency-based routing (Route53)** | Minimize RTT by routing to AWS region with lowest measured latency | Only works within AWS regions; latency data is periodic, not real-time | AWS-native SaaS |
| **Weighted DNS** | Canary deploys, gradual traffic shifts | Can't guarantee exact split (resolvers cache); rough distribution only | Stripe, Shopify |
| **Service mesh (Envoy/Istio)** | Dynamic, millisecond-aware routing within a cluster | Overkill for inter-datacenter; adds sidecar overhead (~2ms, 50MB RAM) | Lyft, Airbnb, Netflix |
| **Hardcoded IPs (no DNS)** | Internal microservices in same cluster with service mesh | No portability; breaks on IP changes; no failover | Avoid in general; sometimes used for DNS bootstrapping |

### My Recommendation

**Use GeoDNS (Route53 latency-based or Cloudflare load balancing) + health checks as your primary cross-region routing strategy.** It is the right tool for 90% of multi-region architectures:

- It works with every client (no SDK required — it's at the protocol level)
- Health-based failover is automatic and well-tested
- The tooling (Route53, Cloudflare) is mature and battle-tested at internet scale

**Switch to anycast when:**
- You're building a DNS provider, CDN, or global proxy (Cloudflare's use case)
- You need sub-10ms DNS resolution globally (anycast nodes are closer to users than regional DCs)
- You need DDoS resilience at the DNS layer (anycast absorbs volumetric attacks by distributing them)

**Layer in service mesh only** when you need millisecond-resolution traffic control (circuit breaking, retries, per-request routing) within a cluster. DNS and service mesh solve different scope problems and are complementary, not competing.

## 8. Trade-offs (Be Opinionated)

### Benefits (Specific, with Numbers)

- **Zero client-side configuration:** Every HTTP client on the planet speaks DNS. No SDK, no configuration change required to redirect traffic.
- **Effective failover speed:** With TTL=60 + Route53 health checks (30s interval, 3x threshold), worst-case failover is **~2.5 minutes** end-to-end. This meets most RTO objectives for non-financial services.
- **Global traffic distribution without a central proxy:** GeoDNS routes European traffic to EU endpoints without hairpinning through a US load balancer, saving 100-200ms of latency per request.
- **Cost-effective at scale:** Route53 charges $0.40/million queries. For 100 million queries/day, that's ~$40/day. A global load balancer appliance doing the same thing costs orders of magnitude more.
- **Propagation is measurable:** Unlike most distributed systems, DNS propagation is deterministic (it equals your TTL). You can calculate exactly when an IP change will fully propagate.

### Costs and Limitations (Honest, with Numbers)

- **Not instant failover:** Even with TTL=30, real-world failover takes 90-180 seconds (detection + expiry + client re-query). For payment processing or trading systems, this may be unacceptable.
- **TTL vs. query cost tension:** Reducing TTL from 3600 to 60 multiplies authoritative query volume by **60×**. For a domain getting 10M queries/day at TTL=3600, switching to TTL=60 means 600M queries/day — a significant cost increase.
- **Resolver IP ≠ User IP:** GeoDNS uses the recursive resolver's IP for geo-lookup. Corporate users behind centralized DNS, VPN users, and DoH users (whose queries resolve at a cloud resolver in another geography) all potentially get routed to the "wrong" region. EDNS Client Subnet (ECS) mitigates this but is not universally supported.
- **DNS is not a load balancer:** Round-robin DNS distributes at the query level, not the connection level. Because resolvers cache results, all users behind a given resolver hit the same backend for the TTL duration. Load distribution is rough at best.
- **DNSSEC operational complexity:** Managing DNSSEC requires key rotation, ZSK/KSK separation, and DS record coordination with your TLD registry. A misconfiguration causes `SERVFAIL` for **all** your domains. Many organizations skip DNSSEC entirely, accepting the spoofing risk.

### Core Tension Being Navigated

**The fundamental tension in DNS architecture is: TTL (cacheability/performance) vs. TTL (change agility/failover speed).**

High TTL = cheap, fast, cacheable DNS, but slow to change.
Low TTL = expensive, more latency variability, but fast failover and change agility.

You cannot have both. Every DNS design decision is a point on this spectrum.

### My Recommendation

**Set API endpoint TTLs to 60 seconds, set CDN/static asset CNAMEs to 300 seconds, and set everything else to 3600 seconds by default.** Then:

1. Automate TTL pre-lowering 24h before any planned IP migration (set to 60, wait for old TTL to expire, then change the IP)
2. Use Route53 or Cloudflare health checks rather than trying to reduce TTL to 0 for failover — health checks + TTL=60 is the right combination
3. Never use your registrar's built-in DNS for production services — always use a managed DNS provider with an SLA, health checks, and an API
4. If you're on AWS, use Route53. If you want Cloudflare's network performance and DDoS protection, use Cloudflare DNS. Don't mix them for the same domain's authoritative records (you'll have inconsistency); but do use both as independent NS records in Route53's hosted zone for secondary DNS redundancy.

## 9. Failure Modes — What Goes Wrong

### Stale DNS Cache After Failover

**Trigger:** A server at IP `203.0.113.42` becomes unhealthy. You update the A record to `203.0.113.99`. Some clients continue hitting the old IP for minutes or hours.

**Symptoms:** Some users report errors while others report the service is fine. Error rate is a function of what percentage of resolvers have already expired their cached record. Errors decrease gradually over time as caches expire.

**Detection:** Monitor error rates broken down by source region. Use `dig +norecurse @resolver_ip yourdomain.com` from multiple geographic vantage points to see what different resolvers are serving. Catchpoint, ThousandEyes, or similar synthetic monitoring from multiple PoPs shows the "propagation frontier."

**Recovery:** There is no instant fix for cached DNS entries. You can:
1. Wait for TTL to expire (this is why pre-lowering TTL matters)
2. Ensure the old IP still works (keep both servers running during transition)
3. For emergency migrations, contact major resolver operators (Google, Cloudflare) — they have manual flush mechanisms but don't expose them publicly

**Real Example:** During the 2021 Facebook outage, once BGP routes were restored at ~21:00 UTC, it still took 30-60 minutes for DNS resolution to fully recover globally because many resolvers had cached `SERVFAIL` responses (with various negative TTLs). The BGP fix was instant; DNS recovery was not.

---

### DNSSEC Chain of Trust Break

**Trigger:** A ZSK (Zone Signing Key) rotation is performed incorrectly, or a ZSK expires without being replaced. The DS record in the parent zone no longer matches the DNSKEY in your zone.

**Symptoms:** Users of DNSSEC-validating resolvers (Cloudflare 1.1.1.1, Google 8.8.8.8, most modern ISP resolvers) receive `SERVFAIL` for all records in the affected zone. Non-validating resolvers (legacy ISP resolvers) continue working fine. This creates the maddening situation where "half the internet can reach you and half cannot" with no obvious connection between which users are affected.

**Detection:** Run `dnsviz.net` on your domain immediately — it provides a visual chain-of-trust graph showing exactly where validation breaks. `dig +dnssec yourdomain.com @8.8.8.8` vs `dig +dnssec yourdomain.com @resolver_without_dnssec` will show the discrepancy.

**Recovery:**
1. Short-term: Remove the DS record from your TLD registrar (this disables DNSSEC validation, but eliminates `SERVFAIL`). This takes effect within the TLD's SOA TTL (typically 900s-3600s).
2. Long-term: Fix the key rotation, re-add the correct DS record, verify with dnsviz.

**Real Example:** The October 2023 Cloudflare resolver incident. ICANN added `ZONEMD` to the root zone, and DNSSEC signatures on the root zone expired. Cloudflare's resolvers returned `SERVFAIL` rather than serving stale records, affecting ~tens of millions of users for ~3 hours.

---

### DNS Amplification / Query Flood

**Trigger:** A recursive resolver (or attacker) begins querying your authoritative servers at high rate. This can happen due to: a buggy application making excessive DNS queries, a misconfigured resolver in retry-storm mode, or a deliberate DNS amplification DDoS attack.

**Symptoms:** Authoritative DNS servers CPU/network saturate. Legitimate queries time out. Downstream services appear unavailable because DNS resolution fails, even though the services themselves are healthy. Monitoring shows unusually high query rates from specific source IPs.

**Detection:** Authoritative DNS query rate metrics will spike. If using Route53, this shows in CloudWatch `DNSQueries` metric. For self-hosted DNS, `dnstap` logging or `qps` metrics from BIND/PowerDNS will show the spike. Source IP analysis will show concentration.

**Recovery:**
1. Rate-limit at the authoritative server level by source IP (Route53 does this automatically after the November 2020 incident)
2. Use Anycast to distribute the load across global PoPs — volumetric attacks are diluted across nodes
3. Blackhole the attacking source IPs at the network layer if the source is identifiable
4. If using a managed DNS provider, they absorb DDoS automatically; this is primarily a concern for self-hosted DNS

**Real Example:** AWS Route53 November 2020 outage — recursive resolvers in retry-storm mode caused cascading overload of Route53 authoritative servers, leading to DNS resolution failures for Route53-hosted domains for ~8 hours.

---

### Split-Brain DNS (Internal vs. External Resolution Mismatch)

**Trigger:** You have internal DNS (for inside-VPC or inside-datacenter resolution) and external DNS (for public internet). They get out of sync — the internal zone serves a different IP or doesn't serve a record that the external zone does.

**Symptoms:** Applications running inside the VPC get different IPs than external clients, causing internal service-to-service calls to fail or route incorrectly. External monitoring shows the service healthy while internal health checks fail, or vice versa.

**Detection:** Run the same `dig` query against both your internal resolver and an external resolver (`8.8.8.8`). If the answers differ unexpectedly, you have split-brain. In AWS VPCs, Route53 private hosted zones and public hosted zones for the same domain must be kept in sync manually.

**Recovery:** Standardize on one authoritative source of truth. In AWS, use Route53 private hosted zones for internal resolution that **override** the public record for VPC traffic only. Automate record sync via Terraform or ExternalDNS so both zones stay consistent.

**Real Example:** A common failure mode in AWS multi-account architectures: a new microservice is deployed in a new account, its Route53 record is created in the new account's hosted zone, but the internal DNS resolver for the legacy VPC doesn't have the cross-account delegation set up. Internal services cannot resolve the new service's hostname despite it being externally reachable.

## 10. When To Use vs. When To Avoid

### Use DNS-Based Traffic Management When:

- **You are routing between multiple geographic regions or datacenters.** DNS is the only layer that works for all clients without SDK changes. GeoDNS + health checks is the de-facto standard for multi-region active-active architectures.

- **Your RTO (recovery time objective) allows 2-5 minutes of failover time.** DNS-based failover (health check detection: 90s + TTL expiry: 60s) consistently achieves 2-3 minute failover. This meets most B2C web application SLAs.

- **You are doing blue-green or weighted canary deployments at the infrastructure level.** Weighted DNS routing (e.g., Route53 weighted records: 95/5 split between two ALBs) is a clean, reversible way to shift traffic during deploys without modifying application code.

- **You need to handle client environments you don't control.** Mobile apps, third-party integrations, CLI tools — they all speak DNS. DNS-level routing is the only traffic control mechanism that reaches every client.

### Do NOT Use DNS-Based Traffic Management When:

- **Your RTO requires sub-30-second failover.** DNS cannot provide this reliably. Use a load balancer with active health checks, or a service mesh with circuit breaking. AWS ALB health checks detect failures in < 10 seconds and remove unhealthy targets immediately.

- **You need per-request load balancing with precise distribution.** DNS round-robin or weighted DNS distributes at the query level, not per connection. With caching, you can have 90% of a resolver's users hitting one server and 10% hitting another, with no guarantee of the intended ratio.

- **You need fine-grained application-level routing** (e.g., route `/api/v2/payments` to one cluster and `/api/v2/search` to another). DNS operates on hostnames, not paths. Use L7 load balancers or API gateways for path-based routing.

### The Number One Mistake Engineers Make

**Assuming that setting TTL=60 on your records means clients will switch to your new IP within 60 seconds when you update the record.**

The reality: TTL is the maximum caching time, not a timer. Resolvers that cached your record 1 second before you changed it will cache the old record for another 59 seconds. Resolvers that cached it 30 minutes ago at TTL=1800 will hold the old record for another 1770 seconds. **The time to full propagation equals the TTL that was in effect when clients last cached the record, not the new TTL you just set.**

Always pre-lower TTL to 60 at least one full TTL period (usually 24-48h) before a planned migration.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a globally distributed API. How do you route users to the closest region?"
- "Your primary datacenter just went down. Walk me through how your system fails over."
- "What is DNS TTL and why does it matter for deployments?"
- "How would you design a zero-downtime deployment for a service with 100 million users?"
- "Your monitoring shows that 30% of users can't reach your service but 70% can. How do you debug this?"
- "Explain how Cloudflare 1.1.1.1 achieves low latency globally."
- "What's the difference between anycast and GeoDNS?"

### What the Interviewer Is Evaluating

- **Systems thinking:** Do you understand that DNS is a caching, distributed system with propagation delays — not an instant switch?
- **Trade-off reasoning:** Can you articulate the TTL trade-off (cacheability vs. agility) without oversimplifying?
- **Failure mode awareness:** Do you know that DNS can cause outages independent of your application servers?
- **Scale sensitivity:** Does your approach change as scale increases, or do you give the same answer for 1K and 100M users?
- **Precision:** Do you say "fast" or do you say "< 3 minutes end-to-end with TTL=60 + Route53 health checks"?

### Questions You Ask Before Answering

Before diving into a DNS design:

1. "What are the geographic distributions of our users? Are we talking single-region or truly global?"
2. "What's the RTO target? Minutes, seconds, sub-second?"
3. "Is the traffic pattern bursty or steady? What's peak QPS?"
4. "Are we already on a cloud provider? That determines whether Route53, GCP Cloud DNS, or Azure DNS is the natural fit."
5. "Do we have any compliance requirements that restrict where data and traffic can route?" (GDPR, PCI-DSS)

### Junior (L3-L4) Answer Example

**Q: What is DNS TTL and why does it matter?**

> "TTL is Time To Live — it tells resolvers how long to cache a DNS record. A shorter TTL means changes propagate faster because resolvers stop serving old records sooner. A longer TTL means fewer queries to your DNS server and faster lookups for users because resolvers have it cached. You'd use a short TTL — like 60 seconds — for an API endpoint where you need fast failover, and a longer TTL — like an hour — for records that don't change often."

This is correct and complete for L3-L4. It shows basic understanding of the mechanic and a practical application.

### Senior (L5) Answer Example

**Q: Same question, but in the context of a multi-region design.**

> "TTL is the central dial in DNS architecture — you're trading off propagation speed against resolver cache efficiency. For a multi-region API, I'd set the A records for my regional endpoints to TTL=60. Here's why: I'll use Route53 health checks with a 30-second interval and failure threshold of 3. That's 90 seconds to detect failure. With TTL=60, worst case a resolver cached the unhealthy IP 1 second before the health check detected failure — so that resolver holds the stale record for 59 more seconds. Total failover window: roughly 90 + 60 = 150 seconds, or 2.5 minutes. That's acceptable for most web services.
>
> The cost: reducing from TTL=3600 to TTL=60 multiplies authoritative query volume by 60x. At scale, that's meaningful in cost and in authoritative server capacity requirements. I'd only lower TTL for records that are actually health-checked — CDN CNAMEs can stay at TTL=300 since they don't need health-check integration.
>
> One critical thing: before any planned migration, I lower the TTL 24+ hours in advance. Because the propagation window is determined by the TTL that was in effect when resolvers last cached the record — not the TTL I just set."

### Staff (L6+) Answer Example

**Q: Design the DNS architecture for a payment processing service with 99.99% uptime SLA.**

> "Payment processing requires sub-60-second failover SLA, which DNS alone cannot guarantee. I'd use DNS for initial routing, but not as the failover mechanism itself. My architecture:
>
> **Layer 1 — DNS (Global Routing):** Route53 latency-based routing with 4 regions (US-East, US-West, EU-West, AP-Southeast). TTL=30 on payment API endpoints — yes, this is aggressive, but payment downtime is more expensive than DNS query cost. Health checks with 10-second intervals rather than 30-second. I'll negotiate with Route53 pricing.
>
> **Layer 2 — Load Balancer (Intra-Region Failover):** Each region's entry point is a Network Load Balancer with active health checks at 5-second intervals. NLB detects unhealthy targets in < 10 seconds and removes them from rotation with zero DNS change required. This is where sub-minute failover actually happens — DNS gets you to the right region, NLB handles individual server failures.
>
> **Layer 3 — Circuit Breaker (Application-Level):** Service-to-service calls within the cluster use a circuit breaker (Resilience4j / Hystrix). This handles latency-based degradation that health checks don't catch.
>
> **The DNS failure I'm most worried about** is what happened to Facebook in 2021 — BGP and DNS becoming co-dependent such that a BGP failure kills DNS recovery. Mitigation: route my authoritative nameservers through a different network path than my application traffic. Use two authoritative DNS providers (Route53 + Cloudflare as secondary) with different BGP upstream providers. If Route53 becomes unreachable, Cloudflare's NS records still serve.
>
> **Key numbers for payment SLA:** DNS failover = 30s detection + 30s TTL = 60s worst case. NLB failover = 10s. Combined: 60s for region-level failover, 10s for instance-level. Against a 99.99% SLA (52 minutes/year downtime budget), a single 2-minute DNS failover event uses 4% of the annual budget — so I need to make sure I'm not failing over more than ~25 times per year at this time scale."
