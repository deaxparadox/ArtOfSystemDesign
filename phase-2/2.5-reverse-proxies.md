## 1. What Is It? (Theory)

### The Core Problem

You have a backend service. It listens on port 8080. It speaks plain HTTP. It trusts every client that connects. It crashes if it gets too much traffic. It can't serve two apps from the same IP. It runs on an internal network that the public internet cannot reach directly.

This is the default state of most backend services. **A reverse proxy solves every one of those problems.**

A **reverse proxy** is an intermediary server that sits between external clients and one or more backend servers. Clients connect to the reverse proxy — they may not even know backend servers exist. The proxy forwards the request to the appropriate backend, receives the response, and returns it to the client.

The word "reverse" distinguishes it from a **forward proxy**. A forward proxy sits in front of clients and acts on their behalf (corporate proxies that log employee traffic, VPNs, Tor). A reverse proxy sits in front of servers and acts on the servers' behalf. The direction of the trust boundary is reversed.

### Why It Was Invented

In the late 1990s, two problems converged:

1. Web servers (Apache, early IIS) were expensive to scale. A single Apache process consumed significant memory per connection.
2. Websites started needing multiple backend services: a PHP app, a Java API, a static asset server — all accessible from the same domain.

Igor Sysoev built Nginx in 2002 specifically to solve Apache's connection overhead problem. By sitting nginx in front of Apache as a reverse proxy, you could handle tens of thousands of concurrent connections at the edge while keeping the number of connections to the heavier Apache processes small. Nginx 1.0 was released in 2004. By 2019, it had surpassed Apache as the most widely deployed web server.

### The Real-World Analogy

Think of a large hospital. Patients (clients) don't walk directly to the cardiologist's office, the lab, or the pharmacy. They go to a **reception desk** (the reverse proxy). The receptionist:

- Checks their identity (authentication)
- Directs them to the right department (routing)
- Keeps track of wait times and sends them to the least-busy doctor (load balancing)
- Won't let them into restricted areas (security policies)
- Speaks the hospital's language even if the patient only speaks English (protocol translation)

The patient never knows the internal layout of the hospital. The hospital's departments don't need to deal with unscreened walk-ins.

### What Breaks Without One

| Problem | Without Reverse Proxy | With Reverse Proxy |
|---|---|---|
| TLS termination | Every backend manages its own certs | One cert, one renewal, one config |
| Multiple apps on port 443 | Impossible — only one process per port | Route by hostname/path to any backend |
| DDoS protection | Backend is directly exposed | Proxy absorbs and filters at edge |
| Rate limiting | Every service reimplements it | Centralized, consistent |
| Backend protocol | Must speak HTTP/1.1 to clients | Proxy can translate (HTTP/2, gRPC, WebSocket) |
| Client IP logging | Backend sees load balancer IPs | X-Forwarded-For populated correctly |
| Graceful deploys | New deploy = connection drops | Proxy drains connections before switching |

### Concrete Numbers

A single Nginx instance on a 4-core, 8 GB VM can:
- Handle **~60,000 HTTP requests/second** as a reverse proxy (passthrough, no caching)
- Terminate TLS at **~20,000 HTTPS requests/second** (with hardware crypto acceleration)
- Maintain **~10,000 simultaneous upstream connections**
- Add **< 1ms** of proxy overhead at p99 under normal load

Without a reverse proxy, a typical Python/Node.js backend handles 200–2,000 req/s before degrading. The proxy is not a bottleneck — it is a force multiplier.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step Request Flow

```
1. Client opens TCP connection to proxy (e.g., 203.0.113.10:443)
2. Proxy performs TLS handshake with client (terminates TLS)
3. Proxy reads HTTP request headers
4. Proxy applies routing rules: match Host header → determine backend pool
5. Proxy applies middleware: rate limit check, auth header validation, WAF rules
6. Proxy selects a backend from the pool (round-robin, least-connections, etc.)
7. Proxy reuses or opens a TCP keep-alive connection to the backend
8. Proxy forwards request over plain HTTP to backend (no TLS on internal network)
9. Backend processes request, sends HTTP response
10. Proxy receives response, optionally caches it
11. Proxy writes response over TLS back to client
12. TCP connection to client may be kept alive (HTTP keep-alive) for reuse
```

### Key Subsystems

**Connection Management**

The proxy maintains two connection pools: one toward clients (downstream), one toward backends (upstream). These are decoupled. A client using HTTP/1.1 (one request per connection) can still hit a backend over an HTTP/2 multiplexed connection. The proxy absorbs the impedance mismatch.

Critical configuration: `keepalive_timeout` on the proxy toward clients should be **longer** than `keepalive_timeout` on the proxy toward backends. If the backend closes a connection before the proxy stops using it, the proxy will forward a request into a half-closed connection and generate a 502. This is one of the most common production misconfiguration bugs.

**TLS Termination**

The proxy holds the private key and certificate. It performs the TLS handshake with the client. Traffic from proxy to backend travels over the internal network in plaintext (or with mTLS if you need it). Benefits:

- TLS handshake cost paid once at the edge (not by each backend replica)
- Certificate renewal in one place
- Backends need no TLS configuration

TLS handshake overhead: ~0.5ms for TLS 1.3 (with session resumption), ~3ms for TLS 1.2 (full handshake). At 10,000 new connections/second, this adds up. Session tickets and OCSP stapling are mandatory at scale.

**Header Injection**

The proxy rewrites headers before forwarding:
- `X-Forwarded-For: <client-ip>` — real client IP for backend logging
- `X-Real-IP: <client-ip>` — single client IP (not a list)
- `X-Forwarded-Proto: https` — tells backend the original protocol
- `Host: api.example.com` — preserve original host (or rewrite for multi-tenant)

Without `X-Forwarded-For`, all backend logs show `127.0.0.1`. Rate limiting by IP on the backend becomes useless. This is a silent failure — everything looks fine until you need the data.

**Routing**

L7 routing decisions are made on: `Host` header (virtual hosting), URL path prefix (`/api/` → service-a, `/static/` → CDN), HTTP method (GET → read replicas, POST → primary), custom headers, query parameters, and cookie values (sticky sessions via cookie injection).

**Caching**

The proxy caches responses based on `Cache-Control` response headers. A cache hit at the proxy layer costs ~0.1ms and uses zero backend CPU. The cache key is by default the full URL. Vary headers introduce per-header cache variants (dangerous at scale — a `Vary: User-Agent` header can explode cache key space to millions of entries).

### Misconceptions

**❌ Misconception: A reverse proxy and a load balancer are the same thing.**
✅ Reality: A load balancer distributes traffic across a server pool. A reverse proxy can do that, but also does TLS termination, caching, auth, header manipulation, rate limiting. All load balancers proxy; not all reverse proxies balance load. Nginx is both. HAProxy is primarily a load balancer. The distinction matters when you're choosing tools and responsibilities.

**❌ Misconception: Putting a proxy in front adds latency.**
✅ Reality: A well-tuned proxy adds < 1ms p99. It often reduces effective latency by keeping upstream connections warm, using HTTP/2 multiplexing to backends, and serving cached responses at 0.1ms. The proxy is rarely the bottleneck.

**❌ Misconception: The proxy sees plaintext traffic only if you terminate TLS there.**
✅ Reality: **TLS passthrough** is also a mode — the proxy forwards encrypted TLS traffic without terminating it. In this mode the proxy cannot read headers, cannot route by Host, and cannot inject headers. It can only route by SNI (the hostname hint sent during TLS handshake before encryption starts). This is an L4 forwarding decision, not L7.

**❌ Misconception: X-Forwarded-For gives you the real client IP.**
✅ Reality: X-Forwarded-For is a list that anyone can append to. A client can spoof it by sending `X-Forwarded-For: 1.2.3.4` before the proxy adds itself. Your rate limiting code must only trust the **rightmost** IP added by a proxy you control. If your proxy is not the first hop (e.g., there's a CDN in front), you must configure trusted proxy ranges.

## 3. Real-World Architecture Examples

### Cloudflare — Reverse Proxy as a Business

Cloudflare is, at its core, a global reverse proxy network. Their product is the proxy. As of 2024, they handle over **57 million HTTP requests per second** at peak across 300+ data centers.

Their edge network terminates TLS for millions of customer domains. Certificates are managed at scale using their own CA infrastructure and automated issuance. Their HTTP proxy (built on their own Pingora framework, open-sourced in 2023) processes every request through a pipeline of: DDoS mitigation → WAF → rate limiting → caching → origin fetch.

**Key decision**: In 2022, Cloudflare replaced their Nginx-based edge with **Pingora**, a custom Rust proxy. The reason: Nginx's process model meant connection pools were not shared across worker processes. Each worker had its own pool to origin servers, leading to `N_workers × N_origins` connections. At Cloudflare's scale, this meant millions of unnecessary connections to origin servers. Pingora uses a multithreaded model with a shared connection pool, reducing origin connections by 87.5% and memory usage significantly. This is a landmark case study in what breaks at extreme scale that works fine at normal scale.

**Failure (2025)**: A TLS bug caused by an incompatible certificate authority bundle configuration affected a narrow slice of clients. The bug was invisible in testing because browsers with cached intermediate certificates worked fine. This illustrates a critical lesson: TLS failures are often partial — they affect some clients and not others, making them hard to detect with standard uptime monitoring.

### Netflix — Edge Proxy and Internal Service Mesh

Netflix operates two layers of reverse proxying:

1. **Edge layer (Zuul)**: A Java-based API gateway / reverse proxy that handles all client traffic (~200 billion requests/day at peak). It does authentication, routing, A/B testing, request fan-out, and response aggregation. Netflix open-sourced Zuul 1 and Zuul 2 (non-blocking I/O).

2. **Internal mesh (Envoy sidecars)**: Every microservice has an Envoy sidecar proxy. Internal service-to-service calls go through Envoy, which handles mTLS, retries, circuit breaking, and distributed tracing (B3 propagation). Netflix uses this to enforce mTLS on all internal traffic — a backend service cannot directly call another backend; the call goes through Envoy which authenticates the caller.

**Key decision that went wrong first**: Netflix originally used a monolithic edge proxy. When they moved to microservices, requests from clients needed to fan out to 10–30 internal services. The monolithic proxy became a bottleneck. The lesson: a single proxy handling business logic (aggregation) does not scale the same way as a pure routing proxy. They eventually separated the two concerns: Zuul for edge routing, Hystrix/Resilience4j for internal circuit breaking, and Envoy for the actual sidecar proxying.

**Numbers**: Zuul at Netflix handles the equivalent of >2 million requests/second during peak evening hours. The internal Envoy mesh handles 10x that volume (service-to-service amplification).

### Discord — Nginx to Envoy at 500M Users

Discord started with Nginx as a reverse proxy. As they scaled past 100 million daily active users and hundreds of microservices, Nginx became a management problem: static configuration files, manual reloads, no built-in support for dynamic service discovery in Kubernetes.

They migrated to **Envoy** as their edge and internal proxy for several reasons:
- Envoy supports **xDS APIs**: backends and routes update dynamically without a reload or restart
- Built-in support for gRPC (Discord uses Go and Elixir heavily)
- Rich observability: Envoy emits per-route, per-cluster metrics automatically
- Circuit breaking and retries are configuration, not code

**What they got wrong first**: Initial Envoy configuration was generated manually. When they scaled to hundreds of services, they hit configuration drift — different services had inconsistent timeout settings, buffer sizes, and retry policies. The fix was generating Envoy config programmatically from a service registry (control plane), which is the intended usage model but requires upfront investment.

### Design Questions to Ask Before Starting

Before configuring a reverse proxy, answer these:

1. **What is the expected req/s and p99 latency requirement?** This determines whether you need a single Nginx or an HA pair, and whether caching is necessary.
2. **Who is responsible for TLS certificate issuance and renewal?** Automated (Let's Encrypt/ACME) or manual? Who gets paged when the cert expires?
3. **How are backends registered?** Static config file, DNS service discovery, or dynamic xDS control plane? Dynamic services (Kubernetes pods) cannot use static config.
4. **What is the timeout budget?** Client-facing timeout > proxy-to-backend timeout. Proxy-to-backend keep-alive < backend idle timeout. If you get these wrong, you get 502s.
5. **Does the backend need to know the real client IP?** If yes, configure `X-Forwarded-For` and trust only your proxy IP ranges.
6. **Are there WebSocket or gRPC connections?** These require different proxy configuration (upgrade headers, long-lived connections, HTTP/2 framing).
7. **Who handles rate limiting?** At the proxy (per-IP, per-path) or in application code? Both layers are common. Proxy rate limiting is cheaper (rejected before app server CPU is used).

### Scale Evolution

**1K users/day (startup)**
- A single Nginx on the same VM as the app is fine
- Nginx handles TLS termination and serves static files from disk
- No HA needed — downtime during deploys is acceptable
- Simple path-based routing: `/` → app, `/static/` → filesystem

**100K users/day (growing)**
- Nginx moves to a dedicated instance (or two in HA with keepalived/floating IP)
- TLS terminated at Nginx; backend speaks plain HTTP
- Rate limiting configured at Nginx: 100 req/s per IP on `/api/`
- Cache-Control headers enforced: static assets cached at Nginx, dynamic bypass cache
- Health checks added: proxy stops routing to unhealthy backends

**1M users/day (scale-up)**
- Nginx replaced with a managed load balancer + WAF (AWS ALB + AWS WAF, or Cloudflare proxied mode)
- Or: Nginx cluster behind a cloud NLB (3+ instances, auto-scaling group)
- gzip compression enabled at proxy — CPU tradeoff reduces bandwidth by 60–70% for JSON
- Connection pooling tuned: `keepalive 32` to backends (persistent HTTP connections)
- Separate proxy instances per service tier (API, WebSocket, static) — different timeout configs

**10M+ users/day (distributed)**
- Multi-region deployment: reverse proxies in 3+ regions, GeoDNS or anycast routing
- Envoy-based edge with xDS control plane (e.g., Envoy Gateway, Istio ingress)
- Service mesh for east-west traffic (Envoy sidecars on every pod)
- Certificate management via cert-manager + Let's Encrypt or commercial CA
- Observability: every request traced, every backend latency p50/p99 tracked per-route

## 5. Code / Implementation Perspective

### Python: Minimal Reverse Proxy Sketch

This demonstrates the core mechanics: accept client connection, forward to backend, stream response back.

```python
import asyncio
import httpx

# A minimal async reverse proxy — NOT production code
# Shows the core mechanics of request forwarding

ROUTING_TABLE = {
    "/api/": "http://backend-api:8001",
    "/auth/": "http://backend-auth:8002",
    "/": "http://backend-web:8000",
}

def resolve_upstream(path: str) -> str:
    """Match longest prefix in routing table."""
    for prefix in sorted(ROUTING_TABLE.keys(), key=len, reverse=True):
        if path.startswith(prefix):
            return ROUTING_TABLE[prefix]
    raise ValueError(f"No route for path: {path}")

async def handle_request(
    scope: dict, receive, send, client: httpx.AsyncClient
) -> None:
    """ASGI handler that proxies to upstream."""
    assert scope["type"] == "http"

    path = scope["path"]
    query = scope.get("query_string", b"").decode()
    method = scope["method"]
    headers = dict(scope["headers"])

    # Inject forwarded-for header
    client_ip = scope.get("client", ("unknown", 0))[0]
    existing = headers.get(b"x-forwarded-for", b"").decode()
    headers[b"x-forwarded-for"] = (
        f"{existing}, {client_ip}" if existing else client_ip
    ).encode()
    headers[b"x-forwarded-proto"] = b"https"

    # Read request body
    body = b""
    async for chunk in _iter_body(receive):
        body += chunk

    # Forward to upstream
    upstream_base = resolve_upstream(path)
    url = f"{upstream_base}{path}"
    if query:
        url += f"?{query}"

    upstream_response = await client.request(
        method=method,
        url=url,
        headers=headers,
        content=body,
        follow_redirects=False,
    )

    # Stream response back to client
    await send({
        "type": "http.response.start",
        "status": upstream_response.status_code,
        "headers": list(upstream_response.headers.raw),
    })
    await send({
        "type": "http.response.body",
        "body": upstream_response.content,
    })

async def _iter_body(receive):
    while True:
        event = await receive()
        if event["type"] == "http.request":
            yield event.get("body", b"")
            if not event.get("more_body", False):
                break
```

### Nginx Configuration: Production-Ready Template

```nginx
# /etc/nginx/sites-available/api.example.com

upstream api_backend {
    # Keep persistent connections to backends
    keepalive 32;
    keepalive_requests 1000;
    keepalive_timeout 60s;

    server backend-1:8080 max_fails=3 fail_timeout=30s;
    server backend-2:8080 max_fails=3 fail_timeout=30s;
    server backend-3:8080 max_fails=3 fail_timeout=30s;
}

# Rate limiting zone: 10MB state, 100 req/s per IP
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/s;

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    # Inject real client IP into requests
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host              $host;

    # Critical: proxy keep-alive timeout < backend idle timeout
    proxy_http_version 1.1;
    proxy_set_header Connection "";  # Enable keep-alive to backends

    location /api/ {
        limit_req zone=api_limit burst=200 nodelay;
        proxy_pass http://api_backend;
        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;   # Must be > slowest backend operation
        proxy_send_timeout    10s;
    }

    location /healthz {
        access_log off;
        return 200 "ok\n";
        add_header Content-Type text/plain;
    }
}
```

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Reverse proxy (Nginx/HAProxy)** | Default choice; any production system | Operational overhead of managing proxy config; worth it almost always | Everyone |
| **Cloud-managed LB only (ALB/GCP LB)** | Full cloud commitment, no infra team, simpler ops | Less flexibility (no custom Lua, no dynamic config beyond cloud console); vendor lock-in | Netflix (Zuul behind ALB), Airbnb |
| **API Gateway (Kong, AWS API GW)** | When you need per-route auth, quota, developer portal | More complexity and cost; can become a bottleneck and a place where business logic leaks | Stripe (API GW at edge), Twilio |
| **Service mesh (Istio/Linkerd)** | East-west (service-to-service) traffic, mTLS required, Kubernetes-native | Very high operational complexity; adds ~2–5ms per hop; Istio control plane is expensive | Google, Lyft, Discord, Airbnb |
| **No proxy (direct client → service)** | Internal tools, dev environments, extremely latency-sensitive internal services | No TLS termination, no routing, no auth layer; every service manages its own concerns | Database connections (intentional), dev laptops |
| **Forward proxy (Squid, Tinyproxy)** | Outbound traffic filtering (egress control), corporate policy enforcement | Different problem — controls what your servers can reach, not who can reach your servers | Enterprises with compliance needs |

### My Recommendation

**Start with Nginx.** It is battle-tested, documented exhaustively, and runs everywhere. For Kubernetes, use the Nginx Ingress Controller (or Traefik if you want zero-touch cert management). If you go deep into microservices and need dynamic configuration without restarts, migrate to Envoy via a Gateway API or Istio. If you're on AWS, the managed ALB is a reasonable default if you do not need custom behavior beyond what the console exposes.

Do not start with a service mesh (Istio) on day one. It is immense operational complexity for benefits you won't need until you have 20+ services and an SRE team. The stack that works at 99% of companies is: Cloudflare (edge) → Nginx (ingress) → services. Add Envoy sidecars when you need mTLS or fine-grained per-service retry policies.

## 8. Trade-offs (Be Opinionated)

### Benefits

- **TLS centralization**: One certificate, one renewal, one config. At 50 services, the alternative (each service manages its own cert) is an operational nightmare. Certificate expiry causes ~20% of "random" production outages at companies without centralized TLS management.
- **Performance multiplier**: Nginx with HTTP/2 to clients and keep-alive to backends reduces backend TCP handshakes by 90% under sustained load. HTTP/2 multiplexing means 10 requests share one connection. This is not a minor optimization — at 50K req/s, the savings in backend connection overhead are measurable in CPU percentage.
- **Security boundary**: The proxy is the only surface the internet touches. Backends are on a private network. If a backend has a vulnerability (log4j-style RCE), the proxy can block exploit patterns at the WAF layer before the request reaches the backend. This is defense in depth.
- **Operational flexibility**: Blue-green deploys, canary releases, A/B testing — all implemented as proxy routing rules, not application code changes. Rolling 5% of traffic to a new backend version takes a config change, not a deploy.
- **Observability chokepoint**: Every request passes through the proxy. Request logs, latency histograms, error rates, status code distributions — all available without touching application code.

### Costs and Limitations

- **Extra network hop**: Adds 0.5–2ms to every request. Trivial for most applications. Significant for ultra-low-latency trading systems (< 1ms SLA).
- **Single point of failure if not HA**: A single Nginx instance going down takes everything with it. Mitigated by running 2+ instances with a floating IP (keepalived) or behind a cloud NLB. But this adds cost and setup complexity.
- **Config complexity at scale**: At 200+ services with different timeout requirements, Nginx config files become a maintenance burden. Templating (Jinja2, Helm) helps but introduces its own complexity. Envoy with a control plane is the right solution at this scale but requires more upfront investment.
- **Connection keep-alive misconfiguration**: The most common production bug. Proxy keep-alive timeout must be shorter than backend keep-alive timeout. If inverted: proxy tries to reuse a backend connection the backend already closed → 502. This is invisible until it happens in production.
- **Cache invalidation complexity**: If the proxy caches responses, you now have a caching layer you must reason about and invalidate correctly. `Cache-Control: no-store` on sensitive routes (auth, payments) is mandatory and often forgotten.

### Core Tension

**Centralization vs. complexity.** Every feature you push into the proxy (auth, rate limiting, routing) simplifies backends but increases the blast radius if the proxy misconfigures or fails. The proxy becomes a shared dependency for every service. A misconfigured rate limit rule can black-out your entire API. You are trading per-service complexity for a single centralized control point — which is the right trade for most organizations, but requires rigor in change management.

### My Recommendation

Use a reverse proxy unconditionally in any system that serves external traffic. The question is not whether to use one, but where to put which features. Keep the proxy thin: TLS, routing, basic rate limiting, header injection. Push business logic (auth token validation, per-user quotas, API versioning) into dedicated services or API gateways. A proxy that understands your business logic is a proxy that breaks in unexpected ways when business logic changes.

## 9. Failure Modes — What Goes Wrong

### Keep-Alive Timeout Inversion (The 502 Bomb)

**Trigger:** Proxy `keepalive_timeout` is set equal to or greater than the backend server's idle connection timeout. Backend closes the connection while proxy still considers it valid and reuses it.

**Symptoms:** Sporadic HTTP 502 errors affecting 0.1%–2% of requests. Errors are non-deterministic — same request succeeds on retry. Backend application logs show no errors (the connection died before the request arrived).

**Detection:** Check proxy error logs for "upstream prematurely closed connection" or "connection reset by peer". Metric: upstream 502 rate > 0 but low (0.1%–1%). Alert on 5xx rate spike that doesn't correlate with backend health check failures.

**Recovery:** Set proxy keepalive timeout to 80% of backend idle timeout. If backend is 60s, set proxy to 48s. Restart proxy (with `nginx -s reload` — this is graceful, zero-drop). Verify 502 rate drops to 0.

**Real Example:** This is documented as a known class of Nginx misconfiguration. iximiuz.com has a detailed write-up. It affects any proxy-backend pair where the backend has an idle timeout and the proxy does not know about it — this includes Gunicorn (120s default), Uvicorn, Rails Puma, and Spring Boot (60s default).

---

### TLS Certificate Expiry

**Trigger:** Automated certificate renewal fails silently. The cert expires. Clients receive `SSL_ERROR_EXPIRED_CERT` or `ERR_CERT_DATE_INVALID`.

**Symptoms:** 100% failure rate on HTTPS traffic. HTTP (port 80) may still work. Browser shows security warning. Users cannot proceed. Revenue impact is immediate.

**Detection:** Monitor certificate expiry date. Alert at 30 days, 7 days, 1 day. Tools: `openssl s_client -connect domain:443`, Datadog TLS check, Prometheus `ssl_cert_not_after` metric. Let's Encrypt certbot logs should be monitored.

**Recovery:** Renew certificate immediately (`certbot renew --force-renewal`). Reload proxy (`nginx -s reload`). If automated renewal is broken, fix the root cause (DNS validation failing, certbot not running, rate limit hit from too many renewal attempts).

**Real Example:** GitHub had a certificate expiry incident in 2018 (widely reported). In 2020, Let's Encrypt expired its root certificate causing millions of sites to fail on older Android devices. The failure mode: old devices don't have the new root CA in their trust store. This illustrates that certificate issues can be subtle — not just expiry of your cert, but changes in the CA chain.

---

### Upstream Connection Pool Exhaustion

**Trigger:** Traffic spike causes all upstream connections to be in use. New requests queue. Queue grows faster than upstream processes requests. Queue overflows. Proxy starts rejecting new requests.

**Symptoms:** HTTP 503 Service Unavailable (proxy-generated). Proxy logs: "upstream: no live upstreams while connecting to upstream." Backend CPU may be low — it is not being saturated, it is simply not receiving traffic because the queue already overflowed.

**Detection:** Monitor `nginx_upstream_peers_total{state="unavailable"}`. Alert on >0 for >30s. Track request queue depth if proxy exposes it. HAProxy's stats page shows current queue length per backend pool.

**Recovery:** Add backend instances to the pool. Increase proxy connection pool size (`keepalive` directive). Reduce upstream response times (the pool drains faster when backends are faster). Short term: shed load at the proxy with rate limiting to protect backends.

**Real Example:** This is the classic failure mode during traffic spikes (Black Friday, product launches, viral events). The proxy appears to be the problem (it's returning 503) but the real issue is the backends cannot keep up. The proxy is working correctly — it's refusing to overload the backends. Without the proxy, the backends would all die under direct connection storms.

---

### Misconfigured Header Trust (IP Spoofing)

**Trigger:** Backend rate limits by IP using `X-Forwarded-For` header. Proxy appends to the header but does not sanitize it. Attacker sends `X-Forwarded-For: 127.0.0.1` in their request. Proxy appends real IP: `X-Forwarded-For: 127.0.0.1, 185.x.x.x`. Backend reads the first IP (127.0.0.1) and does not rate limit.

**Symptoms:** Rate limiting completely bypassed. No obvious errors. Attack traffic increases without triggering any alerts.

**Detection:** Log the full `X-Forwarded-For` header at the proxy. Alert on requests where the first IP in the chain is a private/loopback address but the connection came from a public IP. Audit: grep access logs for `X-Forwarded-For: 127.0.0.1` or `10.` prefix.

**Recovery:** Configure proxy to **overwrite** (not append to) `X-Forwarded-For` with the real client IP for requests coming from untrusted sources. In Nginx: `proxy_set_header X-Forwarded-For $remote_addr;` (instead of `$proxy_add_x_forwarded_for`). Only use the append variant if you have a trusted upstream proxy (Cloudflare IP ranges).

**Real Example:** This class of vulnerability affected multiple applications using Flask-Limiter and similar libraries when behind proxies. The Django documentation explicitly warns about this in its `ALLOWED_HOSTS` and `REMOTE_ADDR` handling section. It is one of the OWASP Top 10 application security misconfiguration categories.

## 10. When To Use vs. When To Avoid

### Use When

**✅ Any production system serving external traffic over HTTPS.** There is no good reason to expose a backend service directly to the internet. The proxy provides TLS, DDoS mitigation, and routing. Cost: < $50/month for a DigitalOcean Droplet running Nginx. Value: enormous.

**✅ Multiple backend services need to be accessible from one domain.** You cannot bind two processes to the same port. A proxy routes `/api/` to service A and `/admin/` to service B, both on port 443. Without a proxy, you need different domains or different ports, which breaks UX and CORS assumptions.

**✅ You need zero-downtime deploys.** The proxy can drain in-flight connections to old backends before switching to new ones. Backends registered with the proxy can be rolled one at a time. Without a proxy, a deploy drops active TCP connections.

**✅ You need centralized observability.** Access logs, latency distributions, and error rates at the proxy give you a complete picture of system health without instrumenting every individual backend.

**✅ East-west service mesh traffic requires mTLS and retry policies.** Envoy sidecars as reverse proxies between services enforce mTLS automatically and apply circuit breaking without application code changes.

### Do NOT Use When

**❌ Ultra-low-latency connections where sub-millisecond matters.** Financial trading systems with < 1ms SLA, real-time gaming with < 5ms requirement, or high-frequency data pipelines may not be able to absorb the proxy overhead. These systems often use kernel bypass networking (DPDK, RDMA) and direct connections. Adding a software proxy adds 1–3ms per hop — unacceptable.

**❌ Database connections.** You generally do not put a reverse proxy in front of PostgreSQL or MySQL. Connection poolers (PgBouncer, ProxySQL) serve a similar function but are specialized for the database protocol, connection pooling semantics, and authentication. A generic reverse proxy doesn't understand database wire protocols.

**❌ Purely internal batch jobs with no external-facing endpoints.** A background worker that reads from a queue and writes to a database does not need a reverse proxy. Adding one adds complexity and failure surface for no benefit.

**❌ You're trying to use a reverse proxy as a replacement for proper authentication.** A proxy can forward auth headers and do basic JWT validation, but relying on the proxy as your sole auth layer means all services behind it are unauthenticated. A compromised internal system (or a misconfigured proxy bypass) gives full access to all backends. Auth must be implemented in application code as well.

### The #1 Mistake Engineers Make

**⚠️ Configuring the proxy → backend `keepalive_timeout` equal to or greater than the backend's idle connection timeout, resulting in sporadic 502s that are invisible in backend logs and extremely difficult to diagnose.**

This is the single most common proxy misconfiguration in production. The fix is simple once you know about it: proxy keep-alive timeout must be 20-30% shorter than the backend's idle timeout. But most engineers discover this only after an embarrassing on-call incident. When you see "sporadic 502s, no backend errors, no pattern" — check your keepalive timeout configuration first.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design a URL shortener like bit.ly" → proxy comes up in traffic routing and rate limiting
- "How would you design a system to handle 1 million requests per second?" → proxy is the entry point
- "Walk me through what happens when a user types `https://example.com` in a browser" → proxy is step 3
- "How would you implement rate limiting?" → proxy-layer rate limiting is the right first answer
- "How do you achieve zero-downtime deployments?" → proxy draining is the core mechanism
- "How does TLS termination work in a large-scale system?" → direct question about the proxy
- "Explain the difference between a load balancer and a reverse proxy" → definitional question

### What The Interviewer Evaluates

1. **Does the candidate naturally put a proxy at the edge?** (Do they know the standard topology?)
2. **Can they explain why — not just what?** (TLS centralization, routing, not just "it balances load")
3. **Do they know failure modes?** (502 causes, timeout configuration, certificate management)
4. **Can they make a tool choice and defend it?** (Nginx for simplicity, Envoy for service mesh, ALB for managed)
5. **Do they consider operational concerns?** (HA, reload behavior, observability)

### Questions YOU Ask Before Answering

Strong candidates clarify scope before drawing diagrams:

- "Is this a public-facing API or internal service-to-service communication?" (different proxy requirements)
- "Are we on AWS/GCP or on-prem/bare metal?" (managed LB vs self-managed Nginx)
- "Are there WebSocket or gRPC connections, or purely HTTP?" (protocol-specific proxy config)
- "What's the expected traffic scale — thousands or millions of req/s?" (single Nginx vs cluster vs Envoy)
- "Is mTLS or mutual authentication required between services?" (service mesh consideration)

### Leveled Answers

**Junior (L3-L4):** "A reverse proxy sits in front of backend servers and forwards client requests to them. It handles TLS termination so backends don't need to manage certificates. Nginx is the most common choice. It also does load balancing across multiple backend replicas."

This is correct but incomplete. It describes what, not why, and doesn't engage with failure modes or trade-offs.

**Senior (L5):** "I'd put Nginx as the edge proxy in front of all backend services. It terminates TLS — that means one certificate to manage, not one per service. Nginx routes by URL path to the right backend pool, and each pool has health checks so we automatically drain unhealthy instances. Rate limiting lives here at 100 req/s per IP on public endpoints. For zero-downtime deploys, I configure Nginx to drain in-flight connections before switching backends. The critical config detail: proxy keepalive timeout toward backends must be shorter than the backend's idle timeout — otherwise you get sporadic 502s that are invisible in backend logs. If we're on Kubernetes, I'd use the Nginx Ingress Controller and manage this via Ingress resources, with cert-manager for automatic TLS."

This shows depth: understands the why, knows a specific failure mode, thinks about operations (k8s, cert-manager), makes specific recommendations.

**Staff (L6+):** "The topology depends on scale and where we are in the stack. At the edge: either Cloudflare in front (handles DDoS, CDN, WAF, handles ~60% of attacks before they hit our infra) or an AWS ALB if we're AWS-native. ALB handles TLS, routes to ECS/EKS, integrates with ACM for free certificates. Below the ALB, in Kubernetes, Nginx Ingress Controller for L7 routing with path-based rules. For east-west traffic between services, I'd evaluate whether we need a service mesh: if we need mTLS enforcement, per-route retry policies, and circuit breaking without code changes, Envoy sidecars (Istio or plain Envoy Gateway) are the right answer. But I'd only add the mesh when we have 20+ services and the operational overhead of Istio is worth it. Specific concerns I'd raise: keepalive timeout alignment between proxy and backends (source of 502s), X-Forwarded-For trust configuration (IP spoofing risk if not set correctly), and certificate rotation — we need alerting at 30 days before expiry, not just at expiry. I'd also question whether rate limiting should live at the proxy or in a dedicated rate limiting service (Redis-backed, shared state across proxy replicas) — per-instance limits at the proxy are not accurate if you have multiple proxy instances without shared state."

This shows architecture judgment, knows when to add complexity (service mesh) vs. when not to, raises specific security and operational concerns, and thinks about the distributed systems implications (shared rate limit state).
