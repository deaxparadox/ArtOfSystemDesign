## 1. What Is It? (Theory)

### Plain English Definition

A health check is a periodic signal a system sends to itself — or receives from an orchestrator or load balancer — to answer one of two fundamentally different questions:

1. **"Is this process alive and worth keeping around?"** — the liveness question
2. **"Is this process ready to serve real user traffic right now?"** — the readiness question

These sound similar. They are not. Conflating them is one of the most common and most damaging operational mistakes in production Kubernetes environments.

A **liveness probe** answers: "Should the container be killed and restarted?" It catches a process that is running but completely stuck — deadlocked, memory-corrupted, in an infinite loop that will never recover on its own. When a liveness probe fails enough times, the kubelet kills and restarts the container.

A **readiness probe** answers: "Should traffic be sent to this container?" It catches a process that is technically running but not yet useful — still warming up, waiting for a database connection, processing a large backlog. When a readiness probe fails, the container is removed from the load balancer's rotation without being killed.

A **startup probe** (added in Kubernetes 1.16, stable in 1.20) answers: "Has the application finished its initialization?" It gates liveness and readiness checks entirely until the application reports it has started. It exists to solve the JVM/Spring Boot problem: apps that legitimately need 90+ seconds to start but where you still want liveness checking once running.

### The Problem at Scale

Without health checks, three bad things happen:

**Traffic to broken instances.** A load balancer sends requests to a container that crashed or whose process is stuck. Users get errors or timeouts. The error persists until a human notices and intervenes. At 1,000 requests/second across 20 pods, even one stuck pod receiving 5% of traffic means ~50 failed requests per second — that's 180,000 errors per hour before anyone notices.

**Stuck processes accumulate.** A process can be running (from the OS's perspective) and completely broken. A goroutine deadlock in Go, a blocked thread pool in Java, a corrupted in-memory cache — the OS sees a live process; the application is unable to serve a single request. Without a liveness probe, this pod sits in the cluster indefinitely, absorbing traffic and failing silently.

**Premature traffic during startup.** A pod can pass a TCP check (port is open) while the application is still loading — before connection pools are ready, before the cache is warm, before schema migrations have run. Without a readiness probe, the load balancer sends traffic immediately, causing a spike of 500s during every deployment.

### Why Health Checks Were Invented

The concept predates Kubernetes. Early-2000s hardware load balancers (F5, Citrix NetScaler) needed to know which backend servers to route to. They periodically sent HTTP GET requests to a known URL; a non-200 response meant "remove this backend from the pool." This is passive health checking in its original form.

Google's internal cluster manager, Borg, extended this with structured liveness semantics: a container that fails its health check is restarted, not just removed from traffic. When Kubernetes was designed by former Googlers (including Joe Beda, Brendan Burns, and Craig McLuckie) and open-sourced in 2014, it encoded Borg's health model as first-class primitives. The `/healthz` naming convention — the trailing "z" — comes directly from Google's internal "z-pages" convention (`/varz`, `/statusz`, `/rpcz`), where `z` was appended to avoid name clashes with real application paths.

### Real-World Analogy

Think of an airport gate agent and an airplane:

- The **liveness check** is whether the plane's engines are running at all. If the engines are dead and won't restart, you need a new plane (container restart).
- The **readiness check** is whether the plane is ready to board passengers. The engines can be running (liveness passes) but boarding is blocked — refueling not done, safety check in progress, previous passengers still deplaning. No new passengers (traffic) until readiness passes.
- The **startup probe** is whether the plane has even taxied to the gate yet. Don't even start the pre-boarding liveness/readiness checks until the plane arrives.

### Concrete Example with Real Numbers

A Java Spring Boot service at a mid-sized fintech company:
- **Startup time:** 75 seconds (JVM warmup + Flyway migrations + cache hydration)
- **Without a startup probe:** Liveness probe fires at t=30s, fails because the app isn't up, kubelet kills the container. The container restarts, tries to start again, fails again at t=30s — infinite restart loop. The deployment never completes.
- **With a startup probe** (`periodSeconds: 10`, `failureThreshold: 12` = 120s max): Liveness checks are blocked until startup probe succeeds at ~t=75s. Normal liveness checks begin only after startup succeeds.
- **Without a readiness probe:** At t=75s the pod is marked Running, the load balancer immediately sends traffic — but Flyway hasn't finished the migration. The app returns 500 for 12 seconds until migration completes. That's ~600 failed requests at 50 req/s.
- **With a readiness probe** that checks database connectivity: Traffic is withheld until t=87s when the migration is confirmed done. Zero 500s.

## 2. How It Actually Works (Deep Mechanics)

### The Probe Execution Loop

Kubernetes health probes are executed by the **kubelet** — the node-level agent running on every worker node. The kubelet is responsible for the lifecycle of every pod on its node. It does not delegate probe execution to the API server or to any centralized component. This is important: probe results are local to the node.

**Step-by-step mechanics for an HTTP liveness probe:**

```
1. Container starts. kubelet notes the startTime.

2. kubelet waits initialDelaySeconds before firing the first probe.
   (This was the only startup protection before startup probes existed.)

3. Every periodSeconds, kubelet fires an HTTP GET to the pod's IP
   at the configured path and port. This request comes from the
   kubelet process on the node — NOT from inside the pod.

4. kubelet waits up to timeoutSeconds for a response.
   - HTTP 200–399 = success. successThreshold counter increments.
   - HTTP 400+, TCP reset, timeout = failure. failureThreshold counter increments.

5. If consecutive failures reach failureThreshold:
   - LIVENESS: kubelet sends SIGTERM to container. If container does
     not exit within terminationGracePeriodSeconds, kubelet sends SIGKILL.
     Container is restarted. RestartCount increments.
   - READINESS: kubelet marks the pod NotReady. Endpoints controller
     removes the pod from the Endpoints object. kube-proxy removes
     the pod IP from iptables/IPVS rules. Load balancer stops sending
     traffic. Container is NOT killed.

6. If consecutiveSuccesses reach successThreshold after prior failures:
   - Probe transitions back to healthy state.
   - READINESS: pod is re-added to Endpoints. Traffic resumes.
```

### The Four Probe Mechanisms

Kubernetes supports four probe types, each with different semantics:

| Mechanism | How It Works | When to Use | Limitation |
|---|---|---|---|
| **httpGet** | kubelet sends HTTP GET; 200-399 = success | HTTP/HTTPS services; most common | Adds HTTP stack overhead; endpoint must exist |
| **tcpSocket** | kubelet attempts TCP connection to port | Non-HTTP services (Redis, MySQL, raw TCP) | Only checks port open — process may be unresponsive |
| **exec** | kubelet runs a command inside the container | Custom scripts, CLI-based checks | High overhead; exec creates a new process each probe |
| **grpc** | kubelet uses gRPC health protocol (v1.24+) | gRPC services natively | Requires implementing grpc.health.v1 in app |

### Key Configuration Parameters

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30    # Wait before first probe (legacy startup guard)
  periodSeconds: 10          # How often to probe
  timeoutSeconds: 5          # How long to wait for response
  failureThreshold: 3        # Failures before action taken
  successThreshold: 1        # Successes to transition to healthy
                             # (always 1 for liveness; can be >1 for readiness)
```

**Detection latency formula:**

```
Worst-case detection time = initialDelaySeconds + (failureThreshold × periodSeconds)
                          = 30 + (3 × 10) = 60 seconds

Best-case detection time = periodSeconds + timeoutSeconds (one probe in-flight)
                         = 10 + 5 = 15 seconds
```

For failover to complete (traffic removed from a failed pod), add:
- ~2s for Endpoints object propagation
- ~2s for kube-proxy iptables update
- 0s for in-cluster clients (they re-read from service discovery)
- 5-30s for external load balancers (ALB health check sync interval)

**Total worst-case time from pod failure to zero traffic:** 60 + 30 = ~90 seconds with default settings. This is unacceptably slow for production. Well-tuned systems achieve 15-20 seconds.

### Key Algorithms and Data Structures

The kubelet maintains a **prober manager** that runs one goroutine per (container, probe type) pair. Results are stored in a **results.Manager** — a thread-safe map keyed by (pod UID, container name, probe type). The readiness manager writes results to the pod's conditions array (`Ready: True/False`), which the endpoint controller watches via a shared informer.

The critical data structure is the **Endpoints** object — a Kubernetes API resource that lists the IP:port pairs for all Ready pods backing a Service. kube-proxy watches Endpoints objects and translates them into iptables or IPVS rules. This is the mechanism by which a failing readiness probe actually stops traffic — it's not a direct signal to the load balancer; it's a cascade through Endpoints.

### Misconceptions

**Misconception 1:**
> "My service is healthy if the container is running."

**Reality:** A running container can be completely broken. `kubectl get pods` showing `Running` means the main process has not exited — it says nothing about whether the process can serve requests. A deadlocked thread pool, a corrupted in-memory state, or a failed background worker are all invisible to the container runtime.

**Misconception 2:**
> "I should use the same endpoint for liveness and readiness."

**Reality:** This is the most common misconfiguration in production Kubernetes. If your readiness probe checks a database connection and the database has a 20-second hiccup, both probes fail. The liveness probe then kills and restarts all your pods — simultaneously, if `maxUnavailable` is misconfigured — while the database is recovering. You have turned a 20-second dependency blip into a multi-minute full-service outage.

**Misconception 3:**
> "A healthy TCP connection to the port means the service is healthy."

**Reality:** A TCP socket check only verifies that the port is open and accepting connections. A Java process can accept TCP connections while all Tomcat worker threads are blocked. A Node.js process can accept socket connections while the event loop is completely starved. TCP probes are a weak signal — use HTTP probes whenever possible.

**Misconception 4:**
> "More aggressive probes (shorter intervals, lower thresholds) mean faster recovery."

**Reality:** Overly aggressive probes under CPU pressure create a self-reinforcing failure cascade. When a node is CPU-throttled due to load, probe HTTP requests take longer to serve. The probe times out. The kubelet restarts the container. The new container starts up, contributing to more CPU load. The next pod's probes also start timing out. You have converted a load spike into a cluster-wide restart storm.

## 3. Real-World Architecture Examples

### Google / Borg — The Origin

Google's Borg cluster manager, which Kubernetes is directly descended from, established the liveness/readiness distinction as a first-class architectural concept. In Borg, the health check (`/healthz`) controlled both traffic routing and container restart behavior. The "z-pages" convention — `/healthz`, `/varz`, `/statusz`, `/rpcz` — was a Google-internal standard that every service was expected to expose. When Googlers founded or joined external companies and open-source projects, these conventions traveled with them.

The Kubernetes API server itself exposes `/livez` and `/readyz` as separate endpoints (the unified `/healthz` was deprecated in Kubernetes v1.16). The `/readyz` endpoint returns 503 during API server startup and graceful shutdown, cleanly signaling to load balancers that the API server is not ready to serve requests even while the process is running. This is dogfooding: Kubernetes uses its own probe semantics in its own control plane.

**What we learn from Google:** The probe system is designed around operational autonomy — the system should be able to react to component failures without human intervention. At Google's scale (millions of containers), manual failure response is impossible. Probes are how the system maintains reliability automatically.

### Stripe — Standard Health Check Contract

Stripe has a documented internal standard: almost every service exposes a `/healthcheck` endpoint that returns HTTP 200 if healthy. This standardization is critical because Stripe uses HAProxy as a load balancer, and HAProxy needs a consistent endpoint to poll across hundreds of services.

At Stripe's scale, their production system emits millions of health indicators per second. The standardized endpoint contract means:
- New services are automatically integrated into the health check ecosystem without custom configuration
- On-call engineers have a consistent place to look when debugging ("is `/healthcheck` returning 200?")
- Automated runbooks can make decisions based on a known API contract

**Stripe's service discovery blog post** (2020) documented that they use health checks as a gate in service registration — a service instance only joins the routing pool after its health endpoint returns 200 a configurable number of times. This is a pre-registration health gate, distinct from the post-registration Kubernetes readiness probe model.

**Key decision:** Stripe chose a shallow health check (`/healthcheck` returns 200 if the process is up) rather than a deep check that verifies database connectivity. Deep dependency checks at Stripe's internal RPC call volume would generate enormous load on shared infrastructure. Deep checks are reserved for dashboard-level diagnostic endpoints, not operational health gates.

### OpenAI — December 2024 Kubernetes Outage

Between 3:16 PM and 7:38 PM PST on December 11, 2024, all OpenAI services experienced significant degradation or complete unavailability. The root cause was the deployment of a new telemetry service that inadvertently caused every node across all large clusters to make expensive Kubernetes API calls simultaneously. The load scaled exponentially with cluster size.

The cascading failure path:
1. Telemetry service deployment → all nodes polling the Kubernetes API at high frequency
2. Kubernetes API servers overwhelmed → control plane degradation
3. DNS-based service discovery broken → pods unable to resolve service names
4. Readiness probes relying on DNS lookups failed across the fleet
5. Mass pod removal from Endpoints objects → traffic to no backends → complete service outage

**The health probe lesson:** When DNS broke, readiness probes that checked external dependencies (which require DNS resolution) failed everywhere simultaneously. This converted a control-plane issue into a data-plane outage. Probes that checked only local process health would have continued passing — maintaining some service availability — even as the control plane was degraded.

**Post-mortem finding:** The incident highlighted that probe design decisions that seem fine in staging can fail catastrophically in production, because the failure mode (DNS unavailability at scale) only emerges in large production clusters.

### Netflix — Multi-Region Health and Eureka

Netflix operates a service mesh at a scale where individual service health checks are aggregated by their internal service registry, **Eureka**. Each Netflix microservice registers with Eureka and sends a heartbeat every 30 seconds. Eureka uses these heartbeats as a liveness signal — if a service stops heartbeating for 90 seconds (3 missed heartbeats), it is evicted from the registry and traffic stops routing to it.

Netflix also implements what they call **"server-side discovery"** — the client fetches the full registry from Eureka, caches it locally, and makes routing decisions client-side. This means health check state changes propagate to clients through cache refresh cycles (typically 30 seconds), not instantly.

**The trade-off Netflix accepted:** 30-second detection + 30-second cache propagation = up to 60 seconds of traffic to a failed instance. Netflix decided this was acceptable because:
- Their Hystrix circuit breakers (now Resilience4j) provide request-level failure detection and fallback much faster than the health check cycle
- The false positive rate of faster health checks outweighed the cost of slightly slower failure detection

**Key insight:** Netflix treats health checks as a coarse-grained signal for routing decisions, not a fine-grained signal for per-request resilience. The 60-second detection lag is explicitly accepted in their availability model.

## 4. Design Deep Dive

### Questions to Ask Before Designing Your Probe Strategy

Before writing a single line of YAML, answer these questions:

1. **What is my application's startup time (p99)?** This drives whether you need a startup probe and what `failureThreshold` should be on it.
2. **What does "healthy" mean for my service?** Can serve a request? Database connected? Cache warm? Internal queue drained?
3. **What external dependencies does my service have?** Which of them, if they fail, should stop my traffic? Which should trigger a restart vs. a traffic drain?
4. **What is my traffic pattern under probe failure?** If all pods go NotReady simultaneously, where does traffic go? Does my service have circuit breakers upstream?
5. **What is the acceptable detection latency?** 10 seconds? 30 seconds? This drives `periodSeconds` and `failureThreshold`.
6. **How expensive is my health check endpoint?** If the `/ready` endpoint does a database query, calculate the probe traffic: 50 pods × 1 probe/5s = 10 DB queries/second from probes alone.

### Scale Evolution

**Startup phase (1-10 pods, 1 service):**

Keep it simple. A single `/health` HTTP endpoint that returns 200 if the process started is sufficient. Don't over-engineer probe logic at this stage. Your biggest risk is not having any probes, not having imperfect ones. Recommended:
```yaml
readinessProbe:
  httpGet: { path: /health, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 5
```

**Growth phase (10-100 pods, 5-20 services, real traffic SLAs):**

Introduce the liveness/readiness split. Add a startup probe for slow-starting services. Begin separating probe endpoints:
- `/livez` — always returns 200 if process can handle HTTP (liveness, never checks dependencies)
- `/readyz` — returns 200 only if all critical dependencies are reachable (readiness)

This is where most teams discover that checking external dependencies in `/readyz` causes cascading restarts. Add dependency timeouts aggressively to probe handlers (max 500ms per dependency check).

**Enterprise phase (100+ pods, 50+ services, multi-region, 99.99% SLA targets):**

Implement the full probe hierarchy:
- `/livez` — local-only process health
- `/readyz` — traffic readiness with dependency checks
- `/startupz` — initialization completion signal
- `/healthz` — aggregate human-readable diagnostic endpoint (not used by orchestrators)

Tune probe parameters per service type:
- Stateless HTTP services: `periodSeconds: 5, failureThreshold: 2`
- Stateful services (caches, queues): `periodSeconds: 10, failureThreshold: 3`
- Batch processing: readiness returns false when queue depth exceeds threshold

Introduce probe observability: expose probe result counters in Prometheus (`kube_pod_container_status_ready`, `kube_pod_container_status_restarts_total`).

### Decision Framework: What to Check in Each Probe

```
LIVENESS PROBE — check only if process is "alive enough" to restart being useful
├── OK to check: can the HTTP stack respond?
├── OK to check: is a critical background goroutine/thread alive?
├── OK to check: is memory within bounds?
└── NEVER check: external databases, caches, message queues, downstream services

READINESS PROBE — check if traffic should be sent right now
├── OK to check: can the HTTP stack respond?
├── OK to check: is the database connection pool healthy?
├── OK to check: is the cache client connected?
├── OK to check: has startup initialization completed?
└── CAUTION: downstream microservices (may cause cascading readiness failures)

STARTUP PROBE — check if initialization has completed
├── Check the same thing as liveness, but with high failureThreshold
└── Disable automatically once succeeded (Kubernetes handles this)
```

## 5. Code / Implementation Perspective

### Python Implementation — Health Check Endpoints

```python
import time
import threading
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Dict, Optional
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

class HealthStatus(Enum):
    HEALTHY = "healthy"
    DEGRADED = "degraded"
    UNHEALTHY = "unhealthy"

@dataclass
class CheckResult:
    status: HealthStatus
    message: str
    latency_ms: float = 0.0

@dataclass
class HealthChecker:
    # startup_complete is set to True once your app finishes init
    startup_complete: bool = False
    startup_time: float = field(default_factory=time.time)

    # dependency check functions: name -> callable returning CheckResult
    dependency_checks: Dict[str, Callable[[], CheckResult]] = field(
        default_factory=dict
    )

    def check_liveness(self) -> CheckResult:
        """
        LIVENESS: only check if the process can respond at all.
        Never check external dependencies here.
        """
        # Example: verify in-memory request counter is incrementing
        # (process is alive and handling work)
        return CheckResult(
            status=HealthStatus.HEALTHY,
            message="process alive"
        )

    def check_readiness(self) -> CheckResult:
        """
        READINESS: check if we should receive traffic right now.
        Check critical dependencies, but with tight timeouts.
        """
        if not self.startup_complete:
            return CheckResult(
                status=HealthStatus.UNHEALTHY,
                message="startup not complete"
            )

        results = {}
        for name, check_fn in self.dependency_checks.items():
            t0 = time.monotonic()
            try:
                result = check_fn()
            except Exception as e:
                result = CheckResult(
                    status=HealthStatus.UNHEALTHY,
                    message=str(e)
                )
            result.latency_ms = (time.monotonic() - t0) * 1000
            results[name] = result

        # Any critical dependency unhealthy -> not ready
        failed = [
            name for name, r in results.items()
            if r.status == HealthStatus.UNHEALTHY
        ]
        if failed:
            return CheckResult(
                status=HealthStatus.UNHEALTHY,
                message=f"dependencies unhealthy: {failed}"
            )
        return CheckResult(
            status=HealthStatus.HEALTHY,
            message="all dependencies healthy"
        )

    def check_startup(self) -> CheckResult:
        """
        STARTUP: only returns healthy once initialization is done.
        """
        if self.startup_complete:
            return CheckResult(status=HealthStatus.HEALTHY, message="started")
        elapsed = time.time() - self.startup_time
        return CheckResult(
            status=HealthStatus.UNHEALTHY,
            message=f"starting up ({elapsed:.0f}s elapsed)"
        )


def make_health_handler(checker: HealthChecker):
    class HealthHandler(BaseHTTPRequestHandler):
        def do_GET(self):
            if self.path == "/livez":
                result = checker.check_liveness()
            elif self.path == "/readyz":
                result = checker.check_readiness()
            elif self.path == "/startupz":
                result = checker.check_startup()
            else:
                self.send_response(404)
                self.end_headers()
                return

            status_code = 200 if result.status == HealthStatus.HEALTHY else 503
            body = json.dumps({
                "status": result.status.value,
                "message": result.message,
                "timestamp": time.time()
            }).encode()

            self.send_response(status_code)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(body)

        def log_message(self, *args):
            pass  # suppress default request logging for probe traffic

    return HealthHandler


# Example dependency check: database ping
def make_db_check(db_pool) -> Callable[[], CheckResult]:
    def check() -> CheckResult:
        try:
            conn = db_pool.getconn(timeout=0.3)  # 300ms max
            conn.execute("SELECT 1")
            db_pool.putconn(conn)
            return CheckResult(status=HealthStatus.HEALTHY, message="db ok")
        except Exception as e:
            return CheckResult(status=HealthStatus.UNHEALTHY, message=str(e))
    return check
```

### Kubernetes YAML — Full Probe Configuration

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0        # Never take a pod down before a new one is ready
  template:
    spec:
      containers:
      - name: api
        image: api-service:v1.2.3

        # STARTUP PROBE — protects slow-starting containers
        # Gates liveness + readiness until app reports started
        # Max startup time = failureThreshold × periodSeconds = 12 × 10 = 120s
        startupProbe:
          httpGet:
            path: /startupz
            port: 8080
          periodSeconds: 10
          failureThreshold: 12   # 120 seconds total startup budget
          timeoutSeconds: 5

        # LIVENESS PROBE — never checks external dependencies
        # Only fires after startupProbe succeeds
        livenessProbe:
          httpGet:
            path: /livez
            port: 8080
          periodSeconds: 10
          failureThreshold: 3    # 30s of consecutive failures before restart
          timeoutSeconds: 5
          successThreshold: 1

        # READINESS PROBE — checks dependencies, gates traffic
        # More aggressive: fail fast to remove from LB, recover fast
        readinessProbe:
          httpGet:
            path: /readyz
            port: 8080
          periodSeconds: 5       # Check every 5 seconds
          failureThreshold: 2    # 10s to declare not-ready
          timeoutSeconds: 3
          successThreshold: 2    # Require 2 successes before re-adding to LB

        # Critical: give app time to drain in-flight requests on shutdown
        lifecycle:
          preStop:
            exec:
              command: ["sleep", "5"]
        terminationGracePeriodSeconds: 30
```

### The Graceful Shutdown — Often Missed

Health probes and graceful shutdown are coupled. When a pod is deleted (during a rolling update or scale-down), Kubernetes simultaneously:
1. Sends SIGTERM to the container
2. Removes the pod from the Endpoints object (stops new traffic)

But steps 1 and 2 are parallel — not sequential. New traffic can still arrive to the pod for 1-5 seconds after SIGTERM while iptables/IPVS rules propagate. The `preStop: sleep 5` hook delays SIGTERM delivery, giving routing rules time to propagate before the container starts shutting down. Without this, you get a small but consistent stream of 502 errors during every rolling deployment.

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Kubernetes liveness + readiness + startup probes** | K8s-managed workloads; need automatic restart on failure | Best practice for K8s; requires K8s 1.20+ for startup probes | Google, Stripe, most cloud-native companies |
| **Load balancer health checks only (no liveness)** | Stateless services behind ALB/GLB; don't want auto-restarts | Fast traffic removal; no restart storms; requires external process monitoring | Early-stage apps; serverless/Lambda (no pods to restart) |
| **Eureka/Consul heartbeat + TTL-based eviction** | Service mesh without K8s; polyglot environments | 30-90s detection lag; false evictions under GC pauses | Netflix (Eureka), HashiCorp customers |
| **Passive failure detection only (circuit breakers)** | Request-level resilience; don't want active probe traffic | Per-request precision; no probe overhead; no route-level protection | Netflix Hystrix/Resilience4j as complement to probes |
| **Sidecar-based active health (Envoy outlier detection)** | Istio/Envoy service mesh; automatic ejection on 5xx rates | More sophisticated than binary pass/fail; adds sidecar overhead | Lyft (Envoy creators), Airbnb, Square |
| **External synthetic monitoring (Datadog, Pingdom)** | Validation from outside the cluster; SLA measurement | True external signal; doesn't trigger restarts; latency adds cost | All large enterprises as complement, not replacement |
| **Startup scripts / init containers as health gates** | One-time initialization checks (schema migration, config fetch) | Run-once guarantee; no periodic overhead; cannot detect runtime degradation | DB migration use cases; complement to probes |

### My Opinionated Recommendation

**Use all three Kubernetes probe types.** The debate about "which probe to use" is a false choice — they answer different questions and operate on different timescales. The correct answer in a K8s environment is:

1. **Startup probe** for any service with startup time > 15 seconds (most JVM services, services that run DB migrations on boot).
2. **Liveness probe** that checks only local process health — no dependencies. If you find yourself wanting to check a database in the liveness probe, that is a code smell: your service has not separated its health from its dependencies' health.
3. **Readiness probe** that checks critical dependencies with tight timeouts (300-500ms per dependency). This is where you put the database check.

The single most important operational decision: **never share the same implementation between liveness and readiness**. Use separate endpoints, separate code paths, separate logic.

If you are not on Kubernetes, use your load balancer's health check (ALB target group, Cloudflare monitor, HAProxy) for the readiness function, and a process supervisor (systemd, supervisord) for the liveness function.

## 8. Trade-offs (Be Opinionated)

### Benefits (Specific, With Numbers)

**Faster MTTR.** With a well-configured readiness probe (`periodSeconds: 5, failureThreshold: 2`), a pod is removed from traffic within 10 seconds of becoming unresponsive. Without probes, the average time to detect and manually remediate is 15-30 minutes in a mid-sized engineering org (based on typical on-call SLA data). That is 90x improvement in MTTD.

**Automatic recovery from transient failures.** A liveness probe set to restart after 3 failures at 10-second intervals (30 seconds) handles the "stuck process" failure mode completely automatically. In production environments where 70-80% of incidents are transient (process deadlocks, memory leaks, corrupted state), this eliminates a large fraction of human intervention pages.

**Zero-downtime deployments.** With `maxUnavailable: 0` and readiness gates, rolling deployments only proceed when new pods pass their readiness probes. Without readiness probes, a bad deployment that crashes immediately results in traffic being sent to restarting pods — a deployment becomes a partial outage.

**SLA impact.** Azure Load Balancer documentation cites that with zero-downtime failover (probes + health gates), availability improved from 99.53% to 99.98% during a 30-minute failure window — a 10x reduction in downtime during failure events.

### Costs and Limitations (Honest, With Numbers)

**Probe traffic overhead.** At 50 pods × 2 probe types × 1 request/5s = 20 probe requests/second continuously. If your readiness probe does a database query, that is 20 extra queries/second to your database — forever. At scale (500 pods), that is 200 probe DB queries/second. This has caused production database overload incidents.

**False positives cause restart storms.** A liveness probe configured to check an external service can turn a 30-second dependency outage into a cluster-wide restart event. Every pod fails its liveness probe, every pod gets killed and restarted simultaneously, the cluster is completely unavailable for 60-90 seconds during the restart storm. This is strictly worse than the original 30-second outage.

**Configuration complexity.** You have at minimum 5 parameters per probe type × 3 probe types = 15 probe configuration values per container, plus graceful shutdown configuration. Getting these wrong — especially `failureThreshold` interacting with `periodSeconds` and `terminationGracePeriodSeconds` — causes subtle production failures that are extremely hard to reproduce in staging.

**Startup probe is frequently forgotten.** JVM services commonly restart-loop during initial deployment because engineers configure `initialDelaySeconds: 30` and assume that is sufficient, when actual startup times are 90-120 seconds. This causes deployment failures that only manifest in production (where load on the JVM during startup is higher than in staging).

**State lag in detection.** Even with a 5-second probe interval and failure threshold of 2, you have a 10-second minimum detection window. During those 10 seconds, a fully down pod continues to receive ~10% of traffic (1 of 10 pods), meaning ~10% error rate for users for 10 seconds.

### Core Tension

**Speed vs. Stability.** Faster probes reduce MTTD and therefore MTTR. But faster probes also have higher false-positive rates — especially under load when CPU is constrained and probe response times increase. The optimal probe configuration is a function of your specific service's response time distribution, your dependency SLAs, and your acceptable false-positive restart rate. There is no universally correct value.

### My Recommendation

Adopt the following defaults and only deviate with data:
```
readinessProbe: periodSeconds=5,  failureThreshold=2, timeoutSeconds=3
livenessProbe:  periodSeconds=10, failureThreshold=3, timeoutSeconds=5
startupProbe:   periodSeconds=10, failureThreshold=12 (120s budget)
```

**Never put external dependency checks in liveness probes.** This is a hard rule. The only situation where this rule might be relaxed is if your service is architecturally unable to serve any request without the dependency (e.g., a pure database proxy) — and even then, use a high `failureThreshold` (10+) to avoid restart storms on transient failures.

**Always add `preStop: sleep 5` to every production container.** The cost is 5 seconds of deployment time per pod. The benefit is eliminating 502 errors during every rolling update. This is almost always the right trade.

## 9. Failure Modes — What Goes Wrong

### Failure Mode 1: The Restart Storm

**Trigger:** Liveness probe checks an external dependency (database, Redis, downstream microservice). That dependency experiences a 60-second outage — brief, recoverable, affects all instances equally.

**Symptoms:** All pods fail their liveness probes within the same `failureThreshold × periodSeconds` window. The kubelet restarts all pods simultaneously. The cluster is completely unavailable for the duration of pod startup (30-120 seconds). The dependency recovers, but now all pods are starting fresh — during startup they all try to reconnect to the just-recovered dependency simultaneously, creating a thundering herd.

**Detection:** `kube_pod_container_status_restarts_total` spikes across all pods simultaneously. `kubectl get pods` shows all pods `CrashLoopBackOff` or `ContainerCreating` at the same time.

**Recovery:**
1. Immediate: If pods are stuck in restart loop, manually scale deployment to 0 then back up.
2. Root cause: Remove external dependency check from liveness probe. Move to readiness probe only.
3. Long-term: Add `failureThreshold: 10` as minimum for any liveness probe that remains.

**Real Example:** This is the documented failure mode from the Kubernetes community blog post "Liveness Probes are Dangerous" (srcco.de). Redis Operator experienced this in production — a readiness probe flaw triggered unintended master promotion and data destruction. The self-reinforcing restart storm is described in detail by Heii On-Call's analysis of the CPU throttle + liveness probe feedback loop.

---

### Failure Mode 2: The Slow Startup CrashLoopBackOff

**Trigger:** A JVM-based service (Spring Boot, Play Framework, Scala) is deployed. `initialDelaySeconds: 30` is configured on the liveness probe, but actual startup time is 90 seconds under production load. The liveness probe fires at t=30s, fails because the HTTP server isn't listening yet, and the kubelet kills the container.

**Symptoms:** Pod restarts repeatedly. `kubectl describe pod <name>` shows `Liveness probe failed: connection refused`. RestartCount increments every ~90 seconds. The pod never reaches Running state. The deployment rolls out but immediately rolls back as the new pods never become ready.

**Detection:** `kubectl describe pod` shows liveness failures before the pod has been Running for more than `initialDelaySeconds`. `kubectl logs` shows the application mid-startup when the probe failure occurs.

**Recovery:**
1. Immediate: Increase `initialDelaySeconds` to exceed the measured p99 startup time.
2. Better: Add a `startupProbe` with `failureThreshold: ceil(max_startup_seconds / periodSeconds)`. Remove `initialDelaySeconds` from the liveness probe (not needed with startup probe).
3. Long-term: Profile and reduce startup time. Every second of startup time is a second of delay on every pod restart during incidents.

**Real Example:** This is the most commonly documented failure mode in JVM-based Kubernetes deployments. Spring Boot services with Flyway migrations that run schema diffs on startup are particularly vulnerable — migration time is environment-dependent (staging DB is small, production DB has 5 years of data).

---

### Failure Mode 3: The Premature Ready Signal

**Trigger:** A service passes its readiness probe (HTTP 200 on `/readyz`) before completing internal initialization — e.g., the HTTP server starts and immediately returns 200, but a background thread that loads a 2GB machine learning model into memory has not yet completed. Traffic arrives before the model is ready.

**Symptoms:** New pods receive traffic immediately after becoming Ready. Requests that require the ML model fail with 500 errors. These errors appear only during deployments, for 30-120 seconds per pod rollout. Ops engineers see "it worked in staging" because the staging model is much smaller.

**Detection:** Error rate spike correlated exactly with rolling deployment events. Errors come from newly-started pods only. Error rate drops as background initialization completes.

**Recovery:**
1. Fix: Readiness probe must check actual initialization state, not just "can the HTTP server respond?"
2. Implementation: Add a boolean `initialized = False` flag, set it to `True` only after background initialization completes. Return 503 from `/readyz` until `initialized = True`.
3. Startup probe alternative: Use a startup probe tied to the initialization completion signal.

**Real Example:** Machine learning services deploying model-serving containers. Model weights can be multiple gigabytes; loading from disk + GPU warm-up can take 30-180 seconds. The HTTP port opens within 2 seconds of container start (before model loading). Without careful readiness probe implementation, every pod restart during model updates causes ~2 minutes of errors to real users.

---

### Failure Mode 4: Probe-Induced Database Overload

**Trigger:** A readiness probe makes a lightweight database query (`SELECT 1`) every 5 seconds. With 200 pods and 2 probe types each, the cluster generates 80 DB queries/second from probes alone. A new engineer adds a more thorough probe check (`SELECT COUNT(*) FROM orders`) for "better health validation." This query takes 50ms and runs on the primary replica.

**Symptoms:** Database CPU creeps up from baseline. Slow query logs fill with probe queries. During peak traffic, probe queries compete with application queries for DB connections, causing application query latency to increase. The health check that was supposed to detect database issues is now contributing to database stress.

**Detection:** Database slow query log shows probe-originated queries (identifiable by lack of application-level query parameters). DB connection pool metrics show connection exhaustion correlating with probe frequency.

**Recovery:**
1. Immediate: Revert probe query to `SELECT 1` or a no-op health check table with no data.
2. Architecture: Direct probe DB connections to a read replica, not the primary.
3. Long-term: Add probe query timing to readiness check — if the probe query itself takes > 200ms, log a warning but still return 200 (the database is degraded but available; don't remove traffic).

## 10. When To Use vs. When To Avoid

### Use When:

**Kubernetes-managed workloads with variable startup times.** Any service that takes more than 15 seconds to start should have a startup probe. Any service behind a Kubernetes Service should have a readiness probe. This is not optional at production scale — the question is whether to do it correctly or incorrectly.

**Services with runtime failure modes that benefit from restart.** Services that use in-memory state that can become corrupted (session state, in-process caches, connection pool state), services with known memory leak bugs pending fix, services that can deadlock under specific traffic patterns — all benefit from liveness probes.

**Zero-downtime deployment requirements.** If your team has a SLA against deployment-induced errors, readiness probes are mandatory. They are the mechanism that makes `maxUnavailable: 0` work — without them, Kubernetes cannot tell when a new pod is ready to receive production traffic.

**Multi-dependency services where a single dependency failure should drain traffic, not restart.** Services that depend on databases, caches, or downstream APIs should use readiness probes to respond to dependency failures gracefully — traffic drains to remaining healthy pods instead of every pod getting killed.

### Do NOT Use When:

**Liveness probes should NOT check external dependencies.** This is the cardinal rule. If the dependency is down, you want traffic drained (readiness problem), not containers killed and restarted (liveness action). Restarting the container does not fix a database outage. It makes it worse.

**Do NOT use exec probes for frequently-run checks.** An exec probe creates a new process via `fork()` and `exec()` inside the container's namespace every `periodSeconds`. For a 10-second interval with 200 pods, that is 20 process spawns per second across the cluster. For complex scripts, this adds measurable overhead. Use httpGet or tcpSocket instead, and expose health logic via your application's HTTP server.

**Do NOT use aggressive probe settings without load testing the probe handler.** `periodSeconds: 2, failureThreshold: 1` means the first 2-second timeout kills your container. Under load (when you most need resilience), probe response times increase. Probe-induced restarts under load are self-reinforcing — each restart adds to load, each load spike fails more probes.

**Do NOT use readiness probes in jobs/batch workloads.** Kubernetes Jobs complete and do not receive continuous traffic — readiness probes are meaningless. For CronJobs, focus on startup probes if initialization can fail.

### The Number One Mistake Engineers Make

Using a single `/health` endpoint for both liveness and readiness probes — and having that endpoint check database connectivity. This is the single most common probe misconfiguration in production Kubernetes environments and the direct cause of restart storms. The correct fix is a 10-minute code change: add a `/livez` endpoint that always returns 200 if the HTTP server can respond, and keep the database check in `/readyz` only.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "How would you design health checks for a microservice deployed on Kubernetes?"
- "What's the difference between a liveness probe and a readiness probe? When would each fail?"
- "A service is in CrashLoopBackOff. How do you debug it?"
- "Your team's deployment is causing a spike of 502 errors every time it rolls out. What's wrong?"
- "A database has a 30-second network partition. What happens to your Kubernetes pods?"
- "Design the health check strategy for a service that runs database migrations on startup and has a 90-second JVM warmup time."

### What the Interviewer Is Actually Evaluating

1. **Do you understand the liveness/readiness distinction?** This separates candidates who have operated Kubernetes in production from those who have only read documentation.
2. **Do you know the failure modes?** Specifically: restart storms from external dependency checks in liveness probes. This is the most common probe-related production incident.
3. **Can you reason about timing?** Detection latency = `failureThreshold × periodSeconds`. Can you calculate worst-case detection time from config values?
4. **Do you know the graceful shutdown coupling?** Probes + `preStop: sleep N` + `terminationGracePeriodSeconds` are a system — do you understand how they interact?
5. **Can you reason about scale effects?** 50 pods × 2 probes × `SELECT 1` every 5s = measurable DB load. This separates L5+ thinking.

### Questions YOU Should Ask Before Answering

- "What is the application's p99 startup time in production?"
- "What external dependencies does this service have? Which ones, if unavailable, mean we cannot serve any request?"
- "What is the acceptable MTTD for a completely unresponsive pod?"
- "Is this behind a Kubernetes Service, an AWS ALB, or both? Both have separate health check configurations."
- "Does the service run database migrations on startup?"

### Answer Examples by Level

**Junior (L3-L4):**
> "Liveness probes restart the container when it fails. Readiness probes stop traffic from being sent to the container. For a basic HTTP service I'd add both pointing to `/health`. I'd set `initialDelaySeconds` to be longer than the app startup time to avoid false failures."

This answer demonstrates awareness of the distinction and one key gotcha (`initialDelaySeconds`). It misses the critical rule against external dependency checks in liveness probes and the startup probe concept.

**Senior (L5):**
> "The key constraint is that liveness probes must never check external dependencies. A liveness probe failure causes a container restart — which cannot fix a database outage, only makes it worse. So `/livez` returns 200 if the HTTP stack responds, nothing more. Readiness probe on `/readyz` checks the database connection pool — if the DB is unreachable, we drain traffic from this pod rather than killing it. For a JVM service with 90-second startup, I'd use a startup probe with `failureThreshold: 12, periodSeconds: 10` to give 120 seconds of startup budget before liveness checks begin. I'd also add `preStop: sleep 5` to handle the race between pod deletion and iptables propagation — without it we get 502s on every rolling update."

This answer hits the critical liveness/readiness separation, the startup probe for JVM services, the failure mode, and the graceful shutdown coupling.

**Staff (L6+):**
> "The design question isn't 'which probe do I use' — all three serve different functions at different timescales. The real design questions are: what failure mode does each probe handle, what is the detection latency at each probe configuration, and what are the second-order effects at scale?

> For detection latency: with `periodSeconds: 5, failureThreshold: 2`, readiness detection is 10 seconds plus ~5 seconds for iptables propagation. For an ALB target group at `interval: 15, threshold: 2`, detection is 30 seconds plus ~10 seconds for backend deregistration. If you're behind both (Kubernetes + ALB), you need both probe sets configured — they operate independently.

> The scale concern I'd raise: at 500 pods with readiness probes checking the database every 5 seconds, that's 100 DB queries/second from probes. With `SELECT 1` that's negligible. But if someone adds a real query — even a fast one — that's 100 × p50_query_latency of load added to the primary. Probe queries should be on a read replica or be a no-op ping.

> The architectural recommendation: separate the health endpoint implementation from the application logic with a probe framework that the team owns. Standardize on `/livez`, `/readyz`, `/startupz` across all services so on-call runbooks work uniformly. Expose probe success/failure as Prometheus metrics (`probe_success_total` by probe type) so you can alert on unusual restart rates or readiness flapping before they become user-visible incidents.

> One thing I'd flag as a cross-cutting concern: readiness probe failures cascade. If Service A checks Service B's health in its readiness probe, and Service B becomes unavailable, Service A becomes unready, and everything upstream of Service A starts seeing errors. In a sufficiently connected graph, a single service outage propagates to the entire fleet through readiness cascades. The fix is to not check downstream services in readiness probes — check only local dependencies (own database, own cache). Downstream resilience is a circuit breaker concern, not a probe concern."
