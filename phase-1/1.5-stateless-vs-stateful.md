# 1.5 — Stateless vs Stateful Systems

> 📍 Phase 1 — Foundations of Distributed Systems | Section 1.5

## Prerequisites

Before reading this section, you should be comfortable with:

- **HTTP request/response cycle** — how a browser or client sends a request and receives a response
- **Horizontal scaling basics** — running multiple server instances behind a load balancer (covered in 1.4)
- **Load balancing** — round-robin, least-connections, and how traffic is distributed
- **Cookies and HTTP headers** — how browsers persist small amounts of data across requests
- **Basic database concepts** — reads, writes, and what a primary key is

If you are fuzzy on any of these, revisit Section 1.4 before continuing. The stateless vs. stateful distinction is foundational — misunderstanding it causes architecture mistakes that are extremely expensive to fix later.

## 1. What Is It? (Theory)

### The Core Distinction

**Stateful** means a server remembers information about a client between requests. **Stateless** means a server treats every request as if it has never seen that client before — all the context needed to process the request must arrive with the request itself.

This is not an academic distinction. It is the single most consequential architectural decision you will make when designing any server component. It determines whether you can add more servers when traffic grows, whether a server crash kills active users, and how complex your deployment pipeline becomes.

### What Problem It Solves at Scale

In the early web (1993–2000), web servers were stateful by default. A user logged in to a server. That server remembered the session. If the server crashed, the user was logged out and lost their work. If traffic doubled, you had to buy a bigger server — you could not simply add a second server, because the second server would not know about any of the sessions stored on the first.

**Statelessness solves horizontal scalability.** When no server stores per-client memory, any server in the pool can handle any request. You can add a third server without migrating sessions. You can restart a server without dropping users. You can deploy a new version without a maintenance window.

### Why It Was Invented

Roy Fielding's 2000 dissertation that defined REST (Representational State Transfer) explicitly required statelessness as a constraint: "each request from client to server must contain all of the information necessary to understand the request." Fielding recognized that stateful servers were the primary obstacle to web-scale horizontal growth.

Before REST constraints became mainstream, PHP and Java EE applications stored session objects in server memory as a matter of course. The `$_SESSION` global in PHP and `HttpSession` in Java Servlet containers made stateful design the default path of least resistance.

### Real-World Analogy

Think of statelessness like a **fast-food counter** versus a **personal chef**.

A fast-food counter: you walk up, place your complete order ("large fries, no salt, Diet Coke"), you pay, you get your food. The next customer does not need to wait for yours. Any register can take your order. If one register breaks, the line moves to the next. The counter remembers nothing about you between visits.

A personal chef: they remember you like extra sauce, they know you are allergic to shellfish, they track what you ordered last time. This is a great experience — but there is only one of them, and if they call in sick, the entire operation halts.

Most internet services need to be fast-food counters. The personal chef experience is worth building *on top of* a stateless foundation, using an external state store like Redis.

### Concrete Example With Numbers

Consider a user authentication service:

**Stateful version:**
- Server A stores: `{ session_id: "abc123", user_id: 42, role: "admin", last_active: "2024-01-15T10:00:00Z" }` in RAM
- Server A handles 5,000 concurrent sessions
- Each session object: ~500 bytes → 2.5 MB total RAM for sessions
- Load balancer must route `session_id=abc123` back to Server A every time (sticky sessions)
- If Server A crashes: all 5,000 users lose their sessions

**Stateless version:**
- Server stores nothing. Client sends a **JWT** (JSON Web Token) with every request
- JWT payload: `{ user_id: 42, role: "admin", exp: 1705312800 }` — signed with HMAC-SHA256
- JWT size: ~350 bytes; verified in ~0.1ms (HS256) to ~0.5ms (RS256) on modern hardware
- Any of Servers A, B, C, D can process this request — no routing constraint
- If Server A crashes: Servers B, C, D continue handling traffic; users are unaffected

At 100,000 concurrent users: the stateful approach requires ~50 MB of session RAM spread unevenly and complex sticky-session routing. The stateless approach requires zero server-side RAM for sessions — only CPU for cryptographic verification.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step: Stateless Request Lifecycle (JWT)

1. **Login**: Client sends credentials (`POST /auth/login`, body: `{ username, password }`)
2. **Server validates**: checks password hash against DB (this is the only stateful step — the credential lookup)
3. **Token issued**: server signs a JWT: `header.payload.signature` using a shared secret or private key
4. **Token returned**: server sends `{ access_token: "eyJhbGci...", expires_in: 900 }` (15 minutes)
5. **Subsequent requests**: client includes header `Authorization: Bearer eyJhbGci...`
6. **Server verifies**: any server instance reconstructs the signature and validates it cryptographically — no database lookup, no shared memory required
7. **Request processed**: server extracts `user_id` and `role` from the token payload and proceeds

Step 6 is the key insight: verification is **pure computation**. It requires only the shared secret (or public key), which all server instances already have. There is no network round-trip to a session store.

### Step-by-Step: Stateful Request Lifecycle (Server Sessions)

1. **Login**: Client sends credentials
2. **Server validates**: checks password hash against DB
3. **Session created**: server generates `session_id = "abc123"` and stores session object in memory or in Redis
4. **Cookie set**: server sends `Set-Cookie: session_id=abc123; HttpOnly; Secure`
5. **Subsequent requests**: browser automatically sends `Cookie: session_id=abc123`
6. **Server looks up session**: either reads from RAM (0.05ms) or queries Redis (~0.5–1ms p99)
7. **Request processed**: session object provides user context

Step 6 introduces a **dependency**: the server must reach the session store. If using in-memory sessions (RAM), routing is forced. If using Redis, Redis becomes a critical shared dependency.

### Key Algorithms and Data Structures

**JWT Structure:**
```
Header:   { "alg": "HS256", "typ": "JWT" }
Payload:  { "sub": "42", "role": "admin", "iat": 1705309200, "exp": 1705310100 }
Signature: HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)
```

Final token: three base64url-encoded segments joined by dots. Verification requires one HMAC computation. Cost: negligible CPU (~0.1ms on any modern server).

**Server-Side Session Storage Options:**

| Store | Lookup Latency | Max Sessions | Eviction | Crash Safety |
|---|---|---|---|---|
| In-process RAM | ~0.05ms | ~50K (500 bytes each, 25MB) | LRU | None — lost on crash |
| Redis (single) | ~0.5ms p50, ~1ms p99 | Millions (limited by RAM) | TTL-based | RDB/AOF snapshots |
| Redis Cluster | ~1ms p50, ~2ms p99 | Billions (sharded) | TTL-based | Replication |
| PostgreSQL | ~5ms p50, ~20ms p99 | Billions (disk-backed) | Cron cleanup | ACID transactions |

### Specific Performance Numbers

- **JWT HS256 verification**: ~0.1ms p99 on a 2023 commodity CPU
- **JWT RS256 verification**: ~0.5ms p99 (asymmetric crypto is 5x more expensive)
- **Redis GET latency**: ~0.3ms p50, ~1ms p99 (co-located), ~5ms p99 (cross-region)
- **In-memory session lookup (HashMap)**: ~0.05ms
- **JWT token size (typical)**: 350–600 bytes
- **Session cookie size**: 40–60 bytes (just the ID)
- **JWT bandwidth overhead at 1M req/day**: ~350MB extra per day vs. cookies

### Misconceptions

❌ **Misconception**: "JWT is always stateless."
✅ **Reality**: JWT *verification* is stateless. But production systems almost always add a **denylist** in Redis for token revocation (logout, account compromise). The moment you add a denylist check, you have introduced state. The system is now "mostly stateless with a thin state layer for revocation."

❌ **Misconception**: "Stateless services never touch shared storage."
✅ **Reality**: Stateless means no *per-session* state lives on the server. Every real stateless service still reads/writes a database. The distinction is that the database holds *domain data* (user profiles, orders), not *session data* (who is currently logged in and what they were doing).

❌ **Misconception**: "Sticky sessions solve the stateful scaling problem."
✅ **Reality**: Sticky sessions reduce stateful scaling to a single-server problem. If Server A gets 3x the traffic by chance, it is overloaded while B and C are idle. If Server A crashes, all its sessions are gone. Sticky sessions are a band-aid, not a solution.

❌ **Misconception**: "Stateless systems are always faster."
✅ **Reality**: Stateless systems add per-request overhead: JWT verification (~0.1–0.5ms) or Redis lookup (~0.5–1ms). In-memory session lookups (0.05ms) are faster in isolation. The trade is per-request latency for horizontal scalability. At scale, the reduced per-server load on stateless systems more than compensates for this overhead.

## 3. Real-World Architecture Examples

### Netflix

**Scale**: 247 million subscribers as of 2023, streaming to ~100M concurrent devices at peak.

**The decision**: Netflix migrated from a stateful monolith to stateless microservices between 2008 and 2012. Their original system used in-memory sticky sessions. A single data center failure in 2008 took the entire service offline for several hours. This was the forcing function for their microservices migration.

**What they got wrong first**: Netflix initially extracted services but kept sticky sessions between them. Services were technically separate but had implicit state affinity. An overloaded service instance could not shed load to its sibling without breaking in-flight session state.

**The correction**: Netflix adopted the explicit rule: *"Services should be built in a stateless manner except for the persistence or caching layers, with no sticky sessions."* Their API tier (Zuul gateway and backend services) holds zero per-user session state. User preferences, watch history, and playback position are stored in Cassandra and EVCache (their Memcached layer). Any of thousands of API service instances can handle any request.

**Outcome**: Netflix now deploys hundreds of times per day with zero downtime. Instances are killed and replaced constantly during autoscaling. Chaos Engineering (Chaos Monkey) randomly terminates production instances — this is only safe because instances are stateless.

**Source**: [Netflix Tech Blog — A Brief History of Scaling Netflix](https://blog.bytebytego.com/p/a-brief-history-of-scaling-netflix)

---

### Cloudflare (Durable Objects)

**Scale**: Cloudflare handles ~45 million HTTP requests per second across 300+ data centers.

**The decision**: Cloudflare Workers (their serverless compute) are fully stateless — each Worker invocation is independent. In 2020, Cloudflare launched **Durable Objects**: named, stateful serverless actors that combine compute with a zero-latency SQLite storage layer.

**What they got wrong first**: Before Durable Objects, developers who needed coordination (e.g., a real-time collaborative document, a live chat room, a rate limiter) had to route to a specific data center and maintain their own external state store. This defeated the purpose of globally distributed edge computing.

**The correction**: Durable Objects give each logical unit (one chat room, one user session, one document) a single object with guaranteed single-threaded execution. The key architectural insight: *statelessness at the edge is ideal for pure request/response work; statefulness at the edge is necessary for coordination and real-time applications*.

**Outcome**: The pattern is stateless Workers as the entry point (authentication, routing, validation) + Durable Objects only where coordination is genuinely required. This achieves sub-10ms latency globally for stateless requests while enabling low-latency stateful coordination without a centralized database.

**Source**: [Cloudflare Blog — Introducing Workers Durable Objects](https://blog.cloudflare.com/introducing-workers-durable-objects/)

---

### Amazon (AWS)

**Scale**: AWS serves millions of customers and runs the world's largest cloud infrastructure.

**The decision**: Amazon decomposed their retail monolith into services starting around 2002 (the famous "Bezos API Mandate"). Every team must expose their functionality through APIs. No direct database sharing between teams.

**What they got wrong first**: Early in decomposition, some services passed session context through synchronous service calls — effectively distributing state as function arguments across service boundaries. This created invisible coupling: if Service B needed the user's cart context, Service A had to fetch it and pass it, making A a stateful intermediary.

**The correction**: Each service owns its data store. No service reaches into another service's database. Services communicate through events (SQS, SNS, EventBridge) or APIs, and each service call carries all necessary context in the request (IDs, not objects). This is stateless service-to-service communication.

**Outcome**: AWS Lambda, their serverless offering, mandates statelessness at the runtime level. Lambda functions have no guaranteed instance persistence. AWS explicitly states: "Lambda functions should be stateless so that AWS Lambda can rapidly launch as many copies as needed." This design choice allows Lambda to scale from 0 to 10,000 concurrent executions in seconds.

---

### Uber

**Scale**: 28 million trips per day, operating in 70+ countries as of 2024.

**The decision**: Uber's original PHP monolith had stateful session management tied to specific web servers. As they expanded globally, the latency of routing users to their home session server became untenable. A driver in Mumbai was being routed to a session on a US server.

**What they got wrong first**: Uber initially tried geographic session replication — copying sessions across data centers in real time. Cross-region session replication added 60-150ms to every request due to replication latency. Worse, during network partitions between regions, sessions became inconsistent.

**The correction**: Uber moved to stateless services where every piece of context required to process a request (driver ID, current trip ID, geolocation) is either in the request token or fetched from an appropriate local store. Their authentication uses short-lived tokens with regular refresh. Trip state is stored in a dedicated database, not in session memory.

**Outcome**: Uber can deploy region-by-region without session migration. Adding a new region requires standing up stateless service instances that connect to regional data stores — no session data transfer needed.

### Key Design Questions to Ask Before Starting

Before designing any service component, answer these five questions:

1. **What context does this request need to be processed?** If all context can come from the request payload + database lookup, the service can be stateless.
2. **What is the read/write pattern?** High-read, low-write workloads favor stateless designs backed by caching. High-write, coordination-heavy workloads (multiplayer games, collaborative editing) may genuinely need stateful components.
3. **What is the failure domain?** If a server crash should not affect users, the server cannot hold user-critical state.
4. **What is the expected scale trajectory?** If you expect 10x growth in 18 months, any stateful component that cannot be sharded becomes a bottleneck.
5. **Is there a genuine need for server-pushed events?** WebSockets and Server-Sent Events require a persistent connection — inherently stateful. Plan for this explicitly rather than discovering it after deployment.

### Scale Evolution

#### 1,000 Users

At this scale, almost anything works. A single server with in-memory sessions is fine. The session store fits in 512KB of RAM. Deploy a stateless design anyway — the discipline is worth it, and retrofitting statelessness later is painful.

**Decision**: Use in-memory sessions with a 30-minute TTL. No Redis needed. One server. If you want to practice good habits, use JWTs.

#### 100,000 Users

In-memory sessions on a single server: ~50MB RAM, manageable. But if you need two servers for availability (you should), sticky sessions create uneven load and a single-server failure mode.

**Decision**: This is the crossover point. Move sessions to Redis. Or switch to JWT-based authentication. Running two servers with sticky session routing is operational debt you will pay in every future incident. The cost of adding Redis at this scale (~$30/month on AWS ElastiCache) is trivial compared to the operational complexity of sticky sessions at 10x growth.

#### 1,000,000 Users

At 1M users with average 10% active concurrently: 100,000 concurrent sessions. Redis handles this trivially (100K session objects at 500 bytes each = 50MB, well within a t3.small Redis node).

**Decision**: Stateless JWT auth for your API tier. Redis only for the token denylist (a much smaller dataset — only actively revoked tokens, not all sessions). Add a CDN in front of static assets. The API tier should be horizontally scalable with no routing affinity.

**Watch out**: Your *database* is now the stateful bottleneck. Add read replicas. Consider connection pooling (PgBouncer for PostgreSQL). The statefulness problem has moved down the stack to where it belongs.

#### 100,000,000 Users

At 100M users: authentication cannot be a single-region concern. Token verification must be distributed. Use asymmetric JWT (RS256 or ES256): the auth service holds the private key and issues tokens; all other services hold only the public key and can verify tokens without calling the auth service.

**Decision**: Regional auth service instances each capable of issuing and verifying JWTs. Public keys distributed via JWKS (JSON Web Key Set) endpoint, cached at each service. Token revocation via a distributed denylist (Redis Cluster or a purpose-built system like Okta). Service mesh (e.g., Istio) handles mTLS between services — service-to-service calls are also stateless with cert-based authentication.

**The scaling law**: Stateless components scale linearly with request volume. Stateful components scale with data volume, which grows faster than request volume. Design so that stateful components are as close to the data layer as possible.

## 5. Code / Implementation Perspective

### Python: Stateless JWT Auth Middleware

```python
import time
import hmac
import hashlib
import base64
import json
from functools import wraps
from typing import Optional

# Shared secret — in production, load from environment variable or secrets manager
JWT_SECRET = "your-256-bit-secret"
JWT_EXPIRY_SECONDS = 900  # 15 minutes


def base64url_encode(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode("utf-8")


def base64url_decode(data: str) -> bytes:
    padding = 4 - len(data) % 4
    return base64.urlsafe_b64decode(data + "=" * padding)


def issue_jwt(user_id: int, role: str) -> str:
    """Issue a signed JWT. This is the ONLY stateful step — called at login."""
    now = int(time.time())
    header = base64url_encode(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
    payload = base64url_encode(json.dumps({
        "sub": str(user_id),
        "role": role,
        "iat": now,
        "exp": now + JWT_EXPIRY_SECONDS,
    }).encode())
    signing_input = f"{header}.{payload}"
    signature = base64url_encode(
        hmac.new(JWT_SECRET.encode(), signing_input.encode(), hashlib.sha256).digest()
    )
    return f"{signing_input}.{signature}"


def verify_jwt(token: str) -> Optional[dict]:
    """
    Verify a JWT. Pure computation — no database, no network call.
    Returns decoded payload dict on success, None on failure.
    """
    try:
        parts = token.split(".")
        if len(parts) != 3:
            return None
        header_b64, payload_b64, signature_b64 = parts
        signing_input = f"{header_b64}.{payload_b64}"

        # Recompute expected signature
        expected_sig = base64url_encode(
            hmac.new(JWT_SECRET.encode(), signing_input.encode(), hashlib.sha256).digest()
        )
        # Constant-time comparison to prevent timing attacks
        if not hmac.compare_digest(expected_sig, signature_b64):
            return None  # Signature mismatch — token tampered

        payload = json.loads(base64url_decode(payload_b64))
        if payload.get("exp", 0) < int(time.time()):
            return None  # Token expired

        return payload
    except Exception:
        return None  # Malformed token


def require_auth(f):
    """Decorator for stateless authentication on any endpoint."""
    @wraps(f)
    def wrapper(request, *args, **kwargs):
        auth_header = request.headers.get("Authorization", "")
        if not auth_header.startswith("Bearer "):
            return {"error": "Unauthorized"}, 401
        token = auth_header[7:]
        payload = verify_jwt(token)
        if payload is None:
            return {"error": "Invalid or expired token"}, 401
        # Inject user context into request — no session store consulted
        request.user_id = int(payload["sub"])
        request.user_role = payload["role"]
        return f(request, *args, **kwargs)
    return wrapper


# Usage — this handler has ZERO shared state
@require_auth
def get_user_profile(request):
    # request.user_id is available from the verified JWT
    # The database call here is domain data, not session state
    user = db.get_user(request.user_id)
    return {"user": user}, 200
```

### Language-Agnostic Algorithm: Stateless Request Verification

```
STATELESS JWT VERIFICATION ALGORITHM

Input: HTTP request with Authorization header
Output: Authenticated user context OR rejection

1. Extract token from Authorization header
   - Expected format: "Bearer <token>"
   - If missing or malformed: return 401

2. Split token on "." delimiter
   - Expect exactly 3 parts: [header, payload, signature]
   - If wrong number of parts: return 401

3. Recompute expected signature
   - signing_input = header + "." + payload
   - expected = HMAC-SHA256(signing_input, shared_secret)
   - Encode expected as base64url

4. Compare signatures using constant-time comparison
   - NEVER use == for string comparison (timing attack vulnerability)
   - Use hmac.compare_digest() or equivalent
   - If mismatch: return 401

5. Decode and validate payload
   - base64url decode the payload segment
   - Parse as JSON
   - Check "exp" field > current Unix timestamp
   - Check "iat" field is not in the future (clock skew tolerance: ±30s)
   - If expired: return 401

6. (Optional) Check denylist in Redis
   - Key: "denylist:" + jti (JWT ID claim)
   - If key exists: return 401 (token was explicitly revoked)
   - This step adds ~0.5–1ms but enables revocation

7. Return decoded payload as user context
   - Downstream handlers receive user_id, role, etc.
   - No further auth lookups needed for the request lifetime
```

```yaml
  sessionAffinity: None
```

**Note on `sessionAffinity: None`**: This is the explicit rejection of sticky sessions in Kubernetes. With `None`, the kube-proxy distributes requests round-robin or by random selection across all healthy pods. This is only safe because the service is stateless.

## 7. Alternatives & Comparisons

### Comparison Table

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **Pure stateless (JWT, no denylist)** | Public APIs, mobile clients, short-lived tokens (< 5 min TTL) | Cannot revoke tokens before expiry | Stripe's webhook verification, many public REST APIs |
| **Stateless + Redis denylist** | Web apps needing logout, admin revocation | Adds 0.5–1ms per request; Redis becomes a dependency | Netflix, Uber, most production web apps |
| **Server-side sessions (Redis)** | First-party web apps, server-rendered apps, when JWT is overkill | Redis required; slightly higher latency vs JWT-only | Django default, Ruby on Rails, traditional PHP apps |
| **Sticky sessions (in-memory)** | Legacy migration, single-server, WebSocket servers without external broker | Cannot scale horizontally; single server failure = session loss | Legacy enterprise apps, some gaming backends |
| **Stateful actors (Erlang/Akka)** | Real-time systems, game servers, collaborative editing, financial order books | Complex mental model; careful partition management needed | WhatsApp (Erlang), Riot Games (Akka), trading systems |
| **Database-backed sessions** | Sessions needing persistence across restarts, audit requirements | High latency (5–20ms per request); database load | Government portals, banking apps with audit requirements |

### Narrative Analysis

**The 2024 industry consensus** has swung toward a hybrid model for most web applications: stateless API services backed by a thin, purpose-built state layer. Pure in-memory stateful sessions are largely considered legacy practice for any new system with more than one server.

The specific pattern that has become canonical:

1. **Short-lived access JWTs** (15 minutes): verified cryptographically, no Redis lookup on the hot path
2. **Longer-lived refresh tokens** (7–30 days) stored in an `HttpOnly` cookie: these are opaque random IDs stored in Redis with a TTL
3. **Minimal Redis denylist**: only stores *actively revoked* access tokens (far fewer than all active sessions)

This pattern achieves: stateless verification on the hot path (fast), revocability when needed (secure), and minimal Redis surface area (resilient).

**My opinionated recommendation**: Use short-lived JWTs with a Redis-backed refresh token flow for any new web service. Do not use server-side in-memory sessions for any service that will ever have more than one instance. Do not use sticky sessions as a solution — use them at most as a crutch during a migration, with a clear deadline to remove them.

The main contested area is **JWT vs. opaque tokens with session store for first-party web apps**. Some engineers (Cal Newport, the author of "Real-World Cryptography") argue that for first-party web apps, traditional server-side sessions in Redis are simpler, more revocable, and have better security properties than JWTs. This is a legitimate position. The difference in operational complexity between the two is small at < 100K users. Choose JWTs if you need stateless API consumption (mobile clients, third-party integrations). Choose Redis sessions if your app is purely first-party server-rendered and you want the simplicity.

## 8. Trade-offs (Be Opinionated)

### Benefits of Stateless Design

- **True horizontal scalability**: add N more servers without any coordination — proved at Netflix (thousands of API instances), AWS Lambda (10,000+ concurrent executions spun up in seconds)
- **Fault isolation**: a server crash affects zero users; requests route to other instances transparently
- **Deployment velocity**: rolling deployments, blue/green deployments, and canary releases are all trivial when servers hold no user state
- **Simplified operations**: stateless instances are identical and interchangeable — debugging one debugs all
- **Auto-scaling precision**: CPU or RPS-based auto-scaling works correctly; no "warm" vs "cold" session distinction
- **No session migration**: adding a new region or data center requires zero session data transfer

### Costs and Limitations of Stateless Design

- **Per-request overhead**: JWT verification adds ~0.1–0.5ms; Redis denylist check adds ~0.5–1ms — this is real, measurable latency added to every authenticated request
- **Token revocation complexity**: pure stateless JWTs cannot be immediately revoked; solving this requires adding state (denylist), partially defeating the stateless benefit
- **Token size overhead**: JWTs are 350–600 bytes vs. 40 bytes for a session cookie; at 1M requests/day, this is ~300MB of extra bandwidth per day (~9GB/month)
- **Secret/key management**: shared JWT secrets must be distributed to all service instances; rotation requires coordinated deployment
- **Replay attacks**: a stolen JWT is valid until expiry; short TTLs (15 min) mitigate but do not eliminate this window
- **Debugging complexity**: distributed stateless traces are harder to reconstruct than a single session log

### The Core Tension

**Security and revocability vs. scalability and operational simplicity.**

Stateless systems scale effortlessly but cannot instantly revoke access. Stateful systems can instantly revoke sessions but require coordination infrastructure that limits scale and adds operational complexity. Every production system sits somewhere on this spectrum — there is no architecture that maximizes both simultaneously.

The secondary tension is **latency vs. scale**: in-memory stateful lookup (0.05ms) is faster than JWT verification + Redis denylist check (0.6–1.5ms). But in-memory lookup cannot scale horizontally. At scale, the reduced per-server load from horizontal scaling more than compensates for the per-request overhead.

### My Recommendation

**Design every service tier as stateless until you have an explicit, unavoidable reason for state.** Push state as close to the storage layer as possible. When you must introduce state (WebSockets, collaborative editing, game servers), use a stateful actor framework (Akka, Erlang/OTP, Cloudflare Durable Objects) rather than improvising statefulness into a service that was designed to be stateless.

For authentication specifically: **use short-lived JWTs (15-minute TTL) with opaque refresh tokens stored in Redis for all new systems**. This is the pattern that Netflix, Uber, and most major SaaS companies have converged on. It gives you 99% of the stateless scalability benefit while retaining the ability to revoke sessions when security requires it.

## 9. Failure Modes — What Goes Wrong

### Session Affinity Breaks Under Load

**Trigger**: Traffic spike causes the load balancer to spin up new instances. Existing requests with sticky session routing cannot be routed to the new instances (they have no sessions). Uneven load: old instances are overloaded, new instances are idle.

**Symptoms**: Response time p99 climbs from 200ms to 2000ms+ on old instances. New instances report near-zero CPU. Users on old instances experience timeouts and errors. Auto-scaling adds instances but does not reduce load.

**Detection**: Monitor per-instance request rate and CPU separately from aggregate. Alert when per-instance request rate variance exceeds 30% across instances in a cluster. CloudWatch, Datadog, and Prometheus all expose per-instance metrics.

**Recovery**: Force a rolling restart of old instances (graceful shutdown, drain connections, restart). This distributes sessions across all instances IF using an external session store. If using in-memory sessions, this terminates all active sessions — a user-visible outage.

**Real Example**: GitHub experienced this pattern during their 2012 availability incident. Their original Rails app used in-memory sessions. Load spikes caused uneven distribution across their web dynos. The incident prompted their move toward stateless API design for subsequent platform services.

---

### Redis Session Store Becomes a Single Point of Failure

**Trigger**: Redis instance fails (hardware failure, OOM, network partition), becomes unreachable, or is overwhelmed during a traffic spike. If sessions are stored in a single Redis instance, all authenticated requests fail simultaneously.

**Symptoms**: HTTP 500 or 401 errors for all authenticated endpoints. Login succeeds (credential check hits DB) but session cannot be written to Redis. Service appears to accept logins but immediately logs users back out.

**Detection**: Redis availability alert at < 99.9% uptime. Redis latency alert at > 10ms p99 (normal: < 1ms). Connection pool exhaustion alerts from application metrics.

**Recovery**: If using Redis Sentinel or ElastiCache with Multi-AZ, failover is automatic (30–120 seconds). During failover, authenticated requests fail. Mitigation: implement a grace period where requests that cannot reach Redis fall back to a short-lived in-memory cache (accept the slight consistency risk) or return a 503 with `Retry-After` header. Long-term: Redis Cluster (3+ shards, 1 replica each) eliminates single-point-of-failure.

**Real Example**: Stack Overflow experienced a Redis availability incident in 2019. Their session store Redis became briefly unavailable, resulting in a mass logout of users. The incident drove investment in Redis HA configuration. Their engineering blog documented the postmortem.

---

### JWT Token Leakage and Unable to Revoke

**Trigger**: A JWT access token is exfiltrated from a client (XSS attack, token logging in error reporting, insecure storage in localStorage). The attacker now holds a valid token that cannot be invalidated without a denylist.

**Symptoms**: Unauthorized API activity from unusual geographic locations or IP ranges. Detected by anomaly detection on user behavior, not by authentication failures (the token is technically valid).

**Detection**: Monitor for authentication from multiple concurrent geographic locations for the same `user_id`. Alert when `user_id` authenticates from > 2 distinct country codes within a 60-minute window. This requires logging the source IP with every JWT-authenticated request and correlating at the user level.

**Recovery**: Without a denylist: only option is to change the JWT signing secret, which immediately invalidates ALL tokens for ALL users — a forced global logout. With a denylist: add the token's `jti` (JWT ID) to Redis denylist with TTL equal to the token's remaining validity window. Affected user re-authenticates with fresh credentials.

**Real Example**: This class of vulnerability was demonstrated in the 2022 Auth0 security disclosure where certain JWT implementations did not validate the `alg` field, allowing algorithm confusion attacks. The recommended fix required adding the token ID to a revocation list for all potentially compromised tokens. This is why OWASP explicitly recommends including a `jti` claim in every JWT issued in production.

---

### Stateful Service Prevents Zero-Downtime Deployment

**Trigger**: You attempt a rolling deployment of a stateful service (one that holds in-flight request state or user session state in memory). The new version is incompatible with the state format stored by the old version. Or: new instances come up without the old instances' in-memory state.

**Symptoms**: Users mid-flow (mid-checkout, mid-upload) experience errors when their request lands on a newly deployed instance that has no record of their prior interactions. Error rate spikes for 5–15 minutes during each deployment.

**Detection**: Monitor error rate during deployments. Compare error rate in the 15 minutes before and after a deployment. Alert if error rate increases > 2x during the deployment window.

**Recovery**: Immediate: extend the drain window on old instances (let in-flight requests complete before terminating). Long-term: redesign the service to be stateless by moving in-flight state to Redis or a database with TTL. For truly stateful workloads (file uploads), use resumable upload protocols (TUS protocol, AWS multipart upload) that externalize state to object storage.

**Real Example**: Discord's engineering team documented that their early voice chat infrastructure held connection state in-process. Deployments required careful orchestration to avoid dropping active voice calls. Their solution was to move session state to an external store and redesign the voice gateway as a stateless router that reconnects to a persistent state backend, enabling zero-downtime deployments.

## 10. When To Use vs. When To Avoid

### Use Stateless Design When:

✅ **You expect to scale beyond a single server** — any application with projected growth beyond what one server can handle should be stateless from day one. Retrofitting statelessness is expensive.

✅ **You need zero-downtime deployments** — rolling deployments, blue/green, canary: all of these are safe only when servers hold no user state. CI/CD pipelines that deploy multiple times per day require stateless services.

✅ **You are building microservices or APIs consumed by mobile clients** — each service instance must be interchangeable. Mobile clients frequently switch networks (WiFi to LTE) and reconnect; they must not be pinned to a specific server instance.

✅ **You are building serverless functions (AWS Lambda, GCP Cloud Functions, Cloudflare Workers)** — the runtime mandates statelessness. There is no choice. Design with this constraint.

✅ **You need fault tolerance without session loss** — if server crashes should be transparent to users, the server cannot hold user-critical state.

✅ **You are building a multi-region or globally distributed service** — state replication across regions is expensive and complex. Stateless services can be deployed globally with no coordination overhead.

### Do NOT Use Stateless Design When:

❌ **The problem fundamentally requires server-side coordination** — real-time collaborative editing (Google Docs), multiplayer game state, live auction bidding, financial order books. These require a single authoritative source of truth that multiple clients interact with simultaneously. Forcing these into stateless design creates race conditions and consistency violations.

❌ **You need sub-millisecond request processing and cannot afford JWT verification overhead** — high-frequency trading systems, ultra-low-latency gaming backends, or any system where 0.5ms matters. In these contexts, in-memory session lookup (0.05ms) may be worth the architectural complexity.

❌ **Your session objects are large (> 10KB) and needed on every request** — passing large context objects in JWT is impractical (large tokens are slow to verify and waste bandwidth). In this case, an external session store with a small opaque ID in a cookie is more appropriate.

❌ **You need immediate revocation of access without any delay** — if your security requirements mandate that a compromised account is locked out within milliseconds (not within the JWT TTL window), you need a stateful session system that can be instantly invalidated.

### The #1 Mistake Engineers Make

⚠️ **Using sticky sessions as a long-term solution instead of eliminating server-side state.**

Sticky sessions are an operational trap. They masquerade as a solution to the stateful scaling problem while actually locking you into single-server failure domains and preventing true horizontal scaling. Engineers discover the need for sticky sessions when they first scale to two servers and find sessions breaking. They add sticky session routing to the load balancer and consider the problem solved. The problem is not solved — it is deferred. Every subsequent scaling event, deployment, and failure scenario is complicated by this decision. The correct response to needing sticky sessions is to eliminate the in-memory state that required them, not to add routing rules that work around it.

## 11. Interview Perspective

### How This Topic Shows Up in Interviews

Interviewers rarely ask "explain stateless vs stateful" directly at senior and above. The topic appears embedded in:

- *"Design a URL shortener"* — when you add auth, how do you handle sessions?
- *"Design a ride-sharing app"* — driver location is stateful. How do you handle it at scale?
- *"How would you scale your auth service from 1M to 100M users?"* — forces you to address statefulness
- *"Walk me through your last incident involving scaling or availability"* — probes for understanding of stateful failure modes
- *"Design a real-time collaborative document editor"* — requires explicit stateful coordination design
- *"How does your service handle zero-downtime deployments?"* — tests understanding of why statelessness is necessary

### What the Interviewer Is Actually Evaluating

- Do you understand *why* stateless is default in modern systems, not just *what* it is?
- Can you identify the trade-offs rather than advocating dogmatically for one approach?
- Do you know the failure modes of stateful systems? Can you design around them?
- Do you understand that "stateless service" does not mean "no state" — it means state lives elsewhere?
- Can you articulate the specific technology choices (JWT, Redis, etc.) and their trade-offs?

### Questions YOU Should Ask the Interviewer

1. *"What is the expected concurrency — number of simultaneous active users?"* — helps size the state layer
2. *"Are there hard latency requirements for authentication, e.g., p99 < 50ms?"* — determines whether Redis denylist overhead is acceptable
3. *"Is there a requirement for immediate session revocation (e.g., banking compliance)?"* — changes the auth architecture significantly
4. *"Is this a first-party web app, mobile client, or third-party API?"* — different clients have different token storage constraints
5. *"What is the deployment frequency target?"* — high-frequency deployments require stateless services

### Three Answer Tiers

**Junior (L3–L4):**
> "Stateless services don't keep session data on the server. Instead, you use JWTs where the client sends a token with each request and the server verifies it cryptographically. This lets any server handle any request, so you can scale horizontally. The main downside is you can't immediately revoke a token."

This answer is correct but lacks depth. It knows the pattern without understanding why or when to choose differently.

**Senior (L5):**
> "I default to stateless services with short-lived JWTs — 15-minute access tokens — paired with opaque refresh tokens stored in Redis. The JWT verification on the hot path costs ~0.1ms and requires no network call. The refresh token is an opaque ID that hits Redis (~0.5ms) only every 15 minutes, not per-request. For revocation, I maintain a denylist in Redis keyed by the JWT's `jti` claim — I only insert entries when a token is explicitly revoked, so the denylist stays small. This gives me stateless performance 99% of the time with the ability to revoke in milliseconds when needed. Kubernetes Deployments — not StatefulSets — for the API tier, with `sessionAffinity: None` on the Service to ensure round-robin distribution."

This answer demonstrates operational thinking, specific technology choices, and awareness of the trade-off between purity and practicality.

**Staff (L6+):**
> "The stateless/stateful question is really a question of *where* state lives and *who owns it*. For auth, I use the hybrid JWT + Redis denylist pattern, but the more interesting design question is the service-to-service layer. Stateless services communicate through APIs that include all necessary context in the request. The failure mode I care about most is not the session store going down — it's the subtle statefulness that creeps into service boundaries when Service A starts passing session context to Service B. That creates invisible coupling that manifests as cascading failures during deployments. I enforce stateless service-to-service communication through API contracts reviewed in design review, not just as a convention.
>
> At 100M+ users, the auth pattern changes: asymmetric JWT (RS256 or ES256), with public keys served via a JWKS endpoint cached at each service. This removes the dependency on the auth service for token verification — any service can verify independently. The auth service is only in the hot path at login and refresh. Token revocation at this scale requires a distributed denylist — either Redis Cluster or a dedicated revocation service with sub-second propagation to all edge nodes. Cloudflare's model with Durable Objects is worth studying here: they moved revocation state to the edge, so revocation propagates globally in < 100ms instead of waiting for CDN cache expiry."

This answer demonstrates systems thinking at the architecture level, failure mode reasoning, evolution across scales, and awareness of industry patterns beyond textbook definitions.

### Key Facts to Have Memorized

- **JWT HS256 verification**: ~0.1ms p99; RS256: ~0.5ms p99
- **Redis GET latency**: ~0.3ms p50, ~1ms p99 (same-region)
- **Typical JWT size**: 350–600 bytes; session cookie: 40–60 bytes
- **Kubernetes**: use `Deployment` + `sessionAffinity: None` for stateless; `StatefulSet` for stateful (databases, Kafka, Elasticsearch)
- **Short-lived access token TTL**: 15 minutes is the industry standard (balance between security and UX)
- **JWT claims to always include**: `sub` (subject), `iat` (issued at), `exp` (expiry), `jti` (JWT ID for revocation)
- **The Netflix rule**: "Services should be stateless except for the persistence or caching layers, with no sticky sessions"
- **Lambda scaling**: 0 to 10,000 concurrent executions in seconds — only possible because Lambda is stateless
- **Token revocation latency**: without denylist, effectively zero revocability; with Redis denylist, < 1ms revocation detection per request
