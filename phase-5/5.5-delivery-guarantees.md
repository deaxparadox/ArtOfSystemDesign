# 5.5 — At-Least-Once vs Exactly-Once Delivery

> 📍 Phase 5 — Messaging & Async Processing | Section 5.5

---

**Prerequisites**

Before reading this section you should be comfortable with:
- Basic producer/consumer messaging patterns (Section 5.1)
- How Kafka, RabbitMQ, and SQS work at a high level (Section 5.4)
- What a distributed transaction is — writes to multiple systems that must all succeed or all fail
- Network partitions and the CAP theorem (why distributed systems fail in unexpected ways)
- What "idempotent" means: an operation that produces the same result whether applied once or many times

---

## 1. What Is It? (Theory)

### Plain English

Every messaging system must answer one question: **if a message might be lost or delayed, what do you guarantee about how many times a consumer sees it?**

There are three answers:

| Guarantee | Meaning | Risk |
|---|---|---|
| **At-most-once** | Deliver the message zero or one time | Message loss — the consumer may never see it |
| **At-least-once** | Deliver the message one or more times | Duplicates — the consumer may see it many times |
| **Exactly-once** | Deliver the message exactly one time | Coordination cost — requires two-phase commit or equivalent |

This section focuses on the practical battle between **at-least-once** and **exactly-once**, because at-most-once is rarely acceptable for production systems that care about correctness.

### The Problem at Scale

Imagine you process 10 million payment transactions per day. A single reboot of a consumer node, a brief network partition, or a GC pause causes your broker to redeliver a batch of 500 messages. Without deduplication, 500 payments get charged twice. Your on-call engineer gets paged at 3 AM. This is not hypothetical — it has happened at every major payment company.

At-least-once delivery is what almost every production messaging system actually provides. Exactly-once delivery is what engineers wish they had.

### Why This Was Invented

Before distributed messaging (pre-2006), systems used databases as their integration layer: write to DB, another service reads from DB. This gave you transactional guarantees but created tight coupling and throughput limits.

When LinkedIn built Kafka in 2010 to handle their activity feed (which hit 1 billion events per day within two years), they needed async decoupling with durability. The trade-off was explicit: Kafka 0.x only guaranteed at-least-once. Engineers had to design idempotent consumers themselves.

Exactly-once semantics in Kafka (KIP-98) did not ship until **Kafka 0.11.0 in 2017** — seven years after Kafka was created. This tells you how hard the problem is.

### What Breaks Without It

Without careful delivery guarantee design:

1. **Financial double-charges** — payment processor bills a card twice when a consumer crashes mid-acknowledgment
2. **Inventory corruption** — stock count decrements twice for a single order
3. **Email spam** — a welcome email fires 5 times because a notification service crashed after sending but before acking
4. **Metric inflation** — analytics event pipeline overcounts user actions by 8-12% (typical observed duplicate rate in at-least-once systems without deduplication)

### Real-World Analogy

Think of postal mail. "At-least-once" delivery is like sending a certified letter: if there is no delivery confirmation after 3 days, the post office sends it again. You might get two copies. "Exactly-once" is like a hand-delivery with signature: the courier confirms you signed before marking it delivered, and will never redeliver.

The certified letter (at-least-once) is cheap and scalable — the post office processes millions per day. The hand-delivery (exactly-once) requires a courier to wait, a signature infrastructure, and a ledger of who signed what. It costs more and takes longer.

### Concrete Numbers

A typical e-commerce platform processing 50,000 orders/day with at-least-once delivery and **no deduplication** will see approximately:
- 0.5-2% duplicate rate during normal operation
- 5-10% duplicate rate during rolling deploys or consumer restarts
- That is 250-1,000 potentially double-processed orders per day

With idempotent consumers (the industry-standard mitigation), the duplicate rate becomes 0 regardless of how many times a message is delivered.

## 2. How It Actually Works (Deep Mechanics)

### At-Least-Once: Step-by-Step

At-least-once delivery is the default behavior when a consumer **acknowledges after processing**:

```
1. Producer sends message M to broker
2. Broker writes M to durable storage (disk/replicas)
3. Broker delivers M to consumer
4. Consumer processes M
5. Consumer sends ACK to broker
6. Broker marks M as delivered

--- FAILURE SCENARIOS ---

Scenario A: Consumer crashes at step 4 (before ACK)
  -> Broker never receives ACK
  -> Broker redelivers M to a new/recovered consumer
  -> M is processed TWICE

Scenario B: Network drops ACK packet (step 5)
  -> Broker never receives ACK (even though processing succeeded)
  -> Broker redelivers M
  -> M is processed TWICE
```

```
AT-LEAST-ONCE FLOW

Producer          Broker (Kafka/SQS)         Consumer
   |                    |                       |
   |---send(M)--------->|                       |
   |<--ack(offset=42)---|                       |
   |                    |---deliver(M)--------->|
   |                    |                       |---process(M)
   |                    |                       |   [CRASH]
   |                    |                       X
   |                    |   (timeout: 30s)      |
   |                    |---redeliver(M)------->|  (new consumer)
   |                    |                       |---process(M) AGAIN
   |                    |<--ACK-----------------|
   |                    |                       |
```

### Exactly-Once: Step-by-Step (Kafka Implementation)

Kafka achieves exactly-once through two mechanisms: **idempotent producers** and **transactions**.

**Idempotent Producers** (producer-side deduplication):

```
1. Broker assigns each producer a unique PID (Producer ID)
2. Producer increments a sequence number (SN) per partition
3. Every message includes (PID, SN, partition)
4. Broker maintains the last 5 sequence numbers per (PID, partition)
5. If broker receives a duplicate SN -> silently discard
6. If broker receives SN out of order -> return OutOfOrderSequenceException
```

This handles the case where a producer retries due to a network timeout. The broker sees the same (PID, SN) and drops the duplicate. **This does NOT help with consumer-side duplicates.**

**Transactions** (read-process-write atomicity):

```
1. Producer calls initTransactions() -> gets TID (Transaction ID) + epoch
2. Producer calls beginTransaction()
3. Producer reads from input topic (or processes business logic)
4. Producer sends results to output topic(s) -- not yet visible to consumers
5. Producer calls sendOffsetsToTransaction() -- commits input offsets atomically
6. Producer calls commitTransaction() -- makes output messages visible atomically

--- If producer crashes between steps 3-5 ---
  -> Transaction Coordinator marks transaction as aborted
  -> Output messages are never made visible
  -> Input offsets are NOT advanced
  -> New producer instance resumes from last committed input offset
```

```
EXACTLY-ONCE (KAFKA TRANSACTIONS) FLOW

Producer          Transaction Coordinator      Output Topic      Consumer
   |                       |                       |                |
   |--initTransactions()--->|                       |               |
   |<--PID+epoch-----------|                       |               |
   |--beginTransaction()-->|                       |               |
   |                       |--register partitions->|               |
   |--produce(msg)-------->|                       |               |
   |                       |           [msg stored, not visible]   |
   |--commitTransaction()-->|                       |              |
   |                       |--mark COMMITTED------->|              |
   |                       |                    [msg now visible]  |
   |                       |                       |--deliver(msg)->|
   |                       |                       |               |--process
   |                       |                       |               |--ACK
```

### Key Algorithms and Data Structures

**Idempotent Producer State (per broker partition):**
```
Map<(PID, Partition) -> CircularBuffer(last_5_sequence_numbers)>
```

**Transaction Log (special Kafka topic `__transaction_state`):**
```
{
  transaction_id: "payment-processor-1",
  producer_id: 42,
  producer_epoch: 3,
  transaction_state: "Ongoing | PrepareCommit | PrepareAbort | CompleteCommit",
  partitions: [("orders", 0), ("payments", 2)],
  txn_timeout_ms: 60000
}
```

**SQS FIFO Deduplication:**
SQS uses a 5-minute deduplication window based on SHA-256 hash of message body (content-based) or an explicit `MessageDeduplicationId`. If the same ID arrives within 5 minutes, SQS silently drops the duplicate — no storage of consumer-side results.

### Real Numbers

| Metric | At-Least-Once (Kafka) | Exactly-Once (Kafka Transactions) | Ratio |
|---|---|---|---|
| Producer throughput | ~500K msg/s per broker | ~400K msg/s per broker | ~20% reduction |
| End-to-end latency (p50) | 5-10ms | 15-25ms | ~2-3x |
| End-to-end latency (p99) | 25-50ms | 80-150ms | ~3x |
| Transaction overhead per batch | 0ms | 2-5ms coordination RPC | — |
| SQS Standard throughput | Unlimited (sharded) | N/A | — |
| SQS FIFO throughput | 3,000 msg/s (batched) | 300 API calls/s (unbatched) | 10x with batching |

### Misconceptions

**Misconception: Exactly-once in Kafka means the message travels exactly once.**
**Reality:** The message may be sent multiple times (retries). "Exactly-once" means the consumer-visible effect happens exactly once. The broker deduplicates internally. The wire can still carry duplicate bytes.

**Misconception: Exactly-once eliminates the need for idempotent consumers.**
**Reality:** Kafka's exactly-once guarantees only apply **within the Kafka pipeline** (Kafka-to-Kafka). The moment your consumer calls an external API (database, payment gateway, HTTP endpoint), you are back to at-least-once. You must still design idempotent external writes.

**Misconception: SQS FIFO provides exactly-once delivery to consumers.**
**Reality:** SQS FIFO deduplicates on the **producer side** (within a 5-minute window). A consumer can still process a message, fail before deleting it, and reprocess. FIFO queues are at-least-once from the consumer's perspective.

**Misconception: Exactly-once is always more correct.**
**Reality:** If your operation is idempotent (e.g., "set user.verified = true"), at-least-once is equally correct and significantly cheaper. Exactly-once adds cost and complexity that buys you nothing for idempotent operations.

## 3. Real-World Architecture Examples

### LinkedIn — Kafka at 7 Trillion Messages/Day

LinkedIn invented Kafka in 2010 to replace a polling-based data pipeline that could not scale beyond their 300M member activity feed. By 2023, LinkedIn ran 100+ Kafka clusters with 4,000+ brokers handling 7 trillion messages per day across 100,000 topics.

**The delivery guarantee decision:** LinkedIn chose **at-least-once** for the vast majority of pipelines. Their consumer applications are designed to be idempotent — they use the Kafka offset as a natural deduplication key for many use cases, and for others they maintain a Redis set of recently-seen message IDs with a TTL of 24 hours.

**What triggered the scale:** At ~1 billion messages/day, they hit the limit of a MySQL-backed pub-sub system. The new system needed to be horizontally partitioned, which meant acknowledging that transactions across partitions were impractical. The explicit trade-off was: give up exactly-once in exchange for unlimited horizontal scalability.

**What they got wrong first:** Early LinkedIn Kafka consumers did not handle rebalance events correctly. When a consumer group rebalanced (a broker failed, a consumer was added), the new consumer re-read from the last committed offset. If consumers committed offsets too infrequently, they reprocessed up to tens of thousands of messages. The fix was to commit offsets after every batch and build idempotent consumers that could safely ignore already-processed messages.

**Cite:** "How LinkedIn customizes Apache Kafka for 7 trillion messages per day" (LinkedIn Engineering Blog, 2023)

---

### Stripe — Idempotency Keys as Exactly-Once Simulation

Stripe processes billions of API calls per year, including payment charges that must never execute twice. Stripe's infrastructure is built entirely around HTTP APIs, not message queues — yet they needed exactly-once semantics.

**The delivery guarantee decision:** Stripe uses **at-least-once HTTP delivery** combined with **application-level idempotency keys**. Every mutating API call (charge, refund, subscription creation) accepts an `Idempotency-Key` header. The server stores the result of each unique key in a database table. On retry with the same key, it returns the stored result without re-executing the operation.

```
-- Stripe idempotency table (simplified)
CREATE TABLE idempotency_keys (
    key            TEXT PRIMARY KEY,
    user_id        BIGINT NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL,
    locked_at      TIMESTAMPTZ,           -- optimistic locking
    recovery_point TEXT NOT NULL,         -- state machine checkpoint
    request_params JSONB NOT NULL,
    response_code  INTEGER,
    response_body  JSONB
);
```

**What triggered the decision:** In 2012, Stripe observed that network retries from client SDKs were causing duplicate charges at a rate of ~0.05% of all payment attempts. While small as a percentage, at Stripe's volume that represented millions of dollars in duplicate charges per year.

**What they got wrong first:** The initial implementation used optimistic locking with a `SELECT FOR UPDATE`. Under high concurrency (a client hammering retries during a network outage), this caused deadlocks that compounded the outage. The fix was to add a mutex-style lock using Redis with a short TTL as the first line of defense, falling back to the database for durability.

**Cite:** "Designing robust and predictable APIs with idempotency" (Stripe Engineering Blog)

### Uber — Real-Time Push and the Exactly-Once Tradeoff

Uber's dispatch system matches riders to drivers using a real-time location update pipeline. At peak, this processes 1+ million location updates per second globally. They also run a notification system that fires push notifications (trip accepted, driver arriving) that must fire exactly once — receiving "Your driver arrived" five times is a terrible user experience.

**The delivery guarantee decision:** Uber uses **a tiered approach** — at-least-once for location telemetry (idempotent by nature: the latest position overwrites the previous), exactly-once semantics for state-change notifications (trip started, payment charged) using an outbox pattern + Redis deduplication.

**The outbox pattern at Uber:** When a trip state changes in the database, the state change is written to an `outbox` table in the same database transaction. A separate poller reads the outbox and publishes to Kafka. This guarantees the message is published if and only if the database transaction committed — eliminating the dual-write problem.

```
BEGIN TRANSACTION;
  UPDATE trips SET status = 'accepted' WHERE trip_id = $1;
  INSERT INTO outbox (event_type, payload, published) 
    VALUES ('TRIP_ACCEPTED', $payload, false);
COMMIT;

-- Separate poller:
SELECT * FROM outbox WHERE published = false ORDER BY created_at LIMIT 100;
-- For each: publish to Kafka, then mark published = true
```

**What they got wrong first:** Uber's first notification system (pre-2017) used a direct Kafka producer call inside the trip state transaction. If the Kafka call succeeded but the DB transaction rolled back (or vice versa), notifications fired for trips that didn't exist — or trips changed state silently. The outbox pattern fixed this by making the database the single source of truth.

**Cite:** "Real-time Data Infrastructure at Uber" (arXiv 2104.00087, 2021)

### Design Questions to Ask Before Starting

Before choosing a delivery guarantee, answer these:

1. **Is the operation idempotent?** — If "set balance to X" or "mark order as shipped" is your operation, idempotency is free. If "add $50 to balance" is your operation, you need deduplication.

2. **What is the blast radius of a duplicate?** — Duplicated analytics events: low. Duplicated payment charges: catastrophic.

3. **What is the acceptable latency budget?** — Kafka transactions add 15-40ms to p99 latency. Is your SLA compatible with that?

4. **Is your consumer external or internal?** — Exactly-once in Kafka only applies to Kafka-to-Kafka. External consumers always need their own deduplication.

5. **What is your message volume?** — At 1,000 msg/s, Kafka EOS overhead is irrelevant. At 1M msg/s, a 20% throughput reduction means you need 25% more hardware.

6. **Do you control both producer and consumer?** — If not (webhooks, third-party integrations), you cannot rely on broker-level EOS. Build idempotent consumers.

### Scale Evolution

```
1K messages/day:
  - At-least-once + idempotent consumer
  - SQLite or Postgres dedup table
  - No need for exactly-once machinery

100K messages/day (~1 msg/s):
  - At-least-once + Redis dedup set (SET NX, TTL 24h)
  - Idempotency key = message ID or content hash
  - Start investing in outbox pattern for DB-originated events

1M messages/day (~12 msg/s):
  - At-least-once + Redis or Kafka consumer groups
  - Offset-based deduplication for sequential processing
  - Consider Kafka idempotent producers (free, always enable)
  - Outbox pattern + CDC (Debezium) for DB→Kafka

100M messages/day (~1,200 msg/s):
  - Evaluate Kafka EOS only for payment/financial flows
  - At-least-once + idempotent consumers for telemetry/analytics
  - Tiered approach: different guarantees for different topics
  - Redis cluster for dedup at scale (100M keys = ~6-8GB RAM)
  - Monitor duplicate rates per consumer group (should be <0.1%)
```

### Decision Points and Why

**Use Kafka EOS (Transactions) when:**
- You are doing read-process-write within Kafka only
- Your operation is not naturally idempotent
- You can absorb 15-40ms p99 latency increase
- The cost of a duplicate exceeds the cost of 20% more infrastructure

**Use at-least-once + idempotent consumer when:**
- Any external system is involved (database, API)
- You need maximum throughput
- Your operation is naturally idempotent (last-write-wins)
- You want simplicity and debuggability

## 5. Code / Implementation Perspective

### Python: Idempotent Consumer with Redis Deduplication

```python
import hashlib
import json
import time
from typing import Optional
import redis
from kafka import KafkaConsumer, TopicPartition

# --- Configuration ---
DEDUP_TTL_SECONDS = 86400  # 24 hours
DEDUP_KEY_PREFIX = "dedup:payment:"

redis_client = redis.Redis(host="localhost", port=6379, decode_responses=True)

consumer = KafkaConsumer(
    "payment-events",
    bootstrap_servers=["kafka:9092"],
    group_id="ledger-service",
    auto_offset_reset="earliest",
    enable_auto_commit=False,   # Manual commit: ack only after processing
    max_poll_records=100,
)


def derive_idempotency_key(message: dict) -> str:
    """
    Derive a stable dedup key from message content.
    Prefer an explicit ID if present; fall back to content hash.
    """
    if "payment_id" in message:
        return f"{DEDUP_KEY_PREFIX}{message['payment_id']}"
    # Content-based: deterministic hash of the semantically unique fields
    canonical = json.dumps(
        {k: message[k] for k in sorted(["user_id", "amount", "timestamp"])},
        sort_keys=True,
    )
    return f"{DEDUP_KEY_PREFIX}{hashlib.sha256(canonical.encode()).hexdigest()}"


def is_duplicate(key: str) -> bool:
    """Returns True if we have already processed this message."""
    return redis_client.exists(key) == 1


def mark_processed(key: str) -> None:
    """Record that this message has been processed. Expires after 24h."""
    redis_client.set(key, "1", ex=DEDUP_TTL_SECONDS)


def process_payment(message: dict) -> None:
    """Business logic — idempotent by dedup guard above."""
    print(f"Processing payment {message['payment_id']} for ${message['amount']}")
    # In production: UPDATE ledger SET balance = balance + amount WHERE user_id = ?
    # Use DB-level idempotency (ON CONFLICT DO NOTHING) as a second defense layer


def run_consumer():
    for record in consumer:
        try:
            message = json.loads(record.value.decode("utf-8"))
            dedup_key = derive_idempotency_key(message)

            if is_duplicate(dedup_key):
                print(f"Skipping duplicate: {dedup_key}")
                consumer.commit()  # Still commit offset — we handled it
                continue

            # Process with at-most-once local failure risk
            # (if crash here, message redelivered and dedup key absent -> reprocessed safely)
            process_payment(message)

            # Mark BEFORE committing offset to avoid a tiny window
            # where crash after commit but before mark causes re-processing
            mark_processed(dedup_key)
            consumer.commit()

        except Exception as e:
            print(f"Processing failed: {e}")
            # Do NOT commit offset -> message will be redelivered
            # Idempotency key not set -> will be processed again (correct behavior)


if __name__ == "__main__":
    run_consumer()
```

### Kafka Producer: Idempotent + Transactional Configuration

```python
from kafka import KafkaProducer
import json

# --- Idempotent Producer (always enable in production) ---
idempotent_producer = KafkaProducer(
    bootstrap_servers=["kafka:9092"],
    enable_idempotence=True,          # Enables PID + sequence number dedup
    acks="all",                        # Required for idempotence
    retries=2147483647,               # Required: must be > 0
    max_in_flight_requests_per_connection=5,  # Max 5 for idempotence
    value_serializer=lambda v: json.dumps(v).encode(),
)

# --- Transactional Producer (exactly-once Kafka-to-Kafka) ---
transactional_producer = KafkaProducer(
    bootstrap_servers=["kafka:9092"],
    transactional_id="payment-processor-instance-1",  # Unique per producer instance
    enable_idempotence=True,
    acks="all",
    value_serializer=lambda v: json.dumps(v).encode(),
)
transactional_producer.init_transactions()

def process_with_transaction(input_message: dict) -> None:
    transactional_producer.begin_transaction()
    try:
        result = {"payment_id": input_message["payment_id"], "status": "settled"}
        transactional_producer.send("payment-settled", value=result)
        # Atomically commit input offset + output message
        transactional_producer.send_offsets_to_transaction(
            offsets={TopicPartition("payment-events", 0): 42},
            group_metadata=consumer.consumer_group_metadata(),
        )
        transactional_producer.commit_transaction()
    except Exception as e:
        transactional_producer.abort_transaction()
        raise
```

### Language-Agnostic Deduplication Algorithm

```
ALGORITHM: Safe At-Least-Once Processing

INPUT:  message M with idempotency_key K
OUTPUT: side effects applied exactly once

1. key = derive_key(M)                   # from message ID or content hash
2. exists = dedup_store.get(key)         # Redis GET or DB SELECT
3. IF exists:
4.     log("duplicate, skipping")
5.     ack(M)                            # advance offset/delete from queue
6.     RETURN
7. ENDIF
8. result = apply_business_logic(M)      # the side effect
9. dedup_store.set(key, TTL=24h)         # mark as processed
10. ack(M)                               # commit offset
```

**Critical ordering note (step 8-10):** You must mark the key as processed (step 9) before committing the offset (step 10). If you crash between processing (8) and marking (9), the message redelivers and is reprocessed — that is acceptable because it is idempotent. If you mark and commit (10) but crash before setting the dedup key, you silently skip future redeliveries — that is a bug.

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **At-least-once + idempotent consumer** | Most production workloads | Requires careful consumer design; duplicates must be handled | LinkedIn, Netflix, Cloudflare |
| **Kafka Exactly-Once (EOS)** | Financial streams, Kafka-to-Kafka only | 20% throughput reduction, 2-3x latency; no external writes covered | High-frequency trading firms, regulated fintech |
| **Outbox Pattern** | DB-originated events that must not be lost | Polling adds latency; requires CDC infrastructure | Uber, most event-sourced systems |
| **Idempotency Key (HTTP API)** | REST APIs, webhooks, payment gateways | Client must store and retry with same key; key expiry edge cases | Stripe, PayPal, Twilio |
| **Two-Phase Commit (2PC)** | When you need true atomic writes across two systems | Locks resources; ~100-500ms coordination; not practical at scale | Legacy enterprise systems, rarely in modern microservices |
| **Saga Pattern (Compensating Txns)** | Long-running workflows across microservices | Complex rollback logic; eventual consistency only | Uber, Amazon checkout |
| **Exactly-once via CRDT** | Counters, sets, distributed state | Limited to CRDT-expressible operations | Redis CRDT (Redis Enterprise) |

### Opinionated Recommendation

**Stop chasing exactly-once as a system-level property. Design for idempotency at the application level.**

The distributed systems research community has a clear consensus: true exactly-once delivery across a network boundary is provably impossible under certain failure models (see the FLP impossibility result and its applications). What Kafka calls "exactly-once" is a specific, scoped guarantee within a Kafka cluster. The moment your code writes to a database, calls an external API, or sends an email, you are back to at-least-once, full stop.

The correct architecture is:
1. Use at-least-once delivery (simpler, faster, more available)
2. Make every consumer operation idempotent (use unique constraint in DB, Redis SET NX, or explicit dedup table)
3. For DB-originated events: use the outbox pattern to prevent dual-write
4. Enable Kafka idempotent producers unconditionally (free, zero trade-off)
5. Enable Kafka EOS transactions only for Kafka-to-Kafka financial flows where latency budget allows

## 8. Trade-offs (Be Opinionated)

### Benefits of At-Least-Once

- **Maximum throughput:** No transaction coordination overhead. Kafka at-least-once can sustain 1M+ msg/s per broker. Kafka EOS drops to ~800K msg/s (20% reduction).
- **Lower latency:** p99 latency of 25-50ms vs 80-150ms with transactions. At Uber's scale (1M events/sec), this latency difference means millions of events stuck in flight at any given moment.
- **Simpler failure model:** When a consumer crashes and restarts, it just re-reads from the last committed offset. No transaction abort/rollback needed.
- **Works with any broker:** Idempotent consumers work with SQS, RabbitMQ, Kinesis, HTTP webhooks — any delivery mechanism. Kafka EOS is Kafka-specific.
- **Simpler debugging:** "Message X was processed twice" is a straightforward bug. "Transaction Y was half-committed" is a debugging nightmare.

### Costs and Limitations of Exactly-Once

- **Scoped guarantee:** Kafka EOS covers only Kafka-to-Kafka. Any external write is at-least-once. Engineers often misunderstand this and disable their idempotent consumer code after enabling EOS — then get duplicate database writes.
- **Throughput cost:** 20% throughput reduction means 25% more hardware to maintain the same message rate. At LinkedIn's scale (7 trillion msg/day), that is hundreds of additional broker nodes.
- **Latency cost:** Transaction coordination adds 2-5ms of coordination RPC overhead, which compounds at p99. For real-time systems, this is often unacceptable.
- **Complexity cost:** Transactional producers require careful management of `transactional_id` uniqueness. Two producers with the same ID will fence each other, causing message loss. Getting this wrong in production has caused several major incidents.
- **Zombie producer problem:** A slow producer can hold a transaction open for up to `transaction.timeout.ms` (default 60 seconds), blocking consumers of the output topic who use `isolation.level=read_committed`.

### Core Tension

**The fundamental tension is this: exactly-once semantics add coordination cost proportional to the number of participants, while at-least-once amortizes this cost by pushing deduplication to the application layer where it can be done asynchronously.**

Coordination is expensive. Idempotency is cheap. Design accordingly.

### My Recommendation

**Default to at-least-once delivery + idempotent consumers. Enable Kafka idempotent producers always (it is free). Reach for Kafka EOS transactions only when all of the following are true:**

1. Both your source and destination are Kafka topics (no external systems)
2. Your operation is non-idempotent and the cost of a duplicate is unacceptable
3. Your latency SLA can absorb 2-3x p99 latency increase
4. Your team understands the transactional.id fencing semantics deeply

In 8 out of 10 real systems I have reviewed, the correct answer is at-least-once + idempotent consumer. The one scenario where I consistently recommend Kafka EOS is financial ledger aggregation within a streaming system — e.g., a Kafka Streams job that aggregates running account balances, where the source and sink are both Kafka topics, and a duplicate would cause incorrect balance calculations.

## 9. Failure Modes — What Goes Wrong

### Duplicate Processing Due to Consumer Rebalance

**Trigger:** A Kafka consumer in a consumer group becomes temporarily slow (GC pause, high load, slow DB query). The broker times it out after `session.timeout.ms` (default 45s) and triggers a group rebalance. The partition is reassigned to another consumer. The original consumer was mid-processing with an uncommitted offset. The new consumer re-reads from the last committed offset.

**Symptoms:** Downstream database shows duplicate rows. Analytics metrics are inflated. Payment processing logs show the same `payment_id` processed by two different consumer instances within a 45-second window.

**Detection:** Monitor duplicate rate per consumer group. Alert when: `COUNT(DISTINCT message_id) / COUNT(*) < 0.999` over any 5-minute window. Also monitor `kafka_consumer_group_lag` — high lag correlates with frequent rebalances.

**Recovery:** Idempotent consumers self-heal — duplicates are silently ignored by the dedup store. If no idempotency: stop the consumer group, manually identify duplicates in the DB using the `message_id` field, run a reconciliation script.

**Real Example:** A mid-size e-commerce company (not publicly disclosed) experienced 23,000 duplicate order confirmations during a Black Friday deployment in 2022. Their consumer nodes had high GC pressure from a memory leak, causing frequent rebalances. They had not implemented idempotency. Recovery took 8 hours of manual data reconciliation.

---

### Transactional ID Fencing (Kafka EOS)

**Trigger:** A Kafka producer using transactions crashes and restarts. The new instance uses the same `transactional.id`. The old instance (zombie — still running in an isolated network partition) tries to send messages with the old epoch. The Transaction Coordinator fences the zombie by incrementing the epoch and raising `ProducerFencedException` in the zombie.

**Symptoms:** The zombie producer logs `ProducerFencedException` and halts. If your code does not handle this exception correctly, the zombie silently stops producing without alerting. Messages from the zombie's in-flight transaction are never committed. Input topic offsets are not advanced for that transaction window.

**Detection:** Monitor for `ProducerFencedException` in producer logs. Monitor consumer group lag on input topics — if lag grows unexpectedly, a producer may have been fenced. Alert on: `kafka_producer_record_error_rate > 0` for transactional producers.

**Recovery:** Fencing is by design and works correctly if handled. The fix is: catch `ProducerFencedException`, log it as WARNING (not ERROR — it is expected behavior), and let the process restart under your orchestrator. The new instance will resume from the last committed offset.

**Real Example:** Confluent's own documentation acknowledges this failure mode. In 2019, a major European bank using Confluent Platform misconfigured `transactional.id` to be static per deployment (not per instance), causing all replicas of a service to fight for the same transaction ID, resulting in continuous fencing and zero message throughput until they reconfigured to use `hostname`-based transactional IDs.

---

### Redis Dedup Store Failure

**Trigger:** Your at-least-once consumer uses Redis for deduplication (SET NX with TTL). Redis becomes unavailable (OOM, network partition, restart). The consumer has two choices: halt processing (backpressure) or continue without deduplication. If it continues, all messages during the Redis outage will be processed without deduplication. If any of those messages are redelivered after Redis recovers, they will be processed a second time.

**Symptoms:** Spike in processed message count during Redis unavailability. Post-recovery: duplicate rows in the database, duplicate charge attempts, duplicate notifications.

**Detection:** Monitor Redis connection health in consumer code. Alert on: `redis_connected = false` in consumer metrics. Monitor downstream DB for duplicate key violations (`ON CONFLICT` hits).

**Recovery:** During Redis outage: fail closed (stop processing) for financial operations; fail open (process without dedup) only for low-stakes analytics. Post-recovery: if you failed open, run a reconciliation query to find duplicates by `message_id` and reverse the duplicates. Add a secondary dedup layer in the database (`UNIQUE` constraint on `payment_id`) as defense-in-depth.

**Real Example:** A Cloudflare blog post describes their queues system explicitly handling this scenario: "Queues guarantee at-least-once delivery. Consumers must implement idempotent handling and should not depend on a single deduplication store." They recommend the database `UNIQUE` constraint as the authoritative dedup layer, with Redis as a performance optimization (fast path), not a correctness requirement.

---

### The 5-Minute Window Problem (SQS FIFO)

**Trigger:** SQS FIFO deduplication windows last exactly 5 minutes. A producer sends a message, crashes, and the same message is resent 6 minutes later (outside the dedup window). SQS treats it as a new unique message. The consumer processes it twice.

**Symptoms:** Duplicate records in the database. Operations teams see the same `MessageDeduplicationId` in CloudWatch logs for two separate SQS receives more than 5 minutes apart.

**Detection:** Log both the SQS `MessageId` and your business-level `payment_id` on each process. Alert when a `payment_id` appears more than once in processed records within a 24-hour window.

**Recovery:** SQS FIFO deduplication is purely a producer-side optimization. Always implement consumer-side idempotency regardless of queue type. Do not rely on SQS deduplication windows as your only defense. Use `MessageDeduplicationId` to reduce duplicate messages, but never as your sole correctness mechanism.

**Real Example:** AWS documentation explicitly states: "Amazon SQS continues to keep track of the message deduplication ID even after the message is received and deleted. The deduplication period is 5 minutes." This is a documented limitation, not a bug. Multiple AWS blog posts warn that FIFO queues still require idempotent consumers.

## 10. When To Use vs. When To Avoid

### Use At-Least-Once When:

- **Your operation is idempotent.** Setting a user's email address, marking an order as shipped, updating a cache entry — these are safe to apply multiple times. At-least-once + idempotent consumer is all you need.

- **You need maximum throughput.** At 500K+ msg/s, a 20% throughput reduction from Kafka EOS means significant additional infrastructure cost. Use at-least-once with application-level deduplication.

- **Your consumer writes to an external system (DB, API, email).** Kafka EOS does not cover external writes. You need consumer-side idempotency regardless. If you need idempotency anyway, at-least-once is simpler and sufficient.

- **You need broker portability.** If your architecture might switch from Kafka to SQS, RabbitMQ, or a cloud-native queue, at-least-once + idempotent consumer works everywhere. Kafka EOS is Kafka-specific.

### Do NOT Use Exactly-Once (Kafka EOS) When:

- **Your consumer writes to any system outside Kafka.** Kafka EOS is scoped to Kafka-to-Kafka. Database writes, HTTP calls, and external service updates are always at-least-once. Using EOS here gives a false sense of safety while adding latency and complexity.

- **You have a strict low-latency SLA.** If your p99 must be under 50ms, Kafka transactions (adding 50-150ms p99) will violate your SLA. Use at-least-once + dedup.

- **Your team does not deeply understand transactional.id fencing.** Misconfigured transactional IDs have caused production outages at companies with dedicated Kafka engineering teams. If your team is not Kafka-expert level, the risk of misconfiguration exceeds the benefit.

- **You are using SQS, RabbitMQ, or any non-Kafka broker.** EOS is a Kafka-specific feature. "Exactly-once" in SQS FIFO is a producer-side dedup window, not a transactional guarantee.

### The Number One Mistake Engineers Make

**Enabling Kafka exactly-once semantics and then removing idempotency logic from their consumers, believing EOS makes it unnecessary.**

It does not. Kafka EOS covers the Kafka pipeline only. The database write inside your consumer is still at-least-once. Every engineer who has made this mistake has eventually had a consumer crash after writing to the DB but before committing the Kafka offset — resulting in a duplicate DB write and, if idempotency was removed, a data integrity incident.

**The rule:** Idempotent consumers are not optional, regardless of your broker's delivery guarantee. They are your last line of defense.

## 11. Interview Perspective

### Real Interview Question Phrasings

- "How would you design a payment processing system that avoids charging customers twice?"
- "Explain the difference between at-least-once and exactly-once delivery. When would you use each?"
- "You're building a notification system for Uber. How do you ensure a 'driver arrived' notification fires exactly once?"
- "Kafka claims to support exactly-once semantics. What are the limitations of this claim?"
- "Your e-commerce checkout service uses SQS. A network glitch causes the order-placed message to be delivered twice. Walk me through how you'd handle that."
- "What is an idempotency key? How does Stripe use it?"

### What the Interviewer Evaluates

- **Depth of failure reasoning:** Can you identify the specific failure scenario (crash-before-ack) that causes duplicates? Or do you only know the happy path?
- **Nuance on exactly-once:** Do you know that Kafka EOS is scoped to Kafka-to-Kafka? Engineers who say "just enable exactly-once" without mentioning external system limitations fail this evaluation.
- **Systems thinking:** Can you trace a message through the full pipeline (producer → broker → consumer → database) and identify every point of failure?
- **Trade-off reasoning:** Can you argue for at-least-once in the right contexts, rather than assuming more guarantees are always better?

### Questions YOU Ask Before Answering

Before you design anything, ask:

1. "Is this operation idempotent — can I safely apply it multiple times?"
2. "What is the blast radius of a duplicate? Financial? UX? Analytics?"
3. "Are we writing only within Kafka, or does our consumer call external services?"
4. "What is the latency budget? Can we absorb 2-3x p99 overhead?"
5. "What is the message volume? Does EOS throughput cost matter at this scale?"

Asking these questions signals staff-level thinking to the interviewer. It also often changes the problem — most "exactly-once" problems are actually "idempotent consumer" problems.

### Answer Examples by Level

**Junior (L3-L4):**
> "At-least-once delivery means the message might arrive more than once, so my consumer needs to handle duplicates. I'd use a unique constraint in the database to prevent double-charging. At-least-once is easier to implement and more scalable. Exactly-once requires distributed transactions and is harder."

This is correct and sufficient for L3-L4.

**Senior (L5):**
> "The key insight is that exactly-once at the broker level doesn't help if you're writing to an external system. Even with Kafka EOS, a consumer that writes to a database is at-least-once, because the consumer can crash between the DB write and the Kafka offset commit. The right architecture is: use at-least-once delivery, make every consumer operation idempotent using a deduplication store (Redis with TTL or DB unique constraint), and use the outbox pattern to prevent dual-write problems when messages originate from database state changes. Enable Kafka idempotent producers always — it's free. Use Kafka transactions only for pure Kafka-to-Kafka financial flows where you can't make the operation idempotent otherwise."

**Staff (L6+):**
> "I want to understand the failure modes before recommending a pattern. The core problem is: you have an at-least-once delivery channel, and a non-idempotent operation. There are three layers of defense: first, make the operation idempotent if you can — that solves the problem cheapest. Second, use application-level dedup with a Redis TTL store or DB unique constraint as the authoritative check. Third, for Kafka-to-Kafka pipelines only, Kafka EOS can eliminate duplicates broker-side, but you pay 20% throughput and 2-3x p99 latency.
>
> For this payment system specifically: I'd use the outbox pattern so the message is published if and only if the DB transaction commits. The Kafka producer should be idempotent (always). The consumer should use a `payment_id` unique constraint in the DB as the dedup mechanism — this is the authoritative layer. I'd add Redis as a fast-path dedup to avoid hitting the DB on duplicates. I'd not use Kafka EOS here because the consumer writes to PostgreSQL, not another Kafka topic, so EOS buys nothing. The Redis TTL should be at least 2x the broker's retention window to handle slow consumers. I'd monitor duplicate rates per consumer group and alert at >0.01%.
>
> One more thing: the dedup TTL must be longer than your message retention. If Kafka retains messages for 7 days and your Redis TTL is 24 hours, a consumer that falls 25+ hours behind and then catches up will reprocess expired dedup entries as if they were new."
