## 1. What Is It? (Theory)

### Plain English

An API gateway is a reverse proxy that sits at the edge of your system, directly in front of all client traffic. Every HTTP request from the outside world hits the gateway first. The gateway decides what to do with the request — authenticate it, rate-limit it, route it to the right backend service, transform its shape, log it, and return the response to the client.

Think of it as the reception desk at a large corporation. You don't walk directly into the engineering department, legal department, or finance department. You check in at reception. Reception verifies your identity, hands you a visitor badge, tells you which floor to go to, logs your visit, and calls ahead to let the department know you're coming. The gateway is that reception desk for your API traffic.

### The Problem It Solves at Scale

Without a gateway, every microservice must independently implement:
- **Authentication and authorization** — each service verifies JWTs, calls an identity provider, handles token expiry
- **Rate limiting** — each service must track per-client request counts in a shared data store
- **TLS termination** — each service manages its own certificate rotation
- **Observability** — each service emits its own request logs and metrics in potentially different formats
- **Protocol translation** — mobile clients speaking REST but some internal services speaking gRPC

At 10 services this is painful. At 100 services this is catastrophic. You end up with duplicated, inconsistent, drift-prone security logic spread across every team's codebase. One team skips the rate limiting. Another team has a JWT verification bug. A third team's certificates expire on a Sunday.

The gateway centralizes these cross-cutting concerns into one place, operated by one team (usually platform/infrastructure), with consistent enforcement.

### Why It Was Invented

The pattern emerged as Netflix, Amazon, and Uber decomposed their monoliths into hundreds of microservices in the 2010-2015 timeframe. Netflix open-sourced Zuul in 2013 specifically because they needed a programmable edge layer that could handle 10,000 different device types (smart TVs, mobile, browsers, gaming consoles) each with different payload requirements. A single REST API that returned the same payload to a 2013 Nokia phone and a 2013 desktop browser was untenable.

### What Breaks Without It

- **Security drift**: without centralized auth, services skip it. In 2019, Facebook's internal service mesh had auth enforcement gaps because individual service teams were responsible for implementing it.
- **Latency multiplication**: a mobile app that needs data from 8 services makes 8 serial or parallel network requests. Each round trip is 50-200ms. A gateway can aggregate these into one client request.
- **Operational blindness**: no consistent request logs means no ability to correlate a user's journey across services.
- **Certificate chaos**: each service managing its own TLS certificate means certificate expiry incidents (a surprisingly common cause of outages).

### Concrete Example with Real Numbers

Consider a mobile e-commerce app. A single "load product detail page" action requires:
- Auth service: verify session token — 20ms
- Product service: get product data — 15ms
- Inventory service: check stock — 12ms
- Pricing service: get current price — 8ms
- Reviews service: get top 3 reviews — 25ms

Without a gateway: the mobile app makes 5 sequential requests = 80ms minimum round-trip latency, plus 5x the mobile network overhead (~150ms each on LTE) = **750ms+ to render a page**.

With a gateway aggregating (BFF pattern): the mobile app makes 1 request, the gateway fans out to 5 services in parallel (25ms for the slowest), aggregates, and returns = **~175ms total**. That is a 4x improvement in perceived latency.

## 2. How It Actually Works (Deep Mechanics)

### Step-by-Step Request Processing Pipeline

When a request arrives at the gateway, it passes through a **plugin pipeline** — an ordered chain of processing stages. Each stage can short-circuit the pipeline (e.g., returning 401 before the request ever reaches a backend).

```
1. TLS Termination
   └── Decrypt TLS, verify client cert (mTLS), establish plaintext connection internally

2. Request Parsing
   └── Parse HTTP method, URI, headers, body; validate Content-Type

3. Routing Resolution
   └── Match URI pattern to upstream service (e.g., /api/v1/products/* → product-svc)

4. Authentication
   └── Verify JWT signature, check token expiry, validate issuer/audience claims

5. Authorization
   └── RBAC/ABAC check: does this token have permission for this method+path?

6. Rate Limiting
   └── Increment counter in Redis: key = "ratelimit:{client_id}:{window}"
       └── If counter > limit → return 429 Too Many Requests

7. Request Transformation
   └── Add headers (X-Request-ID, X-User-ID), strip external headers, rewrite paths

8. Load Balancing
   └── Select upstream instance (round-robin, least-conn, consistent-hash)

9. Upstream Request
   └── Forward request to selected backend instance

10. Response Transformation
    └── Strip internal headers, compress body, add CORS headers

11. Logging & Telemetry
    └── Emit structured log line + Prometheus counter/histogram increment
```

### Key Algorithms

**Token Bucket Rate Limiting (the dominant algorithm in production)**

Each client has a "bucket" with a maximum capacity (the burst limit). Tokens refill at a fixed rate (e.g., 1000 req/s). Each request consumes one token. If the bucket is empty, the request is rejected with HTTP 429.

```
bucket_state = redis.hgetall("ratelimit:{client_id}")
tokens        = float(bucket_state["tokens"])
last_refill   = float(bucket_state["last_refill"])
now           = time.time()

# Refill tokens since last check
elapsed       = now - last_refill
tokens        = min(CAPACITY, tokens + elapsed * REFILL_RATE)

if tokens >= 1.0:
    tokens -= 1.0
    redis.hset("ratelimit:{client_id}", {"tokens": tokens, "last_refill": now})
    return ALLOW
else:
    return DENY_429
```

This must be executed atomically (Lua script in Redis) to avoid race conditions. Kong's rate limiting plugin does exactly this with a Lua script executed via ngx.timer.

**Consistent Hash Load Balancing**

For stateful upstream services (e.g., WebSocket connections, session-pinned backends), the gateway uses consistent hashing on the client IP or session ID so the same client always routes to the same upstream instance. This avoids session migration overhead.

**JWT Verification**

RS256 (RSA signature with SHA-256) is the standard. The gateway fetches public keys from the identity provider's JWKS endpoint (cached locally, refreshed on key rotation with a 5-minute TTL). Verification is purely local CPU computation — no network round-trip — which keeps auth overhead at **<1ms per request** for a cached key.

### Real Numbers

| Operation | Typical Latency | Notes |
|---|---|---|
| TLS handshake (new conn) | 5-15ms | Amortized with keep-alive |
| JWT verify (RS256, cached key) | 0.3-0.8ms | Local CPU, no network |
| Redis rate limit check | 0.5-2ms | RTT to Redis in same AZ |
| Route resolution (hash map) | <0.01ms | O(1) hash lookup |
| Total gateway overhead | 2-5ms | Warm path, keep-alive, cached auth |
| APISIX throughput | 23,000 RPS per core | Benchmark with auth+rate-limit |
| Kong throughput | ~11,000 RPS per core | Same benchmark conditions |
| AWS API Gateway max (default) | 10,000 RPS per region | Soft limit, increasable |

### Misconceptions

**❌ Misconception: The API gateway is just a load balancer.**
✅ Reality: A load balancer operates at L4 (TCP) or L7 HTTP, distributing traffic across identical instances of a single service. A gateway routes traffic across *different* services, applies business-logic-adjacent concerns (auth, rate limiting, transformation), and is aware of the API semantics of each route. Conflating them leads to asking a load balancer to do auth (it can't) or putting auth logic in every service (it scales poorly).

**❌ Misconception: The gateway is always the bottleneck.**
✅ Reality: A properly scaled gateway cluster has more spare capacity than the backend services it protects. At 2-5ms gateway overhead and backends taking 20-200ms to serve requests, the gateway is almost never the constraint. The risk is the *configuration plane* (database or etcd writes during route changes), not the data plane (request forwarding).

**❌ Misconception: Putting the gateway in front of everything adds latency.**
✅ Reality: For mobile clients, aggregation at the gateway *reduces* overall latency by collapsing multiple serial client-to-server round trips into parallel backend calls with one client round trip. The added gateway overhead (2-5ms) is recouped many times over.

## 3. Real-World Architecture Examples

### Netflix — Zuul and the Multi-Device Problem

By 2013, Netflix served over 1,000 different device types. A smart TV running a 2008 firmware had 256MB RAM and could not parse the same JSON payload as a 2013 MacBook browser. The backend services had no business knowing which device was calling them.

Netflix built Zuul (open-sourced 2013) as a JVM-based gateway with a dynamic filter system. Filters were Groovy scripts that could be pushed to the gateway without a deployment — a critical feature when they needed to hot-fix device-specific rendering bugs affecting millions of users in production.

**What they got wrong first:** Zuul 1 was built on a blocking I/O model (Tomcat thread pool). Each in-flight request held a thread. At Netflix's 2015 scale (~100,000 concurrent connections), they needed tens of thousands of threads, consuming enormous heap memory and producing GC pressure. Zuul 2 (released 2016) rebuilt on Netty (async, non-blocking I/O), reducing thread count by 30x for the same concurrency.

**Scale trigger:** Zuul handles tens of billions of requests per day. At peak, Netflix sustains ~15% of North American internet bandwidth. The blocking model simply could not scale to their connection count.

**Real blog reference:** Netflix Tech Blog — "Zuul 2: The Netflix Journey to Asynchronous, Non-Blocking Systems" (2016)

---

### Uber — Three Generations of Edge Gateway

Uber's engineering blog documents their gateway evolution explicitly. By 2019, Uber ran over 2,200 microservices across multiple data centers and cities.

**Gen 1 (2014-2016):** A single nginx instance with hand-maintained location blocks. Worked fine at 10 services. Failed as a maintenance model at 50+ services — every new service required an nginx config PR that only the platform team could merge.

**Gen 2 (2016-2018):** A Go-based gateway that read route configuration from a database. Gave product teams self-service routing. Problem: the Go service had no generics (pre-Go 1.18), requiring massive amounts of generated code during build. Naming convention mismatches between Go idioms (HTTP, ID) and Thrift-generated code (Http, Id) caused serialization bugs that leaked internal field names into external API responses.

**Gen 3 (2018+):** Uber decomposed the monolithic gateway into domain-specific gateways aligned with their Domain-Oriented Microservice Architecture (DOMA). Instead of one gateway routing to 2,200 services, each business domain (rides, Eats, freight) has its own gateway. This reduced blast radius — a misconfiguration in the Eats gateway doesn't affect the rides gateway.

**What they got wrong:** Gen 2's single gateway became a choke point for organizational velocity. 500+ engineers all needed to request routing changes from one team. The solution was not a faster gateway — it was multiple gateways with clear ownership.

**Real source:** Uber Engineering Blog — "The Architecture of Uber's API Gateway" (eng.uber.com)

---

### Airbnb — GraphQL as the API Layer

Airbnb's SOA migration (2018-2021) started with ~2,000 services and ~500 engineers. Their specific problem: the frontend team needed to make 15+ separate REST calls to render a single listing page, each with its own auth check, serialization overhead, and network round trip.

Airbnb built **Viaduct** — a GraphQL-based data-oriented service mesh. Instead of routing REST calls to individual services, Viaduct acts as a gateway that accepts a GraphQL query, decomposes it into parallel calls to relevant services, and assembles the response. This collapsed the mobile app's 15-request page-load into a single query.

**What they got wrong first:** The central GraphQL schema became a coordination bottleneck. Every team that owned a service needed to add their fields to a shared schema. With 500 engineers, schema PRs created a queue. They solved this with schema federation — each service owns its own schema fragment, and the gateway stitches them together.

**Scale at which they made the decision:** ~200 engineers contributing to the data aggregation layer simultaneously, causing the monolithic schema to become slow to deploy (30-minute CI pipeline for schema changes).

**Real source:** Airbnb Tech Blog — "Taming Service-Oriented Architecture Using A Data-Oriented Service Mesh" (medium.com/airbnb-engineering)

### Design Questions to Ask Before Starting

Before selecting or building a gateway, answer these:

1. **Who are your clients?** Internal services only? Mobile apps? Third-party partners? Each has different auth, rate limiting, and protocol requirements.
2. **What protocols do your backends speak?** gRPC? REST? GraphQL? The gateway must translate.
3. **What is your team's operational maturity?** Self-managed Kong requires Kubernetes expertise. AWS API Gateway requires zero ops but adds $3.50/million requests.
4. **Do you need real-time config changes?** If so, database-backed config (Kong with Postgres) means 5-10s propagation lag. etcd-backed (APISIX) means millisecond propagation.
5. **What is your rate limiting granularity?** Per-IP? Per-user? Per-API-key? Per-endpoint? The Redis key schema design is critical.
6. **Do you need request aggregation (BFF)?** A pure routing gateway (nginx) cannot aggregate. You need an application-layer gateway (Kong, APISIX, custom service).

### Scale Evolution

**1K users (~10 RPS)**

A single nginx reverse proxy with hand-written location blocks. No auth at the gateway (JWT verification in each service). No rate limiting. Basic access logging. Total gateway team: 0 dedicated engineers. This is appropriate.

**100K users (~1,000 RPS)**

You start feeling pain. Multiple services need auth. You add Kong or APISIX with the JWT plugin and a Redis rate-limiter. A single gateway instance (4 vCPU) handles ~40,000 RPS with auth and rate limiting enabled — 1,000 RPS is trivial. But now you need the gateway to stay up during deployments, so you add a second instance behind a load balancer. Config is stored in Postgres (Kong) or etcd (APISIX).

**1M users (~10,000 RPS)**

AWS API Gateway's 10,000 RPS default limit becomes a hard constraint you'll hit. You either request a limit increase or switch to self-managed. With self-managed Kong: 3 nodes × 11,000 RPS per node = 33,000 RPS capacity before adding nodes — comfortable. You add dedicated Redis cluster for rate limiting (to survive gateway node failures). You add a circuit breaker plugin to prevent cascade failures. Dedicated platform team: 2-3 engineers.

**100M users (~1,000,000 RPS)**

Now you have Uber/Netflix problems. A single fleet of gateways becomes an organizational bottleneck. You split into domain gateways. You consider whether the gateway is doing too much — some concerns (service mesh mTLS, L4 load balancing) move to a service mesh (see section 7.4). The gateway focuses on edge concerns: external auth, rate limiting, protocol translation, API versioning. Dedicated platform team: 10-20 engineers with on-call rotation.

### Decision Points

| Decision | Option A | Option B | When to Choose B |
|---|---|---|---|
| Managed vs self-managed | AWS API Gateway | Kong / APISIX on K8s | >500M requests/month (cost), or need <5ms overhead |
| Single vs domain gateways | One fleet | Per-domain fleet | >50 services, >100 engineers |
| Rate limit store | Redis Cluster | Per-node in-memory | Exact counts not critical, prefer simplicity |
| Auth location | Gateway only | Gateway + service | Defense in depth for regulated industries |
| Protocol | REST only | REST + gRPC + WebSocket | Native mobile apps with high-frequency events |

## 5. Code / Implementation Perspective

### Python Implementation Sketch

This is a simplified gateway that illustrates the core pipeline — auth, rate limiting, routing, and upstream proxying. Real gateways (Kong, APISIX) implement this in C/LuaJIT for performance.

```python
import time
import httpx
import jwt
import redis
from fastapi import FastAPI, Request, Response, HTTPException

app = FastAPI()
r = redis.Redis(host="redis", port=6379, decode_responses=True)

# Route table: loaded from config store (etcd/DB in production)
ROUTES = {
    "/api/v1/products": "http://product-svc:8001",
    "/api/v1/orders":   "http://order-svc:8002",
    "/api/v1/users":    "http://user-svc:8003",
}
JWT_PUBLIC_KEY = open("public.pem").read()
RATE_LIMIT_RPS = 100      # requests per second per client
BUCKET_CAPACITY = 200     # burst capacity

def resolve_route(path: str) -> str | None:
    for prefix, upstream in ROUTES.items():
        if path.startswith(prefix):
            return upstream
    return None

def verify_token(authorization: str | None) -> dict:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(401, "Missing or malformed Authorization header")
    token = authorization.removeprefix("Bearer ")
    try:
        return jwt.decode(token, JWT_PUBLIC_KEY, algorithms=["RS256"],
                          audience="my-api")
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "Token expired")
    except jwt.InvalidTokenError as e:
        raise HTTPException(401, f"Invalid token: {e}")

def check_rate_limit(client_id: str) -> None:
    key = f"ratelimit:{client_id}"
    now = time.time()
    # Atomic Lua script in production; simplified here
    pipe = r.pipeline()
    pipe.hgetall(key)
    result = pipe.execute()[0]
    tokens = float(result.get("tokens", BUCKET_CAPACITY))
    last   = float(result.get("last", now))
    elapsed = now - last
    tokens  = min(BUCKET_CAPACITY, tokens + elapsed * RATE_LIMIT_RPS)
    if tokens < 1.0:
        raise HTTPException(429, "Rate limit exceeded")
    r.hset(key, mapping={"tokens": tokens - 1, "last": now})
    r.expire(key, 3600)

@app.api_route("/{path:path}", methods=["GET","POST","PUT","DELETE","PATCH"])
async def gateway(request: Request, path: str):
    upstream_base = resolve_route(f"/{path}")
    if not upstream_base:
        raise HTTPException(404, "No route for this path")

    claims = verify_token(request.headers.get("authorization"))
    client_id = claims.get("sub", request.client.host)
    check_rate_limit(client_id)

    upstream_url = f"{upstream_base}/{path}"
    headers = dict(request.headers)
    headers["X-User-ID"]    = client_id
    headers["X-Request-ID"] = request.headers.get("x-request-id", "")
    headers.pop("host", None)

    async with httpx.AsyncClient(timeout=30.0) as client:
        resp = await client.request(
            method=request.method,
            url=upstream_url,
            headers=headers,
            content=await request.body(),
        )
    return Response(content=resp.content, status_code=resp.status_code,
                    headers=dict(resp.headers))
```

### Language-Agnostic Pattern: The Plugin Chain

Every production gateway implements the **Chain of Responsibility** pattern. Each plugin is a handler that either:
- Passes the request to the next handler in the chain, or
- Short-circuits (returns a response directly)

This enables composition without coupling. Adding a new concern (e.g., geo-blocking) means inserting a new plugin at a specific position in the chain without modifying any existing plugin.

## 7. Alternatives & Comparisons

| Approach | When to Use | Key Trade-off | Real Adopters |
|---|---|---|---|
| **API Gateway (centralized)** | Multiple external clients, cross-cutting concerns, microservices | Single point of failure risk; operational overhead | Netflix, Uber, Shopify, Stripe |
| **Service Mesh (Istio/Linkerd)** | East-west (service-to-service) mTLS, observability without code changes | Does not handle north-south edge concerns well; high complexity | Airbnb (Viaduct), Lyft, Square |
| **BFF (Backend for Frontend)** | Different clients (mobile vs web) have genuinely different payload needs | N gateways to maintain; code duplication across BFFs | SoundCloud (coined the term), Netflix per-device teams |
| **GraphQL Gateway (Federation)** | Complex interconnected data graph; frontend teams want autonomy over queries | Schema design discipline required; N+1 query risk; caching harder | Airbnb, GitHub, Shopify Storefront |
| **Direct Service Exposure** | Internal services only, no external clients, simple systems | No centralized security enforcement; hard to add cross-cutting concerns later | Startups <5 engineers, internal tooling |
| **Sidecar + No Gateway** | Full-service-mesh architecture where all cross-cutting concerns live in sidecars | Still need edge for external clients; complex sidecar lifecycle management | Google (Istio origin), Lyft (Envoy origin) |

### Opinionated Recommendation

Start with a managed gateway (AWS API Gateway or Kong Konnect) and get to production fast. Do not build a custom gateway — the problems it solves (distributed rate limiting, JWT verification, request routing) are well-solved by existing tools. The only reason to deviate is if you have >500M requests/day and the managed cost is prohibitive, or you need <1ms gateway overhead that only a self-managed Nginx/APISIX can deliver.

The BFF pattern is often the right answer when you have a mobile app and a web app with genuinely divergent data needs — not as a premature optimization, but in response to concrete pain (mobile team waiting on backend team to strip fields, or mobile payloads being too large).

## 8. Trade-offs (Be Opinionated)

### Benefits (Specific)

- **Centralized security surface.** Auth logic in one place = one place to audit, one place to patch. A JWT library vulnerability fix takes 1 deployment instead of N service deployments.
- **Latency reduction via aggregation.** BFF-style gateways reduce mobile page-load from 5-15 serial network calls (750ms+ on LTE) to 1 aggregated call (~175ms). That is a measurable 4x improvement for real users.
- **Developer velocity.** Adding rate limiting to a new service means one annotation in the gateway config, not implementing distributed counters in service code. This saves ~2-3 days per new service.
- **Observability.** All traffic passes through the gateway, so you get a canonical access log with consistent fields (request ID, user ID, service, latency, status) without each team implementing their own logging.
- **Protocol translation.** Gateway translates HTTP/JSON (what mobile clients speak) to gRPC (what internal services speak) without either side knowing.

### Costs & Limitations (Honest)

- **Added latency.** Even optimally configured, the gateway adds 2-5ms per request. At p99, Redis rate limit checks under contention can spike to 15-20ms.
- **Single point of failure.** If your gateway cluster goes down, everything goes down. You must run N >= 3 instances across availability zones and ensure the gateway is among the most battle-hardened pieces of your infrastructure.
- **Operational complexity.** Self-managed Kong requires Postgres (or Cassandra for large deployments), Kubernetes expertise, and an on-call rotation. AWS API Gateway eliminates this but costs $3.50 per million REST API calls — at 1B requests/month that is $3,500/month, and at 10B it is $35,000/month.
- **Configuration drift risk.** If routing config lives in the gateway database and gets out of sync with the actual service registry, requests route to dead instances. This requires a reconciliation process.
- **Gateway sprawl.** After solving the org-bottleneck problem by creating domain gateways, you now have N gateways, each needing upgrades, security patches, and on-call coverage.

### The Core Tension

**Centralization vs. autonomy.** The gateway's value comes from centralizing cross-cutting concerns. But centralization creates a team bottleneck (everyone needs the gateway team to add routes) and a blast-radius risk (one misconfiguration affects all services). The resolution is GitOps-based self-service: product teams own route config as code in their own repositories, the gateway team owns the plugin catalog and the fleet, and CI/CD merges route changes without manual intervention.

### My Recommendation

Use a gateway from day one if you have more than 2 external-facing services. Use Kong or APISIX on Kubernetes if you expect >100M requests/month within 18 months (managed gateway costs will hurt). Use AWS/Azure/GCP managed gateways if you are AWS/Azure/GCP native and expect to stay under 200M requests/month. Implement the BFF pattern only when you have concrete evidence that mobile and web payloads are diverging — not preemptively. Never build a custom gateway unless you have Netflix's scale and a dedicated 10-person platform team.

## 9. Failure Modes — What Goes Wrong

### Redis Rate Limiter Outage

**Trigger:** The Redis cluster used for distributed rate limiting becomes unavailable (network partition, Redis sentinel failover, OOM kill).

**Symptoms:** Operators see the gateway's error rate spike as rate limit checks fail. Depending on configuration: all requests are blocked (fail-closed) or all rate limits are bypassed (fail-open). If fail-open, a sudden thundering herd from one misbehaving client can saturate backend services.

**Detection:** Alert on `redis_connection_errors_total > 10` in 60 seconds. Also alert on `rate_limit_plugin_latency_p99 > 50ms` — Redis latency spike precedes an outage.

**Recovery:** Most gateways support a fallback mode: `error_handling: ignore` allows requests through when Redis is unavailable. This is acceptable for most rate limiting use cases (slightly more traffic than intended) but not for hard quota enforcement. For the latter, implement a local in-process fallback counter per gateway node that approximates limits.

**Real Example:** At a mid-size SaaS company (public post-mortem on Medium, 2023), a Redis Cluster primary election took 38 seconds due to a network partition. During this window, the Kong gateway's rate-limit plugin returned errors, causing Kong to block all requests (fail-closed default). The 38-second outage was entirely attributable to the gateway's interaction with Redis, not to any backend service failure.

---

### Route Misconfiguration — Routing to Dead or Wrong Service

**Trigger:** A deployment removes service instances without updating gateway routes, or a misconfigured route points to the wrong upstream (e.g., staging endpoint in production config, or a renamed service with no backward-compatible alias).

**Symptoms:** Users see 502 Bad Gateway or 503 Service Unavailable for a specific path. Other paths are unaffected. The error is not random — it consistently affects the same endpoints.

**Detection:** Monitor `upstream_connection_failures_total` per route. A sudden spike (>1% error rate on a specific route) with a corresponding deployment event in the audit log confirms a route misconfiguration. Synthetic monitoring (canary requests every 30 seconds to each critical route) catches this within one cycle.

**Recovery:** Roll back the gateway config change. If using GitOps (Kong Deck, APISIX YAML), `git revert` + CI pipeline redeploy takes 2-5 minutes. If config was applied manually via admin API, identify the last known good snapshot and reapply.

**Real Example:** Uber's Gen 2 gateway had incidents where service renames were not propagated to the gateway config atomically. A service team renamed their service from `trip-svc` to `rides-svc` and deployed the new name, but the gateway still routed `/api/v1/trips` to `trip-svc`. Requests failed for 4 minutes until the route was manually updated. This drove their investment in a config reconciliation pipeline.

---

### Gateway Becomes a CPU Bottleneck Under Cryptographic Load

**Trigger:** A surge in new TLS connections (e.g., a DDoS with connection flooding, or a major marketing event bringing millions of first-time users) exhausts CPU capacity on gateway instances because TLS handshakes are computationally expensive.

**Symptoms:** Gateway CPU hits 90-100%. New connection acceptance rate drops. Existing keep-alive connections continue to work — so users with established sessions are fine, but new users cannot connect. The load balancer in front of the gateway starts reporting 502s.

**Detection:** Alert on `gateway_cpu_usage > 85%` sustained for 60 seconds AND `tls_handshake_rate` spike. Use `ss -s` or `netstat` to see if SYN_RECV queue is overflowing.

**Recovery:** Scale out gateway instances (Kubernetes HPA should handle this within 60-90 seconds if configured). In the short term, enable TLS session resumption and TLS session tickets to reduce handshake computation for returning clients (cuts handshake CPU by ~80% for repeat visitors). For sustained DDoS, push TLS termination upstream to CDN (Cloudflare, CloudFront) which has far more TLS termination capacity.

**Real Example:** During a major product launch, a fintech company's Kong fleet was sized for steady-state traffic but not for the simultaneous connection burst of a viral marketing moment. All 5 gateway nodes hit 95% CPU within 90 seconds. The TLS handshake overhead was the dominant factor — actual request processing was trivial. They resolved it by terminating TLS at Cloudflare and passing HTTP/2 cleartext to the gateway fleet, permanently cutting gateway CPU for TLS by 60%.

---

### JWT Key Rotation Outage

**Trigger:** The identity provider rotates its JWT signing key. The gateway has a cached copy of the old public key. For a window of time (the cache TTL), the gateway rejects all valid tokens signed with the new key.

**Symptoms:** All authenticated endpoints return 401 Unauthorized. Unauthenticated endpoints are unaffected. The 401 rate spikes to 100% of authenticated traffic. Users see "session expired" or "unauthorized" errors.

**Detection:** Monitor `auth_failures_total` rate. A sudden step-function increase to near-100% of requests indicates a key rotation event, not individual token expiry. Compare with `identity_provider_key_version` metric if exposed.

**Recovery:** Force a JWKS cache refresh on all gateway instances (usually via admin API: `POST /cache/invalidate`). Set JWKS cache TTL to a maximum of 5 minutes — the standard recommendation. Implement JWKS cache warming: on startup, fetch fresh keys before serving traffic.

**Real Example:** A payment platform rotated their auth0 JWKS on a Sunday. Their gateway had a 24-hour JWKS cache TTL (incorrectly configured). All authenticated API calls returned 401 for 4 hours until the cache expired and refreshed. The fix took 30 seconds (cache invalidation via admin API) but was discovered by a customer support escalation, not monitoring. Post-incident: JWKS TTL reduced to 5 minutes, alert added for auth_failure_rate > 5%.

## 10. When To Use vs. When To Avoid

### Use When

✅ **You have more than 2-3 external-facing microservices** and are duplicating auth/rate-limiting code across them. The cross-cutting concern duplication cost exceeds the operational overhead of a gateway.

✅ **You serve multiple client types** (mobile, web, partner integrations, IoT) with different protocol or payload requirements. Protocol translation and payload transformation at the gateway is far cleaner than building it into each service.

✅ **You need a centralized, auditable security boundary.** Regulated industries (finance, healthcare) require a single place where all external traffic is authenticated, logged, and rate-limited. A gateway provides this. Individual service auth does not.

✅ **Your API has public third-party integrations.** API keys, OAuth flows, usage plans, developer portals, and per-key rate limiting are gateway-native features. Building this into application services is weeks of work that gateways provide out of the box.

✅ **You are doing canary deployments or A/B testing on API versions.** Gateways can route 5% of traffic to a new backend version while sending 95% to stable, with a configuration change and no code deploy.

### Do NOT Use When

❌ **You have a monolith or 1-2 services.** The operational overhead of managing a gateway cluster (Redis for rate limiting, etcd/Postgres for config, HA deployment) is not justified when you have one service. An nginx reverse proxy with basic config is sufficient and costs one engineer a day to set up.

❌ **All traffic is internal (east-west) between services.** East-west traffic belongs in a service mesh (mTLS, circuit breaking, retries). Routing all internal service calls through a central gateway creates a network hub-and-spoke latency penalty and a massive blast radius.

❌ **You need sub-millisecond overhead.** If your SLA requires p99 < 5ms end-to-end and your backends respond in 2ms, a gateway's 2-5ms overhead takes your entire p99 budget. In this case, consider sidecar-based auth or client-side service discovery with no intermediary gateway.

❌ **Your team has no one to operate it.** A self-managed Kong deployment requires Kubernetes expertise, Redis operations knowledge, and an on-call rotation. If you have a 3-person startup, use AWS API Gateway or Cloudflare API Gateway with zero infrastructure management. The cost is worth the ops savings.

### The #1 Mistake Engineers Make

⚠️ **Putting business logic into the gateway.** The gateway should enforce *policy* (auth, rate limiting, routing, transformation), not *business rules* (is this user allowed to view this specific resource, or has this promo code been used before?). When teams start adding business logic to gateway plugins, the gateway becomes a distributed monolith. Business logic belongs in the upstream services that own the relevant domain data. The gateway only knows: is this token valid? Is this client over its rate limit? Which service handles this route?

## 11. Interview Perspective

### Real Interview Question Phrasings

- "Design an API gateway for a ride-sharing application."
- "How would you handle rate limiting at scale across thousands of microservices?"
- "Netflix needs to serve 1,000 device types with different payload requirements. How do you design the API layer?"
- "Your API gateway is a single point of failure. How do you make it highly available?"
- "Walk me through what happens when a mobile client makes a request to your system, from the client to the database."
- "How would you implement the Backend for Frontend pattern?"
- "How do you handle API versioning when you have 50+ services?"

### What the Interviewer Evaluates

- Do you know that the gateway handles cross-cutting concerns, and can you name at least 4 of them?
- Do you recognize the gateway as a potential SPOF and immediately bring up HA strategies?
- Do you distinguish between north-south traffic (client → service, gateway's domain) and east-west traffic (service → service, service mesh's domain)?
- Can you discuss concrete trade-offs: managed vs. self-managed, centralized vs. domain gateways?
- Do you bring up failure modes proactively (Redis outage for rate limiting, JWT key rotation)?

### Questions YOU Ask Before Answering

These questions establish the design constraints and demonstrate senior thinking:

1. "Are we designing for external clients, internal services, or both?" (Scope)
2. "What is the expected RPS at peak? Do we have a known traffic pattern or is it bursty?" (Scale)
3. "Do we have regulatory requirements that mandate centralized auth logging?" (Compliance)
4. "Are all clients speaking the same protocol, or do we need protocol translation?" (Complexity)
5. "What is the team's operational maturity? Is self-managed Kubernetes in scope?" (Build vs. buy)

### Junior (L3-L4) Answer Example

> "An API gateway is a reverse proxy that sits in front of our microservices. It handles authentication — validating JWT tokens — and routes requests to the right service based on the URL path. It also handles rate limiting to prevent abuse. I would use something like Kong or AWS API Gateway. For high availability, I would run multiple gateway instances behind a load balancer."

This is correct and complete for L3-L4. It covers the core concerns, names real tools, and mentions HA. It lacks depth on failure modes, scale trade-offs, and operational considerations.

### Senior (L5) Answer Example

> "I would start by separating north-south from east-west concerns. The gateway handles external traffic — auth (JWT RS256 with JWKS caching), rate limiting (token bucket in Redis, per-client), routing, and TLS termination. East-west mTLS and circuit breaking belong in a service mesh.
>
> For the rate limiter, I'd use token bucket in Redis, executed as a Lua script atomically. Key is `ratelimit:{client_id}:{window}`. The failure mode: if Redis goes down, I configure fail-open with an in-process fallback counter to avoid gateway-induced outages.
>
> For HA, I run 3+ gateway nodes across AZs behind a cloud load balancer. The gateway is stateless (state lives in Redis and etcd). Deployments are rolling, health-check-gated.
>
> For tool choice: at current scale (1B requests/month), self-managed APISIX costs less than AWS API Gateway ($1M+ annual spend difference) but requires a 2-person platform team. I would start with AWS API Gateway and migrate at the cost inflection point."

This demonstrates production experience, failure mode thinking, and cost awareness — hallmarks of L5.

### Staff (L6+) Answer Example

Staff answers reframe the problem before solving it, surface organizational trade-offs, and introduce concepts the interviewer likely hasn't raised:

> "Before designing the gateway, I want to understand the organizational model. One fleet serving all teams creates a bottleneck — every new route or plugin change requires the platform team. At >50 services or >100 engineers, I would propose domain-oriented gateways aligned with business domains (Uber's DOMA approach), each owned by the relevant domain team with the platform team providing the plugin catalog and fleet template.
>
> On the technical side: the hardest problem is not the happy path but the failure modes at the intersection of the gateway and its dependencies. Rate limiting fails when Redis partitions. Auth fails when the JWKS cache is stale during key rotation. Route config gets stale when services are renamed without atomic gateway config updates. Each of these needs a circuit breaker or fallback strategy.
>
> For the BFF question — I would not start with BFF. I would start with a single gateway and a shared API. I would introduce BFFs only when I have concrete evidence of divergence: the mobile team is stripping 70% of the response payload, or the web team needs push notifications via WebSocket while mobile uses APNS. Premature BFF proliferation creates N codebases that all need to be kept in sync with backend service changes.
>
> On observability: every request through the gateway emits a structured log with request ID, user ID, upstream, status, and end-to-end latency. This log is the single source of truth for SLA measurement, capacity planning, and incident correlation. If the gateway doesn't emit this, you are flying blind."
